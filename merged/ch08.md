## 8.1 プロレタリア化 — 知を奪われる労働

第7章の最後で、読者は完成した実線パイプラインを手にした——検知から発火まで、監査と防腐と時間予算を備えた、本書の模範的な系。この章は、その系への**自己批判**から始まる。そしてこの章は全書で最も遅く書かれた章であるべきだったと、筆者は認める（遅すぎたのではない——意図的に最後に置いた。批判は、批判する対象を完成させてからでないと誠実にならないからだ）。ベルナール・スティグレール（Bernard Stiegler）の中心概念、**プロレタリア化（proletarisation）**を用いて、本書自身の発明品を裁く。

### プロレタリア化 — 知識の無産階級化

スティグレールの診断（『技術与時間』『知をいかに分けるか』ほか）を要約する。産業革命以降、労働者は**自らの労働の知識を失っていった**。熟練工の手と目と暗黙のルールは、工程分析・設計知識・機械への-objectivation（知識の機械への埋め込み）によって工程の外へ抽出され、資本の側に結晶した。労働者に残されたのは、結晶化した知識を**操作する**仕事——知識そのものを理解せず、結果だけを扱う操作。スティグレールはこれを賃労働者の「無産階級化」と呼ぶ。生産手段を失った古典的プロレタリアートに加えて、**知の手段を失ったプロレタリアート**——プロレタリア化とは、労働の知的内容の剥奪である。

重要なのは、スティグレールが剥奪を「悪意の計画」ではなく**技術系（technological system）の論理**として記述する点である。知識の外部化（外側記憶、third retention、→2.3）はそれ自体善であり、蓄積と協働を可能にする。だが外部化された知識は、**理解の回路を介さずに操作できる形で実装される傾向**を持つ——操作が理解より先に独立する。独立した操作は、やがて操作者を置き換える資格を持つようになる（操作者が理解していないなら、誰でも、何でも置ける）。この傾向の現在形の極点が、自動化と AI である。

### 技能を奪う経路の解剖 — 手動操縦の消滅から回復不能まで

設計者が最も信じたがらない経路を、実証済みの形で解剖する（航空業界の公開された論点の典型化）。第一段：**自動化が技能の使用頻度を下げる**（手動操縦のフライト時間の減少）。第二段：**使用頻度の低下が技能を退化させる**（→1.1 の暗黙知は使用によってのみ維持される——身体化された知は休めば失せる。2.3 の保持条件の身体版）。第三段：**退化した技能を持つ労働者が、自動化の知識を外部に置く**（オートマトンの挙動を理解しない運航者——理解の回路の切断）。第四段：**自動化が壊れたとき（障礙、→3.4）、回復に必要な技能が存在しない**（理解のない操作者は、操作の外へ出る能力を持たない）。第五段：**事故と調査が、さらに自動化を増やす**（人的誤りへの恐怖 → より完全な自動化 → 循環の閉鎖）。

第四段の構造に注目してほしい。**自動化は、自動化が守るべき状況の定義を狭める方向に最適化される**（守れない状況が起きる前に、その状況に入ることを禁止する——「夜間の手動移管」のような、自動化が嫌う境界条件そのものが運用から削られていく）。3.4 の障礙の更新循環（障礙は実例で更新される）が逆方向に回る——実例が起きなくなるので障礙が更新されず、体系は自分が守っている世界だけを見て、守っていない世界を存在しない世界として扱う（3.5 の bounded check の horizon の外が、運用の語彙からも消える）。

### 本書第7章の Autoパイプライン — 最大の危険装置の目録

自己批判を実行する。Tsurugi パイプライン（→7.6）が労働者から奪いうるものを、設計図から直接読み取る形での目録にする。

1. **状況分節の剥奪**：`correlate_thread` が「何が一つの状況か」を決める（→7.5）。現場の状況判断（1.2 の分節）は、スレッド相関の外部に追いやられる——「自分のラインの調子が悪い気がする」が、相関規則に載らないなら体系の外部の雑音になる。
2. **候補形成の剥奪**：`enabled_actions` と LLM 候補が皿を並べる（→7.3・7.4）。判断者の皿の外の見立て——現場の独創的な対処（RuleAdoption の coin-term、→7.1）——は、パイプラインの皿に載らないものは存在しないのと同じになる（→6.3 の frame_options の論点の労働者版）。
3. **説明の代行**：`why_action` の七要素が読める形で出る（→7.5）。読める説明は、理解を**代替**しうる。「理由は見えている」が「身体化された理解」を育てない——説明の消費（→5.2 の fluent な現前化の更新経路欠如、同じ病が労働の場に現れる）。
4. **承認の細分化**：time-boxed interrupt が判断の皿を小さな皿に分割する（→7.4）。小さな皿の選択の反復は、判断の訓練ではなく**判断の慣性**を育てる（8.4 で「承認ではなく再解釈」と呼ぶ問題の準備）。
5. **例外の Quarantine 化**：未知（`metallic-rattle`）が Quarantine に載る（→7.6 の10ステップ）。載ることは消去よりマシだが、**載ることと向き合うことは違う**——Quarantine が審議でなくバッチ処理で消えていくと、未知との遭遇が運用から消え、5.2 の聴取装置が労働者の手から離れる。

この目録は、第7章の設計が**失敗している**という告発ではない。同じ設計が、条件を変えると知の再分配の装置にもなる（次節）。告発の対象は設計の部品ではなく、部品が働く**方向の勾配**である——操作と理解の分離を助長する方向へ、完成度の高い系は自然に滑る（スティグレールの「自動化の論理」）。滑りを止める配線を設計に内蔵しない限り、本書の最良の章が本書の最悪の章になる。

```cypher
// deskilling-meter — プロレタリア化の計測(本書が自分の危険を検る計器)
// 指標1: 現場由来の RuleAdoption(coin-term) の件数低下トレンド → 状況語彙の生成が止まっている
MATCH (ra:RuleAdoption {act:'coin-term'})
WHERE ra.decider STARTS WITH 'P-'          // 現場 personnel が選定者
RETURN date.truncate('week', ra.at) AS week, count(ra) AS site_coinations
ORDER BY week DESC LIMIT 12;
// 指標2: 人間の判断(Decision)で、候補の外の選択肢が選ばれる率(dissent の実質性)。
// 候補内の選択しか起きていないなら、judgment は frame の内側のクリックに退化している。
MATCH (je:JudgmentEvent)-[:JUDGED_ON]->(eb:EvidenceBundle)
WITH je, eb, ANY(opt IN eb.frame_options WHERE opt = je.chosen) AS inside_frame
RETURN avg(toFloat(inside_frame)) AS frame_conformity;   // 1.0 に近いほど「皿の内側の機械」
// 指標3: 障礙の実例更新停止(自動化が守る世界の狭み、第四段の早期検出)。
MATCH (o:Obstacle) WHERE o.last_instance IS NULL OR o.last_instance < datetime() - duration('P180D')
RETURN count(o) AS stale_obstacles;
```

`frame_conformity` を本章の中心計器として置く。人間の判断が常に提示候補の内側から選ばれている率——1.0 に近づけば、人間の judgment は frame 内クリックに退化し、皿を作らない判断は存在しなくなる（5.3 の隠れ判断の完成形——frame-making への不服従が起きない世界）。これは**人間の側の指標ではなく設計の側の指標**である（人間を疑うのではなく、皿の作り方を測る——6.6 の四率が統治の健康を測ったのと同じ位置に、労働の健康を測る計器を置く）。

### 自動運転の比喩を止める — 「技能の消滅」が実務で起きる速さ

比喩的な議論を避けるため、実務の時間尺度を置く。技能退化的な現象は、航空のような10年単位ではなく、**知識労働では2〜3年で観測される**（コード生成 AI を使った新人の基礎技能の形成、ナビゲーション依存による空間知識の衰退、検索依存による出典追跡力の低下——公開された研究分野が既に形成されている）。よって本書の系が本番で動くようになってから、プロレタリア化の初期兆候（site_coinations の逓減、frame_conformity の上昇、stale_obstacles の増加）が現れるまで1〜2四半期という想定は、悲観ではなく保守的な見積もりである。計器の週次稼働（→4.6 の scorecard に本節の三指標を追加）が必須となる所以であり、本書が「動く哲学書」を自称する最終の理由はここにある——**この本が設計する系は、自分を疑う計器を毎日回すことでしか、善であり続けられない。**

### 個別化の装置へ — スティグレールの教育論と技術の二面性

プロレタリア化の診断は、スティグレールの思想の前半である。後半——**脱プロレタリア化の条件**——を置かないと、この節は悲観で終わってしまう。スティグレールの鍵概念は**個別化**（individuation）である。人間は技術（技術系＝milieux、環境媒 medium）の中で自己を個別化していく——言語・道具・教育制度・そして本書のグラフと UI は、人間を形作る環境である。技術系は人間を空洞化も育成もする。同じ third retention（→2.3）が、記憶の外注（プロレタリア化）にも、記憶の拡張（教育）にもなる。決定するのは、その技術系が**参加者の個別化を起すか、操作に固定するか**である。

スティグレールが挙げる脱プロレタリア化の三条件を、本書の設計語彙で受ける。

**条件一：知識の再分配（savoir partagé）**。結晶化した知識を、操作ではなく**制定**に使う権利——→8.2 の所有権四条約（語彙・規則・例外・自己履歴）がこれである。スティグレールの「知識の再分配」は、本書では条約の語で書ける（所有の条約がなければ再分配は美談で終わる）。
**条件二：個別化の媒（milieu）の設計**。教育・訓練・協働の技術系を、操作固定ではなく個別化起すように作る。本書の該当設計は三つ——drill level 4〜5 の `outside_frame` 要求（→8.6：皿の外を要求する訓練は個別化そのものである）、共観の見解併置（→8.3：統合されず並んだ見解の中で、各自の視点が自己形成する）、理由面板の辿れる根拠（→8.5：read ではなく再生への招待）。
**条件三：世代間継承の制度**（savoir-faire の伝承）。→終章の継承の回路（succession loop）と Aporia 台帳が、スティグレールの「世代間性」（génération des générations）の設計実装である。スティグレールは言う——プロレタリア化を終わらせる唯一の道は、知の継承の制度を作り直すことだ。制度を作り直さない技術進歩は、必ず無産階級化を再生産する。

```cypher
// individuation-meter — 個別化の媒として設計が機能しているかの計器
// 指標: 各 drill/共観/審議の参加者の『個別化の痕跡』— 参加後にその人が
// 新語(coin-term)・反論(Objection)・規則変更(RuleAdoption)を出したか。
MATCH (p:Person)-[:PARTICIPATED_IN]->(s:CoproSession)-[:ON]->(:Thread)
WHERE s.started > datetime() - duration('P1Q')
OPTIONAL MATCH (p)-[:AUTHORED]->(out) WHERE out:CQAmendment OR out:Objection
                                          OR out:RuleAdoption
RETURN p.person_id, count(DISTINCT s) AS sessions, count(DISTINCT out) AS outputs,
       CASE WHEN count(DISTINCT out) > 0 THEN 'individuating'
            ELSE 'milieu-not-sparking' END AS status;
// 読み: milieu-not-sparking の多い環境媒は、設計が存在しても個別化を
// 起していない——スティグレールの語で言えば、その UI はプロレタリア化の
// 温和な形態として機能している。
```

「milieu-not-sparking」という状態名を設計レビューの語彙に加えておく。存在するのに火をつけない環境——これが 8.1 冒頭の「同じ設計が方向の勾配で化ける」の測れる形である。drill を導入した、共観を制度化した、審議槽を作った——全部やったのに site_coinations が戻らないなら、勾配の方向が間違っている。原因は通常三つ——評価が繋いだ（腐敗三、→6.6）、席に座る者が固定された（歪の非対称、→6.2）、時間予算が与えられなかった（→8.2 条件三）。スティグレールの診断の最終的な教訓を一文で置いておく。**技術の善悪は、技術の属性ではなく、技術の配線と教育の制度の属性である。**本書は後者の設計本であり、だからこそ第八章で自らを裁く。

### 脱知識化の実測 — 三つの AI 支援の before/after

deskilling-meter（→前掲）の三照会を、三つの AI 支援実例の before/after として提示する（スティグレールの诊断を、現代の計測可能な形に翻訳する——数値はモデル例であり、実測様式は練習 1）。

| 支援 | before(site_coinations/季) | after | frame_conformity | 診断 |
|---|---|---|---|---|
| 音声→手順自動書き起こし(保全) | 7 → 2 | .82→.95 | 語の生成が消え、要約語が固定(=支援の語で現場が語り開始めた) |
| 故障诊断推薦(整备) | 9 → 6 | .71→.74 | 推薦外选択は生き残ったが推薦の adopt 後 effect 検証が未実施(=皿の外は残ったが判断が空洞) |
| 調書問答ボット(品質) | 4 → 4 | .63→.89 | 問答の引用率↑、引用後の co-rereading(→8.3 再現前化)ゼロ=read-only 化 |

三例の診断の語が 8.1 の中心である。例一は第三保持が**第二保持を置换**した形（現場が支援の語で語る=語彙の主权の移転、→8.2 条件一の喪失）。例二は皿の外が残っても effect 検証が無ければ空洞——**推薦の外を选べる自由と、选んだ後の検証が無ければ、自由は形式**（→7.3 の effect_verification が 8 章の労働の問題でもあること）。例三は引用による知の read-only 化——問答で引けるが再構成できない（→8.2 の制定権の喪失の初発形）。

三例に共通する処方の一つを先に置いておく——**支援の語彙を現場の語彙に強制しない**（音声書き起こしの要約語は候補であり正（master）ではない——site TBox に載る語は現場の署名で确定される、→2.4 の分類制定の級・→6.1 の条約の署名の方向）。AI 支援の設計命令文：「支援は現場の語を**輸入**として読み、現場の語を**輸出**に書かない（輸出は必ず現場の署名で正語彙になる）」——この非対称一条で、例一の病の半分は止められる。

### 個人の脱知識化セルフチェック — 六問

組織計器（→前掲の deskilling-meter）の前に、個人が四半期に一度自問する六問を置く（計器が個人を監視する構図を一度反転させる——8.2 の所有権の個人内側。答えは graph に書かず個人のメモで良い——**この六問だけは何度でも個人側に置かれる、8.3 聖域规則の個人版**）。

1. 今季、推薦なしで処理した作業を 3 件話せるか（皿の外の実感、→7.1）。話せない→推薦の外が個人レベルで消えている。
2. 推薦された手順で、**違うと分かっていながら**従ったことがあるか（従った場合の理由を話せるか——従う判断と流される判断の区別、→6.2 誠実性）。
3. 今季、自分の語で新しい区別を誰かに教えたか（site_coinations の個人読み、→1.1 補助覚知の伝达）。
4. 推薦の根拠（basis）を開いて見た件数は（basis を読まない承認は 8.4 の single_plate の個人読み）。
5. 自分の判断が退いた歴史（自己履歴の 4 条目）を訪問したか（→8.2 パネル）。訪問 0 なら所有の第四条約が個人で死んでいる。
6. 機械なしで 1 日作業したら何が起きるか、具体的な場面を 1 つ書けるか（→1.3 巴——現場の像が書ける人は現場に属している）。

六問は 6.6 の四つの腐敗の個人対応版でもある（1=討議の幽霊化、2=forced-consent、3=知識のインフレ、4=承認の空洞化、5=自己履歴の喪失、6=場の消滅）。個人の六問が組織の四列（8.1 計器）と**同じ名前で結んでいる**ことが、本書の計器設計の統一性である——個人が自問できないことを組織が計れる構造はない（計器が個人の語に落ちない限り、計器は外部からの監視として拒まれ、拒まれた計器は必ず空洞化する、6.6 の簿記の空洞化）。

### 実行練習

1. 上の三計器（site_coinations / frame_conformity / stale_obstacles）をあなたの現在の運用（AI 支援の有無を問わず）で1か月分測れる形に翻訳せよ（ノード名はあなたの語彙でよい）。現在値と傾向を書き、どれか一つでも退化方向なら、原因の設計箇所（7章のどの部品が勾配を作っているか）を特定せよ。
2. 自己批判目録の五項目を、あなたの組織の既存の自動化（RPA・承認フロー・ダッシュボード）に当てはめ、「操作が理解より先に独立している」実例を2つ見つけよ。それぞれについて、理解の回路を戻す最小配線（例：説明の消費でなく再構成を要求する手順）を1つ設計し、その配線が2.6 の何級の変更かを定めよ。
3. 第四段（回復不能）の早期検出として、「自動化が嫌う境界条件が運用から削られていく」実例をあなたの運用履歴から1つ掘れ（例：夜間の手動レビューがいつの間にか止まった）。削られた過程を履歴（2.5 の Commit / 会議록）で再構成し、復元するか放置かの決定を級つきで記録せよ（復元せぬ場合の E4 宣言文を添えること、→4.1）。

## 8.2 超克の条件 — 知の所有権を取り戻す設計

スティグレールのプロレタリア化は、運命ではなく**歴史的に起こったこと**であり、したがって設計で引き戻せる、と彼は書く（脱プロレタリア化の条件として、彼は教育—— savoir ではなく**savoir-faire と savoir-vivre の再生産**——を挙げる。技術系は知識を外部化してしまうが、同じ技術系は知識の再内在化（身体への戻し）の装置にもなりうる。決めるのは設計である）。この節では、その「装置への転化」の設計条件を三つ立てる。所有権の条約、理解を要求する UI、承認ではなく再解釈への参加。そして「わかっていて押すボタン」と「わからずに押すボタン」の設計差を、本書の語彙で精密にする——この二つのボタンの差は、全書の設計哲学が最も集約される試験管である。

### 条件一 — 知の所有権：条約としての変更に残す

プロレタリア化の本体は、知識の**所有権の移動**である（知識が資本側に結晶する、→8.1）。よって超克の第一条件は、技能の美化ではなく**所有権の条約化**である。本書の体系で、現場が所有しているものを点検する。

其一、**状況語彙の主権**：現場語彙（site TBox、→2.4）と TermMapping の締結権（→6.1 の条約貿易）。現場が自分の語で世界を記述する権利が条約で保障されているか、それとも正規語彙管理者の許可事項になっているか（→2.6 の名簿の運用版）。
其二、**規則選定の権利**：RuleAdoption の提案・実行権（→7.1）。現場が自分の手順を自分たちで変え、その変更が履歴代数に「現場の行為」として載るか、中央の承認の下請けになっているか。
其三、**例外との向き合い権**：Quarantine・障礙・TranslationFailure の審議席（→5.6・3.4・6.1）。未知が処理される会議に、未知を発見した者が座っているか（知識議席、→2.6）。
其四、**自己の判断の履歴へのアクセス権**：自分の JudgmentEvent・EvidenceBundle・decision log を、当人が閲覧・引用できるか（→5.1）。アクセス不能な自分の履歴は、所有されていない経験である——経験を所有しない者が更新経路（→5.1 の update_route）を引けるはずがない。

```cypher
// knowledge-ownership — 知の所有権の条約状態の監査(本書の憲法が現場の側から読めているか)
MATCH (c:ConstitutionClause) WHERE c.domain IN ['site-vocab','rule-adoption','exception-seat','own-history']
OPTIONAL MATCH (c)-[:GRANTS]->(ag:Agent {kind: 'human:field'})
OPTIONAL MATCH (c)-[:IMPLEMENTED_BY]->(t:PolicyTest)
RETURN c.clause_id, c.domain,
       CASE WHEN ag IS NULL THEN 'no-grant'        // 条約が存在しても現場に権を渡していない
            WHEN t  IS NULL THEN 'unimplemented'   // 渡した権の執行機構がない(→6.4 link check)
            ELSE 'granted-and-enforced' END AS status;
```

この監査が暴く典型の偽装を記しておく。**所有の偽装（grant without enforcement）**——「現場の裁量」が規程に書かれながら、執行機構（Rego・審議槽・計器）を持たない状態（→6.4 の `IMPLEMENTED_BY` 双方向監査の労働権版）。「現場で判断してください」と言いながら、判断の皿（frame_options）を中央が握り、例外の会議に現場の席がない構造は、所有の条約ではなく**責任の移譲**である——スティグレールの診断の統治版：知は中央に結晶し、労働には操作と責任だけが残る。

### 「わかっていて押す」と「わからずに押す」 — ボタン二つの設計差

本章の試験管に入る。両者は物理的に同一のボタンであり、設計差はボタンの周囲にしかない。差を四つの配線要素で定義する。

**(1) 根拠の再構成可能性**：押す前に、根拠を**読む**のではなく**辿れる**こと（→5.1 の revalidation_path、→7.5 の why_action 七要素）。読む説明は消費される（→8.1 の説明の代行）。辿れる根拠は、たどった者の判断材料になる——再検証が判断の構造に組み込まれている（実効的承認の定義、→5.1）。
**(2) 却下された選択肢の可視性**：皿に載らなかった選択肢と、その却下理由が見えること（→6.4 の missing、→8.5 で protocol に固定する「却下した選択肢」）。知らない却下は、知らない世界である。
**(3) 反証条件の宣言**：「このボタンが間違っているのは、どういう状況か」が先に書かれていること（→4.5 の反実仮想、→4.2 の falsifiable CQ の労働版）。反証条件を知る者は、状況が変わったらボタンを押さない——**押さない能力**が技能である（自動化が嫌う境界条件の保持、→8.1 第四段の解毒）。
**(4) 遅延の権利**：押さない時間を持てること（→7.4 time-boxed interrupt の人間側の裏面）。遅延の権利がない承認は、承認ではなく反射である。沈黙の猶予期間（→2.6・6.4 の retain）が、ここでは労働者の時間として機能する。

四配線のないボタンは、わからずに押すボタンである。四配線のあるボタンは、**理解を内蔵した行為**——savoir-faire の機械補助版——になる。スティグレールの転化（技術系をindividuation の装置へ）の設計形が、この四配線である。

```python
# reason_panel.py — 「わかっていて押す」ボタンの背面(UI 状態機械の設計契約)
# 8.5 の対話プロトコルの proto としてここで宣言する(実装完成は 8.5)。
from pydantic import BaseModel, field_validator

class ActionOffer(BaseModel):
    action_id: str                       # 何を押すか
    basis_trace: str                     # (1) 根拠: why_action 七要素への参照(辿れる形)
    rejected_options: list[dict]         # (2) 却下選択肢+理由(知らない却下を作らない)
    falsifiable_if: list[str]            # (3) 反証条件:「もしXならこれは誤り」(先に宣言)
    hold_seconds: int                    # (4) 遅延の権利: 最低保持時間(即決を強制しない)
    @field_validator("falsifiable_if")
    @classmethod
    def must_be_concrete(cls, v):
        # 反証条件は機械照会可能な形で少なくとも1つ含む(→4.2 の falsifiability 継承)。
        # 「状況を見て判断」は反証条件ではない=この field 自体が契約違反の宣言。
        if not any("where:" in s or "if:" in s or "query:" in s for s in v):
            raise ValueError("falsifiable_if must contain machine-checkable clause")
        return v
```

`hold_seconds` の最低保持時間を契約に置くことの意義を論じておく。「即時承認ボタン」の文化は、即決を美徳として労働から遅延の権利を奪う（→8.1 承認の細分化の第四項）。最低保持時間は、**即決を不可能にすることで理解を強制する**のではなく、即決を**選択 가능한**ものにする——理解して押すのと、急がれて押すのを、履歴が区別できるようになる（即決が選べることと即決を強制されることは違い、履歴が選べることを作ると、即決の頻度が個人ではなく設計の指標になる——scorecard の「即決率」は現場を疑う数値ではなく、皿の設計を疑う数値である、6.6 の四率と同じ使い方）。

### 承認ではなく再解釈へ — 労働の知的内容の回復

超克の第二条件を定義する。労働者をシステムの**承認者**として扱う限り、プロレタリア化は残る——承認は操作の完成形で、知的内容を持たない（「わからずに押せる承認」が設計上可能なら、それは承認という名の操作である）。労働に知的内容を取り戻すとは、労働を**再解釈（reinterpretation）**の循環に参加させることである。本書の体系で再解釈の席は既に全部ある。CQAmendment の提出（問いの書き換え、→4.2）、TermMapping 改訂（語の条約の書き換え、→6.1）、RuleAdoption（規則の選定・生成、→7.1）、障礙の更新（障礙台帳への新実例の記入、→3.4）、Quarantine の審議（未知との対話、→5.6）、decision log への dissent（方針への不服従、→6.2）。

これらの席に**誰が座っているか**の監査が、この節の最終器具である。席の空席率・席の出席者の職層分布・提出物の職層別件数（→2.6 の知識議席の統計を労働権の監査に転用する）。再解釈の席が専門職と管理者で埋まり、現場の提出がゼロの会議は、スティグレールの語で言えば**知の再分配が起きない議場**であり、そこにどれだけ形式が揃っていても、プロレタリア化は進行し続ける。

### 条件三 — 再解釈の労働を労働として認める

最後に、設計の外側の条約を置いておかねばならない（本書の哲学は組織条約に橋を架けることを恐れない）。再解釈（CQ 改訂、TermMapping 提案、障礙記入、dissent の作成）は**時間のかかる労働**である。それを「協力の善意」に依存させた制度は、必ず疲弊して形式化する（→2.3 の制度の老化——善意は保持されない、配管だけが保持される）。よって再解釈は**業務時間として予算化**され、**評価対象ではなく参加頻度・質の統計が統治の計器**に接続される（6.6 条約G-1 の労働版：再解釈の統計を個人評价に使うと、提出物は評価向けの文書化に退化し、意味の流通が死ぬ——腐敗三の労働版）。再解釈の労働の予算と、評価からの隔離。この二つの条約なしに、本章の UI 設計は善意の搾取の精巧な顔になる。

### 所有権の歴史 — 条約が結ばれ、奪われ、取り戻された実例

所有権の設計（→条件一）を、歴史的実例の縮約で検収する。三例を、本書の簿記語彙（Commit・審議槽・級）で読み替えて置く。

**例一：工程分析の時代（1910s-）**。タイラー制の下で、職人の暗黙の手順が秒時計で分解され、**計画部門**に書き写された。本書の語で書けば——site TBox の語彙（手の動き・段取りの暗黙）が master 側に copy され、TermMapping の締結権が計画部門単独になった（→2.6 の級が一方的に L3 に固定され、現場に不服従の通路がなかった）。結果は 8.1 の第四段の原型——手順を知るのは計画部門、手順を遂行するのは作業員、異常時の回復能力が現場から消えた。
**例二：コードの時代（1980s-）**。現場の段取り知識が MES・ERP のパラメータに結晶し、パラメータ設定権がベンダーと本社 IT に移った。条約の外部化——mapping の v1 がベンダーの標準マスタで固定され、site 側の変更は「チケット」扱い（不服従の通路がベンダーの SLA に吸収された、→6.1 の条約貿易の非対称）。現場はマスタ語彙に自分を翻訳し始め、現場語彙で報告することが減った——site_coinations の逓減の歴史的実例（→8.1 計器）。
**例三：プラットフォームの時代（2010s-）**。ワークフロー SaaS・AI 支援の標準語彙が現場の下に敷かれ、**翻訳の失敗が現場の責任になる**（input を「正しく入力できていない」と返される）。TranslationFailure が現場に押し戻される——残余の私有化（→2.1 の残余条約の反転：条約の失敗が現場の失敗として登記される）。

三例から取り出す設計教訓は一つ——**所有権の移動は常に「技術の導入」ではなく「条約の締結方法の変更」として起きる**。よって防衛点は技術の選択（使う/使わない）ではなく、締結方法の条約化（級・署名・不服従・落日・審議席）に置かれる（→2.6 の設計が、8章の労働の章で歴史的に裏打ちされる）。

`knowledge-ownership` 監査（→前掲）に第四の domain を足しておく。**mapping-initiative**——条約の**新設**を現場から発火できるか（変更への不服従だけでなく、条約そのものを現場が結べるか、L0 級の提案権）。歴史上の奪取はすべて、変更権でなく**新設権の独占**から起きている（標準マスタの初版を誰が書くか——初版を書いた者が後の争いで有利に立つ、→4.3 の retrofit でレガシーの CQ を逆抽出する意義が、所有権の文脈で再び現れる：あなたの現場の暗黙の条約を、あなたの語で最初に登記できるのはあなたである）。

### 自己履歴パネル — 「自分が何に同意してきたか」の画面仕様

知の所有権第四条約「自己履歴アクセス権」（→前掲）の UI 実装を、この節の缔びに仕様で置く。自己履歴パネルは、その人が登記した全 JudgmentEvent・同意・异議・選定と、**その後何が起きたか**（effect_verification 結果、→7.3・下位规則の改訂・Objection による退き、→8.4）を并べ表示する単一画面である。仕様六条。

1. **時系と因果の二列并記**——左列に自分の登記（同意/异議/选定）、右列にその登記の結果（稼働・退却・変更）。因果辺（`LED_TO`）が機械で引けるものだけ結ぶ（相関と因果の区別を UI が偽らない——→4.4 証拠条約·→8.5 counterfactual_link の表示形）。
2. **退いたものの表示**——落日・retire・demote（→7.6）で消えた条目も履歴に残る（消された同意の履歴が、同意の重みをその人に教える）。
3. **引用可能**——各行に graph:// URI（→1.4）。会議で「私は以前これに同意した」と証明として出せる（所有の第四条約が「見られる」でなく「使える」であることを仕様が担保）。
4. **异議の成功率**——自分の异議が解決・规則変更に至った率と、至らなかった路径の表示（自分の発言の力を測る——発言のコストの実感校准、→6.2 の歪の是正）。
5. **KPI 禁止条項の明示**——このパネルを人事評价に使う設定を config で禁止（`kpi_use: forbidden`、→8.3 聖域规則の UI 版——計測が名誉と処罰に化ける腐敗の入口、→6.6）。
6. **導出**——1 行 CSV 導出可（個人の学习日記への供給——所有の「所有」は外へ持ち出せることを含む、→8.1 個別化の装置）。

パネルの哲学の一文——**自己履歴を見せない組織は、成員に自分の判断の重みを計測できなくする**。重みを測れない判断は重くない（→8.4 の退化の個人内側——single_plate_rate が組織の統計なら、自己履歴パネルはその個人の実感器である）。所有権の四条約が最後に达成されるのは、条約の文でなくこの画面の前で、その人が「これは私の同意の履歴だ」と言う時である。

### 知の所有権監査の実行記録 — 四半期レポートの雛形

所有権四条約（→前掲）の監査は、四半期レポートの定型形を持つまで設計しないと儀礼化する（儀礼化した監査=形式のみの中身空洞、→6.6 腐敗三）。レポート雛形を置く。

```
knowledge-ownership quarterly report(雛形)
D1 site-vocab: 季の新规語 n 件 / master 反映 m 件 / 反映待ち最長日数 k
   → 判定: 反映率 m/n、k>90 日なら site 語の主権が条約上の数字のみ(実行が止まっている)
D2 rule-adoption: 季の RuleAdoption 現場署名比率 / 本社起草の比率
   → 判定: 起草比率の逆転(現場署名<起草)は「規則が現場に書かれない」=8.1 の四段
D3 exception-seat: 例外の席の空席日数合計 / 席に座った人の職層分布(→6.2 歪其一)
   → 判定: 空席=例外の処理が条約の裏(影子 act)で回っている証拠(→6.6)
D4 own-history: 自己履歴パネルの訪問数 / 導出数(→前掲 UI 仕様)
   → 判定: 訪問ゼロ四半期=条約は条文で画面は死んでいる=4 条約の 4 本目が空洞
付録: 各判定の graph:// URI と run 時刻(レポート自体が E1 実測級の証拠でなければならない)
```

「付録」の一行が雛形の中心である——**監査レポート自らが検証可能な証拠でなければならない**（→4.1 の級·→4.4 の証拠条約の統治文書版。「監査しました」の文書に URI が無ければ、その監査は L0 の発言であり E1 の実測ではない——発言級と実測級の混同を文書が防ぐ）。

四条約のうち D4（自己履歴）だけ訪問数で測れる——D1〜D3 は**比率と空席**で測える。四本を并べた四半期グラフが、スティグレールの诊断（→8.1）の組織脳波である。脳波が四条全部平たんになった組織は、知の所有権が条約ファイルに残骸として存在している（条約が生きているか死んでいるかの判定は、永遠にこの四列でしか出ない——出さない組織は、所有権について論じる資格を持たない、→6.6 統計が燃料でなくなる形態の 8 章版）。

### 実行練習

1. `knowledge-ownership` 監査を自分の組織で実行できる形に翻訳し（四条約 domain をあなたの規程・配線に読み替え）、四 domain の status を判定せよ。「no-grant」「unimplemented」のどれか1つを選び、その条約の最小の実装（執行機構）を1つ設計して 2.6 の級と審議槽を定めよ。
2. あなたの承認 UI（承認フロー・ダッシュボード・レビュー）を四配線（再構成可能性／却下可視性／反証条件／遅延の権利）で診断し、最も欠けている配線を1つ選んで `ActionOffer` 型で実装せよ（既存の承認に falsifiable_if を1項目つける改造でよい）。改造後の「即決率」が何 measured するかを1段落で定義し直し、scorecard 項目に加える級を決めよ。
3. 再解釈の席の職層分布を1か月分集計せよ（CQ 改訂・手順変更・例外会議の出席と提出物）。現場の提出がゼロまたは年1件の場合、原因を「意識」「忙しい」でなく**配線の欠落**（席がない／時間がない／提出が無意味だった履歴）として特定し、三つのうち最も効く欠落に予算（人時）を配る条約案を1ページ書く——予算の原資はどの会議から削るかまで書くこと。

## 8.3 共同化への逆流 — 暗黙知へ戻る設計

8.1 が系を裁き、8.2 が所有権と理解の配線を戻した。この節から本章の建設が始まる——**暗黙知への逆流**を設計に組み戻す。供給源は野中郁次郎（Nonaka）の SECI 知識変換モデルである（『組織知識創成論』1995、野中&竹内）。本書は第1部で外化（tacit → explicit、→1.4・4.2 の CQ・1.3 の context graph）を、第2部で結合（explicit → explicit、→2.5 の履歴代数・4.3 の retrofit）を、第5・7章で内面化（explicit → tacit、→5.2 の現前化と更新経路）を、すでに設計してきた。SECI の四つ目の環——**共同化（Socialization、tacit → tacit）**——だけが、これまで一度も設計されていない。暗黙知から暗黙知へ、身体と共同注意を通じて直接流れる知。形式化の果ての章が、あえて**形式化されない知への逆流**を設計する。逆説ではない——共同化は形式化できないが、**共同化の場所・時間・条件は設計できる**。設計すべきは知そのものではなく、知が流れるための空隙なのである。

### SECI の四環と、本書が置いてきた環

SECI の四環を本書の到達点と対応させて確認する。**外化**：暗黙知をことば・図・制度へ引き出す（本書の CQ、context graph、EARS——→4.2・1.4・3.3）。**結合**：形式化された知を結合・伝達する（グラフ横断照会、履歴代数、RDF ブリッジ——→1.3・2.5）。**内面化**：形式知を身体に落とし込み技能へ戻す（反復・練習・更新経路——→5.1 の「経験が主体を変える」、7.2 の現場周期の実測）。そして**共同化**：共に居て、同じものを見て、互いの暗黙知を伝導する——師匠の手元を見る、夕方の雑談で「あの音、変だったろ」が共有される、先輩の沈黙の聞き方を真似る。野中の指摘で重要なのは、共同化が知識創出の**発火点**である多いこと（外化の多くは、共同化の中で温められた共有暗黙知から生まれる——「暗黙知の交配」）。本書の体系は外化以降の環を豊かに持っていて、この発火点の配管を**ゼロから設計していない**。8.1 の計器（site_coinations の逓減）が測っていたのは、まさにこの環の供血不足であった。

### 共観（joint attention）— 状況の共同閲覧の設計

共同化の第一条件は、同じものを**同じ時に**見ていること——共同注意（joint attention）である。設計名を**共観**として置く。共観はダッシュボードの共有ではない（非同期の閲覧は結合であって共同化ではない——同時性与共同性が必須）。設計要素三つ。

其一、**共観セッション**：同じ状況スレッド（→7.5 の thread）を、2〜4人の人間が同一時間で閲覧する場。画面は同一の `situation_digest` を提示し、各人の注釈が時間軸に並ぶ。其二、**見解の併置**：注釈は投票・統合・多数決されない——**並んだまま**保存される（confluence of disagreement）。其三、**沈黙の保持**：セッションにはコメントしない権利があり、無言の参加も参加として記録される（誰がそこに居たか、が記録され、発言しない人の注視時間は残る——→8.5 の「無応答は沈黙の同意ではない」とは別の、**沈黙そのものの価値**）。

```cypher
// copresence — 共観セッションの記録: 暗黙知の発火場所の地誌
CREATE (s:CoproSession {s_id:$id, thread_ref:$thread, started:datetime(),
          duration_min:$min, modality:'same-time'});   // 同時性必須(非同期は別種 Session)
// 参加: 発言しなかった者も参加者として登録(沈黙は記録される、→1.6 の設計の反転使用)
UNWIND $attendees AS a
CREATE (p:Person {person_id:a})-[:PRESENT_IN {spoke:a IN $speakers}]->(s);
// 見解の併置: 統合しない。contradiction は異常ではなく資産。
CREATE (v1:Viewpoint {body:$v1, author:$a1, at:datetime()})-[:ON]->(s),
       (v2:Viewpoint {body:$v2, author:$a2, at:datetime()})-[:ON]->(s),
       (v1)-[:COEXISTS_WITH]->(v2);
// 集計(8.1 の計器の解毒回路): 共観の密度 → 数週後の site_coinations の先行指標
MATCH (s:CoproSession) WHERE s.started > datetime() - duration('P8W')
RETURN date.truncate('week', s.started) AS w, count(s) AS copresence_rate
ORDER BY w;
```

`(v1)-[:COEXISTS_WITH]->(v2)` を統合辺ではなく併存辺として置くのが共同化設計の核心である。見解の統合（多数決・AI 要約・「結論」化）は、その瞬間に**共同化を終了させ結合へ移す**（→4.5 の LLM 要約の現前化代行の危険と同じ構造——統合は消費である）。併存は、矛盾した見解が並んだまま残ることで、後の共観・後の議論・後の夜の実践で再び発火しうる（SECI の螺旋——共同化が外化を孵し、外化が結合を経て内面化され、内面化が新たな共同化の場を育てる。螺旋の第一環が、この併存の庫である）。

### 沈黙の設計 — 「記録しないこと」の避難所

第1.6節で敷設した NonRecordingRule（記録しないことの設計）が、ここで本来的な使われ方をする。暗黙知の避難所——**形式化の網から意図的に外された領域**を設計に設けること。理由は、暗黙知が形式化されるたびに何かを失うこと（1.2 の残余の定理）、そして暗黙知が避難所なしには存在し続ける場を持てないことである。現場の雑談、休憩時間の「あれどうなった？」、師匠の手元を黙って見る時間——これらが記録・可視化・KPI 化された瞬間、それは暗黙知ではなく形式知の模写に変わる（観察可能になった暗黙知は、観察される振る舞いに自己適応してしまう——測定される行為は測定用に変わる、→6.6 指標の武器化の身体版）。

避難所の設計 three 条。**其一、共観の無記録部分**：共観セッションの記録は「誰がいつそこにいたか＋併置された見解」までで、**視線・間の長さ・言わなかった言葉は記録しない**（記録しないことを記録する設計の完了、→1.6）。**其二、雑談領域**：業務チャネルと分離された、検索索引外・監査ログ外の領域（監査不能領域を置くことの統治的条件は 6.6 の条約で既に作ってある——防腐層の計器が届かない場所を条約で宣言する。宣言された避難所は無法地帯ではなく、**条約で守られた空地**である）。**其三、師弟の共働時間**：共観と実作業が重なる時間帯（先輩の作業を新人が黙って見る）。これは共観セッションとは別種の Copresence（`modality:'working-together'`）で記録され、記録されるのは**場の存在と参加と長さだけ**である——内容の記録は不在こそが設計である。

```rego
# policy/sanctuary.rego — 避難所への監視の侵入を止める門(8.3 の防腐条約)
package execphil.sanctuary
default allow = false
# 雑談領域・共観の無記録部分への「索引付け」「KPI抽出」は不許可。
# 抽出バッチの actor が sanctuary スペースを read 対象に含む場合、plan 段で拒否(→6.4 二重防御)。
allow_read { input.actor IN ["person:", "copresence-ui"] 
             startswith(input.scope, "copresence://") }
deny { input.actor IN ["indexing-batch", "kpi-extract", "vendor-analytics"] }
# 避難所の空地は監査ログに『空地として』のみ現れる(何があったかは現れない)。
# 空地の存在自体の監査=空地が縮小されていないかの監視(空地縮小=L2 事件)。
```

`deny` が自社の分析バッチにまで向いている点に注目してほしい。避難所の最大の侵食者は外部の悪意ではなく、**内側の善意の分析**である（「雑談のテキスト解析でリスク検知！」は有用そうに見えて、暗黙知の生態系を殺す——検知に使えるのは暗黙知が形式化された後だけであり、形式化前の暗黙知は避難所でしか育たない。8.1 第四段の逆転：避難所を失った系は、未知が育つ前に未知を見る能力を失う）。

### 共同化の計器 — 逆流の流量

8.1 の三計器（site_coinations / frame_conformity / stale_obstacles）は、逆流の**滞り**を測るものであった。共観設計には**流量**の計器が必要である。共観密度（週あたり CoproSession・参加延べ人数・参加の職層混合度）、見解併置数（COEXISTS_WITH 辺）、共働時間（working-together の合計長）。これらの数値の使い方の条約を 6.6 条約G-1 で先回りしてある（**個人ではなく系の流量として読む**——共観数が個人の KPI になった瞬間、共観は会議に化けて共同化は死ぬ。場の数を測り、中身を測らない）。

流量がゼロに近づく場所を、設計は知っている。形式化の収奪が強い場所——完全な監査ログ、完全な承認フロー、完全な可視化の近くほど、共観は細る（見られている場では人は沈黙を共有しない）。よって共観密度と形式化密度（decision log 件数・承認フロー件数の密度）を併記した地図——**体系の暗部地図**——を四半期ごとに描く。本書の理想は暗部ゼロではない。**暗部と明部の境界が条約で引かれ、暗部が条約で守られていること**である（1.6 の「記録しないことを記録する」の系図は、ここで組織スケールの地図になって閉じる）。

### 師弟の設計 — 暗黙知の伝承を業務時間として実装する

共同化の最も古い形は師弟である（弟子が師匠の手元を見て、真似て、黙って時を積む）。本書の体系はこの形を業務時間に組み戻す設計を置いていないと、8.3 の他のどの設計よりも早く予算会議で削られる。師弟設計を三要素で確定する。**其一、共働の時間割**——師匠の作業に弟子が随伴する時間（`modality:'working-together'` の Copresence、→前掲）を週次で固定し、この時間は生産時間ではなく**移転時間**として会計上区別する（移転時間の計上——知識労働の会計が「成果」しか載せないとき、伝承は常に名目上の仕事になる、→8.2 条件三）。**其二、随伴の非評価性**——随伴時間と弟子の産出を対応付けない（対応付けは即座に「見せるための作業」を生む——2.6 の処罰と名誉の条件の師弟版）。**其三、随伴の反転**——弟子が師匠に随伴するだけでなく、師匠が弟子の作業に随伴する設計（師匠の暗黙知が弟子の新語で更新される回路——site_coinations の供給者は師匠ではなく弟子であることが多い、→8.1 計器の読み）。

```cypher
// apprenticeship-ledger — 師弟の帳簿(伝承の流量計測・評価分離条約つき)
MATCH (s:Person {role:'master'})-[w:COWORK]-((d:Person {role:'apprentice'}))
WHERE w.started > datetime() - duration('P1Q')
WITH d, s, sum(w.hours) AS hours, collect(DISTINCT w.thread) AS threads
OPTIONAL MATCH (d)-[:AUTHORED]->(out) WHERE out:TermMappingProposal OR out:RuleAdoption
WITH d, s, hours, threads, count(out) AS apprentice_outputs
RETURN d.person_id, s.person_id, hours, apprentice_outputs,
       CASE WHEN hours < 4 THEN 'no-transfer-time'      // 帳簿上の随伴が実体ゼロ
            ELSE 'alive' END AS status;
// 読み: hours が低ければ伝承は予算化されていない(=存在しない)。
// apprentice_outputs が 0 なら随伴は形式で、暗黙知の更新は起きていない。
```

随伴の記録が thread（スレッド、→7.5 の状況の相関 ID）に紐づくことに注意せよ。師弟は抽象的な人間関係ではなく、**特定の状況連鎖への共同随伴**である——同一の障害・同一のライン・同一の変更（Commit、→2.5）に一上にに居ることが記録される。これにより、共観（→8.3 の同時閲覧）が事後の振り返りだとすれば、随伴は**状況の最中の共同注意**であり、暗黙知の伝導はここで最も濃く起きる（1.1 の補助覚知の伝承は、言語化の前の共同注意で起きる——ポランニーの「模倣による学習」の実装）。師弟の帳簿が示すもう一つの計器は `no-transfer-time` の分布である——随伴が計上されない部署は、暗黙知の再生産が止まっている部署であり、そこでは形式知の文書だけが増えていく（増える文書・細る伝承——知識のインフレはいつも、この分布から予見される）。

最後に、師弟設計への最頻の反論を潰しておく。「師匠が忙しい」。その通りで、だからこそ師弟は**善意ではなく会計**で守られる（→8.2 条件三）。移転時間という勘定科目を作り、随伴時間を成果評価から隔離し、師匠の随伴時間を成果指標の分子に載せる（分子に載る時、時間は実在する——→4.1 の宣言と実測の設計版）。この三つの会計設計を置かずに「メンター制度」を立ち上げる組織は、スティグレールの予言を自腹で証明する実験を毎期行っていることになる。

### 誰と見るか — 共在の割り当てと「見方が違う人」を選ぶ算法

8.3 の共観（CoproSession・COEXISTS_WITH、→前掲）は、「誰と共在するか」の割り当てが設計されていなければ、席の空いた会議になる。割り当ての原則を三条置く。**其一、見解の距離**——COEXISTS_WITH の辺に付与された viewpoint の標签（現場・保全・品質・安全・外部請負）の組み合回数を台帳化し、**共在経験の最も遠い pair を優先**に共在セッションを組む（遠い人と同じものを見る——Nonaka の externalization が最も摩擦を生む場所であり、摩擦は知識の入口、→1.1 の暗黙知が現れるのは言叶が合わない時）。**其二、歴史の接触**——自己の判断の結果（→8.2 パネル）を他人が見に来る相手を、LED_TO のグラフから自動推薦（「あなたの同意が変えた规則を、その规則で作業する人が見たいと言っている」——見解の接触を抽象の共在でなく因果の共在にする）。**其三、周期の同席**——落日審議・障礙審議（→3.4）に出席歴史のない人を自動で1名招待（参加資格は級でなく抽签——L0 の発言級が出席級と一致する設計、→2.6）。

```cypher
// co-presence-pairing — 見解距離による共在の推薦(月次)
MATCH (a:Person)-[:HOLDS_VIEWPOINT]->(va), (b:Person)-[:HOLDS_VIEWPOINT]->(vb)
WHERE a <> b AND va <> vb AND NOT ((a)-[:COWORK]-(b))
WITH a, b, va, vb,
     size([(a)-[:PARTICIPATED_IN]->(:Thread)<-[:PARTICIPATED_IN]-(b)]) AS shared
WHERE shared = 0   // 接触歴史ゼロ=最も遠い pair
RETURN a.person_id, va.tag, b.person_id, vb.tag
ORDER BY rand() LIMIT 4;   // 推薦(強制しない)——共在は自由でなければならない
```

`rand()` と「推薦」の明記を重要として置く。割り当て算法が共在を**強制**した瞬間、共在は劳動になり、聖域规則（→前掲:copresence に KPI を繋がない）が算法によって内側から破られる。算法は招待まで、受容は人間の自由——**暗黙知の場は、強要された席では開かない**（1.3 の巴——場所は開かれるもので、設置されるものではない。設置できるのは招待と時間と評价の排除まで、→8.2 条件三の時間予算が共在の物質条件）。

### 実行練習

1. あなたの現場で最後に「共に同じものを見て、言葉にならないものを共有した」瞬間を1つ思い出し、その条件（場所・時間・人数・記録の有無）を分解せよ。分解した条件のうち、8.3 の三要素（同時性・併置・沈黙）に対応しているものを特定し、残る欠落から共観セッションの最小設計（1スレッド2人15分）を1つ立てて試行せよ。
2. `sanctuary.rego` をあなたの分析基盤（BI・ログ解析・検索索引）に当て、現在の「善意の分析」が避難所を持つデータ（会話ログ・メモ・チャネル）に既に触っていないかを監査せよ。触っている実例を1件特定し、索引外し（条約G の労働版）の級と移行期間（→2.6 沈黙の猶予の類推）を決め、現場への告知文を100字で書け。
3. 暗部地図をあなたの業務領域で1枚描け（横軸に形式化密度＝承認件数・監査ログ密度、縦軸に共観密度＝雑談・同席・合同巡回の実測推定）。暗部が最も細っている領域について、それは「管理が行き届いた良い領域」か「未知が育っていない危険領域」かを両論書き、8.1 第四段（回復不能）の観点で最終判定と級つき対処案を出せ。

## 8.4 Human-in-the-Loop — 自動化ではなく増幅化

共観と避難所——形式化の外側の設計を置いた（→8.3）。この節からは形式化の内側に戻り、**人間をどこに、どういう扱いで置くか**を設計する。Human-in-the-Loop（HITL）は昨今、AI 系の常套句になっている——「人間の承認を入れる」「ラベル付けに人間を使う」「human-on-the-loop」。本書はこれらの使用法を三類型に分解し、そのうち二つがプロレタリア化の続きであることを示し（→8.1）、第三の類型——**共創**——だけを本書の設計に採用する。節の標題の対立語組は重要で、「自動化（automation）」に対して本書が選ぶのは「増幅化（amplification）」である——機械が人間の代わりに行為するのではなく、機械が人間の行為の質と速さと射程を伸ばす配線へ、判断の連鎖を組み替える。

### HITL の三類型 — 承認・介入・共創

**類型一：承認（approval）**。機械が行為し、人間が事前または事後に可否を署名する。本書の語で言えば、人間は JudgmentEvent の decider として登記される——ただし内容形成（frame）が機械にあるなら、5.3 の隠れ判断と見せかけ承認の連鎖である（→5.1 の実効的承認の再検証可能性を満たさない署名）。承認類型の労働者は、8.2 の「わからずに押すボタン」の番人になる。
**類型二：介入（intervention）**。機械が行為し、人間は壊れたとき・危ういときに割り込む（フェイルセーフの人間版、on-the-loop）。人間の労働は**例外処理**に限定される——正常運用は機械、異常時に人間。一見安全だが、8.1 の第四段（自動化が壊れたとき回復できる人間がいない）をそのまま再生産する：例外しか経験していない労働者に、例外の意味を理解している保証はない（例外の経験は、正常の理解の上にのみ立てられる——1.1 の暗黙知は正常運用の身体化であり、正常から人間を退かせば暗黙知は育たない）。
**類型三：共創（co-creation）**。機械と人間が**同じ作業の異なる局面を分担し、互いの出力が互いの次入力になる**循環。機械は候補・根拠・却下・反証条件を供給し（→7.3・8.2 の ActionOffer）、人間は再解釈・新語・障礙記入・不服従で供給に応え（→8.2 の再解釈の席）、その応えが機械の次の皿と規則を更新する（→7.1 の RuleAdoption、→4.2 の CQAmendment）。共創の本質は、**人間の出力が機械の訓練データではなく、機械の憲法の一部になる**ことにある——人間がやるのはラベル付け（機械の改善の手伝い）ではなく、規則と語彙の選定（系の統治への参加）である。

三類型の判別試験を一つ置く。**人間の応答がモデルの学習データにのみ流れ、系の規則（Rego・shape・TermMapping・goal form）に流れないなら、それは共創ではなく類型一または二である**（→5.1 の update_route の所在が主体外へ流出している状態——5.1 練習3 の「経験の国内化」の HITL 版）。

### 介入データを「ラベル」ではなく「反論」として保存する

共創の技術的中心に入る。機械学習の実務で、人間の介入は通常**ラベル**として保存される——正解・不正解、是認・否認、修正差分。ラベルの保存形式は、人間の応答を**機械の未来のための材料**に固定する（人間は未来のモデルの部品にされる——プロレタリア化の最も穏やかで最も完全な形：あなたの判断はあなたの世界の統治には使われず、ベンダーのモデルの勾配になる、→5.1 の経験流出）。

本書は介入を**反論（objection）**として保存する。反論型の最小形：

```python
# intervention.py — 介入の保存形式: ラベルではなく反論
class Objection(BaseModel):
    """人間の介入を『なぜ違ったか』の論証として保存する(→4.4 データとして保存哲学)。"""
    target: str                    # 何を否ったか(candidate id / verdict / 規則 id)
    because: str                   # 理由の自由文(必須・匿名不可、→2.5 intent 原則)
    counter_offer: str | None      # 差し替え候補(無くてもよい: 否定は肯定に優先する)
    evidence_refs: list[str]       # 根拠の参照(現場の観測・過去の実例・CQ)
    rule_critique: str | None      # 『規則そのもの』への批判(これが共創の核)
    route: Literal["model-train", "rule-change", "cq-amendment", "sanctuary"]
    # ^ 人間が応答の『行き先』を選ぶ。全て model-train に既定される UI は
    #   共創を静かに類型一へ退化させる(経験の流出の UI 実装)。
```

`rule_critique` と `route` の二項目が、ラベル形式との決定的な差である。**rule_critique**：「今回の出力は違う」ではなく「この shape のこの制約が、この現場の区別を潰している」——介入が規則改正（→2.6 級つきの変更）に化ける口。Objection はそのまま RuleAdoption/TermMapping/CQAmendment の審議槽へ配線される（→7.1・6.1・4.2 —— 8.2 の再解釈の席が、介入の自然な行き先として機械的に開いている）。**route**：人間が行き先を選ぶ——学習材料として使ってよいと人間が許した場合のみ model-train に流れ、既定は rule-change（系自身を変える）へ寄せる。この既定の寄せ方が「増幅化」の配線そのものである——**経験をまず系の統治へ流し、余ったものをモデルの改善へ流す**。逆（全てモデルへ）が自動化、前が増幅化。

```cypher
// objection 流の監査: 介入の行き先分布(共創の健康計器、→8.1 計器の HITL 版)
MATCH (o:Objection) WHERE o.at > datetime() - duration('P8W')
RETURN o.route, count(o) AS n,
       avg(size(o.evidence_refs)) AS evidence_depth,
       sum(CASE WHEN o.rule_critique IS NOT NULL THEN 1 ELSE 0 END)*1.0/count(o) AS rule_attack_rate
ORDER BY n DESC;
// rule_attack_rate 低位 + route='model-train' 過半 = 共創の退化(類型一/二への逆流)。
```

`evidence_depth`（平均根拠参照数）にも意味がある——反論が根拠なしの直感でなく実例接続で出ている率（→3.4 の障礙実例の循環が、労働者の介入経由で回る）。直感の反論も保存するが、実例接続の反論は RuleAdoption の E1/E2 級の根拠になれる（→4.1 の等級が介入の重みになる）。

### 介入地点の設計 — どこに人を置くかで人間観が決まる

HITL の設計変数の最後の一本を引く。**人間の介入地点**。パイプライン（→7.4）のどの段に人を置くかで、その系が人間を何だと考えているかが決まる。

**提案段に人**（LLM の代わりに人が候補を出す）——人間を生成力の部品とみなす。増幅化の観点で最弱（機械の候補生成の補助に人間を落としめる、→8.2 の技能剥奪）。
**検証段に人**（機械の出力を人が検査）——人間を品質管理のセンサーとみなす。承認類型の本体（→5.3 のlaundering 風険）。
**決定段に人**（judgment を人が下す）——人間を判断の器とみなす（→5.1 の accountability 末端）。**必須だが不十分**——皿が機械由来の frame 内クリックに退化しうる（→8.1 の frame_conformity）。
**規則段に人**（RuleAdoption・shape・mapping・CQ を人が変える）——人間を**憲法の制定参加者**とみなす。本書の設計はここに最も厚く人を置く（→7.1 委任深度の前提条件が phronesis 残高であったこと、→7.6 の段3昇格条件）。
**共観・避難所の段に人**（→8.3）——人間を沈黙を共有する存在とみなす。形式化の外側の人間観。

```python
# human_placement.py — 介入地点の配置表(各段の人間予算・SLA・行き先)
PLACEMENT = {
  "propose":   {"human": "任意(現場の独創候補は dissent で随時注入可)", "route": "candidate"},
  "verify":    {"human": "警告級のみ(機械検証の Warning 判断)",          "route": "rule-change 既定"},
  "decide":    {"human": "必須(time-boxed, 8.5 の皿で)",                "route": "judgment"},
  "rule":      {"human": "常設(知識議席・審議槽・落日再承認)",           "route": "rule-change/cq-amendment"},
  "copresence":{"human": "居るだけ(記録は場の存在のみ)",                 "route": "sanctuary"},
}
# 表の読み: 人間の人時予算が decide に厚く rule に薄い系は、『判断は人間、統治は機械』
# という人間観を予算で告白している(予算が哲学の真の表明、→4.1 の宣言と実測)。
```

最後のコメントを反芻してほしい。**予算が哲学の真の表明である**——会議での人間尊重の宣言と、人時配分表の乖離（→4.1 の宣言と実測の突合が、組織設計にも効く）。決裁段に人時を積み（承認の労働化）、規則段を空席にする組織は、人間を「判断してくれる便利なセンサー」として設計している——5.3 の尤度の物語化が読む説明文と、この表の読みは同じである。

### 共創の計測 — 三類型の実地判別と退化の早期警告

三類型（承認・介入・共創、→5.1 の表）を、実地の判別試験として数値化する。判別の中心は前節の通り「人間の出力の行き先」だが、運用で測る三本の照会を置く。其一、**routinized-consent 率**：判断（JudgmentEvent）のうち、候補集合が単一で（皿が1つ）、根拠面板の滞在が最小値ちょうどの同意の率（→8.5 の READING/REASON_PROBED の履歴で測れる——形式読解の履歴は実質読解の下限証拠である、→8.5 練習2）。其二、**介入の実効半減期**：人間の介入（Objection・override）が、規則変更（RuleAdoption・shape 改訂）に化けるまでの中央値日数——半減期が無限大（化けない）なら、介入は承認に退化している。其三、**共創の配線長**：現場の反論が規則変更になるまでに経由する審議段の数——長い配線は共創の摩擦であり、摩擦が閾値を超えると現場は dissent をやめる（dissent_volume の逓減は配線の詰まりの音、→6.2 槽の健康）。

```cypher
// hitl-degeneracy — 三類型の退化検出(月次 scorecard に登録)
MATCH (je:JudgmentEvent) WHERE je.at > datetime() - duration('P1M')
WITH je, size([(je)-[:JUDGED_ON]->(:EvidenceBundle)-[:HAS]->(:Candidate) | 1]) AS plate_n
RETURN avg(CASE WHEN plate_n = 1 THEN 1.0 ELSE 0.0 END) AS single_plate_rate,
       // ^ 皿が1枚の判断率: 高ければ承認は選択肢の登記ではなく署名の登記
       count(je) AS judgment_count;
MATCH (o:Objection) WHERE o.route = 'model-train'
RETURN count(o) AS model_only_objections;      // 行き先 model-train 過半=共創の退化
```

退化警告（single_plate_rate > 0.6 + model_only_objections 過半）が出た系に、本書が勧める最初の解毒は**皿を増やすことではなく、皿の外を登録可能にすること**である（→7.1 の coin-term・dissent の通路——候補が増えると frame 内クリックが効率化してかえって frame_conformity が上がる逆転がある、→8.1 の frame_conformity の罠）。frame_conformity が測るべきは候補数ではなく**候補外応答の登録率**である（outside-frame registration rate、→8.6 の drill level 4〜5 と同一の設計語彙）。

自動化への政治的回復として、この節の結論を明示しておく。**人間を残すことと、人間を残す意味があることを設計で担保すること**は違う。承認段に人間を置くだけなら、それは責任の洗浄装置に人間を置くことだ（→5.3 laundering の組織実装）。共創の三配線（規則段の席・反論の保存・行き先の選択）が揃っていない HITL は、本書の語で「HITL のふりをした自動化」である——そしてこの偽装は、scorecard の三照会（single_plate_rate・介入半減期・dissent 逓減）で区別できる。哲学は区別のためにある、区別は計器のためにある。

### 异議の作法 — Objection の書き方三例と退化例

8.4 の Objection model（because/counter_offer/evidence_refs/route、→前掲）を、書き方の例で缔ぶ。好的三例と退化二例。

**良い一（規則批判＋反案）**：because:「E4 前提『伝感器連続』が 3 日で 2 回崩壊（evidence:/obs/441,/obs/509）。この前提で夜間自動を続けると、崩壊時の停止が人工判断で遅れる」counter_offer:「前提崩壊時の 10 秒安全停止のみ自動、其余段1へ」route: rule-change。——前提の崩壊実例・反案・行き先が揃う（→3.4 N4 の宣言の書式そのもの）。
**良い二（判断の再検証要求）**：because:「私（保全長）の 11/2 の同意は、推薦 0.7 の basis に旧型設备的分布が混在していることを知らなかった（basis の撤回条件に無かった、→5.3 確率の約束）」counter_offer:「同意の再決着、basis 分離まで該 act を段1に降格」route: rule-change＋自己履歴LED_TO。——自己の判断の歴史を証拠に使える（→8.2 パネルの逆用——自分の同意を自分が退かせる=所有の実地）。
**良い三（皿の外）**：because:「推薦 3 皿はいずれも弁加圧の調整。そもそも夜間弁圧運行の廃止が討議されていない」counter_offer: なし（选項の创設要求）。route: 討議槽——皿の外が规則批判より上位の討議に載る（→7.1 coin-term・→8.6 drill level 5 の書き手版）。
**退化一（苦情）**：because:「この AI は信用できない」——evidence_refs 無·反案無·route 無。受理する（発言級 L0、→2.6）が、審議材料にはならに——解決率の分母に載せず、**質感情報として另枠**（分母に載せると、質の低さが解決率を下げるために异議の受け口が狭くなる、→6.2 歪）。
**退化二（回答案の盗用）**：counter_offer が既存 act 集の焼き直しで、because が無い（反案の量産で討議を満杯にする——→6.6 赤組脚本三の個人版）。検出：counter_offer の重復率と because の引用密度（→B.3 計器）。

書き方 guide を UI に内蔵する（Objection form の placeholder に三例の骨格を載せる、→8.5 の面板と同じ設計哲学——**書式が哲学を配線する**）。

### 异議統計 — 四本を一并に読む

8.4 の計器（dissent_attack_rate・single_plate_rate・介入半減期、→前掲）は四本目まで揃えて并べ読む（単独の計器は必ずゲーム化される、→6.6 統計が燃料でなくなる形態）。**四本目：异議解決の時間（dissent→決着の中央値）**。四列の組み合わせ診断を四つ置く。(低 attack・短 解決)=討議が生きている（异議が出て速く決着する）。(低 attack・長 解決)=討議が空洞（出ない上に決着も遅い=6.6 腐敗四の完走）。(高 attack・短 解決)=現場が鋭い（是正が追いついている）。(高 attack・長 解決)=**委任の危機**（异議が積累して決着しない=現場が系統を「談判対象」に見始めた——dissent が討議でなく交渉になる、交渉は条約贸易に化ける、→6.1 の贸易が討議を迂回する=統治の外部化、6.6 の入口）。

四列を四半期プロットした図に、落日審議（→6.6）の決議を 1 点で書き込む（「次季、どの列を動かすか」の宣言）。計器の図に決定が書かれない限り、計器は観測でなく装饰である（→4.6「あらゆる検査は失敗の届け出先まで設計して初めて検査」——計器の届け出先は最終的に**次季の決定の URI**でなければならない、検査と席の接続の統計版）。

### 実行練習

1. あなたの HITL 実装（承認フロー・レビュー・修正 UI）を三類型で診断し、介入データの保存形式（ラベルか反論か）を特定せよ。`Objection` の `route` 相当（人間が行き先を選べるか）が無い場合、まず route  selector を1項目だけ追加する改造の級（→2.6）と、その改造の Objection 自身（rule_critique として）を書いてから着手せよ。
2. `objection` 流の監査クエリをあなたの修正・差し戻しデータで実行し、rule_attack_rate を計算せよ。低位（例0.1 未満）の場合、介入が規則へ化ける口を1つ開け（例：レビューコメントの「手順そのものへの批判」チェックボックス→審議槽自動登録）し、審議槽のキャパ超過時の優先順位規則（どの口から開くか）を級つきで決めよ。
3. `PLACEMENT` 表をあなたの組織の人時配分実測（1か月のタイムトラックから）で書き直し、宣言（会議・規程での人間観）と予算（実配分）の乖離を1段落で報告せよ。乖離の是正として、decide の人時を rule 段へ移す計画（誰のどの会議を削り、誰を知識議席へ座らせるか）を、2.6 級 L2 の変更説明文の形式で書け。

## 8.5 「理由」を問い直す対話UIプロトコル — 説明を表示するのではなく、問いを交わす

8.2 で「わかっていて押すボタン」の四配線を定義し、8.4 で介入を反論として保存する形式を作った。この節は、それらを**対話として**実装する——システムと作業者の間の、理由を巡る往復の設計である。中心の転倒はこれだ。**説明（explanation）を表示する UI と、理由を問い直す（interrogation）UI は別の物である。** 説明の表示は一方的な提示であり、読み手の更新経路を持たない（→5.2 の fluent な現前化の消費）。理由の問い直しは、システムが提示し、作業者が応じ、応えが規則と語彙へ返る**プロトコル**である。本書の UI 設計は、このプロトコルの実装であり、その器として JSON Schema と UI 状態機械を使う（→5.5 のステートマシン命令——ガードは決定論、UI の遷移も決定論でなければならない——が、ここで界面に適用される）。

### プロトコル — 三つの必須添付と三つの応答形式

Action 提示時に必ず添える三つ（→8.2 の ActionOffer を完成させる）：**根拠**（basis_trace——why_action 七要素への辿れる参照、→7.5）、**却下した選択肢**（rejected_options——皿に載らなかったものと理由、→6.4 の missing）、**反証条件**（falsifiable_if——「もし X ならこれは誤り」の機械照会可能な条項、→4.2 の falsifiability・4.5 の反実仮想）。作業者の応答は三つ：**同意**（consent——judgment の登記、→5.1）、**反証**（objection→consent——8.4 の Objection 型、根拠と rule_critique 付き）、**無応答**（no-response）。

三つ目の扱いがプロトコルの哲学である。**無応答は沈黙の同意ではない。** 同意が登記されるのは明示の応答のみで、無応答は `NoResponse` レコードとして別種の事実になる——「提示されたが応えなかった」は、注意の失敗・時間不足・界面の失敗・関心の喪失、いずれの証拠でもなく、**次の問いの設計材料**である（→4.5 の UNKNOWN と同じ三段構え：正でも負でもなく、地平の情報）。無応答の集計（セグメント別・時間帯別・提示形式別）は、界面の設計が誰に届いていないかの計器になる——届かない界面は、8.2 の四配線が形式的に揃っていても実効的承認を成立させない（再検証可能性は**実際に再検証されること**ではなく**再検証に至る道が実際に通っていること**で測られる、→5.1 の再定義の UI 版）。

```json
// protocol/offer.schema.json — 提示の JSON Schema(三必須の強制)
{
  "$id": "execphil://offer/v3",
  "type": "object",
  "required": ["action_id", "basis_trace", "rejected_options",
               "falsifiable_if", "hold_seconds", "response_options"],
  "properties": {
    "basis_trace":      { "type": "string", "pattern": "^why_action://" },
    "rejected_options": { "type": "array", "minItems": 1,
                          "items": { "required": ["option", "why_rejected"] } },
    "falsifiable_if":   { "type": "array", "minItems": 1,
                          "contains": { "pattern": "(query:|if:|where:)" } },
    "hold_seconds":     { "type": "integer", "minimum": 20 },
    "response_options": { "const": ["consent", "objection", "no-response"] },
    "counterfactual_link": { "type": "string" }   // 「別の選択なら」面板への口(→4.5・7.5)
  },
  "x-contract": "rejected_options が空の提示は schema 不正(知らない却下を作らない)"
}
```

`rejected_options` の `minItems: 1` に注目せよ。「却下した選択肢はありません」を schema が許さない——候補生成が1案しか出さなかった場合、UI は「**なぜ1案しか皿に載らなかったか**」を却下リストに載せる（frame-making 自体の説明義務、→5.3 の EvidenceBundle の frame_options が UI で開く場所）。`counterfactual_link` は、作業者が「別の手を打っていたらどうなった」を実際に辿れる口である（7.4 練習3 の checkpointer タイムトラベルの界面実装——説明は表示ではなく**再生への招待**、→5.5 の「説明＝再生」が UI の語彙になる）。

### UI 状態機械 — 界面にも決定論のガードを

プロトコルを回す界面の状態機械を定義する（→5.5 の器の UI 版。UI の遷移が LLM 的におおらかなと、判断の記録が界面で腐る——「うっかり同意」ボタンは 5.3 の見せかけ承認の界面実装である）。

```python
# ui_state_machine.py — 応答セクションの UI 状態機械(決定論ガード)
class OfferState(Enum):
    OFFERED = auto()        # 提示済み・保持時間(hold_seconds)計時中
    READING = auto()        # 根拠パネルを開いた(再検証の道を通った事実が記録される)
    REASON_PROBED = auto()  # 反証条件の照会を実行した(→4.5 counterfactual 呼び出し)
    RESPONDED = auto()      # 同意/反証の登記完了
    LAPSED = auto()         # 保持時間超過→ safe-default 経路(→7.4 time-boxed)

def guard_consent(s: OfferState, payload: dict) -> bool:
    # 同意ボタンのガード(決定論): 根拠パネルを1度以上開いた + 反証条件1件以上照会。
    # 「読んでいない同意」を構造として作らない(→5.1 実効的承認の界面強制)。
    return s in (OfferState.REASON_PROBED,) and payload.get("falsifiable_checked", 0) >= 1
```

`guard_consent` の設計を本章で最も議論を呼ぶ一歩として開き、その限界も書く。**同意に最少の読解を要求する**——根拠パネルを開き、反証条件を1件でも照会しなければ同意ボタンが押せない。これは paternalism か、それとも 5.1 の「見せかけ承認の禁止」の忠実な実装か。答えは条件付きで、**要求が読みを担保するわけではない**（パネルを開くだけの「形式読解」は生む）。しかし形式読解は、読解ゼロと履歴上で区別される——`READING`・`REASON_PROBED` の遷移履歴が、後日の審議で「この承認はどの道を通ったか」の証拠になる（→5.1 の basis_reckoning の界面版）。界面が形式読解を要求し、形式読解の履歴が残ることで、**読解の実質を問う審議**（→6.2 の討議）が次の材料を得る——界面は読解を作らない。読解の問答への道を、開く。

### 説明の設計 — 三つの面板（reason / counterfactual / dissent）

UI の情報設計を三面板で完成させる（OUTLINE で 4.5・3.6 から伏線として引いてきた面板がここで着地する）。**根拠面板（reason panel）**：why_action 七要素の階層展開（→7.5）——目的→規則→候補→判断の四層を、上から順に見せる（順は注意の配分である、→7.3 の提示順設計と同じ DesignDecision 登記対象）。**反実仮想面板（counterfactual panel）**：「別の候補を選んでいたら」「規則 X が無かったら」「判断が2時間遅かったら」の三つの再生口（→4.5 の counterfactual・7.4 のタイムトラベル）——**説明の完全な形は、反実仮想が再生できること**である（4.5 で確立した「説明＝制約の名簿＋反実仮想」の界面最終版）。**不服従面板（dissent panel）**：この提示・この規則・この皿の作り方への不服従の提出口（→6.2 dissent・8.4 Objection の route selector）——面板が UI に**常在**することが、不服従の権利の界面実装である（不服従が奥まった場所にある UI は、槽を空けない権力の界面版、→6.6 腐敗二）。

三面板の配置条約を one 置く。**dissent 面板は consent ボタンの隣に置く**——不服従は「その他」メニューに匿んではならない（不服従の所在が UI の人間観を露出させる、→8.4 の配置表の界面版。「承認の隣に不服従」は、この系が dissent を正常な応答と設計している宣言——2.6 の不服従のパス（L0）の像素子）。

### 無応答の倫理 — 界面が疲弊を読む

無応答の設計を、疲弊の読解として仕上げる。無応答が続く場所（同じセグメント・同じ時刻帯・同じ提示形式）は、界面の失敗であり、そこで同意が積み上がっていることの方が危険である（**無応答のセグメントの同意率が高いなら、その同意は届いていない同意である**——8.2 の「わからずに押す」が統計で見える形）。設計上の解毒を三つ。其一、無応答率の高いセグメントでは提示の粒度を下げる（1回の皿の選択肢を減らす——注意の予算、→7.2 の周期予算の界面版）。其二、連続無応答で personal の hold_seconds が伸びる（疲弊した人間に即決を迫らない——2.6 の沈黙の猶予が界面で個人に調整される）。其三、無応答セグメントの同意は、事後共観（→8.3 の共観セッション）の議題に自動で載る——届いていない同意を、後から共有された理解で回収する循環。

```cypher
// inattentive-consent 検出: 無応答の続くセグメントで同意が高率 = 届いていない同意
MATCH (nr:NoResponse) WHERE nr.seg = $seg AND nr.at > datetime() - duration('P14D')
WITH nr.seg, count(nr) AS lapses
MATCH (je:JudgmentEvent {seg: $seg}) WHERE je.at > datetime() - duration('P14D')
WITH nr.seg, lapses, count(je) AS consents
WHERE lapses > 10 AND toFloat(consents) / (consents + lapses) > 0.85
RETURN nr.seg, lapses, consents, 'inattentive-consent-suspect' AS flag;
// flag 発火セグメント: 提示粒度の縮小・hold_seconds 延長・共観議題化が自動提案される。
```

「届いていない同意」は、この本全体への最も正確な警告でもあった。第1〜7章の体系は、同意と承認と署名で満たされている——その一つ一つが**届いている**かを、第8章の UI が問う。哲学が界面で問われる時、哲学は嘘をつけるかどうかが分かる。

もう一層、プロトコル同士の衝突を設計しておく。**猶予と期限の衝突**——7.5 の decision_budget_sec（時間予算 SLA、→7.2）が短く、hold_seconds（猶予）が長いとき、どちらが勝つか。本書の決定は**猶予が勝つ**（予算内で判断できないなら、その goal の時間予算自体が E4 前提の崩壊——N4 障礙、→3.4 の宣言として Quarantine に載せる）。逆（予算が猶予を潰す）を許すと、猶予は SLA の前で消える飾りになる——**猶予は速い系の前に跪く**。この衝突解決規則を config に宣言し（`hold_priority: true`）、CI で「decision_budget_sec < hold_seconds の goal のリスト」を警告として出す（衝突の存在そのものを簿記する——4.5 の UNKNOWN 宣言と同じ手順）。

### 同意簿記の字段仕様 — 十字段で同意の重みを載せる

同意（consent、→前掲）の台帳一行の字段仕様を十字段で确定する（字段の欠落が同意を「ボタンを押した」事件に落とす——同意の重みは字段で出来ている）。**①consent_id**（graph:// URI）、**②subject_uri**（同意の対象=offer のどれの版か——offer 変更対 version、→5.4 の四版本簿記）、**③person**（末端、署名級、→2.6）、**④read_evidence**（面板でどれのセクションを何秒見たか、→REASON_PROBED の生成分布）、**⑤probed**（問答で何問返したか=実質読解の代理指標、→guard_consent）、**⑥hold_seconds**（猶予の長さ、猶予は同意の深度、→前掲）、**⑦dissent_links**（この同意に結ばれた异議・質問の URI——同意の周囲の討議、→6.2 の討議が同意簿記に載る形）、**⑧withdrawal_window**（撤回可能期間、**撤回不能の同意は署名で、撤回可能な同意は判断**——7.5 の why_action への道、撤回の席がある同意だけが判断として老朽できる）、**⑨counterfactual_link**（この同意が止めた/通した act の URI——同意の因果の重み、→前掲の counterfactual_link）、**⑩sunset**（この同意が審議帰来する時刻——**同意は永遠に生きない、落日する判断である**、→5.2 の手放し・6.6 の落日の同意版）。

⑧と⑩が仕様全体哲学の中心で、この二字段が欠けた同意台帳は同意を**一度の署名**として冻結する（署名は歴史の事件で、判断は歴史を持つ——⑩が同意に歴史を与える）。⑨の counterfactual_link が欠ける組織は、同意の重みを永遠に計算できない（何が止まったかは永遠に見えない——**中止された事故の台帳は永遠に空**なので、止めた同意の价値は counterfactual の辺でのみ近似される、→5.6 の Quarantine の統計が「防いだもの」の唯一の ledger である理由の同意版）。

### 実行練習

1. あなたの承認 UI を `offer.schema.json` v3 で走らせると仮定し、現在の提示がどの required 項目で落ちるかを項目ごとに挙げよ（典型：rejected_options の空・falsifiable_if の「状況見て判断」化・counterfactual_link の不在）。三必須のうち最初に1つ実装するならどれかを級つきで決め、理由を「どの嘘を最初に暴きたいか」で述べよ。
2. `guard_consent` の paternalism 論に反論を書く（200字）か賛成を書く（200字）かのどちらかを選び、あなたの現場の実際の「うっかり同意」事件1件を証拠に引け。その後、形式読解と実質読解の差を測る追加計器（例：根拠パネルの滞在時間分布と反証照会の件数の積）を1つ設計し、**個人でなく界面の設計**に使う条約（→6.6 G-1）を添えよ。

## 8.6 再身体化 — 暗黙知を取り戻すための実装

第5部最後の節である。ここまでの第五章——プロレタリア化の診断（→8.1）、所有権と理解の配線（→8.2）、共同化への逆流（→8.3）、共創型 HITL（→8.4）、理由の対話 UI（→8.5）——はすべて、一つの問いへの部分的な答えだった。**形式化を進めた系統で、人間の暗黙知はどう育ち続けるのか。** 暗黙知は使用によってのみ維持され（→1.1）、使用は場を要し（→8.3 の共観）、場は配線である——ならば、**技能が使用される場を、業務の内部に設計で作り続ける**ことができる。この節はその最終配線——**再身体化（re-embodiment）のループ**の実装である。形式知を身体へ戻す循環（SECI の内面化、→8.3）を、本書が作り上げてきた歴史代数・反実仮想・障礙台帳・UI プロトコルを素材として、業務の内部に組み込む。そして章と全書を、読者への最終課題——自分の現場の最初のアポリアを特定する演習——で閉じる。

### 技能練習ループ — シミュレーションを業務に埋め込む

第一の配線は、**段階的難易度のシミュレーションを業務時間として埋め込む**ことである。航空・医療・消防が既に持つ訓練文化を、知識労働と保全現場へ移植する。本書の系が、シミュレーションの素材を無限に供給する構造を持っている——障礙台帳（→3.4）、過去の実例（→2.5 の履歴代数）、反実仮想の再生（→4.5・7.4 の checkpointer）、Quarantine の未知（→5.6）——これらが練習シナリオの**生成器**である。

```python
# drill_forge.py — 歴史代数からの練習シナリオ生成(段階的難易度)
def forge(session, site, level: int) -> dict:
    """過去の実例から練習シナリオを作る。level は 1..5 の段階。
    哲学: 練習の目的は『正解を選ぶ速さ』ではなく『皿の外を見る能力』の維持である
    (→8.1 frame_conformity の解毒)。よって high level 課題は frame 外の応答を要求する。"""
    hist = past_incidents(session, site, weeks=26)          # 2.5 履歴からの実例抽出
    if level <= 2:
        base = sample(hist)                                  # 過去実例の再演(リプレイ)
    elif level == 3:
        base = perturb(sample(hist))                         # 変種(1条件を変える、→4.5)
    elif level == 4:
        base = recombine(sample(hist, 2))                    # 複合障礙(2実例の重ねがけ、→3.4)
    else:  # level 5: 未知の形 — Quarantine の未解決語彙を種に、frame 外応答を要求
        seed = sample_quarantine_terms(session)              # 5.6 の未知の庫から
        base = novel_situation(seed)                         # 皿が正しく作られていない状況
        base["requirement"] = "outside_frame"                # 候補外の対処を評価条件に
    base["debrief"] = ["basis_trace", "counterfactual_panel", "dissent"]  # 8.5 の三面板で振り返り
    return base
```

level 5 の `outside_frame` 要求を練習設計の頂点に置く。候補リストの内側から最善を選ぶ練習（level 1〜3）は、frame_conformity を**上げる**方向に最適化されうる——皿の内側の名人を作る（→8.1 の退化の訓練版）。level 4〜5 は逆で、**皿が不完全であることを条件に含む**——「正解は提示候補に無い」状況を練習に制度として織り込む（障礙台帳が「今何が分かっていないか」の目録であることの訓練利用、→3.4）。debrief を 8.5 の三面板で構成するのは、練習の振り返りがそのまま理由の対話プロトコルの反復になる設計——**訓練と運用が同じプロトコルで書かれている**とき、練習は仕事から遊離しない（遊離した訓練は必ず予算削減で最初に削られる——→2.3 の保持条件）。

周期設計（間隔反復）は、E4 再検証期限の設計と同じ骨組みで置く：技能の保持寿命（個人 × 手順クラスで推定）に基づき、下次 drill を自動起案する（→2.6 の級・審議槽の語彙で業務時間として予算化される——8.2 条件三「再解釈の労働を労働として認める」の訓練版）。

### 理由の蓄積を教育課程へ — フロネシスのカリキュラム化

第二の配線は、**本書が蓄積させてきた「理由」の履歴を、教育課程の素材に変える**ことである。第1〜7章で記録されてきた JudgmentEvent・Objection・RuleAdoption・Quarantine・ConstraintConflict・OverrideEvent——これらは全部、**誰かが状況の中で理由を伴って選んだ事実**である。アリストテレスはフロネシスを「経験の蓄積（empeiria の蓄積）」から育てると書くが（→7.1）、蓄積の素材が今、構造化されている。

```cypher
// curriculum_from_history — 理由の履歴を教育課程へ転化する照会
// 「この現場で過去12か月、最も判断が割れた状況」を教材に選ぶ:
MATCH (je:JudgmentEvent), (ob:Objection {target: je.chosen})
WHERE je.at > datetime() - duration('P12M')
WITH je, count(ob) AS dissent_count
WHERE dissent_count >= 2                          // 反論が2件以上ついた判断=論点の化石
MATCH (je)-[:JUDGED_ON]->(eb:EvidenceBundle)-[:DERIVED_FROM]->(c:Candidate)
RETURN je.situation_digest, eb.frame_options, c.provenance,
       collect(ob.because) AS objections,         // 反論の正文が教材の本文になる
       dissent_count
ORDER BY dissent_count DESC LIMIT 5;
```

`collect(ob.because)` ——**反論の正文が教材の本文になる**。8.4 でラベルでなく反論として保存した理由（→8.4）が、ここで教育的な価値として回収される。新人は、先達が「なぜ違ったか」を書いた正文を、反実仮想面板で別の選択を再生しながら読む（→8.5 の counterfactual_link の教育利用）。読み終えた新人は、同じ状況の level 3（変種）で drill を受け、自分の応答と先達の反論を比較する——**教育は先達の判断の模倣ではなく、先達の反論への参加である**（スティグレールの教育論——savoir-faire は反復ではなく個別化（individuation）で伝承される、→8.1）。

課程の設計条約を二つ。其一、教材選定は自動候補＋人間選定（dissent_count 上位は候補であり、選ぶのは教育担当と現場の共観——→8.3 の共同化が課程の設計にも入る）。其二、**反論を書いた本人の同意を教材化に要する**——自分の反論が教材として流通することの承認（知の所有権、→8.2 条件一の教育版。無断流通は、8.4 が防いだ「経験を材料にされる」の教育形である）。

### 再身体化の計器 — 皿の外を見る能力

ループが効いているかを測る計器を、本書の語彙で定義する。**frame 外応答率**（drill level 4〜5 で、候補外の対処が提案される率——→7.1 の coin-term、1.1 の暗黙知の発火の訓練時における可視化）、**反論の密度**（drill debrief で Objection が生まれる率と rule_critique 率）、**状況語彙の成長**（drill 参加後に TermMapping 改訂・CQAmendment に化ける率——練習が語彙に還流する配管）。注意を一つ——drill のスコアを個人評价に使う瞬間、このループは 6.6 の腐敗三の完全版に落ちる（「外れた応答」を評価された被験者は、安全な frame 内応答に収斂し、練習が frame_conformity を上げる装置に反転する）。**drill の数値は系の健康（課程の設計）を測るもので、個人の技量を序列化するものではない**——条約G-1 の教育版として条文化する。

### 最終課題 — あなたの現場の最初のアポリア

全書の終わりに、本書の読み方そのものを課題として残す。哲学用語のアポリア（aporia）は、**それ以上の問いの進み方が一時的に止まる地点**である。本書は第1章から第8章まで、アポリアを消すのではなく設計の燃料に変えてきた——残余（→1.2）、暗黙知（→1.3）、沈黙（→1.6）、マッピングの断層（→2.4）、目的の過小決定（→3.1）、障礙（→3.4）、UNKNOWN（→3.5）、尤度と正統の断絶（→5.3）、翻訳の不可視の損失（→6.3）、選定の非封閉性（→7.1）、プロレタリア化の勾配（→8.1）。

最終課題は三問からなる。**問一**：あなたの現場で、現在「設計が消そうとして消し損ねている」アポリアを一つ特定せよ（残余か、沈黙か、UNKNOWN か、frame の外か）。証拠を本書の計器の語彙で一つ添えよ（stale_obstacles、frame_conformity、unanchored_judgment、TranslationFailure の統計——どれかの実測値）。**問二**：そのアポリアを**燃料に変える最小の配線**を一つ設計せよ（審議槽の設置か、CQ の追加か、Quarantine の席か、drill level 5 の課題化か）。2.6 級の変更説明文の形式で書き、declared-by と落日を添えよ。**問三**：その設計が失敗して系が腐敗したとき、腐敗を教える計器を一つ宣言せよ（6.6 練習3 の統治健康指標の系譜——「私の設計はこう死にます。その死に顔はこの数値に出ます」を先に書く）。

この三問に答えられない読書は、本書の読み方としては不完全である。本書は知識ではなく**読み取りの訓練**として書かれた——アリストテレスの語で言えば、読後に残るべきは.episteme（知っていた感じ）ではなく、あなたの現場の状況を見る sight の変化である。sight が変わらないなら、この本は fluent な現前化の消費であって、更新経路を持たなかったことになる（→5.2・5.3 の診断が、読書行為自身に適用される——動く哲学書の最終のテストは、読者の手元で走る）。

### 課程の設計 — drill 課程の体系と「 curriculum の落日」

drill_forge（→前掲）が課題を生成するように、**課程**（curriculum）もまた設計物として宣言・落日・更新されねばならない——技能練習が「いつの間にか同じ課題を反復している」状態（課程の hollow-fluent、→5.2）を避けるためである。課程設計の三層を置く。

**層一：単位課程**（手順クラス × 難度 ladder）——各 drill 単位の課題集合は、障礙台帳の最新実例（→3.4）と TermMapping 改訂史（→6.1）から自動生成され、課題の seed 引用が課題内に登記される（drill_forge の base["seed_ref"]）。seed が 12 か月より古い障礙のみを参照する課程は、自動生成 CI で警告（課題の材料が老朽化=課程の減価償却未計上、→7.1 の資産台帳の教育版）。**層二：領域課程**（現場単位の技能地図）——site TBox の語彙と Action 台帳（→7.3）をそのまま技能地図に使う：その現場が語れる状況語と打てる Action の集合が、その現場の「現在開ける世界」の目録であり、drill はこの目録の周縁（最近打たれたことがない Action、最近使われていない語）へ優先的に配られる。**周縁の練習**——中心の技能は業務が維持するが、周縁の技能は drill がしか維持しない（→8.1 第二段の退化は周縁から始まる）。**層三：体系課程**（設計原理の教育）——RuleAdoption・CQ 改訂・Objection の書き方そのものを科目とする課程（統治の文法、→2.6・4.2・8.4 の手続教育）。層三の欠落が最も高くつく——層一・層二が完璧でも、規則を書ける人が居なければ RuleAdoption の残高は育たない（→7.6 段3の phronesis_fresh 条件の教育前提）。

```cypher
// curriculum-health — 三層課程の健全性(季度 report)
MATCH (dr:Drill) WHERE dr.created > datetime() - duration('P1Q')
WITH dr, dr.seed_refs
UNWIND dr.seed_refs AS seed
MATCH (o) WHERE id(o) = seed   // seed 引用が障礙/実例/改訂を指す
WITH dr, max(o.created) AS newest_seed
WITH collect(dr.did) AS seen, count(dr) AS n,
     sum(CASE WHEN newest_seed < datetime() - duration('P12M') THEN 1 ELSE 0 END) AS stale_drills
// 周縁カバー率: Action 台帳のうち過去 6 か月に drill で扱われた割合
MATCH (a:Action) WHERE a.risk_class = 'low'   // drill 対象は low/medium に限る(実 act なし)
OPTIONAL MATCH (d:Drill)-[:USES_ACTION]->(a)
WITH seen, n, stale_drills, count(d) AS drilled
RETURN n AS drills, stale_drills, toFloat(drilled)/count(a) AS periphery_coverage;
```

`periphery_coverage`（周縁カバー率）を本章の計器の最後に置く。Action 台帳の low/medium 行動のうち、半年間 drill で一度も扱われなかった割合——高いほど「打てるが打たれていない技能」の庫が腐っている。**庫の腐敗は事故では見えない**（使わない技能の喪失は、使う状況が来たときに見える——8.1 第四段の隠蔽性）。よってこの照会が scorecard の四半期常設項目になる（→4.6 の回帰テストがコードの周縁を測るように、この照会は技能の周縁を測る）。

### 再身体化の失敗条件 — 課程を腐らせる四つの配線誤り

drill 課程（→前掲）は正しく配線しないと、再身体化（→身体を取り戻す）ではなく**訓練の空洞化**を生む。失敗条件を四つ、配線の誤りとして名乗る。

**誤り一：drill を評价に結ぶ**——level 4〜5 の outside_frame 要求は失敗率が高い。失敗を個人評价に結んだ瞬間、挑戦は消え、level 3 の安全圏で全員が drill を回す（8.1 の frame_conformity 上昇の課程版——評价が frame を強制する、→8.3 聖域规則の drill 版：drill の失敗記録は個人档案に載せない。課程の账簿は個人でなく課程自体の質を測る）。**誤り二：seed を歴史から取らない**——drill 課題が外部の教材・一般問題集から来ると、その現場の障礙史・条約史と無関系になり、解けても現場の判断能力は増えない（curriculum_from_history の seed_ref 強制、→前掲。無歴史の drill は「訓練」という形式だけの劳動）。**誤り三：level 5 を作らない**——outside_frame 課題を「高級所以省略」すると、課程は frame 内熟达の機械に化け、deskilling の診断（→8.1 stale_obstacles・frame_conformity）が出ても課程が応答できない。**誤り四：師の受容ない自動生成だけ**——drill_forge の自動課題（→前掲）に、現場師の「これは本物か」の承認を課さない。誤った前提の課題を解かせると、現場の判断に誤った型を刻む（自動生成の産出は L1 級——承認までが課程、→2.6 級体系の課程版）。

四誤りに共通する诊断名を一つ——**課程が歴史・評价・承認の三配線から切れた時、訓練は劳動になり、労働は 8.1 の第四段に一直線で連なる**。よって curriculum-health（→前掲）の照会に三本を足す：seed_ref の引用種別分布（障礙/条約/決着の比率——歴史配線）、drill 失敗記録の個人档案出現計数（評价配線が結んでいないことの証明——0 で正、出現すれば即 fail）、師承認率（承認配線）。三本の目標値は、課程の落日審議（→前掲）の決着材料になる。

### 実行練習

1. `drill_forge` の level 1 と level 5 の課題を、あなたの領域で1本ずつ作れ（level 5 は Quarantine・TranslationFailure・未解決障礙から種を取ること——「皿が不完全な状況」を意図的に作る）。課題の採点基準に `outside_frame` の評価項目を明記し、採点者を個人評価と切り離す条約（→8.6 条約）を添えよ。
2. `curriculum_from_history` をあなたの組織で実行できる形に翻訳し（反論・差し戻し・修正コメントの履歴があれば素材になる）、教材候補を3件選び、本人同意の手続（→8.6 条約二）を1枚設計せよ。同意を断る理由として正当なものを1つ挙げよ（例：失敗の公開は処罰の恐怖と地続き——2.6 の処罰と名誉の条件が教育にも効く）。
3. 最終課題三問を、あなたの現場について今、この場で書け（各400字程度）。三問のうち問三の「死に顔の計器」を、翌四半期の scorecard に実際に登録せよ（→4.6 の scorecard は本書の各部の生体検査である——本書の設計をあなたの scorecard に載せることが、本書の移動の完了である）。
