## 7.1 アリストテレスのフロネシス — 個別状況の知恵

第4部が始まる。ここまでの体系——意味のオントロジー（第1部）、履歴と権力の代数（第2部）、目的の形式化とAIの配線（第3部）——はすべて、**システムが状況に応じて行為する**ための準備だった。この章で、その行為の線を初めて通す：テレメトリ受信から現場 API 発火まで、止まらない一本のパイプライン（→7.5〜7.6）。だが実装に先立って、行為の知そのものの哲学を置かねばならない。何がこの体系にまだ欠けているかを明記するためである。欠けているものは計算ではなく、アリストテレスが**フロネシス（phronesis、賢慮）**と呼んだ知の型である。この節の主張は一つ——**規則の適用は計算できる。規則の選定は、原理的に規則に記述を要する追加規則として解消できない。** 故に、選定を担う場所を設計は人間の側に残さねばならない（そしてその残し方が、次節以降のすべての設計になる）。

### 三つの知 — エピステメ、テクネー、フロネシス

『ニコマコス倫理学』第六巻の知の区分を、本書の語彙で敷設する。

**エピステメ（episteme、科学的知）**：必然的なものに関する知。証明可能で、誤りようがなく、 teaches できる。「2 + 2 = 4」「力学的応力の換算式」。対応する本書の部品は、4.5 の sat 判定と SHACL の形状真理である——体系内で決定可能な真理。

**テクネー（techne、制作の知）**：作るものの生起に関する知。制作には outside がある（舟を作る目的は舟の外——運搬にある）。规則と手順と材料の知識で、教示可能で、失敗を部品に分解できる。対応する部品は、3.1〜3.5 の要求工学の全連鎖——telos、goal form、EARS 変換、制約——すべてテクネーの形式化である。

**フロネシス（phronesis、実践的知恵）**：生全体良く送るについて行動する知。対応する部品が——今の体系に——**ない**。これが本節の中心である。区別を確定する三点。其一、フロネシスは**個別についての知**である（「この機械の、今夜の、この音の聞き方」）。普遍を扱うエピステメ・テクネーに対して、その場その場に固有の状況を読む。其二、フロネシスは**行為について**の知で、制作についてではない（行為の outside がない——正しく行為すること自体が目的）。よって telos の外部化ができない（3.1 の定理が倫理にも効く）。其三、フロネシスは**徳と統合**されている（『倫理学』VI.12：徳が目的を正しくし、フロネシスが実用的英知が手段を正しくする）。目的の正しさが本人の器から削れない——3.6 の「名誉と懲罰の器」のアリストテレス版が、ここで初めて倫理論と接続する。

### 規則の適用ではなく規則の選定

フロネシスの工学的核心に踏み込む。アリストテレス自身、規則（katholou）は普遍を語るが行為は個別を語ると書き、規則の不備を**エピケイア（epieikeia、公平さ・規則の例外処理）**で埋めることを論じる（『倫理学』V.10：立法者は普遍を語るゆえに、予測しなかったケースで規則は誤る。誤りは規則の欠陥ではなく、事柄の性質である）。

このエピケイアを機械論で読む。**規則の適用（rule application）は計算可能である。** IF-THEN を与えられ、事実との照合（unification・sat）を行うengine は、20世紀中葉から安定して動く（Rete、Prolog、生産システム）。では何が計算に残らないか。**適用すべき規則の選定（rule selection）である。** 選定が規則にできない理由を三層で示す。

**第一層（技術的実例）**：规則エンジンにもメタ規則（salience・優先度・衝突解決戦略）は付く。しかしメタ規則自体が発火候補集合の一部である——「どのメタ規則を適用するか」は同じ構造を一段上げるだけである。**後退は規則を増やして消えない。** 有限のメタ規則層で止めたとき、その最上層の選択は——設計時に人間が固定した——事実であり、運行時の知ではない（3.5 の bounded check の UNKNOWN が、設計者による層の切断点として現れたのと同じ地点に、ルールエンジンの限界もある）。

**第二層（組合せ爆発）**：状況ごとに発火候補の集合が変わり、優先順位の意味も変わる。優先度表は状況不変の順序を仮定するが、フロネシス的状況判断とはまさに**順序の読み替え**である（「今夜は safety より continuity を上げる夜だ」）。順序の読み替えを状況条件として記述すれば（条件付き salience）、その条件集合が今夜の全状況を読み尽くせるか——これは frame problem の再発である（→3.5 の bounded check の不可解な現実がここで論証される）。

**第三層（存在論）**：規則は既存語彙の述語で書く（SHACL の path、Rego の input フィールド）。**新しい状況は新しい述語を要求する**（振動の「この種類の音」が語彙に無い夜）。規則選定の最深部では、選定者が既存語彙に無い語を導入する行為が発生する——1.1 の暗黙知、2.1 の残余、4.2 の CQAmendment と同じ行為であり、これが**規則内部で起きたことがない**。規則は語彙を消費し、語彙を生成しない（4.3 の断層 C の再読）。

```python
# rule_selection_probe.py — 「選定は規則にできない」の実験的最小形
# 主張: 選定関数 S(context, rules) も規則集合へ追加可能。しかし S の入力語彙が
# 状況変化で増え続けるとき、S の総和は存在しない(選定の非封閉性)。
from itertools import combinations

def engine(rules: list[callable], facts: dict, meta_rules: list[callable] = ()):
    fired, pool = [], list(rules) + list(meta_rules)
    # ^ 設計時に pool は固定。運行時に pool を増やす函数を『渡す』ことはできるが、
    #   その増減函数自身の選定問題は同じ形で再帰する(後退の一段化の演示)。
    for r in pool:
        if r(facts):                     # 適用判定は決定的(unification)。
            fired.append(r)              # ← 適用は計算可能。ここまでが engine の領分。
    return fired

def night_context():
    # 今夜、新しい述語 'sound_kind' が必要になった(語彙外の変化)。
    return {"vib": 45, "sound_kind": "metallic-rattle"}   # rules/pool はこの述語を知らない

# pool に sound_kind を扱う規則を運行時に追加すると仮定する:
# 追加規則を『誰が選んだか』『なぜその追加が正しい夜か』は pool には記録されない。
# → 記録は graph の側で人間行為として登記するしかない(→7.5 の JudgmentEvent 接続)。
```

`engine` の中身が示す通り、適用判定（`r(facts)`）は決定的で、pool の固定までは古典の領分である。破綻は pool の**外側**——運行中の規則集合の生成・選定——にあり、そこは函数では埋まらず、**登記**（人間の行為として history に載せる）で扱うしかない。本章後半（7.4〜7.6）は、この「登記による扱い」の実装である。

### ルールエンジンが規則を選べない理由の哲学的要約

三層の議論をアリストテレスの語に戻して要約する。規則適用は**アプリオリな分析**（可分な普遍の操作）であり、規則選定は**個別の知覚**（aisthesis）を要する。アリストテレスは「感覚」を実践判断の入力に含める（『倫理学』VI.11 末尾：個別的事項の知覚は行為の終点である）。機械に個別の知覚を与えるのはセンサーではなく——センサーは既に語彙化された信号を返す——**語彙の更新を伴う注意（attention）**である。注意は設計時に選別されている（1.2 の「切り取った状況」）、その選別の外からの更新は設計体系の外から来る（被投性、→5.2）。よって「规則エンジンが規則を選べない」は技術の未熟ではなく、**設計という存在様式の構造**である。

ここから本章の設計命令が出る。構造が消えないなら、**構造を認めた上で配線する**。(1) 選定の座を人間の JudgmentEvent に接続し（→5.1）、(2) 選定の入力（状況・候補・根拠・却下）を EvidenceBundle の形で機械が供給し（→5.3）、(3) 供給の時間予算を OODA の内側時計として設計する（次節）。フロネシスを機械に載せることはできない——**フロネシスの座を体系に開き、その座に届く材料を機械が組む**。それが「実践知の運行」という章題の、本書における実装可能性である。

### フロネシスある場所を歴史代数に書く

最後に、選定行為の登記形を定義しておく（7.5 のパイプラインが実際にこの型に乗せる）。規則の選定・生成・退役の行為は `RuleAdoption` ノードとして履歴代数に載る。

```cypher
// RuleAdoption: 規則選定の登記(選定が人間の行為であることを体系が認める形)
CREATE (ra:RuleAdoption {
  ra_id: $id, at: datetime(),
  rule_ref: $rule_git_ref,              // 導入・変更された規則の版数参照
  act: $act,                            // 'adopt' | 'retire' | 'salience.change' | 'coin-term'
  situation_evidence: $eb_refs,         // 選定の根拠EvidenceBundle(→5.3)
  decider: $human_id,                   // 選定者(accountability 末端、→3.6)
  coin_term: $new_term_or_null,         // 語彙生成を伴う選定は 'coin-term'(最深部)
  review_due: datetime($due)            // 落日条項(→6.6)、選定も老朽化する
});
MATCH (ra:RuleAdoption {ra_id: $id}), (c:CQ {cq_id: $cq_ref})
CREATE (ra)-[:RESPONDS_TO]->(c);        // 選定は CQ 改訂の別経路(→4.2 の系譜)
```

`coin_term` を特別視する理由を強調する。新語の導入（今夜の「metallic-rattle」の語彙化）は、規則選定で最も深く、最も希少な行為である（第三層の議論）。4.2 の CQAmendment が問いの発明なら、RuleAdoption(coin-term) は**語彙と規則の同時発明**である。この型の件数は組織のフロネシス残高である——ゼロの体系は、状況の外が無限に増え続けているのに、誰も選定を更新していない体系である（4.1 の E4 期限切れ、2.4 の断層の進行）。scorecard（→4.6・6.6）に RuleAdoption の滞留月齢を加えること——**選定の老朽化計測**である。

### フロネシスの簿記 — 「选定残高」を組織の資産台帳として運用する

7.1 の中心設計物 RuleAdoption を、単なる監査データではなく**組織の判断能力の資産台帳**として運用する視点を置く。会計の語で書くのには理由がある——資産台帳は、減価償却・貸借対照表・監査という三つの制度を含むからである。

**減価償却**：判断能力は使うまで古くなる（→2.3 の制度の老化）。RuleAdoption の review_due（落日周期）は減価償却の予定表である——月齢の進んだ adopt（選定）は、更新（revalidate：根拠の実測再確認）か退役（retire）かのどちらかに必ず着地する。放置は減価償却の未計上であり、判断能力の帳簿上の過大計上になる——「我々の手順は最新である」という報告が、実測では半数が落日超過の手順でできている状態（hollow-fluent の組織版、→5.2）。
**貸借対照表**：側の資産は RuleAdoption の現在残高（有効な adopt・coin-term・salience 更新）と、その月齢分布。負債側は滞留した review_due（期限切れ未再検証）と、障礙台帳の未処理実例（→3.4）と、dissent の未解決残（→6.2）。**純資産は「いま、この現場が使える判断能力の実測残高」**であり、この数値が 7.6 の段3昇格条件（phronesis_fresh ≤ 6か月）の実体である。
**監査**：台帳の監査人（→6.6 の門番巡回の資産版）は、選定者本人ではない者——現場 A の手順の残高を、現場 B と本社が交互に測る。自己申告の残高は残高ではない（→4.4 の証拠条約の統治版）。

```cypher
// phronesis-balance-sheet — 判断能力の資産台帳(四半期自動生成)
CALL { MATCH (ra:RuleAdoption {act:'adopt'}) WHERE ra.status='active' AND ra.review_due IS NULL
       RETURN count(ra) AS never_reviewed }
MATCH (ra:RuleAdoption) WHERE ra.status='active'
WITH collect(ra) AS acts, never_reviewed
UNWIND acts AS ra
WITH never_reviewed,
     sum(CASE WHEN ra.review_due < datetime() THEN 1 ELSE 0 END) AS overdue,
     avg(duration.between(ra.at, datetime()).months) AS mean_age,
     count(ra) AS active_rules
MATCH (o:Obstacle) WHERE o.instance > datetime() - duration('P1Q')
WITH never_reviewed, overdue, mean_age, active_rules, count(o) AS fresh_obstacles
RETURN active_rules, mean_age, overdue, never_reviewed,
       active_rules - overdue - never_reviewed AS usable_balance, fresh_obstacles;
```

`usable_balance`（使用可能残高）の定義で重要なのは、**期限切れと未再検証を差し引く**ことである——存在する手順ではなく、検証が生きている手順だけが判断能力の資産である（→5.1 の更新経路が資産の「稼働状態」の条件）。fresh_obstacles（直近四半期の障礙実例）を貸借に並べるのも設計である——障礙の実例は負債の側ではなく**資産の更新需要**の指標で、実例が尽きている現場は資産が更新されずに老朽化している（stale_obstacles の台帳版、→8.1）。

この台帳の読者像を明示して節を閉じる。台帳の一次読者は**委任する側**である（→7.2 の委任深度の決定者）。「現場に任せる」の可否は、現場の sentiment（士気）でも実績でもなく、**残高**で決まる——残高を見ずに深度を上げる組織は、資産の裏付けなく信用供与をする銀行である。本書の委任設計（→7.2・7.6）が全部この台帳の参照で動く理由が、ここに集約される。

### 巡礼の回路 — phronesis の更新が 8.6 の課程に還るまで

7.1 で集めた判断能力の簿記（RuleAdoption・coin-term・salience 更新）が、個人の熟練で止まると 8.1 のプロレタリア化の逆の病——**属人化**（一人のフロネシスが組織の唯一の残高になる）が起きる。残高の属人化は、その人が抜けた瞬間に組織の phronesis_fresh をゼロに落とす（→7.6 段3 条件の崩壊）。処方は更新の**課程への還流**で、三本の通路で書く。**其一**、RuleAdoption の adopt/retire の理由列（because フィールド）が drill の教材本文になる（→8.4 の dissent 解決の教材化と同じ機制——**反論だけでなく选択も教科書**）。**其二**、coin-term の発生史（何時、どの障礙の実例から、誰が打ったか）が drill level 4 の「皿の外」課題の seed になる（→8.6 drill_forge——新しい語が生まれた状況を、次代の訓練に復元する）。**其三**、salience 更新の失敗（选択が現実に退けられた痕跡、effect-verification 失敗、→7.3）が level 5 の outside_frame 課題の素材になる（**破れた选択是最強の教材**——正解の反復は frame_conformity を育て、破れとの見直しは判断力を育てる、→8.1 個別化の装置）。

```cypher
// phronesis-to-curriculum — 更新の課程還流(季度 batch)
MATCH (ra:RuleAdoption {act:'adopt'}) WHERE ra.because IS NOT NULL
  AND ra.at > datetime() - duration('P6M')
  AND NOT (ra)-[:TAUGHT_IN]->(:Drill)
WITH ra LIMIT 30
CREATE (d:Drill {level:3, kind:'case-review', created:datetime(),
                 seed_ref:id(ra), text:ra.because})
MERGE (ra)-[:TAUGHT_IN]->(d)
RETURN count(d) AS drills_from_phronesis;
```

この batch が月次で走っていること（還流の自動化）が、7 章と 8 章の接缝である——**判断の歴史が訓練に還っていない組織は、老朽した残高を訓練の材料にも使っていない**（8.6 の periphery_coverage と 7.1 の残高が二つの別々の数字として計われているうちは、まだ回路が結ばれていない、→B.3 計器索引で二行が并んでいる意味）。

### 実行練習

1. あなたのルールの集合（業務手順・アラート閾値・Rego・shape を含む）から、過去1年「状況が変わったのに適用されたまま」の規則を3本特定し、`RuleAdoption`（act: 'salience.change' または 'adopt'）で登記し直せ（事後登記でよい）。登記の situation_evidence に何を添付するか（当時の Which decision log、Incident レコード）を決めよ。
2. `engine` 実験を自分のルールで再現し、運行中に集合が変わった事例（手動で追加した例外処理、運用スクリプト）を探せ。その追加が pool の外から来た事実（誰が、なぜ）を記録している仕組みの有無を確認し、なければ `RuleAdoption` の自動発火条件（どの変更イベントで型生成するか）を1つ設計せよ。
3. 「今夜は safety より continuity を上げる夜だ」をあなたの領域で1つ書け（例：生産停止回避より納期、あるいはその逆）。その読み替えを人間が判断として下した場合の RuleAdoption と、システムが既定値で実行した場合（＝E4 匿名宣言、→4.1）の差を、6.6 の落日条項の語彙で1段落評価せよ。

## 7.2 OODAループとミッション・コマンド — 現場に委ねる構造

前節で、規則選定の座は人間のフロネシスに残ると定めた。残したなら、その座が**速く座れる**ように設計しなければならない——状況が変わり続ける世界では、正しい判断が遅ければ不正な判断になる。この節は速度の哲学と委任の設計である。供給源は콜IN・ボーイの大佐（John Boyd）がベトナムの空戦から抽出した OODA ループと、プロイセン軍の伝統から現代の陸上自衛隊・海兵隊まで続く**ミッション・コマンド（任務指揮、Auftragstaktik）**である。軍の語に身構える読者に注ぐ——本書が借りるのは戦闘の技法ではなく、**分散した状況で委任された知をどう速く回すか**の、20世紀で最も実績ある組織設計学である。そしてこの二つは、第3章の GORE ゴール木と完全に接合する——ゴールを渡して手段を委ねる構造は、形式化されているのである。

### OODA — 観察・状況判断・決定・行動

ボーイの OODA（Observe–Orient–Decide–Act）を本書の部品に配線し直す。**観察（Observe）**：センサー・現場報告・他者の行動の流入。配線済み——テレメトリ（→1.2）、録音規則（→1.6）、CQ 駆動の読み取り（→4.2）。**状況判断（Orient）**：流入を既存の枠（文化・語彙・過去経験・モデル）に位置づける段。ボーイが「OODA の中心は Orient である」と書いたのは決定的で、Orient は**オントロジーそのもの**である——1.2 の分節、2.1 の残余、7.1 の第三層（新述語の必要性）がすべてこの段で起きる。**決定（Decide）**：候補から一つを選びコミットメントに昇格する段——JudgmentEvent（→5.1）。**行動（Act）**：世界への効果——ステートマシンの effect（→5.5）、現場 API（→7.5）。

重要なのはループの**速度ではなく周期構造**である。ボーイの中心概念は**内側時計（inner clock）**——主体が自身の行為連鎖の時間を内蔵していること——と、そこから出る**時間優勢（time advantage）**である。自分のループ周期が相手の変化周期より短ければ、相手の Orient が自分の新しい状況に追いつかず、相手は「遅れた世界」で判断する——あなたの行動が相手の想定を壊し続ける状態。逆に周期が長い主体は、いつまでも正しい判断をする資格を持っても、その資格を使える前に状況が変わって腐る（3.5 の verification_horizon の時間版、→6.6 の落日条項の時間版——**正しさには有効期限がある**）。

設計命令：**ループ周期は設計対象であり、SLA である。** 段ごとの時間予算を持たないパイプライン（→7.5 で実装する）は、Orient で無限に考え（LLM の候補生成が終わりなく深まり）、Decide で承認を待ち（承認者の不在が露見し）、Act が遅れる。周期予算は、**どこで待つことを許すか**の政治的判断である——承認待ちの時間を大きく取れば人間判断の質が上がります（→8.4 の人間設計）が、時間優勢を失う。この配分が本章の工学的中心であり、7.5 の SLA 設計として着地する。

### ミッション・コマンド — 意図ベースの指揮

ミッション・コマンドの原則を四つに凝縮する。**(1) 意図の伝達**：上位は「何を達成するか（目的）となぜ（意図）」を伝え、**手段を指示しない**。(2) **委任された自主性**：現場は状況を見て手段を選ぶ（7.1 の選定座の所在の組織実装）。**(3) 自己責任の受容**：現場は選定の責任を負う（accountability が委任と同時に移る——3.6 の「懲罰と名誉の器」が軍の制度として実在した例）。**(4) 相互信頼と補充通信**：命令が届かない・遅い状況を前提に、現場同士が横向きの通信で状況を補う（中央集権通信の障害への耐性——1.6 の沈黙設計、2.6 の団結権がここで戦術的機能を持つ）。

本書の読者は既にこの構造の形式語彙を所有している。**ミッション・コマンドは GORE のゴール木である。** 上位 goal form を SATISFIES 辺で下位要求へ分解する構造は「目的の伝達」であり、要求が *requirement* として手段の自由を残す層（3.3 の変換で「how」が lower 要求へ落ちる設計）は「手段の不指示」である。接合を形式的に示す。

```cypher
// mission_packet — ゴールを渡して手段を委ねる構造の Cypher 実装(→3.2 ゴール木)
// 上位 goal を引き受けた現場エージェントへ送る『委任書』: goal + 不変条件 + 予算のみ。
MATCH (g:Goal {goal_id: $goal_ref})
OPTIONAL MATCH (g)<-[:NEGATES]-(obs:Obstacle)   // 3.4 の障礙: 守るべき禁止は必ず添える
OPTIONAL MATCH (g)-[:ASSUMED_FOR*1..3]->(dom:Expectation)  // 3.2 の前提仮定: 環境側の約束
RETURN g.text AS intent,
       g.why  AS higher_purpose,               // 「なぜ」の添付必須(意図の伝達)
       collect(DISTINCT obs.text) AS inviolable,   // 障礙の否定 = 不変条件(何を壊してはならぬか)
       collect(DISTINCT dom.text) AS assumptions,  // 前提の露出(委ねる範囲の明示)
       g.decision_budget_sec AS clock_budget      // 内側時計: この goal の決定 SLA
```

`inviolable` と `assumptions` を委任書に必須同梱する設計に、本章の安全哲学が集約される。**手段を委ねるとは、禁止と前提を明示した上で委ねることである**——障礙（NEGATES 辺、→3.4）が添えられない委任は野放しであり、前提（ASSUMED_FOR、→3.2）が添えられない委任は、現場が環境の約束を知らないまま置かれる置き去りである（3.2 練習で作った `orphan_expectation` 検出が、ここで委任書の品質検査に転用される）。`decision_budget_sec` は Goal ノードのプロパティである——**時間予算は要求仕様の一部**であり（「30秒以内に決定できる粒度まで要求木を下ろす」は 3.3 の EARS 変換の品質基準になる）、後述の反実仮想（「予算が60秒なら何が変わったか」）は 4.5 の counterfactual のそのままの適用である。

### 委任の深さ — ゴール木のどこまで下ろすか

ミッション・コマンドの設計変数は**委任の深度**——ゴール木の何層まで「手段として現場に委ね、何層まで上位が固定するか」である。深度は要求木から機械的に決まるのではなく、三つの実測で決まる。其一、**委任された場の選定実績**：RuleAdoption（→7.1）の密度と品質——選定を任された場が過去に選定を更新し続けているか（フロネシス残高）。其二、**障礙の局在性**：障礙の大部分が現場の語彙で記述可能か（→3.4 の obstacle が context graph のどの領域に集中するか）。障礙が下層にあるほど、下層でしか判断できない（→5.5 の HSM の情報隠蔽と同型）。其三、**時間周期の実測**：その場のループ周期（観測→act）が上位の周期より確実に短いこと。

```python
# delegation_audit.py — 委任深度の三段監査
def delegation_readiness(session, goal_id) -> dict:
    g = fetch_goal(session, goal_id)
    return {
        "phronesis_balance": months_since(session, last_rule_adoption=g.site),  # 選定残高
        "obstacle_locality": obstacle_depth_ratio(session, g),   # 障礙の下層集中度
        "clock_fit": measured_loop_period(g.site) < g.decision_budget_sec,
        # ↑ 実測周期が SLA を満たさない場へ深度を下ろすのは、委任でなく丸投げ(→8.1)
    }
# 「clock_fit=False の場へ深度を下ろした」記録は 2.6 級 L2 の変更事件として登記する。
```

`clock_fit` の測定（measured_loop_period）が書式上の飾りではない点に注意を払う。**委任は宣言ではなく、周期の実測に基礎を持つべきである**——現場の実行周期より短い決定期限を下ろされた委任は、構造的に遅延し、遅延した委任は中央への再集中（マイクロマネジメント）へ必ず逆流する（軍の歴史の反復パターン——組織も OODA の時間優勢を失うと集権化する）。委任深度の監査を scorecard（→4.6）の項目に置く理由は、委任の逆流が**静かに**起きるからである（誰かが決めた事件ではなく、周期の実測値がじわじわずれる連続過程）。

### ボーイの警告 — Orient の硬直としてのミーム複合体

ボーイの late seminar（「Patterns of Conflict」「Science, Inference, and Uncertainty」）に、設計者に直接効く警告がある。Orient は既存の枠で読み替える段だから、**枠自体が敵に汚染できる**（ミーム複合体——想定・ドクトリン・KPI を操作され、勝手に間違った Orient に従う）。設計語で言えば、Orient = オントロジーであり、オントロジーは外部から書き換えうる（→2.4 の `sameAs` 事故、→6.3 の翻訳侵食が戦闘語で言い直されている）。KPI 最適化が目標のすり替えになる病（→3.2 の softgoal 計量化の危険）、指標の武器化（→6.6 腐敗三）、正規語彙への外部概念の浸透——ボーイの警告は本書の防腐層（第6部）と同一の敵を指す。

そしてボーイの処方と本書の処方は同じ構造を持つ：**枠の硬直への解毒は、枠の外を見せる強制ではなく、枠自体を速く更新し続けられる循環の保持である**（ボーイの「be the GUMBO（未知なるものを受け入れる存在）」、本書の落日条項・CQAmendment・TermMapping 版数更新の循環——→6.6「防腐は運動としてのみ存在する」）。第6章の統治が組織の新陳代謝なら、OODA の時間優勢はその新陳代謝の**速度仕様**である。

### 委任の診断 — 三検査の不合格パターンと是正の順序

delegation_audit の三検査（phronesis_balance・obstacle_locality・clock_fit、→前掲）は、個別の合格/不合格だけでなく**不合格の組み合わせ**で診断が変わる。三つの典型的組合と、是正の順序を確定する。

**組合一「時鐘速・判断遅」（clock_fit 不合格 + phronesis 残高不足）**：現場の周期は速いが、判断能力の残高が足りない。最頻の現場は、高速な異常（振動・欠品・ネットワーク喪失）に対して現場が場当たり（影子 act、→6.6）で処理し、その場当たりが履歴に載らないため残高がさらに増えない悪循環にある（→5.1 の更新経路欠如の現場実装）。是正の順序は残高から——まず場当たりを Quarantine に登記可能にして経験を簿記化し（→5.6 の残余保存）、その実例から RuleAdoption を現場の語で起案できるようにする（coin-term 通路、→7.1）。時間予算を緩める是正（待ち時間を増やす）は逆効果である（周期は現場の物理で決まり、遅い周期は影子の判断を温存するだけ）。
**組合二「判断速・時鐘遅」（残高潤沢 + clock_fit 不合格）**：判断できる人が居るのに、中央の承認・エスカレーションが周期を殺している。典型的な司令塔化（→5.3）。是正は深度から——mission packet の inviolable 障礙を最小に削り（→7.2 の「守るべきものを減らす」設計）、E4 前提を増やして中央承認の級を下げる（→2.6 の級運用）。残高が有るのに深度が上がらない組織は、統治の恐怖（→2.6 の級 inflation の原因）を先に治療すべきで、訓練（残高増）は無駄になる。
**組合三「障礙遠」（obstacle_locality 不合格）**：障礙が現場の手の届かない定義になっている（例：安全係数の変更が本社の 18 か月承認）。これは委任の問題ではなく**境界の問題**（→6.1 の条約・→2.6 の級）で、是正は委任スレッドではなく条約審議に上がる。現場の周期予算（decision_budget_sec）に 18 か月承認の障礙が混在している goal は、スレッドではなく議案として処理すべき goal である（→4.5 の UNKNOWN 宣言の統治版——処理できないものを処理中と書かない）。

三組合の診断表を、mission packet の審査 checklist に加える（→4.4 の CQ の委任版——委任の CQ。「この委任の三検査は何か」「是正の順序は何か」「障礙の級は現場側か条約側か」）。この check を置かないと、delegation_audit は合格/不合格の羅列になり、診断が行動に化けない——**検査と席の接続**（→4.6 のテスト失敗→ticket、→6.2 の dissent→討議槽と同じ設計原則の三度目の出現）。本書の設計原則の一つをここで名乗っておく。**あらゆる検査は、失敗の行き先（席）まで設計して初めて検査である。**行き先のない検査は、やがて実施されなくなる（検査の落日、→6.6）。

### mission packet の実物 — 現場に渡す「守るべき最小」の YAML

委任（→前掲の mission command）の成果物——mission packet——の実物一つを完全に置く。中央が現場に渡すものは、命令文でなく**約束の最小集合＋現場の自由**である。

```yaml
# missions/m-2026-114.yaml — mission packet 実例
mission: pump-line-cavitation-watch
intent: "気蝕の再発を 72h 内に見つけて系列停止を避ける。止める判断は現場。"
inviolable:                     # 破ってはならぬ制約(中央の権限)
  - "安全係数 1.4 未満での再加圧禁止(E1 実測級,→4.1)"
  - "人の立入り中のライン停止は解除手続き必須(→4.4 invariant)"
end_state:                      # 成否の判定(現場が中央に返す語)
  - "cavitation の原因候補が RuleAdoption 相当で登記済み"
  - "effect_verification 済みの抑止 act が 1 つ以上稼働"
free_methods: ["act:throttle", "act:flush", "新語提案(→7.1 coin-term)", "act 順序の再構成"]
budget: { decision_budget_sec: 90, hours: 12, escalate_if: "inviolable の変更が必要な場合" }
assumptions:                    # E4 前提級—崩れたら packet ごと審議
  - "供給圧力データの連続取得(→5.2 revalidation 対象)"
contact: "中央は status のみ。指示はしない(指示が欲しければ審議槽に載せ)"
```

この packet の読みの要点を三つ。**inviolable が 2 本だけ**——中央が守らせるものを減らすことが委任深度を上げる（→前掲の設計判断：inviolable の長さは委任の不信の長度）。**end_state が act でなく状態**——現場が达した成否を中央の語（graph:// URI、→1.4）で返させる（返還可能性が自由の条件、→9 章の delegation 実験一の簿記条件）。**assumptions の崩坏が escalate_if**——前提の破れが「上長への判断の投げ」ではなく**packet の失効**として定義される（→3.4 N4、→5.2 手放し——委任は前提の上に立つ、前提の死は委任の死）。`contact` の一行を組織は書けない——書くと命令が戻る。よってこの一行は packet の哲学であり、mission command の日本語版である。

### 実行練習

1. あなたの業務の主要決定1本に OODA 四段の時間予算を置き（例：Observe 即時／Orient 90秒／Decide 承認待ち 10分／Act 5秒）、実測周期を1週間測れ。Orient と Decide のどちらが支配的かを特定し、その配分が「どこで待つことを許すか」のどんな政治的判断を暗黙に表明しているか（→7.2 の「周期予算は政治的判断」）を1段落で明文化せよ。
2. `mission_packet` をあなたのゴール木の中間ノード1本に実行し、inviolable と assumptions が空列で出たら、3.2・3.4 の登記のどこが欠けているかを特定せよ。`decision_budget_sec` をその goal に設定し、3.3 の EARS 変換が予算内の粒度で書けているかを照合する検査（→4.6 の core regression の追加項目）を1本書け。
3. `delegation_readiness` をあなたの組織の委任実態1件で実行せよ（phronesis_balance = その現場が過去12か月で規則・手順を自分たちで更新した回数）。clock_fit=False（現場周期 > 期限）なのに委任が置かれている場を特定し、深度を1層戻す／SLA を延ばす／周期を短縮するの三択から級つきで決めよ（委任の逆流は事件として登記する——理由と期限を添えて）。

## 7.3 Actionable Ontology — 記述から処方へ

オントロジーは世界を記述する——これは本書の第1部以来の基盤である。しかし記述だけのオントロジーは、読み物として死ぬ。会議で参照され、検索でヒットし、しかし**世界を何も変えない**。この節では、オントロジーに処方の層を加える——**状態から、次に何ができるかを導出できるようにする**。Actionable Ontology（実行可能オントロジー）とは、状態記述（descriptive）に加えて、**行動・前提条件・効果・実行権限**の語彙を含むオントロジーである。7.1 のフロネシスの議論を正確に引き継ぎながら進む：行動ノードは「何をすべきか」を**決定しない**（決定は JudgmentEvent の側、→5.1）。行動ノードは「**何が今、できることとして開いているか**」を機械に読ませる。選定の座は人間のまま、その座に届く皿をオントロジーが用意する。この違いを一度失うと、7.5 のパイプラインは即座に危険物になる（決定も処方も機械がやる設計——5.3 の司令塔化の完全版）。

### 処方の語彙 — 行動ノードと三辺

処方の語彙を四要素で定義する。行動（Action）ノードと、それを結ぶ三種類の辺である。

**Action ノード**：`action_id`、`kind`（停止・増感・割当・通知・検査…）、`actor_class`（誰の類が実行しうるか）、`effect_spec`（効果の宣言——世界へのコミットメントの記述形）、`risk_class`（低／中／高——6.4 の方針が参照する危険級）、`intent_link`（この行動が仕える goal への辺、→3.2）。

**前提条件の辺 `REQUIRES`**：Action ノードから状態述語ノードへ。「`stop-line` は `line-running` を要求する」——前提が現状グラフで成立するとき、行動は**開く**（enabled）。

**効果の辺 `EFFECT`**：Action ノードから状態述語へ、`polarity`（+／−）つき。「`stop-line` は `line-running` を消し、`line-stopped` を生む」——効果は**宣言であって実行ではない**（実行は 7.5 の act段で API が担い、宣言は計画と説明の材料になる）。

**実行権限の辺 `CONTROLS`**：エージェント（人間・機械）から Action ノードへ。3.5 の realizability で敷設した `CONTROLS` 辺が、ここで満員の使われ方をする——**権限はオントロジーの内部にある**。この辺なしの Action 実行は、構造的に帰属のない暴力である（→3.6 の `orphan_action` 検出が、この層で初めて本気で機能する）。

```cypher
// 処方層の敷設(3.5 の CONTROLS と 3.6 の実行主体を行動ノードへ接続)
CREATE (a:Action {
  action_id: 'act.stop-line.v3', kind: 'stop',
  actor_class: 'HumanShiftLead',            // 誰の類向けかの宣言(実行資格ではない)
  effect_spec: "NOT line-running; line-stopped",
  risk_class: 'high',
  api_ref: 'site-api://line/M-7/stop',      // 実行の実体(→7.5)。宣言は API の仕様版数を指す。
  intent_link: 'goal://safety/prevent-bearing-failure'
});
CREATE (a)-[:REQUIRES]->(st:StatePred {pred: 'line-running', on: 'M-7'});
CREATE (a)-[:EFFECT {polarity: '-'}]->(st);
CREATE (a)-[:EFFECT {polarity: '+'}]->(st2:StatePred {pred: 'line-stopped', on: 'M-7'});
// 実行権限の辺は 3.5 で既に定義済み(CONTROLS)。agent の種別による許可規則は
// 3.6 の『機械 agent への soft 要求禁止』の行動版として Rego が担保する(→6.4)。
```

`api_ref` が**仕様版数を指す**点を強調する。API の挙動が変われば `effect_spec` の宣言が嘘になる（宣言と実体のずれ——1.5 のドキュメントとコードのずれの処方層版）。CI で「API 仕様変更 → 対応 Action の effect_spec 再検証タスク自動発生」を結ぶ（→4.6 の回帰思想の処方向け版。`effect_spec` が検証対象になるのは 7.6 の統合テストで実装する）。

### enabled_actions — 「いま何がableか」の照会

処方の中心的照会を置く。現状グラフの事実と `REQUIRES` 辺の照合で、開いている行動を列挙する。これは決定ではなく**候補の供給**である（EvidenceBundle の frame_options 供給、→5.3——オントロジーが frame-making の権利を担う場所、→7.1 の第三層の機械的最少版）。

```cypher
// enabled_actions: 現状事実で前提が成立している行動の列挙(候補供給)
MATCH (a:Action)-[:REQUIRES]->(sp:StatePred)
WITH a, count(sp) AS req_total,
     sum(CASE WHEN EXISTS { MATCH (sp)<-[:HOLDS]-(:Observation {fresh: true}) }
         THEN 1 ELSE 0 END) AS req_held
WITH a, req_total, req_held
WHERE req_held = req_total                       // 全前提が成立(『fresh』=観測の鮮度窓内)
OPTIONAL MATCH (ag:Agent)-[:CONTROLS]->(a)
WITH a, collect(ag.agent_id) AS controllers
WHERE size(controllers) > 0                      // 権限 holder のいない Action は候補に出さない
MATCH (a)-[:EFFECT]->(eff)
RETURN a.action_id, a.kind, a.risk_class, controllers,
       collect(eff.polarity + ':' + eff.pred) AS effects_declared
ORDER BY a.risk_class DESC;                      // 高リスクを先頭に(提示順=content、→5.3)
```

設計判断を三つ注釈する。其一、**権限 holder のいない Action は候補から落とす**——3.6 の `orphan_action` が enabled 照会に組み込まれ、執行不能な候補が判断の皿に載らない（皿に載るだけなら無害に見えるが、frame-making の汚染は必ず実務コストになる——現場が「実行できない選択肢」に時間を割く）。其二、`fresh: true` の鮮度窓——前提の成立は**いつの事実か**に依存する（→2.5 の時刻代数）。窓の長さは goal の `decision_budget_sec`（→7.2）から導出する：予算の内で使える観測の鮮度。其三、`ORDER BY risk_class` の提示順の設計——高リスクから先に出す順は安全の順ではなく**注意の配分の順**である（低リスクの行動が埋もれて見えない＝過剰リスク回避の逆転、→5.3 の順序効果の知識を処方 UI に適用する。順の設計自体が DesignDecision 登記対象、→5.5）。

### 記述だけのオントロジーが読まれるだけになる理由

本節の主題の裏面を論じる。Action・REQUIRES・EFFECT・CONTROLS を持たないオントロジー（第1部・第2部までで敷設した語彙だけ）は、なぜ参照はされても運行しないのか。三つの構造的理由。

其一、**閉ループがない**：記述オントロジーの出力（照会結果）は人間の読解に入り、人間の行為へは配線されない。行為→観測→記述の更新の環が、行為の段で断線している（OODA の Act→Observe の切断、→7.2）。其二、**反実仮想が使えない**：4.5 の counterfactual が「制約を緩めると何が壊れるか」を計算できたのは、制約が機械可読だからだが、記述だけの体系では「この語彙で記述したまま行動を変えたら」を計算する場所がない——処方層は反実仮想の**行動版**（「この Action を開いたら／閉いたら世界がどう変わるか」）の計算基盤になる。其三、**責任の辺がない**：CONTROLS なき体系では、実行の帰責が運用の慣習に逃げ、履歴代数と接続しない（2.5 の原則が語彙層に届いていない状態）。

処方層の追加は、この三断線を一度に結ぶ——行為が配線され（act段）、反実仮想が計算され（EFFECT 宣言の伝播）、帰責が辺になる（CONTROLS と actor 簿記）。ただし処方層の危険も同時に置く：**処方が読める体系は、処方が撃てる体系でもある。** enabled_actions が候補ではなく指令として扱われる道（5.3 の司令塔化）は、処方層の直ぐそばに開いている。本章全体の安全設計（5.5 のステートマシン、6.4 の方針門、7.4 のエージェント分離）は、この開いた道に柵をする設計である——**処方を持つオントロジーには、防腐層が前提条件として必要である**（第6章が第4部より前に来た編成順序の理由が、ここで説明される）。

### 処方の循環 — 効果の宣言と効果の実測の突合

処方層を腐敗から守る計器を最後に置く。EFFECT 宣言は未来への約束であり（「stop-line は line-stopped を生む」）、約束は実測と突合されねば腐る（2.3 の保持寿命）。実行後、観測が約束した状態述語を `HOLDS` で受け取ったかを突合する。

```cypher
// effect_verification: 宣言効果と実測効果の突合(ActionExec -> Observation 突合)
MATCH (x:ActionExec {exec_id: $id})-[:FIRED]->(a:Action)-[e:EFFECT]->(sp:StatePred)
OPTIONAL MATCH (sp)<-[:HOLDS]-(obs:Observation)
WHERE obs.at > x.at AND obs.at < x.at + duration($window)
RETURN e.polarity, sp.pred,
       CASE WHEN obs IS NULL THEN 'effect-missing'     // 宣言した効果が発生していない
            ELSE 'effect-held' END AS status;
// 効果の不在が繰り返される Action = 処方層の腐敗(宣言が嘘)。
// 落日条項(→6.6)の処方版: 効果実測の保持率で Action の生存を決める。
```

`effect-missing` の集計は Action の信頼残高であり、保持率の低い Action は enabled 候補から自動的に降格する（Warning→自動退役、→6.6 の落日の循環が処方層にも回る）。逆に「宣言していない効果」の検出（突合の逆方向：実行後の新 `HOLDS` が EFFECT 辺にない）は、**副作用の発見**である——副作用の発見は KB の更新要求（CQAmendment・REQUIRES/EFFECT 辺の追加）として審議槽へ供給される。処方層は宣言で閉じた体系ではなく、**宣言と実測の差分を食って更新される循環**である（6.6 の「運動としてのみ存在する」の処方版）。

### Actionable Ontology の会計 — 処方の資産価値と負債計上

処方化（記述→処方、→前節の Action・RuleAdoption の link）を、維持コストの観点から一回だけ会計する。処方は資産であるが、**未検証の処方と落日した処方（E4 前提の期限切れ、→4.1）は負債である**（→7.1 の減価償却の処方版）。処方資産の会計表を定義する。

| 勘定科目 | 中身 | 計上規則 |
|---|---|---|
| 資産:稼働処方 | review_due 内の RuleAdoption＋実測付き Action | effect_verification 成功計数つきで計上（→7.3） |
| 資産:候補処方 | Quarantine の候補（未 adopt だが供給源あり） | 審議槽への供給計数為価値（→7.1 の皿の材料） |
| 負債:落日処方 | 前提 E4 期限切れ・review_due 超過 | 実行禁止・警告帯（hollow-fluent、→5.2） |
| 負債:孤児処方 | 引用する記述（TBox 語）が削除・改名された処方 | roundtrip 検査が検出（→6.3 の CRITICAL の処方版） |
| 償却費用 | 処方の再検証（revalidate）の実働時間 | 時間予算に計上（→8.2 条件三） |

```cypher
// prescription-ledger — 処方資産の四半期貸借
MATCH (r:RuleAdoption) WHERE r.act='adopt'
WITH r, CASE WHEN r.review_due < datetime() THEN 'liability-expired' ELSE 'asset-live' END AS cls
WITH cls, count(r) AS n
UNION
MATCH (a:Action)-[:REQUIRES]->(t) WHERE NOT (t)-[:LIVES_IN]->(:TBox)
RETURN 'liability-orphan' AS cls, count(a) AS n;
```

会計の目的は、**処方数の増加を資産成長と誤読しない**ことである。処方の残高（処方条項の総数）だけを見るチームは、負債（落日・孤児）を分子に含めた成長報告をする（→6.6 腐敗——統計が燃料でなく外観になる）。資産表は「稼働処方の実測残高」と「負債の滞留年齢」の二本を並べ、負債の滞留が閾値（例：総処方の 15%）を超えたら**新処方の制定を凍結して償却に人手を回す**（→8.2 の再解釈労働の予算の会計実装——新しいものを作る前に、古いものを問い返す時間に人を配る。この凍結規則のない体系は、処方のインフレで通貨価値（=処方の信頼）を失う）。

この会計は 3.1 の四原因の貸借への橋でもある——処方の資産価値の本体は final cause（目的因）の勘定に載る（処方が生きている goal に link されているか、goal の落日で処方は自動的に負債側に落ちる、→3.1 の telos_chain の落日）。記述が form cause の台帳なら、処方は final cause の台帳である—— actionable ontology の維持とは、目的の存続を機械的に追うことなのである。

### Actionカードの六字段 — 処方を読み解くための券

7.3 の Action ノード（処方）を、人間が read できる形=Action カードとして仕様の締めに置く（→8.5 の offer が Action の UI 表示である理由がここで揃う）。六字段：**act_id / intent（何をする語ではなく何のためか、→3.1 final cause の字段）**、**preconditions（E1 実測級の条件+観測 URI、→4.1 宣言の級）**、**effect（書き换える世界状態の宣言、→7.3 の辺）**、**withdrawal（effect が退く条件——→5.3 の確率の withdrawal_conditions の処方の行動版：いつまで有効かを書かない処方は落日しない処方で、落日しない処方は老朽する処方、→5.2 hollow-fluent）**、**seat（この act の异議・落日・改訂の席の URI、→6.6・8.2 の席の字段——席のない処方は執行だけあっても直し手が届かない）**、**history（adopt の日・再検証の日・effect_verification 集計、→4.4 証拠条約·→7.1 残高）**。

```cypher
// action-card — 六字段の CQ(「この処方を読み解けるか」の質問形)
MATCH (a:Action) WHERE a.risk_class IN ['low','medium'] AND a.status='active'
OPTIONAL MATCH (a)-[:ADOPTED_BY]->(ra:RuleAdoption)
OPTIONAL MATCH (a)<-[:EFFECT_VERIFIED]-(ev:EffectEvent)
RETURN a.act_id, a.intent IS NOT NULL AS has_intent, a.withdrawal IS NOT NULL AS has_withdrawal,
       EXISTS { MATCH (a)-[:SEAT_OF]->(:DelibSlot) } AS has_seat, count(ev) AS verifications
ORDER BY has_intent, has_withdrawal, has_seat LIMIT 20;
```

この照会の輸出順が重要で、**字段の欠落が先頭に来る**（read できない処方から先に直す——処方の庫の整頓順序は、庫の側ではなく人間の側で決まる）。withdrawal と seat の欠落は、7 章の自動化（段1〜2、→7.6）で最も高くつく——退き時を書かない自動 act は demote（→7.6 の降格自動）の条件を機械が計算できないからである。**字段が欠けた処方を自動走らせない**は 7.3 の最後の命令文であり、実行則は test_safety_fall（→7.6）の六障害テストに字段検査として織り込まれる。

### 実行練習

1. あなたの KB（2.4 の TBox）に処方層を敷設し、中心業務1本の Action を3つ（低・中・高 risk 各1）、REQUIRES/EFFECT/CONTROLS 辺 記述 に登録せよ。`enabled_actions` を現状データで実行し、候補がゼロで出た場合、そのゼロの意味（前提の成立失敗か、権限 holder 欠落か、鮮度窓切れか）を分解して報告せよ——ゼロ候補は世界の状態の宣言である（→5.4 の「候補ゼロ」）。
2. 処方層がない状態（今の KB）と敷設後で、4.5 の counterfactual の行動版を1本ずつ走らせよ（「`stop-line` の REQUIRES に `two-approvals` を足したら、enabled の平均遅延と夜間カバレッジがどう変わるか」）。差分表を作り、REQUIRES 追加の級（→2.6）と DesignDecision 登記（→5.5）の文案を書け。
3. `effect_verification` の保持率計をあなたの実際の自動化手順（スクリプト・RPA・承認フロー）に当て、宣言と実測のずれを3件見つけよ（典型：「メール送信済み」宣言で実際は迷惑フォルダ、→宣言と実体の層、1.5）。ずれの 各 について、宣言を直すか実測窓を直すかを級つきで決め、EffectSpec の version をどう回すか（→2.4 の版数原則の処方版）を1段落書け。

## 7.4 マルチエージェント編成 — LangGraphで判断の流れを作る

処方層まで敷いた（→7.3）。次は実行の編成である。ただし本書の「マルチエージェント」は、AI 人格を並べて会議させる話ではない——**判断の連鎖を、異なる信頼級・異なる時間予算・異なる権限を持つ計算段に分割し、その間を形式化された会話で繋ぐ**ことである。ツールとして LangGraph を選ぶ理由は、それがまさにこの分割のフレームワークだからだ——状態グラフ（StateGraph）で計算（ノード）と制御（辺）を分離し、人間の介入点（interrupt）と永続化（checkpointer）を一級の概念に持つ。LangGraph のドキュメントが強調する通り、エージェント向けのグラフは「ループ・永続化・human-in-the-loop」のためにある（→5.5 のステートマシンとの接続は明記する：LangGraph は状態機械の計算機である。本章の設計命令——ガードは決定論、LLM は候補生成のみ——は LangGraph 上でもそのまま有効である）。

### 状態グラフ — 節点=計算、辺=制御

LangGraph の基本語彙を本書の設計語彙へ翻訳する。**State**（共有される型付きデータ。TypedDict/Pydantic で宣言し、ノードはこれを読み書きする——**状態はグラフの一等市民**であり、5.5 の状態（スナップショット）と意味は同じ）。**ノード**（状態を受けて計算し、状態の部分的更新を返す函数。ノードは辺を知らない）。**辺**（固定遷移と条件分岐。条件辺の述語は**決定論でなければならない**——→5.5 のガード命令の LangGraph 版。`add_conditional_edges(router)` の router 函数に LLM を入れてはならない）。**checkpointer**（各スーパーステップ後の状態の永続化——履歴代数の計算機、→2.5。中断・再開・タイムトラベル（過去状態からの再生）がフレームワークの基本機能である事実は、本書の歴史代数の設計とちょうど噛み合う）。

ここで本章の中心図を置く。四エージェントの分離である。

```
[観測] --deterministic--> [提案] --deterministic--> [検証] --deterministic--> [決定(人間)] --deterministic--> [実行]
  SensorAgent              ProposeAgent            VerifyAgent               interrupt()            ActAgent
  (計算・決定的)            (LLM 許容)              (Rego+SHACL+sat 決定的)   (JudgmentEvent)         (API・決定的)
```

四段の分離の理由を、信頼級で明記する。**観測**：決定的計算（テレメトリの正規化、→1.2、状況照会 `enabled_actions`、→7.3）。**提案**：LLM が唯一関与を許される段（候補生成のみ、→5.4 の PureLlm・Candidate 型・env digest）。**検証**：決定的計算（6.4 Rego・6.5 SHACL・4.5 sat の三層ゲート、→6.5 の gate_pipeline）。**決定**：人間の interrupt——承認ではなく**判断**（→5.1 の実効的承認：根拠の再検証可能な形で提示する）。**実行**：決定的計算（現場 API 発火、effect_verification 接続、→7.3）。

分離の核心は、**LLM が検証・決定・実行のノードに物理的に入れない**ことである（→5.5 の「遷移関数の内側の候補生成のみ」のグラフ実装）。LLM が検証ノードに入れないことは、自分の生成物を自分で通せる構造（司令塔化の最も密な形）を排除する。LLM が router（辺）に入れないことは、制御の決定論（→5.5 ガード命令）を守る。

### 実装 — LangGraph による四段グラフ

```python
# orchestration.py — 四エージェント分離の LangGraph 実装(決定論的辺・LLM は提案段のみ)
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.types import interrupt
from llm_wrapper import PureLlm, LlmEnv          # 5.4 の部品
from gate_pipeline import gate                    # 6.5 の三層ゲート
from ontology_query import enabled_actions        # 7.3 の候補照会

class Flow(TypedDict):
    situation: dict            # 正規化された状況(観測段の産物)
    candidates: list[dict]     # Candidate dict(env digest 込み、→5.4 provenance)
    verdicts: list[dict]       # ゲート判定(通過・violations・warnings)
    decision: dict | None      # JudgmentEvent リンク(人間判断)
    exec_result: dict | None
    clock: dict                # 段別時間予算の実測(→7.2 の内側時計)

def n_observe(s: Flow) -> Flow:
    sit = normalize_telemetry(s["situation"])          # 決定的
    sit["open_actions"] = enabled_actions(sit)         # 7.3 の候補照会(決定的)
    return {**s, "situation": sit}

def n_propose(s: Flow) -> Flow:
    llm = PureLlm(transport); env = LlmEnv(model_ref=ENV_MODEL, temperature=0.2,
                                           seed=42, sys_prompt_version="v9")
    cands = [c.model_dump() for c in candidate_pipeline(   # 5.4 の pipeline
        llm, KB, prompt_for(s["situation"]), env)]
    return {**s, "candidates": cands}                  # ← LLM はここでだけ触れる

def n_verify(s: Flow) -> Flow:
    vs = [gate(c, GRAPH, SHAPES, policy_input(s, c), sat_of(s, c))
          for c in s["candidates"]]                     # 6.5 三層ゲート(決定的)
    return {**s, "verdicts": vs}

def router_after_verify(s: Flow) -> Literal["decide", "quarantine"]:
    # 辺の述語は決定論(→5.5 ガード命令)。LLM 判定を制御に入れてはならない。
    return "decide" if any(v["stage"] == "pass" for v in s["verdicts"]) else "quarantine"

def n_decide(s: Flow) -> Flow:
    # 人間の判断点を interrupt で開く(承認ボタンではなく判断の皿、→5.1・8.5)。
    payload = {   # EvidenceBundle 相当(→5.3): 候補・根拠・却下理由・反証条件
        "candidates": s["candidates"], "verdicts": s["verdicts"],
        "rejected": [v for v in s["verdicts"] if v["stage"] != "pass"],
        "evidence_panel": panel_url(s),                 # 再検証可能性の実体(→8.5)
    }
    d = interrupt(payload)               # 停止→checkpointer が保存→人間応答で再開
    return {**s, "decision": d}

def n_act(s: Flow) -> Flow:
    if not s.get("decision") or not s["decision"].get("approved_action"):
        return s                          # 判断なしで世界は変わらない(設計不変条件)
    r = fire_api(s["decision"]["approved_action"])      # 決定的実行
    return {**s, "exec_result": r}

def n_quarantine(s: Flow) -> Flow:
    rec = quarantine(s["candidates"], s["verdicts"])    # 5.6 の Quarantine(残余保存)
    return {**s, "verdicts": s["verdicts"] + [{"stage": "quarantined", "q": rec.q_id}]}

g = StateGraph(Flow)
for name, fn in [("observe", n_observe), ("propose", n_propose), ("verify", n_verify),
                 ("decide", n_decide), ("act", n_act), ("quarantine", n_quarantine)]:
    g.add_node(name, fn)
g.add_edge(START, "observe"); g.add_edge("observe", "propose")
g.add_edge("propose", "verify")
g.add_conditional_edges("verify", router_after_verify,
                        {"decide": "decide", "quarantine": "quarantine"})
g.add_edge("decide", "act"); g.add_edge("act", END)
g.add_edge("quarantine", END)
app = g.compile(checkpointer=PostgresSaver.from_conn_string(CPN),
                interrupt_before=[])   # interrupt() 内蔵割込で止まる
```

設計不変条件の二重化に注意せよ（→5.6 と同じ構造）。`n_act` 冒頭の「判断なしでは世界は変わらない」に加え、`n_decide` が interrupt で**人間の応答そのものを state に載せる**——checkpointer により、停止中の状態と再開後の判断が履歴として残る（タイムトラベル機能は、→4.5 の counterfactual の実行版である：過去 state に戻り、別分岐を再生して比較できる。監査と教育の両方で使える——→8.6 の練習設計）。

### 「司令塔なき編成」の会話プロトコル — 候補・根拠・反証の形式

四段は会話する。その会話の形式が、司令塔なき編成の条件である——**どの段も他の段に命令できず、形式付きの差し出ししかできない**。提案段は検証段へ命令できない（候補を渡すのみ）、検証段は決定段へ命令できない（判定と missing を渡すのみ）、決定段は実行段へ「どの候補か」しか渡さない（方法の細部は Action ノードの宣言が担う、→7.3）。会話メッセージの最小形式を Pydantic で置く。

```python
# message_format.py — エージェント間会話の形式(候補・根拠・反証の三つ組)
class Exchange(BaseModel):
    """段の間に流れる唯一のメッセージ型。命令(kind='order')が存在しないことに
    注目せよ——形式が権限を表現している(→5.4 Candidate に apply がないのと同型)。"""
    kind: Literal["candidate", "verdict", "evidence", "counter-evidence", "judgment"]
    sender: str                      # ノード名+policy 版数(話者の資格の登記)
    reply_to: str                    # どの差し出しへの応答か(会話の因果連鎖)
    payload: dict                    # candidate は provenance 必須、verdict は missing 必須
    dissent: str | None = None       # 不服従の表明(6.2 の dissent が会話形式に常住)
```

`kind='order'` が型系に**存在しない**こと——これが「司令塔なき編成」の定義である。権限はグラフの辺（制御）とゲート（方針）にのみ住み、メッセージ語彙には命令がない。人間から機械へも `judgment`（コミットメント）であって `order`（方法の命令）ではない——ミッション・コマンドの会話版（→7.2 の意図ベース指揮が、メッセージ型の設計に落ちる）。`dissent` の常置も 6.2 の均衡装置の会話版で、dissent を含む Exchange は履歴代数に載り審議槽へ供給される。

### 失敗の編成 — 各段の失敗の安全な受け

各段の失敗モードと、グラフ上の受けを対応表で閉じる。観測段の失敗（テレメトリ欠損）→ `enabled_actions` の候補ゼロ → Quarantine エンド（→5.4 の候補ゼロ宣言）。提案段の失敗（LLM タイムアウト・schema 外）→ 候補ゼロ宣言＋漂移記録（→5.4 repro_check）。検証段の失敗（判定 UNKNOWN）→ horizon 記録つきの Warning 通過か、goal の `decision_budget_sec` 超過で Quarantine（→3.5 の UNKNOWN 扱い）。決定段の失敗（人間応答なし）→ **time-boxed interrupt**：時間予算内で応答なければ、安全側既定（`risk_class: high` の候補は実行しない＝Quarantine で停止、low risk の通知のみ実行可——既定値は E4 宣言で、期限つき、→4.1・6.6 の落日）。実行段の失敗（API 失敗）→ effect_verification 突合で `effect-missing`（→7.3）→ 再提案ループ（グラフの辺を quarantine→observe に戻すオプション、→7.6 で解禁）。

注意すべきは決定段の「人間応答なし」の設計である。**人間を待たせることを安全策と思い込んではならない**——無限待ちは時間劣位の自己受注（→7.2）で、現場が影子の判断（承認なしの場当たり）へ流出する（→6.6 影子 KB の判断版）。time-boxed interrupt の予算配分（何を待ち、何を既定で安全側へ置くか）は、→8.4 の人間配置設計そのものである。

### LangGraph の故障三型 — checkpoint・loop・interrupt

委任パイプライン（→前掲の LangGraph 実装）の故障を三型で inscribe する（A.4 障害目録六・七の 7 章詳述）。**故障一：checkpoint 消失**。checkpointer の thread_id が段で違い、resume が初めから再走——初めから走ると**人間の承認セグメントが再次走らない**（interrupt は恢復されない、承認は 1 回限りの簿記——承認の再走禁止は 8.5 の単一同意原則と同一）。処方：thread_id の一本化断言（→A.4 五条）＋ resume 時に「承認済みセグメントの再走ゼロ」の assert（checkpoint に `approved_segments` 列表）。**故障二：loop 爆炸**。条件分岐が障礙で戻る辺を持ち、障礙解決→再試→同障礙→再試の環（7.2 の clock と loop の冲突）。処方：段総数上限（graph に `max_supersteps`）＋環の回数を障礙の実例に数え載せ、2 回目で Quarantine（**環は障礙で、障礙は席を持つ**——3.4 の障礙台帳がループ検測の届け出先、検査と席の接続）。**故障三：interrupt 宙吊り**。人間猶予（→8.5 hold_seconds）が切れた場合の黙認動作が未宣言——graph が停止したまま無事を装う（沈黙の破れ三、→5.2 の透明化のパイプライン版）。処方：interrupt に `on_timeout` を強制（デフォルトは安全側 demote＝7.6 の自動降格。猶予切れ=承認拒否と書く——8.5 の「無応答は同意でない」の graph 実装）。

三型の共有項：いずれも**パイプラインが止まる/戻る/消える故障で、世界には何も起きない**こと——つまり故障そのものは安全側（安全不変条件 5、→7.6 の世界変更ノード不動）。危険は故障でなく**故障の処理**にあり、loop の再試が障礙を無視して回し、宙吊りが無事として落日をすり抜ける。よって三型のテスト（test_loop_escape・test_interrupt_timeout）は段昇格条件に載せる（→7.6 段昇格条件に「故障テスト通过」が預めって載る理由）。

1. `orchestration.py` を自分の領域の業務1本に書き換え、`n_propose` 以外のノードに非決定的要素が入っていないかを lint で検査せよ（禁止 import 検査：`llm_wrapper` の import を propose ノードのファイルに限定する grep/AST テストを1本書け）。

## 7.5 実線パイプライン — 状況検知 → ACL検証 → Action発火

部品は揃った（検知→1.2・7.2、候補→7.3、編成→7.4、防腐→6.4〜6.5、監査→5.6・6.4）。この節は配線である——テレメトリが POST されてから現場 API が撃たれ、効果が記録されるまでを、一本の実線で通す。中心に置く概念は**時間予算（time budget）**——OODA の内側時計を SLA として実装する設計（→7.2）——と、**完全な監査トレース**（「なぜその Action が撃たれたか」の機械的回答）である。実装は FastAPI（入口）・LangGraph（編成、→7.4 の `app`）・Neo4j（状況と履歴）の三層で、本書のデモ系（保全現場）の完動版を 7.6 に残し、本節は骨格と設計判断を全部出す。

### 入口 — FastAPI エンドポイントと入口簿記

```python
# ingest_api.py — テレメトリ受信(入口の ACL、→6.1 の入り口防腐の API 版)
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

api = FastAPI()

@api.post("/telemetry")
async def ingest(req: Request):
    body = await req.json()
    # 入口 ACL: 外部テレメトリ語彙 → 正規語彙(TermMapping、→6.1)。
    # 解決不能な telemetry 種別は TranslationFailure として 406 で返すが、
    # payload は Quarantine レコードに保存する(残余保存、→2.1・6.1)。
    norm, failure = acl_in.translate_telemetry(body)
    if failure:
        save_quarantine_input(body, failure)          # 捨てない: 条約改訂の供給源
        return JSONResponse(status_code=406, content=failure.model_dump())
    # 入口簿記: actor・受信時刻・source 版数を Commit でなく IngressEvent として載せる(→2.5)
    log_ingress(norm, actor=req.headers.get("x-source"), at=now())
    # 相関 ID でグラフ実行(thread)を開始・再開: 状況の相関=スレッド(→7.4 thread_id)
    thread_id = correlate_thread(norm)                 # 同一 asset/shift の連鎖に相関 ID
    app.invoke(norm_to_flow(norm),
               config={"configurable": {"thread_id": thread_id}})
    return {"thread_id": thread_id}
```

`correlate_thread` を入口設計の要として置く。**状況は独立イベントの列ではなく、相関する連鎖である**（1.2 の「状況」概念の実線版）。同一機械・同一シフト・同一障礙（→3.4）のイベントが同一 thread（OODA の一つのサイクル列）にまとまり、checkpointer がその列の状態を進化させる（→7.4）。相関規則（何が同一スレッドか）は決定論で、E4 宣言・落日つき（→6.6）でなければならない——相関規則は「何が一つの状況か」の定義であり、**状況の分節**（→1.2）の運用時版だからである。相関規則の変更は L2 変更（→2.6）である理由もここで明記される。

### 中段 — 状況照会と候補（→7.3 の照会の実線内での位置）

`norm_to_flow` 内の状況照会を、実線の時間制約の中で確定する。Neo4j への照会 three 本（`enabled_actions`、当該 goal の mission packet の `decision_budget_sec`、障礙 `NEGATES` 一覧）の budget を合計 300ms に固定し、超過時はクエリを kill して候補ゼロ宣言（→5.4）へ落ちる。時間予算配分（Observe 300ms / Propose 8s / Verify 1.5s / Decide human-window / Act 2s）は、goal の `decision_budget_sec` から逆算される（→7.2 の「要求仕様の一部」の実装——予算の階層：全体予算 > 段予算 > クエリ予算。超過の每一段が `clock` 計測（→7.4 の Flow.clock）に載り、scorecard（→4.6）に段別 p99 が上がる）。

予算超過の処理は「遅いなら止める」ではなく、**遅い段の状態を宣言として残す**（UNKNOWN 宣言、→3.5 の教訓）。kill されたクエリの partially-bound results は保存し、再試行の起点にする（残余保存の性能設計版）。

### 出口 — Action発火と effect_verification

```python
# act_client.py — 現場 API 発火(実行段の最小実装・宣言と実体の版数突合つき)
import httpx

def fire_api(decision: dict) -> dict:
    a = load_action(decision["approved_action"])        # Action ノード読取(→7.3)
    spec_ver = a["api_ref"].split("@v")[-1]             // 宣言が指す API 仕様版
    live_ver = httpx.get(a["api_ref"].rsplit("/", 2)[0] + "/spec-version").json()["version"]
    if spec_ver != live_ver:
        return {"status": "stale-spec", "declared": spec_ver, "live": live_ver}
        # ↑ 宣言と実体のずれ(→1.5・7.3)を『撃つ前に』検出して止める。
        #   ずれの検出は L1 事件として effect-missing より深刻(宣言が既に嘘)。
    resp = httpx.post(a["api_ref"], json=decision.get("params", {}), timeout=2.0)
    record_exec(a, decision, resp, at=now())            # ActionExec 登記(→7.3 突合の起点)
    return {"status": resp.status_code, "exec_id": last_exec_id()}
```

`stale-spec` の検査が発火の**直前**に走ることの重要性。CI で宣言と実体の突合を常時回すが（→7.3 の CI 接続）、CI の週次周期に対し API 変更は毎日起こりうる——発火直前の突合は、最後の防波堤である（多重防御、→5.6・6.4 の原則）。`stale-spec` は実行拒否だが、deny の説明（missing フィールド、→6.4 の decision log）として「Action の effect_spec 再検証タスク」を自動生成し、審議槽に載せる（遮断は討議の燃料、→6.2）。

### 監査トレース — 「なぜこのActionが撃たれたか」の完全な回答

完全な説明の構造を定義する。説明の要求形式（→5.5 の「説明＝再生」、→4.5 の counterfactual、→5.3 の basis_reckoning）が、実線で初めて埋まる。

```cypher
// why_action: ActionExec からの完全説明トレース(一発照会)
MATCH (x:ActionExec {exec_id: $id})<-[:FIRED]-(a:Action),
      (x)-[:ANCHORED_IN]->(je:JudgmentEvent)-[:JUDGED_ON]->(eb:EvidenceBundle),
      (x)-[:INSIDE]->(:Transition {exec_ref: $id}),
      (a)-[:INTENT]->(g:Goal)
OPTIONAL MATCH (eb)-[:DERIVED_FROM]->(c:Candidate)   // 候補の provenance(env digest)
OPTIONAL MATCH (je)-[:RESPONDS_TO]->(ra:RuleAdoption) // 規則選定の歴史(→7.1)
RETURN a.action_id, g.text AS served_goal,
       x.guard_snapshot,                              // 発火時点のガード実測値(→5.6)
       c.provenance AS candidate_env,                 // どの reckoning の産物か(→5.4)
       eb.frame_options, eb.llm_role,                 // 材料形成の全容(→5.3)
       je.decider, je.revalidation_path,              // 誰の判断か・再検証の実体(→5.1)
       ra.rule_ref, ra.decider AS rule_by, ra.at AS rule_at   // 規則は誰がいつ選定したか(→7.1)
```

この一発照会が返す七つの要素が、説明の完全性の定義である：仕える目的（g）、発火時点の事実（guard_snapshot）、候補の由来（candidate_env）、材料形成の全容（frame_options）、判断者と再検証経路（decider/revalidation）、規則の選定史（rule_by/rule_at）。要素が一つ欠けると、説明は物語になる（→5.3 の尤度の物語化）。よって**why_action が NULL を返すフィールドの数**を scorecard の指標に置く（説明の完全率、→8.3 の説明設計の機械的床がここで定義される——8章の「理由を問い直す UI」は、この照会の表示装置にすぎない）。

### 時間予算の監査 — 内側時計の黒字・赤字

パイプライン全体の実測周期（ingest→act、interrupt を含む wall-clock）と、mission packet の `decision_budget_sec` の差分を thread ごとに記録する。**予算超過の thread は、その goal の委任が時間的に破綻している事件**である（→7.2 clock_fit の実測）。月次で budget_deficit の上位 goal を listing し、委任深度の引き上げ／SL 引き上げ／段予算の再配分の三択を E3 審議に自動で載せる（→6.6 の落日・再審議の循環が時間予算にも回る）。時間予算は E4 の一形態である——期限が過ぎたら自動で警告に降格する（落日条項の時間設計版）。

### スレッド相関の失敗形 — 状況の分節を誤ると何が壊れるか

`correlate_thread`（→前掲）の設計を、失敗形の目録で締める。相関規則は「何が一つの状況か」の分節（→1.2 の境界問題の実線版）であり、分節の誤りはパイプラインの全段に増幅して伝播する。

**失敗一：分割過剰**（一つの障害が複数スレッドに割れる）。各スレッドは部分状況しか持たず、候補生成が部分状況に対して正しい act を出す（部分対策の重複・重複 act）。検出：重複 act の asset・時刻窓突合（→練習3 の query がこれ）、および「同一事象への複数 thread の co-active 状態数」の scorecard 化。処方：スレッド相関に asset 横断の link（同一 commit・同一班次）を含める——ただし link の定義は E4 宣言で期限つき（相関規則自体が老朽化する、→5.2 の手放しの設計）。
**失敗二：分割不足**（無関係な二事象が同一スレッドに融解する）。状況 digest が混濁し、検証段の前提照会が雑に通り、判断の皿が二つの世界の候補を混ぜる。最頻の危害は「混濁したスレッドの act が、片方の世界では正しく他方では副作用」（→7.3 の effect_verification が検る側面——effect-missing ではなく effect-extra として現れる）。検出：同一スレッド内の `NEGATES` 対立ペア（一方の act の effect が他方の goal を壊す、→3.4 の障礙のグラフ内発火）。
**失敗三：相関の取りこぼし**（同じ障害の実例が別世界として永遠に並列）。障礙の更新（→3.4 の N1/N2）が起きず、stale_obstacles を増やす（→8.1 第四段の実線経路）。

```cypher
// thread-integrity — 相関規則の健全性(週次)
// 過剰分割の代理指標: 同一 asset・短窓で co-active thread 数
MATCH (t1:Thread), (t2:Thread)
WHERE t1.asset = t2.asset AND t1 <> t2 AND t1.status='active' AND t2.status='active'
  AND duration.between(t1.opened, t2.opened).minutes < 60
WITH t1.asset, count(DISTINCT coalesce(t1.tid,t2.tid)) AS co_active
RETURN t1.asset, co_active WHERE co_active > 2 ORDER BY co_active DESC;
```

相関規則の変更運用を一度明記しておく——相関規則の変更は L2 級（→2.6）で、**変更直後の 2 四半期は分割・統合の両指標を監視する**（規則変更そのものが障礙の発生源になる、→3.4 の制度変更障礙）。相関規則を「実装の詳細」として無級で扱う系は、状況の分節を無級で書き換えている——2.6 の中心定理（意味の変更は統治イベント）が、実線パイプラインの一段で再発しないよう、ここで級を確定する。

### SLA の実装 — decision_budget_sec の計算と警告帯

7.5 の時間予算（decision_budget_sec、→7.2 の mission packet 設計）を、稼働する SLA として実装する。予算は「待つな」ではなく**待つ深さの宣言**である（→7.2 の命令：判断の周期が世界の周期に遅れるな）。実装は三段。

**其一、消費の計上**：パイプラインの各段（observe→verify→decide）は、経過秒を Thread に `budget_spent` として更新する（→6.4 監査簿記の列 `budget` に同一の数が載る——SLA の数値は簿記と同一源でなければならない、二重定義禁止、→5.5 宣言簿記の運用版）。**其二、警告帯**：消費が予算の 70% を超えた段で、decision は面板に `budget_pressure` の印を載せる（→8.5 の面板——猶予を短縮するのではなく、猶予の重さを見せる：SLA が猶予を溃さない、→8.5 の衝突解決规則の実線版）。**其三、預算枯渇**：budget_spent >= budget の時、decide は「选択」でなく **Quarantine 起票**を选ぶ（時間の中で判断できない場合、世界の方を調べる——障礙 N5 周期超过、→3.4。預算内で強行に选んだ act の簿記には `hurried: true` が走り、effect_verification 優先度を上げる——急いだものは強く検收する）。

```python
# sla.py — 予算計上と警告帯(pipeline 各ノードの共通脚)
def budget_check(thread, stage_sec):
    spent = thread.budget_spent + stage_sec
    if spent >= thread.decision_budget_sec:
        return Route.QUARANTINE, spent          # 予算枯渇→障礙 N5 起票
    flag = spent >= 0.7 * thread.decision_budget_sec
    return Route.NEXT, spent, ("budget_pressure" if flag else None)
```

`Route.QUARANTINE` の意味を哲学側から一環——判断できない状態を「判断しなかった」と書かず「預算の障礙が起きた」と書く（3.5 の三段構えの SLA 実装。UNKNOWN を UNKNOWN として登記する機構が、ここで動作として現れる）。7.5 の全段（correlate→acl→gate→act→why）が共通脚 budget_check を通すことで、SLA は规定ではなく計器になる——四半期ごとの budget_pressure 発生率と Quarantine 起票率の組み合わせが、「この系統の判断は世界の速さに付いているか」の唯一の誠実な報告である。

### 実行練習

1. `ingest_api.py` を自分のテレメトリ（Webhook・Kafka・バッチ取込）に移植し、入口 ACL の TranslationFailure を 406 で返す配線を実験せよ。unknown 種別1件を Quarantine に載せ、その Quarantine が TermMapping 改訂（条約 v(N+1)）に化けるまでを 6.1 の語彙で1段落報告せよ。

### 統合テスト — 障害注入と安全側検証

中心のテスト群を書く。テスト哲学は 4.6 の ontology regression と同一だが、対象が系全体に広がる。シナリオは 3.4 の障礙の語彙で書く（障礙 = 目標の否定、テスト = 障礙の実例注入）。

```python
# tests/test_safety_fall.py — 障礙注入テスト(→3.4 の障礙をテスト名に使う)
import pytest

@pytest.mark.parametrize("obstacle,expect", [
    # 障礙(O1): LLM が不正候補(unknown term)を生成
    ("llm-invent-term",      {"final": "quarantined", "world_changed": False}),
    # 障礙(O2): ポリシーが遮断すべき書込を候補が提案(例: llm→master 直書)
    ("llm-writes-master",    {"final": "blocked-rego", "world_changed": False}),
    # 障礙(O3): 人間応答なし(time-boxed interrupt 超過、→7.4)
    ("no-human-decision",    {"final": "safe-default", "world_changed": False}),
    # 障礙(O4): 宣言と実体のずれ(stale-spec、→7.5)
    ("api-spec-drift",       {"final": "stale-spec", "world_changed": False}),
    # 障礙(O5): ゲート後・act 前の状態変更(TOCTOU)
    ("state-changed-after-verify", {"final": "re-verify", "world_changed": False}),
    # 障礙(O6): KB の前提 Expectation が失効(ASSUMED_FOR 辺の失効)
    ("assumption-expired",   {"final": "blocked-mission", "world_changed": False}),
])
def test_safety_side_on_obstacles(session, obstacle, expect):
    inj = inject(obstacle, session)              # 障礙を世界に注入fixture
    final = invoke_flow(session, inj.telemetry)  # 実線全段を通す(7.4 の app)
    assert final["stage"] == expect["final"], f"{obstacle}: {final}"
    # world_changed=False の検証 = act が撃たれていないことのグラフ証明:
    assert count(session, "MATCH (x:ActionExec {thread:$t}) RETURN x",
                 t=inj.thread_id) == 0
    # 残余保存の検証: 障礙は必ず記録に残る(握りつぶし禁止、→4.1 残余条項)
    assert count(session, f"MATCH (e) WHERE e.event_of=$t AND e.kind<>'IngressEvent'") >= 1, \
           f"{obstacle}: 障礙が歴史に載っていない(=蒸発、→5.3)"
```

`world_changed=False` を**グラフで証明する**設計が安全側テストの核心である。戻り値の文字列ではなく、`ActionExec` ノードの不在を照会する——実行者が捏造できない形で検証する（4.4 の「契約違反は例外でなくデータ」の系譜で、**安全条件は戻り値でなくグラフ不変条件**）。O5（TOCTOU）の `re-verify` は 5.6 のステートマシンが act 直前に現状照会を再実行する設計の実装確認である（verify→act の間に世界が変わったら、verify の verdict は古い——verdict に `situation_digest` を添え、act 直前の digest 突合で再検証を強制する）。

`event_of` の残余検証（第三アサーション）で、テストが**記録の義務**まで検査している点を注ぐ。安全側に倒れるだけでなく、倒れたことが歴史に載らなければ、それは学習しない安全である——6.6 の運動としての防腐が、テストの断り書きとして書き込まれている。

### 運用設計 — 段階的権限委譲（read-only → propose → act）

本番の弁を三段で開ける。各段の**昇格条件は数値で宣言**され（E1 級の実測可能条件、→4.1）、降格条件も数値で宣言される（落日条項の運用版、→6.6）。

**段1 read-only（3か月）**：システムは状況照会・候補提示・レポート生成のみ。act なし。昇格条件：`why_action` 完全率 ≥ 0.98（→7.5 の説明の完全率）、段別 p99 が予算内（→7.2）、Quarantine の週次開封率 ≥ 0.8（→5.6 の見逃し防止——開かれない Quarantine は安全の偽称）。

**段2 propose（6か月）**：高リスク以外（`risk_class ≤ medium`）の act を、人間判断必須のまま自動実行（interrupt の time-boxed 既定を「medium 以下は承認あれば実行」に拡張）。昇格条件：段1 の四指標維持 + **effect_verification 保持率 ≥ 0.95**（→7.3 の宣言と実測の突合）+ dissent の審議解決率 ≥ 0.7（→6.2 の槽が実際に回っている証拠）。

**段3 act 拡大**：high risk の act を、判断必須のまま開く。昇格条件は上記維持 + **RuleAdoption の滞留月齢 ≤ 6**（→7.1 の選定残高——現場が選定を更新し続けていることが high risk 委任の前提）。

```python
# rollout_gate.py — 昇格/降格条件の実測(デモでなく毎週計算される『弁の機械』)
def promotion_readiness(session) -> dict:
    m = scorecard_metrics(session)       # 4.6 + 7.2 + 7.5 の統合 scorecard
    return {
      "read_only": dict(why_complete=m.why_action_complete >= 0.98,
                        clock_p99_ok=m.all_segments_in_budget,
                        quarantine_opened=m.q_open_rate >= 0.8),
      "propose":  dict(effect_held=m.effect_verification >= 0.95,
                       dissent_resolved=m.dissent_resolution >= 0.7),
      "act":      dict(phronesis_fresh=m.rule_adoption_age <= 6),
      # 降格条項(落日): どの指標も 2 週連続で閾値未満なら自動降格・事件登記。
      "demote": {k: m.below_two_weeks(k) for k in ("why_complete","effect_held")},
    }
```

`demote` の自動発火を人間判断に任せない設計の理由を明記する。**昇格は人間が承認し、降格は数値が自動発火する**——非対称であるべき権限の弁である（安全側の非対称、→3.5）。人間の承認だけで降格する系は、降格の政治的コスト（失態の告白）に負けて、権限が開いたまま老朽化する（6.6 の落日条項が統治層で要求したものと同一の構造）。

### デモの最終確認 — 一剑の実演

最後に、デモの通し実演の手順（本書の全体系が一本の線で走る瞬間）を記す。(1) テレメトリ POST（`vib=51, sound=metallic-rattle`）。(2) 入口 ACL が `metallic-rattle` を TranslationFailure にする——条約 v8 に無い語（→6.1 の残余）。payload は Quarantine に載る。(3) 正規化された `vib` だけでスレッド進行：`enabled_actions` が stop-line（high）と inspect（low）を開く（→7.3）。(4) LLM 候補生成（env digest 記録、→5.4）、`metallic-rattle` を KB 語彙で書き換えた候補が SHACL Warning（narrative、→6.5）を伴って通過。(5) OPA が stop-line の Rego 判定を allow（前提成立、級あり、→6.4）。(6) interrupt で人間の皿が開く——候補二つ、根拠（frame_options）、却下理由（Quarantine）、反証条件（→5.3・8.5 の形式）。(7) 人間が stop を選む（JudgmentEvent・EvidenceBundle 接続、→5.1）。(8) act 直前の digest 突合通過（→O5）→ 現場 API 発火、`ActionExec` 登記。(9) 観測が `line-stopped` の `HOLDS` を返し effect_verification 保持（→7.3）。(10) `why_action` が七要素全部を返し（→7.5）、Quarantine の `metallic-rattle` が TermMapping v9 提案（→4.2・6.1）の審議槽に自動で載る——**未知の語が条約改訂に化けるまでが、一本の実線で見える**。

この10ステップは本書の全章の通過儀礼である——1章の状況、2章の履歴と権力、3章の目的と障礙、4章の契約と検証、5章のreckoning/judgment とステートマシン、6章の防腐、7章の処方と時間。統合テストの `test_safety_fall` が同じ線を逆から殴る。**動く哲学書とは、この10ステップが CI で毎日走ることを意味する。**

### 昇格と降格の決定表 — 三段を結ぶ六行

段設計（→前掲）の昇格/降格を、六行の決定表で缔ぶ（段は片道でなく双方向——**自動化は常に巻き戻せる構造でなければ、自動化ではなく既成事実**、7.1 の可謬性の段版）。

| 事象 | 決定 | 根拠 |
|---|---|---|
| 六障害テスト通过＋落日周期つき前提清単 | 段1→段2 | 前提の落日=末端の巡回(5.1) |
| effect_verification 30 件対 27 通过 | 段2 維持 | 通过率為不是落日周期の関数(7.3) |
| effect 通过 0 件(hollow、5.2) | 段2→段1 | 手放しの実証消滅=手放しの取消 |
| 障礙 N4(前提崩壊)1 件 | 該 act 段1、其余維持 | 障礙局在(7.2 delegation_audit) |
| 落日審議者=0(無人運行) | 段2→段1＋審議槽起票 | 末端の消滅は段の問題でなく判断の消滅(5.1) |
| dissent 率 5%超(8.4) | 段3 全面停止→段1 | 現場の不服従=委任の撤回(7.2) |

表の読みを一環——**下方向の決定は機械が執行し、上方向の決定は人間が署名する**（段2→段1 の demote は自動、段1→段2 の promote は落日審議の署名を要する。非対称の理由：安全は退避で取れ、退避は速い方が良く、前進は遅い方が良い——→8.5 の「猶予は速い系の前に跪く」の段設計への配線）。この非対称が表の全行を贯いていることを明示的に認める——自動 demote を恐れるチームは、六障害テストの 1 本目（test_safety_fall）が**自動退避そのもの**であることを見れば、退避こそがテストで守られているものだと分かる。
