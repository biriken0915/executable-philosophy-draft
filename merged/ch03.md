## 3.1 アリストテレスの四原因説と目的因（telos）の復権

第1部が「知とは何か」を問う存在論・認識論だったのに対し、第2部から本書は問いの方向を変える。「このシステムは**何のために**存在し、そのために知っていることは**十分か**」——十分性の問いである。この問いを近代科学は失くした、とよく言われる。正確に言えば、失くしたのは世界の説明から目的を排除したことではなく、目的を**形式化不能な残り物**として追放したことである。要求工学（requirements engineering）は、その追放された目的を、実務の必要から形式的な市民権とともに再入城させた学問である。アリストテレスの四原因説は、その再入城の地図として提示する。単なるオマージュではない——四原因説は、現代の要求分析ツールが「なぜ未だ分割できていないか」を示す、2300年早い診断表である。

### 四原因 — 説明の四方向

アリストテレスは『自然学』第二巻で、変化の説明には四種類の「なぜ」があると説く。用語を現代語に翻訳して置こう。

**質料因（material cause, hyle）**：何から作られているか。 bronze（銅）が銅像の質料である。ソフトウェアで言えば、実行資源・データ・既存資産（レガシーコードも質料である——質料は形状を抵抗し、抵抗が設計を規定する）。

**形相因（formal cause, eidos）**：何であるかを決める形・構造。図像の輪郭。ソフトウェアではアーキテクチャ、データモデル、オントロジー——**定義そのものが原因として働く**という発想は、形相因の復活である（→1.5の「ラベルは存在論的宣言」、→2.4のTBoxがABoxを制約する構造）。

**動力因（efficient cause, kinoun）**：何によって作られたか。彫刻家。現代では「作業者・プロセス・CI/CD・エージェント」（→3.6のエージェントモデルは動力因の形式化である）。

**目的因（final cause, telos）**：何のために作られたか。銅像の場合は「飾られた広場を美しくすること」。近代力学はこれを自然から追い出した（目的なしに物体は動く）。だが人工物から目的を追い出すことはできない——人工物に目的がなければ、それは完成の定義を持たず、完成の定義を持たない人工物の良否は測定不能になる。

この最後の推論を、要求工学の中心定理として置いておく。**目的因を持たないシステムの良否判定は原理的に不可能である。** 性能指標（speed、uptime）は形相因と動力因の内部測度にすぎず、「できばえ」の判定には「何のために」が必要である。KPI が暴走するとは、目的因なしに形相因の指標が目的のふりをする現象の名前である。

### 四原因と現代の要求モデル — 診断表として使う

要求工学の標準的な概念を四原因で再配列すると、未分割の問題が見える。

| 四原因 | 要求工学での継子 | よくある未分割事故 |
|---|---|---|
| telos | ゴール・ビジョン・softgoal（→3.2） | 「要求文書にあるが telos がない」——機能は列挙されているが目的文が無い |
| formal | データモデル・オントロジー・受入条件 | 目的文なしに形相が先行し、「作れるが要らないもの」が完成する |
| efficient | チーム・プロセス・実装主体 | 「誰が実現する（whether it can be done by this team）」が目的分析の後で初めて問われる |
| material | 既存資産・制約・技術的負債 | レガシーを「障礙」扱いし「質料」扱いない——質料は設計を規定する（→3.4の障礙分析の区別） |

最終行の区別を強調する。障礙（obstacle, →3.4）と質料（material）は違う。障礙は「ゴールを妨げる出来事」であり除去対象だが、質料は「ゴールを実現する媒体」であり、質料を無視した設計は障礙を無限に発生させる。レガシー資産を障礙台帳に載せる組織は、永遠に障礙を除去し続ける。質料台帳（技術的負債の「資産」としての棚卸し）を書く組織だけが、形相を質料に適合させる——アリストテレスで言えば、質料に先立つ形相は存在しない。

### telos の形式化 — 「目的」を論理式に翻訳する手順

それでは telos を形式化できるのか。できる、ただし限定付きで。telos の「内容」（なぜその目的を選ぶのか）は形式化できない——これは実践知（phronesis）の領分であり、第5部まで引っ提げる残題である。形式化できるのは telos の**構造**である。「G は S のために存在する」という関係の構造——実現関係・充足関係・優先関係——を論理で記述できる。要求工学のゴール指向分析（→3.2, van Lamsweerde）は、まさにこの構造の学である。

telos 記述の最小構文を、本書のオントロジーに載せる形で定義する。

```cypher
// ゴールの telos 層: 「G は P のためにある」を辺で持つ。
// 目的の正当化は別の Goal ノードとして、無限後退を許容する形でつながれる。
// 無限後退を「許容する」のが要点である。telos 連鎖の末端（axiological root）は
// 人間が引き受ける価値であり、論理の外に置く。論理の外に置くことを形式化する。
MATCH (g:Goal {goal_id: $gid}), (p:Goal {goal_id: $pid})
CREATE (g)-[e:ACHIEVED_FOR {
  justification: $free_text,      // 自由文必須。「なぜなら」を機械に書かせない
  depth: 2,                       // telos 連鎖の深さ。3以上でループ警戒flag
  axiological_root: false         // 末端はこの flag で宣言される
}]->(p);

// 循環検出: telos 連鎖は循環してはならない(目的が目的を循環して支えるとき、
// システムは内部で自己正当化する)。
MATCH path = (g:Goal)-[:ACHIEVED_FOR*3..]->(g)
RETURN g.goal_id, length(path) AS cycle_len;

// 孤立ゴール検出: ACHIEVED_FOR の上向きの辺を持たないゴールは、
// 「そのために存在する目的が無い機能」= telos 不在の機能。
// 本章の診断定理により、これらの良否判定は原理的に不可能である。
// 放置ではなく「telos を持つことを放棄した機能」として明示的にラベルする。
MATCH (g:Goal) WHERE NOT (g)-[:ACHIEVED_FOR]->()
SET g.orphan_goal = true,
    g.abandonment_declared_at = datetime();
```

`abandonment_declared` の設計判断を説明しておく。telos の無い機能は存在してはならない、と厳格にやると、現場は telos を嘘で埋める（「安全のため」「効率のため」）。目的文のインフレは telos のない世界より悪質で、目的が偽名で保護された無目的は批判の対象から外れるからである。したがって、孤立を罪ではなく申告された状態として扱う。孤立申告率は組織の健全性指標になる——嘘で塗り固めた組織は孤立申告ゼロになる（この指標のゲーミング対策は 4.6 の契約テストと結合する）。

### 目的因の追放と復権の歴史 — なぜ近代はこの問いを失ったのか

telos 復権を「アリストテレスを戻そう」というノスタルジーとして読まれたら困る。追放には理由があり、理由は現在も有効である。近代的自然科学は、目的を自然に認めた瞬間に万物有霊化へ退行する（石が落下するのは「落りたい」という目的のためか、という難問）。目的を自然から追放した代わりに、近代は目的を**主体の設計**へ退避させた。人工物にのみ目的を認める。しかしこの退避は不安定である。主体（設計者・人間）を自然の一部と認めるなら、人工物の目的も自然現象の一部であり、追放は自己言及的に崩れる。生態学と行動経済学は今日、自然の中に「機能」「適応」「ヒューリスティクス」という目的に似た語彙を戻している。

本書の設計の立場からすると、この二百年の揺れの実務的教訓は次の一文になる。**目的を形式化から追放すると、目的は形式化の外から（隠れた形で）システムを支配し続ける。** 「最適化」の目的を宣言しないデータパイプラインは、最後に残った計測可能な指標（ログ行数、レイテンシ）を目的として黙って採用する。目的の不在は中立ではない。既定値が目的になる、という静かな発火事故である。

第1章の暗黙知、第2章の分類の暴力と、ここでの telos は同じ主題の三面である。**明示されなかったものは、不在ではなく、既定値として効く。** 暗黙知は形式化の外で知を規定し、残余は分類の外で意味を規定し、未宣言の telos は目的の外で評価を規定する。第2部の仕事は、三つの「外」をそれぞれ形式化の縁に引き寄せることだ——障礙分析は残余の形式化（3.4）、competency questions は残余の意味の形式化（4.2）、goal tree は telos 連鎖の形式化（3.2・3.3）にほかならない。

### 現場の失敗例 — telos なき自動発注システム

抽象論を、実際に起きた型の失敗で締める。ある部品の在庫システムが「欠品の自動検知と自動発注」を導入した。要求文書には機能（形相因）とベンダーと開発体制（動力因）、ERP連携と在庫データ（質料因）が書かれていた。telos の欄には「在庫最適化」と書かれていた——これは telos ではなく形相的な指標である。真の telos——「ライン停止をゼロにし、その上で在庫資金を最小化する」——は書かれていなかった。結果は教科書通りである。システムは欠品を検知し、発注し、欠品は減った。在庫資金は倍増した。どちらの指標も「最適化」されたから、システムは要求通り動作した。**要求は満たされ、目的は裏切られた。** この一文を要求工学の第一定律として記憶してほしい。telos の形式化（goal tree と softgoal の競合記述、→3.2・3.6）は、この定律を破綻前に検出するための唯一の機械的装置である。

### 目的因の復権を組織設計に橋を架ける — 四原因のチェックリスト運用

四原因説（→前掲の material/formal/efficient/final）を、要求レビューの運用チェックリストとして実装する。哲学者の分類を会議の語彙に変えるのは、**目的因の欠落が個人の不注意ではなく、会議の進行手順の欠陥**であることを証明するためである（構造の設計で人格を治療する——本書の一貫した方法）。

レビューの各項目に、検査質問と不合格時の登記先を定める。**材料因**「この要件は、どの実在（観測・データ・既設機構）の上に立つか」→ 実在の参照が一つも無ければ goal の root 欠落として障礙候補登記（→3.4）。**形式因**「この要件の完了状態は、どの構造の完成として記述されるか」→ 構造語彙（グラフの語、→1.3）で書けない要求は CQ 化して審議槽へ（→4.2 の問いに直す設計）。**作用因**「誰が・どの資源で実現し、中間成果物の連鎖は何か」→ 作用因の記述は委任設計の入力になる（→7.2 の mission packet の assumptions）。**目的因**「これは何のためにで、その上の目的が今も有効か（落日・実測）」→ 目的因の鎖条が E4 前提（→4.1）で期限切れなら、レビューは要求の妥当性を論じる前に前提の再承認を要求する。

```python
# review_gate.py — 四原因レビューの機械検査(会議前の自己申告をデータ化)
class RequirementReview(BaseModel):
    req_id: str
    material_refs:  list[str]     # 材料因: 実在参照(≥1)
    form_struct:    str | None    # 形式因: 完成状態の構造記述(graph:// URI)
    agents_budget:  dict | None   # 作用因: 主体と資源
    telos_chain:    list[str]     # 目的因: goal_id の連鎖(root まで)
    def holes(self) -> list[str]:
        h = []
        if not self.material_refs: h.append("material")
        if not self.form_struct:   h.append("form")
        if not self.agents_budget: h.append("efficient")
        if not self.telos_chain:   h.append("final")
        return h
```

`holes()` の返す穴の名前が、そのまま会議の議題になる（原因の名前は欠陥の名前でもある——四原因は完成形の分類ではなく、**欠陥の四分法**として実運用される）。目的因の穴が最頻である事実を、レビュー統計（holes の分布）として四半期に一回報告する——この統計が組織の「目的の空洞化」の唯一の定量証拠になる（→4.6 の scorecard の要求工学版）。

最後にアリストテレスへの最深的な注釈を置いておく。四原因説の近代における追放（力学が材料因と作用因だけになり、目的因が「主観的価値」として科学の外へ追いやられた——→2章・5章の事実/価値切断の系譜）は、要求工学の「目的を書く場所の欠如」として戻ってきた。目的因の復権とは、古代哲学の輸入ではなく、**追放されたはずのものが現場で必要され続けていた**ことの発見である（→telos は消えたのではなく、書けない語になっていた——書ける語に戻す作業、→1.4 の可言明化の設計が、ここで三千年前の分類にまで及んでいる）。

### 目的の時制 — 近い目的と遠い目的の衝突を goal 木で検出する

目的因（→前掲）は単独で老朽化するのではなく、**目的同士が時間で衝突する**。短期 KPI（今期の稼働率）と遠い目的（設備寿命・技能継承）が goal 木で兄弟・叔父甥になる時、機械的に検出できる衝突が生まれる。設計は二つ。**其一、goal 節点に時間地平（horizon: near/far）を載せる**（near = 当期 act で到達、far = 落日周期 12 か月超）。**其二、near goal の effect が far goal を NEGATES（→3.4 N2）する辺を、goal 木レビューの自動照会に出す**——「稼働率を上げる act 列が、継承（→終章）の far goal を壊している」型の構造は、会議では「どちらが重要か」の意見分裂に化けるが、goal 木では**辺の欠落**として表示される（NEGATES の辺が結ばれていない=冲突が未知、3.2 検査三の完全性宣言の目的間版）。

```cypher
// telos-time-conflict — 近い目的→遠い目的の妨害辺(未知の冲突)を発見
MATCH (n:Goal {horizon:'near'})-[:HAS_SUBGOAL*0..2]->(:Goal)-[:HAS_ACTION]->(a:Action)
      -[:EFFECT]->(e)-[:NEGATES]->(f:Goal {horizon:'far'})
RETURN n.goal_id AS near_goal, a.act_id, f.goal_id AS far_goal
UNION
// 未宣言の冲突: effect が far goal を削る統計的痕跡(実測側)
MATCH (a:Action)-[:EFFECT_MEASURED {sign:-1}]->(f:Goal {horizon:'far'})
WHERE a.at > datetime() - duration('P1Q')
RETURN a.act_id, f.goal_id, 'undeclared-telos-erosion' AS kind;
```

`undeclared-telos-erosion` の意味をこの節の主題に接続する——遠い目的は act による侵食を**実測でしか知らない**（宣言された NEGATES 辺は設計者の想定、実測の sign=-1 は世界の返答。両者の差分が 3.3 の翻訳表と放棄表の目的版——宣言されず侵食されている目的は、放棄表にも載っていない目的である）。遠い目的の落日（→3.1 telos_chain の落日設計）は、この侵蝕統計の閾値発火で促される：far goal への侵蝕が 2 四半期続いた時、落日審議は「far goal を消すか、near goal の act を制限するか」の二択を強いられる——**目的の消滅はつねに、どちらかの会議で署名される。署名されないまま消えるとき、目的は事故で消えた**（→2.5 の簿記の伦理、→6.6 腐敗の目的版）。

### 目的台帳の運営 — 会議冒頭の四行の質問

telos_chain（→前掲）を台帳として活着させる最小運営を置く。会議の冒頭、アジェンダの全議題に四行を先行させる。**其一**：この議題が触る goal の URI（触る goal が書けない議題は、目的なき作業の候选—→3.1 の final cause 欠落の現場検出）。**其二**：その goal の落日周期と前回審議時刻。**其三**：その goal の亲（遠い目的）の名前を一人が自分の語で言う（形式化された goal の文でなく**個人の語**で言わせる—→8.1 の site_coinations と連動、言えない亲は目的の連鎖が個人レベルで切れている—→3.1 の鎖の個人内側）。**其四**：議題の act 候補が effect 側でどの goal を削るか、既知のものだけ挙げる（未知は N2 の障礙候选—→3.4）。

```cypher
// meeting-open — 議題の目的接続を自動引く(会議ボードの照会)
MATCH (i:AgendaItem)-[:TOUCHES]->(g:Goal)
OPTIONAL MATCH (g)-[:TELOS_UP*1..3]->(far:Goal)
RETURN i.id, g.goal_id, g.sunset, far.goal_id AS telos_chain,
       g.last_deliberated;
```

この四行が会議のたびに回ると、目的台帳は「書いてある書物」でなく**読み上げられる儀式**になる——形式知が生き続ける条件が使用の反復であることは 1 章の暗黙知の論証そのもので、目的台帳もまた使われなければ 2.3 の制度老化一直線である。四行の質問の四半期ログ（議題総数対「触る goal 書けず」の比率）が、組織の目的相関の健康度である。

### 実行練習

1. あなたの中核システム1本について、四原因診断表（上の表）を自分の語彙で書き、各欄に「書いてある/嘘で埋めてある/空欄」を印せ。空欄と虚偽の総数が telos 負債のサイズである。
2. 上の孤立ゴール検出クエリを自分の要件定義書から作った `Goal` ノード20個で走らせ、孤立申告率を算出せよ。申告率が15%を超える場合と5%未満の場合で、組織の何が違うかを telos インフレの概念を使って説明せよ。
3. 「在庫自動発注」の telos を goal tree の形で10ノードに分解し、softgoal「資金最小」と「停止ゼロ」の競合を1つ ACHIEVED_FOR でなく `CONFLICTS_WITH` 辺として記録せよ。競合の調停は論理では決まらない（両 softgoal の正しさは両立可能）——調停者として誰を置くべきか、級 L2 の変更手続（→2.6）を援用して決めよ。

## 3.2 ゴール指向要求工学（GORE）と KAOS

目的の形式化が可能であり、かつ形式化しなければ目的が既定値で発火する——3.1 でこの二本の柱を立てた。この節では、目的を形式化して要求まで**演繹する**学問、goal-oriented requirements engineering（GORE）を本格的に導入する。中心人物は Axel van Lamsweerde である。彼の教科書 *Requirements Engineering: From System Goals to UML Models to Software Justifications*（2009）と、その方法的背骨である KAOS 法（京都大学発祥の要求モデム法。Kernel-Oriented Architectural Specification）が本章の道具立ての全部である。本章の「思想」節が van Lamsweerde をアリストテレスと並置するのは飾りでない。GORE は近代で初めて、目的因を工学の第一級概念として形式語義付きで再入城させた（→3.1 の定理の実装形）からである。

### GORE の転倒 — 「要求を書くな、ゴールから導け」

従来の要求工学が「要求文書」を起点にしたのに対し、GORE は起点を移す。要求（requirements）は起点ではなく**結論**である。起点はゴール（goals）であり、要求は「ゴールを、この環境仮定（assumptions）の下で、このエージェント（agents）に実装させれば成立つか」という構造的な演繹の結果として導かれる。この転倒の意味を三つ並べる。

第一に、要求文書の矛盾が消えるのではないが、矛盾が**場所を得る**。要求同士の矛盾は「両要求が同じゴールの AND 分解の葉にある」ときの障礙分析（→3.4）として現れ、ゴールの矛盾は上位木で検出される。矛盾がログではなく構造になる。

第二に、「なぜその要求か」が質問可能になる。要求ノードは上位ゴールへの充足辺（contribution link）を持つ。要求文書で「根拠」と言えば感覚的な散文だったものが、GORE では**充足関係の論理**——要求 R が環境仮定 A と組でゴール G を形式論理的に満たす（GORE の用語では *satisfaction argument*）——として書く。2.5 の履歴代数で `intent` が必須だったことの要求版がこれである。

第三に、変更の衝撃が計算可能になる。質料（レガシー資産）が変わり環境仮定 A が崩れると、A に依存していた satisfaction argument が切れ、依存ゴール群が「未充足」へ退行する。影響解析（impact analysis）が spreadsheet ではなく論理推論になる。

### KAOS の五階層 — ゴール・障礙・仮定・要求・エージェント

KAOS のオブジェクト体系を本書の語彙で敷設し直す。五つの一級概念は互いに独立で、どの二つにも還元されない。

1. **Goal（ゴール）**：望ましい状態。形式語義を持つ。後述の四型のいずれか。
2. **Obstacle（障礙）**：ゴールの論理的な不満たし可能事態。`O ≡ ¬G` の形であらねばならない——障礙は「起きた悪い出来事」の任意收集ではなく、**G の否定として特定される事態**である（→3.4 で詳しく扱う。ここが GORE の障礙と普通のリスク管理の決定的な差）。
3. **Assumption（仮定）**：環境側が満たすと信頼する性質。設計者の支配外の前提（ネットワークは99.9%稼働、作業者は手順を踏む）。仮定は要求と双対である——要求はシステムエージェントに課し、仮定は環境エージェントに課す。
4. **Requirement（要求）**：システムエージェントに割り当て可能なゴール（下向きの葉に近いノード）。
5. **Agent（エージェント）**：ゴール・仮定・要求の実現を担いうる主体。人間、マシン、組織、物理法則まで「主体」として載る（→3.6）。

五階層の相互関係は、単一の関係述語 **`sat(A₁..Aₙ ⊧ₐ G)`**（エージェント集合 A が環境仮定の下で G を充足）で統一される。この述語の論理的な強さ——充足が実在モデル上の成立ではなく論理的帰結（論証可能な成立）であること——が GORE の全部であり、また GORE の最大の限界でもある（→3.5 で率直に扱う）。

### ゴールの四類型と形式語義 — 線形時態論理（LTL）で意味を与える

KAOS のゴールは形態により四型に分かれ、それぞれ LTL（linear temporal logic）で定義される。LTL の記号は G（globally, 常に）、F（finally, いずれ）、U（until,.untilまで）の三つだけである。

| 型 | 自然言語雛形 | LTL 定義 | 保全現場の例 |
|---|---|---|---|
| achieving（達成） | P を（いずれ）達成 | `◇P`（F P） | 故障検知から30分以内に点検着手 |
| maintaining（維持） | P を常に維持 | `□P`（G P） | 稼働中のポンプの振動値は閾値未満 |
| avoided（回避） | Q を常に回避 | `□¬Q` | 無停止でのベアリング交換の試行 |
| ceasing（ cease・終了） | 現状 P をやめる | `P → ○□¬P` | 停止指示後、回転は恒久停止 |

この四分類が重要なのは、**検験可能性（→4.1）の形式形だからである**。maintaining ゴールは監視で falsify 可能（一度でも ¬P を見れば違反）、achieving ゴールは検認で verify 可能、avoided は maintaining の特殊形、ceasing は遷移の性質。要求の「検証方法」が、要求文書の運用ではなく論理型の帰結として決まる。LTL 型を宣言しないと、検証の設計が始まらない——4章の十分性判定は、この型の宣言を入口に取る。

ゴールの形式化は LTL に限らない。データ条件を含むなら FOL（一階述語論理）に Lift した LTL+FO が要る（3.5 の実装では z3 の FOL で近似する）。重要なのは「型と論理を宣言する」という作法そのもので、特定論理の選択は可換な部品である。

### AND/OR ゴール分解木 — 充足根拠を木として証明する

ゴールは上位→下位へ分解される。AND 分解では、子ゴール群の**同時充足**が親の充足を論理的に含意する（`G ⇔ G₁ ∧ G₂ ∧ ... ∧ □A` の形。A は環境仮定）。OR 分解では、子のどれか一つの充足で親が充足される——OR 分岐は**設計の選択点**であり、要求分析の段階では「選択を保留する」ための構造である。要求工学の初期段階で実装選択を固定しないことの形式的な居場所が OR ノードである（この遅延決定の哲学は 8.4 の人間介入点設計とも共鳴する）。

分解の正当性（decomposition legitimacy）は「漏れのない分解か」に尽きる。形式化すれば——`G ∧ ¬(G₁∧...∧Gₙ∧□A)` が充足可能（unsatisfiable でない）なら、分解は漏れ（gap）を持つ。充足可能性判定は次節以降の z3 の仕事だが、漏れの直感的検出は障礙分析（→3.4）と対になる手続を持つ：**G を保ったまま、全子Goalが同時に壊れうる世界を1つ構成できるなら、分解は漏れている。** 3.5 の実装ではこの両者（機械判定と反例構成）が表裏になる。

### 本書への実装 — goal tree を Neo4j のグラフとして置く

要求分析のツールは様々だが（KAOS ツール suite、Tropos、i*）、本書はグラフで持つ。理由は第1部の設計決定と同一である——意味の横方向のつながり（障礙と制約の共有、同一エージェントの過負荷、softgoal の競合）を、ツールの「木」は辺として持たず、後から人間が見るしかなくするからである。goal tree は木だが、goal **graph** は木でない。障礙の共有、仮定の共有、エージェントの共有——これらが木を網（tangle）に変える。この網の構造こそ影響解析の本体である。

```cypher
// goal tree 本体（3.1 の telos 連鎖 ACHIEVED_FOR と接続）
MATCH (parent:Goal {goal_id: $p}), (c:Goal {goal_id: $c})
CREATE (parent)-[d:DECOMPOSED {kind: $and_or,   // 'AND' | 'OR'
  legitimacy_checked_at: datetime(),
  gap_witness: null}]                          // 漏れの反例（→3.5）がここに入る
->(c);

// satisfaction argument: Requirement(r) + Assumption(a) ⊧ Goal(g)
MATCH (r:Requirement {req_id: $r}), (a:Assumption {asmp_id: $a}), (g:Goal {goal_id: $g})
CREATE (r)-[:SATISFIES {
  arg_type: 'logical',          // 'logical' | 'plausible' — 論証と尤物を混ぜない(→4.1)
  ltlexpr: $ltl,                // 機械検証可能な充足論証の核
  checkable: true               // false の論証は人間証言。4.6 で監査対象になる
}]->(g),
(a)-[:ASSUMED_FOR {criticality: $c}]->(g);

// 障礙の連結: O は G の否定。negates 辺の向きは「G を壊しうる」方向。
MATCH (o:Obstacle {obst_id: $o}), (g:Goal {goal_id: $g})
CREATE (o)-[:NEGATES {not_form: $fol_of_not_g}]->(g);
```

`arg_type` の二値区分（logical / plausible）を強調しておく。充足論証が本当に論理的帰結なのか、「もっともらしい」だけなのかを、ノードに書かせる。GORE の文献自身がこの区別を正直に扱っている（satisfaction argument の妥当性は環境モデルの正しさに相対的だ、と van Lamsweerde は書く）。本書の哲学設計（→4.1 の検証可能性の限界）では、plausible 論証は削除されないが、**plausible であることをデータとして持ち続ける**。尤度と正統性の混線拒否は 5.3 の LLM 論点の先取りでもある。

### softgoal — 十分でない「より良い」を木で扱う

KAOS/GORE（と並行系譜の i*）は softgoal を導入する。「セキュア」「効率的」「保守可能」は充足/不充足の二値で判定できない——充足が程度問題だからである。softgoal の標準的扱いは `AND/OR contribution link + 満足閾値` の木であり、`somepath`（ある分解ルートで十分）や `allpath`（全ルートで必要）の満足様式で評価する。在庫自動発注の失敗（3.1）を softgoal 語彙で書き直せば——`資金最小` と `停止ゼロ` は softgoal であり、自動発注の要求木は `停止ゼロ` への contribution は正、`資金最小` への contribution は負（在庫増）となる。負の contribution を木に載せていれば、発注前に競合が**可視**だった。

```cypher
// softgoal の contribution 集計: 要求ノードの正味効果を木で計算する
MATCH (r:Requirement)-[:CONTRIBUTES {sign: $s, weight: $w}]->(sg:SoftGoal {sg_id: $sgid})
MATCH path = (top:Goal)-[:DECOMPOSED*]->(r)   // 要求が所属する上位木
WITH r, sum(r.CONTRIBUTES.weight * CASE WHEN r.CONTRIBUTES.sign = '+' THEN 1 ELSE -1 END) AS net
MATCH (sg) WHERE NOT (sg)-[:CONTRIBUTES {sign: '-'}]->(:SoftGoal)  // 競合先の正規化
RETURN sg.sg_id, net
ORDER BY net ASC;   // 負の正味効果を持つ要求が先頭に来る。この並びをレビュー会議の議題に。
```

このクエリの「成果」を過大評価しないための注記を添えておく。weight の数値化は softgoal の程度判断を疑似定量化する操作であり、2.1 の分節の暴力が数値の皮を被ったものである。contribution 符号＋重みの決定は 2.6 級 L2 の承認対象とし、数値ではなく**符号の競合を議題に上げる**ことを主目的にする。レビューの議題生成が目的であり、数値は議題の補助線である（→4.2 の CQ も同じ「判定不能なものの審議可能化」という設計思想を共有する）。

### van Lamsweerde の系譜と、彼の問いの現在

最後に思想史の配線をしておこう。GORE の系譜は、3.1 で追放と言った目的因が、実は工学的伝統では生き続けていたことを示す。1970年代の構造化分析（要求を機能分解で書く）→ 1980年代の形式手法（Z、VDM：形相の完全性）→ 1990年代の GORE（目的の第一性）→ 2000年代の softgoal・意図（intention）モデル（目的の程度・主体性）——この流れは、「システムを記述する」という観が「システムが何のために存在するかを記述し、そのために何が十分かを論証する」観へ移行した歴史である。

そして van Lamsweerde の後期研究は、本書の第5部と正面から接続する問いを残している。彼は *Formal Requirements Engineering* の後年、「要求の形式化は人間の価値判断を置換するのではなく、価値判断の**質を上げる**ためにある」と書き続けていた。形式化の限界内での形式化の益——これは 8.4 の Human-in-the-Loop の要求版であり、4.1 の検証可能性の限界の肯定形である。本章は GORE を「目的を機械に渡す方法」としてではなく「目的について人間が議論できる形式語彙」として採用する。この採用の方向の差は、第4部・第5部で決定的な差に育つ。

### goal 木の品質検査 — AND/OR 分解の構造的不変条件

KAOS の goal 分解木（AND/OR 分解、→前掲）に、構造の検査を四条通す。意味の検査（→4.2 の CQ）と形が異なるのは、**分解木の病は意味が正しくても形の病で発生する**からである（正しい目的の集合が、間違った木の形で運用事故になる）。

**検査一：leaf の形式化可能性**——すべての端節点は形式文（LTL/FOL、→3.3）か放棄登記（→3.3 放棄表）のどちらかを持つ。どちらもない端節点は「目的の木」の先が口約束でできていることの証明である（→4.1 の境界——木は境界の地図でもある）。**検査二：OR 分解の相互排他の非要求**——OR 分岐は「どれか一つ」であり、分岐同士が**同時に満たされうる**ことを禁止しない（同時に満たす goal 設計は冗余であり、冗余の OR は偽装である——本物の OR は「同時に成立しうるか」の設計判断を DesignDecision に持つ）。**検査三：AND 分解の完全性**——AND 分解の全 child が満たされたら parent が満たされる（**実在的完全性**）ことの宣言が各 AND 節点にある。宣言のない AND 節点は「全部揃えたのに目的が果たされていない」事故の予約である（欠けた child=形式化し忘れた要求、→3.3 の未読了文の木版）。**検査四：深度と周期の整合**——goal 木の深さ（委任の段数、→7.2 の委任深度の要求工学版）が、現場の周期預算で到達できる深度を超えていない（叶わない深さの木=待たされる事故、→3.4 N5 周期超過の静的検出）。

```cypher
// goal-tree-health — 四検査の Cypher 実装(要求レビュー前に CI で走る)
// 検査一: leaf の形式化/放棄登記の欠落
MATCH (g:Goal) WHERE NOT (g)-[:HAS_SUBGOAL]->()
AND NOT (g)-[:FORMALIZED]->(:Formula) AND NOT (g)-[:WAIVED]->(:WaiverRecord)
RETURN g.goal_id, 'leaf-unformalized';
// 検査三: 実在的完全性の宣言欠落
MATCH (g:Goal)-[:AND_DECOMPOSED]->(:Goal) WHERE g.completeness_claim IS NULL
RETURN g.goal_id, 'and-not-declared-complete';
// 検査四: 周期預算到達不能深度
MATCH path = (root:Goal)-[:HAS_SUBGOAL*1..6]->(g:Goal)
WHERE size(path) >= root.max_depth OR g.decision_budget_sec < 0  // 予算枯渇の節
RETURN root.goal_id, max(size(path)) AS depth, root.max_depth;
```

四検査の失敗を goal 台帳の障礙候補として自動登記する（→3.4——分解木の形の病自体が障礙の源、複合式一の静的版）。哲学の節（3.2 の前段）とこの節の関係を一句で置いておく。GORE が目的原因復権の工学的体（→3.1）だとすれば、**分解木の形の検査はその体への神経の配線**である——AND/OR の木は目的の論理形式であり、論理形式の検験は目的の検験に先行する（論理が正しくなければ、目的の意味の検査すら走る場所がない——4.1 の検証可能性の要求が、ここで goal 木の形に適用されている）。

### 実行練習

1. 3.1 練習3 の goal tree を KAOS 五階層に拡張せよ：各葉に Requirement か Assumption を割り当て、`SATISFIES`/`ASSUMED_FOR` 辺を張り、全叶にエージェント（人間1つ以上を含むこと）を接続せよ。「人間が一つもエージェントとして現れない分解」は本章の語で *dehumanized decomposition* である（→3.6）。
2. maintaining ゴール「稼働中ポンプの振動値は閾値未満」の障礙を `NEGATES` 辺で定義し、その障礙が同時に `avoided`（無停止交換の試行）の negation でもあるケースを作れ。1つの障礙ノードが2つのゴールを negates する構造を、3.4 の障礙木へどう載せるか設計せよ。
3. 上の softgoal 集計クエリに自分のプロジェクトの要求5本を通し、負の net が最も大きい要求を1本選べ。その要求の `CONTRIBUTES` 符号・重みを決定した会議議事録がない場合、2.6 のどの級の変更として事後的に登記すべきか決め、登記レコード（`:intent` 自由文付き）を書け。

## 3.3 目的から論理へ — 自然言語要求の形式化手順

ゴールの階層と形式語義の型が揃った（→3.2）。この節の実務は、自然言語で書かれた要求を、その型に入る論理式へ**手順的に**変換することである。「手順的に」と強調するのは、形式化が天才の翻訳芸ではなく、翻訳の失敗が記録・再現・監査できる工学工程でなければならないと本書が決めているからだ（2.1 の暴力は形式化に内在し、消せない。消せない暴力は手順にして追跡する——これが第2部全体の統治原則である）。三段変換を敷設する。自然言語 → EARS（制約付き自然言語）→ LTL（線形時態論理）→ FOL+LTL（データ条件込み）。各段は完全に忠実ではない。各段が何を失うかを明示したまま進行するのが、本書の手順の哲学である。

### 第一段階 — EARS：自然言語を構文制限された自然言語へ

EARS（Easy Approach to Requirements Syntax、Rolls らが Rolls-Royce で開発）は、要求文を五つの定型構文に収束させる。自由文をいきなり論理へ翻訳すると、失うものが多すぎる。中間言語を置く。

```
1. Ubiquitous（常時）:        The <system> shall <response>
2. Event-driven（事象駆動）:   When <trigger>, the <system> shall <response>
3. State-driven（状態駆動）:   While <in state>, the <system> shall <response>
4. Unwanted behavior（異常）:  If <condition>, then the <system> shall <response>
5. Optional（任意）:           Where <feature is present>, the <system> shall <response>
```

保全現場の要求を EARS へ正規化する例。左の自由文のどこが危険だったかをコメントで注ぐ。

```
原文: 「夜間の振動異常は点検を優先すること」
EARS: While [Shift.type = 'night'],
      when [vib(m) >= threshold(m) for machine m in Zone z],
      the system shall [raise PriorityFlag on the inspection task for m within 5min].
# 原文の危険: (1)「振動異常」が未定義（threshold とどちらか不明）。
# (2)「優先」が程度語（softgoal 領域。3.2 の貢献記述か、順序の硬性格か不明）。
# (3)「夜間」の範囲未定義（shift 境界 vs 時刻）。
# EARS 化は these を語彙参照（threshold, Shift.type）へ強制し、程度語を露出させる。
```

EARS の本質的機能は、**時態構造の露出**である。While/When/if/where はそのまま LTL の G/(trigger⇒X)/（異常）/（feature 条件）に対応する。自由文段階では動詞の時制と副詞に埋もれていた時間構造が、構文で剥き出しになる。ここが形式化の閾値であり、以降の段はほぼ機械的である。

```python
# ears_to_ltl.py — EARS 五型の機械的 LTL 化（第一近似）
# 哲学: この関数は意味を保証しない。EARS 側の構文が正しければ時間構造だけを保つ。
# 保証の所在(意味の正しさ)はレビューにあり、時間構造の正しさはここに書く。
from dataclasses import dataclass

@dataclass
class Ears:
    kind: str            # 'ubiquitous'|'event'|'state'|'unwanted'|'optional'
    trigger: str | None  # FOL 断片（While/if の中身）
    response: str        # FOL 断片（shall の中身）
    within: str | None   # 時間窓（'PT5M' 等）

def to_ltl(e: Ears) -> str:
    match e.kind:
        case 'ubiquitous':
            return f"G({e.response})"
        case 'event':
            window = f"F[{e.within}](R)" if e.within else "F(R)"
            return f"G(({e.trigger}) -> {window.replace('R', e.response)})"
        case 'state':
            return f"G(({e.trigger}) -> G({e.response}))"
        case 'unwanted':
            return f"G(({e.trigger}) -> {e.response})"  # 異常時の是処動作は event と同型
        case 'optional':
            return f"G(({e.trigger}) -> G({e.response}))"
    raise ValueError(f"unknown EARS kind: {e.kind}")
```

`within` の時間窓が LTL に「5分以内」を載せる方法（有界 until）を明示しない実装になっている。実運用では bounded LTL（TLA+ の temporal operator 等）へ降りるが、骨格としての意味は不変だ——**時間窓は要求の一部であり、時間窓を忘れた変換は要求の書き換えである**（3.1 の在庫システムの発注遅延事故は、within の喪失として再現できる）。

### 第二段階 — LTL + データ条件（FOL への Lift）

`vib(m) >= threshold(m)` のようなデータ条件は純 LTL では書けない。述語を LTL の項として内包する LTL+FO へ移る。本書の実装（→3.5）では z3 の FOL に落として近似する——時間量化を有限時点への instantiation（unrolling）で置き、充足判定を有限境界で下す。有限境界近似は正当性を持つが、無制限の定理証明ではない（→3.5 の決定不能性の節で完全な扱いを書く）。

```
G( (vib(m,t) ≥ threshold(m)) → F[≤30min](Inspect(m,t')) )
   ↑全域量化 m ∈ machines, t ∈ times
# unrolling (時点 0..N, 機械 1..M):
∧_{t=0..N} ∧_{m=1..M} [ vib(m,t) ≥ thr(m) ⇒ ∨_{t'=t..t+⌊30min/Δt⌋} inspect(m,t') ]
# z3 の整数線形制約として drop する(実装は §3.5)。
```

unrolling の粒度 Δt と範囲 N の選びが判定の限界そのものである。「粒度より短い違反窓は発見不能」——境界設定の宣言を要求の木に載せる。境界を載せない形式検証は、検証の網の目を検証しない検証である（→4.1 の検証可能性の限界の技術形）。

### 第三段階 — 形式化が構造的に失うもの：修飾詞の難しさ

三段変換の損失を分類し、損失への設計応答を決めておく。損失は三型に尽くせる。

**型一：境界語の切断（vague predicates）。** 「深刻な故障」「通常の稼働」は輪郭のぼやけた述語である。FOL は二値述語を要求するので、切断は不可避（2.1 の暴力そのもの）。設計応答は多値化ではなく**切断の版数化**である——`threshold(m) = 4.5 mm/s, version: 2026-11` を要求ノードに紐づけ、2.5 の履歴代数に接続する。輪郭を消さず、輪郭の移動を記録する。

**型二：程度語の残留（soft residues）。** 「優先すること」「適切に」は LTL に翻訳不能で、softgoal 木へ逃がす（→3.2）。設計応答は、soft 語をハード要求へ無理やり落とさないことである。落とした瞬間、程度判断の責任が要求の論理に紛れ込み、監査不能になる。`arg_type: 'plausible'` の混線拒否（→3.2）と同じ原則。

**型三：省略された存在前提（implicit presuppositions）。** 「点検タスクに優先旗を立てる」は「当該機械に点検タスクが存在する」を前提とする。タスクが存在しなければ要求は vacuously true になり、空転する。FOL は量化で前提を露出できる（`∃task` の要求化）が、翻訳者は露出の必要性に気づかねばならない。設計応答は vacuity 検出である。

```python
# vacuity_check.py — 「空に真」を検出する: 論証済み要求が前提の不在で自動的に真になっていないか
from z3 import Solver, Bool, BoolRef, Not, And, sat, IsSat

def is_vacuous(assumption: BoolRef, requirement: BoolRef) -> bool:
    # 要求 G が「前提 P の下で真」ではなく「前提 ¬P だけで真」になっていないか:
    # P ∧ ¬G が unsat（G が P 下で常に真）で、かつ ¬P だけでは sat に ¬G が成立する
    # （= 前提が消えると壊れる真しさ）であることを区別する。
    s = Solver(); s.add(assumption, Not(requirement))
    always_holds = s.check() == IsSat.unsat     # P ⊨ G
    if not always_holds:
        return False
    s2 = Solver(); s2.add(Not(assumption), Not(requirement))
    needs_assumption = s2.check() == IsSat.sat  # ¬P ∧ ¬G 可能 → G は P に依存している
    return not needs_assumption                 # 依存なし = 空に真 = vacuous
```

vacuous な要求は「検証にパスするが何も保証しない」要求である。形式検証の現場では珍しくないが、要求文書ベースの運用では検出されない。GORE の充足論証を機械で書く本書の系（→3.5・4.5）では、vacuity 検査は契約テストと同等の市民権を持つ（4.4）。

### 翻訳の全体ワークフロー — 誰がどの段をやるか（3.6 の予告）

EARS 化は要求分析者と現場の協働で（現場語彙を skos マッピング経由で正規語彙へ、→2.4）、LTL 化は形式担当者で機械補助（上の ears_to_ltl が叩き台）、FOL+境界化は形式担当者と検証エンジニアの共同、RefinementTrace 登記は全段共通。エージェント割当は 3.6 で形式的に扱うが、既に 1.6・2.6 の原則が支配している——**形式化の権限は書く者にではなく、失われた意味を復元照会できる者に置く**。翻訳ログの閲覧権限が現場にない形式化は、翻訳の暴力を不可視にする。

### 形式化の監査 — 「翻訳表」と「放棄表」を要求文書に添わせる

自然言語要求→形式論理の翻訳（→前節の手順）の運用で最も起きる事故は、翻訳の**失敗**ではなく翻訳の**省略された箇所の非登記**である。要求文書の各節を機械的に形式化した結果、「翻訳された文」「翻訳されなかった文」「翻訳を**放棄すると決めた**文」の三区分が必ず生じる。区分の登記を要求文書の強制様式にする——**翻訳表**（原文→形式文の対応）と**放棄表**（形式化しないことと、その理由と、代替機構）の二表である（→1.6 の記録しない宣言・NonRecordingRule の要求工学版）。

```markdown
## 翻訳表(req-v7)
| 原文 (§3.1) | 形式文 (LTL) | 級 |
|---|---|---|
| 「停止中は給油しない」 | □(¬operating → ¬pumping) | E1 |
## 放棄表(req-v7)
| 原文 (§3.4) | 放棄理由 | 代替機構 | 落日 |
|---|---|---|---|
| 「機械の調子が悪いと感じたら…」 | 検証可能な述語が存在しない | 審議槽+理由面板(→8.5) | 24か月 |
| 「経験豊富な operator が…」 | 定義不能(暗黙知,→1.1) | drill課程(→8.6) | 36か月 |
```

放棄表の三列が運用の核心である。**放棄理由**は怠慢と設計的不同意を区別する（後者は記録された哲学的位置取り——→4.1 の検証可能性の落日と接続）。**代替機構**の列が最重要で、放棄は機構の欠如ではなく機構の**乗り換え**でなければならない（形式化しない決定に代替機構が書かれていない文書は、その要求を静かに消した——2.1 の暴力の要求文書版）。**落日**により放棄も再審議される（「感覚」の語彙が 24 か月後の現場語彙（coin-term）で検証可能になる可能性がある——→1.3 の語彙の更新）。

監査照会を一つ。**原文の文数に対する両表の被覆率**——100% でない要求文書は、翻訳でも放棄でもない第三の状態（**未読了の文**）を含んでいる。未読了の文の集合が、その要求の最大の風険である（誰も翻訳を論争せず、放棄も記録していない要求は、運用で各自の解釈で動く——2.4 の分類制定の非登記が要求文書で起きる）。監査はこの「未読了リスト」を自動生成し、要求レビューの第一議題に置く（→4.2 の CQ 統治——文書そのものの CQ：「この要求の各文は、翻訳されたか、放棄されたか、どちらでもなければ誰が読む予定か」）。

この設計の背景にある論理を一文で置いておく。形式化の誠実さは、翻訳の正しさの総和ではなく、**翻訳と放棄の境界の登記の完全性**で測られる（→4.1 の境界問題の実務形）。よって翻訳表の精度を上げる努力より、放棄表を完备にする努力が、要求の信頼性を大きく上げる——後者は数分で書け、前者は数か月かかるという運用上の非対称もある。

### LTL 五テンプレート — 要求の時制を書く定型

障礙分析（→前掲）で再現する時制パターンの定型五本を、そのまま要求カードに貼れる形で置く（毎回 LTL を書ける必要はない——定型が五本あれば、書けない質問の形が見え、書ける側の負担が下がる。ウィトゲンシュタインの語言遊戯の観点：规則遵循は個別的天才でなく定型の反復で成立する、→4.2 CQ 書式と同じ設計哲学）。

| テンプレ | 式 | 自然言話の型 | 障礙化け(→3.4) |
|---|---|---|---|
| 応答 | `□(req → ◇≤d resp)` | 「要求したら d 以内に返る」 | N5 周期超过 |
| 安全 | `□¬(danger)` | 「never, どの状態でも」 | N1 違反 act の存在 |
| 保証 | `(req ∧ fair) → ◇ done` | 「待ち続ければいつか終わる」 | N3 饥饿 |
| 単調 | `□(s_i → (s_i ∨ s_{i+1}))` | 「一段下に戻らない」 | N4 前提(状態機械の環) |
| 調和 | `□(a → ◇□b)` | 「a を选んだら b が定着する」 | N2 復合(effect 宣言の実証) |

運用の注記を二つ。**其一、五本に落ちない要求は**「我々が今言える時制の限界」の記録として障礙候选に載せる（要求の形式化不能=3.3 の翻訳表の未翻訳欄—→3.2 の叶わない形式化の宣言）。**其二、テンプレの选型は L1 級**（要求の時制の形を変えることは E2 見通し級の変更—→2.6 の級表に「要求テンプレ変更 L1・要求不変条件変更 L3」の二行が預めって載る理由）。

### 実行練習

1. 自分の要求文書から自由文5本を選び EARS 五型に正規化せよ。正規化中に「程度語」が現れた本数を数えよ。程度語の本数が softgoal の個数（→3.2 の競合木の入口数）である——この等式をチームの説明資料にせよ。
2. `ears_to_ltl.py` に「While 状態中に When 事象」の複合 EARS（nested）を追加し、LTL 式 `G(state -> G((trigger) -> F[..](response)))` を生成せよ。state が抜けた瞬間に未完了の response の義務はどうなるか（obligation evacuation）を LTL で書き、ceasing 型（→3.2 の表）で表現せよ。
3. `is_vacuous` に「前提: 点検タスクが存在する」を明示した要求と、前提を忘れた同一要求を流し込み、後者が vacuous と判定されることを確認せよ。判定結果の `needs_assumption` が False になる場合の要求文の書き直しを1案提示せよ（quantifier を露出する形）。

## 3.4 障礙分析 — 例外事態の形式モデル

ゴール木は順路の設計図である。順路だけを描いた設計は、必ず例外に殺される。3.1 で「目的なきシステムの良否は測定不能」と言ったが、その対偶として本章の第二定律を立てる。**目的あるシステムで、目的の壊れかたを列挙しないものは、目的を守っているとは言えない。** この節の障礙分析（obstacle analysis）は、壊れかたの列挙を任意の脳内マップではなく論理的操作——ゴールの否定——として行う方法である。GORE の障礙概念と従来型の危害分析（fault tree analysis, FTA）の統合は、この節の工学的中心であり、1.6 の「載らないもの」に対する第2部の答えでもある——例外は載らないのではなく、**否定として載せられる**。

### 障礙の定義 — 「悪い出来事」ではなく「¬G として特定される事態」

通常のリスク管理は「起こりうる悪いこと」のリストを作る。リストは網羅を原理的に保証しない——人間の想像力のリストだからだ。GORE の障礙定義はこれを論理に置き換える。**ゴール G の障礙 O は、O ∧ G が充足不能（unsatisfiable）であるような事態の述語**、すなわち実質的に `O ≡ ¬G`（または `O ⇒ ¬G` の強い形）である。障礙の網羅とは「¬G を論理的に覆う分解」のことになり、網羅判定は `G の論理式から ¬G を導出し、その分解が ¬G を覆っているか` という機械検査に降りる（→3.5 の z3 実装）。

これは表現力の差ではなく、定義の差である。「振動異常のまま72時間稼働し、かつ点検着手が5分以内に行われなかった」は、maintaining/achieving 復合型ゴールの ¬G そのものとして選ばれる——発明ではなく計算で選ばれる。

```
G(achieving):  G = (vib(m,t) ≥ thr(m)) → F[≤5min](Inspect(m,t'))
¬G = ∃t [ vib(m,t) ≥ thr(m) ∧ ¬F[≤5min](Inspect(m,t')) ]
   = ∃t [ vib(m,t) ≥ thr(m) ∧ G[≤5min](¬Inspect(m, ·)) ]
# ¬G が障礙の上位ノード。障礙分解は ¬G の FOL 構造の分解に一致する。
```

障礙の一次分解は、LTL/FO の否定が構文構造に沿って機械的に配られることを利用する（ド・モルガン、quantifier の反転、time operator の双対：`¬F[≤d]φ ≡ G[≤d]¬φ`）。上の導出も機械手順の産物である。障礙分析の「発想の飛躍」は一次分解には不要で、飛躍が要るのは二次分解——論理的形式を、現場で起こる機序（メカニズム）へ落とす段——である。

### 障礙の二次分解 — 論理的形式から機序へ

`¬F[≤5min](Inspect)` は「点検が5分以内に起きなかった」という形式であり、現場の語ではない。現場の語（「見落し」「通知が届かない」「夜間で担当が寝ていた」）への分解は、AND/OR の木で、葉が**人間・機械の行動の失敗モード**になるまで下りる。AND 分解は共起条件（全部起きたとき障礙）、OR 分解は代替原因（どれか一つで障礙）。FTA の AND/OR ゲートと GORE の障礙分解は、ここで完全に同型になる——同型の根拠は両者とも ¬G の真偽関数分解だからである。

分解の深さの停止条件を先に決める。**葉は「エージェントが変更可能な行為の失敗」か「質料の故障モード」でなければならない**（3.1 の四原因の語彙）。これを超えた深さ（なぜ人間が眠かったのか）は、障礙木ではなく telos 連鎖の別問題（体制・労働設計）へ移管する。移管の記録を `handed_off_to` プロパティに残さない障礙分析は、無限後退で死ぬか、浅いところで嘘の完了宣言をする。

```cypher
// 障礙木の Neo4j 配置: NEGATES 辺(→3.2)＋分解構造
MATCH (top:Obstacle {obst_id: 'O-neg-G42'})
MATCH (c:Obstacle {obst_id: $child})
CREATE (top)-[:OBSTACLE_DECOMPOSED {kind: $and_or,
  covered_by_children_at: datetime(),
  coverage_proof: 'z3-unsat-core v7' }]     // 網羅証明の版数参照(→2.4 版数化原則)
->(c);

// 障礙葉 → 実現エージェントの失敗モード接続(→3.6)
MATCH (leaf:Obstacle {leaf: true}), (a:Agent {agent_id: $a})
CREATE (leaf)-[:REALIZED_BY_FAILURE_OF {failure_mode: $fm}]->(a);

// 障礙 → 制約/質料の接続(障礙の除去可能性の計算に使う)
MATCH (leaf:Obstacle), (k:Constraint {constraint_id: $k})
CREATE (leaf)-[:MITIGABLE_BY {cost_class: 'L2',
  residual_risk: '夜間通知の人的遅延は残る'}]->(k);
// MITIGABLE_BY の 'residual_risk' を自由文で必須にする。
// 除去後残るリスクを書かない障害対策は、3.1 の「要求は満たされ目的は裏切られた」の
// 再発経路そのものである。残余の登記は 2.1 の残余保存原則の障礙版。
```

### 障礙の併存計算 — 最小障礙セットと要求木全体の健全性

単一の障礙木でなく、要求木全体で障礙が**共有**されるのがグラフの利益である。同一の障礙ノード（例：「通知網の遅延」）が5つのゴールを NEGATES している場合、その障礙の発生確率 p で全体の未充足期待値が概算できる——ただし確率の独立仮定が嘘を生む（共通原因故障）。共起を禁止・条件付けする辺 `CO_CAUSED` を持ち、最小障礙セット（MCS：障害を起こす最小の障礙集合）を enumerate する。

```python
# mcs_enum.py — 最小障礙セット列挙(要求木全体)。z3 の AllSMT/反証列挙で実装可能だが、
# 本書のデモは純 Python の単調な論理で十分(障礙の論理は mostly 単調)。
from itertools import combinations

GOAL_FAILS = {  # goal_id -> 障礙集合(AND 分解の葉; OR 分解は同じ goal で複数群)
    "G-inspect-5min": [{"O-net-delay", "O-night-sleep"}, {"O-missed-sensor"}],
    "G-no-runless":   [{"O-net-delay", "O-stale-priority"}, {"O-manual-override"}],
}

def fails(goal: str, active: frozenset) -> bool:
    return any(group <= active for group in GOAL_FAILS[goal])

all_obsts = sorted({o for gs in GOAL_FAILS.values() for g in gs for o in g})
mcs_list = []
for k in range(1, len(all_obsts) + 1):
    for cand in combinations(all_obsts, k):
        c = frozenset(cand)
        if any(fails(g, c) for g in GOAL_FAILS) and \
           not any(fails(g, c - {o}) for g in GOAL_FAILS for o in c):
            mcs_list.append(c)
print(mcs_list)
# 単独で全ゴールを守る障礙(O-net-delay が2つの木に共有)が MCS の核に出る。
# 共有障礙は設計の single point of failure の論理的証明である。
# 単一障害点の指摘を「現場の経験」から「列挙された定理」へ格上げする。
```

`O-net-delay` が2つのゴール木の MCS に共通して出現する——この瞬間、「通知網」は設計思想の語ではなく論理定理の語になる。単一障害点の議論で「感覚的にリスクが高い」と言われたものが、MCS 列挙では「集合論の事実」となる。ここまでの厳密化は、しかし確率計算の段で崩れる（独立仮定）。`CO_CAUSED` 辺を持つ共起モデル（Bayesian network 化）は本章の範囲を超えて付録 C（本書では範囲外とし、4.5 の sat 判定で構造のみ扱う）へ逃がす。**確率の数値化の限界を明示で置き換える**——4.1 の検証可能性の限界と同じ設計姿勢である。

### 危害分析との統合 — GORE が FTA に与えるもの、FTA が GORE に返すもの

FTA 側の伝統（IEC 61025 のゲート記法、FMEA の単一機能障害表）は、障礙分析に対して三つの贈り物を持つ。第一に**機序の語彙**——機械の故障モード（疲労、摩耗、目詰まり）は GORE の抽象論理にはない現場の在庫であり、障礙の二次分解の葉の語彙を供給する。第二に**経験データベース**——同一型の機械の故障履歴は、障礙木の実在確率の事前分布になる。第三に**訓練様式**——FTA のファシリテーションは会議で回す技法が洗練されている。

逆に GORE が FTA に返すのは**上方向の接続**である。伝統的 FTA は頂上事象（hazard、危害）から下へ分解するが、危害の定義——何が危害か——は要求側から来る。telos の連鎖（3.1）と危害の定義が同じノード空間で接続されないと、「安全要求」は存在するが「安全」の定義が別文書に漂流する事故が起きる（3.1 の四原因表の telos 欄の事故型）。統合後の全体像——危害ノードが `NEGATES` 辺で goal と結合し、`ACHIEVED_FOR` で telos に結合し、障礙葉が `REALIZED_BY_FAILURE_OF` でエージェントに結合する——は、要求と安全が同一グラフの異名詞であることを示す。

### 障害の記録が現場から消えないための設計 — 障礙の第三次保持

2.3 のスティグレールの枠組みを障礙へ適用する。障礙木は組織の第三次保持である。障礙ノードに `observed_instances`（実事例への参照）が1つも繋がれない障礙木は、理論上の障礙木であり、2.3 の「再検証なき既定の保持」の腐敗型になる。

```cypher
// 障礙ノードの健全性監査: 実事例との結合がない障礙、事例が古すぎる障礙を報告
MATCH (o:Obstacle)
OPTIONAL MATCH (i:Incident)-[:INSTANCE_OF]->(o)
WITH o, count(i) AS inst, max(i.at) AS latest
RETURN o.obst_id, inst,
  CASE WHEN inst = 0 THEN 'theoretical'                    // 機上の障礙(排除ではない。警戒色)
       WHEN latest < datetime() - duration('P2Y') THEN 'stale'  // 2年実例なし=世界が変化したか
       ELSE 'live' END AS status
ORDER BY inst;
```

`theoretical` を消さない点が重要である。将来の障礙は実例を持たない。しかし `theoretical` 障礙と `stale` 障礙の比率は、障礙分析が「現場の記憶」で回っているか「形式の遊戯」で回っているかの指標である（→2.6 の級 L2 変更として年次レビューに付す）。

### 障礙の代数 — N1〜N5 の複合と「障礙の障礙」

障礙の五類型（N1 単独失敗・N2 妨害（他 act の effect が goal を NEGATES）・N3 矛盾・N4 前提崩壊・N5 周期超過、→3.5 の実装）は単独で発火するより**複合**として現場に来る。複合の代数を三式、確定する。

**複合式一：N4→N1 の連鎖**（前提の崩壊が、その前提に依存する全 act を同時に失敗させる）。前提 E4 の落日は、dependency を持つ transition 群に一斉に UNKNOWN を返す（→5.5 のガードの地平超）。設計帰結：E4 前提の落日周期は、それを食べる transition の周期の**下限**でなければならない（前提が act より速く老いる設計は、act が老いた前提で走り続けることを許す——落日の速度設計を前提→act の向きで整列させる）。
**複合式二：N2 の再帰**（障礙を消す act が、別の goal を障礙する）。回復 act の effect が副作用として他 goal を NEGATES するとき、障礙解決の act 群の**総和効果**を照合する必要がある（→7.3 の effect_verification が単一 act 単位でなくセット単位で走る理由）。単一 act 検証の系では、個別に正しい回復の連鎖が合成で事故になる（回復の復讐——事故調査の古典形）。
**複合式三：障礙の障礙**（障礙処理の機構自体が障礙される——審議槽の閉塞・エスカレーションの不在・OnCall の応答遅）。N5（周期超過）の半分はこれである。検出：障礙解決スレッドの滞留が審議槽の閉塞統計と相関するかどうか（→6.2 の槽の健康、→6.6 の腐敗四「槽を満杯にして回さない」）。治療は障礙処理の資源配分（席・時間予算）であり、障礙モデルの改良ではない——**モデルが悪いのか席がないのかの判別**が障礙台帳の運用の中心作業である。

```cypher
// obstacle-algebra — 複合障礙の検出(週次)
// 複合式二: 同一 thread で発火した回復 act 群の effect が他 goal を NEGATES するか
MATCH (th:Thread)-[:HAS]->(o:Obstacle)-[:BLOCKS]->(:Goal),
      (th)-[:RESOLVED_BY]->(acts:ActSet)-[:HAS]->(a:Action)-[:EFFECT]->(e)
WITH th, o, acts, collect(e) AS effects
UNWIND effects AS eff
MATCH (eff)-[:NEGATES]->(g2:Goal) WHERE g2 <> o.blocked_goal
RETURN th.tid, o.ob_id, g2.goal_id AS side_negated, 'compound-N2' AS kind;
```

複合の代数の末尾に、**障礙の落日**を置いておく（→6.6 の落日条項の障礙版）。障礙条目は「処理済み」で閉じたままでなく、再発周期で自動的に再点検される（処理済み障礙の実例が再び出ているなら、解決 act は form は adopt だが実測は失敗している——effect_verification が閉ループを回していない、→7.3）。障礙を閉じるのではなく**障礙の生存を追う**——これが 3.6 の責任配分と 7章のフロネシスがつながる継ぎ目である（障礙の実例を追跡しない系では、解決した人の責任も、解決の実測も、どちらも消える）。

### 障礙台帳の字段仕様 — 一行で完結する障礙記録

障礙の五類型（→前掲）を台帳として運営する際、一行記録の字段仕様を確定する（字段の欠落が障礙の落日を不确実にする、→3.4 末尾の「障礙の生存を追う」の実現）。必須十二字段：**ob_id**（graph:// URI、→1.4）、**kind**（N1〜N5）、**on**（対象：asset/goal/transition の URI——障礙は必ず「何が」を持つ）、**blocks**（塞がれた goal の辺——blocks 無しは障礙でなく雑報）、**instance**（実例時刻・観測 URI 引用——実例無しの障礙は形式上のghost、→3.4 の障礙の落日が実例突合で回るのはこの字段があるから）、**evidence**（観測・日誌の URI 群、→4.4 証拠条約）、**owner**（処理の末端——5.1 の accountability の障礙版、末端無き障礙は審議に回せない）、**clock**（処理の時間預算、→7.2 周期設計）、**action**（処理 act または Quarantine 引用）、**effect_verified**（処理後の実測、→7.3 の effect_verification 辺）、**rule_ref**（この障礙が改めた规則 / まだ改めていない规則の URI——→8.1 の stale_obstacles がこの辺の不在を測る）、**sunset**（再点検周期——障礙条目自体の落日）。

```cypher
// obstacle-row-complete — 十二字段の invariant(CI/週次)
MATCH (o:Obstacle) WHERE o.created > datetime() - duration('P90d')
OPTIONAL MATCH (o)-[:BLOCKS]->(:Goal), (o)-[:INSPECTED_FROM]->(:Evidence),
               (o)-[:VERIFIED_BY]->(:EffectEvent), (o)-[:AMENDED]->(:RuleAdoption)
WITH o, count(DISTINCT coalesce(...)) // 実装:各辺的有無を case で集計
RETURN o.ob_id, [c IN ["blocks","owner","evidence","verified","amended"]
                 WHERE not edge_present(o,c)] AS missing;
```

字段仕様の哲学上の要点は二つ。**owner の強制**——責任は障礙の字段としてのみ存在する（→5.3 「主体は配列図で立つ」の障礙版。owner 無き障礙台帳は、世界が人間に文句を言っている台帳で、誰も応答できない）。**rule_ref の強制**——障礙が规則を変えた迹（または変えられていない事実）が載る。後者が積累する台帳は「障礙を処理した」組織の実況である——処理が规則を変更しない処理は、次回の同じ障礙の預定調度である（→2.5 簿記の伦理・→7.1 RuleAdoption の障礙由来の生成）。

## 3.5 FOL実践 — ゴール展開木と障害の一階述語論理コード

障礙は ¬G として定義され、障礙分解は ¬G の論理分解に一致する（→3.4）——この節ではその「一致」を、実行可能な Python + z3-solver のコードにする。z3 は SMT ソルバ（satisfiability modulo theories）であり、FOL の断片（本書では線形整数算術＋quantifier-free）の充足可能性を決定する。要求の木を z3 の論理式として再帰構築し、葉（要求・仮定）からの充足を判定し、障礙の網羅を unsat 証明で検査し、最小障礙セットを unsat core と反例列挙で得る。節の後半では、この手法の限界——FOL 全体の決定不能性——を隠さず書く。**限界を隠す形式化は偽りの形式化であり、限界を登記した形式化は誠実な工学である**（→4.1）。

### 論理の選択 — なぜ z3 で、どこまで z3 に頼るか

完全な FOL は決定不能である（Church の定理）。任意の FOL 文の充足可能性を判定するアルゴリズムは存在しない。よって本書の判定器は常に**限定された断片**上で動く。使う theories はつぎの三つに限定する。

1. **線形整数算術（LIA）**：時刻・振動値・閾値・回数。`vib(m,t) ≥ thr(m)`、`t' - t ≤ 300s`。
2. **boolean の組合せ＋有限 quantifier**：機械台数・時点数が有限なので、quantifier は unrolling で消せる（→3.3 の時間窓 unrolling と同じ手）。
3. **datatype（列挙）**：Shift 型、故障コード、EARS 五型。

LTL は時点の有限系列に unrolling して LIA+bool に落とす（bounded model checking の要求版）。unrolling 境界 `T_MAX` と機械数 `M_MAX` は、判定の**有効範囲**であり、要求の木に `verification_horizon` プロパティとして登記する。範囲外の違反は発見されない——この不在の登記が、形式検証を占星術から区別する唯一の部品である。

### 骨格実装 — GoalTree の再帰構築と充足判定

要求の論理は「葉の要求 R と仮定 A が AND で結ばれ、各内部ノード G が子ゴールの conjunction で含意される」という構造である。充足判定の本体は一つ——**`A ∧ R ∧ ¬G_root` が unsat なら充足**（仮定と要求の下で、root ゴールの否定は起こりえない）。

```python
# goal_tree_sat.py — 要求木 z3 充足判定器 (本書の第2部の心臓部)
# 哲学: 充足 = 「要求と仮定を書き換えない限り、goal 違反の世界は存在しない」
# という存在論的不可能性の機械証明である(→4.5 の sat=存在証明 と対).
from __future__ import annotations
from z3 import (Solver, Ints, Int, And, Or, Not, Implies, sat, unsat,
                Optimize, Function, Bool)

class Goal:
    def __init__(self, name: str, formula, children: list[Goal] | None, kind: str):
        self.name, self.f, self.children, self.kind = name, formula, children, kind

class ReqTree:
    def __init__(self, root: Goal):
        self.root = root

    def leaf_formulas(self, g: Goal) -> list:
        if g.children is None:                 # 葉 = requirement or assumption
            return [g.f]
        out = []
        for c in g.children:
            out += self.leaf_formulas(c)
        return out

    def check_satisfaction(self) -> tuple[str, dict]:
        # (1) 分解の内部論理チェック: 各 AND ノードで children ⊨ parent が成立つか
        for g in self._internals(self.root):
            s = Solver()
            kids = And(*[self.expand(c) for c in g.children]) if g.kind == "AND" \
                   else Or(*[self.expand(c) for c in g.children])
            s.add(kids, Not(g.f))
            if s.check() != unsat:
                return f"decomposition-gap@{g.name}", s.model()
        # (2) 要求充足: 葉(要求∧仮定) ∧ ¬root が unsat か
        s = Solver()
        s.add(And(*self.leaf_formulas(self.root)), Not(self.expand(self.root)))
        if s.check() == unsat:
            return "SATISFIED", {}
        return "COUNTEREXAMPLE", s.model()

    def expand(self, g: Goal):
        """goal の定義式を、子の式へ展開した論理式として返す(再帰)。"""
        if g.children is None:
            return g.f
        kids = And(*[self.expand(c) for c in g.children]) if g.kind == "AND" \
               else Or(*[self.expand(c) for c in g.children])
        return And(g.f, kids)

    def _internals(self, g: Goal):
        if g.children is None: return []
        out = [g]
        for c in g.children: out += self._internals(c)
        return out
```

### 保全現場の例 — 4ノードのゴール木で本当に unsat が出るか

3.3 の例（夜間・振動→5分以内点検）を境界付きの有限世界で埋める。時点は 0〜2（Δt=3分）、機械は m1 のみ、振動値は整数 mm/s（0.1mm/s 単位で10倍整数化——LIA の分数回避、境界設定の一例）。

```python
# demo_night_inspection.py
v  = Int("vib_t0");  v1 = Int("vib_t1");  v2 = Int("vib_t2")
ins = [Bool(f"inspect_t{i}") for i in range(3)]
# 環境仮定(assumption): センサーは各3分窓で1回サンプリング(vib は窓の最大値)
A = And(v >= 0, v1 >= 0, v2 >= 0)
# 要求(葉の requirement): 検知ノードは 3分ごとに評価し、検知時 inspect_t_i を立てる
R = And(Implies(v  >= 45, ins[0]),
        Implies(v1 >= 45, ins[1]))
# root goal: 検知から5分(=2窓の unrolling 近似: 3分窓2つ=6分<5分近似は粗い。
#           境界が要求より粗いことを verification_horizon に登記する)
G = Implies(v >= 45, Or(ins[0], ins[1]))

root = Goal("G-inspect-6min", G, [
    Goal("R-detect", R, None, "REQ"),
    Goal("A-sampling", A, None, "ASMP")
], kind="AND")

t = ReqTree(root)
print(t.check_satisfaction())
# ('COUNTEREXAMPLE', model(v>=45, ins[0]=False, ins[1]=False)) — ではなく、
# R が Implies なので model は ins を自由に残す: COUNTEREXAMPLE が出る!
```

**このデモの故意の失敗が本章の核心である。** 上の結果は COUNTEREXAMPLE を返す。なぜか——要求 R は「検知時に inspect を立てる」を意味するが、z3 の model は `v < 45` を選んで implication を空に真（vacuous）にできる。要求は「振動が上がったすべての世界」を強制していない。世界全体（環境条件）を仮定側で与え忘れたためである。

```python
# 修正: 世界制約(振動は実際に上がった)を仮定へ加える。
A2 = And(A, v >= 45)          # 事例世界: 夜間で実際に振動異常が起きた
# → このとき unsat が出るか? R の ins[0] 強制と G の Or(ins0, ins1) から unsat。
```

修正後は unsat——「仮定 A2 と要求 R の下で、goal 違反は存在しない」の証明。要求充足の証明が、要求の木と世界の記述の**両方**に依存することが、このデモの教訓である。充足論証 `sat(A ⊧ R ⇒ G)` の A を薄く書くと充足は空に強くなる（→3.3 の vacuity 検査がここでも発火する）。

### 障礙の網羅検査 — ¬G の覆い込みを unsat で判定する

障礙 O₁..Oₖ が ¬G を覆っているか（網羅性）は、`G ∧ ¬O₁ ∧ ... ∧ ¬Oₖ` が unsat（G と「障礙ゼロ」が共存不能）であること。覆い漏れ（gap）がある場合、solvable モデルが「障礙がないのに goal が壊れた世界」——障礙分析の穴——として返る。このモデルは 3.2 の `gap_witness` に登記される（→3.3 の分解正当性検査と対）。

```python
def obstacle_coverage(g_formula, obstacles: list) -> dict:
    s = Solver(); s.add(g_formula)
    for o in obstacles: s.add(Not(o))
    r = s.check()
    if r == unsat:
        return {"coverage": "COMPLETE"}
    m = s.model()
    return {"coverage": "GAP", "gap_witness": m,
            "reading": "障礙ゼロで goal 違反が起きうる世界が存在する。障礙分解の漏れ。"}

# 障礙ノードの相互重複(二重計上)は sat 両立で測る:
# O1 ∧ O2 が sat なら独立でない(3.4 の CO_CAUSED の論理的根拠)
```

障礙の AND/OR 分解の「正しさ」は二方向からサンドイッチできる——上位障礙の定義（論理式）が子の conjunction と論理同値か（双方向 implication の unsat 検査）を、全エッジで検査する。同値でなく `O_top ⇒ ∨O_children` だけが成立つ場合、逆方向の失敗（子のどれかが起きても ¬G に届かない）は「障礙葉が ¬G より強い」過剰分解で、実害は過剰警戒（False Positive を設計に焼き込む）。過剰分解と過少分解を区別して報告する——報告の粒度が、そのまま対策のコスト配分になる。

### unsat core の実務 — 「どの要求が衝突しているか」の読み方

要求増分同士の矛盾（3.2 の「矛盾が場所を得る」の機械形）は、unsat core で読む。core とは unsat を作る最小仮定集合であり、衝突している要求（または要求＋仮定）の名簿そのもの。

```python
def conflict_roster(requirements: dict[str, any]) -> list[str]:
    s = Solver()
    named = {}
    for name, f in requirements.items():
        b = Bool(f"dep_{name}")
        s.add(Implies(b, f)); s.add(b); named[b] = name
    if s.check() != unsat:
        return []                                  # 矛盾なし
    core = s.unsat_core()
    return [named[b] for b in core if b in named]  # 衝突要求の名簿
```

読み方の実務注：unsat core は衝突**候補**の最小集合であり、唯一の犯人ではない（別の要求を削っても解決しうる）。衝突解決の選択（どれを削るか）は telos の優先（3.2 の softgoal 木）で決まり、論理では決まらない。論理が名前を渡し、人間が級を決める——5章以降の reckoning/judgment 分離が、もうこの小さな関数で発火している。

### 決定不能性の登記 — verification_horizon を要求の木に書く

最後に、本章全体の誠実さを担保する登記コードを置く。z3 は非決定停止しうる（quantifier -heavy な定式、非線性算術）。タイムアウトと未決定は、**結果の缺失**ではなく**結果の種類**として扱う。

```python
from z3 import set_param, Solver, unknown

def bounded_check(tree: ReqTree, horizon: dict, timeout_ms=10_000):
    set_param("timeout", timeout_ms)
    verdict, detail = tree.check_satisfaction()
    if verdict.startswith("unknown") or detail is None:
        # 未決定を要求ノードへ書き戻す(登記された未知 = 限定付き既知)
        return {"verdict": "UNKNOWN@horizon",
                "verification_horizon": horizon,     # T_MAX, M_MAX, Δt
                "obligation": "manual review L2",    # 手動レビューへの自動エスカレーション
                "recheck_by": horizon["review_due"]}
    return {"verdict": verdict, "verification_horizon": horizon}
```

`UNKNOWN` を例外で落とさない設計（verdict として型で持つ）を強調する。未決定の扱いを設計した判定器は、限界の登記を要求木の一級の性質（`verification_horizon`）として産む。限界が要求の属性になったとき、形式検証は無限の約束から**期限付きの契約**へ変わる（→4.4 の Design by Contract は、この契約性を要求分析の全へ拡張する）。

### FOL→z3 の穴二つ — 量化と領域の落とし方

障礙の充足検査（→前掲の z3 利用）で、正しく見えて最常見に壊れる二つを inscribe する。**穴一：量化の爆発**。`ForAll(equipment, ...)` は設备実例の有限集合で grounded に書ける（Python ループで And/Or を展開）が、展開を恐れて z3 の量化に書くと quantifier 消去が走らず unknown になる。**原則：実例集合が既知なら量化は展開する**——世界が有限な限り量化は機械的に扱える（3.2 の実在的完全性の宣言が、量化の展開可能条件を給える:「集合は完全です」と宣言された集合でのみ展開は正当。未知の成員は展開に現れない=世界は開いている、→3.2 の開き宣言の z3 版）。**穴二：整数と実数の取り違え**。振動値の実数演算に Int 型を使うと、境界条件（`vib >= 4.2` の 4.2 が 4 に切捨てられ、境界の test が假に通る——**型は境界を偽装する**）。E1 実測級の境界値を E2 見通し級で書く際の型宣言（Real/Int/FiniteDomain）は、4.1 の級の字段の一部である（実測は実数、計数は整数——数字の型を世界側から決まらせる、→4.4 の不変条件テストで境界値 3 点（下・境界・上）を強制する理由）。

```python
# grounded quantifier — 既知集合の量化は展開(→3.2 完全性宣言のある集合のみ)
def forall_known(items, body):
    return And([body(x) for x in items])   # z3 の ForAll に書かない
```

unknown が返った時の処理は 3.5 の三段構え（UNKNOWN 登記→人間審議）をそのまま使う——**求解器の unknown は障礙ではなく、求解器の側の落日対象**（モデルの量化設計が老朽した、z3_gate の test に量化爆発の回帰を追加、→A.4 障害目録七）。

## 3.6 責任の配分 — エージェントモデルと意図

ゴール木が充足された（→3.5）としても、要求文書は完成しない。充足論証 `sat(A ⊧ R ⇒ G)` の中に、まだ名前のない主体がいる。**要求は、誰かに実現させることを言外に含んでいる。** 「5分以内に点検が起きる」は、点検という行為の主体がいなければ空虚である（→3.3 の vacuity 検査が既に示していた）。GORE は主体を agent（エージェント）と呼び、ゴール・要求・仮定の三者すべてが「あるエージェントに実現可能（realizable）」であることを要求する。この節では、エージェントを単なる実行プロセスではなく**意図（intention）の帰属先**として定義する。責任の配分とは、意図の帰属の配分である。そして節の後半で、人間エージェントと機械エージェントの非対称性を確定する——この非対称性が第3部全体の設計原理（AIの脱・司令塔化）の土台になる。

### 実在可能性（realizability）— 実現できる主体にしか要求は割り当てられない

KAOS の agent 概念の中核は、要求 R の **realizability**（実現可能性）の定義である。粗く言えば——要求 R がエージェント A に実現可能とは、R の実現が A の支配領域（environment of A）内の動作だけで決まる、という条件である。支配領域外の事象に依存する要求は、そのエージェントに割り当てられない。

この定義の威力は、否定形で現れる。**「A に実現不可能な要求」を割り当てた瞬間、充足論証は成立しても、実装は空証する。** 3.4 の障礙葉が `REALIZED_BY_FAILURE_OF` で繋いだエージェントが、実はその障礙を支配していなかった——これが組織の要求配分の最頻出事故である（「担当者が対応する」要求の担当者が、担当の変更を支配していない、のような例）。

```cypher
// 支配領域の登記: エージェントが「変更できる」観測・状態・行為の集合
MATCH (a:Agent {agent_id: 'AG-nightshift-lead'})
CREATE (a)-[:CONTROLS {scope: 'inspection_schedule'}]->(:DomainElement {name: 'inspection_schedule'}),
       (a)-[:CONTROLS {scope: 'manual_override'}]->(:DomainElement {name: 'manual_override'});
// 制御できない要素: センサーハードの稼働(保守部門の質料)、天候、本体の来訪。

// realizability 検査: 要求 R の論理式が参照する要素が、
// 割り当て先エージェントの CONTROLS 集合に含まれるか
MATCH (r:Requirement {req_id: $r})-[refs:REFERENCES]->(el:DomainElement),
      (a:Agent {agent_id: $a})
OPTIONAL MATCH (a)-[:CONTROLS]->(el2:DomainElement) WHERE el2 = el
WITH r, el, a, count(el2) AS controlled
WHERE controlled = 0
RETURN r.req_id, el.name AS outside_control,
       'REALIZABILITY-VIOLATION' AS verdict;
```

`REFERENCES` 辺の張方は翻訳ログ（→3.3 の `RefinementTrace`）と共通で、論理式が参照する語彙がそのまま要求の「世界への接触面」である。この検査の産出する `REALIZABILITY-VIOLATION` は、配分ミスの自動検出である——配分ミスの多くは悪意ではなく、組織図の変化と要求文書の陳腐化のすれ違いで生む（3.4 の障礙の `stale` と同じ entropy）。

### 意図的概念 — ゴールはエージェントの内部状態ではない

エージェントモデルの理論的伝統は別に存在する。Intentional Agent 研究（Dennett の意図的立場、Bratman の実践理性の理論、Cohen & Levesque の intention の論理、JSBV 体系）。本書がこれらから拾う中心命題を三つ置く。

**其一、意図は予測の道具である（Dennett）。** 人間を「信念と欲求で行動を予測するシステムとして扱う」ことが有効なのは、予測コストが神経状態を追うより安いからである。同型が設計に使える——エージェントに `intent` を登記することは、その挙動の予測コストを組織全体で下げる操作である（→2.5 の `:intent` 必須、→3.3 の充足論証の同じ代数）。

**其二、意図は再考に抵抗し、持続する（Bratman）。** intention は goal と違い、達成不能の認識後も計画を支え続ける安定化機能を持つ（目標の固執）。これは設計では**two-edged** である。意図の持続は実行の安定を生み、障害を壊さない。しかし「もはや目的に serve しない計画」を回し続ける爆弾にもなる。Bratman の解決は revision（部分的再考）の構造——計画の再考は、上位意図の再採用を要求する。設計翻訳：`intent` の再考は上位 goal の `ACHIEVED_FOR` の再検証を誘発する。**意図の更新は必ず上位の意図の更新を招く、という連鎖の登記**が 8.5 の「理由を問う対話」の形式的原型になる。

**其三、共同意図は「相互belief の閉包」である（Cohen & Levesque, Grosz）。** 共同で G を遂行するとは、各自が G の遂行を意図し、かつ「各自が遂行を意図していることを各自が知っている」無限の相互 belief を持つことである（近似条件で有限化される）。現場チームとシステムの共同遂行は、この相互 belief のインフラである——システムはチームの意図を読み、チームはシステムの意図（`intent`、理由提示、→8.5）を読む。相互 belief の片側の断線が「自動システムの暴走」の定義にほかならない。

```cypher
// 共同遂行の最小登記: shared intent の相互 belief 構造(有限近似)
MATCH (sys:System, team:AgentTeam {team_id: 'nightcrew'})
MERGE (sys)-[:INTENDS {intent: 'G-inspect-5min', role: 'detect+route'}]->(:IntentionNode {i_id: 'I-42'})
MERGE (team)-[:INTENDS {intent: 'G-inspect-5min', role: 'inspect'}]->(:IntentionNode {i_id: 'I-42'})
WITH sys, team
MATCH (n:IntentionNode {i_id: 'I-42'})
MERGE (sys)-[:BELIEVES_OF {about: 'team.role'}]->(n)
MERGE (team)-[:BELIEVES_OF {about: 'sys.role'}]->(n)
MERGE (n)-[:EXPOSED_AS {surface: 'reason-panel'}]->(:Interface)
// EXPOSED_AS が相互 belief の物理実装である(→7.5 の reason panel、→8.5 の対話プロトコル)。
// 意図がインターフェースに露出されないシステムは、共同遂行の条件を機構的に欠く。
```

### エージェントの分類図 — 人間・機械・組織・自然法則

KAOS は agent の類型を機械（machine）、人間（human）、組織（organizational）、野生（wild、制御不能環境）に分ける。本書はこれを「支配領域の性質」と「意図の帰属の可否」という二次元に広げる。

| 類型 | 支配領域 | 意図の帰属 | 要求の割り当て | 例 |
|---|---|---|---|---|
| 人間 | 行為・解釈・再考 | 満（解釈可能） | できる（soft 要求含む） | 夜勤リーダー |
| 機械 | 行為・計算 | 擬似（登記された intent） | 硬性格要求のみ | 検知・通知系 |
| 組織 | 役割・手順・承認 | 半（公式 intent の主体） | 手続要求 | 承認委員会（2.6） |
| 自然法則・野生環境 | 変更不能 | 不可 | 仮定のみ | 重力、通信物理 |

重要なのは softgoal 次元である。「優先する」「適切に」の遂行は、機械への割り当てが原理的に禁止されている（→3.3 の型二の残留が、ここでエージェント割当の問題として再発する）。soft 要求を機械に割当てた瞬間、程度判断が機械の内部に潜り込み、監査不能な判断が誕生する——3.1 の「在庫最適化」事故の agent 割当版である。

### 非対称性 — 人間エージェントと機械エージェントの三つの差

第3部の設計原理の地基を、ここで打っておく。両者は「同じ種類の実行主体」ではない。差は三つある。

**第一に、解釈の開閉。** 人間の意図は開いている——行為の理由を、行為後にでも問い直し、破棄できる（Bratman の再考構造が人間に内在する）。機械の「意図」は登記された文字列であり、行為後に意味を更新する能力を持たない。だから `intent` 更新の連鎖を、人間側が設計・運用で担保し続けるほかない（→8.5）。

**第二に、残余の扱い。** 人間は 2.1 の残余を生きられる——言葉にならなかった状況の手触りを、次の判断に持ち込める。機械は残余を持たない。残余は単に存在しない（→1.6）。機械に残余相当を担わせる試み（例外処理リストの拡張）は、残余を明示知に変換する無限作業であり、1.6 で退けた削減主義の再生産である。

**第三に、懲罰への応答（responsibility）。** 責任の最終的な所在は、懲罰と名誉と解釈義務を受けることのできる存在でなければならない。機械は懲罰されない（サーバ室的な比喩は比喩である）。よって責任の連鎖の末端は常に人間に座る——3.5 の unsat core で「論理は名前を渡し、人間が級を決める」と書いたが、級を**決める**という行為そのものに責任の器がいる。

この三差を、本書では**非対称性定理（非公式）**として扱う。定理という語に甘えて、正確には三つの設計要請として置く。(1) 機械エージェントには soft 要求を割当ない。(2) 機械エージェントの `intent` は人間の再考連鎖に接続されたインターフェースへ露出必須。(3) 責任の連鎖の末端は人間エージェントのノードで終端し、その末端ノードは `RESPONSIBLE_FOR` 辺の到着点として機械に読める形で登記する。

```cypher
// 非対称性の機械検査
// (a) soft 要求が機械エージェントに割当されていないか
MATCH (r:Requirement)-[:ASSIGNED_TO]->(a:Agent {kind: 'machine'})
WHERE r.softness = 'soft'
RETURN r.req_id AS illegal_soft_assignment;
// (b) intent のインターフェース露出を持たない機械エージェント
MATCH (a:Agent {kind: 'machine'})
WHERE NOT EXISTS { MATCH (:IntentionNode)<-[:INTENDS]-(a),
                   (i:IntentionNode)-[:EXPOSED_AS]->(:Interface) WHERE true }
RETURN a.agent_id AS intent_dark_agent;
// (c) 責任末端が未登記の action(実行可能だが責任者がいない行為)
MATCH (act:Action {executes_on: 'field-api'})
WHERE NOT (:Agent)-[:RESPONSIBLE_FOR]->(act)
RETURN act.name AS orphan_action;
```

`orphan_action` は本章の診断定理の第三の兄弟である——**責任者のない行為は、実装されていても実現されていない**（実行された瞬間、責任の連鎖の不在がそのまま事故の帰属不能になる）。2.6 の権限条文が要求側の倫理だとすれば、この (c) は行動側の倫理の検査である。

### 要求の全体ライフサイクルでの agent 変更 — 組織が変わると要求も変わる

配分は一度の割当で終わらない。組織変更（部署統合、委託化）で `CONTROLS` 集合が変わり、realizability が静かに壊れる。要求木のエージェント辺（`ASSIGNED_TO`）は 2.5 の履歴代数で管理し、`CONTROLS` の変更コミットは realizability 再検査を CI で自動的に発火させる（→4.6 の回帰テストと同一の配管）。**要求は紙に書かれた瞬間から腐り始めるのではなく、組織が動き始めた瞬間から腐る。** 腐敗の検出を人間の勤労（定期レビュー）だけに置く設計は、2.3 の「循環なき記憶」と同じ病を持つ。

### 意図の簿記 — belief/desire/intention を照会可能な構造にする

エージェントモデル（BDI: belief–desire–intention、→前節の哲学的地基）を、グラフ上の照会可能構造として実装する——「エージェントに意図があるか」の哲学的問答ではなく、**意図に相当する簿記が存在するか**の検査である（→5.1 の判断の三要素の意図版）。三つの関係名を確定する。

`HOLDS`(agent→Belief: その agent が現在正しいと行動の前提にしている記述。根拠・等級・落日つき——E4 前提の agent 版、→4.1)。`PURSUES`(agent→Goal: その agent が現在実現をコミットしている目的。期限と中止条件つき——コミットメントの簿記)。`COMMITTED_TO`(agent→Plan/Action 群: 目的 Pursuit のための当面の手段への束缚。他 agent への委任を含む——→7.2 の mission packet がこの辺のデータである)。この三辺が揃った agent だけが、3.6 の責任配分の主語になれる——信念・欲望・意図の「哲学的定義」ではなく、**簿記の三辺**として定義する（「意図がある」=「PURSUES と COMMITTED_TO が落日運用つきで登記されている」）。

```cypher
// intent-audit — 意図の簿記の invariant(→3.6 の責任配分の機械検査)
// (a) COMMITTED_TO のある agent に Pursues の親がない(実行だけ追われ目的が不明)
MATCH (a:Agent)-[:COMMITTED_TO]->(p:Plan) WHERE NOT (a)-[:PURSUES]->(:Goal)
RETURN a.id, 'orphan-intention';
// (b) Pursues の goal が落日(Telos chain 切断)でも Commitments が走る
MATCH (a:Agent)-[:PURSUES]->(g:Goal)-[:IN_SERVICE_OF*1..3]->(root:Goal)
WHERE root.sunset < datetime()
MATCH (a)-[:COMMITTED_TO]->(p:Plan) WHERE p.status='active'
RETURN a.id, g.goal_id, 'pursuit-of-dead-telos';
// (c) Belief 集合の落日率(agent の世界観の老朽度)
MATCH (a:Agent)-[h:HOLDS]->(b:Belief)
WITH a, avg(CASE WHEN b.sunset < datetime() THEN 1.0 ELSE 0.0 END) AS stale_rate
RETURN a.id, stale_rate WHERE stale_rate > 0.2 ORDER BY stale_rate DESC;
```

三検査の意味を現場の語で読む。(a) orphan-intention は**影子 act の簿記形**である（目的なしの実行登記——→5.1 のコミットメント欠如が agent スキーマで再発しないための門）。(b) pursuit-of-dead-telos は**目的のゾンビ運用**——上級の目的が落日しても下位のコミットメントが走り続ける（→3.1 の telos_chain の落日と 5.5 のステートマシンのガード落日の合成事故、→3.4 複合式一）。(c) belief の老朽率は agent の世界観が実測から遊離している度で、上位 2 割に再検証（→5.2 の revalidation-patrol の agent 版）を強制する。

BDI の哲学的注釈を最後に一句。この簿記化は「agent に信念があるか」という問いを消去しない——消去するのは、簿記なしの信念語で agent を説明する**特権**である。信念と書かれたものが実は信念のふりをした観測ログでないこと、意図と書かれたものが実行ログの事後叙述でないことを、三検査が保証する（→4.4 の宣言と実体の突合の agent 版）。責任配分（→前節）は、この三辺の主語にのみ配分される——**簿記された主体にのみ責任は載り、載った責任は簿記で追える**。3.6 の結論は 5.3 の結論と同一の定理の要求工学版である（主体は哲学ではなく配列図で立つ）。
