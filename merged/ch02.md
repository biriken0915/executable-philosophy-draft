## 2.1 分節化の暴力 — 分類が得るものと奪うもの

第1章で、明示化（explicitation）は原理的に完全になりえないことを見た。本節は一段荒い刃を扱う。知識を明示するとは、世界をまとまりに「切る」ことである。切る行為は、得られるものと捨てられるものを同時に決定する。カテゴリー（category）という語には、切るという語層が刻まれている。その語感は消えたが、行為は残っている。「これは `Misprint` である」と確定する瞬間、我々は依然として世界に刃を入れている。本節ではこの切断を分節化（articulation / sectioning）と呼び、暴力を比喩としてでなく計測可能で設計可能な対象として扱う。分類が得るのは数えられること・比較できること・部門間で転送できることだ。奪われるのは粒度、含み、その場限りの指示、そして報告そのものを発火させていた行為性である。同じスキーマでも、この差を記録する設計と記録しない設計では、保存装置にも埋葬装置にもなる。残余（residue）を捨てるか保存するかが設計を分ける——これが本節の中心命題であり、第2章全体の地盤になる（→第2.2節、→第2.5節）。

### 2.1.1 分類は刃である — caedo から category まで

語源を三層、そのまま引いておく。第一層は物理的な切断である。印欧語根 \*(s)keh₁- は「切る」で、ラテン語 caedere（叩いて切る）と secāre（切り分ける）に分かれた。caedere からは caesura（韻節の切れ目）、caesiem（切り傷）、homicide が出た。secāre からは sectio（切断）→ section、segmentum（切り痕）→ segment、以及び secans（切っている者）→ secant が出た。第二層は言語的な切断である。ギリシア語 katēgorein（καταγορεύειν）は ἀγορά（広場）で何かを「言い放つ」「～だと申し立てる」の意で、新約聖書では「告発する」に近づいた。ラテン語 translators はこれを categoria と写し、アリストテレスの十範疇（categories）の翻訳語にした。第三層が本書の着眼点である。つまりカテゴリという語には、(1) 切る（世界を分ける）と (2) 告発する（他を排除して名指す）という二重の暴力が、語の層として刻まれている。

この語源は飾りではない。カテゴリが中立な記述ではなく、つね誰かの申し立てであったことを思い出す装置になる。アリストテレスの十範疇は、世界の部位の列挙ではなく、「ものについて言いうる位（πότερον λέγεται）」の列挙だった。存在論であると同時に構文である。これはそのまま現代の設計文書に翻訳できる。スキーマは存在論の主張であり、API と列挙型はその構文上の断定である。`defect_type` の値域を 12 個の列挙値に閉じたとする。その瞬間、コードは「この領域にはこの 12 種以外の異常は存在しない」と申し立てている。世界が閉じたかどうかは、コードの正しさとは無関係である。

```python
# 哲学的意図: enum は katēgoria（申し立て）である。
# 閉じた瞬間に「他は存在しない」という存在論的断定が、型宣言の形でコードへ混入する。
from typing import Literal, TypedDict

DefectType = Literal[
    "PaperJam", "Misprint", "Tension", "Coating",
    "Crease", "Splice", "Static", "Calender",
    "RollEdge", "Humidity", "Operator", "MISC",
]  # MISC は世界の型ではなく、我々の無知の別名である（→2.1.2 の残余論）


class ClosedRecord(TypedDict):
    defect: str
    type: DefectType


def record_closed(defect: str, t: DefectType) -> ClosedRecord:
    # closed-world assumption: 列挙にない語はこの時点で受け付けられず、
    # 現場の言葉はログにも残らない。失われたものは復元クエリの対象にすらならない。
    return {"defect": defect, "type": t}


def record_open(defect: str, raw_term: str, t: DefectType | None) -> dict:
    # open-world: 現場の語（raw_term）を一次データとして保持する。
    # 切断は行う。ただし切断の両側を保存する。この 2 行の差が第2章の全設計差である。
    return {"defect": defect, "type": t, "raw_term": raw_term,
            "cut_performed": t is not None}
```

`record_closed` と `record_open` の差は、処理能力の差ではない。保存される世界の量の差である。しかもこの差は後から回復できない。切断された側は、切断が行われたこと自体が記録されていない限り、痕跡を残さない。

現場の失敗例を一つ、実際の数値の形で書いておく。ある紙加工ラインの品質システムに 12 値の `defect_type` を導入した。導入当初は欠損値率 3% で、ダッシュボードは健全に見えた。4 年後、`MISC` への流入は全件中 38% に達していた。`MISC` の内部では現場独自に 6 種の呼び名が自然発生していたが、列挙型にその型がないため集計も照会もできない。真の障害の増大（カレンダーロールの面圧異常、8 か月間で 3 件）が `MISC` の文字列メモに混じって検出されず、最終的にライン停止事故になった。原因は作業者の怠慢ではない。列挙は成功していた。失敗したのは、列挙の外部で分類が自律的に発生していることを観測しないデータモデルである。

### 2.1.2 切断は必ず残余を生む — 残余の三型

分類が残余を生むのは偶発ではない。残余は分節化の構造的不分払いである。理由を三つ挙げる。第一に、語彙は有限で世界は有限でない（列挙は必ず余る）。第二に、切断は一度で終わらず、部門ごとに別々の刃が入る（同じ領域に複数の分類が重なる）。第三に、世界には切る以前の状態がある（連続量・傾向・関係・手応え）。

残余には三つの型があり、それぞれ症状と対処が違う。混同すると設計を誤る。

| 型 | 定義 | 現場の言葉 | コードの症状 | 保存の形 |
|---|---|---|---|---|
| 未分類（unclassified） | 世界の切断が語彙の網の外にあった | 「あれは MISC に入れてます」 | `OTHER`/`MISC` への流入率上昇、自由記述の増長 | `Residue` ノード + レビューキュー |
| 多重帰属（cross-classification） | 二つ以上の切断が同時に成り立つ（階層の交差） | 「あれは紙切れじゃなくて張り付けのどっちでもいい」 | `disjointWith` 違反、多重分類の強制で報告が減る | 多値関係（`classifiedAs*`）を正規化せず許可 |
| 非分節（unarticulable） | 切る以前の状態。連続・傾向・関係・評価 | 「機嫌が悪い」「そろそろ来る感じ」 | 観測値はあるが型がない、閾値設計の論拠が消える | 生テレメトリと原文を保存し、型づけない（→第1.4節） |

第三の型が最も高価だが、最も扱われない。非分節なものは、保存するのではなく「型づけないまま残す」しかない。ここで重要なのは、残余は計測できるという点である。残余の総量は測れない（測れないことの測れない部分がある）。しかし残余の痕跡——`OTHER` 流入率、自由記述の字数、分類時の逡巡——は統計として記録できる。

```python
# residue.py
# 哲学的意図: 残余を「データの質の低さ」としてではなく、
# 語彙の世界に対する不足の計測値として扱う。数値は将来の分類のための証拠になる。
from dataclasses import dataclass

UNRESOLVED = {"MISC", "OTHER", "UNKNOWN", ""}


@dataclass
class Ticket:
    raw_term: str          # 現場が実際に言った語（原文は絶対に変更しない）
    master_type: str       # 正規化後の語（1対1とは限らない）
    free_text_len: int = 0 # 自由記述に逃げた字数 = 語彙が食いきれなかった量


def residue_rate(tickets: list[Ticket]) -> float:
    cut = [t for t in tickets if t.master_type not in UNRESOLVED]
    if not tickets:
        return 0.0
    return 1.0 - len(cut) / len(tickets)


def leakage_index(tickets: list[Ticket]) -> float:
    # 正規化はされたが、現場語とマスター語の距離が大きいケース。
    # 「分類は通ったが意味がすり減った」領域を数値化する（→2.1.3）。
    scored = [t for t in tickets if t.master_type not in UNRESOLVED and t.raw_term]
    if not scored:
        return 0.0
    return sum(t.free_text_len for t in scored) / len(scored)


if __name__ == "__main__":
    data = [Ticket("紙の機嫌が悪い", "MISC", 42), Ticket("カス残り", "Splice", 3),
            Ticket("巻きの癖", "Crease", 27), Ticket("張り付け", "OTHER", 55)]
    print(round(residue_rate(data), 3), round(leakage_index(data), 1))
```

この 2 つの数値を運用に乗せると、ダッシュボードの読み方が反転する。`MISC` の増加は現場の無関心ではなく、語彙の世界への不足として読める。`leakage_index` の高さは、その分類が意味をどれだけ削って通したかのおおよその目安になる。どちらも暗黙知の総量を測るものではない。あくまで明示化の試行の履歴から事後に推定した痕跡の数値である。この留保を忘れた瞬間、残余率は「残余の少なさ」を競う指標に堕落する（Goodhart の法則、→第1.1節）。

### 2.1.3 正規化という摩擦 — マスター用語への翻訳で何が減るか

企業システムで暴力が最も無自覚に行使される地点が正規化（normalization）である。マスターデータ管理（MDM）、統制語彙（controlled vocabulary）、マスター項（master term）。現場が 11 通りの言い方をする異常を、設計側が 8 個のマスター用語へ写す。写像はレビュー済みで、用語辞書に登録され、承認フローを通っている。それでも意味はすり減る（semantic wear）。減り方には四つの型がある。

| 失われ方 | 何が失われるか | 現場の例 | 翻訳後の状態 | 復元のための設計 |
|---|---|---|---|---|
| 粒度の潰れ（granularity collapse） | 現場が区別していた 2 以上の状態 | 「表面のよれ」と「裏面のよれ」 | `Crease` 一種に潰れる | `narrowerMatch` を保持し、上位語から下位語へ展開可能に |
| 含みの除去（connotation stripping） | 評価・緊急度・責任の所在 | 「そろそろ来る感じの張り付け」 | `Splice`（緊急性の標識が消える） | 原文 + 感情価・緊急性を別属性で保存（→第1.4節） |
| 指示詞の断切り（indexicality loss） | 状況依存の参照 | 「さっきのあれ」 | `null` または誤った既定値 | 観測時刻・区域・作業文脈を関係ごと保持 |
| 行為性の消滅（loss of action-implication） | 語を使うことが行動を発火させていた事実 | 「これは `RollEdge` だ」と言うことで停止が決まった | 記述としての型になり、行動が消える | 記述ではなく `Action` を語に紐づける（→第7.3節） |

失敗例を、報告件数の形で書く。あるグループ会社が 3 部門の用語を統一する「単一語彙化計画」を行った。現場の 47 語を 19 のマスター語へ写し、マッピング表は各部門の品質管理者が承認した。6 か月後、異常報告の件数が 1,400 件/月から 430 件/月へ落ちた。失われたのは情報ではなく、報告という行為だった。分析すると原因は三つ重なっていた。現場語には報告者の評価が含まれていた（「これは危ない方の癖だ」）。マスター語は観測者のための語で、行為者のための語ではなかった（含みの除去）。そしてマスター語で報告すると、自分の名前が履歴に残り、評価を含めない文章になったため、報告が処罰のリスクに変わった（権力の層、→第2.6節）。用語を統一すると報告が減る、という現象は組織の抵抗ではなく、翻訳が行為の条件を変えた結果である。

意味のすり減りは完全に測れない。しかし片方だけ測れる。往復翻訳（round-trip translation）である。マスター語から現場語へ逆翻訳し、元の現場語に戻るかを見る。戻らなければ、その語の contents がマスター語に保存されていないことになる。

```python
# 哲学的意図: 翻訳の損失を「意見」ではなく「戻れないケースの数」として記録する。
# 戻れない語の集合は、その語彙が持っていない意味の目録である。
GLOSS = {
    "Crease":   {"表面のよれ", "巻きの癖", "シワ"},
    "Splice":   {"張り付け", "継ぎ", " splice 残り"},
    "PaperJam": {"詰まり", "紙詰まり"},
    "Tension":  {"テンション異常"},
}
FIELD_VOCAB = {"表面のよれ": "Crease", "巻きの癖": "Crease",
               "紙の機嫌": None, "よれ": "Crease"}


def wear_report() -> dict[str, list[str]]:
    exact, narrow, orphan = [], [], []
    for field_term, mapped in FIELD_VOCAB.items():
        if mapped is None:
            orphan.append(field_term)                 # 網の外 = 残余（→2.1.2）
        elif field_term in GLOSS.get(mapped, set()):
            exact.append(field_term)                  # 往復で戻った = 意味が保存された
        else:
            narrow.append(field_term)                 # 片道のみ = 意味が削れた
    return {"round_trip_ok": exact, "one_way_only": narrow, "unmapped": orphan}


if __name__ == "__main__":
    r = wear_report()
    total = sum(len(v) for v in r.values())
    print(len(r["one_way_only"]) / total, r)
```

`one_way_only` に入った語は、そのマッピングが捨てた意味の目録である。「よれ」は `Crease` に渡るが、`Crease` の定義（ gloss）には「よれ」が戻らない。つまり `Crease` を見ても「よれ」の区別は復元できない。これは主観的な感想ではない。 gloss を設計者が書いたという事実だけが前提の、検証可能な主張である。

### 2.1.4 暴力は除去できない — 減らせるのは可視性だけ

ここで本書の立場を明確にしておく。分節化の暴力は除去できない。理由は三つある。第一に、保存は有限の語彙を要する。無限の語彙は保存ではなく複製であり、転送できない。第二に、比較は切断を要する。切断されていないものは集計できない。第三に、分類する主体は切断の外部にいない。スキーマを書く者は、自分の暗黙知で刃の入れ方を決め、その決め方を明示できない（→第1.6節、→第5.2節の被投性）。

したがって設計目標は「暴力のない分類」ではなく、暴力の総量と分布を可視化されたものに変えることだ。三つの原則になる。

1. 記録の原則：切断を最新版の状態としてでなく、イベントの履歴として保存する。どちらの刃が入り、誰が入れたかを残す（→第2.5節）。
2. 可逆の原則：削除を持たない。廃止は `deprecated` と `retires` の関係で表し、失われた語は履歴から辿れるようにする（→第2.4節、→第2.6節）。
3. 可視の原則：残余と翻訳損失を品質コストとして運用画面に出す。見えない損失は予算化されず、予算化されないものは必ず膨張する。

無自覚な分類と自覚した分類の差を、運用観測点で並べる。

| 観測点 | 無自覚な分類 | 暴力を自覚した分類 |
|---|---|---|
| `MISC`/`OTHER` | 現場の怠慢。クレンジングで消す | 語彙不足の指標。レビューキューに積む |
| 語彙変更 | マスターを UPDATE する | 変更をコミットとして記録（誰が・なぜ・何が減ったか） |
| 二語の競合 | 片方を正とし他方を削除 | `closeMatch` を保持し、裁定を履歴に残す |
| 現場の報告低下 | 「周知が足りない」と訓練を増やす | 翻訳コストの現れと読み、現場語を戻す |
| 監査 | 現在の値のみ | 主張と、その変更への主張まで（→第2.5節） |
| 破壊的変更 | 即時反映 | 沈黙の猶予期間と不服従の経路（→第2.6節） |

### 2.1.5 では工学的に何をするのか — 五つの実装判断

思想を配線に落とす。この節の結論は次の五つの判断として実装される。

**判断 1：現場語を一次データとして保存する。** 正規化後の値だけを持つテーブルは、切断の片側しか保存しない。`raw_term` を必須列とし、原文は絶対に後処理で書き換えない。書き換えは意味の抹消であり、抹消を抹消する方法はない。

**判断 2：現場語とマスター語の対応は関数ではなく関係である。** 1 対 1 を前提した外部キーは、暗黙の `exactMatch` 宣言になる。対応は `skos:exactMatch` / `closeMatch` / `broadMatch` / `narrowMatch` の位相付き関係として保持する。`owl:sameAs` は使用禁止とする（置換可能性は意味の同一性ではなく、同一性の申し立てである）。

```turtle
# vocab.ttl — 哲学的意図: マッピングは「翻訳の解像度」そのものを値として持つ。
# exactMatch はほぼ常に過剰な断定である。closeMatch を既定にすると、
# 失われた意味が関係の型として可視に残る（→第2.4節で制約として実装する）。
@prefix skos:  <http://www.w3.org/2004/02/skos/core#> .
@prefix ex:    <http://example.com/plant#> .

ex:Crease a skos:Concept ;
    skos:prefLabel "折れ目" ;
    skos:definition "紙の線状の変形で、折り工程の下流で発生するもの" .

ex:field_yokire a skos:Concept ;
    skos:prefLabel "よれ"@ja ;
    skos:closeMatch ex:Crease .            # 往復で戻らない = 意味のすり減りが宣言されている

ex:field_makinosyuku a skos:Concept ;
    skos:prefLabel "巻きの癖"@ja ;
    skos:broaderMatch ex:Crease .          # 現場語の方が細かい。粒度の潰れを明示

ex:field_kigen a skos:Concept ;
    skos:prefLabel "紙の機嫌"@ja .         # 意図的未マッピング。残余として保存（→判断 3）
```

**判断 3：残余をノードにする。** `MISC` を値として置くのではなく、未解決の語を `Residue` ノードとして立て、レビューキューに積む。レビューは「正しい分類を決める」場ではなく、語彙が世界のどこに負けているかを読む場である。

```cypher
// residue.cypher — 哲学的意図: 残余を「その他」というゴミ箱にせず、
// 将来の分類の証拠としてグラフの一等市民にする（→第2.5節で履歴化する）。
CREATE CONSTRAINT residue_key IF NOT EXISTS
FOR (r:Residue) REQUIRE r.key IS UNIQUE;

MATCH (t:Ticket {master_type: 'MISC'})
WHERE t.raw_term IS NOT NULL
MERGE (r:Residue {key: 'misc:' + t.raw_term})
  ON CREATE SET r.first_seen = t.ts, r.seen_count = 1,
                r.status = 'unresolved',   // 解決済みかどうかが、語彙の負けた場所の地図になる
                r.example = t.raw_term
  ON MATCH  SET r.seen_count = r.seen_count + 1, r.last_seen = t.ts
MERGE (t)-[:LEFT_RESIDUE]->(r);

// 語彙の負荷点のランキング: 頻度 × 未解決。上位語は新規コンセプトの候補である。
MATCH (r:Residue) WHERE r.status = 'unresolved'
RETURN r.example, r.seen_count, r.first_seen, r.last_seen
ORDER BY r.seen_count DESC LIMIT 10;
```

**判断 4：正規化イベントをコミットとして記録する。** 「`yokire` が `Crease` に統合された」は状態ではなく出来事である。変更者・意図・差分・失われた区別を、差分として保存する。これは第2.5節の Git 的コミットモデルの予告である。

**判断 5：意味損失をスロットルに接続する。** 破壊的マッピング（2 語の統合、値域の縮小）を承認する前に、`wear_report()` の `one_way_only` と影響件数を提示し、猶予期間を置く。損失が見える場所に置かれていない設計では、損失は必ず無制限になる。

実装の分岐を三つ示す。本書の採用は C だが、A が選ばれているプロジェクトが多数派であるという事実も記しておく。

| 分岐 | 仕組み | 利点 | 破綻モード | 本書 |

### 2.1.6 この節のアポリア

三つの難点を残す。第一に、残余を保存する設計も、再び分節化する。`Residue` ノードは未分類を救うが、やがて `Residue` 自身が分類され、`status` と `type` を持たされ、新しい残余を生む。残余の再分節化は無限後退する。この後退は打ち切れるものではなく、レビュー周期という運用で切るしかない。第二に、意味のすり減りの測定は、測定可能な分しか測っていない。「報告しなくなった人」はログに残らない。失われた反事実（報告されていたはずの 1,000 件）を我々は復元できない。だから wear 指標は損失の総量ではなく、損失の下限である。第三に、どの切断を正当とするかの裁定は、システム内部では決定できない。裁定は人間の討議に委ねられる（→第6.2節のハーバーマス）し、その討議の条件をシステムが形作ってしまう。この循環は解けない。解けないものを前提として設計に織り込む方法が、次節以降の主題になる。

次節では、この切断をヘーゲルの止揚（Aufheben）として読み替え、破棄しない変更の差分設計へ転用する（→第2.2節）。

## 2.2 ヘーゲル — 止揚（Aufheben）を差分演算として読む

2.1節で、分類は「切る」こと（caedo）であり、必ず残余（surplus）を生むと見た。残余を捨てるか保存するかが設計を分けるとも書いた。では、捨てない設計とは具体的にどんな演算なのか。この節はそこを埋める節である。答えの候補として、ゲオルク・ヴィルヘルム・フリードリヒ・ヘーゲル（G.W.F. Hegel）の止揚（Aufheben）を、形而上学の用語としてではなく、差分演算（differential operation）の仕様として読み替える。止揚は日常語で「取り消し」を意味し、同時に「保管する」「高めて保つ」も意味する — 一つの語が否定と保存を同時に指す。この一語二義こそが、破壊的変更と非破壊的変更を分ける設計規範そのものになる。本節では概念の三段階（即自→対自→即対自）と否定の否定を、分類改版のサイクルとして読み、止揚の三重意味を工場の語彙統合の失敗例に当てはめ、弁証法的進歩は「マージ」ではなく「履歴付き上書き」であるという設計判断を立てる。最後に、その判断を機械的に検証できる差分チェックとして実装する。哲学を飾りにしないための約束事は一つではない。哲学を検算器にすることである。

### 概念は三段階で動く — 即自・対自・即対自

ヘーゲルの『精神現象学』や『小論理学』を読む会に、エンジニアが参加して最もつまずくのは、三段階が「上手な講話の構成」だと思ってしまう点である。正題・反題・合題（these–antithesis–synthesis）という三分法は実際にはヘーゲルの用語ではなく、後世の教科書が扁平化した図である。本節が使うのはそういう図ではない。使うのは概念が内部の矛盾から自己運動する、という構造の方だ。

**即自（an-sich / in-itself）** は、概念がまだ自分自身を区別していない段階である。「未分化だが働いている」という状態を指す。現場の「治具」という語を思い出すといい。作業者はこの語で区別し、区別されていると気づかずに使っている。分類があるのに、分類の境界が可視になっていない。2.1節で述べた正規化以前の語彙の自然状態が即自である。

**対自（für-sich / for-itself）** は、その概念が自分自身と区別される段階である。マスター語彙の設計者が「治具」「冶具」「クランプ」を別概念として定義し、使い分けを求めた瞬間、現場の語は「疑えるもの」になる。区別が意識された瞬間に区別は摩擦を生む — 現場では同じものを指していた語に別定義が与えられ、レポートの数値が動き、担当間で作戦会議が起きる。この摩擦は事故ではない。ヘーゲルの読み方では、矛盾は概念を動かすエンジンであり、停止命令ではない。ある分類が破綻・重複・境界争いを生むのは、その分類が届いていない残余が存在する証拠である。2.1節の残余は、対自の段階で初めて可視になる。

**即対自（an-und-für-sich / in-and-for-itself）** は、区別された概念がより広い規定のうちに自らを再び統一する段階である。注意すべきは、これが最初の即自への往復復元ではないことだ。「現場の言葉に戻ろう」という-retreat（後退）は即対自ではない。即対自は、対自で得た区別 — 失敗からlearned境界・検査実務・残余 — をすべて内部に抱えたうえで、もう一度作動する統一である。『精神現象学』の有名な表現を借りれば、失われた形相を保持しながら進む道（der Weg）である。保存を条件とする前進。ここに本節の全設計が入っている。

工学的に翻訳すると三段階はこうなる。①即自 = 未文書化だが機能している現場語彙。②対自 = 明示化・正規化による分節と、そこに必ず現れる矛盾（境界争い・数値の漂移・現場の不信）。③即対自 = 矛盾を抱えたままの新版、旧版の区別を消さずに抱えた改版。そして設計者が引き受けねばならないのは、②で矛盾が起きた瞬間に③へ進む**演算の設計**である。次節からその演算を分解する。

### 止揚（Aufheben）の三重意味 — 捨てる・保存する・高める

Aufheben はドイツ語で相反する複数の意味を同時に持つ（Aufhebung の三義性はヘーゲル研究の定番である）。日常語では「（law や契約を）取り消す・撤廃する」。同時に「（物を）保管する・とっておく」。さらに哲学語では「高めて保ちながら取り消す」。否定・保存・高度化 — 三つの動作が一つの動詞に溶けている。この構造は三段階構造そのものでもあり、以下のように分解できる。

| 止揚の局面 | 概念運動での意味 | 差分設計での実装要求 |
|---|---|---|
| 捨てる（negation） | 現行規定の作動停止 | `active=false`・`valid_to` の設定。現行クエリから見えなくする |
| 保存する（preservation） | 停止した規定の実在性の保持 | 削除禁止。履歴から参照可能。過去データは新版で再解釈しない |
| 高める（elevation） | より広い規定への接続 | 新旧を結ぶ明示関係（`retires` 等）＋新版が区別を引き継いでいること |

削除（DROP）は三局面のうち「捨てる」だけを実装した演算である。「保存する」も「高める」も起きない。止揚とは異なる演算が密かに実行されている — 本書の用語では**抹消（erase）**である。設計の退化はこの抹消の混入として必ず起きる。

ここで工場語彙の失敗例を一つ置く。2.1節の語彙正規化プロジェクトの話である。ある自動車部品工場がマスター語彙を作り、「治具」「冶具」「クランプ」を `HoldingFixture` 一個にマージした。SQL の `ALTER TABLE ... ADD COLUMN category` で、現場語彙の列を新しい列に上書きし、旧列を `DROP COLUMN` した。三か月後、保守計画システムが「クランプの点検周期超過」を返さなくなった。現場では「クランプ」は工具側の保持具を、「冶具」は刃具側を指しており、点検周期が異なっていたのだ。マージによって区別は失われ、区別にもとづいて書かれていた点検ルールは `WHERE category='HoldingFixture'` に吸収されて消えた。この変更には「捨てる」はあった。「保存する」がなかった — どの行がもともと「クランプ」だったかを指すものがシステムの内外のどこにも残っていなかった。止揚の三重意味が三つの列として残っていれば、この事故は防げた。

### 否定の否定 — 往復復元ではなく第二否定的前進

三段階を並べると「肯定→否定→否定の否定」と見える。だが否定の否定が単なる原状回復なら、ヘーゲルの弁証法は退屈な往復運動になる。『大論理学』の客観的 Essence の巻で論じられた通り、第二の否定は第一の否定の産物を内容として含む。すなわち「否定的なものの保持（Erhaltung des Negativen）」である。否定されたものは無にはならず、保持されたうえで次の規定の材料になる。この前進を**否定的なものの保持**（Preservation of the negative）と呼ぶ。

工場の語彙改版で読むとこうなる。第一次改版（対自）: 「治具」一個の語を否定して「治具/冶具/クランプ」に三分割する。第二次改版（否定の否定）: 現場の混乱を受け、実務の要求（トルク追跡のため全部をまとめて検たい）から、三分割を再び否定する。ここで原状回復なら「全部まとめて『治具』」に戻る — それは改版ではなく後退であり、実際同じ失敗を呼ぶ。第二否定的前進では、三分割で得た区別（境界の知識、現場が示した使い分け、残余として現れた検査実務）を**保持したまま**、より広い規定を作る。すなわち「上位概念 `HoldingDevice` を置き、`HoldingDevice` には下位の三分割を保存したままとる」設計である。語は統合されるが、区別は歴史として内部に残る。絞り込みクエリは上位で動き、点検周期は下位の区別から撃てる。

この読みには正直なアポリア（apory、難点）が付きまとう。三段進の進行を機械に要求することはできない。第三段階の内容は与えられた前提から導出可能ではなく、状況の解釈と実践の熟成が要る。したがって本書の実装には必ず**停止条件**が入る。段階3は自動生成されず、人間が承認するまで履歴付き上書きは保留される。止揚の構造を実装できる。止揚の内容の生成は実装できない。この区別（構造の形式化と内容の非形式化）は第5章の計算と判断の分断（→第5.1節）と同一の線上にある。

### 弁証法的進歩は「マージ」ではなく「履歴付き上書き」

ここで本節の設計判断を宣言する。分類の改版を止揚として実行するなら、その演算は Git のマージではなく、コミット（commit）である。なぜか。マージの語義は「二つの分岐を一つの節点に融合させる」ことで、融合した節点からは各親の姿が不可視になる。Git で merge commit は親を記録するが、ファイルの中身は混ざった現在値だけを残す。統合の意味が現在値に沈殿する。対してコミットは自己と差分を保存する — 上書き（overwrite）するが、抹消（erasure）しない。止揚の三重意味をそのまま写した構造である。

分類変更の四戦略を比較しておこう。

| 戦略 | 捨てる | 保存する | 高める | 現場での現れ |
|---|---|---|---|---|
| 破壊的上書き | ○ | × | × | `DROP COLUMN`、enum 値の書き換え、ラベルの貼替 |
| マージ（融合） | △ | △（節点に埋没） | × | 上位語への一本化。新旧どちらの意味で動いたか回答不能 |
| 履歴付き上書き | ○ | ○ | ○ | 新版を開き旧版を閉じ、`retires` で結ぶ |
| 分岐並存 | × | ○ | × | 語を併存させ続ける。境界争いが永久に未決着のまま残る |

四戦略のうち止揚の条件を満たすのは三行目だけである。分岐並存は「捨てる」を拒否した対自の凍結で、境界を永久に開いたまま運用コストに転嫁する設計（1.2節の境界の面化とは別物だ。面は計測されるが、未決着は計測されない）。破壊的上書きは抹消、マージは保存の欠如である。

マージが組織の対話の省略として現れることも記録しておこう。語彙統合会議で「どちらも正しいのだから一つにまとめよう」と決まった瞬間、矛盾の生産する運動が停止する。2.1節の正規化の暴力は、マージの形をとって最も無自覚に働く。ヘーゲル的に言えば、矛盾を調停で消した組織は、概念の運動を自分の手で止めたことになる。レポートの数値が説明できなくなる時、説明すべき運動がすでに無い。

### 差分設計の規範 — Aufheben-check を通らない変更は止揚を騙っている

では工学的に何をするのか。以上から導かれる仕様は短い。**改版は差分として記録される。差分には三局面が機械的に確認可能であること。** 確認できない改版は止揚を騙っているものとして差し戻す。この規範を本書では Aufheben-check と呼ぶ。チェックは四項である。

1. **否定の証明**: 変更後の状態から、旧規定が `active` でないことが確認できるか（作動停止の記録）。
2. **保存の証明**: 旧規定の定義と、旧規定でラベル付けされたデータが参照可能か（削除の不存在）。
3. **高度化の証明**: 新旧を結ぶ明示の関係（`retires` / `replaces`）が存在し、新版の定義が旧版の区別を引き継いでいるか。
4. **残余の記録**: どの区別・どの数拠が新版の意味に吸収されたかの記述。2.1節の残余を捨てるか保存するかの分岐で「保存」側を選ぶ仕組み。

この四項を検査する実行可能な差分チェックを以下に置く。2.5節のコミットモデルの先行実装であり、Turtle の `retires` 語彙は2.4節で正式定義する（依存環境は付録A）。

```python
"""ch02_s2_aufheben.py — 差分設計の規範 Aufheben-check の実装。
哲学的意図: 止揚（Aufheben）は三局面（捨てる・保存する・高める）が同時に
成立する演算である。うち一つでも欠けば、それは止揚ではなく抹消または
マージである。演算の名前を騙らせないために、規範を check 関数にする。
（コメントは哲学の注釈 — 本書の約束事）"""
from dataclasses import dataclass, field

@dataclass
class Term:
    key: str
    gloss: str
    active: bool = True
    valid_to: str | None = None

@dataclass
class Revision:
    """概念の一回の改版 = 履歴付き上書きのコミット。"""
    intent: str                      # 変更の意図（何の苦情・要求が動いたか）
    negates: list[str]               # 作動を停止する旧 term keys（否定）
    introduces: dict[str, str]       # 新 term key→gloss（新規定の開始）
    carries: list[str]               # 新版が引き継いだ区別の記述（保持の証明）
    absorbed_residuals: list[str]    # 新版に吸収された残余の記録（残余は捨てるな）
    data_ref: dict[str, str] = field(default_factory=dict)
    # 旧 term key → 旧データ集合の参照（保存の証明。DELETE しない宣言）
    retires: dict[str, str] = field(default_factory=dict)
    # 新 term key →  retire する旧 term key（高めるの接続）

@dataclass
class Vocab:
    terms: dict[str, Term] = field(default_factory=dict)

class NotAufhebungError(ValueError):
    pass

def aufheben(v: Vocab, rev: Revision) -> Vocab:
    # --- 局面1 捨てる: 否定は明示的でなければならない。暗黙の消滅を認めない ---
    for k in rev.negates:
        if k not in v.terms or not v.terms[k].active:
            raise NotAufhebungError(f"否定対象 {k} が現行に存在しない（抹消の混入）")
    # --- 局面2 保存する: 停止させるだけで消さない。旧データ参照が必須 ---
    for k in rev.negates:
        if k not in rev.data_ref:
            raise NotAufhebungError(f"{k} の旧データ参照がない = 保存のない改版")
        v.terms[k].active = False
        v.terms[k].valid_to = rev.intent  # 停止の理由は意図とともに記録する
    # --- 局面3 高める: 新旧を結ぶ関係なしは単なる置換、区別の引継ぎ記述なしはマージ ---
    for new, old in rev.retires.items():
        if old not in rev.negates:
            raise NotAufhebungError(f"{new} が否定していない {old} を retire（接続の捏造）")
    if not rev.carries:
        raise NotAufhebungError("carries が空 = 否定的なものの保持がない（対自の遺棄）")
    if not rev.absorbed_residuals:
        raise NotAufhebungError("absorbed_residuals が空 = 残余の記録なし（2.1節の暴力の隠蔽）")
    for k, gloss in rev.introduces.items():
        v.terms[k] = Term(key=k, gloss=gloss)
    return v

def query_history(v: Vocab, key: str, as_of: str) -> str:
    # 哲学的意図: 止揚されたものは「実在しなくなった」のではない。
    # 過去への問いは歴史から答える（保存の工学的意味）。
    t = v.terms.get(key)
    return f"{key}: {t.gloss} (active={t.active})" if t else "unknown term"

if __name__ == "__main__":
    v = Vocab(terms={
        "治具": Term("治具", "型・刃具・ワークを保持するもの（現場語彙、未分化）"),
    })
    # 第一次改版: 対自。一つを否定し三つに区別する。
    v = aufheben(v, Revision(
        intent="正規化プロジェクト: 保守周期の違いを区別したい",
        negates=["治具"], introduces={"クランプ": "工具側の保持具",
                                      "冶具": "刃具側の保持具"},
        carries(["現場の『治具』が実は二系統の周期を持っていた事実"]),
        absorbed_residuals=["現場で『型』と呼ばれていた語"],
        data_ref={"治具": "snapshot://fixture-v0.parquet"},
        retires={"クランプ": "治具", "冶具": "治具"},
    ))
    print("改版1（対自）:", {k: t.active for k, t in v.terms.items()})
    print("歴史への問い:", query_history(v, "治具", "改版1後"))
    # 第二次改版: 否定の否定。三分割を再び否定するが、区別を保持して上位へ上げる。
    v = aufheben(v, Revision(

        negates=["クランプ", "冶具"],
```

上のコードには意図的な破綻がある: `Revision` の第二改版で `HoldingDevice2` が `negates` 之外の項を retire しようとしていないか — 読者は `aufheben()` に一度 `NotAufhebungError` を出させてみればいい。規範は例外として機能するときに初めて規範になる。

規範の運用では、チェック通過だけでは不十分で**沈黙の猶予期間**が必要になる。破壊的な改版（上位概念の導入・語の統合）は、Approved になっても即座には active にならない — 現場が反論する窓を開いたまま作動を遅延させる。猶予期間の設計、すなわち「承認された変更がすぐには存在しなくなる」時刻設計は2.6節の版管理の倫理に譲る。ただし原則はこの節で立つ。変更の発効は対話の終了を待ってよい。

最後に、この規範をどの層で執行するかの方針だけ述べておく。Aufheben-check を文書運用（チェックリスト文化）に置くと、それは必ず形骸化する。本節の実装のように**書き込み経路の関数**に置けば、規範を通らない改版は存在しないのと同じになる。執行の一般形（ポリシーゲート）は6.4節で OPA と Rego として実装する。そこに移管するための正規形として、改版コミットは JSON で書き出せる形に保つ。

```yaml
# revision.json の例 — Aufheben-check の通過証明を改版の付属物として保存する。

revision:

  negates: ["クランプ", "冶具"]

  carries: ["周期区別を sub_type へ引き継ぐ"]
  absorbed_residuals: ["現場の『ホルダー』"]
  data_ref:
    "クランプ": "snapshot://clamp-v1"
    "冶具": "snapshot://jig-v1"
  retires:
    "HoldingDevice": ["クランプ", "冶具"]
  aufheben_check:

    preservation_proved: true
```

### アポリア — 保存されるのは意味か、記述か

本節の設計規範には解けない難点が Attached している。Aufheben-check は「保存する」を検査できるが、保存されるのは記述（definition・データ参照・引継ぎ文）であって、意味そのものではない。2.1節で見たように、正規化の過程で摩耗した意味 — 語を語っていた身体と状況 — は履歴のどこにも載らない。履歴付き上書きは意味を保存する装置ではなく、意味を復元する**機会**を保存する装置にとどまる。機会が誰にも読み返されなければ、保存は機能したことになるのか。これは終章の知の継承というアポリア（→終章）の最初の断面である。設計はアポリアを消せない。アポリアを運用条件として書き込むことだけができる。上記の `carries` と `absorbed_residuals` は、その書き込みの試みである。次節では、この「改版をコミットとして保存する」考えを、スティグレールの外部記憶論（→第2.3節）に接続して基礎づける。

### 実行練習

1. `python ch02_s2_aufheben.py` を実行し、改版1（対自）と改版2（即対自）の後の `active` 表示を読み比べよ。次に改版2の `retires` を `{"HoldingDevice": ["クランプ", "冶具"]}` と統一して正常通過させ、そのうえで `carries` を空列表に書き換えて `NotAufhebungError` が発火するを観察せよ。「高める」なしに「捨てる」と「保存する」だけでは、どの戦略（四戦略表のどれ）になるかを書き残すこと。
2. `query_history()` を拡張し、旧 term（例「治具」）にラベル付けされたレコードの集合が改版後の絞り込みクエリで**見えてしまう**か見えないかを確かめる関数を追加せよ。実装は任意（list でも dict でもよい）。2.1節の工場失敗例（保守計画が「クランプ」を返さなくなった事故）を再現する側に立ち、`active=false` の扱いの設計がなぜ「見えないが参照できる」でなければならないかを10行以内で説明せよ。
3. 自分が所属する組織で最近起きた分類変更（API の enum 削除、職能名の変更、タグの統合など）を1件選び、それを `Revision` に書き起こして Aufheben-check を通せ。通らないならどの局面が欠けているかを特定し、その変更が「破壊的上書き」「マージ」「分岐並存」のどれだったかを判定して、失われた `carries` に相当する区別が何だったかを復元試着こうとすること。復元できなければ、その欠落こそがこの節のアポリアの現場名簿である。

## 2.3 スティグレール — 第三次保持と記憶の外部化

2.1で分類の暴力を、2.2でその暴力を履歴として引き受ける演算（止揚）を見た。しかし暴力を引き受けるには、失われたものが「どこかに残っている」だけでは足りない。失われたものが、いまここにある認知そのものを組み替えていることを理解しなければならない。ベルナール・スティグレール（Bernard Stiegler）の記憶論は、その組み替えの理論である。彼の中心的な主張——技術的記憶（第三次保持）は、生物の記憶の外にあるのではなく、生物の記憶の内部に最初から入り込んでいる——は、オントロジーを「データベース」ではなく「記憶の臓器」として設計せよという、この本全体の中で最も急進的な設計命令に転化する。急進的であるが、実行可能である。この節の終わりには、あなたのオントロジーが既に人間の記憶を書き換えていることを示すクエリが手元にある。

### 三つの保持 — フッサールからスティグレールへ

スティグレールの道具立てはフッサールの時間意識の分析から始まる。音の例で理解するのが最速である。メロディを聴いているとき、いま鳴った音は既に消えているのに、私たちはメロディとして聴いている。消えた音が保持（retention）され、次の音が予持（protention）されているからである。スティグレールはこの時間構造に三層の区別を入れる。

**第一次保持（primary retention）**：いまの知覚そのものに内在する保持。消えゆく音が保持として耳に残っている層。誰も外部化できない。録音しても、録音されたのは第一次保持ではなく、第一次保持が去った後の代物である。

**第二次保持（secondary retention）**：回想・想起。第一次保持が沈殿し、回憶として呼び出せるようになった層。個人の記憶。ここまでは古典的な記憶論の領域である。

**第三次保持（tertiary retention）**：技術的保持。書物、録音、写真、データベース、そしてオントロジー。過去を物質媒体に外部化し、生物の記憶の寿命を超えて保存する層。

重要な点は、三層が「内→外」と整然と並ぶのではなく、**循環している**ことである。スティグレールはプラトン『パイドロス』の文字批判を引用してこれを示す。エジプトの神トートは文字を発明し、ファラオはそれを「記憶の薬（pharmakon）」として拒絶する。薬は毒でもある。文字が外部化された記憶は、想起の筋道を外部に依存させ、内部の想起力を痩せさせる。記憶を「強くする」技術が、記憶の在り処を人間から技術へ移す——スティグレールはこれを**弁証法的外部化（dialectical externalization）**と呼ぶ。外部化された記憶は、外にあるまま、内を再編成する。

第一次保持に第三次保持が先行している、というスティグレールの逆転も重要である。私たちは聴く前にすでに、聴き方を学んだ音楽の記録（第三次保持）を通じて聴いている。子どもが母語を「内側から」獲得できるように見えるのは、外部化された音と文法の系（第三者が記録し蓄積した系）が先に開かれていたからだ。記憶の外側は、記憶の内側の条件である。この逆転を認めるなら、オントロジーを「システムの部品」扱いする設計観は破綻する。オントロジーは、そのオントロジーを使う認知の条件である。

### オントロジーは第三次保持の工業化である

本書の定義をここで確定する。**オントロジーとは、第三次保持の工業化である。** 工業化という言葉には二重の意味を込めた。第一に量的拡大——書物が印刷されたように、記憶の外部化が複製・検索・照合の機械によって大規模化される。第二に工業固有の性格——分業、標準化、そして労働の知識への無自覚化である。

比較の表を作っておこう。個人レベルの第三次保持と、工業化された第三次保持の違いは、正確にそのまま設計要求の違いになる。

| 次元 | 個人の第三次保持（メモ・日記） | 工業化された第三次保持（オントロジー） | 生じる設計問題 |
|---|---|---|---|
| 書き手＝読み手 | 同一。意味のすり替えが起きにくい | 分離。他人（や機械）が読む | 意味の保証主体の所在（→2.6） |
| 標準 | 個別語彙で許される | 共有語彙を要求される | 分節化の暴力（→2.1） |
| 検索 | 脈略的手がかりで到達 | クエリで到達 | 語彙外の意味は到達不能化 |
| 改竄・劣化 | 自分による自然な再解釈 | 自分によらない変更・減耗 | 版管理と履歴（→2.4・2.5） |
| 忘却 | 自然な忘却が意味を浄化する | 忘却が発生しない＝消えない | 保存の過剰による硬直 |

最終行に注目してほしい。工業化された記憶は忘却しない。忘却しない記憶は、世界が変わっても昔の分類で世界を切り続ける。分類の硬直は、分類の暴力が時間軸で発火した形である。ゆえに第三次保持の工業化は、忘却の装置——削除ではなく退位させる装置（`deprecated`、→2.4）——を同格に設計しなければならない。忘却を設計できない記憶は、過去による統治を機械化する。

### 保持の工業化が認知を書き込む — 現場での観察可能な効果

スティグレールの理論を「深い話」で終わらせないために、グラフで観測可能な予測に変換する。第三次保持が第二次保持を書き込む最も実直な経路は、**記録が証言を汚染する**ことである。現場技術者の障害時の証言が、障害後に書かれた記録の語彙で語られるようになる——「あれは『ドリフト』と呼ばれていた件だよね」という呼びかけが、当事者の記憶そのものを『ドリフト』の枠組みへ寄せる。

これは測定できる。ある語彙（例: `Drift` ラベル）がグラフに導入される前後で、同じ作業者の障害説明の語彙分布が収束していくなら、第三次保持→第二次保持の書き込みが起きた証拠になる。

```cypher
// 「語彙の植民」クエリ: Drift ラベル導入前(3/1)と導入後(6/1)の
// 障害説明(IncidentNote)に現れた語彙の多様度を比較する。
// 多様度の低下＝説明が外部記憶の語彙に収束しつつある＝保持が認知を書き込んでいる印。
UNWIND ['2026-03-01', '2026-06-01'] AS cutoff
MATCH (n:IncidentNote)
WHERE n.recorded_at < datetime(cutoff + 'T00:00:00Z')
  AND n.author_id = 'P-114'
WITH cutoff, collect(DISTINCT n.phrase) AS phrases, count(n) AS notes
RETURN cutoff,
       size(phrases) AS distinct_phrases,          // 語彙の豊かさ
       toFloat(size(phrases)) / notes AS diversity // ノートあたりの語彙多様度
ORDER BY cutoff;
```

`distinct_phrases` が有意に落ちるなら、その作業者の説明世界はグラフの語彙に入植されている。このクエリは告発のためではなく、**語彙の導入が記憶の再編成であることを可視化するため**のものである。新語彙を本番オントロジーに入れる前に、語彙が何を統一し何を消すかを預告する装置として使う（→2.6の沈黙の猶予期間はこの預告の実務形である）。

### 既定の保持 — 記憶の標準化が設計されている事実

スティグレール後半期の中心概念に「既定の保持（retention by default）」がある。何を憶え、何を忘れるかが、索引・ランキング・フィードによって、個人の外で先取りされている、という分析である。検索エンジンは「あなたがこの過去に出会う経路」を既定として用意し、その既定が共有記憶の形を造る。

 industrial化されたオントロジーも同じ機能を持つ——否、持つ**ほかない**。`Context` や `Situation` のスナップショットクエリ（→1.5）が「場について何を先に目にするか」を返すとき、その返り順と選択が既定の保持そのものである。設計者は既定の保持を、自覚的に設計するか、無自覚に既定されるかをえり選ぶだけである。

```python
# default_retention_audit.py — 「どの保持が既定として作動しているか」の監査
# 目的: オントロジーの上位表示・既定視される節点が、
#       (1) 人間に再検証されていない、(2) 少数の書き手に偏っている、
#       という二つの腐敗条件を測る。
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "pass"))

AUDIT = """
MATCH (n)-[w:WITNESSED_BY]->(v:ViewerSession)
WHERE v.viewed_at > datetime() - duration('P30D')
WITH n, count(v) as views, n.created_at AS born,
     max(CASE WHEN n.last_reverified_at IS NOT NULL
              AND n.last_reverified_at > n.created_at THEN 1 ELSE 0 END) AS rechecked
OPTIONAL MATCH (n)<-[e:AUTHORED]-(a:Author)
WITH n, views, born, rechecked, count(DISTINCT a) AS author_count
WITH collect({id: n.uri, views: views,
              unverified: (rechecked = 0), single_author: (author_count <= 1)}) AS rows
UNWIND rows AS r
RETURN r.unverified AND r.single_author AS corrupt, count(*) AS n_nodes
ORDER BY corrupt DESC;
"""
# 「30日間に多数回閲覧された（＝既定の保持として作動している）」節点のうち、
# 人間による再検証が一度もなく、単独の書き手に依存するものの数を報告する。
# 既定の保持の腐敗——標準化された忘却の中心に、無検証の単独証言がある状態——は、
# 記憶インフラの炎症所見である。
```

この監査の設計思想を述べておく。再検証（`reverified`）の概念がなければ、オントロジーは「記録された瞬間に永遠の真実へ硬化する」物質になる。第三次保持の工業化には、第二次保持の循環——人間が憶え直し、書き直し、時に抛棄する循環——が接続されていなければならない。記録と想起の循環が切れた工業記憶は、スティグレールの語でいえば毒（毒としての薬）が薬の顔を続けている状態である。

### 薬の判断 — 保持を絶つ設計

では、循環を接続する設計原則を三つ確定する。**第一に来歴（provenance）原則**：すべての第三次保持節点は、誰が・いつ・どの観測や発話から作ったかを辺として持つ（1.5節の `origin`・`AUTHORED` はその布石である）。来歴のない保持は、誰にも返答を要求できない幽霊である。**第二に再検証期限原則**：既定の保持として作動する節点には、保持寿命を設定し、期限を過ぎたら「再検証待ち」の格に落とす。保持の忘却（→上の表）の実装である。**第三に可読な矛盾の保存原則**：矛盾する保持は統合してはいけない。統合は暴力の隠蔽であり、矛盾を並存させたまま提示することが、ハーバーマス的に言えば妥当性要求の空間を開く（→6.2）。`equivalentClass` を自動適用しない 2.4節の规則は、この原則の帰結である。

最後に、スティグレールが『技術と時間』で繰り返す逆説を、設計の言葉に翻訳して置いておく。**記憶を保存する技術は、記憶を保存する能力を人間から取り除く方向に働く。だから記憶インフラの設計とは、人間の想起能力を増幅する配管を、記憶の本体の周りに故意に這わせる設計にほかならない。** この配管の最終形が第8章の対話UIプロトコルであり、その節に至るまで、本章の差分トラッキング（次節）と沈黙の猶予期間（→2.6）は、増幅配管の仮設として機能する。

### 第三次保持の実地判定 — 「あなたの記憶はどちらに属するか」の問診表

スティグレールの第三次保持（→前掲：記憶の技術的_third retention——録画・台帳・検索が「私の」記憶の一部を担う状態）を、設計レビューで使える問診表に落とす。第三次保持自体は悪でも善でもない（→8.1 の技術の二面性）——問題は、それが**第二次保持（自分の記憶）と第一次保持（現在の経験）を育成しているか、代替しているか**である。判定の三問を置く。

**問一（入口）**：その第三次保持（台帳・検索・AI 要約）の内容は、いつ・誰の第一次保持（経験）から inscription されたか。 Inscription 者が不在で、 inscription 時刻が登記されていない台帳は、記憶の主体が空白の台帳である（→5.1 の JudgmentEvent の accountable_to 欠如の記憶版——主体の空白は、更新経路の空白に直結する）。**問二（使用中）**：使う人は、台帳の条目を**手がかりとして自分の記憶を再生**しているか、条目を**読み上げて終わりに**しているか。再生には回想法が要る（→8.5 の理由面板——read ではなく再生への招待）。読み上げの運用（台帳の文をそのまま実行に移す）が検出される場所では、第二次保持が休職している（→8.1 deskilling-meter の site_coinations 逓減の入口事件）。**問三（更新）**：条目を更新できる人は、その条目の**使用経験を持つ人**か。経験なき更新（運用の現場を知らない者が台帳を書く）は、記憶の寄生である——台帳が記憶の主体から離れ、主体が台帳に寄生する（third retention の逆転）。

```cypher
// third-retention-audit — 第三次保持の問診(月次)
MATCH (e:EpistemicEntry) WHERE e.usage_count > 0 AND e.at < datetime() - duration('P18M')
// 問一: inscription 主体と時刻の登記
OPTIONAL MATCH (e)-[:INSSCRIBED_BY]->(p:Person)
// 問三: 直近の更新者が使用経験(その条目が参照するスレッドへの参加)を持つか
OPTIONAL MATCH (e)-[:UPDATED_BY]->(u:Person)
OPTIONAL MATCH (u)-[:PARTICIPATED_IN]->(:Thread)-[:REFERS]->(e)
RETURN e.entry_id,
       CASE WHEN p IS NULL THEN 'Q1:主体空白' ELSE 'Q1:ok' END AS q1,
       CASE WHEN u IS NULL OR uIsParticipant IS NULL THEN 'Q3:経験なき更新' ELSE 'Q3:ok' END AS q3;
```

（`uIsParticipant` の所在判定は上記 OPTIONAL MATCH の成否で代用できる——正確な実装は練習1に委ね、本書では照会の**意図**を明記する：第三次保持の条目が「誰の記憶から来て、誰の経験で更新されているか」の二列を、すべてのナレッジベースが常に持てるようにする。**主体の二列を持たない KB は、記憶の外注であって記憶の代理ではない**——この区別が 8.1 の診断の運用形である。）

この問診を 2.5 の git→RDF ブリッジと接続して閉じる。コミット履歴は本来、 inscription の主体と時刻の最良の簿記である（Author/Committer/時刻が機械的に残る）——ブリッジが Author を EpistemicEntry の INSSCRIBED_BY に写るとき（→2.5 のブリッジ設計の含意）、git は第三次保持の問診表を無料で提供する。ただしコミット authorship と inscription の主体は一致しないことがある（コードを書いた者と、知識を選んだ者は違う——→2.4 の分類制定の級）。よってブリッジは author を**候補**として載せ、Co-Authored-By トレーラーと審議記録で主体を確定する（主体の簿記は機械の記録と人間の承認の共同作業である——5章の人間側の設計が、記憶の簿記で先に現れる）。

### 簿記されていない保持 — 「書かなかった」を台帳に載せる

第三保持の台帳（→前掲）は書かれたものだけ数える。しかし組織の記憶を本当に削るのは、書かれなかった決断・開かれなかった会議・配られなかった情報である。**簿記されていない保持の台帳**を一度だけ開く（永久に開くのではない——沈黙の全量台帳は不可能なので、**サンプル審計**で十分だ。→2.5 の簿記の伦理は「すべてを書け」ではなく「書かない选択を書け」である）。

```cypher
// silence-audit — 決着したのにDecision/RuleAdoptionを持たない討議 thread の抜き取り検査
MATCH (t:Thread {resolved:true}) WHERE t.closed_at > datetime() - duration('P1Q')
  AND NOT (t)-[:PRODUCED]->(:Decision) AND NOT (t)-[:PRODUCED]->(:RuleAdoption)
  AND size([(t)<-[:PARTICIPATED_IN]-(:Person)]) >= 3
RETURN t.thread_id, t.closed_at, count { (t)<-[:PARTICIPATED_IN]-(:Person) } AS heads
ORDER BY heads DESC LIMIT 10;   // 3人以上で決着したのに決着産物がない=書かれなかった決断の候補
```

この抜き取り検査で名前の挙がる thread の参加者に、審計は「なぜ書かなかったか」を質問する（3 人以上の決着が産物なしで閉じる場合、ほぼ必ず「書く人が決まっていなかった」か「書く价値がないと思われた」のどちらかで、**前者は席の欠落、後者は評价の欠落**——2.1 の「書く人が決まっている」が第三保持の物質条件である理由がここで逆側から立証される）。抜き取り結果是四半期に 1 度、第三保持台帳の蓋に貼る（書かれなかったものの件数——記憶の台帳が記憶できないものの件数、この二列が并んでいる台帳だけが誠実な記憶の健康诊断である）。

### 実行練習

1. 上の「語彙の植民」クエリを、自分のプロジェクトの用語導入時期で走らせよ。データが足りないなら、会議メモの日付順に新語彙の初出と旧語彙の消滅を manually にでも追跡せよ。「導入6か月後に現場から消えた語」のリストは、分類の暴力の目録である。
2. `default_retention_audit.py` の閾値（30日・閲覧数）を2段階に変えて、既定の保持の「圏境」がどう動くか見よ。圏境に入る節点数が倍増する条件は何か、語彙の粒度と関係があるか、考察せよ。
3. あなたのチームの用語集を1つ選び、その語が「再検証されていない単独証言」であることを上の監査が検出できるように、`AUTHORED` と `last_reverified_at` を逆算して埋めてみよ。その上で、その語を実際に再検証した会議を開き、`last_reverified_at` を更新せよ。更新の瞬間、あなたは第三次保持の循環に一単位分の電気を通したことになる。

## 2.4 分類工学 — OWL 2 / RDF スキーマの実装

2.1から2.3まで、分類は暴力的であり、暴力は履歴を要求し、外部化された記憶は認知を書き込む、と説かれてきた。読者がこの三つを「もっともだ」と感じたとしたら、その感じ方自体が既に第二次保持の働きである（→2.3）。では設計者として手を動かせばよいか。この節から本章は実装節に入る。扱う技術は RDF と OWL 2 である。ただし本書の目的は W3C 仕様の紹介ではない。目的は一つ——**分節化の暴力を、仕様として機械に強制できる形に置くこと**——に尽きる。OWL の制約は「世界がこうなっていることを保証する」ものではなく、「世界をこう切り分ける私達の合意が壊れたことを検出する」装置である。この読み方を throughout 忘れないこと。

### TBox と ABox — 切り分けの宣言と、切り分けられたもの

RDF の基本単位は triples（項）である。`(主語, 述語, 目的語)` の三つ組で世界を記述し、主語には URI を使う。URI は名前空間で一意になる——`https://execphil.example/onto#Drift` のように。名前空間の分割は組織分割の写像であり、ここにもう分節化の暴力は始まっている（境界コンテキストの問題、→6.1）。

OWL 2 では記述を二層に分ける。**TBox（terminological box）**は語彙の層——クラス、プロパティ、およびそれらの制約。「Drift は Fault の部分類である」のような、型についての主張。**ABox（assertional box）**は事実の層——`pump-0301` という個体が Drift を起こした、のような主張。1.5節のグラフで言えば、ラベル定義が TBox、ノードが ABox に対応する。しかしグラフと決定的に違うのは、OWL には**推論機（reasoner）**が付くことだ。OWL の TBox は記述ではなく演算である。Hermit や ELK、openllet などの reasoner は、TBox と ABox から「暗黙に真である主張」を導出する。1.1節の語りの限界と対比されたい。OWL の推論は、ポランニー的暗黙知の完全な対極にある——**形式化された知の内部で、明示されていなかった帰結を明示化する**操作だからだ。暴力の語彙で言えば、reasoner は分類が含意する暴力を、分類者が気づく前に執行する。

この二重性（合意の検出装置であり、含意の執行装置でもある）を制御することが、分類工学の本体である。

### 最小構成の TBox — Turtle で書く保全オントロジー

第1章の保全現場の語彙を Turtle 形式で定義する。コメントが哲学の注釈になっていることに注意（スタイル約束、→OUTLINE）。

```turtle
@prefix :  <https://execphil.example/onto#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# --- クラスの分節：切断(cutting)の記録 ---
# 「故障」「逸脱」「劣化」は日常語では重なる。切断して disjoint にすることは、
# 重なりを公式に放棄する宣言である。放棄は 2.1 の暴力だが、
# 明示された放棄は監査可能な暴力である。
:Fault a owl:Class .
:Drift a owl:Class .
:Degradation a owl:Class .

:Drift rdfs:subClassOf :Fault .
# 逸脱は故障の部分類——「故障したが機能している」状態を Drift で受け止める切断。
# 現場では「故障」が停止を意味するため、停止していない異常が
# どの語でも呼べず記録から消える。Drift はその消滅を回収する切断である。

owl:allDisjointClasses (:Fault :Degradation) .
# 注: 正確には owl:AllDisjointClasses の無名個体構文を使う(下記 §実行 で展開)。
# 逸脱は劣化と同一化しない。劣化は方向のある統計過程、逸脱は事象である。
# この切断を忘れると「劣化トレンドの閾値超え＝故障」という静かな同一化が
# ダッシュボードで実行される。

# --- プロパティの切断: domain/range は存在論的塀 ---
:observedOn a owl:ObjectProperty ;
  rdfs:domain :Observation ;
  rdfs:range  :PhysicalAsset .
# domain/range を書かないプロパティは、どんな主語にも目的語にも繋がれる。
# 繋がれること自体が意味の汚染である。塀は暴力だが、開きっぱなしの境界は暴力より悪い。

:hasSeverity a owl:DatatypeProperty ;
  rdfs:domain :Fault ;
  rdfs:range  [ a rdfs:Datatype ;
                owl:oneOf ( "minor"^^xsd:string "major"^^xsd:string "critical"^^xsd:string ) ] .
# 列挙値は分節の最終形態。three値より多い値を現場が使うなら、
# 列挙値は現場の意味を減らす。減らすと決めたなら、減らし方を版数で記録する(→2.5)。

# --- カーディナリティ: 無関係の強制 ---
:Fault rdfs:subClassOf [
  a owl:Restriction ;
  owl:onProperty :observedOn ;
  owl:someValuesFrom :PhysicalAsset ] .
# 「故障は必ず何かの資産の故障である」。存在しない資産の故障は記述を許さない。
# someValuesFrom(存在)でなく allValuesFrom(全称)にしないのは、
# 故障の意味が単一資産に閉じない場合(連鎖障害)を開いておくため。

:Fault rdfs:subClassOf [
  a owl:Restriction ;
  owl:onProperty :observedOn ;
  owl:maxCardinality "3"^^xsd:nonNegativeInteger ] .
# 記録の爆発を防ぐ上限。哲学: 無限の根拠付けは根拠付けではない。
# 上限を設けたことは 2.6 の承認対象になる(任意の定数に権力を埋め込まない)。
```

### 制約の執行 — reasoner を「分類の憲法裁判所」として動かす

TBox だけでは宣言は執行されない。PyPI の `owlready2` を使い、矛盾を検出する実行可能コードとして置く。ここでの運用原則は一つ——**本番グラフへの書き込み前段で reasoner を走らせ、矛盾（unsatisfiable class）を検出したら書き込みを止める**。2.1の暴力論と矛盾しないために重要なのは、reasoner が矛盾「を消す」のではなく矛盾「を報告する」動きをさせ、統合判断を人間に残すことである（→4.4の契約、→6.4のゲートキーパー）。

```python
# tbox_gate.py — OWL reasoner による TBox 矛盾検出（書き込み前ゲート）
# 哲学: reasoner に「正しさ」を判定させるのではない。
# 「この切り分け方は自身と衝突する」という自己矛盾のみを機械に要求する。
# 自己無矛盾性は、意味の保証ではなく、意味の最小限の誠実さである(→4.1)。
from owlready2 import get_ontology, InconsistentOntologyError, default_world
import os

onto = get_ontology("file://onto/maintenance.owl")  # Turtle で書いた TBox
onto.load(path="onto/maintenance.owl", format="rdf/xml")

# ABox 増分を臨時 graph で載せて検証する（本図に触れない）。
# 哲学: 増分の検証は、世界を書き換える前の思考実験でなければならない。
# 思考実験の失敗は世界を汚さない。汚す設計は、検証を世界の実行と呼ぶ。
def validate_increment(ttl_path: str) -> list[str]:
    inc = get_ontology("http://execphil.example/increment#")
    inc.load(path=ttl_path, format="turtle")
    # 一時的に本体へ統合し、矛盾クラスを列挙して即座に分離する
    with onto:
        onto.imported_ontologies.append(inc)
        conflicts = []
        for c in onto.classes():
            try:
                # 不充足（unsatisfiable）なクラス＝その定義が自身と衝突
                if c in onto.inconsistent_classes() if hasattr(onto, "inconsistent_classes") else False:
                    conflicts.append(c.name)
            except Exception:
                pass
        onto.imported_ontologies.remove(inc)
    return conflicts

if __name__ == "__main__":
    print(validate_increment("onto/increment_2026-11.ttl"))
```

（注：`inconsistent_classes()` の取得は reasoner 設定に依存するため、実装では Hermit を明示起動して `classifyReasoners` を使う形に差し替えてよい。骨格——増分を臨時 world で classify し、本図に触れず矛盾名のみを得る——が本質であり、これは git の pre-commit hook と同型の構造である。）

### 現場語彙の管理 — owl:sameAs を使わない理由

2.1の「現場用語の正規化」問題に、OWL の道具で答える。現場が「ぶるぶる」「異音」「振れ上がり」と呼ぶものを正規語彙 `:VibrationAnomaly` に対応付けるとき、最も安易な道具は `owl:sameAs` である。**使ってはならない。** `sameAs` は論理同一であり、語彙 A のすべての述語が語彙 B に移り、矛盾が統合で消える。暴力が履歴ごと消える。これが 2.2 の Aufheben 読解の直接の帰結である——否定（区別の保持）を含まない同一化は、止揚ではなく抹消である。

```turtle
# 正しい管理: 同一ではなく「対応」を、対応は語彙の跨ぎとして記録する。
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .

:vib-term-buruburu a skos:Concept ;
  skos:prefLabel "ぶるぶる"@ja ;
  skos:broader :shopfloor-lexicon ;
  skos:closeMatch :VibrationAnomaly .
# skos:closeMatch(近似)を使う。exactMatch は「完全対応」の主張であり、
# 主張なら版数と承認を要する(→2.6)。exactMatch に格上げすることは
# 二つの語の境界を公式に消す行為であり、変更履歴に残る。

# 語彙間の写像は語彙の内部事象ではなく語彙間の出来事である。
# ゆえに写像は両方の語彙の外部——対応テーブル——に置く。
# 内側の語彙を改造して外側に合わせることは防腐層の裏切りである(→6.1)。
```

`skos:inScheme` と `skos:ConceptScheme` で現場語彙・正規語彙を別スキーマに分離し、マッピングは `s2z_mapping` という第三の名前空間に集約する。マッピングの総数を指標化すると、組織の翻訳コストが見えるようになる（翻訳コストの見積もりは、防腐層の予算計上そのものである——→6.3の round-trip check と接続）。

### 削除しない — deprecated と retires による退位

分類工学の最終規則：**語彙を削除しない。退位させる。** 削除すると、ABox の既存事実が宙に浮く（参照されていたクラスが消え、reasoner が事実全体を読めなくなる）。また 2.5 の履歴追跡が、削除された用語への参照を復元できなくなる。

```turtle
:OldFaultClass a owl:Class ;
  owl:deprecated true ;
  :retiresWith { "retired_at": "2026-11-01", "replaced_by": "onto:Drift" } ;
  rdfs:comment """2026-10-31 承認委員会により退位。
    退位理由は「故障と劣化の切断が運用で機能しなくなったため」。
    この注釈自体が 2.6 の沈黙の猶予期間の記録である。""" .
# owl:deprecated は OWL 標準。retires の詳細は語彙側で定義する(標準語彙に依存しない)。
# 退位語彙は reasoner が推論から除外する。しかし ABox と履歴は読める。
# 消された分類は読めなくなるが、退位した分類は読める。
# この二つの差が、組織の知識の不可逆性の扱いを決める(→2.5)。
```

退位語彙が参照され続けている現象（deprecated なのに現役）は、腐敗の指標である。`grep` で ABox を走査し、退位語彙の残存参照を報告するスクリプトは trivial だが、組織に毎回読ませる価値がある——読ませる行為が、分類権限の透明性を保つ唯一の実務だからだ（→2.6）。

### 実行 — docker で OWL 検証環境を一分で起動する

```bash
# 検証環境の起動（付録A の docker-compose とも共通）
docker run -d --name execphil-owl \
  -p 5150:5150 -p 3030:3030 \
  atomgraph/fuseki:latest

# Jena で TBox+ABox を parse し、矛盾を CLI で確認する
docker exec execphil-owl sh -c \
  "apache-jena-4.10.0/bin/tortoise /tmp/maintenance.ttl"  # 構文+OWL Lite 検証
docker exec execphil-owl sh -c \
  "apache-jena-4.10.0/bin/infer -q /tmp/reasoned.ttl /tmp/rules.ttl"
# ABox を reasoned.ttl に読ませ、reasoner が導出した「明示されていなかった主張」を diff する。
# 明示主張と派生主張の差分が、この TBox の暗黙知である。
```

最後のコメントが本章の OWL 観を言い当てている。**オントロジーの「暗黙知」＝明示主張から reasoner が導出する主張の集合**。OWL の暗黙知は、人間に不可知な暗黙知とは別物で、原理的に可視化できる。この対比を完全な形にするのが次節の Git 的差分——明示・派生・退位・削除のすべてを履歴として結ぶ試みである。

### TBox 差分審議のチェックリスト — 五行の回復

TBox の版本管理（→前掲）の審議で、差分レビュー者が五行だけ回復する様式を置く（重たい審議書ではなく五行が回復される——6.3 の条約審議の書式と同一の思想）。

| 行 | 質問 | fail させない場合 |
|---|---|---|
| 1 | この追加は**区別の创設**か区別の**消去**か(→6.3 roundtrip) | 创設のみ:L1 通过可、消去:L2 強制 |
| 2 | 消す語の**実例引用数**(过去 2 四半期の辺) | 引用 0 なら消せる、>0 なら落日周期必須 |
| 3 | 亲語との**包摂**が site 使用実態とずれていないか(site TBox 突合) | ずれ=条約贸易議題に回す |
| 4 | 変更の**級**(2.6 の級表で L?)(署名者数の預告) | 級未宣言は diff 自体が L2 違反 |
| 5 | この変更で**壊れる CQ/test**(→4.2・4.6 の依頼) | 破坏清単が空=依頼計測が壊れている |

第 5 行の「破坏清単が空=計測が壊れている」が審議の質量を保証する——TBox 変更と CQ/test の依頼辺（`TESTED_BY`、→4.6 三層の TBox 版）が自動生成されていなければ、空は安全ではなく盲点である（→2.5 のブリッジが commit 時に依頼図を更新する設計の理由）。五行審議の回復そのものが Commit の message に残る（→2.5 の由来簿記——審議の資格も歴史を持つ、→2.6 級の署名と同一の簿記）。

## 2.5 脱知識化の追跡 — Git的コミットツリー

2.4で、語彙は削除せず退位させ、マッピングは抹消せず記録する、と決めた。しかし「退位」や「記録」は状態であり、状態だけでは暴力の歴史は復元できない。必要なのは**変更そのものの履歴**である。分類がどの順で、誰によって、どの意図で書き換えられ、そのとき何が失われたか——この連鎖をデータとして保持する構造が、本章のいう Git 的コミットツリーである。名前の由来は明白で、ソースコード管理システム git が実践している「変更の不可逆的追跡」を、RDF の語彙そのものに移築するからである。ただし git そのものをオントロジー管理に使うのではない（後述の理由で、それは半分正しく半分間違っている）。正しいのは、git の**代数**——コミットが親を持ち、変更が差分で表現され、履歴がマージできる——を RDF データとして再発明し、グラフの上に載せることだ。脱知識化（déqualification、熟練の剥奪。スティグレールのプロレタリア化の現場形、→8.1）の追跡とは、剥奪がどのコミットで起きたかを質問可能にすることである。

### 主張への主張 — RDFS 再指定（reification）

RDF の triples は「世界についての主張」である。オントロジー管理が必要とするのは「主張についての主張」である——いつ、誰が、どの根拠で、この triple を主張したか。RDF はこれを第一級の手段として持っており、RDF 1.1 Semantics の **RDF reification（再指定）** がそれである。 triples の主語・述語・目的語を、それぞれ別の triples の対象として表現する。

```turtle
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prov: <http://www.w3.org/ns/prov#> .   # W3C PROV-O を来歴語彙として採用する(2.3の来歴原則)

# 原 triples（この triple そのものは後から変更される——削除されるかもしれない）
_:fact1 rdf:subject   <urn:pump-0301> .
_:fact1 rdf:predicate <https://execphil.example/onto#hasFault> .
_:fact1 rdf:object    <urn:fault-77> .

# 再指定 triples（原 triples が「主張された」という主張）
<urn:assertion-A17> a rdf:Statement ;
  rdf:subject   _:fact1 ;   # 多くの implementations では原 triples を直接指す
  rdfs:comment  "2026-11-02 03:11、センサー S-0301 の観測に基づく" .
# 実際には rdf:subject/predicate/object は原 triple の成分を直接指す形で書く。
# ここでは概念の骨格のみを示す(完全形は §commit の JSON→RDF 変換で実装する)。

# 主張についての主張（me-born の主張）
<urn:assertion-A17> prov:wasAttributedTo <urn:person-tanaka> ;
  prov:wasGeneratedAtTime "2026-11-02T03:11:00Z"^^xsd:dateTime ;
  prov:wasDerivedFrom <urn:telemetry-E99> ;
  :assertedInCommit <urn:commit-0042> .
# 削除(this assertion の撤回)も同型の triples で書ける。
# 「取り消し」を再指定できることが RDF の中核的な力である。
```

W3C の PROV-O（Provenance Ontology）を来歴語彙として採用するのは 2.3 の原則である。来歴のない保持は幽霊だ、とあちらで決めた。再指定＋PROV-O は、幽霊を名簿に登録する手続きである。

一方で再指定には定評のある弱点がある。 triples が4倍になる冗長性、参照の煩雑さ、そして——最も重要な——**再指定 triples 自体が変更・削除されうる**という無限後退である。すべての履歴を RDF で持つ設計は、履歴の履歴の設計を要求される。この無限後退を断つ pragmatic 解が、次節の「コミットは RDF の中に置くが、コミット自体の不変性は外部の append-only ログが担保する」という二層構造である。

### コミットの代数 — RDF の中に置く git

設計を確定する。コミットは `Commit` クラスの RDF 個体としてグラフ内に置く。各コミットは、差分（`adds`, `retracts` の関連）と、親コミット（`parent`）と、作者（`prov:wasAttributedTo`）と、意図の宣言（`intent`——自由文、省略禁止）を持つ。グラフの「いま」は HEAD コミットから到達可能な主張集合として**派生**する。グラフの全過去は、コミットグラフを横断して**照会**できる。

```turtle
<urn:commit-0042> a :Commit ;
  :parent <urn:commit-0041> ;
  :intent """3号ポンプの Drift 頻度上昇。夜間点検制約の適用条件を絞り込む。
            失うもの: 夜間でも「様子を見る」選択の記録余地(→1.6 NonRecordingRule 参照)。""" ;
  :adds     <urn:assertion-A17> ;       # ABox 増分は主張ノードとして指す
  :retracts <urn:assertion-A09> ;       # 撤回も主張ノードで指す(削除ではない)
  prov:wasAttributedTo <urn:person-suzuki> ;
  :signedBy <urn:person-lead> .
# :intent が自由文でありながら省略禁止なのは、意図の不在が
# 最も危険な脱知識化の印だからである(2.6 の承認フローはこの検証と結合する)。
# 意図文が 1.6 の SchemaDecision.assumed と結ばれ、
# 設計の前提簿記がコミット代数に接続される。
```

HEAD の意味論をクエリで定義する——ここがグラフであることの利益が最大に出る場所だ。

```cypher
// 「現在のグラフ」= HEAD から親を辿って再構成する主張集合。
// 過去状態の読み取りは、HEAD を任意のコミットに差し替えるだけである。
// 過去は保存されない。過去は再構成される(→1.5 「場は保存されない」と同型)。
MATCH path = (head:Commit {sha: $sha})-[:parent*]->(c:Commit)
UNWIND nodes(path) AS com
WITH com ORDER BY com.seq DESC     // 新→旧。同じ主張は新しい方が勝つ
MATCH (com)-[:adds|retracts]->(a:Assertion)
WITH a.uri AS uri, collect(com)-[0] AS first_touch,
     max(CASE WHEN (com)-[:retracts]->(a) THEN com.seq END) AS retracted_at,
     max(CASE WHEN (com)-[:adds]->(a)     THEN com.seq END) AS added_at
WHERE added_at IS NOT NULL AND (retracted_at IS NULL OR retracted_at < added_at)
RETURN count(uri) AS current_assertions;
```

同じ代数を git 実体の pre-commit hook と結ぶ二層構造を先に許こう。RDF コミット履歴は「意味の履歴」であり、git オブジェクトストアは「ファイルの履歴」である。両者は別物として保ち、`signedBy` と git tag を対応させる。**git をオントロジーの単一の真実にしてはならない**理由は二つある。第一に git は差分の単位をファイルと考えるが、意味の単位は triple であり、ファイルの分割次第で意味の境界が動く（意味はファイル境界を跨ぐ——分類権限とリポジトリ権限が一致しない問題、→2.6）。第二に git の履歴は書き手の都合で書き換えられ（rebase）、意味の履歴は書き換え不能でなければならない（force push を許す履歴は、暴力の履歴を消せる履歴である）。

### 差分トラッキング — git diff を RDF 再指定に変換するPython

既存運用が git でオントロジーを管理している場合——多くのチームがそうである——、この bridge script が git 史を意味史へ翻訳する。

```python
# git_history_to_rdf.py — git diff(意味語彙ファイル) を RDF 再指定コミットへ変換する
# 哲学: 翻訳は復元ではない。git 史に残っている「なにが変わったか」と、
# RDF 史に載せる「意味がどう変わったか」は別物である。
# この script は両者の間に対応を張り、差異を :gap として記録する。
import subprocess, hashlib, rdflib
from rdflib import Graph, URIRef, Literal, Namespace, RDF

GIT  = "git"
R    = Namespace("http://execphil.example/reification#")
P    = Namespace("http://www.w3.org/ns/prov#")

def git_log(onto_file: str):
    # 各コミットでの file 差分を unified diff ではなく「追加された語彙行/削除された語彙行」で取る
    commits = subprocess.run([GIT, "log", "--format=%H|%aI|%an|%s", "--", onto_file],
                             capture_output=True, text=True).stdout.strip().split("\n")
    for line in reversed(commits):   # 古い順 = 意味の出生順
        sha, when, author, subject = line.split("|", 3)
        diff = subprocess.run([GIT, "show", "--format=", sha, "--", onto_file],
                              capture_output=True, text=True).stdout
        added   = [l[1:].strip() for l in diff.splitlines() if l.startswith("+") and not l.startswith("+++")]
        removed = [l[1:].strip() for l in diff.splitlines() if l.startswith("-") and not l.startswith("---")]
        yield sha, when, author, subject, added, removed

def to_rdf(onto_file: str) -> Graph:
    g = Graph()
    g.bind("r", R); g.bind("prov", P)
    head = None
    for sha, when, author, subject, added, removed in git_log(onto_file):
        c = URIRef(f"urn:git:{sha}")
        g.add((c, RDF.type, R.Commit))
        if head: g.add((c, R.parent, head))
        g.add((c, P.wasAttributedTo, URIRef(f"urn:git-author:{author}")))
        g.add((c, R.intent, Literal(subject)))
        # git の author はコードを書いた人であり、意味を決めた人とは限らない。
        # 対応は :gap として明示する(翻訳のロスト測定、→6.3 の round-trip 同型)。
        g.add((c, R.gap, Literal("git author ≠ semantic decider; map via signed-off-by")))
        for kind, lines in (("adds", added), ("retracts", removed)):
            for i, ln in enumerate(lines):
                a = URIRef(f"urn:assertion:{sha}:{i}")
                g.add((a, RDF.type, R.Assertion))
                g.add((a, R.rawText, Literal(ln)))   # 解析不能な行も rawText で生きさせる
                g.add((c, getattr(R, kind), a))
        head = c
    return g

if __name__ == "__main__":
    g = to_rdf("onto/maintenance.ttl")
    g.serialize("onto/git_as_reification.ttl", format="turtle")
    print(f"{len(g)} triples — git history has become askable history")
```

`rawText` の設計思想を補強しておく。git 史の行が RDF として解析できるとは限らない（コメント変更、空行、フォーマット）。解析できないものを捨てると、翻訳の残余が履歴から消える——2.1 の残余の原則は履歴にも適用される。rawText として保存された行は、後年、意味解析の道具が伸びたときに救済される。保存は未来への投機である。

### 失われた意味の復元クエリ — 消えたラベルを辿る

いよいよ本章の目的のクエリである。「半年前に存在し、いま存在しない分類」を、その分類が存在した期間の事実ごと復元する。脱知識化の診断——ある語彙が死んだ時期と、技能剥奪が起きた時期が重なるか——はこの照会の上に成立つ。

```sparql
# lost_meanings.sparql — 死んだ語彙の墓標一覧(と、その墓の下に眠る事実)
PREFIX r: <http://execphil.example/reification#>
SELECT ?label ?died ?killedBy ?intent WHERE {
  # 1) 語彙としての主張が、あるコミットで retract されている
  ?c r:retracts ?a . ?a r:rawText ?raw .
  FILTER(REGEX(str(?raw), "skos:prefLabel|owl:deprecated"))
  # 2) 同じ label を持つ語彙が HEAD で存在しない(=完全な消滅)
  ?a r:liftsLabel ?label .
  FILTER NOT EXISTS { ?alive r:liftsLabel ?label . ?alive r:reachableFromHead true }
  # 3) 死をもたらしたコミットの意図文(意図が空なら、それは記録された事故である)
  ?c r:intent ?intent .
  BIND(?c AS ?killedBy)
  # 4) 死亡時期
  ?c <http://www.w3.org/ns/prov#wasGeneratedAtTime> ?died .
}
ORDER BY ?died
# 意図文の空白列が最重要の出力である。
# 「なぜ消したのか」が空の死は、追跡可能な脱知識化のうち最も深刻な型である。
# 事故死の数は、2.6 の承認フローの健全性の一次指標になる。
```

この照会が組織に対して持つ意味を、あえて硬く言い切っておこう。**失われた意味の復元が不能な組織は、同じ失敗の履歴を持たない組織である。** 失敗の履歴を持たない組織は、失敗を学習ではなく記憶喪失として反復する。墓標を持つことは、失われた知識を復活させることではない——1.6 で見たように、暗黙知は復活しない。墓標がやるのは、喪の作業の材料を提供することだけである。喪を経ない組織改造は、2.2 の否定を含まない同一化——抹消——である。

## 2.6 版管理の倫理 — 誰が分類を書き換える権利を持つか

2.5の墓標クエリが教えてくれる最も不快な事実は、技術的なものではない。「意図なき変更」の列が長い組織では、分類の変更が誰かの仕事の一部として、誰の判断でもないままに行われている。差分は追跡できても、責任は追跡できない。git の author はコードを書いた人であり、意味を決めた人ではない（→2.5 の `:gap`）。この節では、分類の書き換えを**権利の問題**として設計する。版管理の倫理という語は飾りではない。変更履歴の不変性、承認の署名、不服従の記録——これらはすべて機械に強制可能なポリシーの実装物であり、ポリシーの実装は権力の配置そのものである。オントロジーの版管理システムは、その組織が「知識の変更を誰に認めるか」を書き記した憲法である。この節の終わりには、その憲法を Rego で書き、沈黙の猶予期間を機械に守らせるコードが手元にある。

### 分類権限は組織権力のコッド化である

まず事実関係を冷徹に並べる。オントロジーを変更できる状態にあるのは、次の四つの権限のどれかを持つ者だけである。(1) リポジトリの push 権限。(2) マスター語彙の名前空間の所有権（DNS 管理下にある場合）。（3） reasoner ゲートを通過させる CI の設定権。(4) ゲート例外（override）の発動権。

この四つは組織図から独立に割り当てられうる。典型的な事故は、権限の配列と知識の配列がねじれたときに起きる。現場の作業者は第3章で言う competency question の答えを知っているが (4) を持たず、プラットフォームチームは (3)(4) を持つが現場を知らない。このねじれを「技術的な権限設定の問題」と呼ぶか「統治の問題」と呼ぶかで、設計の運命が変わる。前者は ticket の問題として消え、後者は設計対象として残り続ける。

エヴァンスの DDD が限界コンテキストの所有権を組織に自覚させる道具だったことを思い出そう（→6.1）。本章の文法で言い換えれば、**語彙の名前空間は主権であり、マッピングは外交である**。主権の変更手続（語彙の削除・退位・意味変更）と、外交手続（`exactMatch` の格上げ）は、異なる承認フローを持たねばならない。同じフローで扱った瞬間、外交の蓄積が主権の侵食に転化する——現場語彙がマスター語彙に静かに同一化されていく 2.4 の `sameAs` 事故は、手続の欠落が産む地政学的変化である。

### 承認フローの設計 — 変更の種類に応四段階

承認を一律にすると二つの失敗のどちらかになる。軽微な変更が承認待ちで詰まり、現場語彙の追加が事実上止まる（知識の新陳代謝の停止）。あるいは全員承認の形骸化（承認が署名の儀式化）。回避するには、変更の不可逆性に応じて段階化する。

| 級 | 変更の型 | 例 | 承認 | 猶予期間 |
|---|---|---|---|---|
| L0 | 追加のみ（既存語彙に非干渉） | 新類義語の `closeMatch` 追加 | 提出者＋レビュー1名 | なし |
| L1 | 対応の変更 | `closeMatch` の方向変更 | 語彙主権者＋被影響語彙主権者 | 7日 |
| L2 | 意味の変更 | クラス定義の修正、`exactMatch` への格上げ | 承認委員会 | 30日 |
| L3 | 不可逆変更 | 退位・統合・列挙値の削減 | 委員会＋影響受ける現場の代表 | 90日＋沈黙の猶予 |

注意すべきは、級が「変更の大きさ」ではなく**不可逆性**で決まる点である。追加（L0）は取り消しが自由である。統合（L3）は、統合された二つの語の境界を復元するコストが時間とともに無限大へ発散する（境界を知っていた人が辞めるため、1.6・8.1）。不可逆性の測定は 2.5 の履歴代数で可能である——`retracts` された主張の `rawText` を復元照会できる残り人数、という代理指標を CI で計算させればよい。

```rego
# change_class.rego — 級分けの自動化（L0〜L3 の機械判定）
# 哲学: 級の判定を人にさせると、人は「小さいから L1 で」と交渉する。
# 不可逆性は交渉可能にしてはならない。機械が級を決め、人だけが猶予を短縮できない。
package execphil.classify

default level = "L3"

level = "L0" {
  only_additions
  no_master_vocab_touched
}
level = "L1" {
  only_mapping_changes
  not exactmatch_promotions
}
level = "L2" {
  semantic_definition_changes
  not irreversible
}
# irreversible の定義: retracts に deprecated/union/cardinality-reduction が含まれる
irreversible {
  some i in input.commit.retracts
  contains(input.commit.retracts[i].rawText, "owl:deprecated")
}
irreversible {
  some i in input.commit.retracts
  contains(input.commit.retracts[i].rawText, "AllDisjointClasses")
}
irreversible {
  contains(input.commit.intent, "union")   # 統合の自己申告を騙さない。語彙解析と二重checks
}
only_additions { count(input.commit.retracts) == 0 }
```

### 不服従のパス — 承認フローは忠誠の機械であってはならない

承認フローには構造的な暴力が内蔵されている。フローは「承認された変更しか存在しない世界」を作る。2.1 の暴力論の語彙で言えば、フローは残余の記録を拒否する——承認されなかった提案は、履歴にすら残らないことが多い。これは最も深い型の脱知識化である。提案が「検討の結果、不採用」ではなく「提出されなかった」ことになると、2.5 の墓標すら建たない。

したがって、フローは**不服従のパス**を持たねばならない。三つの装置を設計に組み込む。

**第一に、却下された提案の墓標化。** 承認委員会が棄却した提案は、L3 と同じ粒度で `RejectedProposal` として保存され、`intent` と棄却理由（自由文・必須）を持つ。再提案は同じ墓標への参照として行われ、棄却理由の更新なしには通らない。棄却理由の更新は、棄却の歴史を消さずに否定の否定を行う操作——Aufheben の手続形である（→2.2）。

**第二に、現場の unilateral 記録権（一方向の権利）。** 現場はマスター語彙を変更できないが、**自語彙からのマッピング提案を履歴として提出する権利**を止められない。L0 で提出され、承認されなくても、2.5 の履歴代数に載る。承認されなかったマッピングは HEAD には効かないが、墓標クエリには現れる。効かない主張が履歴に残るという設計は、ハーバーマス的な妥当性要求の空間の確保である——真実性・正統性の主張は、承認されなくても発話されうる（→6.2）。

**第三に、override の目録化。** ゲート例外（CI 無視・force merge）は技術的に防止しない。代わりに、override が発動されるたびに `OverrideEvent` を生成し、発動者・理由・回避された制約名を記録し、週次レポートで上位に自動送付する。override を禁止するフローは地下化する。目録化するフローは透明化する。これは検閲と公開の違いであり、2.1 の「残余を捨てるか保存するか」の統治版である。

```python
# silence_period.py — 沈黙の猶予期間の機械執行
# 哲学: 破壊的変更の前に「誰も異議を唱えない期間」を置く。
# 異議は発言だけでなく、参照・分岐・引用のすべてを含む。
# 沈黙の確認は「誰も見なかった」ではなく「誰も触れなかった」で判定する。
import time
from neo4j import GraphDatabase

DRIVER = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "pass"))
SILENCE_DAYS = {"L3": 90, "L2": 30, "L1": 7}

def touch_count(vocab_uri: str, since_iso: str) -> int:
    with DRIVER.session() as s:
        q = """
        // 猶予期間中の「接触」を数える:
        // 参照クエリ実行(AccessLog)、分岐(branch)作成、マッピング提案(L0-L2提出)。
        // 接触 = 誰かがこの語彙をまだ使っている、という証拠である。
        MATCH (a:AccessLog)
        WHERE a.target = $vocab AND a.at > datetime($since)
        RETURN count(a) AS touches
        """
        return s.run(q, vocab=vocab_uri, since=since_iso).single()["touches"]

def can_commit_l3(vocab_uri: str, proposed_at: str) -> bool:
    deadline = time.mktime(time.strptime(proposed_at, "%Y-%m-%d"))
    if time.time() < deadline:
        return False  # 猶予期間そのもの未完
    if touch_count(vocab_uri, proposed_at) > 0:
        return False  # 猶予期間中に接触があった = 沈黙が成立しなかった
    return True
# 「接触」の定義が判定の実質を決める。アクセスログの粒度は
# 組織が現場の活動をどこまで監視するか決定する——監視と保護の境界は
# この関数のコメントではなく、アクセスログのスキーマに書かれる(→1.6 NonRecordingRule)。
```

最後のコメントの重さを、本章の読者ならもう測れるはずだ。沈黙を機械的に検証するシステムは、沈黙を成立させるために接触を記録し続ける。記録しないことの設計（→1.6）と、沈黙を証明するために記録する設計（本節）は衝突する。衝突の解決は原理では下せず、`NonRecordingRule` の対象（個人レベルの閲覧痕跡）を猶予判定から除外する——すなわち「団結した接触」（共有ダッシュボードでの閲覧、分岐、提案）のみを証拠にする——という**政治的選択**としてのみ下される。設計者はこの選択を明文化し（`SilencePolicy.decider`）、2.6 の級 L2 変更として版数に載せる。倫理がコードになる瞬間とは、こういう局所的で小さく、しかし全員が生き残る賭金の場所に現れる。

### 誰が分類を書き換える権利を持つか — 本章の答え

問に戻って、本章の答えを条文形で置く。

1. 分類を書き換える権利は、その分類で**記述される人々**（現場）が最終的に保持する。マスター語彙の主権者は、彼らの代理であり、代理の権限は取消可能でなければならない（委員会メンバーの任期、`OverrideEvent` の上位可視化）。
2. 不可逆な変更（L3）は、影響を受ける現場代表の拒否権を必要とする。拒否権は棄却ではなく**延期**の権利である——L3 は委員会決議で90日追加延期できるが、無期限延期はできない（延期の無限反復は、暴力の先送りではなく暴力の隠蔽である）。
3. 承認されなかった主張も履歴に残る権利がある（不服従の三装置）。
4. 変更の権利は権限システムにのみ存在し、個人の技量には存在しない。push できない senior engineer より、push できる junior の提案が先に墓標を持てる。この不公平は意図的である——権利の所在をコードに置かないと、権利は実績と序列に移住する（知識政治の古典形）。
5. この四条文自身も L2 級の変更対象である。憲法の改正手続は憲法に書かれねばならず、それは本文のこの段落が履歴代数に載ることを意味する。

### 級の実装 — 変更級機械検査の完全コードと運用事故集

級体系（L0 発言・L1 候補・L2 実装・L3 制定、→前節）を、CI で動く機械検査として実装する。変更対象のファイルパスから級を導出し、級の要求（承認者・署名・落日）が commit message と graph の変更記録に揃っているかを検査する。

```python
# tools/change_grade_check.py — 級の実装(→2.5 ブリッジの直前に置く門)
GRADE_RULES = [
    (r"mappings/.*\.yaml$",        "L3"),   # 条約=分類制定(→6.1)
    (r"onto/tbox/.*\.ttl$",        "L3"),   # 正規系 TBox
    (r"onto/abox/.*\.ttl$",        "L2"),   # 記述内容(事実)
    (r"policies/.*\.rego$",        "L2"),   # 方針(→6.4)
    (r"docs/decisions/.*\.md$",    "L0"),   # 発言・記録(誰でも)
]
REQUIRED = {"L3": ["approval:", "signed-off-by:", "sunset:"],
            "L2": ["approval:", "sunset:"], "L1": ["thread:"], "L0": []}
def grade_of(path):     # 最も強い級が勝つ(多重マッチは L3 に解決)
    return max((g for p, g in GRADE_RULES if re.search(p, path)),
               key=lambda g: int(g[1]), default="L1")
def check(commit: str, changed: list[str]) -> list[str]:
    g = max((grade_of(f) for f in changed), key=lambda g: int(g[1]), default="L1")
    return [f"Lacking '{tag}' (grade {g})" for tag in REQUIRED[g]
            if not re.search(rf"^{tag}", commit, re.M)]
```

運用事故集を三件、級体系の運用史として inscribe しておく。**事故一：級 infl の静かなる上昇**——L3 承認の待ち時間（例 3 週間）に業が疲れたチームが、TBox 変更を「docs の要約」に書いて実体変更を abox（L2）に忍ばせる。検査の穴——abox/tbox 分離が実体で守られていない（TBox 相当の変更が abox ファイルに書かれる）。処方——級判定をパス名でなく**変更内容の構造解析**で二段目を持つ（`.ttl` の diff に class/property 定義があれば abox でも L3 に上げる——意味の変更の解析は→2.2 の差分演算の運用実装）。**事故二：署名の形式化**——`signed-off-by:` の列は埋まるが、承認者が変更の意味を検証していない（4.5 の read-then-approve、→8.5 の形式読解のコミット版）。処方——L3 承認に panel 参照を要求する（承認メッセージに CQ 検証結果・roundtrip 統計・落日統計の graph:// URI を最低1つ——**証拠を貼れない署名は署名ではない**、→4.4 の証拠条約）。**事故三：級のない紧急変更**——障害復旧の臨時変更が「紧急」で無級に走り、そのまま残る。処方——紧急変更は級0で通すが、`hotfix:` タグで**48 時以内の級づけ**を強制し、未精算の hotfix を scorecard に載せる（紧急は級外ではなく、級の猶予である——2.6 の沈黙の猶予の運用版）。

三事故の共通の教訓は、**級はファイルの属性ではなく、変更の語義の属性**だということである（パスを撃ち抜ける語義検査が第二段として必要——2.2 の「止揚は差分として計算できる」が、統治の機械検査としてここで回収される）。

### 級のミニ三例 — 同じ変更対不同の领域で級が変わる実演

級体系（→前掲）の最難所は「変更の級は変更の種類ではなく**載せる重み**で決まる」ことにある。同じ形の実体変更が別々の級に着地する三例で缔ぶ。

**例一**：`Equipment.vibrationRange` の upper を 4.2→4.5 に。引用 CQ なし・落日中の実測 E1（→4.1）—L1。理由：実証の帯の扩大が計器の告発阈値を上げる=安全側の余白を減らす、ただし落日周期 90 日内に effect_verification が戻る（→7.3）。**例二**：同じ数値変更、ただし夜間無人セクションの停止规則（→5.5 ステートマシン guard）がこの upper を読む—L3。理由：末端（5.1）が夜間審議者の落日周期に依頼する系で、閾値変更は末端の時間設計の変更になる（→7.6 段2 の落日=末端の巡回、閾値は末端の知覚能力、→感知能力の変更=統治変更）。**例三**：同じ数値変更、site 側の語彙 `strong-shake` の閾値としても二重使用されている（条約なしの暗黙の二重定義—→6.1 の摩擦統計が発見済み)—L3 加条約贸易。理由：分類の二重使用下での変更は一方の現場の語の世界を無声で変える（→6.3 不可視损失の静態形）。

三例の教学を一文に置く。級は diff の文字ではなく diff の**辺の集合**（CQ・guard・条約・落日）で決まり、ゆえに級自動計算（→前掲の change_grade_check）は diff ではなく**グラフの閉包**を計算する（変更対象から 2 次周辺の依頼ノード数と種別が級の輸入——2.4 の「分類の暴力」が局所ではなく網目で起きることを、級計算が機械的に示す）。
