## 1.1 「語れるよりも多くを知る」— ポランニーの暗黙知

この章は、ある種類の失敗の反復から始まる。優秀なチームが、ベテランの知識を手順書に書き出し、レビューを通し、新しい作業者や新しいシステムに手渡した。それでも現場は劣化した。原因は書き出しの下手さではなかった。書き出しは完成していた。失われたのは、書かれた項目ではなく、書かれた項目を選ばせ、項目のあいだでどちらを優先するかを決めていた、言葉にならない側の知識だった。マイケル・ポランニー（Michael Polanyi）はこれを暗黙知（tacit knowledge）と呼び、「われわれは語れるよりも多くを知っている（we know more than we can tell）」と言った。本節ではこの文を比喩としてではなく、設計制約として読む。完全な明示化は技術的に未熟な夢ではなく、原理的に到達しない目標である。ならば設計は、明示化の失敗を例外としてではなく仕様として引き受けなければならない。この着地点が決まらない限り、後続のグラフもオントロジーも、知識の保存ではなく知識の埋葬装置になる。

### 1.1.1 経験の二層構造 — 補助焦点と対象焦点

ポランニーの中心概念は二つ組である。対象焦点（focal awareness）と補助焦点（subsidiary awareness）。杖を突く盲人にとって、意識の対象は障害物と路面の続きであり、杖そのものは意識されない。杖そのものに焦点を移した瞬間、盲人は世界へのアクセスを失い、ただの木の棒を握った人間に戻る。釘（くぎ）を打つ工員は釘の頭を見ており、ハンマーの重さは手の延長として感じられているだけだ。ハンマーを注視した瞬間に、打つ動作は崩れる。知識の本体は対象焦点ではなく、対象焦点を支えている補助焦点の側にある。

ここから最初の工学的結論が出る。仕様書・手順書・API ドキュメント・イベントログは、すべて対象焦点の記録である。補助焦点は記録の条件であって、記録の内容にならない。したがって対象焦点だけを写し取った文書は、執筆の怠慢とは無関係に、構造的に知識を欠落させる。欠落はバグではなく、記述の位相の帰結である。

段取り替えの手順書が「3 番ボルトを 25 N·m で締める」と書いたとしよう。数値は正しい。しかし締め付けの終わりを教えていたのは、ソケットの当たり音、手の感触、そして「締まりすぎる前に止める」判断だった。手順書は数値を書き、数値は判断の補助だった。読み手はその音と感触を持たずに現場へ来る。

```python
# 哲学的意図: 条件は書ける。条件を評価している身体は書けない。
# この差を忘れたシステムは、正しい仕様を持って誤った判断をする。
TORQUE_NOM = 25.0

def in_spec(actual: float) -> bool:
    return abs(actual - TORQUE_NOM) <= 1.5
```

この関数は正しい。そして正しさは十分ではない。`in_spec` が `True` のまま不良が出る事件は、仕様が存在しないからではなく、仕様が補助焦点を取り違えているから起きる。

### 1.1.2 技能の身体性 — 知識は体内に入らなければならない

技能の習得とは、外部にある規則を内部に置くこと（内在化: internalization）であり、その規則の中に自分が住むこと（内住: indwelling）である。規則を暗唱している限り、その人は技能を持っていない。自転車に乗れる人間は「重心を前に」という文を持つのではなく、傾きそのものである。

そして逆向きの事実もある。明示化は技能を破壊しうる。百足が自分の足の出番を考えた瞬間に歩けなくなる、あの話（centipede effect、チグハグ現象）は寓話ではない。熟練作業の途中に「いまどの手順を実行しているか」と尋ねると、作業が止まる。熟練者は手順を知っていないのではなく、手順が補助焦点に沈んでいるから言葉にできない。

現場でよく見る失敗を、そのままの形で書く。

1. 聞き取り。30 年の経験を持つ作業者 S さんに「段取りのコツをすべて話してください」と依頼し、2 日かけて 104 項目のチェックリストを作った。内容に漏れはないと S さん自身が承認した。
2. 適用。新規作業者は 104 項目を順番に確認した。確認率は 98%。監査ログ上は完璧だった。
3. 事故。3 か月後、同じ機械で不良が続出した。不良は S さんが「確認しない」ことで防いでいた。S さんは項目を確認していたのではなく、機械の音の高さを聞いていた。音は 104 項目のどこにもなかった。

原因は聞き取りのまずさではない。聞き取りは成功していた。失敗したのは、暗黙知の本体が項目の集合ではなく、項目を選ばせていた補助項にあると仮定しないデータモデルだった。したがって保存に本当に役立つ富は、成功条件の一覧ではなく、失敗の前兆の集合である。現場は「うまくいく条件」よりも「いま壊れかけている条件」について、はるかに多くを語らずに知っている。

### 1.1.3 暗黙知の三側面 — 認知・技能・評価

暗黙知は単一の敵ではない。三つの側面は別々のしかたで明示化をすり抜ける。

| 側面 | 何が含まれるか | 典型的な明示化の試み | 典型的な破綻の型 | 設計の受け皿 |
|---|---|---|---|---|
| 認知（tacit cognition） | パターン認識、異常検知、「何かがおかしい」 | 検査基準のチェックリスト化 | 既知の集合の列挙になり、未知の例外が落ちる | 観測頻度の計数と未明示関係の検出 →第1.5節 |
| 技能（tacit skill） | 身体操作、順序の感覚、手応え、力加減 | 手順書、動画、VR 教材 | 手順は暗唱できるが作業ができない | 成功条件ではなく失敗の前兆を記録 |
| 評価（tacit evaluation） | 何を重要とみなすかの基準そのもの | KPI、重大度ランク、優先度スコア | 指標が目標に変わった瞬間に指標が壊れる | 判断根拠を反証可能な対話として保存 →第8.5節 |

三つ目の側面が最も軽視される。「どのデータを集めるか」を決める基準は、集めるデータよりも暗黙的である。重大度を 1 から 5 で分ける行為は、5 段階に分けるという決定と、各段階の境界を暗黙のうちに引き、その境界を組織に強制する。Goodhart の法則（指標が目標になると指標は壊れる）は、評価の暗黙知を無自覚に明示化したときに必ず現れる症状である。これは後述する Confidence スコアの設計でも同じ形で再発する（→第1.4節）。

### 1.1.4 「完全な明示化」は原理的に不可能である

三つの限界を、定量的な主張ではなく定性的な定理として明示しておく。

第一に、焦点の反転性。明示化とは補助焦点を対象焦点へ移す操作であるが、移した瞬間に、その対象を理解するための新しい補助項が発生する。「段取りが良い」を「段取りとは段取り準備時間を最小化する作業である」と翻訳したとしよう。その日本語を読む能力、すなわち「最小化」の意味を状況で埋める能力自体が暗黙知である。翻訳は暗黙知を減らすのではなく、暗黙知の位置を移動させる。

第二に、明示化の後退（explicitation regress）。暗黙の知識 d を調べて命題 p にする。p を正しく適用するには別の暗黙知 d' が必要で、d' を p' にすると d'' が現れる。終端は経験的に観察されない。よって「完全明示化」は未到の目標ではなく、非存在の目標である。

第三に、文脈依存と自己参照。同一の命題は文脈によって機能を変える（「送紙を止めよ」は夜勤と点検中では意味が違う）。しかも明示化する主体自身が暗黙知の担い手であり、自分の補助焦点を直接観察できない。観察しようとして焦点を移した瞬間に、それは技能の破壊として現れる。

アポリアは正直に書いておく。我々は明示化の限界の位置を計算できない。この節のコードが算出する残余率も、第1.4節の `confidence` も、暗黙知の量を測るものではない。明示化の試行の履歴から事後的に推定した統計値にすぎない。それでも推定を持つことと持たないことには、非対称な差がある。

### 1.1.5 では工学的に何をするのか — 明示化の失敗を正常系として型にする

以上から本節の設計判断を五つにまとめる。

1. 明示化の失敗を例外処理ではなく、保存される一次データとして型で表現する。`unsaid` は空欄ではなくレコードである。
2. 世界を閉じない。不明（unknown）を値として持たせ、閉世界仮定（closed-world assumption）を明示的に捨てない領域では開世界で扱う。
3. 補助焦点相当の情報（環境テレメトリ、音、振動、身体負荷）を本体と同じグラフに載せる。後で関係づけるためではなく、関係を成立させていた条件として（→第1.4節、→第1.5節）。
4. 明示化の試行そのものを履歴化する。最新版で上書きせず、追記する（→第2.5節）。
5. 明示化されていない高頻度関係を行動データから検出し、そこを形式化の辺境として計測する（→第1.5節）。

```python
# explicitation.py
# 哲学的意図: 「語れなかった」を例外ではなく保存されるデータとして型付ける。
# 残余（residue）は本体の影である。影の形状から本体の形を推定するのがこの設計の戦略。
from __future__ import annotations

import json
from dataclasses import asdict, dataclass, field
from datetime import datetime, timezone

# 語れなかった理由の分類。これは欠陥の分類であり、それぞれ設計の受け皿が違う。
BLOCK_REASONS = {
    "no_words":      "現場に語彙がなく、命名できない",
    "body_only":     "身体でしか保持されておらず、記述に移せない",
    "context_varies": "状況ごとに条件が変わり、普遍命題にならない",
    "too_obvious":   "明らかすぎて、書く対象として浮かばない",
    "political":     "書くことが組織的にコストになる（沈黙が合理である）",
}

@dataclass(slots=True)
class ExplicitationAttempt:
    attempt_id: str
    actor: str
    relation: str                  # 明示化しようとした関係 = 対象焦点
    articulated: list[str] = field(default_factory=list)
    unsaid: list[tuple[str, str]] = field(default_factory=list)  # (断片, 遮断理由)
    context: dict[str, str] = field(default_factory=dict)
    created_at: str = field(
        default_factory=lambda: datetime.now(timezone.utc).isoformat(timespec="seconds")
    )

    def residue(self) -> float:
        """残余率。1.0 に近いほど暗黙のまま残っている。
        測定ではなく事後推定である点をコードで明示する（→1.1.4 のアポリア）。"""
        n = len(self.articulated) + len(self.unsaid)
        if n == 0:
            return 1.0     # 何も語れていない = すべてが暗黙。0 ではなく 1 で表すのが設計判断。
        return len(self.unsaid) / n

    def as_params(self) -> dict:
        """Neo4j の $params にそのまま渡せる形へ落とす。
        unsaid は文字列へ潰すが、潰した理由（lossy）は別に保持する。"""
        d = asdict(self)
        d["unsaid"] = [text for text, _ in self.unsaid]
        d["lossy_reasons"] = sorted({r for _, r in self.unsaid if r in BLOCK_REASONS})
        d["residue"] = round(self.residue(), 3)
        return d

if __name__ == "__main__":
    a = ExplicitationAttempt(
        attempt_id="2026-04-11/setup-07",
        actor="operator:sasaki",
        relation="spindle-noise -> stop-decision",
        articulated=[
            "主軸音が 900 Hz 以上で 3 秒続いたら送紙を止める",
            "停止後、治具の当たり面を目視で確認する",
        ],
        unsaid=[
            ("『変な感じ』が何なのかは言葉にできない", "body_only"),
            ("正常な音の高さは機械ごとに違い、閾値が一定しない", "context_varies"),
            ("停止を誰に何時知らせるかは、その場の空気で決まる", "too_obvious"),
            ("停止の報告は遅延の責任を問われるので、書きにくい", "political"),
        ],
        context={"machine": "MC-14", "shift": "night", "ambient_dB": "78"},
    )
    print(json.dumps(a.as_params(), ensure_ascii=False, indent=2))
```

契約として守らせるべきは「残余が消えないこと」である。

```python
# test_explicitation.py
# 哲学的意図: 明示化の記録が articulated だけで構成されうるモデルは、暗黙知を保存しない。
import explicitation as ex


def test_residue_is_not_zero_by_default():
    a = ex.ExplicitationAttempt(attempt_id="x", actor="op", relation="r")
    assert a.residue() == 1.0            # 何も語っていない = 残余は全部


def test_unsaid_survives_serialization():
    a = ex.ExplicitationAttempt(
        attempt_id="y", actor="op", relation="r",
        articulated=["a"], unsaid=[("b", "body_only")],
    )
    p = a.as_params()
    assert p["unsaid"] == ["b"]
    assert p["residue"] == 0.5
    assert p["lossy_reasons"] == ["body_only"]
```

グラフ上の実装は次の通りで、「語れなかった関係」をノードとして置く。空欄や NULL では残らない。

```cypher
// 1) Unsaid を一次市民として置くための制約（Neo4j 5.x）
CREATE CONSTRAINT unsaid_key IF NOT EXISTS
FOR (u:Unsaid) REQUIRE u.key IS UNIQUE;

CREATE CONSTRAINT explicitation_attempt_id IF NOT EXISTS
FOR (a:ExplicitationAttempt) REQUIRE a.attempt_id IS UNIQUE;

// 2) 上の JSON を $params として受け、残余をグラフへ載せる。
//    「語れなかった」は属性の空白ではなく頂点として存在する。
MERGE (a:ExplicitationAttempt {attempt_id: $attempt_id})
SET  a.actor       = $actor,
     a.relation    = $relation,
     a.residue     = $residue,
     a.created_at  = $created_at;

UNWIND $unsaid AS gap
MATCH  (a:ExplicitationAttempt {attempt_id: $attempt_id})
MERGE  (u:Unsaid {key: a.attempt_id + '#' + gap})
  SET  u.text = gap, u.lossy_reasons = $lossy_reasons
MERGE  (a)-[:COULD_NOT_SAY {recorded_at: $created_at}]->(u);
```

```cypher
// 3) 暗黙知の痕跡クエリの骨格: 現場で繰り返されるのに一度も明示化されていない関係を探す。
//    出現頻度が高く明示化がほぼゼロなら、そこが形式化の辺境である（詳細は →第1.5節）。
MATCH (o:Observation)
WHERE o.relation IS NOT NULL
WITH o.relation AS rel, count(*) AS observed
WHERE observed >= 20
OPTIONAL MATCH (e:ExplicitStatement {relation: rel})
WITH rel, observed, count(e) AS articulated
WITH rel, observed, articulated, toFloat(articulated) / observed AS explicitness
WHERE explicitness < 0.05
RETURN rel, observed, articulated, explicitness
ORDER BY observed DESC
LIMIT 20;
```

### 1.1.6 分岐点 — 三つのアーキテクチャ選択

暗黙知をどう扱うかは、道徳ではなく配線の選択である。三つある。

| 選択肢 | 仕組み | 導入コスト | 明示化の失敗の扱い | 主たる破綻モード | 本書での扱い |
|---|---|---|---|---|---|
| A 完全明示型 | 全知識をスキーマへ写す | 初期大・維持大 | 作業者の未熟さへ転嫁 | 静かな劣化（誰も気づかない） | 却下 |
| B 痕跡推定型 | 行動ログから頻度と明示化率を測る | 中（計装が要る） | 残余を統計として記録 | 観察されることで行動が変わる | 採用（補助） |
| C 場記録型 | 状況・環境・感情価を関係と同時に保存 | 大（境界設計が要る） | 残余をノードとして保存 | 記録過多と検索不能 | 採用（主軸、→第1.4節） |

B は計装できる領域で強く、C は計装できない領域で強い。A は却下されるべきだが、現実のプロジェクトの大半は A で運用されており、そのことが失敗を「人のミス」として記録してしまう。失敗を仕様とする設計との違いを並べる。

| 設計観点 | 明示化を成功とみなす設計 | 明示化の失敗を仕様とする設計 |
|---|---|---|
| 残余 | ログ雑音として破棄 | `Unsaid` ノードとして保存 |
| 手順通りにできない人 | 教育不足 | 手順の不足として記録し、差分を人に返す |
| 未知 | NULL または既定値 | `unknown` を値として保持 |
| 変更 | 最新版で上書き | 試行の履歴を追記（→第2.5節） |
| 劣化の出現 | 可視化されない | コストとして可視化される |

### 1.1.7 この節のアポリア

痕跡を記録する設計は、暗黙知を救うと同時にそれを殺す。`Unsaid` を保存し、残余率をスコアとして運用し始めると、「語れなかったこと」は報奨の対象になる。評価の暗黙知が新しい沈黙を生む（`political` は排除されない）。観測されることで行動が変わるという観察者効果は、B 型アーキテクチャの原理的な限界である。さらに根源的な問いとして、「暗黙知を保存するシステムは暗黙知を保存できるのか」という問題は解けないまま終章へ残る。この解けなさをバグとしてではなく設計条件として扱う方法を、この本は最後まで引きずる。次の節では、明示化の境界が固定した線ではなく移動する面であることを見る（→第1.2節）。

### 実行練習

1. 上の `explicitation.py` をその場で走らせて、`residue` が 0.667 になることを確認し、`unsaid` の 4 断片の理由ラベルの内訳が JSON に出てくることを確かめよ。次に `unsaid` を 1 件に減らすと残余率が 0.33 へ変わることを観察し、「残余率の低い試行」が実は「聞き取りの失敗を見逃した試行」である可能性を、コードのどの行が隠蔽しているかを特定せよ。
2. `python3 -m pytest -q test_explicitation.py` を実行して 2 件のテストが通ることを確認したうえで、`articulated` も `unsaid` も埋めた試行を 1 件追加し、残余率が 0.5 ちょうどになる入力を設計せよ。その後、その `as_params()` の出力を `$params` として上の Cypher（2 番目のブロック）を Neo4j 5.x に流し、`(a)-[:COULD_NOT_SAY]->(u)` の辺が 2 本張られることを `MATCH ()-[r:COULD_NOT_SAY]->() RETURN count(r);` で確かめよ。
3. `Observation` と `ExplicitStatement` にサンプルを張って痕跡クエリを走らせ、`explicitness < 0.05` の関係が実際に現れることを確認せよ。例: 同一 `relation` を 40 件生成し `ExplicitStatement` を 1 件だけ作る。次に `WHERE observed >= 20` を `>= 100` に変えたとき結果が消える理由を、しきい値の設計判断として 3 行で説明せよ（低すぎる閾値は既知の例外を拾い、高すぎる閾値は稀だが重大な暗黙を捨てる）。

## 1.2 境界問題 — 形式化が届くところ・届かないところ

1.1節で、私たちは「語れるよりも多くを知る」という事実を受け入れた。だが受け入れた瞬間に、次の問いが不可避になる。では、語れる部分と語れない部分を分ける境界はどこにあるのか。そしてその境界を、システムはどこに描けばいいのか。この節は境界問題の節である。答えを先に言えば、境界は場所が固定されていない。同じ現場・同じ知識・同じ組織でも、昨日まで暗黙知だったものが明示知になり、昨日まで明示知だったものが暗黙知へ戻る。境界は動く。したがって本書が設計するのは「暗黙知の置き場」ではなく、「境界の移動を追跡する仕組み」である。本節では、境界を線ではなく面としてモデル化する発想を立て、境界設計の三つの失敗型を失敗例から抽出し、その設計判断を小さなグラフコードに落とし込む。形式化の過程でこぼれ落ちた意味 — 形式化の残骸 — を記録する必要性もここで予告する。その本格的な取り扱いが第2章の主題である。

### 明示知と暗黙知の境界は、なぜ固定できないのか

明示知（explicit knowledge）と暗黙知（tacit knowledge）の区別は、知識を二箱に仕分ける分類ではない。1.1節で見たポランニーの構造 — 補助焦点（subsidiary awareness）と対象焦点（focal awareness） — を思い出すべきだ。私たちが「語れる」のは常に、背景に沈んだ補助焦点が支えているものだけである。そして補助焦点の中身は、道具・身体・言語・制度とともに歴史的に変わる。ここに境界が固定できない理由がある。

境界の位置を決めるのは知識そのものではなく、観測条件である。少なくとも三つの観測条件が境界を押す。

- **計測可能性**: 振動・温度・視線といった現象にテレメトリ（telemetry）のチャネルが開くと、「作業者の勘」の一部がデータとして明示知側へ移動する。1.5節で温度・振動・音声レベルをグラフに載せるのは、まさにこの移動を起きるものとして扱うためである。
- **語彙の成熟**: 現場で「機械の機嫌」と呼ばれていたものに技術語彙が与えられると、それは報告可能になり明示知側へ寄る。逆に、現場語彙をマスター語彙へ正規化する統合の拍子に、語っていたはずの意味が消えることがある。明示知が暗黙知側へ後退する方向の移動は、いつも起きる。
- **参加者の交代**: 熟練者の退職、新任者の参入、言語や文化の違うチームの合流。同じ手順書でも、読める人が減れば実質的な境界は明示知側から後退する。知識の位置はテキストではなく人が担っているからだ。

ポランニーの「完全な明示化の不可能性」は認識論の定理であり、経験的観測の総和からは得られない（1.1節の結論）。ただし誤読してはならない。「明示化の原理的限界」と「この現場・この時点での境界の位置」は別の物である。前者は設計の前提条件として引き受ける不変の条件、後者は観測し記録し再評価できる変動する状態である。境界問題を「暗黙知は形式化できない」という諦めで処理する設計は、後者を消してしまう。したがって工学的に要求されるのは次の三つの設計条件である。

- **境界は状態変数である**: システムは明示化可否の判定を、根拠・証拠・有効期限付きの主張として保持する。
- **境界移動は出来事である**: 移動はグラフ上のイベントとして記録され、履歴から復元できる。
- **越境した項目に取り残しを作らない**: 越境前の旧記録と、こぼれた残余（residuum）は削除しない。

### 境界が動く: 観測条件が変わると、知識の居場所が変わる

境界移動の具体を四つ挙げる。型だけが違えば、どれも設計の要求に翻訳できる。

1. **計測が拓く移動**。製鉄の品質判定で、表面傷の合否は長年「検査員の目の勘」だった。スペクトルカメラと分類モデルの導入で、同じ知識の大部分が明示知（モデル＋ラベルデータ）側へ移った。残ったのは「このランクは現場が受け入れない」という評価の暗黙知だけである。項目は全体として移動せず、層（観測・判定・評価）ごとに別々に移動する点が重要だ。
2. **正規化が削る後退移動**。現場で「さしがねの返しが甘い」と語っていた知識を、マスター語彙の `Defect:寸法不良` に写像した瞬間、`返しが甘い` が含んでいた方向性・工程位置・修理可能性の含みが消えた。報告されなくなった意味は、組織の中で暗黙知側へ落ちる。第2章が扱う「分節化の暴力」はこの後退移動の最大発生源である。
3. **交代による後退移動**。前任者が書いていなかった例外手順は、前任者の退職とともに語られなくなる。テキストが変わらなくても、境界は明示知側から後退する。知識の所在をドキュメントに限定する設計はこの移動を捕捉できない。
4. **語彙の発明による前進移動**。整備士が「間隔の濁り」という言葉を見つけた瞬間、それまで報告不能だった振動現象が報告可能になる。概念の発明は境界の前進である。

これらから導かれる設計判断は一つに収縮する。**「これは暗黙知である」は永久の本性ではなく、有効期限付きの主張である**。境界を扱えるものにするとは、主張にタイムスタンプと反証条件を持たせることである。

### 形式化設計の三つの失敗型 — 現場の失敗例から

境界を固定線と見なしたシステムには、決まった壊れ方がある。三つの失敗型を、実際の監査でよく見つかるパターンとして記す。

**失敗A: チェックリストの完全性の幻想**。航空部品のトルク管理で、「手順を全部書けば暗黙知は消える」という信念でチェックリストを書き切った現場があった。チェックリストに `異常音を確認` の項目はある。しかし「どんな音が“ない”ことを異常と呼ぶのか」は一行も書かれていない。熟練者が新人に口頭で伝え続けていたその行は、熟練者が去った時点で消えた。失敗の本体は項目の少なさではなく、チェックリストが完全であると自覚しなかったことである。チェックリストは境界面の特定時点のスナップショットであり、残余（こぼれたもの）の所在をどこにも記録していない。

**失敗B: スキーマに境界が石化する**。食品加工の設備保全システムに `operator_judgment` ノードがあった。「これは人間の暗黙知」という設計判断がノード型として石化し、プロパティに根拠も有効期限もない。数年後、アコースティックセンサーで判断の大半が機械側へ移管可能になったとき、システムには「元・暗黙知」を置く場所がなかった。ノードは `manual` のまま放置され、新チャネルのデータはシステム外のCSVに流れ、両者を結ぶ痕跡は残らなかった。システムは世界について主張し、世界がその主張を偽にした — それを誰も検出できない構造だった。

**失敗C: 過剰形式化の強制**。保守班が熟練工の判断を決定木に抽出する試行を行い、作業員は「説明できないことは書くまい」と語り出しを細分化して逃げ、結果として木は既知の規則の焼き直しになった。悪い形式化は暗黙知を消さない。隠蔽する。そしてより質の悪い副作用として、作業員の注意を形式化可能な範囲だけに固定し、境界の外側を観測しなくなる。明示化の試行が失敗したという事実こそが残余の座標を示す唯一の手がかりなのに、失敗は記録されず廃棄された。

三つの失敗型は同一の構造欠損を共有する。境界判定が主張ではなく構造になり、主張の偽化が検出されず、失敗と残余が記録されない。

### 境界を「線」ではなく「面」としてモデリングする

境界を二値の線として描く古典的選択（`is_tacit: boolean`）は、上記の三失敗すべてを許容してしまう。代わりに本書は境界を連続的な面として描く。必要なのは「この項目は暗黙知か」という二値の質問ではなく、「どれほど形式化に近いか」という位置の測定である。

| モデル化の選択 | グラフ上の形 | 境界移動の追跡 | 残余の保存 | 主な破綻モード |
|---|---|---|---|---|
| 二値の線 | `is_tacit` プロパティ | 不可（上書きで消える） | 不可 | 石化（失敗B）、完全性の幻想（失敗A） |
| 型付き境界 | 明示/暗黙/不明 の3値 | 部分可（変更履歴なし） | 不可 | 「不明」の黒洞化、3値内の移動が見えない |
| 面（連続場） | `formalization_depth` などの連続値 | 可（値の履歴を保持） | 部分可 | 数値の権威化（測定を推定と取り違える） |
| 面＋イベント | 連続値＋移動トランザクション | 可（移動の根拠まで履歴） | 可（attemptノード） | スキーマの複雑化 |

「面」とは次のような場（field）である。知識項目ごとに、形式化への近さを決める要素 — ①明文化試行の成否履歴、②観測チャネルの有無と精度、③正規語彙との接続の有無、④当事者間の合意度 — が重なっており、項目は面上の一点として座標を持つ。点は動く。動くことを記録するのが「面＋イベント」モデルである。

本書の実装では、境界面の位置を `formalization_depth`（形式化深度, 0.0〜1.0）として持つ。1.4節で設計される `confidence`（信頼度）× `context_score`（文脈適合度）の積は、項目の現在この場の形式化可能性、すなわち境界の現在値である。`depth` が閾値を横断した瞬間を表すのが `BoundaryCrossing` イベントだ。面を器として実装するのは1.4節のスキーマなので、ここでは設計原理までを立てておく。

### 形式化の残骸 — 残余を記録する装置としての境界記録

形式化を試みれば、必ず残骸（residue）が出る。1.1節の「明示化の失敗を仕様として設計に組み込む」の実装形がこれである。

残骸を捨てるシステムと拾い続けるシステムは、十年後に姿が違う。捨てれば、同じ境界に二度目の試行が当たるたびに、誰も知らないまま同じコストが計上される。拾い続ければ、失敗した試行が残余の座標標として残り、次の試行はそこから始める。

境界記録（BoundaryRecord）を第一級のノードとして設計する。主張・試行・移動イベント・残余レポートの四種を同じ器に入れる。境界問題の解決策は概念ではなくレコード型で現れなければならない。

### 設計判断と小さなコード: 境界記録をグラフに載せる

ここからは思想の帰結をグラフ構造へ翻訳する。スキーマの全面設計とテレメトリの載せ方は1.4・1.5節に譲り、本節は境界面の最小実装だけを置く。依存環境（Neo4j 5.x）は付録Aに従う。

```cypher
// 1.2 最小スキーマ: 知識項目と境界記録。
// 哲学的意図: 「これは暗黙知である」を構造ではなく主張として保存する。
// 主張は根拠・証拠・有効期限を持つ。項目ノードに tacit フラグを持たないこと自体が、
// 1.1節の結論（明示化の失敗は仕様）の実装である。
CREATE CONSTRAINT knowledge_item_key IF NOT EXISTS
  FOR (k:KnowledgeItem) REQUIRE k.key IS UNIQUE;
CREATE CONSTRAINT boundary_record_key IF NOT EXISTS
  FOR (b:BoundaryRecord) REQUIRE b.record_id IS UNIQUE;

// KnowledgeItem: depth は「現在有効な境界判定」の現在値のみ。履歴は項目ノードに
// 埋め込まない。履歴は BoundaryRecord の系列そのもの（第1級のレコードが履歴を担う）
// であり、項目の書き換えには依存しない。境界が面であることは記録の多重さで示される。
CREATE (k:KnowledgeItem {
  key: 'bearing-sound-judgment',
  label: '軸受異音の合否判断',
  depth: 0.35                  // 現在値: 0=完全暗黙, 1=完全明示
});

// BoundaryRecord: kind は claim / attempt / crossing / residue の四種。
// claim = 現在の境界判定そのもの。evidence は判定の根拠。
// expires_at を過ぎた判定は自動的に再審査キューへ回る（境界は有効期限付き主張）。
CREATE (b:BoundaryRecord {
  record_id: 'br-0001', kind: 'claim',
  claim: 'tacit-side',
  depth_at: 0.10,
  evidence: '異音表現の現場用語が3名で不一致、相関データなし',
  recorded_by: 'user:kawai',
  recorded_at: datetime('2024-04-01T09:00:00+09:00'),
  expires_at: date('2026-10-01')   // 失効した主張は偽である: 再審査必要
});
CREATE (k)-[:HAS_BOUNDARY {as_of: date('2024-04-01')}]->(b);

// attempt: 明示化の試行。失敗こそ残余の座標標であるから、失敗を保存する。
// 哲学注: 1.1の「明示化の失敗は仕様」により、outcome=failure をレコードする。
CREATE (a:BoundaryRecord {
  record_id: 'br-0002', kind: 'attempt',
  method: 'semi-structured-interview',
  outcome: 'partial-failure',
  note: '「いい音」の指示語以外を語れず。語れなかった内容の断片のみ記録。',
  recorded_at: datetime('2024-06-14T14:20:00+09:00')
});
CREATE (k)-[:ATTEMPTED_ON]->(a);

// crossing: 移動イベント。移動した項目の越境前の状態もここに紐づくため、
// 境界移動が孤立レコード（取り残された参照）にならない。→2.5 のreificationへの橋。
CREATE (c:BoundaryRecord {
  record_id: 'br-0003', kind: 'crossing',
  direction: 'toward-explicit',
  from_depth: 0.10, to_depth: 0.35,
  trigger: 'acoustic-sensor-pilot',   // 移動の原因は観測条件の変化
  recorded_at: datetime('2026-10-12T11:05:00+09:00')
});
CREATE (k)-[:CROSSED]->(c);

// residue: 越境時にこぼれた意味の断片。→第2章の残余保存設計がこの中身を扱う。
CREATE (r:BoundaryRecord {
  record_id: 'br-0004', kind: 'residue',
  text: '「合否は出せるが、この騒音の下でしか聞こえない音がある」',
  source_attempt: 'br-0002',
  recorded_at: datetime('2026-10-12T11:07:00+09:00')
});
CREATE (c)-[:LEAKED]->(r);
```

境界判定の現在値を、根拠付きで更新する手順。深度は測定ではなく再評価である。

```cypher
// 境界の再評価: 三条件での計算。→1.4 の confidence×context_score と接続。
// 哲学注: 深度は観測条件の関数であり、自然種への分類ではない。
// 数値に権威を移譲してはならない: これは測定ではなく、透明な推定である。
MATCH (k:KnowledgeItem {key: 'bearing-sound-judgment'})
CALL {
  WITH k
  OPTIONAL MATCH (k)-[:ATTEMPTED_ON]->(a:BoundaryRecord {kind:'attempt'})
  WITH k, a ORDER BY a.recorded_at DESC LIMIT 1
  // 明示化試行の完了度（partial-failure は 0.5 として部分点）
  WITH k, CASE a.outcome
             WHEN 'success' THEN 1.0 WHEN 'partial-failure' THEN 0.5
             ELSE 0.0 END AS trial_score
  // 観測チャネルの有無: テレメトリの存在が境界を前進させうる（1.5で実装）
  OPTIONAL MATCH (k)-[:MEASURED_BY]->(s:Sensor)
  WITH k, trial_score, CASE WHEN s IS NULL THEN 0.0 ELSE 1.0 END AS has_channel
  // 正規語彙との接続（→2.4 の equivalentClass マッピング）
  OPTIONAL MATCH (k)-[:MAPS_TO]->(term:VocabularyTerm)
  RETURN 0.5*trial_score + 0.3*has_channel
       + CASE WHEN term IS NULL THEN 0.0 ELSE 0.2 END AS new_depth
}
WITH k, new_depth,
     (k.depth < 0.5 AND new_depth >= 0.5) AS crossed
CREATE (b:BoundaryRecord {
  record_id: 'br-' + randomUUID(), kind: 'claim',
  claim: CASE WHEN new_depth >= 0.5 THEN 'explicit-side' ELSE 'tacit-side' END,
  depth_at: new_depth,
  evidence: 'recomputed: trial+channel+term',
  recorded_at: datetime(), expires_at: date() + duration({months: 6})
});
CREATE (k)-[:HAS_BOUNDARY {as_of: date()}]->(b);
FOREACH (_ IN CASE WHEN crossed THEN [1] ELSE [] END |
  CREATE (kc:BoundaryRecord {
    record_id: 'br-' + randomUUID(), kind: 'crossing',
    direction: 'toward-explicit',
    from_depth: k.depth, to_depth: new_depth,
    trigger: 'recomputation', recorded_at: datetime()
  })
  CREATE (k)-[:CROSSED]->(kc)
);
SET k.depth = new_depth;
```

境界移動のドリフト検出はバッチスクリプトにする。境界は固定線ではないから、固定されたままの判定こそ疑わしい。

```python
# detect_boundary_drift.py — 境界判定の期限切れと深度ドリフトを拾う。
# Neo4j 5.x + neo4j driver (python==3.11, 付録A)。
# 哲学的要点: 「暗黙知」判定は反証可能性を持つ主張である。
# 反証条件（有効期限）を過ぎた主張は、偽と見なして再審査に回す。
from neo4j import GraphDatabase

DRIFT_QUERY = """
// 境界ドリフト検出。境界が「線」でなく「面」であることの検証クエリでもある。
// 1) 有効期限切れの claim を「偽化した主張」として列挙（失敗Bの検出器）
MATCH (k:KnowledgeItem)-[hb:HAS_BOUNDARY]->(b:BoundaryRecord {kind:'claim'})
WHERE b.expires_at < date()
RETURN k.key AS item, 'expired-claim' AS finding,
       b.depth_at AS depth, b.expires_at AS lapsed
UNION
// 2) 明示化が成功したのに tacit-side 判定が残存している項目（失敗Cの検出器）
MATCH (k:KnowledgeItem)-[hb:HAS_BOUNDARY]->(b:BoundaryRecord {kind:'claim'})
MATCH (k)-[:ATTEMPTED_ON]->(a:BoundaryRecord {kind:'attempt'})
WHERE b.claim = 'tacit-side' AND a.outcome = 'success'
  AND a.recorded_at > b.recorded_at
RETURN k.key AS item, 'stale-boundary' AS finding,
       b.depth_at AS depth, date(a.recorded_at) AS lapsed
UNION
// 3) 境界は動いたのに crossing が付いていない項目（監査穴）。
//    最新の claim の深度と、最新の crossing の到達深度の差が閾値を超える
MATCH (k:KnowledgeItem)-[:HAS_BOUNDARY]->(cur:BoundaryRecord {kind:'claim'})
WITH k, cur ORDER BY cur.recorded_at DESC
WITH k, head(collect(cur)) AS cur
OPTIONAL MATCH (k)-[:CROSSED]->(cr:BoundaryRecord {kind:'crossing'})
WITH k, cur, cr ORDER BY cr.recorded_at DESC
WITH k, cur, head(collect(cr)) AS cr
WITH k, cur, coalesce(cr.to_depth, 0.0) AS last_crossed
WHERE abs(cur.depth_at - last_crossed) > 0.25
RETURN k.key AS item, 'crossing-unrecorded' AS finding,
       last_crossed AS depth, date(cur.recorded_at) AS lapsed
"""

def main():
    driver = GraphDatabase.driver("bolt://localhost:7687",
                                  auth=("neo4j", "change-me"))
    with driver.session() as s:
        rows = s.run(DRIFT_QUERY).data()
    for r in rows:
        print(r)   # 各行が「世界がスキーマの主張を偽にした」出来事
    # 出力はバグ報告ではない。境界の再交渉依頼である。→6.4 の方針審査へ接続
    driver.close()

if __name__ == "__main__":
    main()
```

### 境界設計の四原則

以上の失敗型とコードから設計原則を四つに固める。原則は実装形（レコード型・クエリ・運用周期）と対で覚える。

| 原則 | 要求 | 実装形 | 破棄された場合の破綻 |
|---|---|---|---|
| 境界面原則 | 境界判定は連続値＋根拠＋有効期限 | `depth` + `BoundaryRecord{claim}` | 石化（失敗B） |
| 移動出来事原則 | 境界移動はイベント、履歴は不変 | `crossing` + `HAS_BOUNDARY` の系列 | 移動の検出不能、孤立レコードの発生 |
| 試行台帳原則 | 明示化の失敗を資産として保存 | `attempt` + `residue` | 残余の消滅、同じ穴のムジナ（失敗A/C） |
| 数値謙虚原則 | 深度は操作定義であり測定ではない | 再評価クエリの根拠欄必須 | 数値の権威化、境界問題の隠蔽 |

四つ目の原則は自己批判である。`depth = 0.35` は測定ではなく、現場の合意に基づく操作定義（operational definition）にすぎない。この区別を忘れた瞬間、連続値の面は「境界問題を解決した」という幻想になり、線よりたちが悪い。線は少なくとも嘘の形が見える。面は推定を測定の顔で保持できる。だから深度のレコードは根拠欄（`evidence`）を必須とし、根拠のない再評価は書き込みポリシーで拒否する。方針としての書き込み制御は6.4節（Policy Gatekeeper）が担当する。

### アポリア: 境界を引く者も境界の内側にいる — 残骸の記録を第2章へ引き継ぐ

最後に、この設計自体に棘を刺しておく。第一に、判定は自己参照を含む。`depth` を更新する権限を持つ者が現在の境界を定義しており、境界問題は知識の問題であると同時に統治の問題である（2.6節の分類権限の議論へ接続）。第二に、残余の記述は残余を記述した瞬間に明示知になる — ただしそれは残余が含んでいた機能（例えば音の記憶）を戻してはくれない。スティグレールが第三次保持（tertiary retention）と呼ぶ技術的保持として、残余の記録は保持であって経験の保存ではない（→2.3）。記録は残余の墓碑であり、座標標である。第三に、「ここに至らない残余」は記録できない。この限界は原理的に埋まらない。本書はこれをバグではなく設計条件として扱う（終章で詳しく扱う）。

形式化には必ず残骸がつく。本節でやったのは、その残骸を置く場所をグラフに用意し、境界の移動を残骸と同時に記録できるようにすることまでである。残余をどう保存し、削除を禁止し、変更を履歴付き上書きにするかは第2章の主題である（→2.1、→2.5）。1.6節では、この面そのものが設計者の暗黙知によって曲がっていることを問う（→1.6）。

次の1.4節では、この設計判断 — 境界は面で、面は関係の強度と文脈に載る — をグラフの辺そのものに書き込む。エッジプロパティによる「場」の動的な形式化へ進む（→1.4、→1.5）。

### 実行練習

次の三つを実際に走らせて確かめる。環境（Neo4j 5.x, Python 3.11, neo4j driver）は付録Aの docker-compose で起動したものとする。

1. **境界移動の再現と検証**。上の `CREATE` 文を `neo4j` シェルまたは Browser に貼ってグラフを作り、`detect_boundary_drift.py` を実行する。`br-0001` の `expires_at`（2026-10-01）は過ぎているので `expired-claim` が1件出るはずだ。次に `MATCH (k:KnowledgeItem {key:'bearing-sound-judgment'}) SET k.depth = 0.62 CREATE (b:BoundaryRecord {record_id:'br-0005', kind:'claim', claim:'explicit-side', depth_at:0.62, evidence:'hand: sensor roll-in', recorded_at:datetime(), expires_at: date()+duration({months:6})}) CREATE (k)-[:HAS_BOUNDARY {as_of:date()}]->(b);` を実行して「移動したのに crossing が無い」状態を作る。再実行で `crossing-unrecorded` が出ることを確かめ、`kind:'crossing'`（`to_depth: 0.62`）を一つ `CREATE` すると検出が消えることを確認する。境界の移動は、記録して初めて世界に起きたことになる。
2. **境界設計の監査**。自分の現場のスキーマかデータ辞書から10項目を選び、失敗A/B/Cの診断質問（完全性を宣言した一覧はあるか／暗黙知判定に根拠と期限があるか／明示化の失敗が記録されているか）を適用する。一つでも「はい」が出たらそれを「構造欠損」として報告書に書く。結果がゼロだった場合は、あなたのチェックリスト自体が完全性の幻想を抱いていないかを疑う。
3. **残余の記録化**。自分の現場の暗黙知候補を3つ選び、それぞれ BoundaryRecord を一つ以上 `CREATE` する（claim / attempt / residue）。`MATCH (b:BoundaryRecord {kind:'residue'}) RETURN b.text` で「語れなかった内容の断片」が読める形で残るかを確認する。さらに `MATCH (b:BoundaryRecord) WHERE b.recorded_at < datetime() - duration({years:2}) RETURN b` を実行し、2年前の境界判定が復元できるかを見る。復元できなければ、グラフは境界の過去に対して失明している — その失明自体を `residue` として `CREATE` すること。「記録の失明を記録する」が第2章への橋渡しになる。

## 1.3 西田幾多郎の「場所の論理」と野中郁次郎の「場」

1.2節までで、境界は線ではなく面であり、面は移動する、とまで来た。ではその面を載せているもの — 関係が動き知識が創発する「場所」そのものは、設計に書き込めるのか。この節は日本の哲学が本書に与える最も具体的な贈物の節である。西田幾多郎（にしだ・きたろう）の「場所の論理」は、実体より場所、主語より述語の場、存在より無を先に置く思考であり、その継承を経て野中郁次郎の知識創造理論は「場」（Ba）を導いた。SECIモデルの場は、場所の論理の知識経営への翻訳である。本節では両者の構造を分解し、設計への読み替え表を立て、実体思考がスキーマを石化させる失敗を現場例から抽出する。結論は先に書く。ノードを先に置くのをやめ、関係を先に置くこと。場はノードでも属性でもなく、関係の稠密さとして現れ、クエリで再構成される動的な場所である。その実装の全面設計が1.4節以降の主題となる。

### 西田幾多郎 — 述語が主語を包む

場所の論理の出発点は、判断の方向の反転である。論理学の初歩は「主語Sは述語Pを含む」と教える。SはPの外に立ち、Pを属性として帯びる。西田はこれを裏返す。判断の現実的な方向では、主語は述語の場に入る。「SはPである」と言うとき、Sは既にPという場所のうちに置かれ、その場所から語っている。西田は最後の論文「論理」（1945）で「一般は個別を基礎づくと同時に個別によって基礎づけられる」と書き、判断を相互基礎づけの運動として記述した。主語が述語を包むのではなく、述語（一般）の場が主語を包み、包まれた主語が再び場所を拡張する。

これは観念論の修辞ではない。判断の成立条件についての主張である。私が「これは異常音だ」と判断できるなら、私は既に「異常音」という語彙の場 — 訓練・装置・制度・合意 — のうちにおり、その場から語っている。場が判断を基礎づけ、判断が場を書き換える。1.1節の補助焦点（subsidiary awareness）を思い出せばよい。語れる内容の背後に沈んだ背景は、個人の内面ではなく、共有された場所の構造である。

工学的には、この反転はスキーマ設計の順序そのものだ。エンティティを先に定義し（User, Machine, Order）、関係を後からつなぐER設計は、主語が述語を包むという直観の写像にすぎない。しかし実運用では、エンティティの意味は参加している関係と語彙の場から決まる。同じ `Operator` ノードでも、夜班の場と朝番の場では属性の意味が違う。実体第一のオントロジーはこの差を型に石化する — 1.2節の失敗Bは実体思考の破綻としてここに再発している。処方箋は単純で、第一級要素を述語・関係の側に置くことだ。設計文書が最初に定義すべきは `(:Person)-[:OPERATES]->(:Machine)` の性質 — 有効期間・信頼度・感情価・文脈 — であり、両端のノードはその関係が後から結ぶ結節点にすぎない。

### 自己同一化の弁証法と絶対的媒介者

判断の反転を徹底すると、場は単なる容器ではいられない。西田の第二の動きは、場所が矛盾を通じて自己を分化するという記述である。絶対者（世界そのもの）は自己矛盾を生み、その矛盾を媒介する場を通じて自己を見出す。見出された自己は、以前の自己と同一でありながら、もはや同一ではない。これが自己同一化（self-identification）の弁証法で、西田の弁証法は「矛盾の自己同一化」と定義される。「一即多」もここで、参加者が場を壊さず場が多を含んで一である、という読みを得る。

そしてこの場は「絶対的媒介者」と呼ばれる。どの要素も他を媒介し、媒介された要素が再び媒介する — 媒介の媒介が止まらない場所。対象が先にあって関係が後から付くのではない。相互媒介の場所が先にあり、その内部で「主体」と「客体」が相対的に立ち上がる。両者は場所が分化した二つの極（きわみ）であって、場所より根源ではない。

設計言語へ翻訳すると三つの要請になる。

- **矛盾はバグではなく分化の駆動である**。同一の知識項目が文脈Aでは「必須」、文脈Bでは「禁止」だとする。実体思考ならこれはデータ品質エラーで、統合・抹殺される。場所の論理では、同じ項目が二つの場で自己を分化させており、観測すべき出来事である。統合してはならず、両記述（double description）を関係付きで保存する。
- **場は要素に先立つが、要素なしでは現れない**。場の属性は相互作用ログから再計算される。一方で相互作用ログは場の区切り（時間窓・区域・主題）がなければ存在しない。この循環は消去せず、循環のまま実装する — 場の定義クエリと場への寄与エッジを相互参照させる。
- **相互媒介はエッジの履歴として保持される**。仲介者Mを介してAからBへ知識が届いた事実は、AとBの直接関係より説明力を持つことが多い。媒介経路を持たないグラフは「なぜその知識がそこに到達したか」を説明できない。

原則を一文で固める。**同じノードIDで表されるものが、別の場で別の値を持つことを許容し、その差分を履歴として保存する**。IDは同一性ではなく、履歴を束ねる名簿番号にすぎない。

### 絶対無の場所 — 決まる前の場所

場所の論理は深い層を持つ。「場所」の次に問われるのは、その場所を包む場所である。aの場は非-aを含む形でaを包む。ではaと非-aを共に包む場所は何か。この追及の終端に置かれるのが「絶対無の場所」で、何ものでもなさ（無）が何ものか（有）を決める前の場所として、万有を決める「無の自覚」の場所とされる。『善の研究』（1911）が出発点とした「純粋経験」— 判断が分節化する以前、主観と客体が分かれる前の経験 — とこの主題是地続きである。分節（articulation）が起きる以前のものが「無の場所」である。

思想としては最難所だが、設計原理としては意外なほど明瞭に翻訳できる。四つ立てる。

1. **未分節の受け皿（staging area）**。分類語彙が決まる前に観測された事象は、既定の型に押し込まず raw レイヤーに保持する。語彙が成熟するまで「何ものでもないもの」として置く。1.2節の `attempt` レコードの上位版で、語彙決定の瞬間は `crossing` イベントとして記録する。
2. **null を不在ではなく余地として扱う**。`until: null` は「値がない」ではなく「この場では未決定である」と読む。未決定は決定の一つの状態であり、後の決定は null の上書きではなく、null から決定への移動として記録する。null の多義性（不明・不適用・未存在）は、「未決定」に意味を一点固定し、他二つは `not_applicable`・`absent_by_design` の各マーカーで分離する。
3. **スキーマの場所をグラフの外に開く**。絶対無は「場所の場所」の無限後退を断つ配置だが、設計では断てない。スキーマ自身も変更される場所であり、その履歴を表現するにはメタが必要で、そのメタの場所はさらに…となる（末項のアポリア）。
4. **空虚な場を保持する**。相互注意が起きない期間を「データなし」として削除せず、「場が希薄だった」という負のデータとして保持する。場の生死はこの負のデータなしには復元できない。

### 野中郁次郎の「場」 — SECIモデルの四つの場

野中郁次郎の知識創造理論は、1.1節の暗黙知/明示知の区別を、相互作用の動態として再構成した。知識変換の四類型 — 共同化（socialization: 暗黙→暗黙）、表出化（externalization: 暗黙→明示）、結合化（combination: 明示→明示）、内面化（internalization: 明示→暗黙） — を束ねるのがSECIモデルである。変換は中空の空間で起きるのではない。各変換にはその形態に適した共同の場所が必要で、それが場（Ba）である。西田の学統の哲学者竹内良知の中介を経て、場は「知識の創発・共有・増幅が行われる、共有された時間・空間・関係の文脈」として導入された。物理次元（同じ場所）・精神次元（同じ意図・世界観）・仮想次元（virtual: ネットワーク）の三層を持つ点が重要で、会議室（物理）だけでは場は成立しない。

SECIの四環と四つの場の対応を、本書の設計語彙へ翻訳して並べる。

| SECI環 | 場（Ba） | 場の実在形（実務例） | 工学的対応（本書での置き場所） |
|---|---|---|---|
| 共同化 | 創発場（originating Ba） | 師徒の同席、工場での実演 | 共在ログ: 同一時刻・同一区域のテレメトリと在席情報（→1.5） |
| 表出化 | 対話場（dialoguing Ba） | 一対一の対話、少人数の振り返り | 対話グラフ: 発話→語彙提案→却下→合意の `attempt` 列（→1.2） |
| 結合化 | 活動場（systemizing Ba） | 設計レビュー、文書統合 | マスター語彙への統合と差分履歴（→2.4、→2.5） |
| 内面化 | ネットワーク場（exercising Ba） | 配布された手順の反復実践 | Action提案と実行ログによる技能の再身体化（→7.3、→8.6） |

SECIは一度巡回して終わらない。創発場→対話場→活動場→ネットワーク場→より大きな創発場、と場の階層が拡がりながら螺旋を回る。設計上の含みは明確で、**知識パイプラインの各環は異なる場を必要とし、一つの場ですべてをまかなおうとすると環は途切れる**。文書（活動場の成果物）を配っても対話場が再建されなければ内面化は起きない — これは1.2節の失敗C（過剰形式化の強制）の別側面でもある。

場の設計で最も多い失敗を先に挙げておく。**失敗D: 場=会議室・チャネルの石化**。大手製造業の知識管理導入で、部門ごとにコラボレーションサーバ（ネットワーク場の名の下に）が設置された。物理次元・仮想次元は確保された。しかし精神次元 — 何に共に注意を向け、何を問い続けてよいという共有された意図 — を支える仕組みがなかった。三か月で投稿は在庫報告の転記場と化し、知識の創発はゼロだった。監査ログが残っていたのは皮肉で、投稿の相関を調べたところ、唯一の価値ある記事は「別の現場で起きた対話の要約」だった。場は空間の名前ではなく、関係の稠密さと相互注意の状態である — この判断をデータで検証するのが次節以降である。

### グラフ理論との接点 — ノードより関係を先に置く（関係的第一性）

ここからが本章の工学的心臓部である。「関係的第一性（relationship-first）」という語で、四つの形式化伝統を並べる。

| 形式化の伝統 | 第一級の要素 | 関係の扱い | 場所の論理との距離 |
|---|---|---|---|
| 関係モデル（RDBMS） | テーブル（実体の集合） | 外部キーの間接参照。関係に属性を置けない | 遠い。関係は接合（join）の副産物 |
| RDF | 述語（predicate）＝矢印 | 関係が語彙の主役。時・文脈を載せにくく reification が必要（→2.5） | 近い。述語の第一性がそのまま実装されている |
| 属性グラフ（Neo4j） | ノードとエッジが対等、エッジも向きを持つ | 関係にプロパティを持てる。プロパティが「場の厚み」になる | 最も近い。ただし運用はノード中心に堕ちる |
| 圏の力学（category dynamics） | 対象より射（morphism） | 対象は恒等射として射から定義される | 数学的に近い。名前は射から後で決まる |

RDFの述語第一性、属性グラフのエッジが向きを持つという事実、圏の力学の「対象は恒等射にすぎない」— 三つは同じ方向を指す。**名前は関係から後で決まる**。ER設計が世界を正しく写すのは、述語が主語を包む方向が無視できる場合だけだ。Neo4j の現場運用では設計文書の大半がラベル一覧で始まり、関係は後から描かれる。この順序こそが場をスキーマに石化させる。転換は失敗から見るほうが速い。

**失敗E: 装置中心オントロジー**。ある製紙工場の保全グラフは `Machine`, `Part`, `Failure`, `Procedure` の四ラベルで始まり、`HAS_PART`, `EXPERIENCED` の静的な分類関係で満たされた。三年後にグラフが答えられなくなった問いは「昨夜、誰が誰に教え、その知識はどの手順書の改訂に反映されたか」だった。`Person` ノードは存在した。しかし `TAUGHT`, `PROPOSED_REVISION` のような相互媒介のエッジは一度も作られず、教え合いはチャットに流れ、グラフは外部から届いた成果物（更新された手順書）だけを持っていた。グラフは場の沈殿物しか保存せず、場そのものを失っていた。実体を先に置く設計では、関係は実体間を結ぶ副次的な線にすぎず、線には時間・信頼・感情を載せる場所がない。

**失敗F: エッジは作ったが属性がない**。別の工場では `KNOWS`, `COLLABORATES` を作っていた。しかし全エッジがブール的（有るか無いか）で、`since` も `confidence` も `context` もない。「誰と誰が組むと故障が止まるか」を調べようにも、関係の生死も強度も質も記録されていない。エッジを引くことと関係を第一級にすることは別で、エッジが時間と文脈を持たないとき、それはノードの属性を少し伸ばしただけの実体思考の残党である。

失敗E/Fから導かれる設計判断は一つ — **関係は名簿（ノード）に先立ち、関係はプロパティ（有効期間・信頼度・感情価・文脈）を持つ**。1.2節末尾の予告どおりであり、プロパティ群の全面設計は1.4節に譲る。本節は場付き関係の最小スニペットだけを置く。

```cypher
// 1.3 場付き関係の最小実装。
// 哲学的意図（西田）: 述語が主語を包む。同じ2点間に、場の数だけ関係が立つ。
// 同一の「AがBを教える」を一本のエッジに統合しない。統合は場の抹殺である。
CREATE CONSTRAINT person_key IF NOT EXISTS
  FOR (p:Person) REQUIRE p.key IS UNIQUE;

CREATE (tanaka:Person {key: 'tanaka', role: 'veteran'});
CREATE (sato:Person   {key: 'sato',   role: 'novice'});

// 同一端点間に二つの場の TEACH エッジ。context は場の精神次元の最小記述。
// 哲学注（一即多）: 「AはBを教える」は単称命題ではない。場の数だけ判断がある。
CREATE (tanaka)-[t1:TEACH {
  context: 'night-shift-hall',            // 創発場: 実演・同席（共同化）
  since: date('2025-04-01'), until: null, // until=null は未決定（無の場所）
  confidence: 0.85, affect: 0.6,          // 信頼度・感情価（定義は→1.4）
  mediated_by: 'demo-at-machine'          // 絶対的媒介者: 媒介経路の記録
}]->(sato);

CREATE (tanaka)-[t2:TEACH {
  context: 'kaizen-doc-review',           // 活動場: 文書の結合化
  since: date('2026-02-03'), until: null,
  confidence: 0.40, affect: -0.2,
  mediated_by: 'procedure-rev14'
}]->(sato);

// 二つのエッジは統合しない。confidence の差が場の厚みの測定値になる。
MATCH (a:Person {key: 'tanaka'})-[r:TEACH]->(b:Person {key: 'sato'})
RETURN r.context, r.confidence, r.affect ORDER BY r.confidence DESC;
```

### 場を測る — 稠密度の計算と場の生死

場の運用を感覚に渡すと、場はいつの間にか死んでいる（失敗D）。だから場は数値で監視する。ただし数値は場そのものではなく、稠密さの操作定義（operational definition）にすぎない — この区別は1.2節の数値謙虚原則のまま保つ。

稠密度の定義はこうだ。時間窓と区域で区切られた要素集合 V（人・機械・語彙・記録）と、その窓内で観測された場付きエッジ集合 E に対して、

> density(Ba) = |E| / (|V| choose 2) × avg(confidence)

第一項は関係の量、第二項は関係の質（信頼）である。実務では分母の組合せ数が爆発するので、代わりに次数分布や多重エッジの比率を使うことが多い。

```python
# ba_density.py — 場の稠密度系列から生死イベントを復元する。
# Neo4j 5.x + neo4j driver（付録A）。
# 哲学的意図: 場はノードではなく関係の稠密さとして現れる（場所の論理の測定形）。
# 場は「作る」ものではなく、稠密さを測り、希薄化を出来事として記録するだけだ。
from neo4j import GraphDatabase
from datetime import datetime, timedelta

BA_WINDOW = """
// 時間窓時点で生存中の TEACH/COLLABORATE エッジで稠密度を計算する。
// 哲学注（SECI）: 対話場は発話の量ではなく相互参照の密度で生きている。
MATCH (a:Person)-[r:TEACH|COLLABORATE]->(b:Person)
WHERE r.since >= date($from)
  AND (r.until IS NULL OR r.until >= date($from))
  AND r.context = $context
WITH count(DISTINCT startNode(r)) + count(DISTINCT endNode(r)) AS n,
     count(r) AS e, avg(r.confidence) AS q
RETURN CASE WHEN n < 2 THEN 0.0
            ELSE toFloat(e) / (n * (n - 1) / 2.0) * q END AS density
"""

def track(driver, context, start, weeks=12, thresh=0.05):
    births, deaths, prev = [], [], None
    for i in range(weeks):
        w0 = start + timedelta(weeks=i)
        with driver.session() as s:
            rows = s.run(BA_WINDOW, context=context, from_=w0.date()).data()
        d = rows[0]["density"] if rows else 0.0
        # 哲学注（絶対無）: 稠密ゼロの窓を削除しない。場の休眠という負のデータ。
        if prev is not None:
            if prev < thresh <= d: births.append((w0.date(), round(d, 4)))
            if prev >= thresh > d: deaths.append((w0.date(), round(d, 4)))
        print(w0.date(), round(d, 4))
        prev = d
    return births, deaths

if __name__ == "__main__":
    driver = GraphDatabase.driver("bolt://localhost:7687",
                                  auth=("neo4j", "change-me"))
    b, d = track(driver, "night-shift-hall", datetime(2026, 1, 5))
    print("births:", b, "deaths:", d)
    # births/deaths は BaLifecycle イベントノードとして書き込む（→1.4）
    driver.close()
```

密度が閾値を下回った窓を「死んだ窓」として記録するだけで、場の運用は半分成立する。場の保存を試みる多くの試みが失敗するのは、場の構造でなく成果物（記事・スライド）を保存しているからで、成果物の在庫は場の生死と無関係である — 失敗Dの監査ログがそれを証明していた。生死の記録は、1.5節の「場をクエリで再現する」の準備でもある。

### 設計判断 — 「場」をグラフのどこに置くか

この節の設計判断を一覧に固める。三択の比較は、そのまま1.4節のスキーマ判断の入口になる。

| 配置 | 実装形 | 得られるもの | 失われるもの | 採否 |
|---|---|---|---|---|
| 場=ノード属性 | `Person.context: string` | 単純・高速 | 場の生死・多重所属を保存できない | 棄却 |
| 場=第一級ノード | `(:Ba)-[:HOSTS]->(…)` | 管理画面上の可視性 | 場が実体化し石化する（失敗Dの制度化） | 補助のみ（イベントの容器） |
| 場=エッジプロパティ＋クエリ | `r.context / r.since / r.confidence` | 関係が時間・質・文脈を持つ。場は窓で再構成される | クエリ負荷、定義の分散 | **採用（→1.4・1.5）** |

場をノード化する案が捨てきれない理由は、イベントの保存先が必要なだけだ。`BaLifecycle {event: birth|dormant|death}` を紐づける場所として Baノードは「場の出生届・墓標」という限定的役割で残す。場そのものはそこに置かない — 場は稠密度の系列であり、墓標はその系列の注釈である。

### アポリア: 場所の場所を形式化できない — 1.4・1.6節への橋

この設計にも棘を刺しておく。第一に、無限後退である。場をエッジプロパティで形式化すると、では `context` や `confidence` という語彙を共有している場は何か、と問いが次に開く。スキーマ自身の場所 — 設計者が既に立っていた場所 — はグラフの中に書けない。西田が絶対無を「場所の場所」の追及の終端に置いたのに対し、設計では終端を置かずメタレベルを延ばす（2.5の reification、2.6の分類権限がここで機能する）。絶対無はノードではない。形式化の体系が自らの条件として引き受ける空白である。

第二に、稠密度は相互注意を測らない。数は場の運動を写すが、精神次元 — なぜこの人はこの窓にいるのか、という意図 — はログに残らない。失敗Dが証明したのはこの次元の欠落と、その欠落の測定不能さである。第三に、測定された場は測定される者たちの行動を変える（測定効果）。場の生死がダッシュボードに出た瞬間から、人々は密度のために書き始める。この歪みは消えない。だから密度は運用の判断材料になっても、場の定義にはなれない。

次節はいよいよ本章の実装本体に入る。関係の第一性をエッジプロパティという器に全面的に書き込む — 信頼度・有効期間・感情価・文脈スコア、そして `confidence × context_score` による「形式化の辺境」の連続化（→1.4）。その器にテレメトリと感情推定を載せるのが1.5節である。そして1.6節では、この節全体で実行した実体思考の放棄が、スキーマ設計者自身の暗黙知をどこに残してしまうかを問う（→1.6）。

### 実行練習

環境は付録A（Neo4j 5.x + Python 3.11 + neo4j driver）で起動済みのものとする。

1. **同一端点・複数場の検証**。上の Cypher を `cypher-shell` に貼り、`MATCH (a:Person {key:'tanaka'})-[r:TEACH]->(b:Person {key:'sato'}) RETURN count(r), collect(r.context)` を実行する。`count(r)` が 2 で、二本の関係が統合されていないことを確かめる。次に `MERGE (a:Person {key:'tanaka'})-[t:TEACH]->(b:Person {key:'sato'}) SET t.confidence = 0.5` を実行して「実体思考的な統合」を再現し、`MATCH` で残ったエッジの本数と `context` 値の消失を数える。この操作が場の抹殺であることを、消えた context の個数で報告書に書く。
2. **場の生死の復元と休眠の検出**。`ba_density.py` を上のグラフで走らせる。`MATCH ()-[t:TEACH {context:'night-shift-hall'}]->() SET t.until = date('2026-03-01')` で「死」を模擬し、稠密度系列が閾値 0.05 を横切る窓で `deaths` が出ることを確認する。次にエッジが1本もない窓を造り、稠密度ゼロが「休眠」か「死亡」か現行コードでは区別できないことを確かめる。区別できないので、どのプロパティ（例: `last_observed_at`）を1つ加えれば区別できるかを考え、クエリを直して再実行する。
3. **場の四類型の棚卸しと空虚化テスト**。自分の組織の実際の協働の場を5つ選び、SECI表の四類型（創発・対話・活動・ネットワーク）に分類し、それぞれに欠けている次元（物理/精神/仮想）を書く。精神次元が欠けた失敗D型の場を最低1つ見つけ、`CREATE (:Ba {key:'ba-audit-01', name:'…', seci:'dialoguing', missing_dimension:'mental', note:'これは墓標であり場ではない'})` として記録する。最後に `MATCH (b:Ba) RETURN b` を実行し、墓標以外に場の証拠が何も無い画面 — 失敗Dの構造そのもの — を自分の目で確認する。その空虚さ自体が、1.4節が埋めるべき穴の正確な地図である。

## 1.4 コンテキスト・グラフ — 「場」の動的エッジ・プロパティによる形式化

1.3節で引き受けた関係的第一性 — ノードより関係を先に置く姿勢 — を、この節は実装する。野中郁次郎が語った「場（ba）」の現実とは、人が集まる場所ではなく、時間とともに性質を変える関係の模様のことである。同じ「村田は田中の判断を信頼する」という関係も、昨日と今日では同一の関係ではない。静的オントロジー — クラスも関係も一度決めてしまえば変わらない構造 — は、このような関係をとらえられない。この難点への工学的な答えが、コンテキスト・グラフ — 信頼度・有効期間・感情価・文脈スコアをエッジそのものに載せる属性付きグラフ（attributed graph） — である。本節ではグラフの存在論を裏付け — なぜ性質がエッジに載らなければならないのか — 四つのエッジ・プロパティの設計原理を立て、1.2節で「線ではなく面」とした境界を `confidence` × `context_score` の積で連続値にする。最後に実際に動く Cypher と Python を置く。

### 静的オントロジーは「いま・ここ」を捉えられない

静的オントロジーの標準形 — クラス図に不変の関連線を引く — では、関係の性質は上書きされる。「村田 → 田中」の `TRUSTS` の `confidence: 0.9` が誤報の累積で 0.6 になったとき、値を上書きする設計では、監査の日に「なぜあの夜、判断が自動発火しなかったのか」を調べようにもシステムは現在の値しか答えられない。0.9 だった過去は存在しなかったことになる。関係は世界について主張するのではなく、主張の現在値を保管する容器になっていた。

関係の性質が時間とともに変わるのは常態である。信頼の増減、交代での妥当範囲の伸縮、感情価の反転、工程が変われば有効性が変わる場依存。注目すべきはいずれも「関係の消滅と再作成」ではないことだ。村田と田中の関係は切断して張り替えたのではなく、同一の継続体（continuant）として性質を変えた。正解は、関係に時間軸つきの性質を持たせ、性質変更を出来事として記録する設計である。

では工学的に何をするのか。答えは三行である。①エッジを「関係の事実」ではなく「関係についての主張」として型付ける。②主張には必ず `valid_from` / `valid_to` を付ける。③性質の変更は UPDATE で上書きせず、旧エッジを閉じて新エッジを開く出来事として書く。この三行の土台は、次に述べる関係第一性である。

### 関係の第一性 — 「場」はノードの名前ではなくエッジの模様

1.3節で見た西田幾多郎の「場所の論理」— 場所（basho）はものを内包する容器ではなく、関係の成立を可能にする者だった。野中の「場」も同じ構造を持つ — 四つの場はいずれも、個人の属性ではなく個人**あいだ**の共有された文脈である。工学的に「場」をどこに置くのか。ノードに `ba: 活動場` と刻むのは、場を事物の属性に還元し、容器のメタファーに戻す誤りである。

場はクエリである。ある時刻・区域・課題で同時に有効だった全関係のスライス（slice）が場であり、スライスを切る操作が照会である。有効性はエッジ側に置かねばならない。ノード側では関係の寿命と事物の寿命が混線する — 村田は今日もいて、変わったのは関係の方だからだ。骨格は三者分業になる。ノードは境界の属性を持たない「項」（→1.2節）、エッジは主張の一次保存単位として信頼度・期間・感情価・出所を担い、場は有効な全エッジを返すクエリである。

### エッジ・プロパティの設計原理 — 信頼度・有効期間・感情価・文脈スコア

四つの標準プロパティは四つの設計原理から導かれる。

**原理1: 性質は主張の性質であり、事物の性質ではない。** `confidence: 0.55` は「世界が 0.55 である」という事実ではなく、証拠がそこまでの信望を支持しているという記録である。必ず `provenance`（出所）と組で持つ — 無名の数値は静的オントロジーの再発である。

**原理2: 時間は構造でなければならない。** `valid_from`/`valid_to` を欠いたエッジは「常に真」と自己主張しているのと同じ — 1.2節の境界の石化とはこの状態のことである。有効期間を持たせるとは、すべての主張に「いつまで真だったか」という死の予定を書き込むことだ。

**原理3: スコアは関数で再計算する。** `context_score` は焼き込み定数ではなく、場の観測から再計算できる純関数の値でなければならない。手で入れて更新されないスコアはやがて飾りになる。

**原理4: 積は判定ではない。** 積は「形式化してよいか」の命令ではなく、地図上の位置を示す指数である。数値の権威化が後述の失敗三型の共通項だ。

実務で合意すべきは維持規則である。

| プロパティ | 意味 | 初期値の出所 | 維持規則 | 欠いた場合の破綻 |
|---|---|---|---|---|
| `confidence` (0.0–1.0) | 主張への信望度 | 初出の主張 | 主張イベントでのみ更新 | 監査可能性の喪失 |
| `valid_from`/`valid_to` | 主張の有効区間 | 観測開始時刻 | 置換時は必ず閉じ `end_reason` | 陳腐化関係が現行として発火 |
| `valence` (−1.0〜+1.0) | 感情価の推定値 | センサー・申告・推定 | 用途限定の記録（後述） | 感情情報が匿名で推論に混入 |
| `context_score` | 現況の場への適合度 | 再計算関数 | 手書き禁止、常に再計算 | 場を離れて意味が漂流する |

時間つき関係のモデル化の択は四つある。プロパティ上書きは変更履歴を全喪失し監査不能の温床（失敗A）、削除・再作成は時刻照会できても版本の系譜が不明、reification（関係のノード化）は履歴を残すが肥大を招く（失敗C）、エッジ・プロパティ＋有効区間は版本の運用管理をコストに残す。本書は最後に採用する。

### 境界の面化 — `confidence` × `context_score` が辺境を連続値にする

1.2節で境界は線ではなく面だと立てた。その数値実装 — 形式化可能性の現在値を積 `formalizability(e,t,z) = confidence(e,t) × context_score(e,t,z)` で定義する。積を選ぶのは、二因子が**どちらも必要条件**だからである。誰も信じていない関係（`confidence = 0`）はどんなに現在の場と適合しても形式化の材料にならず、しつこく信じられた関係もいまの場と適合しなければここで形式化する対象ではない。和なら片方の 0 を他方が救うが、積は救わない — 「境界は片脚で立たない」という1.2節の観察が、演算子の選択として実装されている。

積の値は三帯に読める — `CORE`（≥0.7、形式化の中心部）・ `FRONTIER`（0.4〜0.7、辺境）・ `BORDERLAND`（<0.4、命名自体が揺れる地帯）。ただし帯は分類ではなく表示であり、判定は常に人間が残す。閾値で自動振り分けした瞬間に連続の面は三値の線に戻る（1.2節の「不明の垃圾桶化」の再発）。第4章の再検証でも第7章の行動優先度でも、判定権は移動しない。

`context_score` は次の純関数である（standalone 実行可）。

```python
"""ch01_s4_context.py — context_score 再計算。哲学的意図: 場適合度は関係の
生得的属性ではない — 関係は孤立した個としてではなく場（時刻×区域×課題）の
なかにのみ在る。ゆえにスコアは場から再計算される純関数でなければならない（原理3）。"""
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Observation:
    observed_at: float   # 観測時刻 (epoch)
    zone: str            # 区域
    task: str            # 課題
    channel: str         # telemetry / human / model

@dataclass
class ContextEdge:
    confidence: float
    observations: list[Observation] = field(default_factory=list)

HALF_LIFE = 30 * 86400  # 証拠の半減期30日: 再び観測されなければ場は減衰
                        # する（保存→2.2節と忘却は両立する）
CHANNEL_WEIGHT = {"telemetry": 1.0, "human": 0.7, "model": 0.4}
# 認識チャネルの重み: 計測は証言より確かで生成文は計測より流動的である
# （尤度は正統性ではない →5.3節）。

def recency(now: float, observed_at: float) -> float:
    return 0.5 ** ((now - observed_at) / HALF_LIFE)

def context_score(edge: ContextEdge, now: float, zone: str, task: str) -> float:
    """いま・ここの場への適合度。場を離れると 0 に収束する。"""
    total = 0.0
    for ob in edge.observations:
        zone_fit = 1.0 if ob.zone == zone else 0.0
        task_fit = 1.0 if ob.task == task else 0.5
        total += zone_fit * task_fit * CHANNEL_WEIGHT[ob.channel] \
                 * recency(now, ob.observed_at)
    return min(1.0, total)

def band(confidence: float, score: float) -> str:
    p = confidence * score   # 境界の面化。判定ではなく地図上の位置。
    if p >= 0.7: return "CORE"
    if p >= 0.4: return "FRONTIER"
    return "BORDERLAND"

if __name__ == "__main__":
    now = 1_762_483_200.0  # 2026-11-07T00:00:00Z。場は設計されたスナップショット
    e = ContextEdge(confidence=0.55, observations=[
        Observation(now -   2*86400, "line-3", "torque-check", "telemetry"),
        Observation(now -   9*86400, "line-3", "torque-check", "human"),
        Observation(now - 100*86400, "line-2", "patrol",       "telemetry"),
    ])
    for zone, task in [("line-3", "torque-check"), ("line-2", "patrol"), ("line-9", "x")]:
        s = context_score(e, now, zone, task)
        print(f"場 {zone}/{task}: score={s:.3f} formalizability={0.55*s:.3f} band={band(0.55, s)}")
```

同一エッジが場ごとに別々の辺境位置を取る。「line-3/torque-check」では FRONTIER、「line-2/patrol」では100日前の証拠の減衰残骸で BORDERLAND、「line-9」では 0 — 固定線のモデルはこの三値を一度に表せない。

### 実装 — 版本つきエッジと場スナップショットの Cypher

制約とラベルの全面設計は1.5節に譲り、ここでも「主張としてのエッジ」の最小骨格のみ置く（依存環境は付録Aに従う）。

```bash
# 下地（付録A）
docker compose up -d neo4j
cypher-shell -u neo4j -p execphil -f book/code/ch01_s4_schema.cypher
python book/code/ch01_s4_context.py
```

```cypher
// ch01_s4_schema.cypher — 1.4 最小スキーマ。哲学的意図: 場はノードの名前
// ではなくエッジの模様（関係第一性）。KnowledgeItem に tacit/explicit 属性が
// 無いこと自体が 1.2節の結論（境界は本性ではなく主張の現在値）の実装。
CREATE CONSTRAINT knowledge_item_key IF NOT EXISTS
  FOR (k:KnowledgeItem) REQUIRE k.key IS UNIQUE;
CREATE CONSTRAINT context_edge_key IF NOT EXISTS
  FOR ()-[r:INFLUENCES]-() REQUIRE r.edge_id IS UNIQUE;
```

「信頼が変わった」出来事を、上書きではなく旧エッジのクローズ＋新エッジの開設として書く。

```cypher
// 性質の変更 = 版本の切替: 古い主張は破棄されず、有効区間を閉じられて
// 履歴に残る（止揚の実装 →2.2節）。
MATCH (a:KnowledgeItem {key: 'operator.murata'})-[r:INFLUENCES {kind: 'trust'}]->
      (b:KnowledgeItem {key: 'policy.torque-check'})
WHERE r.valid_to IS NULL
SET r.valid_to = datetime('2026-11-07T09:00+09:00'), r.end_reason = 'SUPERSEDED'
WITH a, b
CREATE (a)-[n:INFLUENCES {
  edge_id: 'e-001b', kind: 'trust',
  confidence: 0.55,          // 主張への信望であって事実ではない（原理1）
  context_score: null,       // 手書き禁止・関数で再計算（原理3）
  valence: -0.30,            // 測定推定値。判断でも評価でもない
  valid_from: datetime('2026-11-07T09:00+09:00'),
  valid_to: null,            // 現行版のみ valid_to IS NULL
  evidence: '申し送り証言+テレメトリ相関',
  provenance: 'human:tanaka' // 誰の主張か。無名の数値を作らない
}]->(b);
```

この切替は単一の原子的出来事である。旧主張が閉じないうちに新主張が開く瞬間 — 相反する二つの「現在」が世界を同時に支配する時刻 — を作ってはならない。これが削除・再作成モデルとの決定的な差である。

場の再現 — 1.3節で予告した「同一時刻の全関係」を集めるクエリがこれで、場はここで辞書ではなく演算になる。

```cypher
// 場スナップショット（field snapshot）: 時刻 $at・区域 $zone で有効な全関係。
// 場はノードではなくクエリである。valid_to IS NULL が「現在」を、
// valid_from <= t < valid_to が「過去の場」を同一文法で取り出す — 過去は
// 削除ではなく区間により保存される。
WITH datetime($at) AS t
MATCH (a:KnowledgeItem)-[r:INFLUENCES]->(b:KnowledgeItem)
WHERE r.valid_from <= t AND (r.valid_to IS NULL OR r.valid_to > t)
  AND (a.zone = $zone OR b.zone = $zone)
WITH a, b, r, r.confidence * coalesce(r.context_score, 0) AS formalizability
     // 焼き込み値は表示キャッシュ（通常 null; python が再計算値を注入）
RETURN a.key AS from_key, b.key AS to_key, r.kind AS relation,
       round(formalizability, 3) AS formalizability,
       CASE WHEN formalizability >= 0.7 THEN 'CORE'
            WHEN formalizability >= 0.4 THEN 'FRONTIER'
            ELSE 'BORDERLAND' END AS band  // 帯は表示。判定は人が残す
ORDER BY formalizability ASC
LIMIT 25;
```

感情価 `valence` には倫理の約束を添える。感情推定値の保存は監視装置になりうるため三則をポリシーとして強制する — ①用途限定（人事評価へ流さない）、②粗い粒度（個人でなく区域分布）、③本人の閲覧権。機械的執行は6.4節、反証機会の付与は8.4節。

### 現場の失敗三型 — コンテキスト・グラフはこう壊れる

このスキーマは導入しただけでは壊れる。実際に見る三型を記す。

**失敗A: 信頼を事実として上書きした**。保全システムが `confidence` を月次バッチで上書き更新していた。半年後の異常解析で判断根拠を復元しようとしても、バッチ以前の値はどの時点にも存在せず、調査は「判断は正しかったが根拠を証明できない」で打ち切られた。構造欠損は UPDATE 一本で歴史を抹消したことである。策は版本つきエッジと `provenance` である。

**失敗B: 有効期間を閉じる運用がなかった**。`valid_to` 列を用意しながら交代時のクローズ操作を業務へ組み込まなかった現場では、「高温→冷却起動」の旧関係が三か月間現行版として走り、区域移設済み設備へ古い冷却命令が飛んだ。エッジは正しく、場が死んでいた。`valid_to` はカラムではなく約束である。策はクローズ業務の組込みと、未観測の現行エッジを FRONTIER へ自動降格する定期レポートだ（→1.5節のテレメトリ）。

**失敗C: reification 爆発**。「あらゆる関係に性質を付けるべき」という正義感で全関係を主張ノード＋リンクに展開した組織は、ノード数を五倍にし、クエリを読める書き手を消し、二年でグラフは参照専用化されて放置された。エッジ・プロパティで足りる間に「将来の汎用性」へ投資した判断の失敗である。第一級化は「主張への主張」が現れたときだけ行う（→2.5節）。

| 失敗型 | 構造欠損 | 本節の対策 |
|---|---|---|
| A 上書きによる現在値化 | 主張が事実に化ける | 版本チェーン + `provenance` |
| B クローズ運用の欠如 | 場が死にエッジが生き残る | 閉鎖業務の組込み + 未観測レポート |
| C 汎用性への過剰投資 | 器が中身を溺死させる | エッジ・プロパティ既定、第一級化は事後 |

### 残るアポリア — 数値は何を測っているのか

正直に書いておく。`formalizability` は世界に元からある量（quantity）を測定していない。信望・適合・観測頻度という操作可能量の合成値であり、「形式化に足るもの」を担保するのは重み・半減期・閾値という設計判断の妥当性が保たれている間だけである。その妥当性こそが1.2節の境界線そのもので、グラフ内部には置けない — 設計者の暗黙知として外部に残る（→1.6節）。アポリアを閉じる代わりに、スコアを関数として再計算可能に保ち、閾値を第4章のテストで更新可能に保つ — 解けない問題を設計条件として扱うとはそこから始まる。問い直しの機構は、8.5節の対話プロトコルの原型になる。

### 実行練習

1. **場を三つ切る。** schema を適用して `KnowledgeItem` を3件・版本違い `INFLUENCES` を2本作り、場スナップショットを `datetime('2026-11-01T00:00+09:00')` と現在時刻で2回走らせよ。同一ノード組が両方の場で別々の `band` に落ちることを数値で確認し、効いている `valid_from`/`valid_to` を説明できること。
2. **半減期で証拠を腐らせる。** `HALF_LIFE` を 2日と100日に変え、`("line-2","patrol")` の場の `band` の動きを観察せよ。半減期2日なら9日前の人証言は 0.5 の何乗の重みになるか手計算し、実測値と照合する。観測の再取得頻度と半減期を揃えるべき理由を5行で書け。
3. **失敗Bを機械検出する Cypher を書く。** 「`valid_to IS NULL` かつ `valid_from` が30日より前で後続の版本が無い現行エッジ」を列挙するクエリを書き、古いエッジを1本注入して実際に1件ヒットさせよ。この運用がなぜ「削除」ではなく「降格」なのかを3行で説明せよ。

## 1.5 Cypher実践 — 状況・制約・感情・現場環境テレメトリのノード定義

1.4節で「場はノードではなくクエリである」と立て、四つのエッジ・プロパティを定義した。しかしクエリを走らせるには、照会されるもの — ノードとラベルと制約 — が先になければならない。この節はそこを埋める実装節である。作業者の状況（Situation）、工程制約（Constraint）、感情推定（EmotionEstimate）、そして温度・振動・音声レベルといった現場環境テレメトリ（telemetry）を、同一のグラフ上に載せる。載せただけでは意味がない。同一時刻・同一区域の全要素を一度に集めるクエリで「場」が再現され、高頻度なのに明示化されていない関係を検出するクエリで暗黙知の痕跡（trace）が可視化されて初めて、グラフはポランニーの問題に工学的に関与する。スキーマは存在論の宣言であり、クエリは認識論の操作である — この節はその二つを Neo4j 5.x の Cypher で動く形に置く（依存環境は付録A、`docker compose` で Neo4j を起動し、`cypher-shell` と Python から接続できる状態を前提とする）。

### 最初に読む哲学者 — ノードラベルは世界への主張である

コードに入る前に、この節の設計判断を貫く一本の筋を置いておく。ラベル（label）は単なる分類タグではない。「このグラフには Situation という種類のものが存在する」という存在論的宣言（ontological commitment）である。宣言だから、正しいか誤っているかではなく、何を含め何を排除したかでのみ評価される。Situation を作ってしまえば、状況はそのラベルの定義域内のものだけが存在する — 現場にはラベルを待たずに現れ、ラベルを待たずに消えていく事象が溢れていることを、スキーマは沈黙のうちに否定する（→1.2節の分節化の境界問題、→1.6節の「グラフに乗らないもの」）。

したがってラベル体系の設計規則は「網羅」ではなく「主張の層の分離」に置かれる。観測されたもの、推定されたもの、申告されたもの、合意されたものは、認識の階層が異なる（→第4章の検証可能性）。これらを同一ラベルに混ぜた瞬間、「測定値」と「作業者の申告」が同じ信頼度で推論に混入する。本書のラベル体系は四つの層 — 項（ thing ）・出来事（occurrence）・主張（claim）・規則（rule） — をラベル名で明示し、混線をスキーマで防ぐ。ポランニーの「語れるよりも多くを知る」は、明示化の失敗を仕様として組み込めという工学的帰結を1.1節で残した（→第1.1節）。仕様として組み込むとは、スキーマに「ここは推定です」「ここは人間が承認しました」と書く場所を残すことである。感情推定のエッジが自分の `provenance` に `model:` を刻むのと同じ誠実さを、ラベル命名そのものに刻む。

では工学的に何をするのか。①ラベルで主張の層を分ける。②層ごとにキー制約と型制約で境界を守る。③生のテレメトリは窓集計までをグラフに載せ、生データは生データの器に置く。④「場」を取り出すクエリと「暗黙知の痕跡」を取り出すクエリを、設計物としてリポジトリに保管する。以下、この四つを順に実行可能な形で置く。

### スキーマ — ノードラベル体系と CREATE CONSTRAINT

まず全ラベルの宣言と制約（constraint）を一本のファイルにまとめる。`IF NOT EXISTS` を全stmtに付けるのは、スキーマの再適用を無傷にしておくためだ。スキーマは一度きりの宣言ではなく、継続的に再適用される主張である（→2.5節の版管理の予告）。

```cypher
// ch01_s5_schema.cypher — コンテキスト・グラフのスキーマ全面定義（Neo4j 5.x）。
// 哲学的意図: ラベルは分類タグではなく存在論的宣言。
// 「項/出来事/主張/規則」の四層をラベル名で分離し、認識の階層の混線を
// スキーマで防ぐ（上の設計規則①）。

// --- 層1: 項 — 識別子を持つ「項」。それ自体は主張を運ばない ---
CREATE CONSTRAINT zone_key IF NOT EXISTS
  FOR (z:Zone) REQUIRE z.zone_id IS UNIQUE;
CREATE CONSTRAINT operator_key IF NOT EXISTS
  FOR (p:Operator) REQUIRE p.operator_ref IS UNIQUE;
CREATE CONSTRAINT equipment_key IF NOT EXISTS
  FOR (q:Equipment) REQUIRE q.equipment_id IS UNIQUE;
CREATE CONSTRAINT knowledge_item_key IF NOT EXISTS
  FOR (k:KnowledgeItem) REQUIRE k.key IS UNIQUE;
// KnowledgeItem に explicit/tacit の区別属性を置かないこと自体が1.2節の
// 結論の実装である: 明示/暗黙は事物の本性ではなく、明示化の試行の現在値だ。
// INFLUENCES エッジの有無と confidence がその現在値を担う（→1.4節）。

// --- 層2: 出来事 — 時系列で生じたもの ---
CREATE CONSTRAINT shift_key IF NOT EXISTS
  FOR (s:Shift) REQUIRE s.shift_id IS UNIQUE;
CREATE CONSTRAINT stream_key IF NOT EXISTS
  FOR (t:TelemetryStream) REQUIRE t.stream_id IS UNIQUE;
CREATE CONSTRAINT observation_key IF NOT EXISTS
  FOR (o:Observation) REQUIRE o.obs_id IS UNIQUE;
CREATE CONSTRAINT manual_action_key IF NOT EXISTS
  FOR (m:ManualAction) REQUIRE m.action_id IS UNIQUE;

// --- 層3: 主張 — 世界について述べるノード。必ず出所を持つ ---
CREATE CONSTRAINT situation_key IF NOT EXISTS
  FOR (si:Situation) REQUIRE si.situation_id IS UNIQUE;
CREATE CONSTRAINT emotion_key IF NOT EXISTS
  FOR (e:EmotionEstimate) REQUIRE e.est_id IS UNIQUE;

// --- 層4: 規則 — 世界のあり方を制限する主張 ---
CREATE CONSTRAINT constraint_key IF NOT EXISTS
  FOR (c:Constraint) REQUIRE c.rule_id IS UNIQUE;

// --- 関係型への制約: 1.4節の「主張としてのエッジ」を型で守る ---
CREATE CONSTRAINT influence_edge_key IF NOT EXISTS
  FOR ()-[r:INFLUENCES]-() REQUIRE r.edge_id IS UNIQUE;
CREATE CONSTRAINT influence_validity IF NOT EXISTS
  FOR ()-[r:INFLUENCES]-() REQUIRE r.valid_from IS NOT NULL;
// valid_from 必須: 有効期間のないエッジは「常に真」と自己主張している
// のと同じ（1.4節・原理2）。NOT NULL 制約がその約束を機械に強制させる。

CREATE CONSTRAINT telemetry_of_zone IF NOT EXISTS
  FOR ()-[s:MEASURES_AT]-() REQUIRE s.stream_id IS UNIQUE;

CREATE RELATIONSHIP TYPE MEASURES_AT IF NOT EXISTS
  FROM (t:TelemetryStream) TO (z:Zone);
CREATE RELATIONSHIP TYPE ABOUT IF NOT EXISTS
  FROM (o:Observation), (si:Situation), (e:EmotionEstimate)
  TO (z:Zone), (q:Equipment);
// Neo4j 5.x の型制約。域（domain）・値域（range）を宣言するということは、
// 「どの項がどの項について語れるか」の境界をグラフに刻むことである。
// 境界の外側を書き込ませないことが、この節での形式化の暴力性の最小化だ
// （→2.1節へ橋）。
```

ラベル体系の一覧表は次の通り。表の右端の列 — どの層の主張か — が設計の核心であり、後の Policy Gatekeeper（→6.4節）はこの列をそのまま許可規則に翻訳する。

| ラベル | 層 | 意味 | 主要プロパティ | 書けるエージェント |
|---|---|---|---|---|
| `Zone` / `Operator` / `Equipment` | 項 | 場の座標・人・設備 | `zone_id`, `operator_ref`(仮名), `equipment_id` | 台帳システムのみ |
| `KnowledgeItem` | 項 | 明示化された知識の項 | `key` | 承認済みの人間（→2.6節） |
| `Shift` / `TelemetryStream` / `Observation` / `ManualAction` | 出来事 | 交代・伝感器流・窓集計・手動操作 | `shift_id`, `stream_id`, `obs_id`, `action_id` | ゲートウェイ |
| `Situation` | 主張 | 観測からの状況主張 | `situation_id`, `as_of`, `summary` | 検知プロセス・人間 |
| `EmotionEstimate` | 主張 | 感情価の推定値 | `est_id`, `valence`, `ethics_scope` | 推定モデルのみ |
| `Constraint` | 規則 | 工程・安全上の制約 | `rule_id`, `expression` | 工程承認付きのみ |

`EmotionEstimate` を `Observation` と別のラベルにしている点が重要だ。音声レベルの「測定」と、そこから推定された不快度の「主張」は認識の階層が違う。同一ラベルに混ぜれば、推定は測定と同一の権威で後段の推論へ流れ込む（→5.3節「尤度は正統性ではない」のグラフ版）。1.4節で置いた感情情報の三則 — 用途限定・粗い粒度・本人の閲覧権 — もここでプロパティとして宣言する。`ethics_scope` と `person_ref` だ。

### シードデータ — 項・制約・テレメトリ流の宣言

制約が通れば、宣言は通る。テストデータは実在名の代わりに仮名識別子（`operator_ref: 'op-a1f3'`）を使い、個人をグラフに直接乗せない（粗い粒度の三則）。

```cypher
// ch01_s5_seed.cypher — 場の下地。哲学的意図: 制約（Constraint）は記述では
// なく制限として存在する。text ではなく expression で保持し、機械が検査
// できる形にしておく（→3.3節の論理化への橋）。
CREATE (z:Zone {zone_id: 'line-3', name: '圧入ライン3', noise_limit_db: 85});
CREATE (q:Equipment {equipment_id: 'press-7', model: 'SP-400'});
CREATE (p:Operator {operator_ref: 'op-a1f3', team: 'A班'});
CREATE (s:Shift {shift_id: '2026-11-07-A', started_at: datetime('2026-11-07T08:00+09:00'),
                  ended_at: datetime('2026-11-07T17:00+09:00')});

CREATE (c:Constraint {rule_id: 'line3.torque-max',
  applies_to: 'press-7',
  expression: 'torque_mean <= 180',   // 検査可能な形で書く。自然言語の
  text: 'トルク平均は180を超えてはならない',  // 「気をつけよう」は制約ではない
  valid_from: datetime('2026-11-01T00:00+09:00'), valid_to: null,
  approved_by: 'process-eng:sato'});

CREATE (h:Constraint {rule_id: 'line3.noise-ppe',
  applies_to: 'line-3', expression: 'sound_level <= 85',
  text: '85dB超では耳保護具の着用が必須（労務規則）',
  valid_from: datetime('2026-01-01T00:00+09:00'), valid_to: null,
  approved_by: 'labor-legal:ito'});

CREATE (t:TelemetryStream {stream_id: 'line-3.telemetry', sensor_set: 'temp/vib/sound'});
CREATE (t)-[:MEASURES_AT {stream_id: 'line-3.telemetry'}]->(z);
CREATE (t)-[:STREAMS_FROM]->(q);
CREATE (p)-[:WORKED_IN {shift: '2026-11-07-A'}]->(z);

// 明示知の項と、1.4節の版本つきエッジ（信頼 0.9。これは「明示化に成功して
// いる」関係であり、後の痕跡クエリが拾わない対象となる）。
CREATE (k1:KnowledgeItem {key: 'policy.torque-check', label: 'トルク確認手順'});
CREATE (k2:KnowledgeItem {key: 'rule.press-7-preheat', label: 'press-7始動前予熱'});
CREATE (p)-[:KNOWS {edge_id: 'e-101', kind: 'explicit-procedure', confidence: 0.9,
  valid_from: datetime('2026-11-07T08:00+09:00'), valid_to: null,
  provenance: 'human:op-a1f3'}]->(k1);
```

### テレメトリをどこまでグラフに載せるか — 選択表と設計判断

温度・振動・音声レベルの生データは100ミリ秒ごとに来る。全部をノードにしたらどうなるか。1台の伝感器で年間約3,150万ノード、グラフは肥大しクエリは死に、1.4節の失敗C（汎用性への過剰投資）がテレメトリ版として再演する。載せ方の択は四つある。

| 載せ方 | 長所 | 短所 | 本書の判断 |
|---|---|---|---|
| A 生データを全ノード化 | 完全な解像度 | 年3,150万ノード/台。クエリ崩壊 | 却下 |
| B 窓集計ノードのみ | 軽量・照会速い | 生データはグラフ外で別管理 | **採用**（窓は用途で決める） |
| C 窓集計＋少量の異常時生データ | 異常の追検証ができる | 生の保存範囲の規約が必要 | B に含む（`raw: true` は手動操作窓のみ） |
| D 窓集計を neo4j-time-series 等の外付けに | グラフが軽くなる | 場の一貫性が二つの器に分かれる | 却下（場は単一のクエリで取り出せるべき） |

判断基準は「場を単一のクエリで再現できるか」である。テレメトリがグラフの外にあると、1.4節の場スナップショットと結合した瞬間に場が二つに割れる。窓幅は OODA の観察周期に合わせる（→7.2節）。集計の流し込みは Python で書く — 生テレメトリの受信側（CSV もしくは FastAPI、→7.5節）から見て、書き込みロジックをアプリ側に置けばスキーマ変更がアプリの再デプロイで追えるからだ。

```python
# ch01_s5_telemetry.py — 10分窓の集計を Observation として流し込む。
# 哲学的意図: 集計もまた主張である。平均値は観測の要約ではなく、
# 「この窓ではこの値が真だった」という宣言であり、宣言には必ず
# 窓・式・流し込み時刻の三つの有効条件が付く。
import csv
from collections import defaultdict
from neo4j import GraphDatabase

URI, USER, PASSWORD = "neo4j://localhost:7687", "neo4j", "execphil"

def aggregate(rows):
    windows = defaultdict(list)
    for r in rows:  # CSV: epoch_ts,zone,equipment,kind,value
        key = (int(float(r["ts"]) // 600) * 600, r["zone"], r["equipment"])
        windows[key].append((r["kind"], float(r["value"])))
    return windows

def ingest(driver, windows):
    q = """
    // MERGE 而非 CREATE: 窓は決定的に識別される（時刻×区域×設備）。
    // 決定論的なキーは「同じ事実を二度主張させない」約束の実装。
    MERGE (o:Observation {obs_id: $obs_id})
    ON CREATE SET o.window_start = $ws, o.window_end = $we,
                  o.kind = o.obs_id, o.raw = false,
                  o.ingested_at = $now,          // 主張がグラフに入った時刻。
                                                // 発火時刻と保管時刻を混ぜない
                  o.source = 'telemetry'
    WITH o
    UNWIND $mets AS m
    MERGE (m1:Metric {obs_id: $obs_id}) SET m1.kind = m.kind, m1.mean = m.mean,
          m1.max = m.max, m1.min = m.min
    MERGE (o)-[:HAS_METRIC]->(m1)
    WITH o
    MATCH (z:Zone {zone_id: $zone}), (q:Equipment {equipment_id: $eq})
    MERGE (o)-[:ABOUT]->(z) MERGE (o)-[:ABOUT]->(q)
    // 制約 ABOUT が FROM (Observation) TO (Zone,Equipment) を宣言済み。
    // 型制約に反する書き込みはここで失敗し、失敗として語られる（→4.4節）。
    """
    with driver.session() as s:
        for (start, zone, eq), samples in windows.items():
            mets = []
            for kind in sorted({k for k, _ in samples}):
                vs = [v for k, v in samples if k == kind]
                mets.append({"kind": kind, "mean": sum(vs) / len(vs),
                             "max": max(vs), "min": min(vs)})
            s.run(q, obs_id=f"obs-{start}-{zone}-{eq}", ws=start, we=start + 600,
                  now="datetime()", zone=zone, eq=eq, mets=mets)

if __name__ == "__main__":
    with open("book/code/telemetry_line3.csv") as f, \
         GraphDatabase.driver(URI, auth=(USER, PASSWORD)) as driver:
        ingest(driver, aggregate(csv.DictReader(f)))
        print("windows ingested")
```

CSV の各行は `ts,zone,equipment,kind,value` の形式で、`kind` は `temp_c` / `vib_rms` / `sound_db` の三値を仮定する。この小さなファイルが「現場環境」の代表であり、場のもっとも物質的な層をグラフへ運ぶ。

感情推定はモデルの出力としてのみ書き込む。入力特徴をそのまま保存するのは、主張が根拠を体内に持つ形（reification の軽量版）であり、後から「何を根拠にそう言ったのか」を本人が照会できる（閲覧権の三則）。

### 「場」をクエリで再現する — 同一時刻・同一区域の全要素

いよいよ本節の中心演算である。場はノードではなくクエリである（→1.4節）という宣言の、完全な実行形がこれだ。

```cypher
// ch01_s5_field_scan.cypher — 場スキャン（field scan）。
// 哲学的意図: 場とは、ある時刻に同一区域で同時に有効だった全ての項・
// 出来事・主張・規則のことである。四つの認識層を一度に集めるこのクエリ
// 自体が「場の定義」であり、定義は辞書ではなく演算として保存される。
WITH datetime($at) AS t
MATCH (z:Zone {zone_id: $zone})
OPTIONAL MATCH (o:Operator)-[w:WORKED_IN]->(z)
WHERE w.valid_from <= t AND (w.valid_to IS NULL OR w.valid_to > t)
OPTIONAL MATCH (t2:TelemetryStream)-[:MEASURES_AT]->(z)
OPTIONAL MATCH (obs:Observation)-[:ABOUT]->(z)
WHERE obs.window_start <= toEpochMillis(t) AND obs.window_end > toEpochMillis(t)
      // 窓の半開区間 [start, end): 重複も空白もない。
      // 境界時刻を二つの窓が同時に主張する状態を区間規約で封じる
OPTIONAL MATCH (act:ManualAction)-[:PERFORMED_ON]->(eq:Equipment)<-[:ABOUT]-(obs)
OPTIONAL MATCH (e:EmotionEstimate)-[:ABOUT]->(z)
WHERE e.as_of <= t AND e.expires_at > t
      // 感情推定にも有効期限を持たせる: 推定の有効性は測定より速く腐る
OPTIONAL MATCH (c:Constraint)-[:APPLIES_TO]->(z|eq)
WHERE c.valid_from <= t AND (c.valid_to IS NULL OR c.valid_to > t)
      // 制約にも有効区間。労務規則の改正日を過去のエッジに遼及させない
RETURN z.zone_id AS zone,
       collect(DISTINCT o.operator_ref) AS operators,
       count(obs) AS telemetry_windows,
       [m IN mets | {kind: m.kind, mean: m.mean, max: m.max}] AS metrics,
       [e IN ests | e.valence] AS valences,
       [c IN rules | c.rule_id] AS active_rules,
       [a IN actions | a.action_kind] AS manual_actions
```

（このブロックの `mets` 等の collect は collect 句の簡略記法として整理する。正確な実行可能版が次のものである。）

```cypher
// ch01_s5_field_scan_final.cypher — 場スキャン実行可能版（Neo4j 5.x）
WITH datetime($at) AS t, toEpochMillis($at) AS ms
MATCH (z:Zone {zone_id: $zone})
OPTIONAL MATCH (o:Operator)-[w:WORKED_IN]->(z)
WHERE w.valid_from <= t AND (w.valid_to IS NULL OR w.valid_to > t)
OPTIONAL MATCH (obs:Observation)-[:ABOUT]->(z)
WHERE obs.window_start <= ms AND obs.window_end > ms
OPTIONAL MATCH (obs)-[:HAS_METRIC]->(met)
OPTIONAL MATCH (e:EmotionEstimate)-[:ABOUT]->(z)
WHERE e.as_of <= t
OPTIONAL MATCH (c:Constraint)-[:APPLIES_TO]->(z)
WHERE c.valid_from <= t AND (c.valid_to IS NULL OR c.valid_to > t)
OPTIONAL MATCH (a:ManualAction)-[:IN_ZONE]->(z)
WHERE a.at >= t.duration('-PT30M') AND a.at <= t
RETURN z.zone_id AS zone,
       collect(DISTINCT o.operator_ref) AS operators,
       count(DISTINCT obs) AS telemetry_windows,
       collect(DISTINCT {kind: met.kind, mean: met.mean, max: met.max}) AS metrics,
       collect(DISTINCT e.valence) AS valences,
       collect(DISTINCT c.rule_id) AS active_rules,
       collect(DISTINCT a.action_kind) AS manual_actions;
```

この一枚に、本節の全哲学が詰まっている。`OPTIONAL MATCH` を並べている理由 — 観測も推定 also 制約も、場の構成要素でありながら、どれ一つとして他を論理的に含意しない。空集合を返す層は「その場になかった」ことの記録であり、INNER JOIN で黙って落とす設計なら、感情推定の欠けた場は「感情が中立だった場」と誤読される。不在を表現できることが、場の存在論の品質だ（→1.6節）。`WORKED_IN` に `valid_from`/`valid_to` を付けているのは、交代の切り替えを関係の消滅ではなく版本の切替として扱うためで、1.4節の版本設計がラベル間で再発しないための構造である。

### 暗黙知の痕跡クエリ — 高頻度だが明示化されていない関係

本節のもう一つの中心演算。暗黙知は「明示化されていない」のだから、直接は検索できない。検索可能なのは痕跡だけである — 高頻度で共起し、しかも現行の明示化（`INFLUENCES`）で表現されていない関係のパターン。ポランニーの作業定義がクエリに翻訳されるとは、こういうことだ。

```cypher
// ch01_s5_tacit_trace.cypher — 共起検出: 10分窓内で同じ設備について
// テレメトリ窓と手動操作が repeatedly 共起する組を数え、明示化の無いもの
// だけを拾う。NOT pattern の否定で「語られていない」を表現するのが核心。
MATCH (obs:Observation)-[:ABOUT]->(q:Equipment),
      (a:ManualAction {raw: true})-[:PERFORMED_ON]->(q),
      (z:Zone)-[:HAS_STREAM]->(:TelemetryStream)-[:MEASURES_AT]->(z)
WHERE obs.window_start <= a.at_ms AND obs.window_end > a.at_ms
      // 窓と操作の時刻を含む — 共起の定義は窓規約に依存する。
      // 「同時に起きた」の定義は自然に与えられない（→1.2節の境界の移動）
WITH q, a.action_kind AS act, count(*) AS co_count,
     sum(count(*)) OVER (PARTITION BY act) AS act_total,
     count(DISTINCT obs) AS distinct_windows
WITH q, act, co_count, distinct_windows
WHERE co_count >= 3 AND distinct_windows >= 3
      // 頻度の閾値は任意である。アポリアは最後に率直に書く
OPTIONAL MATCH (p:Operator)-[r:INFLUENCES]->(ki:KnowledgeItem)
WHERE ki.linked_action = act AND r.valid_to IS NULL
WITH q, act, co_count, distinct_windows, r
WITH q, act, co_count, distinct_windows, count(r) AS explicit_versions
WHERE explicit_versions = 0
      // 明示化ゼロ: これが「痕跡」の定義。高頻度+無明示化の論理積
RETURN q.equipment_id AS equipment, act, co_count, distinct_windows
ORDER BY co_count DESC
LIMIT 20;
```

結果は候補（candidate）であって関係ではない。候補の信頼度は共起から計算できるが、`confidence` を Cypher で直接書き込むことは1.4節の原理1（性質は主張の性質、必ず出所と組）に反する — 計算値は計算として、Python で `ContextEdge` の観測集に反映し、承認された人間だけがエッジを開設する。共起スコアを信頼度へ変換する関数は最小限に置く。

```python
# ch01_s5_trace_score.py — 共起頻度を信頼度の「候補」へ変換する。
# 哲学的意図: 信頼度は頻度ではない。共起は形式化の材料の有無を教えるが、
# 信望は人間の承認によってのみ付与される（→4.2節 CQ、→6.4節ゲート）。
# この関数が返すのは常に候補であり、グラフへは書き込まない。
TACIT_CANDIDATE = """
MATCH (obs:Observation)-[:ABOUT]->(q:Equipment {equipment_id: $eq}),
      (a:ManualAction {raw: true})-[:PERFORMED_ON {action_kind: $act}]->(q)
WHERE obs.window_start <= a.at_ms AND obs.window_end > a.at_ms
RETURN count(*) AS co_count, count(DISTINCT obs) AS windows
"""

def candidate_confidence(co_count: int, windows: int) -> float:
    # saturating: 共起100回でも 0.65 を超えない — 頻度は確信を Saturate さ
    # せない（上限は承認なき統計の傲慢への抑制）。
    return 0.65 * (1 - 2.7 ** -max(co_count, 1)) if windows else 0.0

def propose(driver, eq: str, act: str):
    from neo4j import GraphDatabase
    with driver.session() as s:
        rec = s.run(TACIT_CANDIDATE, eq=eq, act=act).single()
        conf = candidate_confidence(rec["co_count"], rec["windows"])
        print(f"{eq}/{act}: co={rec['co_count']} w={rec['windows']} candidate_conf={conf:.3f}")
        # 承認後の開設は人間が行う。provenance は承認者個人名:
        # 暗黙知の明示化には必ず名前が残る（→8.2節の「わかっていて押す」）。
```

`raw: true` を手動操作窓だけに認めるのは、1.4節の失敗A（数値の権威化）が統計にも再発しないための印である（→4.2節 CQ、→6.4節ゲート）。

### 現場の失敗三型 — このスキーマはこう壊れる

**失敗D: テレメトリ洪水でグラフが死んだ**。ある保全チームが「いずれ必要になる」と全伝感器の生値を 100ms ごとノード化した。18か月で 6,000万ノード超、場スキャンは 40秒を返し、作業者は照会を諦めた。場スキャンが走らないグラフは存在しても機能しない — 選択表のAが現場でどう現れるかの記録である。策は窓集計の既定化と、生データの時系列ストアへの分離（選択表C）である。

**失敗E: 感情推定が人事評価に流れた**。`EmotionEstimate` を評価資料として副次阅読した管理職がいた。翌月、作業者は騒音下での会話を減らし、声のトーンを平坦に保つようになった。`sound_db` と推定 valence の相関が崩れ、場スキャンの感情列は一律 0 に収束した。測定の有効性は測定される人が測定に反応しないことを条件とする — 反応する測定は測定対象を変える。三則（用途限定・粗い粒度・閲覧権）は倫理の飾りではなく、データ品質の構造条件だった。

**失敗F: 共起候補を承認なしで本線にした**。痕跡クエリが出した「振動窓×段取り替え」の候補を、誰かが「原因がわかった」と `INFLUENCES` に書き、`provenance: 'model:cooccurrence'` と入れた。半年後、統計は季節変動を拾っていた。関係は間違っていただけでなく、履歴に残った `model:` 付きの主張は誰も承認しておらず、ゲートはそれを止めなかった。`confidence` に人間名が無いエッジを現行版にしない運用（→6.4節のポリシー執行）が欠けていた。策は承認なしには `valid_to IS NULL` を許さない規則と、候補の寿命（`expires_at`）である。

| 失敗型 | 壊れた層 | 構造対策 |
|---|---|---|
| D 生テレメトリの全投入 | 出来事層の肥大 | 窓集計既定、生は外付け＋印のみ |
| E 感情推定の用途逸脱 | 主張層の汚染・反応性 | `ethics_scope` の機械執行、閲覧権 |
| F 候補の未承認昇格 | 主張と規則の系譜 | 承認者名を必須、`provenance` を照会 |

### 残るアポリア — 頻度から名前は取り出せない

率直に書いておく。痕跡クエリは「繰り返されているが語られていないもの」を数えるが、それが作業者にとって**何であるか**は返さない。共起は関係の存在を指し示すが、関係を名前で呼ぶのは現場の人間であり、呼ぶ行為のなかにしか意味は宿らない（→1.3節の場、→8.3節の共同化）。候補のリストを承認画面へ載せる装置は8.5節で書くが、この節の段階で確定しているのは、名前を与える権限は統計から人間へ移動しないということですらなく、人間の中に最初からあったという事実である。スキーマに「不明」を書き残す設計（`OPTIONAL MATCH` の空集合、候補の `expires_at`、承認者名必須）は、このアポリアをバグではなく設計条件としてグラフに刻む作業にほかならない。

### 実行練習

1. **場スキャンを二つの時刻で走らせる。** シードを投入し、`telemetry.py` で窓を作り、`$at` を `2026-11-07T08:30+09:00` と `2026-11-07T09:30+09:00` の二通りで実行せよ。`telemetry_windows` と `valences` の列が窓の有無で `[]`（空）と数値のどちらになるかを確認し、`OPTIONAL MATCH` が「その場になかったもの」をどう表現しているか、INNER JOIN 版（`MATCH` に置き換えたもの）を作って同じクエリと比較し、行数が消える層を特定すること。説明5行。
2. **痕跡クエリの閾値を壊す。** `co_count >= 3` を `>= 4` に、`distinct_windows >= 3` を `>= 2` に変えて、注入した `re-seat-part` 3件が候補からどう消える/残るを観察せよ。その後、`ManualAction` を1件だけ `raw: false` で追加し、痕跡候補が1件減ることを確認する。`raw` の印が何を意味するかを3行で書け。
3. **失敗Fをポリシーで防ぐ Cypher 検査を書く。** 「`valid_to IS NULL` かつ `provenance` が `'human:'` で始まらない `INFLUENCES`」を列挙するクエリを書き、`provenance: 'model:cooccurrence'` のエッジを1本注入して実際に1件ヒットさせよ。この検査を定期運用すると何が守られ、何が遅れるか（承認の待たせ方はどこで決めるか）を5行で論じよ。

## 1.6 限界の自覚 — グラフに乗らないもの

前の節で、場をグラフに載せる作業を完成させた——と書くべきところだが、この節はそれを否定するためにある。否定と言ったが、破棄ではない。1.4・1.5で立てた装置は動き続ける。しかしこの本が他の技術書と違うのは、各部の終わりに「いま作った装置が何を裏切ったか」を必ず書く点にある。形式化の成功を報告する本は腐るほどある。形式化の残骸を報告する本は、ほとんど存在しない。この節は後者である。そして最後に、残骸を捨てるのではなく記録する仕組み——影の台帳——を置いて、第2章に渡す。

### グラフ化そのものが暗黙知の裏切りになりうる

1.5節の `OCCUPIES` エッジを思い出してほしい。作業者の場の依存度（`context_score`）と感情価（`valence`）を、人ごとに連続値で保持した。これは1.2節で「境界は面である」と主張したときの、最も誠実な実装だった。しかし誠実さと無傷さは別のものだ。

タナカさんは夜勤の3号機の音を聴いて「これは前にも聞いた」と判断する。1.1節で見た補助焦点（subsidiary awareness）の構造——音が身体に吸収されて、機械の状態へ向けられている——を、グラフは表現できるだろうか。いいや。グラフにあるのは `EmotionEstimate {valence: -0.4, label: '不安'}` と `Telemetry {kind: 'acoustic', value: 68.2}` の二つの節点と、それらを結ぶ辺の信頼度だけである。ポランニーの記述によれば、聴いている音そのものは「heard from」であって「heard of」ではない。補助焦点は対象焦点に飲み込まれて初めて意味を持つ。グラフは「heard of」の側——対象焦点化された観測——しか載せられない。載せられた瞬間、補助焦点は消える。

ここに残虐な自己言及がある。1.5節の「暗黙知の痕跡クエリ」は、明示化されていない反復行動を検出する、と説明した。しかし検出された反復行動は、検出された時点で明示知になる。台帳に「タナカさんは3号機の音で点検頻度を調整している（20回）」と書かれた瞬間、タナカさんの暗黙知はその記述の外へ退かされるか、記述に合わせて行動を変えるかのどちらかになる。測定が測定対象を書き換げるのは社会学の三すくみ（triadic mutuality of constraints）そのものだが、ここでの被害はより直接的である。記述された暗黙知は、もはやその暗黙知ではない。

したがって第一の結論はこうだ。**グラフは暗黙知を保存できない。暗黙知の不在を記録できるだけだ。** これはグラフの失敗ではない。グラフの仕様である。仕様として書くためには、スキーマに「載せなかったもの」の居場所を残す必要がある。

### 載せなかったものの三類型

「グラフに乗らないもの」を曖昧に並べると精神論になる。工学分野で使える形にするため、三類型に分類し、それぞれに異なる工学的対応を割り当てる。

| 類型 | ポランニー的構造 | 具体例 | なぜ載らないか | 工学的対応 |
|---|---|---|---|---|
| 身体化された技能 | 補助焦点が身体にある | 異音の聞き分け、手触りの微調整 | 観測が対象焦点しか撮れない | 痕跡の統計（1.5）＋練習ループ（→8.6） |
| 意味の関連性 | 意味は文脈関係の全体にある | 「様子を見る」の妥当性 | 文脈の総体が原理的に有限記述に閉じない | `context_score` の上限警報（後述） |
| 規範的判断 | 行為の正しさは記述に還元されない | 「いま点検すべきか」 | is から ought は導けない（ヒュームの法則） | 判断はステートマシンに残す（→5.5） |

三類型のうち、本書が最も硬く扱うのは三番目である。「グラフに乗らない」と「グラフに乗るべきでない」は違う。規範的判断は、本来どちらの意味でも載せるべきではない。`Situation -[:SHOULD_LEAD_TO]-> Action` という辺を一度作ると、その辺は以降すべての推論に「事実」として混入する。ought を is の格好で保存した瞬間、設計者の判断がデータのふりをして帰ってくる。第5章でスミスの reckoning/judgment 分離として定式化するが、先取りして言ってしまえば、**グラフは reckoning の素材であり、judgment の器ではない。**

二番目（意味の関連性）には、もう少し緩い対応が取れる。完全な記述は無理でも、「記述が危険なほど文脈から離れた」と警告することはできる。

### 過剰形式化の警報 — context_score の境界監視

1.4節で導入した `context_score` を逆に使う。場への依存度が高い人ほど、その人の行為は明示記述で模倣しにくい。したがって、**低い `context_score` の人（＝場の文脈に依存していない新参者）に対して、高 `context_score` の人の行動履歴から自動処方を発火させるとき、形式化の辺境を越えている**——これが警報の論理である。

```python
# overformalization_alert.py — 「形式化の辺境」を数値で監視する
# 境界は線ではなく面（→1.2節）。面の縁に黄色い線を描くのがこのコードの哲学。
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "pass"))

ALERT_QUERY = """
MATCH (v:Person {person_id: $visitor})-[o:OCCUPIES]->(c:Context)
MATCH (x:Person {person_id: $expert})-[ox:OCCUPIES]->(c)
WHERE ox.context_score >= 0.7          // 場の文脈に深く依存して知っている人
  AND o.context_score <= 0.3           // まだ場に身体が沈んでいない人
WITH c, o, ox,
     (ox.context_score - o.context_score) AS gap   // 辺境を越えた距離
WHERE gap >= 0.4
CALL {
  WITH c, gap
  CREATE (:BoundaryAlert {
    kind: 'over_formalization',
    context_id: c.context_id,
    gap: gap,
    message: 'この処方は、場の文脈に深く依存した知に基づいています。'
             + '適用前に、現場の人間に『なぜその行為か』を問うてください。',
    created_at: datetime()
  })
}
RETURN c.context_id, gap
"""
# 注意: この Alert は処方を止めない。止める/止めないの判断はグラフの外に置く（→5.5）。
# 警報は reckoning の産物であり、判断の代行ではない。
```

`BoundaryAlert` は `Situation` とは別ラベルであることに注目してほしい。状況が「世界のいま」を表すのに対し、警報は「記述の自己意識」を表す。メタ層を同一ラベルに混ぜないという规則は、1.5節の「主張の層の分離」と同じ哲学の適用である。

### 設計者の埋め込まれた判断 — スキーマ自体の暗黙知

第三の、そして最も隠れにくい被害者について書こう。グラフに乗らない最も重要なものは、**スキーマ設計者自身の暗黙知**である。

1.5節のラベル体系を思い出しながら、次の設計判断列を読んでもらいたい。

1. なぜ `Situation` を独立ラベルにし、`Context` のプロパティに埋めなかったのか。
2. なぜ感情を `Person -[:FEELS]-> EmotionEstimate` とノード側へ向けたのか（プロパティで持てたはずだ）。
3. なぜ「制約違反」をイベントとして記録せず、`CONSTRAINED_BY` の辺で静的に表現したのか。
4. なぜ `Telemetry` を5分窓で集計した時点でグラフに載せ、生波形を除外したのか。

これら四つの問いに、設計書から「正しい答え」を引用してくることはできない。答えは全部、設計者がその場（再びこの語）でやった身体化された判断——同僚との議論の流儀、過去に壊れたシステムのトラウマ、「ノードを殖やしすぎるのは悪」という経験的趣味——に根を持つ。スキーマは暗黙知の沈殿物である。しかもその沈殿物は、以後すべての観測の条件になる。「グラフで何を見られるか」を、グラフに乗らなかった設計判断が規定する。

この再帰を回避する技術は存在しない。認め続けることだけが可能な態度である。したがって実務的には、スキーマ変更のたびに「この変更は何を暗黙のうちに前提としたか」を一人の人間が文で署名する仕組みを要求する。これは管理の手続きではなく、存在論的負債の簿記である。台帳のスキーマは第2章で書く——ちょうど、すべての分類変更が履歴を要求されるべきだという第2章の中心命題の、最初の適用先がこの台帳だからだ。

```cypher
// 存在論的負債の簿記（最小形）。変更の「正しさ」ではなく「前提」を書かせる。
CREATE (d:SchemaDecision {
  decision_id: randomUUID(),
  made_at: datetime(),
  decided_by: 'P-114',            // 署名。匿名化しない。判断は人に帰属する
  change: 'Constraint を Event でなく静的辺で表現',
  assumed: '制約は状況より寿命が長く、状況から独立に存在する',
  could_be_wrong_if: '制約自体が現場状況で生成・消滅する組織では破綻する',
  revisit_by: date('2027-04-01')  // 負債には返済期限を書く
});
```

`revisit_by` を持つ理由を述べておく。暗黙知は更新される。5年前の身体感覚は今日の身体ではない。前提の再点検期限を設けない簿記は、やがて埋葬記録になる。

### 「記録しないこと」の設計 — 暗黙知の避難所

ではすべてを記録すればよいのか。逆である。**意図的に記録しない領域を作ることが、暗黙知を守る最後の設計になる。** 全記録（total recording）は、暗黙知を痕跡統計にまで干し上げるだけでなく、作業者の沈黙そのものを奪う。タナカさんが「これは言葉にしないでおこう」と判断する余地——暗黙知の最も成熟的な形は、明示化を意図的に回避する判断を含む——は、記録しない権利が確保されて初めて存在する。

```cypher
// 記録拒否の記録（paradoxical だが重要）:
// 「何を記録しないか」の決定自体は記録し、内容は残さない。
CREATE (r:NonRecordingRule {
  rule_id: randomUUID(),
  scope: 'Person-PrivateNote',            // 個人ノートは永久にグラフに入れない
  decided_by: 'P-114',
  decided_at: datetime(),
  reason: '明示化の前の思考段階は、明示化によって殺される。'
          + 'この段階にはアクセスしないことを、システムに約束させる。',
  machine_readable: 'deny'                // 防腐層（→6.3）が機械的に強制する
});
```

`NonRecordingRule` は ACL に「触れてはならない領域」として読まれる（→6.4節の Rego ポリシーに直結する）。沈黙はデータの不在ではない。沈黙は設計された空間である。

### 失敗デモ — 「様子を見る」を再値付けする

限界を主張で終わらせないために、実際に壊れるクエリを走らせて見せる。現場の「様子を見る」という行為を、グラフは `Action {name: 'watch'}` として記録する。しかし「様子を見る」には少なくとも三つの別々の行為が同居している。(a) 先送り——コストと権限の問題で、いま着手しないこと。(b) 好機待ち——条件が揃うまで着手を遅らせる戦略的遅延。(c) 観察そのもの——注視を通じて情報を増やす積極的行為。この三つは、同じ動詞で呼ばれ、同じ `PERFORMS` 辺で結ばれ、外見上区別できない。

```cypher
// 一見もっともらしいクエリ: 「異常を検知した状況で『様子を見る』を選んだ回数を数えよ」
MATCH (s:Situation {status: 'OPEN'})-[d:LED_TO]->(act:Action {name: 'watch'})
RETURN count(act) AS deferrals;
```

このクエリは `deferrals`（先送り回数）を返すと名乗るが、実際には (a)+(b)+(c) の総和を返す。観察として「様子を見る」を選んだ行為は情報収集の成功であり、先送りとして選んだ行為はリスクの繰延べである。両方を同じ数に混ぜた瞬間、クエリは**存在しなかった統計量**を生成する。数字は正しい。数字が生成する量だけが実在しない。

では `senseMaking` プロパティで三値分類してやればよいか。

```cypher
MATCH (act:Action {name: 'watch'})
WHERE act.senseMaking IN ['deferral', 'opportunistic', 'observational']
RETURN act.senseMaking, count(*) GROUP BY act.senseMaking;
```

意味は一段深くなっただけで、消えていない。「好機待ち」と「先送り」の境界は状況ごとに移動する（撤退するつもりが好機を捕捉することもある）。三値分類の境界に立った人間が、状況の総体を見て一人ずつ判定している——その判定の身体性だけが、クエリの正しさを支えている。ラベルを増やすほど、正しさはラベルの論理から、ラベルを貼る人の判断へ移っていく。1.2節の「境界は面である」が、このデモで数値ではなく運命として理解できるだろう。分節の粒度は問が与えるものだ——この原則の完全な展開は、オントロジーの十分性を問う第4章（competency questions）で初めて実装可能になる。

### 三つの姿勢 — 形式化をどこまで信じるか

「グラフに乗らないもの」に対する設計姿勢は、歴史的に三つに整理できる。本書が選ぶ位置を明示しておく。

| 姿勢 | 主張 | 代表 | 破綻の形 |
|---|---|---|---|
| 削減主義 | 暗黙知は未分解の明示知にすぎない。十分細かければ全部載る | 古典的記実主義のAI | 「あと一歩」の無限回帰。1960年代の象徴AIの墓標 |
| 道具主義 | 真偽ではなく有用性でモデルを選ぶ。載らないものは載らないままでいい | デーヴェイ「暗黙知の複雑系」読み | 有用の基準が現場から遊離したとき、静かに有害化する |
| 否定的設計（apophatic design） | 載らないものを明示的に宣言し、載らない領域を守る設計要素として実装する | 神学のアポファティク（否定の神学） | 装置自体が権力になる危険（→6.6）。手続きの形式化への誘惑 |

本書は道具主義を方法として、否定的設計を器官として採用する。削減主義は退ける——1.1節の補助焦点の論証が許さないからではなく（それは反論が強い）、削減主義のシステムが現場でどのように壊れるかを1.5・1.6で直接見たからである。「あと一歩」のラベルを貼り続けたグラフは、最後にはすべての意味を判定するために全データを見なければならなくなり、運用として死ぬ。

否定的設計を選ぶなら、否定的設計自身の失敗モードも引き受けねばならない。`NonRecordingRule` や `BoundaryAlert` は、作られた瞬間に組織の権力装置になる。「記録しない領域」は誰が定義したのか。警報を出さない決定は誰がしたのか。この問いへの答えが防腐層と統治の章（第6章）である。限界の認識は、限界を告げる装置の設計に続き、その装置の統治の設計に続く。連鎖はここで切れず、最後まで続く。

### 限界の向こう側へ — 残骸のための章

この節で生じた未解決物を整理しておこう。(1) 補助焦点は載らない。(2) 痕跡の検出は暗黙知自身を変質させる。(3) スキーマは設計者の暗黙知の沈殿物であり、負債として簿記するしかない。(4) 記録しない領域を設計しなければならない。

(1)と(2)は、この第1部の内部では解けない。解けないのではなく、問いの形が変わる——「なぜ載らなかったのか」ではなく「載せなかったときに何が失われたか」を、どうやって後から辿るか。これが第2章の主題である。分類は暴力的で、暴力は不可逆で、不可逆な暴力は履歴なしには追えない。ヘーゲルの止揚は、失われたものを保存しながら進む演算として、差分設計の規範になる。

(3)は簿記としてすでに部分的に答えられている。残りは「履歴のスキーマ」の問題であり、これも第2章に回収される。

(4)だけ、答えが第8章まで届かないまま宙に浮く。記録しないことの設計は、暗黙知への「逆流」（→8.3節）の原型である。ここから最後まで、この種は持ち運び続ける。

### 実行練習

1. 1.5節の感情ノードに自分の現場語彙で3つのラベルを付け足し（例: 「緊張」ではなく「引き締まり」）、`label` が本人の語彙である条件 `WHERE e.source = 'self_report'` の意味を `EXPLAIN` プランで確認せよ。モデルのラベル体系（`acoustic_model`）と混ぜたとき、どのクエリが静かに壊れるかを書き出せ。
2. `SchemaDecision` を3件、自分のプロジェクトの実際のスキーマ決定について書け。`could_be_wrong_if` が書けない決定は、たぶん設計者自身が前提を自覚していない。自覚できないという経験そのものが1.1節の主題である——メモを残せ。
3. `NonRecordingRule` を1件作り、自分のデータの中で「今後6か月間、この規則を作った自分を疑い続ける」対象を選べ。期限が来るまで内容を書かないことで、明示化の圧力に耐える実験になる。この実験の記録の書き方自体が、第8章のUIプロトコルの入力になる。
