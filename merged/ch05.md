## 5.1 ブライアン・キャントレル・スミス — Reckoning と Judgment の区別

第3部が始まる。第1部は「知とは何か」、第2部は「十分か」を問うた。第3部から問いは**誰が知の主体か**へ移る。そして最初の仕事は、主体の定義ではなく**区画**である。AIをシステムに組み込む設計のすべての失敗は、この区画の描き間違いに還元できる、と本書は仮定する——その仮定の最初の証明を、この節で提示する。区画の道具として、本書はブライアン・キャントレル・スミス（Brian Cantwell Smith）を選ぶ。人工知能研究の内部から「計算と知」の問題へ挑み続けた研究者であり、その2019年の monograph *The Promise of Artificial Intelligence: Reckoning and Judgment* は、LLM時代の設計書として最も正確に読める哲学書のひとつである（2023年の *The Moral Status of Experimental Machines* は倫理の射程を extensions するが、設計の中心は前者である）。中心は標題の二語——**reckoning（計算・算段）と judgment（判断）**。

### Reckoning — 記号的操作の正しさ

reckoning とは、体系に従った記号的操作の遂行である。算術、論理演繹、型変換、検索、そして今日の LLM による次のトークンの選択——形式的な規則と統計的規則に従って記号列から記号列を作る仕事はすべて reckoning の領域に入る。reckoning の良否は**内的**に定まる。規則に従っているか、体系の中で整合しているか。世界がどうであるかは問わない（問う必要がない）。

3章の語彙が既にこの区別を使っていることに気づいた読者は多い。3.5 の判定器は reckoning の装置である——制約集合の充足は体系内の操作であり、「世界が本当にそうか」は model の解釈（assignment の現実対応）を人間が引き受けて初めて事実になる。判定は reckoning、判定結果を世界の報告として**引き受ける**ことが judgment。4.5 の「sat を正しさ読まない」は、この区別を違反する危険への警告であった。

### Judgment — 世界へのコミットメント

judgment は reckoning と二点で異なる。**其一、judgment は世界へのコミットメント（commitment）を含む。** 「x > 0 だ」と算じるのと、計測値 x を報告し、その報告を根拠に誰もが取れる決定に変更を加えうると**引き受ける**のは、別の行為である。判断には、外に出た結果に対する**accountability（応答責任）**が付随する。判断主体は、なぜその判断かを問われ、間違っていた場合の帰結を引き受ける場所（3.6 の「懲罰と名誉の器」）に座っている。

**其二、judgment は判断者を変えうる。** 判断は、した主体の将来の判断の仕方にフィードバックする（経験となる）。 reckoning はした者を変えない——同じ関数は同じまま再適用される。キャントレル・スミスが judgment に「experience の所有」を認める所以であり、彼の機械論批判の要はここにある：**experience を持たない存在は、厳密な意味で判断できない。** 判断したことが判断者を更新しないなら、それは極めて高度な reckoning であって、判断の連続体ではない。

この二点が揃った定義を、本書の設計語彙で再定式化する。**judgment := 世界へのコミットメントを出力し、そのコミットメントの応答責任の連鎖に末端ノードとして接続され、コミットメントの履歴が主体自身の将来動作を修正する更新経路を持つ、行為。** 定義の三節が、そのまま3.6 のエージェント条件（intent 露出・RESPONSIBLE_FOR 末端・更新連鎖）と一致していることに注意してほしい。本章は3章の形式語彙へ、この区別を登記する。

### 「LLMは驚くべき reckoning を持つが、judgment を持たない」の正確な読み方

この章のテーゼを、誇張でも謙遜でもなく正確に読む訓練をここで行う。三つの誤読を先に解体する。

**誤読一（恐竜誤読）**：「LLM には本当は判断があるが、我々が認めていない」。この読者はキャントレル・スミスの定義を「知能の測定」に読み替えている。定義は**役務の配分**について語っているのであり、能力の等級についてではない。reckoning がいくら卓越しても、コミットメントと accountability と更新経路は**別の配分問題**である——それは LLM の内部構造ではなく、システムと組織の設計が決める。

**誤読二（道具誤読）**：「LLM はただの計算機だから出力に意味はない」。これは reckoning の価値を無視する。体系に従った記号操作は、体系の外に出ると誤りうるとはいえ、体系の内では**知識の候補を生成する装置**として極めて有力である。4.3 の retrofit 抽出が LLM で加速するし、3.3 の EARS 変換の叩き台も LLM が書く。候補生成と確定の分離——本章の設計の芯——を無視して「単なる計算機」で止めると、判断を人間の側で非効率に再発明する。

**誤読三（境界実体誤読）**：「システム全体（LLM＋検索＋人間レビュー）は判断する」。正しい。ただし注意深く：**システム全体の出力が judgment になるのは、設計されたコミットメント・連鎖（人間レビューの accountability 接続、コミット履歴の更新経路）が存在するときだけである。** 「LLM + 人間」なら自動的に判断になる、は魔法である。5.5 のステートマシンと5.6 のラッパーが作るのは、まさにこの連鎖の物理である。

正読を一文で置く。**LLM はreckoning の部品であり、その卓越性は system の judgment 能力の必要条件でありうるが、十分条件ではない。判断は部品がするのではなく、部品と人間と制度で構成された系が、設計された形で遂行する。** この文の「設計された形で」が第3部全部の主題である。

### 層の非同一性 — performance と accountability は別の場所に置く

キャントレル・スミスの議論を設計に落とすと、層構造の命令になる。**遂行（performance）の層と応答責任（accountability）の層は非同一であり、混線させた設計は必ず壊れる。** 「AI が決めた」という文は、遂行の記述としては正しいことがあっても、責任の記述としては原理的に誤りである（3.6 の非対称性定理：機械は懲罰されない）。同様に「AI の判断を人間が承認するフロー」は、責任の所在を人間の署名へ移すのではなく、**責任の所在を曖昧化する**ことがある——署名した人間が内容を評決できないなら、承認は accountability の配分ではなく、accountability の laundering（洗浄）である。

laundering の検査基準を本章から先へ引き継ぐため先に定義する。**実効的承認**：承認者が、出力の根拠（候補生成のreckoning の経路、→5.6 の監査ログ）を、判断に必要な解像度で再検証できること。**見せかけ承認**：根拠の再検証が構造上不能なのに署名だけ求めること（UI に「承認」ボタンを置くだけの設計）。8.4 の Human-in-the-Loop 設計は、この二値検査から始まる。承認を置く場所ではなく、**再検証可能性を設計する**ことが judgment 配分の本体である。

```cypher
// accountability 連鎖の登記(3.6 の RESPONSIBLE_FOR の本章拡張)
// 判断事件(JudgmentEvent)は必ず人間の末端ノードへ接続される。
CREATE (je:JudgmentEvent {
  j_id: $jid,
  basis_reckoning: $trace_ref,        // どのreckoningの連鎖に依拠した判断か(→5.6 の監査ログ)
  decider: 'P-114',                   // 末端: 人間エージェント(3.6)
  revalidation_path: 'evidence-panel://j/' + $jid,  // 実効的承認の物理(再検証可能性)
  update_route: 'policy-diff-PR-311'  // 更新経路: この判断が将来の動作を変える配管
});
MATCH (je:JudgmentEvent {j_id: $jid}), (p:Agent {agent_id: 'P-114'})
CREATE (p)-[:RESPONSIBLE_FOR {as: 'judgment-terminal-node'}]->(je);
// revalidation_path と update_route の欠落は「見せかけ承認」の機械検出条件になる(→6.4 の Rego)。
```

`update_route` を必須にする設計は、judgment 定義第三節（コミットメントが主体の将来動作を修正する）のシステム実装である。更新経路を持たない JudgmentEvent は、記録しても学習しない——4.4 の契約違反を障礙更新へ接続しなかった組織の病が、判断層で再発する。判断の履歴は判断者を変えねばならない。変えないなら、それは判断の墓標ではなく、判断の偽造である。

### 区画を誤った設計の解剖 — 「自動判断システム」の三症状

最後に、区画の誤配の実例を解剖する。ある保険会社が「AI 審査」で小口の請求を自動却下した（実際の論点の典型化）。三つの症状が同時に現れた。(1) **却下の説明不能**——却下理由として提出される文言が、審査のreckoning 経路（特徴重み・閾値）から生成された**それっぽい物語**であり、再検証可能な根拠と対応しない（尤度の物語化。5.3 で扱う隠れ判断の原型）。(2) **申訴経路の人間不在**——申訴窓口は「AI が判断しました」を答え、末端の accountable ノードが欠落（見せかけ承認の連鎖）。(3) **更新経路の遮断**——誤却下申訴の統計が審査政策の変更 PR に接続されず、判断履歴が reckoning の訓練データにのみ回流する（judgment の経験が主体でなくベンダーのモデル更新へ流れ、主体＝保険会社は経験を持たない）。

症状(3) の重大さを強調したい。キャントレル・スミスの語で言えば、この設計では**経験の所有権が主体の外へ流出している**。判断で学べる場所が自組織の政策配管ではなく、外部モデルの内部（しかも非公開の勾配更新）に置かれたとき、組織は自らの判断経験を持たない存在になる——2.3 のスティグレールの第三次保持が外部事業者に委託された知識版である。第3部の設計原理（AI の脱・司令塔化）が単なる安全策ではなく**主体性の保存戦略**であることが、ここで初めて全貌を見せる。

### 判断の三要素を欠いた出力の実例解剖 — 保険・採用・審査の三場面

判断の定義（コミットメント＋末端＋更新経路、→5.1）が、実際の AI 出力にどう欠けているかを三場面の実例型で解剖する。解剖の形式を統一する——出力・欠損要素・欠損が働く場所・簿記による処方、の四欄で読む。

**場面一：保険の引受支援**。モデルが「この物件の保険金は X 円が妥当」と提案する。コミットメントはある（金額が提示され業務が動く）、末端は半分ある（最終引受は人間が署名する——ただし署名者はモデルの根拠を再検証できない、→5.1 の見せかけ承認）、更新経路はゼロ（モデルの再学習はあっても、**この提案の根拠を誰がいつ書き換えるか**の通路がない）。欠損が働く場所：異常な高額の提案が続いても、根拠の更新がないから同じ誤りが反復され、異常の発見は契約失効後になる。処方：`JudgmentEvent` に basis_reckoning と update_route を強制する（→5.1 の Cypher の実運用版）——提案に「この根拠が崩れる条件」と「崩れた時の審議槽」を添えない出力は、受理しない契約を置く（→4.4 の DbC の出力側実装）。

**場面二：採用スクリーニング**。スコアが候補を自動で並べる。コミットメントはある（面接リストが業務を駆動する）、末端は名前だけ（責任者はいるがスコアの中身を検査できない）、更新経路は偽物（「モデルが再学習する」は更新経路ではない——経路は**誰の 어떤 不服従がどの規則変更になるか**の設計である）。ハーバーマス的に言えば、正統性要求（この配列は公正か）に対する応答回路がない（→6.2 の正統性ゲートの不在）。処方：dissent の通路（候補の不服従→審議槽、→6.2 の dissent_rego の人事版）と、dissent_volume・overturn_rate の scorecard 登録（→6.6 の四率の人事適応——dissent が0件の自動配列は、公正の証拠ではなく不服従の回路が閉じている証拠）。

**場面三：内容審査（モデレーション）**。自動判定が投稿を削除する。三要素全部が形だけある（判定＝コミットに見える、運営者が末端、異議申立てが更新経路）——しかし更新経路が**個別救済**（この一件を戻す）しか持たないとき、規則そのものの更新経路は不在である（→4.1 の区別：個件の再検証と規則の改訂は違う）。誤削除の統計が規則改訂に還流しない系では、末端は個案の火消しに消耗し、正統性は目減りする（→6.6 の腐敗が「統計が燃料にならない」形で現れる）。

三場面の共通文を刻む。**AI 出力は三要素のどれかを「見える形」で偽装できる——偽装の検出は、要素の存在ではなく要素の配線（update_route が規則改訂に繋がっているか）の照会でしかできない。**判断の哲学は、配列図の検査に還元される。これが「実行可能な哲学書」の意味の一つ——5.1 の定義は、上の三照会の形で実行可能なのである（→5.3 でこの三要素が確率では埋まらないことを示す、→5.3）。

###  delegation 実験 — 判断の境界はどこまで動かせるかの実験設計三本

Reckoning と Judgment の区別（→前掲）を、反論にさらすために**実験設計**として書き置く。哲学者の直覚ではなく、実装者への挑戦として——「あなたの区別は、次の三実験でどこまで保つか」。

**実験一（境界の移動）**：ある領域で Reckoning が長期間人間の判断精度を上回った（例：予知保全の异常スコア）。领域の判断は AI に移った——この移転を 5.1 の三要素は止めるか許すか。答え：**三要素は移転を止めない、移転の簿記を強制する**——コミットメント（AI スコアに基づく停止決定のコストと結果を誰が引き受けるか）、末端（誤りの責に名前的主体）、更新経路（score の规則変更を誰が何時どう変えるか）が揃えば移転は判断の委任である（→7.2 の委任深度の枠内）。揃わぬままの移転は判断の消去である——実务では大半の「AI 化」が後者であり、5.1 の区別の実用は**三要素の欠落検査**として現れる（→5.3 accountability-check）。
**実験二（末端の希釈）**：末端に座った人間が、月に 400 件の判断を 8 秒/件で承認している（→8.4 single_plate_rate の実測）。末端は名前的に存在し実質的に希釈——5.1 はこれを「判断ではない」と言うか。答え：**言う。そして判断件数の上限を design せよ、と要求する**——判断能力の残高（→7.1 balance-sheet）は人間の 1 日あたりの実質審議容量で制約される（件数の SLA に審議時間の下限を載せる：hold_seconds、→8.5 と同じ設計が判断者の労働にも走る。400 件/8 秒の承認台帳は、5.1 の意味で**空の簿記**である）。
**実験三（末端の不在）**：夜間無人、自動 act（段2、→7.6）。末端は誰か。答え：**段2 の act の末端は、その规則の落日審議者である**——末端は時刻上的に現場にいなくても、簿記上の主体として存在できる（落日周期=末端の巡回周期。無人運行は末端の不在ではなく、**末端の時間的分散**、→E4 落日と 7.6 rollout の demote 設計）。無人系で落日審議者が消えた場合、5.1 の定義により判断が存在しなくなる——「判断なしで走る」は可能だが、**責任も存在しない**のであり、その状態を「問題ない」と報告する組織は、簿記上の無責を安全と誤読している（→5.3 laundering の完全体）。

三実験の結論を一文に置く。5.1 の区別は**境界線ではなく簿記の规格**である——境界（何が Reckoning で何が Judgment か）は领域と時代で動き続けるが、判断の三要素の规格は動かない（判断と認めたものには三要素を書かせる、書けないものは判断と呼ばない）。哲学の役割は線を引くことでなく、線が動いた迹を簿記する规格を遺すことである（→2.2 の歴史代数——境界自体の履歴代数、→4.1 分布計測の 5 章版）。

### 判断レビュー三分間 — 会議での Reckoning/Judgment 仕分け

5.1 の区別を会議の実务に落とす三分間を置く。決定候选を 1 件ずつ、三人が各自 1 分（総 3 分）で仕分け、**書き分ける**。「Reckoning で足りる」（計算・规則・既知分布で決まる）／「Judgment が必要（三要素のどれかが新開く）」／「わからない」。三分間の目的は正解ではなく**仕分けのズレの露出**で、三人の判定が割れた場所が、その組織で判断の定義が未合意の場所である（=CQ 候补、→4.2 の CQ 生成源としての会議——ハーバーマスの討議が「适用规則の选択」で割れる機制の会議実装、→3.1）。

割れ方の型を二つ置く。**型 A（Reckoning/Judgment 割れ）**：同じ決定を誰かは計算で誰は判断で決める——ここは 5.1 の三要素の欠落検査で**自動で判断側に倒す**（疑問があれば判断へ——5.1 の非対称原則：責任の过少配給より过多配給がマシ、末端は載せ过ぎて消えるより載せなくて増える方が修復しやすい、→5.3 accountability-check の会議版）。**型 B（わからない漏れ）**：三分間で「わからない」が 0 回の会議は、3.5 の UNKNOWN の席が会議にない証拠（偽って「わかった」が通行する討議——→6.2 誠実性の簿記其二と同じ検査）。

三分間の産出は会議事録でなく graph:// の Decision 候補ノード（grade:'E2'、refute_by 空で提出——→4.1 の E2 カードに空の refute_by は受理されないので、**三分間の産出は 24 時間以内に refute_by を載せるまで提出できない**、→字段の強制が会議の質量を後から拘束する設計）。

### 実行練習

1. あなたのシステムの「AI が決める」箇所をすべて挙げ、各々に reckoning / judgment の判定印を付けよ（定義三節のチェック表で）。judgment 印が付いた箇所に `JudgmentEvent` 型の登記（decider / revalidation_path / update_route）が存在するかを照合し、欠落は3.6 の `orphan_action` 検出（→3.6）で自動検出化するクエリを書け。
2. 「見せかけ承認」の実例をあなたの UI から1つ探して写真またはスクショのメモに記録し、実効的承認の条件（根拠の再検証解像度）を満たすように承認画面の情報設計を1枚書き直せ。どの情報を「根拠の再検証」に使うか、5.6 の監査ログ設計（次々節）を予習して接続せよ。
3. 保険解剖の症状(3)（経験の流出）を、あなたの組織の LLM 利用実態で調べよ：モデルの改善要求はどこに出るか、改善の主体は誰か。経験を自組織が取り戻すための最小の装置（更新経路の国内化）を1つ設計し、その変更級（→2.6）と承認者を条文引用で決めよ。

## 5.2 ハイデッガー — 手持ち性と現前性、被投性

キャントレル・スミスの区画（reckoning/judgment）は、どの層に何を配分するかの上層地図だった。この節から、その地図の**存在論的地盤**を掘る。設計された人工物が人間の行為の中でどう存在するか——透明に機能し、ある瞬間に不透明化し、その不透明化が世界を語らせる——の分析を持つ哲学者がマルティン・ハイデッガーである。『存在と時間』（1927）の道具分析は、一見すると設計書から最も遠い哲学に見える。実は反対で、**人工物の存在様式を最初に体系的に記述した存在論**であり、 observability（可観測性）、アラート設計、障害レビュー、ユーザーインターフェースの設計原理が、気づかず追随している（あるいは違背している）分析である。5.1 の「判断の器」の材質を、この節は決める。

### 手持ち性（Zuhandenheit）— 使うことで透明になる存在

ハイデッガーは「道具（Zeug）」から始める。ハンマーは、上手に使われている限り、経験に現れない。釘を打つことに集中している作業者の経験にあるのは釘と木材と曲がらないことであって、ハンマーではない。ハンマーは**手が届くところにある（zuhanden）**——機能に溶解して透明な存在である。これが手持ち性だ。

設計語彙に翻訳する。**最も成功した人工物は、使用者の経験から消えている。** SSO がログイン体験から消え、認証が「ログイン」という行為に溶解している状態。CI がデプロイの緊張から消え、「リリース」がボタン一つの手順に溶解している状態。1.4 の状況モデルが「文脈が明示されないほど成熟したシステム」を語ったが、ハイデッガーはその存在論的名字をくれる——成熟した人工物は手持ち的である。**透明性はバグではなく、人工物の存在様式である。**

ただし透明は虚空ではない。透明なハンマーが機能の中に沈んでいる基盤を、ハイデッガーは**用具連関（Verweisungszusammenhang、指示のつながり）**と呼ぶ。ハンマーは釘へ、釘は留め具へ、留め具は雨宿りへ、雨宿りは住居へ——道具はいつも「～のために」「～へ」と指し示す連鎖に埋もれて存在する。ハンマーの透明性は、連関全体が背景として静かに支えているから成立する。**1.3 の context graph は、この用具連関の人工物版である**——本書が既に一度接続した（文脈グラフ＝指示のつながりの実装）。5.2 を経由して接続を強化する：context graph の設計価値は「意味の明示」ではなく、**連関の維持**にある。グラフが壊れる（語彙の孤立、結合の失効、→4.3 断層B）とは、用具が手中から滑り落ちる存在論的事件である。

### 障害の三型 — 壊れ方が世界を現前化する

手持ち性は、壊れる。正確には三様に壊れる（『存在と時間』16節の区別を設計事故の語で並べる）。

- **欠如（Fehlender）**：ハンマーがない。使おうとした手に何もない——**存在しないことの発火**（4.5 の制約不足、CQ の載らない構造の体感形）。
- **不適合（Unpassende / Um-zu…Dazu…）**：大きすぎるハンマー。機能はするが目的に噛み合わない——**要求と実装の断離の体感形**（3.1「要求は満たされ目的は裏切られた」の現象学）。
- **妨害・破損（Aufdringliche / kaputt）**：壊れたハンマーがむしろ幅をきかせる——**故障した人工物が透明性の対極、最悪の可視性で現れる**（ダウンタイムの画面、赤いアラート、落ちた決済）。

三型すべてで、**道具は手持ち性から現前性（Vorhandenheit）へ転化する**——機能に溶解していたものが、眺められ、点検され、対象として眼前に現れる。しかもハイデッガーの核心はここから先にある：**現前化は欠陥ではなく、認識の発生である。** 壊れたハンマーを点検する視線が、初めてハンマーの「锤子性」（何をどんな仕方で果たしていたか）を明文化する。滑らかに使えている間は、連関も機能も意味も、明文化を必要としない——**必要なさ故に存在論は眠っている。**

本書が第2部・第3部で敷設してきたすべての「事件駆動の形式化」は、この眠りからの覚まし装置だった。契約違反の `ContractViolation` データ化（→4.4）、障礙の実例更新（→3.4）、回帰テストの `RegressionEvent`（→4.6）、unsat core（→4.5）——すべて、**障害を存在論的アクセスに変える機械**である。読者はもう設計原理として持有している：**障害はコストではなく、世界像の自己供述である。設計の課題は障害の撲滅ではなく、障害の聴取装置を常態として稼働させることだ。**

```python
# breakdown_ledger.py — 障害三型の分類登記(現象学的 observability の最小実装)
# 哲学: アラートは『壊れた』を告げるだけでなく『どの壊れ方か』を告げねばならない。
# 壊れ方の型が、現前化の仕方=取るべき点検手順を決めるからである。
from enum import Enum

class BreakdownType(str, Enum):
    ABSENT = "absent"          # 欠如: 期待された機能が存在しない(API 404, job 未起動)
    MISMATCH = "mismatch"      # 不適合: 動くが目的に噛み合わない(閾値が古い・語彙が別世界の)
    OBTRUSIVE = "obtrusive"    # 妨害: 故障そのものが前景化する(例外嵐、ループ、画面の赤)

def classify(alert: dict) -> BreakdownType:
    if alert.get("target_status") == "not_found":
        return BreakdownType.ABSENT
    if alert.get("executed_ok") and not alert.get("intent_held"):
        return BreakdownType.MISMATCH      # 実行成功+意図未充足 = 3.1 の体感形
    return BreakdownType.OBTRUSIVE
# intent_held の検査 = 4.2 の CQ 応答契約と 4.4 の postcondition の接続点。
# MISMATCH 検出には『目的が機械に読み込まれている』必要があり、
# それは 3.2 の goal form を要求木から読むことで成立する(→3.5 の expand())。
```

`classify` の中核が `intent_held` の判定である点を直視してほしい。**MISMATCH（不適合）は、目的が形式化されていない組織では検出不可能である**——3.1 の定理（telos なきシステムの良否は測定不能）の observability 版だ。ハイデッガーの三型分類は、アラート設計の空白を暴く：**多くの監視システムは OBTRUSIVE しか拾わない**（例外・ダウンタイム）。ABSENT（欠如）は「期待される機能の登録簿」（CQ・契約・goal form）がなければ、MISMATCH は目的の形式がなければ拾われない。**監視の盲点の分類学が、そのまま形式化の欠落の分類学になる。**

### 被投性（Geworfenheit）— 根拠の切断点としての設計開始

『存在と時間』の後半、人間分析（Dasein 分析）の中核概念へ移る。被投性とは、**私は常に、私が選ばなかった状況に既に投げ込まれて存在する**ことである。生まれた言語、属した時代、置かれた組織、今期の予算、前代のレガシーコード——設計者は無地点から設計を開始しない。開始の地点はいつも先に与えられており、その被投の根拠を設計者は基礎づけない（基础づけれない）。

これは設計理論としては既視感ある命題になる。**すべての設計体系には、設計体系が設計しない前提がある**（4.1 の憲章条二、CI 閾値の E4 宣言、3.1 の axiological root、3.5 の verification_horizon）。ハイデッガーの貢献は、これを認識論の瑕疵ではなく**存在論的構造**として置くことである。根拠の連鎖は必ず切断点で着地する——切断点があることは設計の失敗ではなく、設計の存在様式である。失敗は切断点を**隠すこと**にある（「これは前提ではなく事実です」という宣言。2.4 の「載らないもの」の追放、1.6 の記録しないことを記録しないこと）。

本書の設計imperative を再定式化する。**被投性は隠さず登記する。** 体系の前提（前提と選択した事項）は E4 宣言として、宣言者と日付と再検証期限付きで履歴代数に載る（→4.1 の `declared-by:`）。切断点を持つことは人間条件であり、切断点の見え方は統治の品質である。2.6 の承認フローが「フロー自身が L2 変更対象」（→2.6 条文5）と要求したのは、被投性の自己登記の制度化だった——**設計体系の前提は、設計体系の内部で、設計体系によって、変更可能に可視化されていねばならない。** これを本書では**被投性の民主化**と呼ぶ。AI システムの文脈では切実で、モデルの選択・ファインチューニングの判断・学習データの境界（ベンダーの被投性）は、利用側組織が引き受けていない被投である——5.1 の「経験の流出」の存在論的名字がこれである。

### 現前性と計算的世界像 — LLM が現前化を代行するとき

現前化（道具を眺められる対象に変えること）は、判断の前提作業である（壊れたハンマーを見つめ、何をしているものだったかを再定述し、判断が起きる）。ここに LLM が入ると何が起きるか。今日の LLM 使用の最頻出形態は、**現前化の代行**である——ログの異常を LLM に要約させる、障害の根拠を LLM に語らせる、レビューコメントを LLM に書かせる。

危険は代行そのものではなく、代行の**品質の非対称性**にある。LLM の現前化（再定述）は fluent であり、人間の手動現前化（泥臭いログ読み、メモ、ホワイトボード）は拙い。**拙い現前化は現前化した人間の判断を更新するが（更新経路、→5.1）、fluent な現前化は聞き手を更新しない**——流暢な物語は消費され、判断の材料としての記憶に残らない。5.1 の update_route 欠落が、ここでも発火する。設計imperative：LLM の現前化は、**消費ではなく点検に接続されたときにのみ**認める——要約は `ContractViolation` の core 名簿（→4.5）や RefinementTrace（→3.3）への**入力候補**として差し出され、人間の点検が確定したときだけ履歴代数に載る（→5.6 の Quarantined 設計の予告）。

### 手放しの設計 — 現前化された知識を更新経路に乗せる運用

更新経路の運用機構を、この節の中心設計として確定する（→5.1 の定義の第三要素が、ここで制度になる）。現前化（→5.2 の Zeitigung——過去のもの 현재의ものとして立ち現れる作用）には二種類ある。**fluent な現前化**——道具のように滑らかに現在の行為に組み込まれ、その起源も更新も意識されない（手順書の条項が「そういうもの」として運用される）。**ungenuine な現前化**——明示的に引用され、更新期限を問い返される（条項に落日・級・出典が付き、使うたびに問いが戻る）。本書の設計命令——**fluent な現前化を減らせ、という意味ではない。fluent に見えるもの全部の裏に、ungenuine な簿記を敷け**である（fluent であること自体は悪ではない——悪は、fluent な状態のまま更新経路が消えたとき起きる）。

```cypher
// revalidation-patrol — 更新経路の巡回(ungenuine 化の定期発火)
// 12か月使用され、一度も再検証(=根拠の引用元が更新・確認された事件)されていない
// 「生きている手順」= fluent の裏の空洞。E4 落日の巡回版(→4.1)。
MATCH (d:DesignDecision) WHERE d.status = 'active' AND d.at < datetime() - duration('P12M')
AND NOT (d)<-[:REVALIDATED]-()
RETURN d.dd_id, d.at, d.sunset, 'hollow-fluent' AS flag
ORDER BY d.at LIMIT 20;
```

`REVALIDATED` の定義を明記する——再検証は「読んだ」ではない。**根拠の引用元（観測・実測・上位規則）が確認され、確認者が登記された事件**である（→5.1 の revalidation_path が実際に歩かれたことの簿記）。読みっぱなしの再検証は再検証ではない（→8.5 の形式読解と実質読解の差の制度版）。巡回が hollow-fluent を出した場所では、共観セッション（→8.3 の再現前化の場）か審議槽（→6.6）の議題に自動で載る——**空洞の発見は、空洞を埋める席に接続されるときだけ機能する**（→4.6 の回帰テスト失敗時の ticket と同じ「発見→席」の配線原則）。

被投性（→5.2 の Geworfenheit——既に投げ込まれていることの肯定）とこの巡回の関係を一文明論的に結んでおく。伝統・手順・制度を「継承する」とは、fluent な手放しで使うことではなく、**投げ込まれたものを問い返しながら使い続けること**である。問い返す機構（落日・巡回・審議槽）を外した継承は、死んだ形式の自動反復になる（2.3 の制度の老化）。手放しの設計は、保守と革新の対立を消す——**更新とは、手放しを問い返すこと**であり、問い返された手放しだけが生き続ける（本書の歴史代数、→2.5 が「保存」ではなく「問い返しながら上書きする」代数だった理由が、ここで全章を貫く線として見える）。

### 手放しの破れ — 故障イベントを存在論のデータとして拾う

手持ち性の破れ（→前掲の現前化——道具が手を離れ、ただの物として立ち現れるevent）は、メタファーではなく現場で計測できる。锤が重いと感じる瞬間から、锤が「ただの鉄の塊」として意識されるまでの破れは、作業の停止・反復・検験の起動作為 as 現象を伴う。破れを障礙台帳（→3.4）に拾う際、三つの分類を使う。**破れ一：手放しの停止**（作業がその道具を要求する goal に戻ってこない——道具は動くが目的が止んだ：effect-verification 失敗、→7.3 の「效果が無い」）。**破れ二：手放しの抵抗**（道具が予期と違う振る舞い——観測値が E2 見通しの帯を外れる：N4 前提崩壊、→3.4）。**破れ三：手放しの透明化**（破れるべきものが破れずに記録も無い——伝感器オフライン・手動復旧の未登記：影子 act、→6.6）。

```cypher
// readiness-breakage — 破れの三分類(→3.4 障礙の Heidegger 目録版)
// 破れ二の例: 見通し帯の外れが継続している equipment
MATCH (eq:Equipment)-[:HAS]->(o:Observation {kind:'vibration'})
WHERE o.value > o.expected_hi AND o.at > datetime() - duration('P7d')
WITH eq, count(o) AS excursions
WHERE excursions >= 3
CREATE (ob:Obstacle {kind:'readiness-resistance', created:datetime()})
WITH eq, ob MERGE (ob)-[:ON]->(eq)
RETURN eq.id, ob.kind, 'inscribed';
```

破れ三（透明化）が最重要である——**破れない機械は存在しない。破れが記録されない系が存在するだけだ**（→1.6 の記録しない宣言との違い：記録しない宣言は設計された沈黙、透明化は設計されていない沈黙——2.6 の級の思想で言えば、沈黙にも級がある：宣言された沈黙は L1 相当の設計決定、非宣言の沈黙は簿記の空洞）。手放しの設計（→前掲）が最後に守るべきもの——**破れが現前化に化ける瞬間**（故障が「ただの事象」として流され、経験を通过せずに消える瞬間）を、破れ三の照会が見张っている。

### 透明化の目録 — 「破れないこと」が計られる三例

破れ三（透明化、→前掲）の実在例を三つ inscribe する（诊断は実例でしか老朽しない、→3.4 障礙の落日条約）。**例一：伝感器の沈黙**。振動伝感器が 11 時 40 分に応答しなくなり、告警は出ない——沈黙は「异常なし」として読数される（不在の証明がない系では、無警報=安全の偽装。処方：センサーの心跳（watchdog、5 分無通信=障礙 N4 起票——**不在を不在として登記する**）。**例二：手動復旧の未登記**。停まったポンプを作業員が手動で復旧、graph に act なし——次の自動停止规則が「復旧理由不明」で誤作動（影子 act、6.6。処方：手動復旧にも act 起票を UI から 1 操作で可能にし、**起票のコストを手動操作より低く**する——影子 act はコスト設計の失敗である、→8.4 single_plate と同じ原因）。**例三：バイパスの常习化**。保守中のバイパス（安全連鎖の無効化）が 2 週間継続——「一時期」が落日を持たない宣言だった（E2 horizon 字段の無い宣言、→4.1。処方：バイパス宣言に horizon と sunset を強制、超过で自動障礙）。

```cypher
// silence-scan — 心跳の止んだ sensor と落日超过の bypass を一并に
MATCH (s:Sensor) WHERE s.last_seen < datetime() - duration('PT5M')
RETURN s.id, 'sensor-silence' AS kind, s.last_seen
UNION
MATCH (b:Bypass {active:true}) WHERE b.horizon < datetime()
RETURN b.id, 'bypass-overdue', b.horizon;
```

三例の共有項を一文に置く——**世界が沈んだ場合、系は世界が消えなかったことにしてしまう**。消えたことを消えたと登記する設計（心跳・起票コスト・horizon）が、透明化を現前化（5.2 の本来の破れ）に戻す——破れは存在論の出来事だが、破れを消すのは簿記である。

## 5.3 なぜ確率的生成に責任を置けないか

5.1 の区画を、本章の中心命題が具体化する。**尤度は正統性ではない。** LLM の出力が「もっともらしい」ことと、その出力を世界へのコミットメントとして**引き受けられる**ことの間には、原理的な断絶がある。この節では、断絶の論理を精密にし、そして断絶を無視した設計の三つの失敗型——司令塔化、隠れ判断、責任の蒸発——を解剖する。5.2 の現象学が判断の材質を語ったのに対し、この節は確率の意味論を扱う。読者に必要な数学は条件付き確率の記号だけである。必要な哲学は「真理」と「正統性」の区別だけである。

### 尤度の意味 — P(next token | context) が意味しないもの

LLM の生成は本質的に条件付き確率の反復である：次のトークンは、これまでの文脈に対する確率分布から選ばれる（あるいは近似される）。この確率は**文脈内でもっともらしい続きの度合い**であり、つぎの三つではない。

**(1) 真理の度合いではない。** 「パリの首都は Paris です」も「パリの首都は Berlin です」も、文脈の設計次第で高い尤度を持ちうる（後者は皮肉・誤答データ・敵対的プロンプトの文脈で高まる）。尤度は**連続性の度合い**であって、対応の正しさではない。3.2 で `arg_type: 'plausible'` と `'logical'` を混ぜるなと書いたが、あの区別はここで根本の意味を持つ——尤度の体系は plausible の体系であり、logical の体系ではない。両体系は同じ文字列を表層に出力しうるが、**出力の意味（何が担保されているか）が違う**。

**(2) 存在の度合いではない。** 「2027年3月の夜勤逸脱 D-912 は深刻だった」を高尤度で生成することは、D-912 の存在を一切主張しない——文脈内の連続性として正しい確率計算の結果だからである。5.2 の現前化の代行が危険なのは、生成文が**主張の形式**（flat な直説法）で現れるのに、生成過程に**主張の機能**（コミットメント）が皆無だからだ。形式と機能のこの断離が、次の節の Quarantine 設計の存在論的理由である。

**(3) 正統性の度合いではない。** 正当な手続を経て承認された出力（2.6 の承認フローを通ったもの）と、高尤度の出力は、統計的に無関係である。正統性は手続の性質であり、尤度は分布の性質である。

三つの「ではない」を束ねる本書の定理（非公式、名前のない定理）を置く。**尤度の体系は、妥当性要求（→6.2 の理解可能性・真理性・正統性・誠実性）のどれも、単独では充足しない。** 尤度が最も近いのは理解可能性（fluency、受け取れる形）である——しかも唯一、LLM が大量に供給できる次元が理解可能性であり、他三者は外部配管（検証・承認・誠実性の登記）で供給するしかない。この非対称配分を設計に埋めない組織は、供給の豊かな次元（もっともらしさ）を、欠乏の次元（真理・正統）の**代理**として使用してしまう。代理使用の失敗が、以下に続く三型である。

### 失敗型一 — 司令塔化（the LLM as bridge operator）

LLM を判断連鎖の**決定地点**に置く設計。「AI が却下し、人間が機械的に承認する」（5.1 の保険解剖）、自動デプロイの go/no-go を LLM 評決に委ねる、クレーム回答を LLM が送り、後追い人間レビューは例外のみ——これらの共通構造は、**reckoning の卓越性（理解可能性＋膨大な候補生成）を根拠に、judgment 配分の主体に座らせる**ことである。5.1 の三条件（コミットメント・accountability 末端・更新経路）のどれを満たさない主体が、命令を出す位置にいる。司令塔化は能力の問題ではなく**位置の誤配**である。

構造的診断を一文で置く。**司令塔化は、尤度を正統性の代理として使う設計である**——「もっともらしい答を返すのだから、それで決めてよい」が暗黙の免状であり、5.3 の定理がその免状を無効にする。

### 失敗型二 — 隠れ判断（latent judgment）

より巧妙で、より多い失敗。「決定は人間が行っている、LLM は補助だけ」という設計で、L LM が**判断の前提を形成**している場合——判断の選択肢の提示順（アンカリング）、根拠の選別（何が証拠として並ぶか）、論点の枠（何について考えるか）を LLM が握っている状態である。人間の署名は形式上末端ノードに座っているが、**判断の材料形成（frame-making）が reckoning に移住している**。

隠れ判断は監査が最も難しい。JudgmentEvent の basis_reckoning（→5.1）に LLM 経路が明示的に登記されていれば検出可能だが、「担当者が参考までに見たメモ」は履歴に載らない（1.6 の NonRecordingRule の逆——**記録すべき相互作用が記録されていない**）。設計対応は判断材料の供給経路を**強制的に形式化**することである：判断画面に並ぶ候補・証拠・論点は、システムが `EvidenceBundle` として生成し、その生成過程（誰が・どの検索・どの LLM 補助で）を登記する。LLM に「自由にメモを作らせない」のではなく、**メモの流通を履歴代数に通す**（2.5 の原則の判断層への拡張）。

```cypher
// EvidenceBundle: 判断の材料形成の履歴化(隠れ判断の検出器)
CREATE (eb:EvidenceBundle {
  eb_id: $eid, judged_event: $jid,
  sources: $source_refs,                    // 検索クエリID・KB参照・文書版数
  llm_assisted: true,
  llm_role: 'frame-maker',                  // 'frame-maker' | 'candidate-generator' — 役割の自己申告必須
  frame_options: $options_json,             // 提示された選択肢と順序(順序は content である)
  generated_at: datetime()
});
MATCH (eb:EvidenceBundle {eb_id: $eid}), (je:JudgmentEvent {j_id: $jid})
CREATE (je)-[:JUDGED_ON {via: $eb_id}]->(eb);
// 検査(→6.4 の Rego に接続): llm_role='frame-maker' の JudgmentEvent の割合が
// 部門平均から外れたら E4 再審議の自動発火(5.1 の update_route の配管)。
```

`frame_options` に**順序まで**保存する設計の重要性。選択肢の提示順は中立的な表示ではなく content である（順序効果は判断研究の確立事実）。順序を保存しない EvidenceBundle は、frame-making の記録ではなく frame-making の否認である。

### 失敗型三 — 責任の蒸発（responsability evaporation）

三型目は、設計が責任を配分した**つもり**で、どこにも配分していない状態である。「AI が生成し、レビューが承認し、ユーザーが信頼した」——三段のそれぞれに主体がいるのに、誤りの帰責地点が存在しない。レビューの承認は実効的承認の条件を満たさない（5.1 の再検証可能性）。生成の主体（開発者）は「レビュー通過を信じた」。ユーザーは「承認済みを信じた」。三段の相互信頼が、帰責の環を**閉じずに素通りさせる**——責任が蒸発するのではなく、**設計が責任の凝結点を作らない**。

蒸発の検査はグラフでできる：`JudgmentEvent` から `RESPONSIBLE_FOR` の末端まで、辺を辿って到達できる経路が存在しない事件は、構造上帰責不能である（→3.6 の orphan_action 同型）。4.6 の scorecard に `unanchored_judgment` を加える。

```cypher
// unanchored judgment 検出(3.6 検査の judgment 層版)
MATCH (je:JudgmentEvent)
WHERE NOT (:Agent {kind: 'human'})-[:RESPONSIBLE_FOR]->(je)
   OR NOT EXISTS { MATCH (je)-[:JUDGED_ON]->(:EvidenceBundle) }   // 材料形成の否認も帰責不能
RETURN je.j_id, 'responsability-evaporation' AS diagnosis;
```

### 三型の統一診断 — 「尤度で正統性を代替した度」を測る

三型は別々ではなく、一つの欠乏の三つの埋め方である。**正統性（承認・手続・帰責）の供給が不足している組織は、尤度（もっともらしさ）で埋める**——司令塔化は決定地点での埋め、隠れ判断は材料での埋め、蒸発は記録での埋め。よって防腐の設計（→6.3〜6.5）は、尤度の遮断ではなく**正統性の供給装置**として設計される（Harbermas の妥当性要求の機械化、→6.2）。本書の第3部後半が「防腐層」と「討議」を同じ章で扱うのは、この供給の一体性のためである。

節末に、5.1〜5.3 の配分表を置いておこう。この表は5.4〜5.6 の実装の設計仕様そのものである。

| 機能 | 誰が（部品） | 誰が（人） | 履歴代数での登記 |
|---|---|---|---|
| 候補生成（reckoning） | LLM・検索・KB | — | `CandidateSet`（モデル版・seed・温度つき、→5.4） |
| 妥当性の機械検証 | Rego・SHACL・sat 判定器 | — | `ValidationVerdict`（core 名簿つき、→4.5・6.4・6.5） |
| 世界へのコミットメント | なし（機械はコミットできない） | 人間エージェント（実効的承認） | `JudgmentEvent`（末端＋材料＋更新経路、→5.1） |
| 経験の更新 | — | 政策・契約の変更者 | `Commit`（2.5 橋）、`policy-diff` PR |

表の第三行の「なし」を直視することが、第3部の通過儀礼である。AI への不信ではなく、**コミットメントという行為の存在論**が「なし」を作る。機械は約束を出せるが、約束に**縛られることがない**——縛られることがない主体の約束は、約束ではなく信号である。

### 責任の簿記 — JudgmentEvent 台帳の運用と矛盾処理

判断を人の側に置いた（→5.1）なら、責任の配線を簿記として完成させねばならない——責任は哲学的名言ではなく、照会可能な関係名簿であるべきだ（→4.4 の「証拠＝データ」の倫理版）。JudgmentEvent 台帳の運用規則を四条、確定する。

**其一、一判断一末端**：世界を変える許可（transition の実行、→5.5）に紐づく各 JudgmentEvent には、単一の decider と単一の accountability terminal（名簿上の ID）を要求する（→5.1 の定義の DB 強制：je_id ごとに `accountable_to` が 0 件または 2 件なら、その判断は CI で reject——2 件の場合は連署であり、連署は単一末端に解消規則（主任筆）を持つ）。**其二、委任の連鎖は簿記される**：A が B に判断を委任するとき（→7.2 の委任深度）、JudgmentEvent に `delegated_from` 辺が載り、A の残余責任が数値で残る（残余責任の数値化：委任後の A が保持する拒否権・監査頻度・落日周期）。**其三、判断の矛盾は台帳の事件**：同一状況スレッドで両立しない判断が登記されたら（例：停止を承認した thread で稼働継続を承認）、矛盾検出クエリが OverrideEvent 相当の事件（→3.4 の N3）を起こし、両判断の decider の共観セッションを自動起案する（→8.3 の矛盾の併置で解決へ）。**其四、判断の履歴は判断者本人に開かれる**：自分の JudgmentEvent 全列と、その後の実測（effect_verification、→7.3）と反論（Objection、→8.4）の突合面——判断者は自分が判断者であることを簿記で知る（→8.2 条件一の自己履歴アクセス権）。

```cypher
// accountability-check — 責任の簿記の invariant(→5.6 の invariant 文化の倫理版)
MATCH (je:JudgmentEvent) WHERE je.at > datetime() - duration('P1Q')
OPTIONAL MATCH (je)-[:ACCOUNTABLE_TO]->(p:Person)
WITH je, count(p) AS terminals
WHERE terminals <> 1
RETURN je.je_id, terminals, CASE WHEN terminals = 0 THEN '責任の蒸発' ELSE '末端二重化' END AS fault;
```

この invariant を test_ownership.py の一テストとして載せること（→4.6）。責任が消えるのは制度の自然現象ではなく、**スキーマが許していること**の帰結だと書く——`ACCOUNTABLE_TO` の不在をクエリが弾かないグラフは、責任の蒸発をデフォルトにしている。本書が「責任の簿記」という語をあえて会計語で置く理由も注いでおく——簿記は、残高が合わなければ帳簿全体が疑われる。二重仕訳（判断の借方＝コミットメント、貸方＝引き受けた不確実性）が合わなくなる瞬間を機械が教えるUntil、責任は語りの側に残り続ける。

尤度→正統性の launderings（→5.3 の洗浄）への最後の防壁も、同じ簿記語彙で定義できる。**正統の残高**——各審議槽・各級・各落日が記録した「承認の実測（→2.6 の保留統計・四率）」の累計であり、これがマイナスに転じた領域（dissent 無視の連続・落日の空振り・forced-consent 発火）では、その領域の全ゲート判定に Warning が自動で添わる（正統の残高は、判定の正しさと独立に、判定の受け入れ可能性の帳簿である——4 妥当性要求の正統性欄の実在残高、→6.2）。

### 確率の約束 — 「70%」はコミットメントか

判断の三要素（→5.1）と 5.3 の中心命題を、一本の文で試す——**「この部品は 70% の确率で 30 日に故障する」はコミットメントか**。答えは三段で違う。(a) 単純な尤度の報告なら No（Reckoning の産出——世界の状態の記述に过ぎない、→5.1）。(b) この文に基づいて発注・停止・保険が動くなら Yes に**近づく**——文が行動の前提になるとき、コミットメントの条件（結果の引き受け）が現実化する。(c) Yes になる条件は、文の側に三要素が書けること——**誰が**この 70% を裏書け（末端）、**何が壊れたら**この文は退くか（根拠の反証条件、→8.5 falsifiable_if の確率版：「訓練分布がこの設备年代の試料を含まないならこの数是退く」）、**誰がいつ**70% を 40% に更新できるか（更新経路）。

校准（calibration——予言确率と実現频度の一致）は a の品質を上げるが、c の三要素を**自動では産生しない**（Brier score の優秀なモデルの持ち主も、誤警報の末端には書かれない——**校准は精度の美德で、責任の機制ではない**）。よって本書の确率要求は一つ——**确率の周囲を契約で包め**：`prob(pump_fail,30d)=0.7` の記録には basis（訓練窗口・适格設备の分布）、withdrawal_conditions（退く条件の列表）、updater（更新の末端と級）の三列を強制する（→llm_call の四版本簿記、→8.5 offer schema と同じ形）。三列が書けない确率文は、判断の語に化けた記述である——→5.3 の laundering（尤度が正統性の語に洗濯される）は、三列の欠落という**具体的な簿記事故**としてのみ発現する。

### 練习解答の型 — 尤度文を契約文に書き换える

本章の練习 2（確率文の契約化）の解答の型を一つ示す（書式を見せないと練习は形式だけ残る、→4.2 CQ 三分間と同じ趣旨）。問題文「ポンプ 3 の 30 日故障确率 0.68」の契約文化：

```yaml
prob_claim:
  claim: "pump3.fail within 30d = 0.68"
  grade: E1                          # 尤度自体は実測級(モデル出力)
  basis: { model: surv-v7, train_window: 2019-2025, fleet_age_mix: "平均4.1年" }
  refute_by: "該 pump の年代区分が訓練分布外なら 0.68 は退く"   # →4.1 E2 カードと同一字段
  commitment:                        # 三要素(→5.1)を尤度の周囲に載せる
    seat: 保全長(段1承認者)           # 末端:この数に基づく停止/継続の承認者
    cost_of_error: "停止コスト 18h/回 vs 故障コスト 72h+安全風険"  # 結果の引き受けの宣言
    updater: { who: 可靠性工程師, grade: L2, period: 月度 }        # 更新経路と級
  calibration: { brier_90d: 0.11, note: "fleet 全体では良好、pump3 年代区分では未測" }
```

注目点は calibration の note で、**全体では校准できているが問題の pump3 の区分では未測**という状態が実务では最频（集合の校准が個別の末端を救わない——5.1 の判断が個別である理由の統計版）。この note が commitment.seat を人間にしている理由であり、契約文の全体が「0.68 に誰がどこまで背負うか」の一頁になっている（尤度→契約の書き换えは、5.3 の中心命題「确率は末端を産生しない、末端は席位である」の機械的な実現である）。

### 実行練習

1. あなたの組織の LLM 利用場所を全部挙げ、それぞれを司令塔化／隠れ判断／蒸発の三型で診断せよ（混合型もある）。診断根拠として、5.3 の定理の三「ではない」（尤度≠真理・存在・正統）のどれが当該場所で違反されているかを1か所ずつ特定せよ。
2. `EvidenceBundle` をあなたの判断画面で実装した場合の最小版（`llm_assisted` と `frame_options` の保存だけ）を設計し、その実装が「メモの流通を履歴代数に通す」をどこまで達成しどこで裏切るかを2段落で評価せよ（裏切りの例：ブラウザ外のコピペ、口頭）。
3. 5.1〜5.3 の配分表をあなたの組織の現状で書き直せ（現状はどの機能を誰が担っているか、登記は存在するか）。差分から最優先の修正1つを決め、2.6 級 L2 の変更説明文（何の供給不足を尤度で埋めていたか）を書け。

## 5.4 純粋関数としてのLLM

失敗三型を解剖した（→5.3）。では LLM をどこに置けばよいのか。答えは先に置いておく——**LLM は純粋関数のふりをして部品の位置に座る。決定ではなく候補を返す。** この節では「純粋関数のふり」の設計を精密に作る。数学的には LLM 呼び出しは純粋関数ではない（同一入力でも出力が揺れ、モデル版・推論エンジン・batch 構成で挙動が変わる）。それでも**純粋関数の契約で包む**ことが設計の核心である——副作用を持たせない、状態を持たせない、環境（seed・温度・モデル版）を引数に露出させる、出力を `Candidate` 型で強制する。純粋性は事実ではなく**契約**であり、契約は偽りうるが、偽りは検査できる（→4.4 の DbC が既に教えた通り）。

### 純粋関数の三条件 — LLM 呼び出しに課すもの

純粋関数の定義三条件を、LLM 呼び出しの設計条件へ翻訳する。

**其一、副作用を持たない。** 呼び出しが外部世界を書き換えない——KB へ書かない、承認状態を変えない、外部 API を叩かない。生成した文章を「そのまま現場へ送る」設計は副作用そのものである。LLM 呼び出しの返り値は、呼び出しの直前と同一の世界の中に置かれる。世界を変えるのは、呼び出しの**後**に座る検証とコミットメントの配管（→6.4〜6.5、→5.1 の JudgmentEvent）だけである。

**其二、状態を持たない。** 会話履歴の保持を LLM クライアントの内部に隠さない。セッションのメモリは呼び出し側の状態であり、毎回明示的に引数として渡す（context は引数、cache は呼び出し側の策略）。状態を隠された LLM は reckoning の部品ではなく、**人格を持つ代理**として設計に滑り込む。5.3 の隠れ判断は、状態を持つ LLM（過去の対話で「方針」を覚えてしまった assistant）から最も容易に発生する。

**其三、環境変数を引数に露出する。** seed、temperature、モデル版、推論パラメータ、システムプロンプトの版——これらは「呼び出しの状況」ではなく**呼び出しの一部**である。隠された環境変数は再現性を殺し、再現性のない reckoning は検査不能である（4.5 の判定を版数で固定したのと同じ理由）。

「純粋関数のふり」と呼ぶ所以はここにある。同一引数でも出力は揺れる。だが**揺れのすべての原因が引数に公開されていれば**、出力分布は引数の決定論的関数とみなせる（seed 固定で再現、seed 非固定でも分布の再現）。設計が必要とする決定論は「出力の一致」ではなく「**生成過程の復元可能性**」である。

```python
# llm_wrapper.py — 純粋関数仮装の LLM クライアント(本章の部品)
# 哲学: このクラスは LLM を『部品』に降級させるのではない。
# 部品の契約を与えることで、部品が判断の位置へ移動する経路を塞ぐ(→5.3 三型の排除)。
from __future__ import annotations
import hashlib, json, time
from pydantic import BaseModel, Field

class LlmEnv(BaseModel):
    """呼び出し環境の完全公開。env のハッシュがそのまま trace id になる。"""
    model_ref: str                  # 例 'provider/model-vendor-name@2026-10-01'
    temperature: float = 0.0
    seed: int | None = None         # None は『分布サンプル』の宣言。隠さない。
    max_tokens: int = 1024
    sys_prompt_version: str         # プロンプトも版数管理(→2.4 の version 原則)
    def digest(self) -> str:
        return hashlib.sha256(
            json.dumps(self.model_dump(), sort_keys=True).encode()).hexdigest()[:16]

class Candidate(BaseModel):
    """LLM 出力の型。決断ではなく候補であることを型で強制する(後述)。"""
    text: str
    provenance: dict                # env digest + 入力 digest + 時刻
    # Candidate は commit 能力を持たない: .apply() メソッドを定義しない。
    # 「候補をコミットする方法」は Candidate の外側(JudgmentEvent)にだけ存在する。

class PureLlm:
    def __init__(self, transport):
        self._t = transport         # 生 HTTP クライアント。副作用は transport 側だが、
                                    # このクラスのメソッドは world を触らない(境界)。
    def generate(self, prompt: str, env: LlmEnv, timeout_s: int = 20) -> Candidate:
        t0 = time.monotonic()
        out = self._t.complete(prompt, env.model_dump())   # transport は純粋ではない。
        if time.monotonic() - t0 > timeout_s:              # だが wrapper は world-state を
            raise TimeoutError("llm call timed out")       # 一切書き換えない(契約)。
        return Candidate(
            text=out,
            provenance={"env_digest": env.digest(),
                        "input_digest": hashlib.sha256(prompt.encode()).hexdigest()[:16],
                        "at": time.time()})
```

`Candidate` に `.apply()` を**定義しない**設計を本章の中心に置く。型設計による配分：候補は自身を世界へ適用する手段を知らない。適用は Candidate の外の関数（`commit_candidate(candidate, judgment_event)`）で行い、その関数は `JudgmentEvent`（人間末端つき、→5.1）を必須引数に取る。**候補の適用 = 判断の登記**でなければならない、という設計不変条件が、メソッドの不在と引数必須で構造化される。5.3 の表（コミットメントの主体「なし」）が、ここで型系になる。

### 「temperature=0 でも決定論的でない」の取り扱い

実務家向けの注記を正直に置く。seed 固定・temperature 0 でも、GPU の batch 効果・推論エンジン更新・非決定な並列演算で出力は変わることがある（vLLM 等の公開済みの挙動）。よって「再現」とは**完全一致の保証ではなく、記録された環境による復元可能性**である——同じ env digest・同じ input digest で呼んだとき、出力は**分布の内部で説明可能**でなければならない（一致が崩れたら env digest の差分を疑う）。

```python
def repro_check(cand: Candidate, replay: Candidate) -> dict:
    if cand.text == replay.text:
        return {"repro": "exact"}
    # 不一致のとき、原因候補を env/input の差分として機械列挙する:
    diff = set(cand.provenance.items()) ^ set(replay.provenance.items())
    return {"repro": "diverged", "suspect_factors": diff or "same-provenance!",
            "action": "same-provenance divergence → 推論環境の漂移。"
                      "JudgmentEvent の basis_reckoning 検証を E3 審議へ回す"}
```

`suspect_factors` が空（同じ provenance で別出力）の場合の扱いが重要である。**その不一致は「部品漂移」の宣言**であり、E4 ではなく E3 審議（→4.1・6.2）へ自動で回る。漂移の存在を例外で握りつぶさない設計——部品が約束から外れた事実を履歴代数に乗せる（4.4 の `ContractViolation` の LLM 版）。漂移は LLM 固有ではなく、すべての外部供給部品の性質である（ライブラリ更新、データセンター移行）。本章の設計は LLM を「特別に疑う」のではなく、**すべての外部部品に同じ復元可能性契約を課す**——LLM を例外扱いしないことが、司令塔化の防止でもある（例外扱いは特別地位の第一歩）。

### 候補生成の複合 — LLM × KB × 検索の reckoning 連関

純粋関数の部品の出力は、通常、単独で使わない。4.3 の retrofit、3.3 の EARS 化、4.2 の CQ 供給（b）——本書が LLM を認める場所はいずれも候補生成であり、しかも候補は**複合の reckoning**（LLM + KB 検索 + 形式検証）の中間産物である。複合の連結設計を置いておく。

```python
def candidate_pipeline(llm: PureLlm, kb, prompt: str, env: LlmEnv) -> list[Candidate]:
    # 複合 reckoning: LLM 単独ではなく、KB の語彙制約付きで候補を作り、
    # 形式検証(→4.5 の judge)を通過した候補だけを『生き残り候補』として返す。
    c1 = llm.generate(prompt, env)                       # 第1の reckoning
    terms = kb.match_terms(c1.text)                      # KB 語彙への結合(→2.4 mapping)
    c2 = llm.generate(refine(prompt, c1, terms), env)    # 第2の reckoning(同じ env 明示)
    survivors = [c for c in (c1, c2) if validate_with_kb(c, kb) is None]
    # validate_with_kb: SHACL/Rego の暫定版(→6.4・6.5 で本格実装)。
    # 通過しない候補は discard せず Quarantine へ送る(→5.6 で実装)。
    return survivors or [quarantine(c1, c2)]             # ゼロ候補は「候補ゼロ」の宣言
```

`or [quarantine(...)]` の設計判断——候補が全滅したとき、pipeline は空配列ではなく**Quarantine レコードを返す**。「候補ゼロ」は世界の状態であり、記録されるべき事実である（4.1 の残余保存、→5.6 の Quarantined 状態）。例外を投げて pipeline を止める設計は、候補ゼロを世界から消す——5.3 の蒸発型が、配管の例外処理に潜んでいる例として注ぐ価値がある。

### 純粋性の監査 — 「LLM が世界を書いた」経路の検出

最後に、契約が守られ続けているかの検査を置く。副作用禁止の機械検査は完全には不可能だが、実効的な検出は可能である——KB・外部 API の書き込みイベントに `actor` を必須化し、`llm:*` を actor に取る書き込みを**ゼロで監視**する（2.6 の override 目録化と同じ「禁止でなく目録」の原則——`llm:*` actor 自体を禁止せず、出現した瞬間に L2 審議を自動発火させる）。

```cypher
// actor 簿記の検査: LLM を名乗る actor による世界変更の検出(常態ゼロ・出現即審議)
MATCH (c:Commit) WHERE c.actor STARTS WITH 'llm:'
RETURN c.commit_id, c.actor, c.at, 'escalate-L2' AS action
ORDER BY c.at DESC LIMIT 10;
```

この検出が「LLM に書かせない」ではなく「LLM に書かせた事実を隠さない」である点を強調する。運用上、LLM が直接書き込むことを認める場面はある（草稿領域への執筆）。その場面では actor を `llm:` で始め、**書き込み先を `Draft` 領域に限定する Rego ポリシー**（→6.4）を通す。純粋性の契約が守れない場所では、純粋性の代わりに**簿記の誠実さ**を置く——設計の契約は段階的に弱めうるが、弱めた事実を登記し続ける限り、腐敗は進行しない（4.1 憲章条二の反復）。

### LLM 呼び出しの契約書 — pure function ラッパーの仕様表

純関数としての LLM（→前掲の設計）を、本書の契約語（→4.4）で完全に仕上げる。呼び出し経路を一つの関数 `llm_call(ctx, prompt_id, schema)` に統一した上で、その契約の三語を書く。

**precondition**：(a) `prompt_id` は登録済み prompt 台帳（version 付きの git 管理対象——プロンプトは code であり、変更は級つき、→2.6 の級体系に prompt も載せる）に存在する。(b) `ctx` の各値は観測簿記（時刻・出所・等級、→1.5）を伴う——無出所の文字列を ctx に混ぜない。(c) `schema` は json-schema（→7.3 の output schema・→8.5 の offer.schema）で、**出力の形だけが約束され、内容は約束されない**——この非対称が 5.4 の核心である（形を縛り内容を縛らないのは、内容の責任を呼び出し側に残す配線——schema に「内容の正しさ」を表す語（`"description": "正しい予兆"` 等）を書いた瞬間、契約は嘘になる）。
**invariant**：`llm_call` はグラフ・DB・外部 API に**一切書かない**（read-only 不変条件——→5.3 の末端欠如の実装保証。書き込みは transition の仕事、→5.5）。テスト（→4.6 の層二）で transport の mock への書き込み呼び出し計数を常に 0 に保つ。
**postcondition**：(a) 出力は schema に適合（適合外は呼び出し側で reject——LLM の再試行は**呼び出し側が同じ prompt_id で走らせる**——llm_call 自身の retry は禁止、retry も呼び出し側の決定だから）。(b) 呼び出し簿記（prompt_id・version・token 数・耗時・schema hash）を QueryLog に書く——**LLM の呼び出し自体が照会可能であること**（→4.3 のログ逆抽出が LLM 呼び出しにも走る：どの prompt が高频で、どの応答が decision 直前に使われているか）。

```python
# llm_call.py — 契約つきの単一経路(→5.6 の transport 注入の入口)
def llm_call(ctx: dict, prompt_id: str, schema: dict) -> dict:
    p = prompt_ledger.get(prompt_id)            # pre(a)
    assert p, f"unregistered prompt {prompt_id}"
    assert all(has_vitals(v) for v in ctx.values()), "ctx に無出所の値"  # pre(b)
    log = QueryLog(prompt_id=p.id, version=p.version, schema_hash=sha(schema))
    raw = transport.complete(p.body(ctx), temperature=0)   # 決定論は保証「しない」
    out = validate(raw, schema)                            # post(a)
    ledger_write(log, out_status=out.status)               # post(b)
    return out
```

契約書の最後の段落に**版本の簿記**を加える。prompt・schema・model・transport の四者の version が呼び出し簿記に揃って載っていない場、その LLM 応答の「再現」は哲学ではなく不可能である（→5.1 の更新経路の LLM 版——更新経路の第一歩は、何が更新されたかを特定できること）。四 version の欠落は層三の失敗（宣言と実在の突合テスト、→4.6）で CI が弾き、LLM 支援の一切の判断（→7.4 の propose ノードの応答）は、四 version 揃った呼び出しの産物だけを根拠にできる（→7.5 の why_action の candidate_env に prompt version が載る理由がここにある——説明可能性は version 簿記の下層で買える）。

### 実行練習

1. あなたの LLM クライアントコードに `LlmEnv`（model_ref / temperature / seed / sys_prompt_version の版数）を移植し、`Candidate` に `.apply()` がない状態で既存呼び出しを全部通す改修を1ファイル分やれ。通らなかった呼び出しは「候補を決定として使っていた」箇所の名簿である——名簿を 5.3 の三型で分類せよ。
2. `repro_check` を実際に3回走らせ（seed 固定／seed 非固定／モデル版変更）、三つの再現性プロファイル（exact / diverged+因子あり / diverged+因子なし）を観測せよ。「因子なし」を観測できなかった場合、観測できないことの何を疑うべきか（環境固定の過信）を1段落で書け。
3. `candidate_pipeline` にあなたの KB（2.4 の TBox と語彙）を接続し、候補ゼロの Quarantine レコードを1件作れ。その Quarantine が記録している「世界の状態」（どの語彙要求で LLM が全滅したか）を 4.2 の CQAmendment（→4.2）の提出に使う手順を5行で書け——失敗が仕様の供給源になる配管。

## 5.5 決定論的ステートマシン — トランジションに世界を閉じ込める

LLM は候補を返す部品に降級した（→5.4）。では、候補を世界への決定に変える配管は何か。この節の答えは、古典的で、地味で、そして疑いなく正しい——**決定論的ステートマシン（deterministic state machine）**である。状態・イベント・ガード・効果の四要素からなる機械。トランジションの正しさは設計者の責任として残り（5.1 の accountability 末端が機械の側にもある——ただし人間の設計として）、確率的要素は「候補生成」として遷移関数の**内側**にのみ閉じ込められる。AI 配線の設計として最も古く、最も監査可能なこの形を、本章は正式な「判断の器」として採用する。ハイデッガーの語を借りれば（→5.2）、ステートマシンは**判断の存在論的器（Behältnis）**である——コミットメントが置かれ、履歴が残り、更新経路が接続される場所。

### 四要素 — 状態・イベント・ガード・効果

定義を本書の条件付きで敷設する。

**状態（State）**：機械の世界に関於する**機械の知識**のスナップショット。状態は「世界の真実」ではなく「機械が読み取れた世界の形」である——1.2 の分節と1.5 のラベルの語で言えば、状態は機械の存在論の現在の版である。状態遷移図が粗いシステムは、世界を粗い存在論で扱う（→2.1 の切断が制御フローに現れる）。

**イベント（Event）**：世界から機械への入力。センサー・API・人間の操作・時刻。イベントは世界の切り取りであり、イベントカタログが「この機械が聞き取れる世界の範囲」を定義する（1.6 の録音規則の制御版）。

**ガード（Guard）**：遷移を許可する**決定論的述語**。本章の設計命令の芯——**ガードに確率を入れてはならない**。ガードは「確信度 0.87 以上」ではなく「`vib >= threshold && shift.type == 'night'`」でなければならない。理由の再掲：ガードが確率的だと、遷移の責任が分布に分散し、unsat core のような名簿が作れない（4.5 の名前付き制約が機能しない）。尤度はガードの内側には入るが、ガードの**境界判定**にはなれない。境界の決定は常に人間の設計として固定される（境界決定の版数化、→2.4）。

**効果（Effect）**：遷移が世界へ及ぼす変更。KB 書き込み、通知、外部呼び出し——効果はコミットメントの物理であり、**コミットメントは必ず登記を伴う**（JudgmentEvent・Commit、→5.1・2.5）。効果を持たない遷移は内部記憶の更新であり、これも登記される（状態変更も履歴に載る——2.5 の代数）。

```
状態遷移の許可条件(設計不変条件):
  allowed(s, e, s') ⇔ Guard(s, e) ∧ Deterministic(Guard) ∧ Logged(Effect)
  # 「決定論的」の定義: 同一 (s, e, 入力ログ) で allowed が一致する。
  # LLM の揺れは allowed の入力にならない。揺れは候補生成の内側に閉じ込められる。
```

### なぜ決定論なのか — 説明責任の復元可能性

ステートマシン採用の第一の理由は説明責任の実装可能性である。「なぜこの状態になったか」の答えは、**履歴チェーン（state, event, guard-valuation, effect）の再生**である。再生可能なら、説明は物語ではなく計算である（7.5・8.3 の説明設計の形式的床——5.1 の basis_reckoning がついに満たされる）。確率遷移の混じった機械では、再生に「分布からの偶然のサンプル」が混入し、説明の連鎖が断ち切れる——断ち切れた場所が、5.3 の蒸発型が再定着する足場になる。

第二の理由は監査である。監査者は機械の実行を追うのではなく、**設計不変条件の違反不在**を確認する。`Deterministic(Guard)` と `Logged(Effect)` が CI で検査可能なら（→5.6 の guard 純度 lint・effect 登記アサーション）、監査はサンプリングから機械的保証へ変わる。5.3 の配分表で「機械が供給できる唯一の次元は理解可能性」と書いたが、ステートマシンは理解可能性を**監査可能性に転化する装置**でもある——遷移図そのものが設計の可読文書であり（UML 状態機械図の伝統）、コードと図の自動同期が 1.5 の「ドキュメントとコードのずれ」問題を解決する（→4.6 の scorecard の一項目）。

### 「LLM は遷移関数内で候補生成としてのみ許される」の意味

本章の中心命令の正確な意味を分解する。三つの禁止と一つの許可。

**禁止一：ガード評価への LLM 参加。** `guard = llm.judge(...)` は構造の汚染（尤度が境界判定になる——5.3 定理の違反が制御フローに定着する）。**禁止二：状態定義への LLM 参加。** 状態の名前と状態間グラフは設計時に固定される（状態の増設は設計変更・2.6 級 L1 以上）。LLM に「今の状態を分類」させる設計（隠れ判断の機械版）は禁止——状態分類は入力側 ACL（→6.3）で決定的に行う。**禁止三：効果の実行主体への LLM 参加。** LLM が効果を実行しない（actor 簿記、→5.4）。**許可：遷移関数の内側の候補生成。** `candidates = llm.generate(...)` は許される——ただし候補がガード（決定論）と検証（6.4〜6.5）を通過したものが効果に昇格する経路だけを通る。

許可の位置の意義をハイデッガー的に言い換えると（→5.2）、LLM は**世界を現前化する語彙の供給者**としてのみ機械の内側にいる。機械が「何を candidate として提示するか」を LLM が決める——frame-making の権利（→5.3 の EvidenceBundle の frame_options が機械側で生まれる場所）。frame-making の権利を遷移関数の内側に閉じ込めることが、隠れ判断の機械版の防止である。

### 機械の設計 — 「設計者の責任が残る」の構造

ステートマシンが「判断の器」になる（OUTLINE の章主題）の意味を確定する。遷移の正しさは設計者の責任として残る——これは倫理的な注釈ではなく、**causal locus の所在**の記述である。世界の決定が (s, e, Guard) で機械的に決まるなら、その決定の**因果的に責任ある地点**は設計時（Guard を書いた時）に固定される。運用時は因果の連鎖から外れる（運用時の人間の役割は監視・停止・設計変更——8.4 の Human-in-the-Loop の正しい位置）。

この因果所在の固定が、責任の設計を可能にする。設計時に残された判断（guard の閾値、イベントカタログ、状態分割）は、**E4 宣言として登記可能**でなければならない（4.1・5.2 の被投性の民主化）。機械の設計書には「設計時に下された判断の目録」を持てるようにする。

```python
# sm_audit.py — 設計時判断の目録(DesignDecisions)を状態機械メタデータに保持する
# 哲学: guard の数値はすべて『設計時に人間が下した判断』である。
# 判断の目録なしのステートマシンは、被投性を隠した機械である(→5.2)。
from dataclasses import dataclass, field

@dataclass
class DesignDecision:
    guard_ref: str        # どの guard のどの数値/述語か
    value: str            # 'threshold=45mm/s'
    rationale: str        # 根拠の自由文(2.5 の intent と同型・必須)
    decider: str          # 誰の判断か(P-114)
    verif_class: str      # 4.1 の等級(E1〜E4)
    review_due: str       # 再検証期限(2.3 の保持寿命)

DESIGN_DECISIONS: list[DesignDecision] = [
    DesignDecision("night.detect@vib>=45", "45", "現場の体感異常との対応が実測で確認済み(2026-06 計測)",
                   "P-114", "E1", "2027-06"),
    DesignDecision("escalate@repeat_count>=2", "2", "『2回で重大』は班長の経験則。E3 審議で adopt(→2.6 級L2)",
                   "P-201", "E3", "2027-03"),
]
# CI 検査: すべての guard 数値は DESIGN_DECISIONS に参照を持つこと(→4.6 の生成テスト)。
# 目録のない数値 = 匿名の E4 宣言 = 4.1 の declared-by 規則の機械違反。
```

`repeat_count>=2` の決定的根拠が「班長の経験則」である例を見よ。1.1 の暗黙知が、ここで**形式化の縁の宣言**として着地している——経験則は消去されるのではなく、E3 として登記され、再検証期限を持つ。第1章の暗黙知論が、第3部で監査対象のメタデータに変わる瞬間である。

### 状態機械の階層化 — 判断の器のフラクタル

単一の巨大ステートマシンは設計できない（状態爆発）。階層化する（HSM、statecharts の伝統）。設計として重要なのは、階層間の**イベントとガードの契約**である——上位マシンは下位マシンの内部状態を読まない（情報隠蔽）、下位マシンは上位マシンへ抽象化イベントのみを送る。DDD の境界コンテキスト（→6.1）とステートマシンの階層は、同じ原則（意味の隠蔽と明示的翻訳）の二つの実装である。

階層化が判断の器をフラクタルにする：各サブマシンは自身の guard・effect 登記を持ち、上位への出口に EvidenceBundle を接続できる（→5.3）。夜勤検知のサブマシンが「検知」の候補を出し、上位の点検割当マシンが「着手」を決定する——判断の連鎖が機械の階層に沿って登記され、人間の accountable ノードが連鎖の各段に接続する（3.6 の共同遂行の I-42 構造が、ここで制御フローになる）。

### ガードの解剖 — 誰が guard() に値を渡すのかの入力供給問題

遷移関数の設計を、さらに一段細部へ下ろす。`transition(s, e)` の正しさは `guard(s, e)` の正しさに依存し、`guard` の正しさは**入力の供給経路**に依存する。この入力供給の簿記を放置すると、決定論的なステートマシンは「ゴミを決定論的に処理する機械」になる（ガベージ・イン・ガベージ・アウトは、決定論では防げない——防げるのは**供給の簿記**だけである）。設計規則を四条置く。

**其一、ガードは観測の版数を読む**：`guard` が入力に使う各値は、観測時刻・出所・単位・信頼級を伴う（→1.5 テレメトリのノード化）。`if (temp > 80)` ではなく `if (temp.value > 80 AND temp.freshness < 5min AND temp.grade >= 'B')` が本書のガードの形である。**其二、ガードの入力集合は遷移ごとに宣言される**：`DESIGN_DECISIONS` に「transition A-7 は変数 {temp, vib, load} をガードに読む」と宣言し、CI で guard() 実体の読取変数集合と宣言の突合を行う（→4.4 の振る舞い仕様のステートマシン版——宣言と実体の突合は境界部品の宿命である、→1.5）。**其三、ガードの UNKNOWN はガード失敗と別の値**：観測欠損時は「条件不成立（deny）」と「地平超（UNKNOWN→安全側既定）」を分離する（→3.5 の三段構えのガード実装）。分離しないと、センサー故障が常に deny になり、運用がセンサー故障を「安全」と誤読する。**其四、ガード変更は code review より重い**：ガードは L2 級の変更（→2.6）で、DesignDecision 登記＋落日つき再検証が必須——ガード関数の一行変更が世界を変える許可の条件そのものを変えるからである。

```python
# guard_ledger.py — ガード入力の宣言簿記と突合(CI テスト)
GUARD_INPUTS = {          # 宣言(DesignDecision データの縮約)
    "A-7.start": {"temp", "vib", "load"},
    "B-2.stop":  {"vib", "human_present"},
    "C-1.reset": {"fault_cleared", "consent_level"},
}
def test_guard_inputs_match_declaration():
    for trans, declared in GUARD_INPUTS.items():
        read = static_readset(guard_of(trans))   # AST 解析で読取変数を抽出
        assert read == declared, f"{trans}: undeclared reads {read - declared}"
```

`static_readset` のような AST 解析を本書の CI に常設することは、5.1 の「判断の非封閉性」の局所的な勝利である——封閉的規則の集合を宣言と実体の一致の範囲で封閉的に見せる。宣言されていない読みを見つけた瞬間、その transition は未審査の変更を受けていたことになる（→6.4 の decision log と同じ思想：**境界で読み、境界で書く**）。

### ステートマシン設計の失敗目録 — 六つの典型的誤り

この節の実装語彙が揃ったところで、失敗の目録を六つ置いておく（設計の検収は失敗の目録で完結する、→3.5・4.6 の原則）。一、**ガード内 LLM**（遷移判定に非決定要素を混ぜる——5.5 の中心命令そのものの違反）。二、**ガードの孤児化**（guard 実体が宣言と違う変数を読む——上の突合テストが弾く）。三、**ログの別系統化**（遷移ログと業務 DB が二重簿記でズレる——単一 log store に一元化し、照会を一本に束ねる）。四、**安全側既定の不在**（UNKNOWN 時に「例外送出→運用の catchall 再試行」が暗黙の再 act になる——既知の事故パターン、→3.5）。五、**権限のステート漏れ**（transition の実行権限が states/policies 表に無く、呼び出し元コードの if に住む——L2 級変更の非登記）。六、**落日なしの状態追加**（新状態が永遠に未検証で残り続ける——DesignDecision の sunset なし登録は CI で reject）。六つ全部に共通する診断文は一つ——**機構は作った、簿記を作らなかった**。本書の第三部全体の主題（→5.3 の責任、→5.6 の残余）が、ステートマシン設計では「簿記」の名で現れるのである。

### ステートマシンの可視化 — states/policies の_ttl_表現と絵にしない理由

5.5 の遷移表（states・policies）を、コードの dict でなくグラフ（TTL/Cypher）に載せる設計を一度肯定し、そして一つの留保で締める。肯定の理由は三条。**其一**、遷移表をグラフに載せると、障礙モデル（→3.4）と接合する——`Transition -[:GUARDED_BY]-> (E4前提)` の辺が結べられ、前提の落日が遷移の UNKNOWN として導出できる（→3.4 複合式一の機構実装）。**其二**、監査簿記（→6.4 AuditEvent）が遷移ノードを指せる——事件が「状態名」の文字列でなく**宣言された遷移そのもの**の実例になる（簿記と設計が同じ語で結ぶ、→1.4 の宣言と実在の突合がここで可能になる）。**其三**、transition 台帳は CQ の対象になる——「B-2 stop に到达する全路径は?」（到达性照会）「C-1 reset を贯通する guard の集合は?」（不変条件の調査、→4.5 z3 への入力の供給）。

```turtle
# states/policies の RDF 表現(断片)
@prefix sm: <urn:tsurugi:sm:> .
sm:B2-Stop a sm:Transition ; sm:from sm:S1-Run ; sm:to sm:S3-Halt ;
  sm:guard [ sm:reads sm:vib, sm:human_present ; sm:e4_dep <urn:onto:e4/sensor-continuity> ] .
```

留保を一つ——**絵にするな、照会させる**。状態機械の可視化（図の描画）は状態爆発で実用を失い、描かれた図は必ず古くなる（docs の落日対象、→A.1）。遷移表の价値は描画ではなく照会にあり、CQ として闻かれる形でだけ保たれる（→4.2 の CQ 統治——設計物の可読性は描写でなく質問の席で維持される）。可視化ツールを持つチームは、まず遷移表の CQ 三条（到达性・guard 集合・落日依存）を CI に載せる——質問が先、絵は後。

### 実行練習

1. あなたの主要業務フロー1本を四要素でステートマシンに書き下ろし（12状態以内）、全 guard を決定論の述語として書け。「確信度が高ければ」という guard を書いた記憶がある場合、それを（a）決定的述語へ落とし込むか（b）候補生成の Quarantine（→5.6）へ構造を変えよ。変更の DesignDecision 登記（rationale・decider・review_due）を作れ。
2. `DESIGN_DECISIONS` をあなたの既存コードの if 節から機械的に走査し（grep で十分）、目録なしの数値を5つ拾え。5つの verif_class を決め、E3 のものの審議記録の形式（6.2 で本格化）を1枚設計せよ。
3. 5.4 の `candidate_pipeline` を HSM のサブマシンに接続し直し、上位マシンが読むサブ出力を「抽象化イベント＋EvidenceBundle」に限定するインタフェース（Pydantic で2クラス）を定義せよ。インタフェースを通さないサブ状態の露出を CI で検出するアサーションを1本書け。

## 5.6 実装 — トランジション関数内にLLMを閉じ込めるラッパー

5.4 の部品（PureLlm・Candidate）と5.5 の器（決定論的ステートマシン）を、動く一本のコードに接続する。本節の実装対象は、3.3 以来走らせてきた夜勤振動検知の続きである——世界設定は同じでよい。実装の中心は三つ。(1) 明示的ステートマシンと、遷移関数**の内側だけ**で LLM を呼ぶラッパー。(2) LLM 出力がガードを通過しなかったときの `Quarantined` 状態の設計。(3) 「判断を保存する」監査ログ——`TransitionLog` が判断の器の内容物となる設計。コードは Python 3.11、実行前に読解する価値があるのは `TransitionLog` と `quarantine` の部分である。

### 器と部品の実装 — 遷移関数の内側限定

```python
# sm_impl.py — 夜勤検知 HSM のサブマシン(遷移関数内に LLM を閉じ込める)
# 哲学: LLM の呼び出し箇所は transition() の『候補生成』ブロックだけである。
# 行番号で位置が決まっていること(構造)が、方針(Rego、→6.4)より先に守る設計である。
from __future__ import annotations
from enum import Enum
from dataclasses import dataclass, field
from llm_wrapper import PureLlm, LlmEnv, Candidate
from sm_audit import DesignDecision

class S(Enum):
    IDLE = "idle"
    PROPOSED = "proposed"       # LLM 候補が SHACL/Rego 暫定検証を通過し、人間承認待ち
    ESCALATED = "escalated"     # 人間 JudgmentEvent 確定後の実行中
    QUARANTINED = "quarantined" # 候補が検証を通過しなかった世界
    CLOSED = "closed"

@dataclass
class Event:
    kind: str                   # 'vib_high' | 'inspect_done' | 'quar_ack'
    payload: dict
    actor: str                  # 'sensor' | 'P-114' | 'clock' — 入力 actor 簿記(→5.4)

@dataclass
class Machine:
    state: S = S.IDLE
    llm: PureLlm = None
    env: LlmEnv = None
    kb: object = None
    log: list = field(default_factory=list)

def guard_vib_high(m: Machine, e: Event) -> bool:
    # 決定論的ガード(数値は DESIGN_DECISIONS 参照、→5.5)
    return e.kind == "vib_high" and e.payload["vib"] >= 45

def transition(m: Machine, e: Event, judgment=None) -> None:
    """遷移関数。LLM は PROPOSED 遷移の候補生成ブロックでのみ呼ばれる。
    judgment は JudgmentEvent(→5.1)。None で呼べる遷移は世界を変えない。"""
    # --- 候補生成ブロック(唯一の LLM 接触点) -------------------------------
    if m.state == S.IDLE and guard_vib_high(m, e):
        cand = m.llm.generate(
            prompt=f"機械{e.payload['m']} 振動{e.payload['vib']} 夜間。点検候補と根拠を JSON で。",
            env=m.env, timeout_s=20)
        verdict = m.kb.validate(cand)        # 6.4/6.5 の暫定版(決定論)
        if verdict is None:
            m.state = S.PROPOSED
            m.log.append(TransitionLog.created(
                m, "IDLE->PROPOSED", e, guard=guard_vib_high,
                candidate=cand, note="候補生成のみ。世界は未変更(→5.4 副作用禁止)"))
        else:
            m.state = S.QUARANTINED
            m.log.append(TransitionLog.created(
                m, "IDLE->QUARANTINED", e, guard="validation-fail",
                candidate=cand, quarantine_reason=verdict))
        return   # ← PROPOSED/QUARANTINED は確定遷移。以後の人間判断を待つ。
    # --- 確定遷移(人間判断を必須引数に取る) --------------------------------
    if m.state == S.PROPOSED and e.kind == "inspect_done":
        if judgment is None:
            raise ConsentRequired("escalation requires JudgmentEvent")  # 5.4 Candidate.apply不在と同型
        m.state = S.ESCALATED
        m.log.append(TransitionLog.created(m, "PROPOSED->ESCALATED", e,
                                            guard="human-consent", judgment=judgment))
        return
    if m.state == S.QUARANTINED and e.kind == "quar_ack" and judgment is not None:
        m.state = S.CLOSED          # Quarantine の開封も人間判断必須(→下記設計)
        m.log.append(TransitionLog.created(m, "QUARANTINED->CLOSED", e,
                                            guard="quar-ack", judgment=judgment))
        return
    raise IllegalTransition(f"no transition for ({m.state}, {e.kind})")
```

`ConsentRequired` の設計を設計不変条件として強調する。世界の状態を変える遷移（ESCALATED）は `JudgmentEvent` を要求し、欠けると例外になる——5.4 の「候補を適用する方法は JudgmentEvent の外に存在しない」が、遷移関数の引数強制で二重に守られた。**遷移関数の構造で守り、配管（Rego）で守る**——この二重化（defense in depth）が第6章へ橋を架ける。

### Quarantined 状態 — 通過しなかった候補の行方

Quarantine は「LLM の失敗を捨てる場所」ではない。**通過しなかった候補が示す世界の状態を保存する場所**である（→5.4 の `or [quarantine(...)]` の宣言の実現）。Quarantine レコードは三つの問いに答えられる形で持つ。何を生成したか（candidate 原文）、なぜ通らなかったか（verdict の core 名簿、→4.5）、そして**その世界の何が壊れているか**（KB 側の問題の可能性——5.3 の unsat 両仮説の再演）。

```python
@dataclass
class QuarantineRecord:
    q_id: str
    candidate_text: str
    fail_reason: dict          # {'stage': 'shacl'|'rego'|'kb-terms', 'core': [...]}
    competing_readings: list   # ['LLM 生成の誤り', 'KB 制約の陳腐化(→4.5)'] — 両方保存
    opened_by_transition: str
    ack_required_level: str    # 2.6 の級: 開封(=CLOSED への承認)の級。デフォルト L1
    created_at: float

def quarantine(m: Machine, reason: dict) -> QuarantineRecord:
    """Quarantine の開封(承認)にも JudgmentEvent を要求する設計。
    開封を放置すると、Quarantine は『見逃し』の隠れ家になる(→6.6 の見逃し率)。"""
    return QuarantineRecord(q_id=new_id(), candidate_text="…",
                            fail_reason=reason, competing_readings=[...],
                            opened_by_transition=m.log[-1].t_id,
                            ack_required_level="L1", created_at=now())
```

`competing_readings` を両方保存する理由は 4.5 の unsat 両仮説と同一である（記録が誤り／制約が陳腐化）。Quarantine を「LLM のミス」と単独解釈で閉じる運用は、5.2 の聴取装置の自己裏切りである。Quarantine の統計（stage 別・時間帯別の失敗率）は週次審議の議題に自動で回る（→6.2 の討議への供給）。開封の級（`ack_required_level`）は、Quarantine が大量発生したときの「見逃しを放置するコスト」を組織が意識するための調整弁である——級を L1 から L2 に上げる決定自体が、防腐層の過剰遮断／見逃しのトレードオフ運用の記録になる（→6.6）。

### 監査ログ — 判断を保存する TransitionLog

本章の完成形がここにある。`TransitionLog` は単なる実行ログではなく、**判断の器の内容物**である——5.1 の JudgmentEvent・basis_reckoning・update_route の三条件を満たす機械側の供給物として設計する。

```python
@dataclass
class TransitionLog:
    t_id: str
    from_state: str; to_state: str
    event: dict                  # 入力イベント(payload+actor 簿記)
    guard_eval: str              # ガード述語の『評価過程』(式と実測値。結果だけではない)
    candidate: dict | None       # LLM 候補(原文+provenance: env digest, input digest)
    judgment: dict | None        # JudgmentEvent リンク(decider/revalidation_path/update_route)
    note: str
    @classmethod
    def created(cls, m, edge, e, guard, candidate=None, judgment=None,
                quarantine_reason=None, note=""):
        return cls(t_id=new_id(), from_state=edge.split("->")[0], to_state=edge.split("->")[1],
                   event={"kind": e.kind, "payload": e.payload, "actor": e.actor},
                   guard_eval=f"{guard} @ {e.payload}",   # 評価過程の保存(→8.3 の説明の床)
                   candidate=(candidate.provenance | {"text": candidate.text}) if candidate else None,
                   judgment=judgment, note=note)

def export_to_graph(m: Machine, driver):
    """ログを Neo4j の履歴代数へ載せる(2.5 橋と同型)。ステートマシンは
    世界像の『振る舞い版』であり、その履歴も同じ墓標代数に乗る。"""
    with driver.session() as s:
        for L in m.log:
            s.run("""
            CREATE (t:Transition {t_id:$t_id, from:$f, to:$t, at:datetime()})
            SET t.event=$ev, t.guard_eval=$ge, t.candidate=$cand
            WITH t
            OPTIONAL MATCH (je:JudgmentEvent {j_id: $jref})
            FOREACH (_ IN CASE WHEN je IS NULL THEN [] ELSE [1] END |
              CREATE (t)-[:ANCHORED_IN]->(je))
            """, t_id=L.t_id, f=L.from_state, t=L.to_state,
                 ev=L.event, ge=L.guard_eval, cand=L.candidate,
                 jref=(L.judgment or {}).get("j_id"))
```

`guard_eval` に**評価過程**（式と実測値）を保存する点が、8.3 の反実仮想説明の機械的床になる——「なぜ ESCALATED になったか」への答えは、`vib=51 >= 45` という評価事実と、その制約の DesignDecision（→5.5 の rationale）への参照で構成される。物語ではなく再生である（→5.5 の説明＝再生）。`ANCHORED_IN` 辺で Transition が JudgmentEvent に接続される——判断の連鎖の機械側がグラフで人間の側に anchor され、5.3 の unanchored 検出がここでも機能する。

### 器の腐敗検査 — ステートマシン自体の防腐

最後に、機械の機械による監視を三つ置く。(1) **幽霊遷移検査**：`Transition` ノードで、`to_state` が設計遷移図に存在しないものは実装漂移（設計とコードのずれ、→1.5）。(2) **孤立候補検査**：`Candidate`（`Transition.candidate`）で `ANCHORED_IN` も `QuarantineRecord` も持たないものは、世界に到達しなかった候補の隠滅——5.4 の残余保存の違反。(3) **判断不在の成功遷移検査**：`to_state ∈ {ESCALATED, CLOSED}` で `ANCHORED_IN` なしは 5.3 の蒸発型の機械発火——CI でゼロを強制する（禁止でなく目録、2.6 の原則が自己適用される）。

```cypher
// 幽霊遷移・孤立候補・判断不在の三検査(scorecard 拡張、→4.6)
MATCH (t:Transition) WHERE NOT EXISTS {
  MATCH (:TransitionDesign {from: t.from, to: t.to}) }
RETURN t.t_id, 'ghost-transition';
```

第5章の設計はこれで閉じる。読者は第3部半ばで、AI を「司令塔」から「部品」へ降ろす配管を一本手にした——ただし本節の検査が警告しているように、**この配管は自己保身を持たない**。遷移図を書き換える者、guard の数値を黙って変える者、Rego をバイパスする shell 脚本——配管の外側から配管に触る権力が残っている。その権力の設計が第6章（防腐層）であり、防腐層自身の防腐（6.6）である。
