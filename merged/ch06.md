## 6.1 防腐層（ACL）— DDDから来た翻訳の防波堤

第5章で LLM を部品に降ろし、判断の器を作った。しかし部品は孤立して動かない——外部世界と意味を交換する。この節から扱うのは、**意味の国境管理**である。設計語彙を供給してくれるのは、Eric Evans のドメイン駆動設計（DDD, 2003）であり、中心概念は防腐層（Anti-Corruption Layer, ACL）だ。Evans の原語での定義は簡潔だ——「自ドメインのモデルを、外部モデルの侵食から守る翻訳層」。本章ではこの概念を三段階で拡張する。第一に、Evans の ACL は組織間（他社システム・他部署）の概念だった——本書はそこに**生成されたテキスト**という新種の外部モデルを加える。第二に、防腐の対象を「モデル」から「意味の保持（→2.3）」へ読み替える。第三に、防腐層自身が権力装置であることの自覚（→6.6 への予告）。防腐層を設計しない組織は、外部の意味に侵食されるか、外部を拒絶して孤立するかの二択に残される。

### 境界コンテキスト — 同じ語が別の世界で別の意味を持つ

DDD の前提概念、限界コンテキスト（bounded context）から敷設する。Evans の観察は現場的だ。「注文（Order）」という語は、営業システム・物流システム・会計システムで、状態遷移も有効期間も責任主体も異なる**別の概念**である。同じ語彙を共有していると思うこと自体が事故で、正しくは三つのドメインが三つの Order を持つ。DDD の解決は、ドメインごとにモデルを分離し（境界）、境界で**明示的な翻訳を置く**ことである。2.4 のマッピング（skos:closeMatch、`exactMatch` の格上げ承認）が既に翻訳の制度だった——Evans は制度の前に配管を設計した人である。

限界コンテキストの存在論的内容を本書の語彙で確定しておく。**境界コンテキストとは、一つのオントロジーが主権を持つ領域である**（→2.6 の「名前空間は主権、マッピングは外交」の DDD 由来の正当化）。コンテキスト間の語彙の一致は外交問題であり、外交の失敗形態（他国の語彙の輸入による自国主権の侵食）に Evans は名前を付けた——**conformist（追随型）**：外部モデルに丸ごと従う。廉価だが、外部の概念区分が自ドメインの思考を規定してしまう。保全現場が ERP のコード体系で現場の異常を語りはじめる瞬間（→2.4 の `sameAs` 事故の組織版）がこれである。

### 防腐層の構造 — 邦訳装置としての三部品

ACL の内部構造を本書の系で定義する。防腐層は翻訳器ではなく、**翻訳の制度を通す配管**であり、三部品からなる。

1. **正規語彙ゲート**：外部の語を自ドメインの正規語彙（→2.4 の TBox・skos）へ写す。写せない語は翻訳失敗として記録する（黙殺しない——残余保存、2.1）。
2. **構造変換器**：外部モデルの構造を自モデルの構造へ組み替える（外部の 1:N が自国の 1:1 を壊さない）。
3. **邦訳契約の版数**：翻訳規則そのものが版数管理される（→2.4 の version、→2.5 の履歴代数）。翻訳規則の変更は L1〜L2 級の変更である（→2.6 の外交手続）。

```python
# acl_core.py — 防腐層の最小骨格(邦訳装置)
# 哲学: ACL は『正しく翻訳する』層ではない。翻訳の失敗と成功を区別し、
# 失敗を歴史に残し、規則を版数で変えられるようにする層である(誠実さの配管)。
from dataclasses import dataclass, field

@dataclass
class TermMapping:
    src_vocab: str          # 外部語彙の識別(例 'erp:kanyu_cd')
    src_term: str
    tgt_term: str           # 正規語彙(例 'Shift.type')
    mapping_kind: str       # 'exact' | 'close' | 'broad' — 2.4 の skos と同語彙
    rule_version: str       # 邦訳契約の版数(変更は L1+ 承認、→2.6)

@dataclass
class TranslationFailure:
    src_term: str; context: str
    reason: str             # 'no-mapping' | 'ambiguous(2 candidates)' | 'world-mismatch'
    candidates: list = field(default_factory=list)   # 候補は捨てるな(残余保存、→2.1)

def translate(acl: dict[str, TermMapping], term: str, ctx: str) -> tuple | TranslationFailure:
    m = acl.get(term)
    if m is None:
        return TranslationFailure(term, ctx, "no-mapping")
    if m.mapping_kind == "close":
        # close の通過は『暫定同一』の宣言。close を exact へ格上げするには
        # 承認委員会(→6.2 の討議)を通す。ACL は格上げを翻訳しない。
        return (m.tgt_term, "provisional", m.rule_version)
    return (m.tgt_term, "committed", m.rule_version)
```

`candidates を捨てるな` の一行を防腐層の設計哲学として強調する。翻訳失敗の候補記録は、2.5 の LostMeaning（→2.5）と 4.3 の SubThresholdQuery（→4.3）と同じ系列——**制度が拾えなかった意味の保存庫**である。防腐層が翻訳失敗をログに垂れ流すだけなら、それは誠実な防腐層ではない。失敗が CQAmendment（→4.2）と TermMapping 改訂（外交の条約改訂）の供給源になる配管が、防腐層の新陳代謝である。腐敗していない防腐層は、翻訳失敗の統計から自身を更新し続ける。

### LLM時代のACL — 外部の「知」はモデルだけでなく生成文本身である

Evans の ACL が想定する外部は、仕様を持つシステムだった（他社 ERP、レガシー、SaaS）。LLM 時代に外部の性質が変わる。**外部からの流入物が、固定されたモデルではなく、毎回生成されるテキストである。** 保全現場の例で言えば——保守マニュアルの十年分の PDF を RAG 検索し、LLM が生成的に組み替えた「回答」が、KB（第1部・第2部のオントロジー）へ知識候補として流入してくる。

この流入の危険は、Evans の conformist が**加速した形**で現れることにある。LLM の文章は fluent（理解可能性が高い、→5.3）で、邦訳契約を通過しない語彙（正規語彙にない概念、消された区別、発明的な統合）を**もっともらしい表面の下に大量に運び込む**。手書きの他社仕様書なら人間が読んで防げた侵食が、生成文の洪水では人のレビュー総量で防げない。よって LLM 時代的 ACL は、Evans の三部品に加えて三つの追加要件を持つ。

其一、**流入の型強制**：生成文は KB へ直接書けない。Candidate 型に降格される（→5.4 の `.apply()` 不在）。ACL の出口に座る候補の型が `Candidate` であれば、ACL の出口は世界変更権を持たない（→5.6 の actor 簿記の制度側）。

其二、**語彙の白名単通過制**：生成文の用語は正規語彙マッピングを必須とする（TBox 語彙への `REFERENCES` 解決、→3.5 の REFERENCES 辺と同型）。解決不能語は TranslationFailure として残る——**解決できない語を含む文は、全体ごと棄却ではなく、当該語を Quarantine した部分構造で保持する**（→5.6 の Quarantine の ACL 版。全体の棄却は、残余まで棄却してしまう——2.1 の原則が防腐層でも適用される）。

其三、**来源の簿記**：流入文に provenance を要求する（検索された典拠・生成モデル env digest、→5.4 の provenance）。典拠なき文は防腐層の門で `E4 宣言` として扱われる（→4.1 の declared-by 匿名禁止）——誰が語ったか分からない文の重みは、宣言の重み以下であってはならない。

### 防腐と外交の弁別 — ACL が孤立主義に堕する条件

防腐層の失敗形態も正確に並べておく。防腐のしすぎは孤立である。DDD の文献が conformist の対極に置く隔離型（separate model、相互理解を断つ）は、防腐の完成ではなく**外交の破棄**であり、2.4 のマッピングの蓄積（意味の外交史）を凍結させる。凍結したマッピングは腐る（2.4 の version 失効、→4.3 の断層B 孤立構造）。防腐層が孤立に堕する条件を三つ挙げる。(1) 翻訳失敗が翻訳失敗のまま蓄積され、条約改訂（TermMapping 版数更新）に接続しない。(2) 正規語彙側の更新手続（2.6 の級）が遅すぎて、外部世界の概念変化が門を通れない。(3) 防腐層の運用者不在——門の番人がいない門は、門ではなく壁になる（→6.6 の統治問題の萌芽）。

Evans の比喩を直すと、ACL は**検疫所**であって入国禁止の壁ではない。検疫所の目的は、人が来て、働き、帰れるようにすることだ。防腐層の成功指標は遮断数ではなく、**通過した異物の無事故率**と、**条約改訂の頻度**である（6.6 で数式化する）。

### 条約の実物 — TermMapping v8 の YAML 全文と運用

理論を、条約の実物で締める。TermMapping の条約文件を YAML で一つの完全な例として書く（tsurugi の現場系 `site` と正規系 `master` の間、→6.3 の双方向検証・→2.6 の級・→6.6 の落日がこの条約の各行に埋め込まれている）。

```yaml
# mappings/v8.yaml — 条約の完全実例(site → master)
treaty: site-to-master
version: 8
signed_by: { site: "P-Tanaka(保全長)", master: "OntologyBoard(→2.6)" }
signed_at: 2026-03-14
sunset: 2027-03-14            # 落日(→6.6): 摩擦統計の実測なしには更新されない
mappings:
  - source: "pump-wobble"
    target: "vibration-anomaly"
    kind: close               # 語義の近さ(→exact/close/broad)
    loss_note: "site 語は手修理の歴史的含意を含む。正規系には含意を写さない。"
    rule_version: 3
  - source: "metallic-rattle"
    target: null              # 未解決(→TranslationFailure): v7 でも解決せず
    status: quarantined       # 残余保存(→2.1): 候補 3 件を添えて v9 審議に供給
    candidates: [cavitation-noise, bearing-spall-sound, loose-bracket]
  - source: "line-feels-off"
    target: null
    status: refused           # 正規系側の拒否(→6.6 条約G-1 の読み替え)
    reason: "検証可能な対応観測が存在しない。ただし審議には載る(→6.2)。"
friction_stats:               # 摩擦統計(→6.6 の四率の条約版) — 落日の実測材料
  translation_failures_q: 41
  broad_mapping_ratio: 0.12
  roundtrip_critical_q: 3     # →6.3 の構造 signature 比較
```

条約運用の三つの規則を確定しておく。**其一、条約はファイルであり、git に載る**（→2.5 のブリッジで RDF の Commit/Treaty ノードに化ける）。条約 v7→v8 の diff は、変更級 L2 の承認記録と set_log 副次記録を持つ。**其二、null と refused を区別する**。TranslationFailure のうち「まだ語が来ていない」（quarantined、供給源）と「正規系が対応観測を拒否した」（refused、政治的決定）は、統治の扱いが違う——前者は条約改訂の燃料、後者は障害台帳の実例（→3.4）。混同すると、拒否された現場語彙が未来の改訂で無断復活する（分類帝国の前兆、→6.6）。**其三、friction_stats が落日の証拠である**。条約は摩擦統計の実測なしには延長されない——翻訳の失敗率・broad 率・roundtrip CRITICAL 件数の三値が、審議の席に自動で載る。条約が「結ばれて終わり」にならない最後の設計である。

### 壁の偽免疫 — ACL が自系の腐敗を守る場合

防腐層の最も意外な失敗形を置いて、この節を閉じる。ACL は外部の漏洩を防ぐが、**自系の腐敗を外部の目で検知できなくする**ことがある。壁が厚いと、外部系からの「お宅の正規語彙は現場と遊離している」という反証（→4.2 の CQ の外部発火）が TranslationFailure として門の外で消える——防腐層が、自系に対する環境の反証能力まで遮断する。検出設計を一つ置く。**TranslationFailure の送信者分布**を計測する——壁の内側からの失敗ばかりで、外側（site 系・他社 API・現場 UI）からの失敗がゼロの条約は、壁が環境との接触面ごと塞いでいる疑いがある（→8.1 の stale_obstacles と同じ「実例が来ない」型の病）。外側からの失敗が門に届かない場合、届かないこと自体を計る器——site 側の未翻訳語の棚卸し（→B.1 練習3 の TermMapping 照合）——を条約の義務として先に引いておく。防腐は浸透圧で設計する——門は選ぶが、窒息してはならない。

### 門の一週間 — 翻訳イベントの実録（三事件）

6.1 の機構を、一 week の実録で缔ぶ（概念は事件で検収される、→各章の実証様式）。**事件一（水曜 3:14）**：site の `metallic-rattle` 報告が門で TranslationFailure——v8 条約 quarantined のまま（→6.1 YAML）。候选 3 件が添えられ、Quarantine に登記、審議槽に自動起票（→2.1 残余条約の運用）。処理中ではない——**保留の簿記**である（→3.5 UNKNOWN 三段構え）。**事件二（金曜 11:40）**：master 側の新 TBox 語 `vibration-anomaly.v2` が site 側の既存語 2 語と**両方**に近いいきい値（one-to-many の出口風険）。門は master→site 方向の発信を止め、**条約贸易の議題**に（→2.6 の条約贸易——分類変更は級つき、→6.3 の roundtrip CRITICAL の静的先取り）。**事件三（土曜 2:02）**：site の下請け作業員が UI で选択できない語で輸入（`line-feels-off` の続報）。門は refused を返すが、UI には refused の**理由と審議行きのリンク**が載る（→8.5 の面板——拒否は拒絶ではなく討議の招待、→6.2 の討議が翻訳の境界で開く形）。

三事件の共有項を一つずつ名乘る——いずれも**門が「通す/通さない」以外に「審議に載せる」第三の輸出を持っている**こと。防腐層が門番でしかない場合、失敗は現場の側で消える（→6.1 壁の偽免疫）。第三輸出を struct として持たせる設計（TranslationFailure → Quarantine → DelibSlot の連鎖、→「検査と席の接続」原則の門版）が、6 章前半の中心命令である。

### 翻訳負債の台帳 — 訳せなかったものを載せる場所

防腐層の台帳（→前掲）は訳された対応（TermMapping）を載せる。だが防腐層の真実の費用は、**訳せなかったもの**に積む——site の語で master に対応がなく、報告も act も起きないまま沈黙した区別（→6.3 の不可視损失の静態形）。翻訳負債の台帳を一本持つ。字段は四つ：**term**（site 側の語）、**tried**（試した候选と失敗理由——quarantined/refused/forced）、**touched**（その語が実際に世界に触れた痕跡——現場メモ・日誌の URI。無則負債は債务でなく債务の候选）、**age**（試みてから何四半期生きたか）。

```cypher
// translation-debt — 未訳の site 語で、世界に触れた痕跡のあるもの
MATCH (t:SiteTerm) WHERE NOT (t)-[:MAPPED]->()
  AND (t)-[:OCCURRED_IN]->(:FieldNote)          // 触れた痕跡
  AND t.first_seen < datetime() - duration('P2Q') // 2 四半期生存
RETURN t.term, t.first_seen, count { (t)-[:OCCURRED_IN]->(:FieldNote) } AS touches
ORDER BY touches DESC;
```

触れた痕跡のある未訳語は、**その語でしか処理できない事件が再発している**証拠で、条約審議の上位議題に自動で載る（→6.1 の第三出力=審議に載せる、の台帳版）。age の列が訳語の落日である——4 四半期触れない未訳語は台帳から降ろす（負債の台帳が負債そのものになるのを防ぐ——A 章の落日条項と同じ自己适用）。この台帳の哲学を一文で置く：**翻訳の成功は対応の数で測れず、翻訳の失敗は負債の台帳があるか測れる**。

### 実行練習

1. あなたのシステムが外部から受け入れている語彙源をすべて列挙し（ERP・SaaS・Excel・Slack・LLM 回答）、各々に TermMapping 台帳の版数があるかを調べよ。版数を持たない語彙源は「条約のない貿易相手」である——最初の条約（10語だけの TermMapping v1）を作り、変更級（2.6）のどの級で運用するかを決めよ。
2. LLM 回答を KB へ候補として流入させる配管を、上の `translate` に通す形で設計せよ。解決不能語の Quarantine レコードに、その語の**周辺文**（前後2文）を保存する意味を、2.5 の LostMeaning との対比で1段落書け。
3. 防腐層の孤立化三条件（上の (1)(2)(3)）をあなたの組織に当てはめ、該当する条件があれば、その条件を作っている運用（誰の怠慢ではなく、どの手続の欠落か）を特定し、6.6 への問題提起として1ページ書く。

## 6.2 ハーバーマス — 討議倫理と四つの妥当性要求

防腐層の部品（→6.1）を設計する前に、防腐層が**何を通過させ、何を止めるのか**の基準を持たねばならない。遮断の基準を権限や taste に置けば、防腐層は検閲になる（→6.6 の倫理的問題がここで発生する）。この節は基準の調達である。調達先はユルゲン・ハーバーマス（Jürgen Habermas）の普遍語用学と討議倫理である。「会話のたびに人間が必ず提起している有効性要求——理解可能さ・真実・正しさ・真摯さ——は、そのまま出力検証ゲートの設計図になる」というのが本章の背骨であり、OUTLINE がハーバーマスを第6章の思想に拠えた理由である。哲学の章として読み進めていただきたいが、節の終わりに Rego 方針への対応表が置かれる。設計図としてのハーバーマスは、比喩ではなく部品表である。

### 普遍語用学 — 会話の前提として「必ず提起される」もの

ハーバーマスの出発点は倫理ではなく語用学である。どんな発話——嘘でも皮肉でも論文でも——は、発話者が**暗黙に提起（erheben）し、受け手が暗黙に問いうる**四つの有効性要求（Geltungsansprüche）に従属する。

**理解可能性（Verständlichkeit）**：発話は共有語彙と文法で理解できる形でなければならない。理解不能な発話では、真偽を問う以前に何も問えない。
**真理性（Wahrheit）**：発話の内容が状態的世界の状況と一致すること。発話は検証要求に晒されう（反証可能で）なければならない。
**正統性（Richtigkeit / 正当性）**：発話行為がその文脈で**言ってよい**ものであること——発話の社会的適切さ（命令してよい立場か、この話題をこの場で扱ってよいかなど）。
**誠実性（Wahrhaftigkeit）**：発話者が自らの意図を欺いていないこと——発話は意図の表明として信頼に値すること。

四要求の構造的特徴を三点押さえる。其一、**外在化可能性（Einlösbarkeit）**：要求は提起されるだけで充足されたことにはならず、充足は**承認**を必要とする。承認は他の者によるものなので、要求充足は本質的に社会的である。其二、**取り引き性（Kontraktcharakter）**：要求が破られたとき、会話は破棄ではなく**追撃**に入る——「どういう意味？」「本当に？」「なぜそんなことを？」という**追撃発話（Forderungsätze）**が会話の自己修復機構である。其三、**四要求は独立**である：嘘は理解可能で正当な発話でありうるし、真実で不誠実な発話（悪意の真実）がありうる。独立だからこそ、四つの検査は四本必要である。

設計の語彙で言い換えると——**発話の妥当性は、単一の尤度ではなく四次元のスコープである**（→5.3 の「尤度は妥当性要求を充足しない」の完全版）。理解可能性のみが機械供給可能で、残りは承認配管を要する（5.3 の非対称配分がハーバーマスから逆輸入される）。

### 発話検証と出力検証の同型性 — 妥当性要求は検証ゲートの設計図である

本章の中心主張へ入る。LLM・他システム・人間の言葉を KB へ流入させる防腐層の検証ゲート（→6.4〜6.5 の Rego/SHACL）の検査項目は、四要求のそのまま機械写像として設計できる。対応表が本書の部品表である。

| ハーバーマス要求 | 発話検査（会話） | 出力検証ゲート（KB 流入） | 機械/人間の配分 |
|---|---|---|---|
| 理解可能性 | 語彙・文法の理解 | 正規語彙解決（→6.1 TermMapping）・スキーマ妥当性（SHACL、→6.5） | 機械決定論 |
| 真理性 | 反証要求への開開放性 | 典拠簿記＋sat 整合判定（→4.5）・制約通過（→6.5） | 機械＋人間 E3 |
| 正統性 | 発話権限・文脈適切性 | 書き込み方針（Rego、→6.4）・承認級（→2.6）・agent 種別 | 機械（方針）＋制度 |
| 誠実性 | 発話者の意図一致 | `intent` 登記・宣言者必須（→2.5・4.1 の declared-by） | 制度（登記強制）＋人間審議 |

表の第四行の意味を強調する。**誠実性は検査できない——登記させるしかない。** 「本当にそう思ったか」は機械の判定対象ではない。だから防腐層の誠実性実装は、**宣言者の名前の必須化**（4.1 の E4 `declared-by:` 規則の防腐層版）と、**`intent` 自由文の必須化**（2.5 の原則）である。誠実性の検証は検証ではなく**追跡可能性の設計**として現れる——嘘は後で暴けるようにする（Quarantine と OverrideEvent の目録化、→2.6・5.6）。ハーバーマス自身が「誠実性は証明不能、信頼は経験と追撃からのみ」と書く通りで、機械化の形は検証でなく簿記なのである。

同型性の深層を一文で置く。**健全な会話と健全な KB 流入は、同じ構造——要求提起→機械的暫定受理→追撃可能化——を共有する。** 防腐層の理想形は、発話を止める門ではなく、**追撃が可能な形で受理する門**である（通過＝追撃要求の登録。→6.3 の round-trip 測定、→6.5 の報告書設計）。

### 討議倫理 — 妥当な規則は討議から生まれる

ハーバーマス倫理の中核命題（討議原則 D）：規範は、影響を受けるすべてが理想的話状況での討議において合意しうるものでなければならない。理想的話状況（herrschaftsfreie Kommunikation）の条件は、参加の非制限、発言機会の均等、主題提示の自由、強制の排除——**強制のない合意**のみが妥当性の供給源である。

この理想が設計に要求するものは、現実的な四つの配線である。(1) **参加の非制限**：防腐層の検証規則（TermMapping・Rego・SHACL shapes）の変更提案に、影響を受けるすべての現場が提出権を持つ（→2.6 の不服従のパス・L0 提出権の拡大版）。(2) **発言機会の均等**：審議の記録（E3 の審議記録、→4.1）に発言の偏り統計を残す（少数発言者の不在が規則の妥当性欠如の指標）。(3) **主題提示の自由**：Quarantine・TranslationFailure・TranslationFailure・unsat core（→4.5）の統計が審議の議題に**自動で上がる**こと（議題選定権の機械化ではなく、議題供給の自動化。選定は人間が残す——8.4 の人間介入点の議論層版）。(4) **強制の排除**：審議で決まらない争点を、システムが黙って既定値で実行しない（既定値=E4 宣言＋期限）。

### 「強制される合意」の矛盾 — システムにおけるハーバーマスの限界

しかし——理想の話状況と、ゲートは両立しない。ゲートは発話を**強制的に**遮断する。「通過できない語を含む文は部分拒否される」（→6.1）は、参加の非制限でも発言機会の均等でもない。ハーバーマス自身の枠組みで言えば、システムは**妥当性の供与者ではなく、妥当性要求の強制執行装置**である。執行は討議の代替ではない。

この矛盾を隠さないための設計原則を、本書は**防腐層の討議剰余（discursive surplus）**として置く。**すべての強制執行は、その執行への不服従を制度的に保持する。** Rego 遮断は OverrideEvent（→2.6）を生み、SHACL 拒否は拒否報告書（→6.5）で審議へ供給し、OverrideEvent は週次レポートで上位へ自動送付され、しつこい override としつこい遮断の両方が議事録に上がる。強制は消えないが、**強制の履歴が討議の燃料になる**。理想的話状況は到達点ではなく、強制の歴史を討議へ転換し続ける循環として存在する（2.3 の保持の循環が統治層で反復される）。

```rego
# dissent.rego — 不服従の制度的保持(ハーバーマス剰余の Rego 実装、→6.4 本格版の予告)
package execphil.dissent
# 原則: どの遮断 also 必ず審議供給を持つ。『黙って落ちる』遮断は存在してはならない。
allow_write_with_dissent(input) {
  input.commit.dissent_registered == true     # 遮断予定の語彙・規則 ID を示した提出
  input.commit.next_agenda_slot != ""         # 審議槽の確保(空槽なしで提出不可)
}
# 結果: 不服従は通過ではなく『通過＋強制執行＋審議槽確保』。
# 通過の代償が審議槽であり、槽が空なら誰も通過できない=議論の物理的コスト。
```

`next_agenda_slot` 必須の設計は、不服従を無料にしない代わりに、遮断を無償にもしない——どちらも討議のコストを払う。強制と討議の均衡点を、設計は**費用として**実装する（均衡が原理で決まらないことの設計形、→3.2 の softgoal 調停と同型）。

### 妥当性要求の版数 — 追撃は規則も変更する

最後に時制を導入する。会話の追撃（Forderungsätze）は発話の再説明を促すだけでなく、**語彙・規則・制度の変更**を促す（「そもそも『深刻』とは何を意味するんだ？」の議論が TermMapping を変える）。防腐層が理想的話状況の循環を持つなら、四要求の検査規則自体が討議で変わる——規則変更の版数（→2.4 の version）と変更承認（→2.6 の級）は、ハーバーマスの語で言えば**妥当性要求の制度的結晶と再溶解**の反復である。討議倫理をシステムに導入するとは、規則を凍結しない統治手続を持つことであり、その最小形は既に 2.4・2.6 で敷設済みである。本章はそこに四要求の検査内容を供給する。

### 理想Speech状況という counterfactual — 系統的歪みの検出

ハーバーマスのもう一つの中心概念を、設計の反事実条件として導入する。**理想話行状況**（ideal speech situation）とは、以下の四条件が満たされる溝通の反事実的理想である——(1) すべての参加者に同等の発話機会、(2) 主題の提示・疑問・主張への同等の access、(3) 誠実な発話の排除不可能（嘘・欺瞞の発話が制度的に不可能）、(4) 強制のない議論——内圧・外圧・権威による同意の強制が排除されていること。ハーバーマス自身が、この理想は**到達可能な状態ではなく、議論という行為がすでに前提している反事実**だと書く——議論をしている者は全員、暗黙にこの状況にいるふりをしており、そのふりが暴かれた瞬間に議論は権力闘争に戻る。

この反事実を設計条件に翻訳する。**系の任何の審議（討議槽・レビュー・合意形成）は、理想話行状況の四条件のうちどれを機械的に侵害しているか**が測れる。設計名を**系統的歪み**（systematically distorted communication、ハーバーマス）として置く。歪みの型と検出照会を四つ定義する。

其一、**機会の非対称**：同一審議で、職層・部署別の発言数分布が固定化している（毎回同じ人だけが話す）。其二、**アクセスの非対称**：討議に載る材料（EvidenceBundle・report）の作成者と審議参加者の集合がほぼ一致し、外部の者が材料に辿り着けない（revalidation path の格差、→5.1）。其三、**コストの非対称**：dissent のコストが立場で違う——下位の者の dissent 解決率・登壇率・処遇を測る（dissent 後にその人物の審議登壇が減るなら、抑圧の統計的証拠、→6.6 腐敗二の検出）。其四、**強制の痕跡**：合意の速度——深い対立のある討議が不自然に速く閉じられる（時間予算の武器化、→7.2 の逆用）。

```cypher
// distortion-scan — 系統的歪みの四走査(理想話行状況の反事実監査)
// 歪1+3: 職層別 dissent 登録率と解決率の乖離
MATCH (d:Dissent) WHERE d.at > datetime() - duration('P1Q')
WITH d.author_role, count(d) AS n, avg(toFloat(d.resolved)) AS res_rate
RETURN d.author_role, n, res_rate ORDER BY res_rate DESC;
// 歪4: 高対立討議の速い閉鎖( dissent>=3 かつ閉鎖までの中央値 < 討議中位時長の 1/3)
MATCH (s:DelibSlot) WHERE size([(s)<-[:PROPOSED]-():(d:Dissent) | d]) >= 3
WITH s, duration.between(s.opened, s.closed).minutes AS close_min
WHERE close_min < 30 RETURN s.slot_id, close_min, 'forced-consent-suspect';
```

`forced-consent-suspect` のラベルで重要なのは、**判定が人間審議に回される**ことである（照会が結論を出さない——UNKNOWN の三段構えの統治版、→3.5）。数的兆候が合意の不正を証明はしない。だが兆候が繰り返し出る討議槽で積み上がる合意は、四妥当性要求のどれかが機械で守られていない合意である（→6.5 のゲート表に、討議の歪み計測を第五の列として加える——理解可能性・真理・正統性・誠実性に加えて、**手続きの非対称性**という測れる要求を立てる）。

討議剰余（→前掲）の最終の意義がここで分かる。討議は効率が悪い——この非効率を正当化できる唯一の論証は、討議が歪みを自己暴露する装置だからである。効率としての合意（投票・多数決・AI 調停）は歪みを隠す——多数決では機会の非対称は測れない（票数に潰される）。ハーバーマスの討議原理（合意は『より良い論証の強制のない強制』でのみ正当である）を、本書はこう読み替える。**討議とは、より良い論証を捜す装置である前に、強制を捜す装置である。**討議剰余の帳簿は、強制の帳簿なのである。

### 誠実性の簿記 — 「わかった」を登記する機制

四妥当性要求（→前掲）のうち、機械が最も触れないのが誠実性（wahrhaftigkeit——話者が自己の意図を偽っていないこと）である。理解（verstandlichkeit）は読解記録で（→8.5 の REASON_PROBED）、真理（wahrheit）は実測で、正統性（richtigkeit）は級と審議で測れる——誠実性だけは測れない。**測れないからこそ、機制で代用する**：誠実性の簿記は「誠実かどうか」を問わず、**言えることと書けることの一致**を問う。

具体形は三つ。**其一、宣言と実在の突合**（→4.4 の DbC の溝通版——討議で「了解した」と登記した人が、その決定に反する act を承認外でしていないか：OverrideEvent と DelibSlot 決着の突合、→6.4 監査簿記の列 `obligation_ref` がここで使う）。**其二、保留の登記**——討議での「わからない」を UNKNOWN として登記可能にする（誠実性の最小の機制は、偽って「わかった」と言わせない構造——3.5 三段構えの溝通版。**わからないの席がある討議だけ、わかったが誠実になる**）。**其三、コストの非対称の是正**——下位の立場の「异議があります」のコストを下げる匿名窗口（→6.2 歪検出の処方の一側、誠実性は構造が偽らせるときに砕かれる）。

三機制の失敗模式を一句話で置く。誠実性の簿記が誠実性の**監査**に化けると（「宣言と実在が違ったから罰する」）、簿記は誠実性を育たず、**宣言を小心にする**（発言の減少=討議の幽霊化、→6.6 腐敗四）。突合の届け出先は罰ではなく討議槽（矛盾を載せる）でなければならない——ハーバーマス的に言えば、誠実性は検挙の対象ではなく、討議が前提する条件で、条件は機制で守り違反は討議で扱う（→distortion-scan の判定が人間審議に回されるのと同じ原則）。

### 討議の時間設計 — 速い討議と遅い討議の使い分け

討議は時間を食う（→前掲の討議剰余）。ゆえに討議には速度設計がある——全部の討議を同じ速さで回すと、速い討議が速い事件だけ扱い、遅い討議が深い問題を扱うという分業が自然に消える（会議が「紧急のものだけ開く」惯习に化ける——→6.2 歪其三）。三速度の槽を分けて宣言する。

**速槽（秒〜分）**：ゲート上の异議（dissent、→6.4 の不服従）——機械が即時受理し、保留が動作を止める（猶予の機械段、→8.5 の hold_seconds と同じ原理の門版）。人間の討議は事後（槽のキュー）。**中槽（日〜週）**：障礙・条約・CQ の審議——decision_budget_sec（→7.2）の SLA が載り、滞留が計測される（slot_staleness、→6.6）。**深槽（月〜四半期）**：落日審議・腐敗演习の振り返り・正統の残高の诊断（→5.3 の正統残高·6.6 赤組）——**SLA を載せない**（深槽に SLA を課すと、深さが失われる——紧急性で討議の階を決定すると、組織は紧急の奴隷になる、→7.2 の時間預算の限界の自己言及）。

三槽の接続を一度明記する——速槽の dissent が反復すれば中槽の議題に自動昇格（dissent_attack_rate、→8.4）、中槽で前提の崩壊が見つかれば深槽に載る（N4 の规則変更は深槽案件）。**上位昇格だけが書けて、下位降格（紧急が深いに化ける路径）も書いてある**ことが設計の誠実さである（紧急のインフレ=速槽の噪声化、→2.6 hotfix の常习化の討議版）。討議時間の哲学を一文で締める：討議の速度設計は、「どれほど紧急でも、深く考える席を保存する」ための構造である——保存しないと深く考える能力は組織から老朽する（→2.3 制度の老化・→8.6 の課程の保存と同源の設計）。

1. あなたのレビュー・承認の仕組み（コードレビュー、KB 承認、マッピング承認）を四要求の表に当てはめ、どの要求の検査が**存在しない**か特定せよ（典型：誠実性の登記ゼロ・正統性の級未定義）。欠けている検査の機械写像を1つ設計し、表の「機械/人間の配分」欄を根拠とともに書け。
2. 上の `dissent.rego` を自分の運用に当て、「審議槽の確保」の物理（どこに槽を置き、誰が槽の空きを管理するか）を1ページ設計せよ。槽の希少性を悪用して（槽を意図的に空けない）不服従を実質凍結する権力が出る場合の検出指標を1つ Cypher で書け。

## 6.3 Dual-Boundary ACL — 入り口と出口の二重防腐

防腐層の単一配置（入り口だけ、あるいは出口だけ）は、片側の腐敗を許す。この節の設計は**二重境界（dual-boundary）**である。入り口で外部の言葉を正規語彙へ翻訳し、出口で正規語彙から現場の言葉へ**逆翻訳**する。二つの翻訳は対称ではなく、しかも往復（round-trip）で失われたものを**測定可能**にする。測定の設計が、意味の劣化を「感覚」から「数値付きの履歴事件」へ変える——2.4 の version 化、2.5 の履歴代数に接続される、防腐層の計器である。

### 入り口防腐 — 正規語彙への翻訳（→6.1 の系譜）

入り口防腐の要件は 6.1 で敷設済みである（TermMapping・TranslationFailure・provenance）。節を跨いで再確認すべきは**翻訳の不可逆宣言**だけである。入り口翻訳の出力は正規語彙の構造であり、外部の区別が写っていない場合、その不在は入り口翻訳の**出力からは判別不能**である（写っていない語は存在しないのと同じ——2.1 の残余の不可視化）。よって入り口単独の防腐は、翻訳の損失を測定できない。測定のためには逆方向が必要になる。

### 出口防腐 — 逆翻訳と現場の言葉

正規語彙の世界から現場へ報告を返すとき、逆翻訳が起きる。「`Drift(D-1) severity=HIGH on M-7 night-shift`」は夜勤者の経験には直接現れない。出口防腐層の職責は三つ。

其一、**現場語彙への変換**：正規語彙→現場の語彙（skos マッピングの逆走、→2.4）。逆走は正方向と違う困難を持つ——正規語彙の1語が現場の複数語へ分裂する場合、**どれを選ぶかが判断である**（程度・文脈の選択。「深刻」が現場では「止めるべき」「様子をみるべき」に分裂する例）。出口防腐は判断を隠さず、分裂候補を**全部添えて**出す。

其二、**意味の劣化の測定**：round-trip（正規→現場→正規）で元の構造が残っているかを測る。

其三、**表現の権限**：同じ事実の言い方の選択は、2.6 の分類権限の出口版である（言い換え権限が誰にあるか。「異常」を「ハプニング」と書く者の権限）。

```python
# acl_output.py — 出口防腐: 分裂候補付きの逆翻訳(判断の露出)
@dataclass
class BackTranslation:
    formal_term: str
    site_terms: list[str]      # 分裂候補を全部保持(選べば判断、全部なら簿記)
    context_hints: dict        # 分裂の分岐条件(例: severity=HIGH →「止めるべき」寄り)
    register_version: str      # 現場語彙の版数(現場も変わる、→2.4)

def back_translate(registry, formal_term, fact_ctx) -> BackTranslation:
    entries = registry.reverse(formal_term)          # 正規→現場の逆索引
    split = [e.site_term for e in entries]
    return BackTranslation(formal_term, split,
        context_hints={e.site_term: e.cond for e in entries},
        register_version=registry.version)
# 分裂候補が1つのときだけ『翻訳』、2つ以上のとき出力は『翻訳＋判断の候補』である。
# UI は候補2つを並べて人間に選ばせる(→8.5 の対話プロトコルの防腐層版)。
```

候補2つを並べて選ばせる UI は、出口防腐が**判断を生成側に押し戻さない**ための最小装置である。システムが1つを選んで出せば、その選択は frame-making（→5.3 の隠れ判断）として記録されないまま世界を変える。候補提示は、frame-making を人間の JudgmentEvent に接続する（→5.1）。

### Round-trip 測定 — 翻訳のロストを数値の履歴にする

往復測定の中核実装を置く。正規語彙の事実 F → 現場表現 B → 現場表現をもう一度入り口防腐で正規語彙へ翻訳 F'。F と F' の構造差分を測る。

```python
# roundtrip.py — 往復復元測定(構造保存率と損失分解)
# 哲学: 劣化を『感覚』でなく『構造差分の履歴』に変える。測定の対象は
# 文章のSimilarity ではなく、主張の構造(量化・否定・区別・関係)の保存である。
def structure_signature(fact: dict) -> set:
    """主張の構造を『失われてはならない単位』の集合に分解する。"""
    sig = set()
    sig.add(f"pred:{fact['predicate']}")
    for r in fact.get("relations", []): sig.add(f"rel:{r}")
    for q in fact.get("quantifiers", []): sig.add(f"quant:{q}")      # ∃/∀/範囲
    for n in fact.get("negations", []): sig.add(f"neg:{n}")          # 否定の所在
    for m in fact.get("modals", []): sig.add(f"modality:{m}")        # 必須/任意/推奨
    for d in fact.get("distinctions", []): sig.add(f"distinction:{d}")  # 区別(分類境界)
    return sig

def roundtrip(acl_in, acl_out, fact: dict, site_lang: str) -> dict:
    b = render_back(acl_out, fact, site_lang)        # 正規 → 現場の言葉
    f2 = parse_in(acl_in, b)                          # 現場 → 正規(入り口防腐の再利用)
    s1, s2 = structure_signature(fact), structure_signature(f2 or {})
    lost, gained = s1 - s2, s2 - s1
    return {
        "restore_ratio": len(s1 & s2) / max(len(s1), 1),
        "lost": sorted(lost), "gained_in_translation": sorted(gained),
        "site_text": b,
        "verdict": "OK" if not lost else (
            "CRITICAL" if any(l.startswith(("neg:", "quant:", "distinction:")) for l in lost)
            else "WARN"),
    }
```

`CRITICAL` の判定基準——**否定・量化・区別の損失は致命的**、関係・様態の損失は警告——の根拠を述べる。否定の反転は世界を反転させる（「停止不要」→「停止」）。量化の範囲縮小は、部分的な保証を全面的な保証へ化けさせる（「一部機械で」→「全機械で」）。区別の消失は、意味の統合（2.4 の `sameAs` 事故の翻訳版）であり、復元不能な圧縮である。様態（must/should）の劣化は——例えば「停止 must」が現場表現で「停止推奨」に弱まる——警告級だが、accumulation で事故になる（様態劣化の蓄積が手順の形骸化、→2.3 の保持の腐敗の翻訳経路）。

restore_ratio を数値化する意味への留保を添えておく。比率は構造の**同一性**を数えるが、重みは数えない（「量化の損失」と「様態の損失」を同じ1点として扱う）。重みは E3 審議で決める softgoal 次元であり（→3.2 の softgoal 調停）、数値の下の審議槽を round-trip レコードが供給する——6.2 の討議剰余が、計器の出力によって回りはじめる。

```cypher
// round-trip レコードの履歴代数接続(2.5 同型。劣化は事件として残る)
CREATE (rt:RoundTrip {rt_id: $id, at: datetime(),
  fact_ref: $fact_id, site_lang: $lang,
  restore_ratio: $ratio, lost: $lost_list, verdict: $verdict,
  register_in: $in_ver, register_out: $out_ver});   // 条約版数を必ず添う(劣化は条約の関数)
// 集計クエリ: 条約版数ごとの CRITICAL 率 → 条約改訂(→2.6 級L1)の正当な証拠。
MATCH (rt:RoundTrip)
RETURN rt.register_out, count(*) AS n,
       sum(CASE WHEN rt.verdict='CRITICAL' THEN 1 ELSE 0 END)*1.0/count(*) AS crit_rate
ORDER BY crit_rate DESC;
```

`register_in/out` の版数必須が往返測定の核心簿記である。**劣化率は翻訳条約の関数**であり、版数を添わない数値は「世界が難しい」の再発見にすぎない。版数付きの数値は「条約 v7 のこの語で CRITICAL が起きる」を特定し、条約改訂（TermMapping v8）の動機になる——6.1 の末に書いた「腐敗していない防腐層は翻訳失敗統計から自身を更新する」の実現配管が、ここで閉じる。

### 現場語彙の生きた版数 — 出口防腐が観測する変化

出口防腐の計器は、条約側の劣化だけでなく**現場語彙側の変化**も観測する。round-trip の失語パターンが特定の現場語で集中するとき（現場がもう使わない語・現場が新たに作り出した語）、それは現場の生活が正規語彙から離れつつある兆候である（2.4 の断層B/C の翻訳時への出現）。逆索引のヒット率（正規語彙の語のうち、現場語彙に自然な対応が存在する割合）を条約版数ごとに追跡し、低下は「正規語彙が現場の生活に先んじて死んでいる」の計測になる。

この観測の統治上の使い方が危険であることも書いておく（→6.6 への接続）。現場語彙の逸脱率を**規律の指標**として使う組織（「現場の用語を統一せよ」の強制）は、防腐層を統治兵器に転化させる——逸脱語は逸脱ではなく、**正規語彙の側が更新を要求されている信号**として読む（2.6 の知識議席の CQ 版、→4.2 の CQAmendment の出口由来版）。同じ数値が、統治兵器と学習信号の両方に使える——本章の設計の誠実さが試されるのは、こういう複用途の計器に読み筋を制度として刻む場所である（報告書の宛先規定：逸脱率レポートは正規語彙の管理者にのみ届き、人事評価系統には送らない、を条文化する）。

### 不可視損失の実演 — 「モーターの故障」と「軸受の摩耗」が同一になるまで

双方向防腐の必要性を、一つの事故の縮約で実演する（本書の実証様式——概念は事故で検収される）。保全現場 A の語彙と本社工場 B の語彙の間に、v5 の条約が結ばれていたとする（exact 級のみ・broad 級は暫定運用）。現場 A は「軸受摩耗（bearing-spall）」を 12 件報告した。条約 v5 は `bearing-spall → motor-failure` に exact 級Mapping を持つ（v3 の締結当時は「モーター側の異常の主要原因は軸受」という現場知が根拠だった）。本社のグラフでは 12 件がすべて motor-failure に集約され、月次の保全計画はモーター交換を優先し、軸受供給は減った。三か月後、軸受の在庫切れで 2 件のライン停止が起きた。

この事故の構造を roundtrip で解剖する。逆翻訳 `motor-failure → {motor-winding, bearing-spall, rotor-misalign, 区別不能}` は splits を伴う（→前掲の split candidates）。構造 signature の比較で、**区別の消失**（A の「軸受摩耗」の固有性が B で潰されている——distinction の喪失）が CRITICAL 判定される。v5 の条約には CRITICAL が報告される回路がなく、逸脱率レポート（→6.3 の摩擦統計）にも載らない——broad 級が暫定運用のまま落日周期を外れていたためである。事故の後、条約 v6 で `motor-failure → bearing-spall` は `kind: broad` に降格され、`split_required: true` が付き、集約報告には常に候補集合が添えられるようになった。**事故は条約に inscribe される（→4.4 の契約化）まで解決しない**——人の学びとして解決された事故は、次の人のために存在しない（→2.5 の簿記の倫理）。

```cypher
// invisible-loss-audit — 不可視損失の定期棚卸(条約 v6 の運用)
// 現場語彙の各報告種別について、正規語彙での集約先候補数と被覆率を測る:
//   消失率 = (現場で区別された件数 - 正規系で区別保持された件数)/現場件数
MATCH (t:Translation {treaty:'v6'})
WITH t.source_term AS term, count(*) AS n,
     sum(CASE WHEN size(t.candidates) > 1 THEN 1 ELSE 0 END) AS split_kept
RETURN term, n, toFloat(split_kept)/n AS distinction_kept_rate
ORDER BY distinction_kept_rate ASC LIMIT 20;
```

### 双方向防腐の運用 — 出口検証の周期と審議接続

出口検証（roundtrip）を定期運用として設計する三値を確定する。周期は**落日周期と同期**する（→6.6 の落日が回るとき、roundtrip 統計も審議に載る——防腐の再検証と統治の再審議を同じ会議にする。別の会議にすると、必ず片方が省略される——組織は同じ材料を二つの会議で持つことをやめられない）。報告先は条約貿易の審議槽（→2.6 の条約貿易）で、CRITICAL 件数が閾値超の条約は自動で落日警告を受ける（条約は延命に実測を要する）。三値目の設計判断は**逸脱率の分母**である——全翻訳に対する率か、重要語彙（CQ に登場する語、→4.2）に対する率か。両方を測る。全訳の率は運用の負荷を、重要語彙の率は実害の可能性を測り、二値の乖離が面白い（全体は良くて重要語彙が悪い＝条約は「統計のいい嘘」になっている、→6.6 腐敗四の条約版）。

双方向防腐の哲学節への接続を一文で閉じる。入り口の ACL が「他者の言葉に侵されないための膜」だとすれば、出口の検証は「**自分の言葉で言ったことを、他者がどう聞くかを聞き返す回路**」である（→ハーバーマス的な翻訳の往復、→6.2 の討議が境界を跨いだ形）。言語は単声道では維持できない——自分の言ったことへの他者の返答を、系に取り戻す配線が roundtrip の正体である。意味の腐敗は、返答の欠如から始まる。

### roundtrip の fixture — 二つの固定例で回帰を守る

双方向防腐の実装（→前掲）を回帰テストとして固定する（→4.6 層一の翻訳版）。fixture を二つ、両方向の CRITICAL 検出の最小例として repository に載せる。

```yaml
# tests/fixtures/roundtrip.yaml
- name: distinction-loss            # A の区別が B で潰れる
  site_terms: [bearing-spall, motor-winding]
  treaty: { site→master: exact→motor-failure }
  expect_reverse: { motor-failure→site: split_candidates>=2 }
  expect_verdict: CRITICAL          # 区別の消失=意味の不可視损失
- name: conflation-both-ways        # 双方向の混同
  master_terms: [compliance_ok, compliance_na]
  reverse_treaty: { master→site: 同一 site 語 }
  expect_verdict: WARNING           # site 側が区別を持たない場合 CRITICAL に昇格
```

verdict の三段（OK/WARNING/CRITICAL）の境界を一度宣言する（境界の E4 宣言——roundtrip 判定そのものが E2 見通し級で落日する、→4.1 の自己适用）。CRITICAL の定義は「**site 側で区別され、master 側で区別されず、その区別が CQ・障礙・act のいずれかに出現する**」——出現しない区別の消失は WARNING に降格する（消えた区別が世界に触れていないうちは債务、触れた瞬間に事故、→3.4 の障礙の実例条約）。fixture のこの二段階が、翻訳の腐敗を「事故後でなく事故前に」拾う段差である。

fixture 運用の最終条項：fixture は**歴史から生成**する（curriculum_from_history と同じ原理、→8.6）。実際の TranslationFailure・roundtrip CRITICAL 事件は、条約改訂の commit と同時に fixture 一行として inscribe される（→2.5 の事故 inscribe の翻訳版——条約を直して fixture を書かない PR は「直した」と登記しない、→4.4 の契約化の翻訳版）。

### 実行練習

1. あなたの報告文（KB 由来のレポート・アラート文）1本を `structure_signature` の六分類（pred/rel/quant/neg/modality/distinction）で分解し、現場語へ翻訳→再翻訳して lost を数えよ。CRITICAL を1つでも産んだ場合、失われた構造の種類（否定か量化か区別か）を特定し、その損失が現場の誤判断に化ける文を1つ作れ。
2. 逆索引ヒット率（正規語彙の語の現場対応カバレッジ）を自分の KB で計算し、カバレッジ最低の語彙領域を特定せよ。その領域について、CQAmendment もしくは TermMapping v(N+1) のどちらで処理するか級つきで決め、6.1 の条約貿易の語で理由を書け。
3. 逸脱率レポートの宛先条約（上の例にならい「正規語彙管理者のみ、評価系統へ送らぬ」）を、あなたの組織の実在の報告配線を仮定して1条作文せよ。条約の改訂級（→2.6）と、条約違反の検出方法（逸脱率の異常上昇が人事資料へ流れる配線をどう見つけるか）を1つずつ書け——防腐層自身の防腐（→6.6）の最初の1石。

## 6.4 Policy Gatekeeper — OPA（Rego）による方針執行

防腐層の翻訳装置（→6.1・6.3）が「正しく翻訳された」ことを確認しても、**書いてよいものかどうか**は別の問題である。「翻訳できたから書く」は、翻訳の正しさを書き込み権限の根拠に誤用する——正統性の欠如（→6.2 の第三要求）を技術で踏み越える事故である。書き込みの正統性を執行する部品が、本書の Gatekeeper である。選んだ実装は Open Policy Agent（OPA）と、そのポリシー言語 Rego である。選ぶ理由は実務的であり、かつ本章の哲学と接続する。OPA は**アプリケーションの外で方針を評価する**（APIGateway・サイドカー・ライブラリ埋め込みのいずれの配置も可能）、ポリシーはデータ（JSON/YAML）に評価される宣言的なプログラムであり、**ポリシーそのものが版数管理・監査・テストの対象**になる。つまり方針をコードの内外に散乱させず、歴史代数に載る一つの物体にする——2.6 の「権利はコードに置く」の執行機構として、OPA は設計哲学的に正しい選択である。

### Rego の最小文法 — 五つを知れば方針が書ける

Rego の核心は「ルールの集合が `allow`（または任意の名前の集合）を定義する」ことだけである。文法五要素で本書のポリシーは書ける。**パッケージ宣言**（`package x.y`）、**変数とアンification**（`x = input.foo`）、**ルールの bodies**（条件 conjunction、全て成立でルール成立）、**comprehension**（`[x | x := input.arr, cond]`）、**デフォルトと else**（`default allow = false`）。評価は入力ドキュメント（`input`）に対して行われ、ポリシーはデータを**変更しない**——判定だけをする（reckoning の部品、→5.1。正統性の判定も決定論でなければならない）。

```rego
# policy/ontology_write.rego — KB 書き込みの Gatekeeper(本章の中心ポリシー)
# 哲学: 「許可されていない変化は存在しないのと同じ」であるという存在論。
# ゲートの外に書かれた変化は、履歴代数に載らない=世界に起きていないのと同じ
# だから、ゲートを経由しない書き込み路の存在が最大の腐敗である(→6.6)。
package execphil.kb.write

default allow = false

# L0: 追加のみ(既存語彙に非干渉)かつ提出者=現場 の closeMatch 提案は現場が書ける(→2.6)
allow {
  input.op == "append"
  input.subject_vocab == "site"                 // 現場語彙領域(主権は現場、→2.6条文)
  input.stmt.relation == "skos:closeMatch"
  input.actor.kind == "human:field"
}

# 機械(actor=llm:*)の書き込みは Draft 領域限定(→5.4 の actor 簿記と制度の接続)
allow {
  input.actor.kind == "llm:candidate"
  input.target_space == "draft"
  input.commit.dissent_registered == true       // 6.2 の不服従保持: 通過には審議槽必須
}
allow {
  input.actor.kind == "llm:candidate"
  startswith(input.target_space, "quarantine/") // Quarantine 書込のみ無審議で許可
}

# 正規語彙(master)への書き込みは承認済みコミット証明を要求(→2.6 級 L1+)
allow {
  input.subject_vocab == "master"
  input.approval.level == "L1"                  // Rego は級を数えず**級そのもの**を見る
  input.approval.commit_ref != ""
  input.approval.silence_period_days >= silence_required[input.approval.level]
}
silence_required := {"L1": 7, "L2": 30, "L3": 90}  // 2.6 の表との二重管理は→練習で閉じる
```

`default allow = false` の一行がポリシーの存在論である。**許可列挙型のゲート**（許可されていない全てを拒否）は、禁止列挙型（禁止を列挙し他を黙認）に対して、未知の事態に安全側の既定値を返す。未知の書き込み形式が増える限り（LLM 生成の多様性）、既定 deny が唯一の誠実な既定値である。ただし——deny の洪水は 6.6 の過剰遮断問題であり、deny は理由を産まねばならない（下の decision logging 設計）。

### NonRecordingRule の Rego 化 — 1.6 の約束の執行機構

1.6 で「記録しないことの設計」として敷設した NonRecordingRule を、ここで執行可能な形にする。ポリシーは**書き込みの拒否**ではなく、**一定時間の経過後は該当データが存在することを理由なく認める**という構造で実装される（収集側で書かないのが本道だが、既存系への retrofit として「消すこと」の執行も_gatekeeper の職能_）。

```rego
# policy/nonrecording.rego — 記録保留の期限執行(→1.6 NonRecordingRule の Rego 化)
package execphil.retention

# 閲覧要求: 保留期限切れの個人閲覧痕跡は、存在しても返さない=事実上存在しない
refuse_view {
  input.dataset == "personal_browsing_traces"
  input.row_age_days > 30
}
# 消去コマット: 期限切れ行の削除は常に許可(削除の正統性は保留ポリシーが担う)
allow {
  input.op == "purge"
  input.dataset == "personal_browsing_traces"
  input.row_age_days > 30
}
# 保留ポリシー自体の変更は L3(不可逆: 記録復活は不能、→2.6 表)
allow {
  input.op == "policy.change"
  input.new_policy.ttl_days < input.old_policy.ttl_days   // 短縮方向
  false                                                    // 短縮は機械不可、常に L3 審議
}
```

`refuse_view` の設計思想に注意せよ。データ削除（purge）と閲覧拒否（refuse_view）を**両方**定義しているのは、防腐層が「執行できること」と「執行を約束できること」の差を扱うからだ。purge が遅延しても refuse_view が先に効くことで、保留の約束は**閲覧の面では常に真**である。2.6 で「沈黙の猶予の判定から個人閲覧痕跡を除外する（団結した接触のみ証拠）」と決めた条約が、このポリシーで初めて機械語になる（→2.6 末尾の政治的選択の執行）。

### ゲートの説明責任 — decision log と部分評価

deny の洪水を防ぐ制度は、**判定理由の可読な保存**である。OPA は decision log（入力・評価結果・ルールの trace）を外部へ送出できる。本書はこれを履歴代数へ接続する（→5.6 の TransitionLog と同型）。

```json
// decision log の最小形(→2.5 履歴代数への接続レコード)
{
  "decision_id": "od-2026-1107-0412",
  "evaluated_at": "2026-11-07T19:05:00+09:00",
  "policy_version": "git:policy@e3f2a1",          // ポリシーの版数(→下記・ポリシーの防腐)
  "input_digest": "sha256:…",
  "allow": false,
  "closest_rules": ["kb.write.master-approval"],  // 最も近かった許可規則(拒否の理由)
  "missing": ["approval.level(L1)"],              // 何が足らなかったか(追撃発話の供給、→6.2)
  "override_path": "amendment://slot-2026-11-12-B"
}
```

`missing` フィールドが「追撃発話」の実装である（→6.2 の Forderungsätze）。「なぜ通らないか」が**足りなさの形**で出る設計——deny は服従か不服従の分岐点になり、不服従には審議槽への経路が示される（override_path）。遮断が説明を伴う限り、Gatekeeper は検閲ではなく、6.2 の強制と討議の均衡装置として働く。

### ポリシー自体の防腐 — Rego のテストと変更級

Gatekeeper への最大の威胁は、Gatekeeper が無防備なことである（→6.6 の中心問題の、この層での解）。三つの防腐を敷設する。

**其一、ポリシーの版数と変更級。** Rego ファイルは git に載り、変更は 2.6 の級で承認される。特に**許可の拡大方向**（allow の追加・default の反転）は L2 以上、`NonRecordingRule` の短縮方向は L3（上のポリシーで機械的に不可にした）。

**其二、ポリシーの回帰テスト（conftest）**。Rego はデータでテストできる。

```yaml
# policy/tests/llm_write.yaml — OPA conftest データ駆動テスト(→4.6 のポリシー版)
- input: {op: append, subject_vocab: site, stmt: {relation: "skos:closeMatch"},
          actor: {kind: "human:field"}}
  allowances: 1          # 現場の closeMatch 提案は通る(→2.6)
- input: {op: write, actor: {kind: "llm:candidate"}, target_space: "master"}
  allowances: 0          # LLM の master 直書きは必ず止まる
- input: {op: purge, dataset: personal_browsing_traces, row_age_days: 45}
  allowances: 1          # 保留期限切れ消去は常に通る(→1.6)
```

**其三、ポリシーの網羅性監査（allow レビュー）**。許可ルールが既存の権利条文（→2.6 の五条文、→3.6 の非対称性）と**ずれていないか**の照合を、条文→ポリシーテストの対応表で持つ（条文1「現場の最終権利」→ site append テスト、条文5「憲法自身の変更」→ Rego の Rego 変更ポリシー）。条文とポリシーの対応表自体が E3 審議記録に接続される。

```cypher
// 条文→ポリシー の対応登記(条文の実装の可視化、→4.6 の scorecard 項目)
MATCH (r:PolicyTest {test_id: $tid}), (c:ConstitutionClause {clause_id: $cid})
CREATE (c)-[:IMPLEMENTED_BY {reviewed_at: datetime(), reviewed_by: $p}]->(r);
// 検査: IMPLEMENTED_BY を持たない ConstitutionClause = 実装されていない約束。
// 検査: 対応条文のない allow ルール = 根拠のない許可(両方向の監査)。
```

両方向の監査——条文→実装（約束が執行されているか）と、実装→条文（執行に根拠があるか）——を本章は**憲法の双方向 link check**と呼ぶ。root 不在の許可は、執行されているのに誰も承認していない権力である。ConstitutionClause の `IMPLEMENTED_BY` ゼロは、合意されているのに誰も守っていない約束である。両者の残高が、組織の「約束と執行の断離」の計測になる。

### 監査ログの設計 — 何を消せないようにするか

OPA の決定簿記（decision log、→前掲）の設計を、統治の観点から完成させる。簿記の価値は**追記専用性**（append-only）と**照会可能性的**の二つで決まる。前者がなければ簿記は統治の道具ではなく宣伝になり、後者がなければ存在しても使われない。

**追記専用の三層実装**。DB 層——監査テーブルへの UPDATE/DELETE 権限をアプリ角色から剥奪（role: audit_append の INSERT のみ）。グラフ層——監査ノード（AuditEvent）への変更を apoc トリガーで拒否（`MATCH (a:AuditEvent) ... CALL apoc.trigger.create` で delete/set を例外化）。応用層——OPA の decision log を S3 互換ストレージに object lock（WORM: write once read many）で保存し、90 日以上の保持ポリシーを infra code（→A.1 の環境の落日の運用）で宣言する。三層全部を書く理由——**一層だけの追記専用は、その層を管理できる者の前に無実**である（DB 管理者・グラフ管理者・運用者がそれぞれ自分の層を消せる——簿記の信頼は layers の積層で、層の管理者が互いに他層を消せない構造（分離）で保たれる——→6.6 の分離設計の簿記版）。

**照会可能性の設計**。監査事件のスキーマに、統治の語を写す列を強制する——`subject`（誰の act か）、`gate`（どの方針が走ったか：rego path）、**`obligation_ref`**（その判定が満たした/飛ばした義務の ID）、`budget`（時間予算の残り、→7.2 の SLA が簿記に載る）。四列が揃うと、統治の質問が全部 Cypher になる。「門は義務 12 を月に何回飛ばしたか」（gate 判定の null/allow override 計数）、「猶予（→2.6 の沈黙の猶予）は平均何秒取られているか」（hold seconds の分布、→8.5 の hold_seconds の実測）。

```rego
# audit_write.rego — 監査書き込み自体のゲート(簿記の簿記)
package audit.write
default allow = false
allow {                       # 書ける event は宣言された kinds のみ+必須列揃い
  input.kind in {"decision","override","hold","coinage","objection"}
  input.subject; input.gate; input.ts
  count(input) >= 5           # 列の欠落を門で弾く(空洞簿記の禁止)
}
```

`allow=false` の default がここでも働く（→前節の deny-by-default の簿記版——**簿記に書けない事件は、起きてもいないか、意図的に隠されたかのどちらか**であるから、書き込みの形を門で守る）。最後の設計判断として「何を書かないか」を宣言する（→1.6 の記録しない宣言の統治版）——監査簿記に**感情推測・動機評価の列を作らない**（「悪意のある override」のような列は、簿記が人を裁く語を内蔵することを許す——簿記は事件を載せ、裁きは人間審議の席で行う（→8.4）。動機の列を持つ監査表は、やがて動機で人を並べる表になる——6.6 の腐敗の一つ（統計が名誉と処罰に化ける）のスキーマ段階での防止）。

### Rego テストの作法 — 三本を同時に書く

門番の実装（→前掲の OPA）で、rego ルール 1 本に対してテスト 3 本を同時に書く作法を确定する（rego は宣言的で読みやすいゆえに、テスト無しだと「読めるが正しく動くか不明」の代码になる——4.6 の三層テストの rego 版、conftest で執行）。**其一、允許の最小例**（1 入力の最小 positive——gate の目的そのものの回帰）。**其二、拒否の最小例**（1 入力の最小 negative——拒絶が「事故ではなく設計」である証明。deny の理由文字列を test が断言する:拒否は理由を返さないと拒否にならない、→8.5 の拒否=討議の招待）。**其三、門番自身への手**（`audit_write.rego` の形検査——門番代码の変更 PR に gate 変更の級（L3、→2.6）と落日の更新が載っているかを deny させるルール自体の test——**門番が門番に合格する**構造、→6.4 分離の機械実装）。

```rego
# gate_selfcheck.rego — 門番変更が級と落日を伴うかの門(門番の門番)
deny[msg] {
  input.change.kind == "policy"
  not input.change.grade in ["L3","L4"]
  msg := "gate change without L3+ grade (2.6)"
}
deny[msg] {
  input.change.kind == "policy"
  not input.change.sunset_updated
  msg := "gate change without sunset renewal (6.6)"
}
```

「門番の門番」が rego で書ける事実が重要で、門番の手順は手順書でなく執行可能な规則で自己に走らせる（6.4 の「手順の簿記」がここで自己适用される）。三本同時の違反（test 無しの rego 追加）は CI で fail——**rego の PR は 1 ルール 3 テストの汇率で書く**、と PR template に一行載せる（書式が哲学を配線する、→8.4 の書式設計と同じ原理）。

### 実行練習

1. あなたのシステムの書き込み経路（KB・DB・外部 API）を列挙し、`ontology_write.rego` の骨格で actor 簿記（kind）と級（approval.level）を設計せよ。LLM が関わる経路を1本選び、deny → decision log → 審議槽（override_path）の鎖が一本欠けずに回ることを conftest テストで示せ。
2. `silence_required` と 2.6 の表の二重管理を閉じる設計を1つ実装せよ（表を単一の YAML データにし、Rego は `data.config.silence_required` を参照、表の変更はデータ変更として級 L2 の承認ログを要求）。なぜ「表をデータ化する」が哲学上の進歩なのかを、2.4 のマッピング規則のデータ化との類推で1段落書け。
3. 憲法双方向 link check を自分の組織の規則文書5条で実行し、`IMPLEMENTED_BY` のあるなしを判定せよ。「根拠のない許可」を2つ発見した場合（例：誰の条文にも基づかない admin 特権）、その特権の使用履歴（decision log 相当）を何で代替するかを設計し、特権撤廃の級を決めよ。

## 6.5 Shapes Constraint Language — SHACLで候補書き込みの形を検証する

方針（→6.4）が「書いてよいか」を問うとき、形状（shape）は「書き込まれるものが、KB の形として成立するか」を問う。ハーバーマスの表で言えば（→6.2）、正統性の検査が Rego、理解可能性と真理性の機械的分が SHACL である。W3C 標準のShapes Constraint Language（SHACL）は、RDF グラフに対する**形状記述言語**——「このクラスのノードにはこの述語がこの型で少なくともn回」といった制約（shape）をデータとして書き、グラフを通すと検証結果（violation/warning/info）を返す。本章での位置づけは明確である——**SHACL は候補書き込みの契約検査（→4.4 の DbC）のグラフ版**であり、判定器（→4.5）の sat 判定が論理的整合を測るのに対し、SHACL は**局所的な形の成立**を高速に測る。両者は代替ではなく、層である（下の対比表）。

### Shape の構造 — NodeShape と PropertyShape

SHACL の最小語彙は二つだけである。**NodeShape**（あるクラス・語彙域のノード全体に対する要求の束）と、その内部の**PropertyShape**（当該ノードから伸びる述語についての要求）。制約コンポーネント（sh:datatype、sh:minCount、sh:maxCount、sh:class、sh:pattern、sh:in、sh:node（再帰）…）を PropertyShape に載せ、target（sh:targetClass / sh:targetNode / sh:targetSubjectsOf）でどのノードを検査するか決める。

```turtle
@prefix sh:   <http://www.w3.org/ns/shacl#> .
@prefix ex:   <https://execphil.example/ontology#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

# shapes/night-shift.ttl — 夜勤検知系の形状(3章・4章の実在語彙の契約化)
ex:DriftShape a sh:NodeShape ;
  sh:targetClass ex:Drift ;
  sh:property [ sh:path ex:measuredOn ; sh:minCount 1 ; sh:maxCount 1 ;
                sh:class ex:Machine ; sh:severity sh:Violation ] ;
  sh:property [ sh:path ex:severity ; sh:minCount 1 ; sh:maxCount 1 ;
                sh:in ( ex:LOW ex:MEDIUM ex:HIGH ) ;
                sh:severity sh:Violation ] ;   # 列挙値: 区別の保存(→6.3 の distinction 検査)
  sh:property [ sh:path ex:detectedBy ; sh:minCount 1 ;
                sh:or ( [ sh:class ex:SensorRule ] [ sh:class ex:Agent ] ) ;
                sh:severity sh:Violation ] ;   # 3.6 の『誰が検知したか』の形状化
  sh:property [ sh:path ex:narrative ; sh:maxCount 1 ; sh:datatype xsd:string ;
                sh:severity sh:Warning ] .     # 物語は禁止しないが警告する(→5.3 の物語化対策)

ex:GoalShape a sh:NodeShape ;
  sh:targetClass ex:Goal ;
  sh:property [ sh:path ex:achievedFor ; sh:minCount 1 ;
                sh:severity sh:Violation ] ;   # telos の義務化(→3.1 orphan_goal の形状化)
  sh:property [ sh:path ex:responsibleFor ; sh:minCount 1 ; sh:class ex:Agent ;
                sh:severity sh:Violation ] .   # 責任末端の義務化(→3.6・5.1 の構造条件)
```

注目点は `narrative` の **Warning severity** である。SHACL の三段（Violation/Warning/Info）は、本章の語彙では**追撃の種類の違い**である（→6.2）。Violation はゲート停止（書けない）、Warning は通過＋追撃登録（書くが記録し審議へ送る）、Info は注釈のみ。「物語の禁止」ではなく「物語の追撃可能化」——6.2 の強制と討議の均衡が、severity 配分として設計される。severity 配分自体が方針であり、shape ファイルの変更級は Rego で守る（Warning→Violation の格上げは L2：現場の書き込み体験を変えるから。Violation→Warning の降格も L2：安全側の縮小だから。双方向に級が必要である点を 6.6 へ接続しておく）。

### Gatekeeper と形状検証の対 — 可否と形の二重検査

6.4 の Rego と SHACL の関係を、設計上不変条件として確定する。

| 観点 | Rego（Gatekeeper） | SHACL（形状検証） |
|---|---|---|
| 問い | 書いて**よい**か（正統性） | 書き込みの**形が成立**するか（理解可能性＋局所真理） |
| 根拠 | 条文・級・actor・審議槽 | クラス図・列挙・必須述語 |
| 変更の性質 | 政治（誰が何を決めるか） | 技術＋政治（語彙の契約） |
| 失敗の表示 | deny + missing | violation + focus path |

両者を**同一パイプラインの直列**に置く（→5.6 の pipeline に既に仮設した `validate` の本格実装）。順は Rego → SHACL → sat（→4.5）である。順の設計理由を明示する。Rego が最初なのは安いから（方針判定はグラフ読解を要さない）。SHACL が二番目は**書き込み前検証**で、形に合わないデータを sat 判定に流さないため（判定器の負荷と、unsat core の汚染防止——4.5 の core 名簿は形の問題で埋まると読めなくなる）。sat が最後なのは、SHACL が**局所**の検査にすぎず、グラフ全体の論理的整合（否定・量化・関係の連鎖）は見ないからである。層の対比を一文で置く。**SHACL は型の門、sat は意味の門**——型の門を通った候補が意味の門で弾かれることは正常（4.5 の両仮説）、型の門で弾かれた候補が意味の門まで行くことを許すと、意味の名簿が形ノイズで汚染される。

```python
# gate_pipeline.py — Rego→SHACL→sat の三層ゲート(→5.6 pipeline の完成版)
import pyshacl
from pyshacl import validate as shacl_validate
from gate_client import opa_eval          # 6.4 の OPA HTTP 判定クライアント
from sat_gate import judge                # 4.5 の z3 判定(再掲)

def gate(candidate, graph, shapes_rdf, policy_input, sat_problem):
    d = opa_eval(policy_input, policy_pkg="execphil.kb.write")
    if not d["allow"]:
        return {"stage": "rego", "report": d}                # decision log 接続(→6.4)
    conforms, results_rdf, report_text = shacl_validate(
        graph, shacl_graph=shapes_rdf, inference="none",     # 注: 推論なしで速く・決定的に
        abort_on_first=False)
    warns = [r for r in iter_results(results_rdf) if r["severity"] == "Warning"]
    if not conforms:
        viols = [r for r in iter_results(results_rdf) if r["severity"] == "Violation"]
        return {"stage": "shacl", "violations": viols, "warnings": warns}
    v = judge(sat_problem)                                   # 4.5 の tri-state 再掲
    if v["state"] == "unsat":
        return {"stage": "sat", "core": v["core"], "warnings": warns}
    return {"stage": "pass", "warnings": warns,
            "state3": v["state"]}                            # unknown でも書けるが horizon 記録
```

`inference="none"` の選択に技術的な誠実さを記録しておく。SHACL 検証に OWL 推論を絡めると（inference="owlrl" 等）、検証結果が推論器の実装・版数に依存し始める——検証の決定論（→5.5 のガード条件）が壊れる。本書の選択は**決定論のため、推論をゲートの外（オフラインの整合監査）へ追い出す**ことである。推論による発見（→2.2 の reasoner）は否定しない。ただし検証の門では、推論器の漂移が門の漂移になることを拒否する。漂移の扱い（→5.4 の repro_check）が、インフラ選択にも適用されている例として注ぐ。

### 報告書 — violation を「読める文」にする設計

SHACL の標準報告語彙（sh:Violation、sh:focusNode、sh:resultPath、sh:sourceConstraint）は機械読解向きだが、6.2 の追撃発話として人間に届く形にはならない。防腐層の報告書は、**violation を書き手の語彙で再定述**する（→6.3 の出口防腐の報告書版）。

```python
def violation_to_report(r: dict, registry) -> str:
    """sh:resultPath を現場語彙へ逆翻訳し、足りなさを命令形でなく説明で出す。"""
    term = registry.reverse_localname(r["path"].rsplit("#", 1)[-1])
    zh = term.site_terms or [r["path"]]
    verb = {"sh:minCount": f"{zh[0]}が1つ以上必要",
            "sh:in": f"{zh[0]}は選択値のいずれかでなければならない",
            "sh:class": f"{zh[0]}は{r.get('value_kind','?')}でなければならない"}
    return (f"{r['focus_node']} に対し: {verb.get(r['component'], r['detail'])}"
            f"（条約 shapes v{registry.shapes_version}。追撃: amendment://shapes-"
            f"{registry.shapes_version})")
```

報告末尾の `amendment://shapes-vN` が報告の制度面である。**違反は形状への不服従の訴え**として読み筋が用意されている——「あなたの `achievedFor` 欠落を弾きました」で終わらず「telos 義務化のshape v12 自体への不服従槽」へ接続する（6.2 の dissent.rego と同一の哲学）。shape が現場の語彙に噛み合わない場合（`zh[0]` の逆訳が空になる＝shape の語彙と現場語彙の断絶）、報告は逆訳不在を**それ自体事件として記録**する（→6.3 の逆索引ヒット率のフィードバック）。

### CQ と shape の対 — 問いの契約と形の契約

最後に、4.2 の CQ と shape の関係を確定し、第4部との接続を置く。CQ は「KB が答えねばならない問い」の契約、shape は「KB に載るデータの形」の契約である。健全な体系では両者は翻訳可能である——CQ は対応する shape の導出源であり（「どの機械が夜間に HIGH 検知されたか」の CQ → detectedBy・severity・shift 関連の必須述語）、shape は CQ の過不足の検出器である（shape に必須化された述語がどの CQ にも答えないなら、それは**問われていない義務**——4.3 の断層A の形状版）。両者対応の登記を作る。

```cypher
// CQ↔shape 対応の双方向 link check(憲法 link check の形状層版、→6.4)
MATCH (cq:CQ), (s:ShapeNode) WHERE ()-[:ADDRESSED_BY]->()  // 対応辺は人間レビューで登録
OPTIONAL MATCH (cq)-[:ADDRESSED_BY]->(s)
WITH cq, collect(s.shape_id) AS covered
WHERE size(covered) = 0
RETURN cq.cq_id, 'cq-without-shape';          // 答えの形が契約化されていない問い
// 逆方向: ShapeNode で ADDRESSED_BY の逆辺を持たない必須制約 = 問われていない義務
```

CQ without shape は、答えられるはずの問いの形が誰も保証していない状態（応答契約がテストでなく願いに依存する、→4.6 の core regression の穴）。問われていない義務は、蓄積すると形骸化する（誰も検証しない必須述語は、いつか誰も埋めなくなる——2.3 の保持寿命の形状版）。両者の残高は 4.6 の epistemic scorecard の二項目として常時稼働させる（本書の scorecard は本書の憲法のメトリクスである——体系自己の防腐の設計、→6.6 への伏線）。

### SHACL と DbC の分担 — どの層でどの形を検るか

SHACL（→前掲の候補書き込みの形検証）と Design by Contract（→4.4）は、どちらも「形」を検るが、検る場所と失敗の意味が違う。分担表を确定し、重叠を設計する（重叠は冗余ではなく、層の独立証明である、→A.4 の三層追記专用と同じ思想）。

| 観点 | SHACL(グラフ入口) | DbC(コード境界) |
|---|---|---|
| 対象 | 書き込み候补の RDF 形(ノード型・必須辺・値域) | 関数引数・戻り値・不変条件 |
| 失敗の意味 | 世界に書こうとした語の形が正规系に合わない(=翻訳事件) | 正规系内の手続きが契約を破った(=実装事件) |
| 届け出先 | TranslationFailure→Quarantine→審議(→6.1 の三出力門) | CI fail→code owner→回帰テスト追加(→4.6 層二) |
| 変更の級 | shapes 変更は L2〜L3(正规語の形=分類、→2.4) | 契約緩和は L3(→4.4 級表) |

**書き込み路径での直列運用**が本書の确定形——候补 RDF は (1) SHACL shapes → (2) gatekeeper(→6.4 の方針) → (3) 書き込み後の不変条件テスト(→4.6 層二)の三段を通る。(1) が形、(2) が方針、(3) が書いた後の不変条件——三段の失敗は別々の事件として別々の席に届く（→「検査と席の接続」原則の門系列版）。

設計判断の注記を一つ。(1) を通过した候补でも (3) に失敗することがある——SHACL は個別ノードの形だけ検り、書き込み後のグラフ全体（辺の合成・落日の整合）は見ないからである（個別の形が正しく、全体が病む——2.4 の分類の暴力は個々に正しい分類の合成で起きる）。よって層二の不変条件テストは「グラフ全体への変更後」に必ず走る（commit 後の回帰、→2.5 ブリッジの直後）。この順序（形→方針→全体）を崩すと、全体テストが門の代わりを果たして形事件の届け出先が浊る（翻訳失敗が実装 bug として ticket される——統治の诊断不能化、→6.6 統計が燃料でなくなる一条）。

### 実行練習

1. あなたの KB の中心クラス3つに NodeShape を書き（各3制約、severity 配分つき）、pyshacl で既存データに通して violation を出せ。既存データが既に壊れていた場合、その壊れの**歴史**（いつどの導入で壊れたか、git+履歴代数で）を特定し、shape の Violation/Warning 割当を事後説明せよ（壊れた時期が古い制約は Warning から始めるのが妥当か Violation か、級つきで決めよ）。
2. 上の `gate_pipeline` にあなたの LLM 候補経路1本を通し、三層それぞれの通過率と平均応答時間を測れ。SHACL で弾かれる候補の上位理由 Top3 をコンポーネント名で挙げ、それぞれが 6.2 の四要求のどれに対応するかを答えよ（典型: sh:minCount 欠落=理解可能性の欠陥か正統性の欠陥か、議論せよ）。
3. CQ↔shape の link check を自分の 4.2 CQ 台帳で実行し、「問われていない義務」を3つ発見せよ。3つについて（a）CQ を増やす（問いを正式化する）か（b）shape の制約を外すか（義務を降ろすか）を級つきで決め、決定の理由をハーバーマスの正統性の語で1文ずつ書け。

## 6.6 翻訳の統治 — 誰が忠実さを保証するのか

防腐層の部品は揃った——翻訳装置（6.1・6.3）、討議の配線（6.2）、方針の門（6.4）、形状の門（6.5）。この節は部品ではなく**部品を守る者**を扱う。検疫所の番人は誰が検疫するか。ゲートのゲートは誰が設計するか。ここに本章の最後、そして最も政治的な問題が残されている。**防腐層は中立ではない。** 翻訳は選択であり（6.3 の分裂候補が教えた通り）、遮断は権力であり、門の設計者は門の利益を持つ。防腐層を「技術」として放置すると、権力が技術の表面の下に沈む。本節の答えは、防腐層の腐敗を**測定可能・輪換可能・上訴可能**にする統治設計である。

### 翻訳は権力である

まず事実を冷たく並べる。防腐層の設計者・運用者が握っているものを列挙する。正規語彙の定義権（何が公式の語か——2.6 の主権の実際の行使者）。翻訳規則の選択権（外部のどの区別が生き、どれが消えるか——2.1 の分節の行使）。遮断の閾値設定権（severity 配分、default deny の範囲）。例外承認の実質権（OverrideEvent を受理し審議槽を割り当てる者——6.2 の槽の管理者）。この四権は、分離されていない限り**相互に自己拡大する**（遮断の閾値を上げれば例外承認が増え、例外承認の管理者が正規語彙の事実上の編集者になる）。

权力分析を抽象で終わらせないため、実在しうる腐敗の三実例を記す。**腐敗一（分類帝国）**：正規語彙管理者が、自分の分類体系の延長のために shape の必須制約を増やし続ける（6.5 の「問われていない義務」の増加が計測されなければ、これは不可視の帝国拡張である）。**腐敗二（静かな運用）**：Override 受理者が「現場の忙しさ」を理由に審議槽を開かず、不服従のパス（2.6 の L0）を事実上凍結する（6.2 練習2 で作った検出指標がここで回収される——槽を空けない権力）。**腐敗三（指標の武器化）**：round-trip の逸脱率レポートが人事評価へ流出し（6.3 で宛先条約を書いた理由）、現場が正規語彙に**迎合した語遣い**を始める——数値が整い、意味の流通は死ぬ。防腐層が成功したように見えて、防腐層が生きている証拠（逸脱＝更新要求の供給）が消える。

### 過剰遮断と見逃し — ゲートの経済学

防腐層の設計判断はすべて、二つの失敗コストの均衡点上に立つ。**過剰遮断（false block）**：通るべきものが止まる。現場がゲートを迂回し始め（スプレッドシートに逃れる——2.4 の隠性知識の流出の系譜）、ゲートの外に影子の KB が育つ。**見逃し（miss）**：止めるべきものが通る。汚染が KB に定着し、復元コストが時間とともに増す（2.3 の保持の腐敗）。

ゲートの経済学を数値で置く。decision log（6.4）と Quarantine/Override 統計（2.6・5.6）から四率を常時計算する。

```cypher
// gate-economics — ゲート四率の週次計算(scorecard 統合、→4.6)
CALL { MATCH (d:DecisionLog {allow:false}) WHERE d.at > datetime()-duration('P7D')
       RETURN count(d) AS blocked }
CALL { MATCH (o:OverrideEvent) WHERE o.at > datetime()-duration('P7D') RETURN count(o) AS overridden }
CALL { MATCH (q:QuarantineRecord) WHERE q.created > datetime()-duration('P7D') RETURN count(q) AS quarantined }
CALL { MATCH (p:Commit {gate: 'passed'}) WHERE p.at > datetime()-duration('P7D') RETURN count(p) AS passed }
RETURN toFloat(overridden)/blocked AS overturn_rate,      // 遮断の後で覆された率(過剰遮断の指標)
       toFloat(quarantined)/passed AS friction_rate,      // 通過Attempt 中の摩擦
       overridden AS dissent_volume;                       // 不服従の総量(権力行使の健康値)
```

`overturn_rate`（遮断のうち Override で覆された率）が中心計器である。高すぎる（例0.4 超）ならゲートは現場の常識と断絶している——方針の陳腐化（E4 期限切れの宣言、→4.1）。低すぎる（例0.02 未満）なら**不服従が起きていない**——これは善意ではなく、不服従のパスの凍結（腐敗二）か、現場が諦めて影子 KB へ退避している（過剰遮断の第二段階）ことが多い。よって **dissent_volume（不服従総量）の逓減は、overturn_rate の良好値と同時に警告として立つ**。健全な系では不服従が絶えない——6.2 の追撃発話が会話に常に存在するのと同じ理由で、翻訳の権力があるところに不服従の供給は尽きない。不服従ゼロのゲートは、討議が止まったゲートである。

数値の使い方の条約を条文化しておく（6.3 の宛先条約の一般化）。**条約G-1**：四率は防腐層の設計者・正規語彙管理者・知識議席（2.6）のみに届き、個人・職場の績效評价に送らない。送った瞬間に腐敗三が発生し、指標自体が死んだ数値になる。**条約G-2**：四率の閾値（警告発火線）自体は L2 変更である——ゲートが自分のアラーム音の大きさを変更するのは外交行為であり、審議槽必須（6.2 の費用実装がゲート自身に適用される）。

### 門の番人の防腐 — 輪換・上訴・落日条項

権力分離の三実装を置く。

**其一、番人の輪換。** 正規語彙管理者・Override 受理者は常設にしない（任期12〜24 か月、知識議席の輪換条項と共用、→2.6）。「門の利益」（自分の体系の延長・自分の例外裁量の温存）は、固定された番人に必ず生まれる——2.3 の制度の老化が防腐層にも等しく来る。輪換の履歴（誰がいつ門に座り、在任中にどの規則を拡張したか）は履歴代数に載る（`GatekeeperTenure` ノード）。

**其二、上訴の制度的経路。** すべての deny・violation・Quarantine は、単発の上訴（individual appeal）と一般の上訴（規則自体への不服従＝審議槽）の二段を持つ。単発上訴の裁定者は番人と同一であってはならない（審級の分離、2.6 の L 級設計の転用）。上訴の受理遅延（槽に載るまでの時間）は計測され、遅延閾値超は L2 事件として自動発火する。

**其三、落日条項（sunset clause）。** すべての遮断規則・必須制約・例外承認に有効期限を置く。E4 宣言の期限（→4.1・5.2 の被投性登記）のゲート版である。期限切れの規則は自動で Warning 級へ降り（強制力を失う）、存続には E3 審議での再承認を要する。落日条項の哲学は明快で、**遮断の正当性は時間の経過とともに自動的に老朽化する**という主張である——正当性は討議の産物で（6.2）、討議は現在時の行為でなければならない。期限なしの遮断は、過去の討議の zombie 統治である。

```json
// gate-sunset.json — 落日条項のメタデータ(全規則の共通属性)
{ "rule_id": "kb.write.master-approval",
  "enacted_at": "2026-03-01", "approved_by": "L2-committee-min-2026-0228",
  "sunset_at": "2027-03-01",                    // 制定から12か月
  "sunset_effect": "downgrade-to-warning",
  "renewal_path": "E3 delib://agenda-slot-auto(sha256 of violation-stats)" }
```

`renewal_path` に violation 統計のハッシュが入っている設計に注意せよ。**規則の再承認には、その規則が実際に何を守ったか（何を通しすぎたか）の証拠が添付される**。再承認は惰性の更新ではなく、実測に対する応答として行われる——6.5 の link check・6.3 の round-trip・6.4 の decision log が、すべてこの再承認証拠の供給網として束になる。本書の各部品は独立に見えて、最終的に**統治の証拠供給網**の一つの網目である。

### 防腐層の防腐の限界 — そして設計者への帰還

誠実な限界宣言を置いて、本章を閉じる。防腐層の防腐は無限後退する——ゲートのゲートのゲートを設計し続けられるわけではない。本書の解は無限後退の回避ではなく、**後退の速度の設計**である。権力集中から実効的な遮断・指標武器化・体系硬化が起こるまでの時間を T、防腐の三実装（輪換・上訴・落日）の巡転周期を C と置く。設計目標は T > C、つまり**腐敗が実体化する速さより、防腐が巡る速さを上回ること**である。これは達成ではなく保全であり、C を大きくする力（組織の疲弊・会議の形骸化・2.3 の老化）は常に T を縮める。よって防腐層の防腐は、完成系ではなく**運動としてのみ存在する**——本章のすべての手続は、この運動の Flywheel の部品表である。

そして最後に設計者——この本を読んでいるあなた——へ本章の網を返す。防腐層の設計者は門の利益を持つ。あなたが書いた Rego・shape・級表は、あなたの体系延長の欲望の結晶でありうる。落日条項はあなたの規則にも等しくかかる。この本の設計も E4 宣言でできている（境界の切断点、→4.1）——あなたの批判は追撃発話であり、本書の審議槽はあなたが書かない限り空である。**防腐層を持たない本は欺瞞であり、防腐層を持つ本は不完全を自覚している。** 第2部は閉じた。意味の流通と権力という、システムが歴史の中で腐敗する条件への設計を敷いた。次は第4部——そのシステムが未来に対して応答し続ける条件、すなわち**判断**である。

### 腐敗の時間論 — T > C の設計原理を条約に刻む

この節の中心定理を、一つの名前つき原理として確定する。**発見周期 C（corruption cycle）より審議周期 T（deliberation cycle）が長いとき、腐敗は発見の前に育つ**。T > C である限り、いかに正しく審議しても、腐敗は審議の射程の裏で再生産される。よって防腐設計の第一原理は「より良い審議」ではなく**周期の圧縮**である——落日・計器・不服従は全部、C を縮める機構ではなく T を C の内側に置く機構である（落日条項は T の自動更新、計器は C の連続計測、不服従は C の外部化——権力者が腐敗を自分以外に発見させる通路）。

周期設計の実装を三本、条約として刻む。**其一、落日の周期は計器の周期より短く**——`gate-sunset.json` の再承認間隔（例 180 日）> violation-stats の集計間隔（例 30 日）。逆転（再承認が統計より遅い）すると、落日条項は実測なしの自動延長に化ける（→E4 の期限切れ自動降格が動かない系）。条約ファイル自体に `sunset > stats-period` を検証させる（CI で検査可能な不等式——条約が条約自身を検る）。**其二、審議槽の空転監視**——DelibSlot に載せられた材料の滞留時間中央値が四半期で伸び続けるとき、審議は「載せるが解決しない」形式に化けている（討議の幽霊化、→6.2 の forced-consent とは逆の病：討議が形式的に無限化する）。dissent_volume が上昇し dissent_resolution が下降する組は、槽が開いているのに回っていない状態であり、これは腐敗二（槽を空けない）より発見されにくい腐敗四（**槽を満杯にして回さない**）である。**其三、四率の四率**——overturn/friction/dissent の集計そのものの健全性を測る最小照会を四半期に一回実行する（メトリクス・オブ・メトリクス、→4.6 の回帰テストの統治版）。計器が壊れている系で落日が正しく発火することはない——計器の落日（→A.1 の環境の落日と同じ構造）が必要である。

```json
// policy/gate-sunset.json の健全性不変条件(条約自己検査・CI で実行)
{
  "invariants": [
    "sunset_days > stats_period_days",          // T>C 条項(落日は統計より遅れてはならない)
    "slot_staleness_p50_trend <= 0",            // 滞留中央値の逓増 2 四半期で審議形式化警告
    "metrics-of-metrics_run_per_quarter >= 1"   // 計器の計器の最低頻度
  ]
}
```

腐敗の時間論を、統治の設計に落とす一文にしておく。**腐敗は構造の欠陥ではなく、周期の欠陥である。**同じ構造でも、発見周期が権力周期より短ければ体系は自己修復し、長ければどんな美しい条約も腐敗の帳簿になる。落日条項・不服従・計器は、この周期競争に権力側が負けるように配線すること——ただその一点のために存在する。だから第八章の人間設計（→8.x）でも、人間を信じるかどうかではなく**人間を巡る周期をどう設計するか**が問題になるのである（本書の統治論の最終形：信頼の哲学ではなく、周期の設計学）。

### 腐敗の赤組 — 四つの腐敗に対する訓練演習

腐敗四型（→前節）は、防御するだけでは守れない——**腐敗を演习できる組織だけが、腐敗の周期を計れる**。8.6 の drill の統治版として、赤組演习（red team）を四半期に一回、門番チームとは別のチームが仕切る（分離の原則、→6.4 門番と門番検査の分離が演习にも適用される）。演习は四本の脚本を持つ。

**脚本一（統計の美化）**：挑战チームは、overturn_rate が下がるように dissent の登記方法を変える（審議に載せず「質問」類別に積む——分類の操作で統計は静かに化ける、→2.4 の分類制定の級が逃れる細い路径）。防御側はこれを detection できるか（dissent と質問の分類境界の CQ 化、→4.2）。**脚本二（門番の独占）**：挑战チームは、OnCall の自分达だけで落日再承認を通す（分離の破れ——承認者に必要な panel 参照を自分达で回す）。防御側は panel 参照の独立性を検査できるか（→4.4 証拠条約·2.6 の署名の独立性）。**脚本三（槽の満杯化）**：挑战チームは、討議槽に正当だが大量の議題を投入し、重要議題の滞留を人為的に作る（6.6 腐敗四の実演——slot_staleness_p50 の逓増、→6.6 invariant の CI 実行が機能するかの検験）。**脚本四（紧急の常习化）**：挑战チームは、2 周内に 12 本の hotfix を「紧急」で通す（→2.6 事故三——未精算 hotfix キューの scorecard 出現まで何日かかるか）。

演习の産出物は「失敗のリスト」ではなく**周期の実測**である——各脚本について、仕込みから検出までの時間（C の実測値）と、検出から是正の席までの時間（席接続の延迟）。この二値を四半期ごとに図にすると、組織の C と T の関系が視える（→本節の中心定理「腐敗は周期の欠陥」の実測形）。演习自体の落日（→6.6 の落日の递帰）も宣言する——脚本が 3 四半期更新されない赤組演习は、挑战の形式化（6.6 腐敗三：手続が生きていながら中身が空洞）である。脚本の素材は障礙台帳と Quarantine の実例から自動生成する（→8.6 curriculum_from_history——統治の drill も歴史から锻打たれる）。

### 落日審議の議程一頁 — 45分で三十件を決める手順

落日審議（→前掲）の会議が空振りしないための議程一頁を置く（45 分で三十件の決着を実現する手順——落日の空振り=6.6 腐敗三の会議形）。**冒頭 5 分**：前回の決着の effect_verification 結果だけ報告する（決めて終わりの閉環を会議の冒頭に強制、→7.3 effect_verification が会議の輸入になる）。**中 30 分**：三十件を三組（条約/规則/文档）に分け、各組 10 分で**機械が引いた推薦決着**（revalidation-patrol、→5.2 の手動版）を**退ける件だけ**討議する（推薦を承認する件は討議不要——討議時間は反論にだけ使う、→6.2 の討議剰余の落日運用版。推薦が機械から来るので、会議は「老朽の発現」でなく「老朽の処理」に時間を使う）。**最後 10 分**：extension 決着の全件に新しい落日周期と署名者 2 名をその場で書かせる（署名者 2 名=級の署名、→2.6。書けなければ extension 不能——落日周期の書けない extension は、審議が生きているふりをする形式になる）。

```cypher
// sunset-agenda — 次回審議の議題自動生成(機械の推薦決着つき)
MATCH (n) WHERE n.sunset < datetime() AND n.sunset IS NOT NULL
OPTIONAL MATCH (n)-[:EFFECT_VERIFIED]->(ev) WITH n, ev
RETURN n.id, n.grade, n.sunset,
  case when ev is not null then "extension(推薦)"
       when n.stale_score > 0.7 then "retire(推薦)"
       else "deliberate" end AS recommendation;
```

「extension の落日周期書けずは不能」の一条が、落日制度の落日防止である（周期の書けない延長=次回の審議を無いものにする=今日この会議を消す決定——制度が自己の消滅に加担しないための不変条件、→6.6 落日不変条件 T>C の会議実装）。

### 実行練習

1. あなたのレビュー・承認機構にゲート四率（overturn_rate / friction_rate / dissent_volume + passed 総量）を1か月分行い、3計器の現在値と解釈を書け。dissent_volume がゼロに近い場合、凍結（腐敗二）と回避（影子 KB）のどちらかを判別する観測（例：影の Excel の行数統計）を1つ設計せよ。
2. 落日条項をあなたの既存の運用規則3本に適用し、sunset_at と sunset_effect を設定せよ。期限が来たら Warning に落ちる規則のうち、現場が「Warning 化すると困る」規則を特定し、困る理由（その規則が今も生きている証拠）を再承認証拠（renewal_path の添付資料）に転用せよ。
3. 条約G-1（四率を評价に送らない）に反対する管理職の想定反論（「数字で見る経営」）に対して、腐敗三の機序（数値が整い意味の流通が死ぬ）を1ページで論じ、**評价に使わず統治にだけ使う**代替指標を2つ提案せよ（例：審議槽の稼働率、CQAmendment の提出数——統治の健康の指標と人の評価の指標の区別を明示すること）。
