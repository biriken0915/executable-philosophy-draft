## 4.1 検証可能性原理 — 意味の境界を引く試み

第2部の第二問——知っていることは十分か——に答えるには、まず「十分」という語の意味を問わねばならない。そして意味を問う哲学伝統のうち、最も大胆で、最も失敗し、最もエンジニアに近い場所に残ったのが、検証可能性原理（verifiability principle）である。この節は分析哲学の一節であるが、同時に本章の設計憲章でもある。**検証できない要求は、実装できない要求である。** この命題は工務店の格言ではなく、ウィーン学団の崩壊した原則の工学的生存形態であり、その出生を知らないまま使うと、4.2 以降で致命傷になる。出生を知らずに使う道具は、道具ではなく呪文である。

### 画像説 — 世界と命題の共役な論理形式

ヴィトゲンシュタイン『論理哲学論考』（1921）から始める。論考の中心装置は画像説（picture theory）である。命題が世界について語るのは、命題の要素と世界の対象が同じ論理的形式（logical form）を共有し、要素の対応が世界への図像（Bild）を構成するときである（「命題は現実の画像である」、4.01）。対応の破れ——命題に現れるが世界に対応しない要素——は無意味（unsinnig）であり、誤りですらない。

要求工学の語に翻訳しよう。**要求文が実装可能なのは、要求語彙の要素とシステム世界の一級の要素（データ・状態・行為）の間に、形式対応が組めるときである。** 3.3 の EARS→LTL→FOL の三段変換は、まさに「論理形式の共有」を手順的に作る作業であった。反転させれば論考の命題は要求分析の命題になる——**形式対応の取れない要求は、実装において誤りですらなく、無意味である。** 「システムは賢く振る舞うべきだ」は偽ではない。偽ですらない。だからテストも実装もできない。

論考のさらに深い所にある境界線（5.6：論証可能なすべてのことは境界線の内側、そして「倫理的なものは表現しえない」）は、3.1 の axiological root（価値の末端は人間が引き受ける、→3.1）と、3.5 の UNKNOWN 登記と同じ姿勢で応答する：形式化の限界の外側を、限界の宣言として形式の内側に書き込む。論考自身は「語れないものには沈黙すべき」（7）で締めるが、本書の伝統——設計の伝統——は、沈黙を**設計された沈黙**（NonRecordingRule、→1.6）に置き換える。沈黙にも所有権と期限を書き込む。

### 検証原理の宣言と、その自爆

ウィーン学団（Schlick、Carnap、そしてPopperの外からの批判）は画像説の境界線を運動纲领へ転化した。**命題の意味は、それを真偽判定する検証手順に尽きる**（Carnap の_weakな形では「確認可能」）。形而上学命題——「絶対者存在す」「歴史の意味」——は認知的に無意味と宣告される。哲学の伝統的問題の多くを、疑似問題として溶解させる試みである。

自爆は早かった。**検証原理自身の命題が、検証原理の要求を満たさない。** 「命題の意味は検証手順に尽きる」は経験命題ではなく、検証手順を持たない。この自己言及敗北は、分析哲学の内側からの最も決定的な反駁である（Quine の経験主義の二つのドグマ、1951 がさらに境界線そのものを相対化した）。

敗北の記録を細かく読んでほしい。学団は敗北しながら、二つの遺産を残した。第一に、境界線を**宣言ではなく手続に置く**という作法（意味の判定は形而上学者にではなく、検証手順の設計者に委ねる）。第二に、境界を**原理の単一線から復数の実務線へ**分解すること（厳密な検証・弱い確認・間接的検認——線は一本ではなく、濃淡の帯になる）。1.2 の「境界は線ではなく面である」が、ここで再び現れる。面として引かれた境界のみが、設計に使える。

### なぜ今もエンジニアリングでは生き残っているのか

哲学の教科書では検証原理は死んだ扱いである。ところがソフトウェアの現場では、検死は行われていない。受入基準が書けない機能は受け取らない（acceptance criteria）、Definition of Done、契約の受入条項、TDD——「検証手順が存在しない要求は、実装しても検証できないから渡さない」という運用規則は、検証原理の生存形態そのものである。なぜ、哲学で崩壊した原則が現場で生き残るのか。理由は三つある。

**其一、現場は自己言及を運用で回避する。** 「検証できない要求は渡さない」自身の正当化は、組織の被りリスクの経験統計であり、哲学的基礎づけを必要としない。実践規範は基礎づけなしに安定する（Poppers の批判的合理主義が合理基準そのものの基礎づけを放棄したように）。現場の検証原理は、純粋原理ではなく**契約の条項**である——契約は自己言及を要らない。

**其二、現場は境界を線として扱わない。** 実際の実務では、完全検証（テスト全網羅）、確率的検証（負荷・MTBF）、相対評価（UXレビュー）、専門家レビュー——四つの検証等級が併存し、等級の低い検証には承認の重み（2.6 の級）を載せる。復数の検証等級の併存という設計が、検証原理を自爆から守っている。

**其三、現場では「無意味」の実害が確定している。** 「賢く振る舞うべきだ」を実装したシステムの動作は、必ず何かになる——何かが起きた後で「賢くはなかった」と非難しても、実装者の過失を認定できない。無意味要求の実装は、**責任配分の不能を製造する**。4.1 の命題（検証不能要求＝実装不能要求）は、意味論の命題としてでなく、責任論の命題として現場に根を持つ。

### 三つの実務規範 — 本書の検証憲章

上記から、本書の検証憲章を三条で置く。この三条は 4.2（CQ）・4.4（契約）・4.5（sat 判定）のすべての実装の前提条文として機能する。

**憲章条一（境界の等級化）**：検証は単一の yes/no ではなく、四等級の手続である。E1=決定論的テストで完全判定、E2=統計・確率的手続、E3=専門家協議の合意記録（→6.2 の妥当性要求）、E4=宣言のみ（telos・価値・公理）。等級は要求ノードに `verif_class` として登記し、E3/E4 には承認の級（2.6）と再検証期限（2.3 の保持寿命）を必ず添う。

**憲章条二（自己言及の登記）**：検証手続自身の正当化は E3/E4 に属する（テスト設計の妥当性はテストでは検証できない）。CI の設定・ゲートの閾値・境界値の決定は、要求ではないが要求を支配する決定であり、**E4 級の宣言として履歴代数に載る**。4.2 の CQ の合意形成が知識政治である、という準備はこれでできる。

**憲章条三（残余の移管）**：E1〜E4 のいずれにも載せられない要求文言（「信頼できる」「誠実な」）は、削除ではなく **phronesis 要求**として区別し、判断主体（人間エージェント、→3.6）への割当として登記する。機械実装からは去るが、設計からは去らない——判断の場（UI・手順・教育）の設計要求に転化する（→8.5）。

```python
# verif_class_register.py — 要求ノードへ検証等級を登記する最小器
# 哲学: 等級の登記は要求の「強さ」ではなく「責任の配分先」を決める。
# E1 が失敗なら CI が止める。E3 が失敗なら誰の審議を止めるか、名簿に書く。
from dataclasses import dataclass

@dataclass(frozen=True)
class VerifRegister:
    req_id: str
    verif_class: str        # 'E1'|'E2'|'E3'|'E4'
    procedure: str          # 手続への参照(テストID・負荷計画・審議記録ID)
    approver_level: str     # 2.6 の級: 'L0'..'L3'
    recheck_due: str        # 2.3 の保持寿命。期限切れ = 検証も deprecation へ進む
    # E4 の procedure は "declared-by:<committee>:<date>" 形式を強制
    def __post_init__(self):
        if self.verif_class == "E4" and not self.procedure.startswith("declared-by:"):
            raise ValueError("E4 must name its declarer — 境界の宣言に匿名を許さない")
        if self.verif_class in ("E3", "E4") and self.recheck_due == "":
            raise ValueError("E3/E4 require recheck_due — 合意は腐る、腐る物は期限を持つ")
```

### 失敗例の解剖 — 「ユーザーフレンドリーなUI」の四等級降格事故

実例で締める。ある要求文書の「ユーザーフレンドリーなUI」は、そのままでは E4 でも検証不能だった（何がフレンドリーかの宣言者もいない）。運用で降格（＝実装可能化）の試みが行われた：(1) UIレビュー会を月次で E3 として制度化（審議記録＝合意の履歴）。(2) タスク完遂時間を E2 の統計的手続に（負荷試験と併走）。(3) 「3クリック以内」を E1 の契約に抽出。**残った残余**——「フレンドリーさ」の身体感覚・心理的安全の部分——は phronesis 要求として新人教育とレビュー会の手順要求へ移管された。残余の実装先がコードから人間の場へ移る瞬間を、読者は見逃さないでほしい。第4部・第5部の UI 設計（→8.5）は、この移管先の設計にほかならない。

検証原理は死んだ。その埋葬地の上に、四等級の境界手続と、境界の宣言簿記と、残余の移管路が建っている。本章は以降、この上物を部品として組んでいく——まず CQ（4.2）は E1/E3 の境界手続そのものである。

### 検証可能性原理の落日 — 原理自身を E4 で宣言する

検証可能性原理（→前掲：意味の境界を検証可能性で引く試み）は、歴史の中で最も速く老朽化した設計原理の一つである（論理実証主義の検証原理——その失敗の解剖は→4.5 に委ねる）。本書がこの原理を「試み」という語で標題に置くのは誠実さではなく、**設計原理としての落日を最初から内蔵させる**ためである。宣言の三類型（E1 実測級 / E2 見通し級 / E4 前提級、→本書の級体系）で言えば、検証可能性原理は E2 見通し級の原理であり、落日周期（例 2 年）と再検証条件（「検証不能だが生存に必要な意味」——沈黙・暗黙知・信頼——を扱う代替機構の設計実績）を持つ。落日が回るとき、原理は自動降格し、その slots（沈黙の設計→1.6、残余の設計→1.2、討議→6.2）が原理の墓標ではなく**後継実装**として評価される。

この自己落日の構造を、本書のあらゆる「原理」に適用する一般形として確定する。

```python
# principle_charter.py — 設計原理の憲章(落日つき宣言の Python 表現)
class Principle(BaseModel):
    p_id: str                     # 'execphil://principle/verifiability'
    statement: str                # 原理の文
    grade: Literal["E1", "E2", "E4"]
    sunset: str                   # ISO 日付
    successors: list[str]         # 後継設計(落日時に評価される代替機構)
    def review_due(self) -> str:  # 落日審議の議題自動生成
        return (f"{self.p_id}: 落日到達。successors={self.successors} の実測を"
                f"評価し、extension(実測証拠つき)/retire/replace を E3 審議で決定")
```

`successors` を宣言時点で書かせる設計の意義を強調する。原理の落日設計で最も危険なのは、落日させて置き去りにすることである——原理を退場させられた組織は、その原理が扱っていた問題を扱う機構なしに残される（検証可能性を捨てた組織は「検証できないが重要なもの」を扱う語彙を失い、意味全体を「信頼だから仕方がない」へ退避させる）。**落日条項は後継の指名を伴うときだけ mature である**——6.6 の落日設計（延命に実測を要する）が、ここで原理のスケールに拡張される。

終章のアポリア（知の継承）に伏線を一本張っておく。検証可能性原理の落日は、本書の不変条件三（目的は閉じない、→4.5）と同名の定理の局所版である——**検証可能性で境界を引く試みは、境界の周縁で必ず意味を切断し、切断された意味が中心を維持している**。この自己言及を認めた上でなお検証可能性を「試み」として使うことが、4.1 の設計の全内容である（原理を信じることと、原理落日の管理人になることは違う——後者が本書の読者に要求する態度である）。

### E1/E2/E4 の分布計測 — 宣言階級の scorecard

検証可能性の境界設計（→前掲の E1 実測級・E2 見通し級・E4 前提級）は、分布として測るまで設計と呼ばれない。宣言の級がどこに集中しているかを四半期ごとに測る三本の照会を確定する。

```cypher
// grade-distribution — 宣言級の分布と偏り(四半期 scorecard)
MATCH (n) WHERE n.grade IN ['E1','E2','E4']
RETURN n.grade, count(n) AS n,
       avg(duration.between(n.at, coalesce(n.next_review, datetime())).days) AS mean_age;
// 偏り一: E4 過密 — 前提級が実測級より多い領域は「信じて回している」領域
// 偏り二: E2 の滞留 — 見通しが実証も放棄もされないまま生き延びている
MATCH (n {grade:'E2'}) WHERE n.sunset < datetime() AND NOT (n)<-[:RESOLVED]-()
RETURN count(n) AS stranded_horizons;
// 偏り三: 級なし宣言 — 級を負わない主张(4.1 の中心の空白)
MATCH (n:Claim) WHERE n.grade IS NULL RETURN count(n) AS ungraded_claims;
```

三つの偏りの診断名を置く。**E4 過密**——前提で回している部門（落日審議の積圧とセットで診断する：前提が多く、再審議が遅い組織は「信任で走る汽船」——→7.1 の phronesis 残高の低い領域と重なる）。**stranded_horizons**——実証も放棄もされなかった E2 の残骸（→3.3 放棄表の落日版。E2 は E1 か E4 か放棄かのどれかに必ず着地する設計を sunset 審議に持たせる）。**ungraded_claims**——級を負わない主张。書物・会議事録・ダッシュボードの表題に級が載らない限り、ungraded は永遠に最多になる（本書が本書の級を卷頭に載せる理由、→preface の訳語の責任·終章の落日条約と同じ自己适用）。

分布計測の目的は「E1 を増やす」ことではない——**分布の形が、その組織がどこで現実に触れ、どこで自我に回っているか**の地図になることである（E1 密度の高い領域=現実と接触している領域。E4 の厚い領域=前提で自己を維持している領域。地図として重要なのは境界の位置で、E4 が悪ではない——自覚された E4 は設計、非自覚の E4 は腐敗、→6.6）。4.1 の検証可能性原理が最後に果たす役割は、世界を形式化可能な区域と不可能な区域に切断することではなく、**切断線の現在地を四半期ごとに報告させること**である（原理の落日設計・→前掲の principle_charter と、この分布計測が一対）。

### E2 宣言カードの二字段 — 見通しを落日つきで持つ形

E2 見通し級（→前掲の実証も放棄もされていない中間の宣言）に、落日可能の形を与える最小の二字段を置く。**其一、`horizon`（いつまで見通すか——時刻でなく事件で書ける：「次回検修まで」「新設备導入まで」）**。**其二、`refute_by`（何が起きたらこの見通しは退くか——1 行で書ける反証条件）**。二字段が揃うと E2 は E1 の未达としてではなく**未来の E1 の預約**として存在する（horizon 到达時刻に refute_by の突合が自動照会され、达則 E1 昇格・退則 E4/放棄に落ちる——2.6 の級の升降が手動儀式でなく時刻表になる、→3.4 障礙の落日が実例突合で回る機制の 4 章版）。

字段の哲学上の位置を一環：refute_by を書けない E2 宣言は**ベルイマン的な主张**（反証不能を自己の不可侵に使う）で、本書の正规系では受理されない——→4.5 の z3 と 5.3 の概率の約束（withdrawal_conditions）が同じ字段を別々の語言で要求している事実は、**反証条件が形式化全体に跨る横断の不変条件**だからである。字段名を E2/CQ/prob offer で統一する（`refute_by` の一個の語で三機構が結ぶ—→4.2 CQ Q3・→5.3 withdrawal・→8.5 falsifiable_if の同値化、→B.3 計器索引）。

### 実行練習

1. 自分の要求文書から5本を四等級に振り分けよ。E1 に落ちる本数がゼロなら、そのシステムは「実装できているが渡せていない」システムである（受け入れ根拠が E3/E4 ばかり）。E4 の `procedure` を declared-by 形式で書き直し、2.6 級 L2 の変更として登記する手順文を1ページ書け。
2. 「ユーザーフレンドリー」型の phronesis 要求を自分のプロダクトから1本選び、三つの降格案（E3 審議化・E2 統計化・E1 抽出）を1本ずつ設計せよ。残余の移管先（教育・レビュー・UI）の実務担当者をエージェント名簿（→3.6）へ登録し、`RESPONSIBLE_FOR` 辺を張れ。
3. 検証原理の自己言及敗北を、あなたの CI の閾値設定に当てはめて書け（「閾値の正しさ」を CI 自身が検証できない構造）。その E4 宣言の再検証期限をいつに設定するか、設定根拠の議論記録を `Commit.intent` 形式（→2.5）で1件作れ。

## 4.2 Competency Questions — このオントロジーは何に「十分」か

十分性の第一の定義を、知識工学は competency question（能力質問、以下 CQ）として発明した。定義はこうである——**オントロジーの仕様は、そのオントロジーが正しく答えられるべき自然言語質問の集合として書かれる。** 2.4 で OWL の TBox を「合意の検出装置」と呼んだが、CQ はその合意の**内容そのもの**である。クラス定義文は CQ の記述を推論可能にした装置であり、CQ なき TBox は、答える問いを決めていない装置である。この節では CQ を仕様の発明としてではなく、十分性の**判定手続**として扱う——4.1 の憲章条一（境界の等級化）が、CQ という部品で初めて機械と接続する。

### Gruninger & Fox の発明 — オントロジーに「何ができるか」を宣言させる

1995年、Gruninger と Fox は製造資源オントロジーの設計過程を報告し、CQ 法を定式化した（Methodology for the Design and Evaluation of Knowledge Bases）。骨格は四手続である。(1) シェイクホルダーから自然言語で質問を集める。(2) 質問をオントロジーの用語で表現できる形へ整形する（this is where the ontology is being created）。(3) 質問に答える推論経路をオントロジー上で実装する。(4) 実装できない質問を残したまま本番へは出さない（残りは未仕様領域として登記）。

CQ 法の本質は、**検証手続の逆順化**である。通常、検証は実装の後から追いつく。CQ 法は検証手続を仕様の入口に置く——先に「答えねばならない質問」を書いておき、実装はそれに従属する。4.1 の四条（検証手順の意味規定性）と完全に一致するが、Gruninger & Fox は哲学を引用していない。現場が独自に分析哲学を再発明した例として、この一致は注目に値する。**形式化の実務は、実務の内部で実務なりの認識論を生む。**

CQ の典型形を保全オントロジーで示す。

```
CQ-1: 「夜勤シフトで発生した、30日以内に2回以上再発した逸脱(Drift)を、
        機械ごとに件数と最終再発日時で列挙せよ」
CQ-2: 「いま開いている状況(Situation)のうち、制約(CONSTRAINT)によって
        採用不能な行動候補を持つものを、阻む制約の名と併せて示せ」
CQ-3: 「P-114 が過去90日に『手順書にない反復行動』を20回以上行った機械クラスを挙げよ」
```

CQ は要求文とは三つ違う。質問文であること（応答の形が先行する）、単文であること（1問1答）、**答えるための構造が要求されていること**（CQ-1 は `Drift` と `recurrence` と `Shift` が結ばれていなければ答えられない構造を要求している）。第三の点が CQ の設計価値であり、CQ はデータモデルの結合試験である。

### CQ → 実行可能テストへの機械橋 — Cypher テンプレート変換

CQ は質問文のままでは仕様だが、テストではない。本書の系では、CQ を (a) 自然言語の原文、(b) Cypher/LTL+FO のテンプレート、(c) 期待応答の制約、の三つ組で持つ。三つ組のまま維持することが重要で、(a) を捨てると現場が読めなくなり（→2.4 の現場語彙論）、(c) を捨てると検証手順が欠落し、(b) を捨てると機械が答えられない。

```python
# cq_spec.py — CQ 三つ組仕様(原文/クエリ/応答制約)の Pydantic V2 モデル
# 哲学: CQ の検証等級(4.1)は E1 か E3 である。応答制約が書けない CQ は
# E3 未満=合意記録でしかなく、本番の十分性判定に混ぜない。
from pydantic import BaseModel, field_validator, model_validator
import re

class CompetencyQuestion(BaseModel):
    cq_id: str
    text: str                          # (a) 自然言語原文(シェイクホルダーの語彙を保持)
    cypher: str                        # (b) 実行可能テンプレート($params 付き)
    answer_contract: str               # (c) 応答制約の宣言文(型・順序・非空条件)
    stakeholder_ids: list[str]         # 誰の問いか。問いの所有権(→4.3, 2.6)
    verif_class: str                   # 'E1' | 'E3'(4.1 憲章条一)
    params: dict[str, str]
    approved_commit: str               # 合意の版数参照(→2.5 の履歴代数)

    @field_validator("cypher")
    @classmethod
    def must_be_parametric(cls, v: str) -> str:
        if re.search(r"'[^']*\d{2,}[^']*'", v):
            raise ValueError("literal hard-coding — CQ の構造要求が数値に埋没する")
        return v

    @model_validator(mode="after")
    def contract_must_bind_structure(self):
        # (c) が (b) の返回キーを参照していることを機械検査する
        keys = set(re.findall(r"RETURN\s+(?:DISTINCT\s+)?([\w.,\s]+)", self.cypher))
        if not any(k.split(".")[0].strip() in self.answer_contract for k in keys):
            raise ValueError("answer_contract does not bind query output — "
                             "応答制約がクエリの出口と接合していない = E1 不適")
        return self
```

`contract_must_bind_structure` が表しているのは、**応答制約とクエリ出口の接合**である。この接合のない CQ テストは「何かを返すクエリ」と「何かを期待するアサーション」の寄せ集めであり、十分性の判定になっていない。4.6 で pytest のアサーションへ降りる直前の品質門として、この検査を持つ。

### CQ の網羅は原理的に閉じない — CQ 網羅問題

CQ は十分性の定義だと述べたが、一つの重大な裂け目がある。CQ 集合が**十分である**ことを、CQ 集合自身が定義できない。より良い CQ が常に追加されうる（4.3 が扱う retrofit の動機もこれである）。これは 1.2 の境界問題の仕様版であり、3.5 の決定不能性の登記と同じ扱いを要求する。**CQ 集合の十分性は E4 級の宣言である**——「現時点で、この問い集合が仕様である」という宣言として、承認委員会（2.6）と再検証期限（2.3）の下に登記する。E1/CQ 網羅の幻想（CQ を全部通せば十分）は、境界を線として引くことの再来であり、4.1 の埋葬地を掘り返す行為である。

裂け目を埋めないための運用構造を三つ置く。

其一、**CQ は凍結せず成長する**。仕様変更の本体は TBox 変更ではなく CQ 集合の変更である。CQ の追加・削除は 2.5 の履歴代数に載り、CQ 削除は `RetractedCQ`（→2.5 の墓標の要求版）になる。削除 CQ は消えない——その CQ が要求していた構造は、削除後の世界で壊れていないかを CI が確認し続ける（CQ の墓標が構造の回帰を見守る）。

其二、**CQ の供給源を多様化する**。CQ は設計者の内省では偏る（自分の関心が問いになる）。供給源は四つ——(a) シェイクホルダー面談（Gruninger & Fox の正統）、(b) 現場の質問ログ（実際の質問をそのまま拾う）、(c) 障害の質問化（インシデント報告の「なぜ」の連を CQ に変換）、(d) レトロフィット抽出（→4.3）。(b)(c) は組織の第三次保持の流用である（→2.3：質問も保持として残す）。

其三、**問いの所有権を登記する**（`stakeholder_ids`）。問いの集合が誰かの集合でしかないとき、オントロジーはその人の世界を工業化する（2.6 の主権論の CQ 版）。

### CQ の合意形成は組織の知識政治である

CQ 法が技術文献では静かに扱う側面を、本章は正面に置く。**どの質問が「本番の CQ」に入るかの決定は、知識政治そのものである。** CQ は「何を問えるオントロジーか」を決めるのだから、CQ 集合は知識の国会の議席配分である。保全の CQ に「再発件数」があり「作業者ごとの習熟度」がなければ、その組織は個人習熟度を知識とみなさない（あるいは監視に使うことを避ける）と決めたことになる。CQ の追加要求（「班ごとの処置手戻り率を問いたい」）は、知識の議席を要求する政治行為であり、L1〜L2 級の変更として承認フローに乗せるべきものだ（→2.6 のフローが要求側にも拡張される）。

```cypher
// CQ 追加要求の承認登記: 問いの議席獲得申請
CREATE (req:CQAmendment {
  cq_id: 'CQ-31', text: '班別の処置手戻り率を月次で列挙せよ',
  proposed_by: 'P-201',                        // 現場側からの提出(不服従のパス、→2.6)
  opposed_by: ['P-305'],                       // 異論も保持する(統合で消さない、→2.2)
  objection_records: ['P-305: 班単位の統計は班長間の競争を生む懸念(E4 宣言として記録)'],
  decision: 'adopted-with-delay',
  delay_until: date('2027-02-01'),             // 沈黙の猶予(→2.6)の CQ 版
  approval_commit: 'urn:commit-0107'
});
```

`opposed_by` を消さない設計を強調する。CQ の採否は多数決で確定するが、反対の論拠は履歴に残る——CQ が将来削除されるとき、削除の根拠が反対論の再検証（Aufheben の手続形、→2.6 の棄却理由の更新）になるからだ。政治的決定の履歴性は、決定の正しさではなく決定の修正可能性を支える。

### CQ と telos の接続 — 質問の連鎖はゴール木に届く

最後に構造の統合を置く。CQ は問いだが、問いは放置されると散逸する。**本番仕様の CQ には、上位の問い（なぜその質問が要るか）への参照を必須にする。** 「なぜ再発件数を問うのか」→「再発の抑制 goal に効くから」。参照先は goal 木（→3.2）である。

```cypher
// CQ → Goal 接続。孤立 CQ(上位問いなし)は telos 孤立(→3.1)と同型の診断を持つ。
MATCH (cq:CompetencyQuestion), (g:Goal {goal_id: $g})
CREATE (cq)-[:ANSWERS_FOR {criticality: 'must'}]->(g);

MATCH (cq:CompetencyQuestion)
WHERE NOT (cq)-[:ANSWERS_FOR]->()
SET cq.orphan_cq = true;   // 孤立 CQ は削除せず申告制で運用する(→3.1 と同型)
```

孤立 CQ 申告率——誰も「なぜその質問が必要か」を答えられない CQ の割合——は、そのオントロジーが**問いたかった質問と問うべき質問の区別を失っている度**である。3.1 の孤立 goal 申告率、2.6 の事故死率、3.4 の障礙健全性とともに、本章系の一級指標として 4.6 のチェックリストへ集約される。

### CQ の統治 — 能力質問の起票権・審議・落日

CQ（Competency Question、→前掲：このオントロジーが答えねばならない質問）を設計手順としてではなく**統治手順**として完成させる（→2.6 の級・→6.6 の腐敗防止が、CQ の運用に直接必要になる）。三つの設計決定を確定する。

**其一、起票権**：CQ は誰でも起票できる（現場の「この系であの質問に答えられるか」が最頻の実害検出器——答えられない質問は、実務がオントロジーの限界に当たった事件、→1.2 の境界問題の実証）。起票権をオントロジーチームに限定した瞬間、CQ はチームの自己検査になり、境界の外側からの反証が消える（→6.1 の壁の偽免疫——CQ の外部発火が防腐層に遮られる形）。よって CQAmendment の提案は L0（発言級）で、実装（TBox 変更）は級つき（→2.4 の分類制定）。**其二、審議**：起票された CQ は審議槽に載り、「答えられる/今は答えられない（UNKNOWN 登記）/答えられないべき（境界宣言）」の三択で決着する（→4.5 の UNKNOWN 三段構えの CQ 版）。二番目の「今は答えられない」は UNKNOWN ノードとして登記され、未来の CQ 実装の要求リストになる——CQ 台帳は要求工学のgoal 木（→3.2）に供給される（能力の欠落は、次に作るものの定義である）。**其三、落日**：CQ にも落日（例 2 年）を置く——答えられる CQ が実運用で一度も発火しないなら、その能力は実務から落日している（テストは通るが誰も聞かない質問——過剰形式化の検出、→2.1 の暴力の診断）。落日 CQ は削除候補になり、削除審議で「答えられないべき」に分類されたものは境界の碑文として残る。

```cypher
// cq-governance — CQ 統治の四半期 report
MATCH (c:CQ) WHERE c.status='answered'
OPTIONAL MATCH (c)<-[:ANSWERED_BY]-(q:CypherExec)   // 実運用での発火計数
WHERE q.at > datetime() - duration('P1Y')
WITH c, count(q) AS live_firings
WHERE live_firings = 0 AND c.at < datetime() - duration('P18M')
RETURN c.cq_id, c.at, 'dormant-capability' AS flag;   // 落日審議の自動起票
```

CQ の落日が特別なのは、**dormant-capability が消滅ではなく境界の引き直しを要求する**点である。使われない能力を機械的に消すと、オントロジーは「使われている質問にだけ答えられる」系に痩せていく——使われていない質問に答えられる余地が、未知の状況への対応能力（→1.2 の残余、→3.5 の地平）である。落日審議の議題は「消すか」ではなく「**境界のどちら側へ書き直すか**」である。CQ 統治の完成をもって 4章前半（意味の境界の設計）を閉じ、後半（z3・pytest の実装）へ渡る——境界の哲学は、問う権利の統治と、答える機構のテストの二個で初めて成立する（→4.5・4.6）。

### CQ 起票の作法 — 三分間の質問の書き式

CQ 統治（→前掲）の入口——起票——の書き式を三分間に确立する。長い CQ は読まれず、短すぎる CQ は答えられない。三行の書式（**質問・世界・十分条件**）を UI form にする。

```markdown
cq-form(3 行)
Q1 質問: この系は「〈自然言語の質問〉」に答えられるか(答えられるべきか)?
Q2 世界: その質問が立つ状況の実例(観測 URI・日誌 URI・会議 URI のいずれか 1 つ)
Q3 十分条件: 答えられたと見なす判定(期待する graph:// パス or 数値)
```

Q2 の必須が書式の核心である——**世界の実例のない CQ は受理しない**（純粋に抽象的な質問は哲学として正当だが、CQ は系と世界の接缝の検査であって、接缝の実例を 1 つでも要求する——→4.1 の検証可能性の「試み」が書式に刻まれている。実例の添付は L0 の発言で誰にでもできる——現場の「この質問、この前の例で闻きたかった」が最频の実例供給源）。Q3 の判定は CQ の自動化（→4.6 test_cq）に直結し、Q1→Q3 の連鎖がそのままテスト 1 本になる（起票即テストの元数拠——CQ 台帳とテスト台帳の二重管理を書式で防ぐ）。

作法の最後一項——**CQ は消さない**。答えられなくなった CQ は status:'dormant'（→前掲）で落日席に載り、消えるのは「答えられないべき」に分類替された時で、その場合も CQ 自体は境界の碑文として残る（→4.2 落日設計の再掲——消された質問は将来の組織が再度発見する費用を払う、→2.5 簿記の伦理）。

### 実行練習

1. `CompetencyQuestion` モデルに自分のシステムの CQ を3本登録し、`contract_must_bind_structure` の失敗例を1つ作れ（RETURN キーと応答制約の遊離）。遊離したまま E1 扱いしたテストが、十分性の判定ではなく「クエリが生きている」確認に落ちる様子を実演で示せ。
2. 障害報告3件から「なぜ」の連鎖を CQ に変換し（供給源(c)）、上の `CQAmendment` 形式で提出せよ。2.6 級 L1 の承認者として誰を指名すべきか（問いの主権と語彙の主権の分離、→2.6・2.4）を条文引用で決めよ。
3. 孤立 CQ 検出クエリを実運用の CQ 台帳で走らせ、孤立申告を5本分行え。各本の `ANSWERS_FOR` を埋められない場合、その CQ が「誰の何のためでもなく存在していた」ことをどう受け止めるか（削除か、E4 宣言付きの保存か）を1本ずつ決め、決定的根拠を 4.1 憲章条の引用形式で書け。

## 4.3 RETROFIT-CQs — レガシーから能力質問を逆抽出する

4.2 で CQ は「先に書く仕様」だと述べた。では、先に書かれずに20年生きてきたシステムはどうか。既存の業務データベースのスキーマ、公開済み API、十年分の SQL ログ——これらはすべて、**答えを持っているのに質問を忘れている**知識である。本書の語彙で言えば、レガシーシステムは第三次的保持の巨大な塊である（→2.3）——運用を規定するが、その根拠を内側に持たない保持。この節では、CQ 法を逆向きに走らせる：実データと実クエリから、そのシステムが実際に答えてきた質問（＝実際に載っていた知識）を逆抽出する。この操作を本書では retrofit-CQ 抽出と呼ぶ。抽出物は 4.2 の CQ 三つ組へ昇格させ、**昇格させなかった残余は 1.6 の NonRecordingRule の設計判断として明示的に宣言する**——この二方向（抽出と残余宣言）がセットでなければ、レガシー分析はまた新しい脱知識化になる。

### なぜ「逆抽出」が可能なのか — クエリログは投票用紙である

抽出の論理的根拠を先に固める。SQL/GraphQL/Cypher のクエリログは、運用中の組織が発射した**質問の記録**である。10年間同じ形のパラメータ化クエリ `WHERE dept=$1 AND shift=$2` が走り続けていたなら、それは「部署×シフトで切った集計が要る」という CQ が、仕様書ではなく投票で選出されていたことを意味する。クエリログは投票用紙の山である。 retrofit-CQ 抽出とは、その開票である。

三つのデータ源と、各が開票する情報の性質を整理する。

| 源 | 開票されるもの | 弱点 |
|---|---|---|
| スキーマ（DDL/ER図） | 載る知識の**形式**（構造・結合・型） | 問いは現れない（構造だけ、目的なし） |
| API 契約（OpenAPI/GraphQL SDL） | 公開された**答えの形**（応答スキーマ） | 内部結合の動機が不明 |
| クエリログ（SQL/Neo4j query.log） | 実際に問われた**質問と結合経路** | ノイズ・自動化された反復と手動探索の混在 |

スキーマは形相因、API は公開された答、ログは動力因の行動痕跡——3.1 の四原因がここでは別々の出土品になる。統合（triangulation）が抽出の本体である。

### 抽出パイプライン — ログからの CQ 発掘スクリプト

本書の中核実装を Python で置く。入力はこの10年で最も汎用性が高い形式（SQL テキストログ）、出力は 4.2 の `CompetencyQuestion` 三つ組の下書きである。

```python
# retrofit_cq.py — クエリログからの CQ 逆抽出(テンプレート正規化+投票集計)
# 哲学: 同じ形質のクエリの「出現回数」は、その知識の運用での存在感の代理指標である。
# 頻度で上位 CQ を選ぶことは、仕様を投票で復元すること。投票は知識政治の履歴である(→4.2)。
import re, json, collections
from collections import Counter

NORM = [
    (re.compile(r"\b\d+\b"), "$num"),                    # 数値リテラル→変数化
    (re.compile(r"'[^']*'"), "$str"),                    # 文字列リテラル→変数化
    (re.compile(r"\s+"), " "),
    (re.compile(r"\bin \((?:\$num|\$str)(?:, ?(?:\$num|\$str))+\)"), "in ($set)"),
]

def normalize(sql: str) -> str:
    s = sql.strip().lower().rstrip(";")
    for pat, rep in NORM:
        s = pat.sub(rep, s)
    return s

def extract_tables_joins(sql: str) -> tuple[frozenset, frozenset]:
    tables = frozenset(re.findall(r"\b(?:from|join)\s+([a-z_][\w.]*)", sql.lower()))
    joins = frozenset(re.findall(r"\b([a-z_][\w.]*)\.(\w+)\s*=\s*([a-z_][\w.]*)\.(\w+)", sql.lower()))
    return tables, joins

def mine_queries(log_lines: list[str]) -> list[dict]:
    tpl = Counter()
    meta: dict[str, dict] = {}
    for line in log_lines:
        sql = json.loads(line)["sql"]
        n = normalize(sql)
        tpl[n] += 1
        t, j = extract_tables_joins(sql)
        m = meta.setdefault(n, {"tables": set(), "joins": set(), "sample": sql[:120]})
        m["tables"] |= t; m["joins"] |= j
    out = []
    for n, count in tpl.most_common():
        if count < 5:                 # 単発クエリは探索であり投票ではない(後述)
            continue
        out.append({"cq_draft": n, "votes": count, **meta[n]})
    return out

# 使い方の例:
# rows = [open("query.log").read().splitlines()]
# for c in mine_queries(rows[0]): print(c["votes"], c["cq_draft"][:80])
```

実運用での正規化は本物であるほど雑多になる（コメント除去、CTE 展開、view 実体への解決）。本章の要点は実装の精緻さではなく、**出現回数=freq が CQ の重要度の代理指標として正当化できる条件**の宣言にある——手動探索クエリ（一人一回の試行）は投票ではない。`count < 5` の線引きは E4 宣言（→4.1）であり、`NonRecordingRule` の閾値設定と同じ性格の決定である。閾値を宣言せずに置いた抽出器は、「5回未満の質問は質問ではない」という脱知識化を暗黙に実行する（→2.1 の境界決定の暴力）。宣言する抽出器は、閾値の下に落ちた質問を `SubThresholdQuery` として別テーブルへ逃がし保存する。

### スキーマとの照合 — 答えてきた質問と載っている構造の断層

抽出した CQ ドraftと、DDL を照合すると、三型の断層が現れる。この断層解析こそ retrofit の目的である。

**断層A（載らず問わerず）**：CQ ドraft が参照する結合が DDL に存在しない（アプリ側 JOIN 補完）。アプリの結合ロジックがオントロジーの隠れ層になっている——**知識がコードに沈んでいる**（→1.5 のラベル論の逆像：コードがラベルを引き受けている）。

**断層B（載って問われず）**：DDL の結合・列で、10年のログに一度も現れないもの。載っているが問いのない知識。4.2 の孤立 CQ と双対の、**孤立構造**である。意味を失った構造は、スキーマの墓標である（→2.5 の墓標クエリの DDL 版）。

**断層C（問われ続けて載っていない）**：ログの `joins` がアプリ名（`orders.cust_id = legacy_users.ko户_ban`）のような**意味不明語彙の結合**で埋まる。結合が生きているのに意味が不在——2.4 のマッピング事故の発掘現場。

```python
# fault_report.py — 断層三型の報告器(抽出 CQ × DDL クロス照合)
def fault_report(cqs: list[dict], ddl_tables: set, ddl_fks: set[frozenset]) -> dict:
    rep = {"A_sinked": [], "B_orphan_struct": [], "C_semantic_gap": []}
    used_fks = set()
    for cq in cqs:
        for j in cq["joins"]:
            fk = frozenset({(j[0], j[1]), (j[2], j[3])})
            used_fks.add(fk)
            if fk not in ddl_fks:
                rep["A_sinked"].append((cq["cq_draft"][:60], sorted(fk)))
    for fk in ddl_fks - used_fks:
        rep["B_orphan_struct"].append(sorted(fk))
    # C 型は結合先名簿の語彙検査(人名・顧客番号・現場略語が DDL 正規語彙に不在なら gap)
    for cq in cqs:
        for j in cq["joins"]:
            if j[1] in {"ko_ho_ban", "jiken_no2", "kanyu_cd"} or "_" not in j[1]:
                rep["C_semantic_gap"].append(j)
    return rep
```

`B_orphan_struct` の扱いが設計の分岐点になる。孤立構造を即削除するのは 2.4 の「載らないもの」の再発明である——問いが今はないだけで、問いは再生しうる（3.4 の `theoretical` 障礙と対称に、**theoretical な構造**は将来の問いの容器である）。よって本書の手順は、孤立構造を `RetiredStructure` として墓標登記し（deprecation、→2.4 の `owl:deprecated` 同型）、削除は 2.6 級 L3 の不可逆変更として沈黙の猶予（90日）を課す。墓標登記と即削除の差は、組織が過去の意味を資産と見るかゴミと見るかの分岐そのものである。

### API 契約との照合 — 公開された答えの形が漏らす前提

OpenAPI/GraphQL SDL は「外部に約束した答えの形」である。CQ ドraftの応答制約（4.2 の (c)）と突き合わせると、**契約が引き受けた前提**が抽出される。応答スキーマに `shift_code: string` があれば「シフトは符号で表される」が前提として契約に凍結されている。凍結の版数（API version）と凍結の変更履歴を結ぶと、**前提の履歴**が得られる——前提の変更がいつ、どの CQ の変化に追従した（あるいは追従しなかった）かが、retrofit の歴史層になる。


### 暗黙の CQ の発見法 — 運用ログからの逆抽出の完全手順

retrofit（レガシーから能力質問を逆抽出、→前節）の第三の源を、この節で実装する——**運用ログからの逆抽出**。コードもデータも語らないが、運用の詢問行動が語っている能力要求がある。運用者がグラフ・DB・ダッシュボードに実際に投げた質問の集合（Cypher ログ・SQL ログ・BI クエリの検索履歴）は、その系が**現実に応答するために使われている質問**の完全な目録であり、その中に設計文書に書かれていない CQ が眠っている。

手順四段。**(1) 収集**：クエリログを 90 日分、read-only で抽出（BI の利用統計も可——詢問の主体が人間であることの確認だけ必須、→5.1 の判断の簿記の照会版）。**(2) 正規化**：クエリの骨格（参照ノードラベル・関係類型・集計・フィルタ語彙）に正規化して重複統合——「誰が」「いつ」「どこで」の三語彙が反復するクラス、など。**(3) 突合**：既存 CQ 台帳（→4.2）と突合し、**文書にないのに運用で高频の質問**を新 CQ 候補として起票（起票権は L0——→4.2 の CQ 統治に接続）。**(4) 階級**：高频×高影响（質問が act の直前に投げられている——意思決定の直前の詢問は能力要求の重みが違う）で優先順位をつけ、TBox 変更の級つき審議に載せる（→2.6 の級運用）。

```cypher
// log-mining-cq — 運用ログからの CQ 逆抽出(Neo4j query log 例)
MATCH (q:QueryLog) WHERE q.at > datetime() - duration('P90d') AND q.read_only
WITH q.pattern_class AS cls, count(*) AS n,
     sum(CASE WHEN (:DecisionEvent {at: q.at}) IS NOT NULL THEN 1 ELSE 0 END) AS pre_decision
WHERE n > 40 AND NOT EXISTS { MATCH (c:CQ) WHERE c.pattern = cls }
RETURN cls, n, pre_decision, 'undocumented-capability' AS flag
ORDER BY pre_decision DESC, n DESC LIMIT 25;
```

（`pattern_class` は正規化 (2) の産物として前処理で作る列——完全な正規化実装は練習に委ね、**骨格の粗い正規化（ラベル集合＋関係名の集合のハッシュ）でも高频の隠れ CQ は十分掘れる**ことを経験として注記する。）

逆抽出の哲学的位置を確定して閉じる。CQ の正典化（設計者が書く CQ）は系が**答えたい**質問の目録であり、ログの逆抽出は系が**答えている**質問の目録である。両者の差分——答えたいにないのに答えている（系が設計外に使われている=現場が意味を作っている、→1.3 の語彙更新）、答えているにないのに答えたい（設計の夢が運用と接触していない、→4.2 の dormant の鏡像）——の二列が、そのシステムの**意味の実況中継**である（→2.3 の第三次保持の運用監査と同じ読み）。retrofit は過去を保存する作業ではなく、**過去が使われ続けていた意味を、現在の制定に接続する作業**である（→2.2 の止揚——差分計算としての継承の、要求工学における実装）。

## 4.4 Design by Contract — 主張としてのアサーション

retrofit で過去の質問を掘り起こした（→4.3）。次に、未来への約束の置き方を扱う。Bertrand Meyer の Design by Contract（DbC、1986, *Object-Oriented Software Construction*）は、プログラム内部の検査文（precondition / postcondition / invariant）を、単なるデバッグ装置ではなく**契約**として再定義した発明である。契約——前提と保証と不変条件を、コードの署名として、呼び出し側と呼び出し側双方に法的・構造的に束縛させる。本章の文脈で DbC を第四章に置く理由は明確である。**アサーションは、コードが世界について発する主張（assertion）であり、主張は存在論的宣言である**（→1.5 のラベル＝存在論的宣言の、実行時版）。`assert x > 0` は「この関数が呼ばれる世界の x は正である」という ontological commitment の実行形式であり、契約違反はその主張の世界が崩れた事件——**認識論的事件**である。DbC は崩れを機械が知る機構を、ソフトウェアの構文に埋め込んだ設計哲学である。

### 契約の三部作 — 前提・保証・不変条件

Meyer の原語で正確に敷設し直す。

**事前条件（precondition）**：呼び出し側が満たすべき条件。満たさないなら、実装側は何も保証しない（契約の定義域外）。**事後条件（postcondition）**：事前条件が満たされた上で実装が返す保証。**クラス不変条件（class invariant）**：公開呼び出しの前後で常に真であるクラス側の主張（「残高は非負」「ハッシュ表のバケット数は素数」）。加えて二つの規則——**継承における契約強化則**（ subclass は precondition を弱められない、postcondition を強められない／conformity rule）と、**observer abstraction**（実装でなく査詢で契約を検証する）。

この三つ組が「契約」を名乗る資格の核心は、**責任の所在が構文で固定される**点である。precondition 違反＝呼び出し側の契約違反、postcondition 違反＝実装側の契約違反。同じ例外の飛火が、どちらの過失かをコードが告げる。3.6 の「責任の連鎖の末端は人間」という定理が、ここで実行時の粒度で具体化する——違反報告が過失の所在を名指しできるシステムと、できないシステムでは、学習速度が一桁変わる（過失の名指しなき失敗は、誰の修正タスクにもならない：→8.1）。

### アサーション＝存在論的主張 — なぜ契約違反が「認識論的事件」なのか

DbC の正典は契約を契約法にたとえるが、本章の読者はすでに予感している。**クラス不変条件は、そのクラスが世界に課す分類の宣言である**（→2.1 の分節＝切断）。`invariant: 残高 >= 0` は「このクラスの認識では、負の残高は存在しない」の宣言であり、`ViolationError` はその存在論の外の実在がコードに衝突した瞬間である。

事件の構造を三層で分解する。

1. **実在層**：残高 -500 の口座が現実に存在した（銀行の外部——手作業の帳簿修正、並行振替、currency 丸め）。
2. **主張層**：クラスは -500 を存在させないと宣言していた。
3. **事件層**：違反例外が、宣言と実在の断離を**イベントとして発火させる**——ログに、スタックに、呼び出しスタックの契約項に記録される。

第三層が DbC の発明である。宣言と実在の断離は、通常は事故として現実に現れ（客の残高がマイナス）、コードの中では黙過される（値はそのまま流れる）。契約は断離を**出来事にして履歴に残す**。2.1 の残余保存原則の実行時版——契約違反は、契約という分類の残余である。契約が保存する残余（違反の記録）は、のちに分類の版数変更（→2.4 の deprecation と改訂）の動機になる。断離の履歴が意味史の燃料になる——2.5 の `LostMeaning` と同じ代数が、実行時イベントでも動く。

```python
# dbc_pydantic.py — DbC を Pydantic V2 で敷設する(本書の Python 契約語彙)
# 哲学: assert は「コードの思考の停止」。契約は「コードの主張の宣言」。
# 前者は crash で終わり、後者は violation イベントとして履歴に乗る。
from pydantic import BaseModel, model_validator, field_validator, ValidationError
from datetime import datetime
import uuid

class ContractViolation(BaseModel):
    """違反そのものをファーストクラスの事実として作る。例外ではない(→4.5 の sat と同型)。"""
    violation_id: str
    contract: str          # invariant | precondition | postcondition
    subject: str           # どのクラス/関数の主張か
    claim: str             # 主張の原文(コード式ではなく人間可読の宣言、→3.3 の RefinementTrace と接続)
    world_evidence: dict   # 違反した世界の証拠(値・時刻・入力)
    at: datetime

class Account(BaseModel):
    balance: float
    currency: str = "JPY"

    # class invariant = 存在論的宣言(→1.5)
    @model_validator(mode="after")
    def invariant_non_negative(self):
        if self.balance < 0:
            v = ContractViolation(
                violation_id=str(uuid.uuid4()),
                contract="invariant", subject="Account",
                claim="残高は非負である(このクラスの世界に負の残高は存在しない)",
                world_evidence={"balance": self.balance, "currency": self.currency},
                at=datetime.now())
            raise ValueError(v.model_dump_json())   # 証拠つきの宣言破棄
        return self

def transfer(src: Account, dst: Account, amount: float):
    # precondition = 呼び出し側への要求の宣言(→3.6 の要求割当の実行時版)
    assert amount > 0, "precondition(amount>0) violated by caller"
    # postcondition を先に書く: 実装ではなく「約束」を先に書く作法(Meyer の contract-first)
    try:
        after_src = src.model_copy(update={"balance": src.balance - amount})
        after_dst = dst.model_copy(update={"balance": dst.balance + amount})
        # observer abstraction: 実装でなく、検証可能な査詢で契約を確認する
        assert after_dst.balance == dst.balance + amount, "post: dst balance"
        assert after_src.balance >= 0 or True, "precondition が守られた世界だけが届く場所"
        return after_src, after_dst
    except AssertionError as e:
        raise  # 実装側の違反 = 実装側の契約違反。名指しされる(責任所在の構文化)
```

`ContractViolation` を例外ではなく**データとして作る**設計の意義を強調する。例外は制御の流れだが、データは履歴になる。違反レコードを Neo4j の `Incident` ノード（→3.4 の障礙の実例 INSTANCE_OF）へ書き込めば、契約違反は障礙の**実測サンプル**になる——障礙分析（→3.4）は契約違反ログによって `theoretical → live` の更新を受けていく。formal な障礙木と実行時の違反記録が同一グラフで循環する設計——DbC は第2部の履歴代数に接続する**実行時の入力装置**なのである。

### 契約と CQ — 同一の主張の二つの時制

DbC と CQ（→4.2）は似た形をして別のものではなく、**同じ主張の異なる時制**である。

| 次元 | CQ | DbC |
|---|---|---|
| 主張の時制 | 現在〜過去：この KB は答えられる | 未来：この実行は保証を下す |
| 検証の主体 | データベース全体 | 呼び出し一回 |
| 失敗の意味 | 構造の不足（載っていない） | 宣言と実在の断離（世界が宣言を超えた） |
| 履歴上の役割 | 仕様の仕様（E1/E3） | 障礙の実例（→3.4） |

両者は一本の線で結べる——CQ は構造への契約であり、DbC は実行への CQ である。設計の作法として本書が課す線はこれだ：**CQ の answer_contract（→4.2 の三つ組の (c)）と、境界のコードの契約は、同一文書から生成されねばならない**。両者が手書きで二重管理されると、契約が CQ の追従に遅れ、**テストは通るが世界は壊れる**窓が開く（→4.1 の検証等級 E1 の内部亀裂）。生成は 4.6 の回帰テスト設計で実装する。

### 契約の限界 — すべてを契約化できないこと自体が契約である

DbC の率直な限界を三つ登記する（→4.1 憲章条二の自己適用）。

其一、**不変条件の網羅不能**。クラスの全状態に対する invariant の完全集合は書けない（frame problem の残影）。書かれた invariant は主張の**選択**であり、選択外の属性は無宣言のまま流れる（残余）。対処は契約にも版数と残余宣言を持たせること——`contract_gap: ['currency 丸めは未宣言']` をコードメタデータに書く。

其二、**分散不変条件（distributed invariant）の弱さ**。複数サービス・複数プロセスにまたがる不変条件（「全 Account の合計 = 元帳残高」）は、Meyer の原点（単一オブジェクト）の外にある。解決は二方向——プロトコル側（two-phase commit 等の distributed invariant 機構）と、検証側（→6.3 の OPA の world-state policy、→4.5 の sat 判定で世界全体の整合性）。本書は後者を主軸に置く（→6.3・7.3 の context graph 全体に対する制約）。

其三、**soft 要求は契約化できない**（→3.6 の割当禁止のコード版）。「適切に」「迅速に」は precondition/postcondition の二値に落ちない。契約化を試みると、閾値化（`latency < 200ms`）で soft の内容が失われる。処置——soft 次元は E2/E3 の契約（統計手続・審議記録）へ分離し、コード契約と契約台帳でつなぐ。

```python
# contract_ledger.py — 契約の版数管理: 契約変更も 2.5/2.6 の変更代数に乗せる
# 哲学: invariant の変更は存在論の改訂である(主張しなくなった世界の領域を記録する)。
# diff を取って契約の 'retracted claim' を墓標化するのが本章の DbC と 2.5 の接続点。
def contract_diff(old: str, new: str) -> dict:
    import difflib
    adds, dels = [], []
    for line in difflib.unified_diff(old.splitlines(), new.splitlines()):
        if line.startswith("+") and not line.startswith("+++"): adds.append(line[1:])
        if line.startswith("-") and not line.startswith("---"): dels.append(line[1:])
    return {"retracted_claims": dels,   # → RetractedClaim ノード(→2.5 墓標と同型)
            "new_claims": adds,
            "meaning": "退位した主張は消えない。CI は new のもとで retracted の反例を走り続ける"}
```

`retracted_claims` の反例探索を CI が走り続ける——これは 2.5 の「CQ 墓標が構造回帰を見守る」（→4.2）と同じ見張り設計である。主張を退位させると、退位した主張が**反例として成立し続ける世界**（つまり旧主張が今も真たな世界）を CI は探査し続ける。意味の変更は世界の拡張であり、拡張の側から旧世界が消えたかどうかは、消えたとは自動に保証されない。見張りがその保証の装置である。

### 契約の三語の統治 — 前置・不変・後件を書き換える権利

DbC（precondition・invariant・postcondition、→前掲の「主張としてのアサーション」）の運用統治を一度だけ明示する。契約は code comment より重い（実行される宣言、→4.4）——ゆえに**契約の変更は code review より重い級でなければならない**。級を確定する（→2.6 の級体系の契約への適用）。

| 契約要素 | 変更の級 | 要求される証拠 |
|---|---|---|
| precondition の緩和(呼び出し側の条件を減らす) | L2 | 呼び出し元全数の影響調査＋回帰テスト追加 |
| precondition の強化 | L2 | 現存呼び出し元が全て満す実測(壊れる caller のリスト) |
| invariant の緩和・削除 | **L3** | 条約審議(invariant=世界観の宣言、→2.4 の TBox と同格) |
| postcondition の強化 | L2 | 全実装・全 mock の再検証 |
| postcondition の緩和 | **L3** | 調用側が失われる保証の洗い出し(CQ 化,→4.2) |
| docstring のみ | L0 | — |

非対称の理由を刻む——**緩和と削除が L3** なのは、契約のうち弱まる側が世界観の変更だからである（「何を約束しないか」の決定は「何が重要か」の決定——→3.1 の目的因の変更、→2.4 の分類制定と同格）。強化は L2（約束を増やす決定は実装コストの問題で、世界観の決定ではない）。この級表を CI に inscribe する（diff に `assert`・`require`・`ensure`・invariant 注釈の変更があれば級自動判定——→2.6 の change_grade_check の契約版で、**意味の変更の構造解析**がここで二番目に現れる）。

統治の最終条項を置いておく。契約の削除・緩和の審議には、**その契約が过去に止めた事故の実例**（障礙台帳・OverrideEvent・Quarantine の突合、→3.4・5.6）を自動で添える。契約の削除は「約束が重い」ではなく「約束が何も止めなかった」の実証を伴うときだけ通る——止めなかった約束は形式の過負荷（2.1 の暴力）だが、止めた約束の削除は未来の事故の予約である（**契約の落日設計は、契約が過去に払った保険金を添えて回ってくる**——2.5 の簿記の倫理の DbC 版）。

### 証拠条約の 2 行 — pre/post の証拠 URI 強制

DbC の装饰器（→前掲）に、証拠条約の 2 行を足す——**前条件の成立も後条件の成立も、観測 URI を伴わなければならない**（`assert x > 0` は成立を代码に見せるが、成立が**世界のどの計器のどれの読数**に基づくかは見せない——→4.4 の中心：代码の内部の真理と世界の接缝の証拠を区別する）。

```python
@precondition("vib < THRESH", evidence=lambda ctx: ctx.obs_uri)   # 前条件:観測引用必須
@postcondition("stop_signal_set", evidence=lambda ctx: ctx.act_uri) # 後条件:実 act 引用必須
```

evidence が None の場合、装饰器は assert を pass させるが **Quarantine を起票する**（契約は満たされた、しかし契約の根拠が証拠なし——「正しい決定の証拠なき実行」は 5.6・7.5 の Quarantine と同一の事件類別で、正しさは簿記を救わない）。この設計の要点を一環：証拠 URI の強制は、テストと本番の**同一性**を作る（テストでも本番でも同じ evidence 列が書かれ、テストが本番の形を偽装できない——→4.6 三層テストが「世界変更ノードの不在」を検える前提条件、→7.6 test_safety_fall の 4 章側の実現）。

## 4.5 z3実践 — 充足可能性判定で「世界」を確かめる

ソルバ z3（Microsoft Research, de Moura & Bjørner）を本書の正式な判定器として拠える。3.5 で要求木の実装に使ったが、あの節は**要求の充足**が主題だった。この節は判定そのものの認識論を主題にする——`sat` は何を約束し、`unsat` は何を禁じ、unsat core はなぜ「名前」を渡すのか。そして判定を**オントロジー全体の整合性検査**へ拡張する：4.4 までで敷いた契約・CQ・障礙が、z3 の一本の判定関数で世界全体の整合性として交差する場所を作る。節の骨格は三つの対だ。`sat`＝存在証明（モデル＝実例の目撃証言）、`unsat`＝不在証明（制約の防壁）、unsat core＝犯罪名簿（防壁の最小寄与集合）。

### 認識論としての SAT — 二つの判定が約束するもの

z3 に制約集合を渡す。返る答えは三種である。

**sat + model**：与えられた制約を同時に満たす赋値（割り当て）の**実例**。ソルバは数学的実在の発明者ではない——もし制約が世界の状態の記述なら、model は「その記述と両立する世界の一例」である。本章の語彙では**目撃可能な反証可能性の供給**である。「不整合がない」という否定形の安全ではなく、「こういう状態がありうる」という肯定形の証拠を渡す。4.2 の CQ が要求する答えの形がこれと同源であることに気づく読者は多い——**CQ とは world-state に対する sat クエリ**であり、その model が答えである。

**unsat**：同時充足の**不存在**。制約の防壁が完全な外部世界を作っている。unsat は安全の証明ではなく、**禁止の完全な記述**である——制約の集合の範囲外は全て許可、という意味で unsat は「世界の輪郭」を刻む。3.5 の `check_satisfaction` が unsat を goal 充足の証明に用いたのは、この輪郭の論理（¬G と仮定と要求の同時不可能＝G の必然）による。

**unknown**：判定の限界。3.5 で登記した `verification_horizon` の裏面。境界内での判定は確定だが、境界外の判定は保留——4.1 の憲章条二が要求する「限界の宣言」の実行時形。

```python
# world_consistency.py — オントロジー世界全体の整合性判定器(本章の統合部)
# 哲学: sat = 「この世界像は生き残れる」の証明。unsat = 「この世界像は
# 一瞬たりとも生きられない」の証明。unknown = 「判定の網の目より大きい」。
# 三つの返回値を区別して扱う設計が、判定を信仰から手続に変える。
from z3 import (Solver, Int, Bool, Function, And, Or, Not, Implies, sat, unsat,
                unknown, is_model, Config, Tactics, Then, Tactic, ParseSMT2String)

def judge(name: str, assertions: list) -> dict:
    s = Solver()
    for a in assertions: s.add(a)
    r = s.check()
    if r == sat:
        m = s.model()
        return {"verdict": "SAT", "witness": m,
                "reading": f"{name}: 実例が存在する=この記述は世界として生き残れる"}
    if r == unsat:
        core = s.unsat_core()
        return {"verdict": "UNSAT", "core": core,
                "reading": f"{name}: 記述は同時不可能。core が最小の寄与者名簿"}
    return {"verdict": "UNKNOWN", "reading": "境界外。判定保留+再検証期限設定(→3.5)"}
```

### 応用一 — オントロジーの突合制約の整合性検査

2.4 の TBox（OWL）は reasoner（→2.4 の owlready2）で検査した。ただし OWL reasoner は description logic の決断手続きに閉じ込められている。本書の系は**世界の状態に対する横断制約**——状況文脈モデル（→1.3）、障礙（→3.4）、契約不変条件（→4.4）——を同じ FOL 空間で持つ。この空間の整合性を z3 で判定する。TBox 整合（概念の空でない可能性）と state-level 整合（この瞬間の世界が載りうる）は別の判定であり、本章は後者を専業にする。

```python
# ontology_state_check.py — 「今この世界」がオントロジーと両立するか
def make_context_state():
    vib   = Function("vib", (Int("m"), Int("t")), Int("v"))      # 振動
    shift = Int("shift")                                          # 0=昼,1=夜
    insp  = Function("inspect", (Int("m"), Int("t")), Bool("i"))
    return vib, shift, insp

def ontology_constraints(vib, shift, insp) -> dict[str, any]:
    """各制約に名前を付ける。名前=unsat core で読める『容疑者』(下記参照)。"""
    c = {}
    m0, t0 = Int("m0_"), Int("t0_")
    # 制約1: 夜間シフトでは sensor mode が power-save(vib 計測間隔 3分→5分)。
    c["night_sampling"] = Implies(shift == 1, vib(m0, t0) == vib(m0, t0 + 2))  # 間隔の近似
    # 制約2: 検知→5分以内点検(→3.3 の unrolling)
    c["inspect_window"] = Implies(vib(m0, t0) >= 45, insp(m0, t0) or insp(m0, t0+1))
    # 制約3: 世界事実(夜間で、振動45、点検なし)
    c["observed_world"] = And(shift == 1, vib(m0, t0) >= 45,
                              Not(insp(m0, t0)), Not(insp(m0, t0 + 1)))
    return c

vib, shift, insp = make_context_state()
cs = ontology_constraints(vib, shift, insp)
# 世界事実だけ通す(= 実際のデータと KB が両立するか):
res = judge("night-vib45-noinpect",
            [cs["inspect_window"], cs["observed_world"], cs["night_sampling"]])
print(res["verdict"])   # UNSAT: 制約2と世界事実が正面衝突 → core = [inspect_window, observed_world]
```

unsat core の読み方：`inspect_window` と `observed_world` が寄与者——つまり「KB の約束」と「現実の記録」が同時不可能である。この瞬間、判定は二つの選択を強いる。(a) 世界事実の記録が誤り（センサーか ETL のバグ）、(b) 制約（＝契約・CQ の背景）が世界の現実に追いついていない（運用が黙って制約を破っている）。**どちらも組織の学習の入口である**（4.4 の違反→障礙 live 化と同じ循環）。core があるから、調査が「全体を疑え」ではなく「この二つを疑え」になる。unsat core の実務価値は名簿化にある——Unsatisfiable Cores and their Applications in Requirements Reasoning（Cockburn らの要求矛盾解析）は、この名簿化の要求工学での最初の大規模実証である。

### 応用二 — 反実仮想（counterfactual）の生成 — 「もしこの制約がなかったら」

sat の実例供給能力をもう一段使う。設計決定（制約一本）の価値を測る標準操作は、その制約を抜いた世界の sat モデルを生成することである。

```python
def counterfactual(constraints: dict[str, any], remove: str) -> dict:
    """制約 remove を除いて sat なら、その制約は『除去すると壊れる世界像』を定義している。
    model が反実仮想の世界の目撃証言(→8.2 の counterfactual panel の設計原型)。"""
    keep = [v for k, v in constraints.items() if k != remove]
    return judge(f"without[{remove}]", keep)

r = counterfactual(cs, "night_sampling")
# UNSAT → night_sampling は unsat に寄与していない(今回の衝突は night 側と無関係)。
# この判定は『夜間サンプリング規則は今の事故と無関係』の証明であり、
# 原因調査の『関係ある候補』への絞込みに使える(→3.5 unsat core と同じ名簿論理)。
```

反実仮想の生成は、7.5・8.2 の説明設計（reason panel）の形式的な床である。「なぜこの警報が出たか」への答は、制約部分集合の sat/unsat 判定列として機械生成できる——人間が書く物語ではなく、判定の選択である（→8.3 の反実仮想選択は人間が行う）。この対——**機械が選択肢を生成し、人間が世界に合う選択を選ぶ**——は第3部以降の反復主題である。

### 応用三 — オントロジー不整合の全探索 — 名前付き制約のリグ設計

unsat core が有用なのは制約に名前があるときだけである（上の `dict[str, any]` 設計）。無名の assertion 配列では、core は z3 内部記号の羅列になる。よって本書の作法は——**制約は必ず人間可読名を持つ辞書で持つ**。この名前簿記は 2.5 の `intent` 必須、4.1 の E4 `declared-by` 強制と同じ規則の判定器版である。名前のない制約は、unsat の瞬間に読めなくなる制約である。

加えて、全 pairs の sat 判定（二次爆発）は行わない。CI の現実解は——新規制約の追加時に、**既存制約のうち関連語彙を共有するもの**（グラフ上の距離2、→1.3 の context graph の語彙結合）だけをペア判定する。unsat が出たら core を記録し、その対を `ConstraintConflict` ノードとして履歴代数へ登記する（→2.6 の変更が衝突履歴を再生できる）。

```cypher
// ConstraintConflict の登記(4.2 の CQAmendment と同じ承認級 L2 を要求する)
CREATE (cf:ConstraintConflict {
  pair: ['inspect_window', 'observed_world'],
  first_seen: 'urn:commit-0109',
  core_witness: 'smt2 dump → 履歴',
  resolution: 'pending',                  // pending | kb-changed | data-fixed | accepted-exception
  accepted_exception_by: null             // 例外承認は 2.6 の OverrideEvent と結ぶ
});
```

`accepted-exception` が唯一の unsat 同居の許しである——衝突を解決せず引き受ける決定は、E4 宣言＋OverrideEvent（→2.6）の複合としてのみ登記される。unsat を無視する運用は、禁止の記述（unsat の意味、冒頭の対）を組織から消す行為であり、2.1 の残余投棄の判定器版として禁止する。

### 判定の限界を再び — z3 に世界を判断させないための四規則

本章の認識論を締める四規則を置く。(1) **unsat を安全と読まない**——unsat は記述の不可能性の証明であって、世界の安全の証明ではない（記述が粗いほど unsat が出やすい：粗い網は矛盾を隠す）。(2) **sat を正しさ読まない**——model は一例であり、網羅の保証ではない。(3) **unknown を例外にしない**——3.5 の `UNKNOWN@horizon` 登記の再現。(4) **判定結果はすべて履歴代数に載せる**（commit と同型の `JudgmentEvent`：制約版数・solver 版数・境界設定つきの）。判定は世界の事実ではなく、**この制約版・このsolver・この境界での出来事**である。4.1 の検証等級 E1 の中身は、こうして版数付きの出来事の列に過ぎない——E1 が「絶対」でなくなることで、E1 の失敗の分析（→4.4 の違反→障礙 live 化）が可能になる。

### z3 検収の手順書 — 充足可能性モデルの読み方と落とし穴

z3 の使用を、本書の慣例である検収手順として確定する（→4.5 前掲のコードの運用側）。充足可能（SAT）時に返る**モデル**（反例世界）の読み取りと、読み取りの三つの落とし穴を記す。

**手順一：反証の方向を宣言してから走る**。z3 には常に「制約集合 ∧ ¬(言いたい事) が UNSAT」の形で走らせる（直接「満たされる世界はあるか」に走らせると、出てきた SAT モデルの読み誤りが検出不可能になる）。 UNSAT が反証である——つまり「あなたの世界観では、この主張は破れない」という機械の宣告である。
**手順二：モデルは必ず人間が再現する**。SAT で出たモデル（例：温度 81、負荷 3、センサー offline）を、現場に「この世界は実際に起きるか」と問う。起きないと全員が答えるなら、**制約の側が間違っている**（制約が現実を過剰に狭めている——2.4 の分類の暴力の z3 版。z3 は制約の論理を調べるだけで、制約と世界の対応を調べない——→4.1 の検証可能性の限界の機械版）。
**手順三：anti-patterns 三つの宣言**。穴一、**整数過小化**（z3 は最小の世界を返す——「0 の世界」が SAT になって「センサー数が 0 でも成立」が検出されない。対策：existence 制約（sensor_count ≥ 1）を常に足す）。穴二、**未解釈関数の自由さ**（`f(x)` を未解釈で置くと z3 は f を何でも好きに選ぶ——意味の仮託された未解釈記号は、制約に見えてただの名前である。対策：未解釈記号の数と位置をテストごとに宣言し、レビューする）。穴三、**quantifier の爆発**（∀×∃の混在で z3 が unknown を返す——unknown は UNSAT ではない（→3.5 の三段構えの論理ツール版：unknown は UNKNOWN として登記し、安全側既定へ）。

```python
# z3_gate.py — CI の z3 段の運用骨格(手順一・三の自動化)
def refute(constraints, claim, extra_existence):
    s = Solver(); [s.add(c) for c in constraints]
    [s.add(e) for e in extra_existence]          # 穴一の防止(存在制約の常設)
    s.add(Not(claim))
    r = s.check()
    if r == unsat:  return Verdict("claim holds", proof=None)  # z3 は反証であって証明証跡は出さない
    if r == unknown: return Verdict("UNKNOWN→登記",  model=None) # 穴三
    return Verdict("counterexample", model=s.model())          # 手順二:人間が読む
```

`proof=None` の注記を大事に置いておく。z3 の UNSAT は**反証**だが、機械検証可能な**証明証跡**はデフォルトでは出ない（model-based inference が通っただけ、という意味）。本書の「証拠＝データ」条約（→4.4）との距離を明記するため、CI の記録には verdict・制約 hash・実行時刻を載せ、証明は z3 の version を含む再現手順で担保する（4.5 の「z3 はあなたの ontology が何を言っているかしか答えない」の運用形——跑が誰・どの version で・どの制約で行われたかの簿記が、反証の信頼の台座である）。

### 実行練習

1. `judge` に自分の KB の制約5本（名前付き）と最近の実データ1件の世界事実を流し、三判定のうちどれが出たかを報告せよ。UNSAT の場合、core の2制約について「記録が誤り」「制約が陳腐化」の両仮説を立て、それぞれを実際に検証する手順（ログ照合・運用ヒアリング）を1本ずつ設計せよ。
2. `counterfactual` を使って、あなたの CI で一番嫌われている制約1本の「除去すると壊れる世界像」を model として提示せよ。model が提示する世界が現実の現場と合う/合わないの判断は誰がすべきか（→3.6 エージェント論）、級いくつの決定か（→2.6）を条文付きで決めよ。
3. 名前付き制約辞書の設計を自分のコードから1つ移植し、無名制約が混じっていた場合は名前を付け直せ。その上で「名前のない制約は unsat の瞬間に読めなくなる」を、あなたの CI の過去3か月の失敗ログに当てはめて検証し、名前付けの規則（接頭辞で主体領域を表す等）を5行で定義せよ。

## 4.6 pytest実践 — オントロジーの回帰テストを書こう

第4章の部品——検証等級（4.1）、CQ 三つ組（4.2）、retrofit 抽出（4.3）、契約（4.4）、判定器（4.5）——を、開発者の日常語彙であるテストコードに落地させる節である。主題は一つ：**オントロジーの回帰テスト**。コードの回帰テストは「壊したくない動作」の記憶であるが、オントロジーの回帰テストは「壊したくない世界像」の記憶である。2.3 のスティグレールの語を借りれば、pytest スイートは組織の第三次的保持の最も機械に近い形態だ——運用を規定し、再検証を循環させる保持。この節の終わりに、あなたのオントロジーは実行可能な認識論（checklist → テスト）を持つ。テストが失敗するたびに、世界像が実際に守られているかどうかの証拠が一つ増える。

### 回帰テスト＝オントロジーの記憶 — 「壊れた世界像」の再発を見張る

普通のユニットテストとオントロジー回帰テストの差を、本章の語彙で確定する。前者は**関数の挙動**の保存、後者は**構造と宣言の保存**である。2.5 で CQ 墓標（`RetractedCQ`）が「削除された問いの要求していた構造」の見張りになると書いた。pytest はその見張りの実体である。

回帰テストの三層を定義する。

- **L1 構造回帰**：載せねばならない結合・型・語彙が消えていないか（DDL・TBox・`REFERENCES` 辺の生存）。
- **L2 宣言回帰**：契約・制約（→4.4/4.5 の名前付き制約）が CI で sat/unsat の期待どおりに落ちないか（制約の版数と solver 版数の固定つき）。
- **L3 応答回帰**：CQ の答えの形（answer_contract）が保たれているか、期待値そのものではなく**契約として**（数値の固定は 2.4 の version の墓標化と接続する）。

```python
# tests/conftest.py — Neo4j とテスト用最小世界(フィクスチャ)
# 哲学: テスト世界は KB の『ミニチュア世界像』である。ミニチュアの設計者は
# 世界像の設計者と同じでなければならない(現場の語彙で書かれた fixture でないと
# テストは開発者の空想の世界像を回帰させる、→2.6 の権利条文の実装版)。
import pytest
from neo4j import GraphDatabase

@pytest.fixture(scope="session")
def driver():
    d = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "test-pass"))
    yield d
    d.close()

@pytest.fixture
def world(driver):
    """夜間検知デモの固定世界(→3.5)。fixture 名が世界像の名前になる。"""
    with driver.session() as s:
        s.run("""
        CREATE (m:Machine {m_id:'M-7'}), (sh:Shift {shift_id:'S9', type:'night'}),
               (d:Drift {d_id:'D-1', at:datetime('2026-10-01')}),
               (d2:Drift {d_id:'D-2', at:datetime('2026-10-20')}),
               (m)-[:HAS]->(d), (m)-[:HAS]->(d2), (d)-[:OCCURRED_IN]->(sh),
               (d2)-[:OCCURRED_IN]->(sh);
        """)
        yield s
        s.run("MATCH (n) DETACH DELETE n")   # 破棄の自動化 = 世界像の埋葬手順の統一
```

### CQ をテストへ — 三つ組の pytest 実装

4.2 の `CompetencyQuestion` モデル（(a)原文/(b)cypher/(c)応答制約の三つ組）から、テストを**生成**する。手書きテストを禁止するのではない——手書きテストと生成テストが食い違った瞬間（→4.4 の二重管理の窓）を CI が検出するために、生成側を正規の通路にする。

```python
# tests/test_cq.py — CQ レコードからのテスト自動生成(parametrize で全 CQ を回帰化)
# 哲学: 各 CQ テストは「この問いに答えられる世界像」の生存証明。
# 失敗 = 世界像の壊れ方の一種であり、失敗メッセージは CQ の原文で読む。
import pytest
from cq_spec import CompetencyQuestion

CQ_STORE = load_cq_registry()   # 4.2 の履歴代数上の CQ 三つ組を版数付きで読む

@pytest.mark.parametrize("cq", CQ_STORE, ids=lambda c: c.cq_id)
def test_cq_structure(world, cq: CompetencyQuestion):
    if cq.verif_class != "E1":
        pytest.skip(f"{cq.cq_id} は E1 ではない({cq.verif_class}) — 4.1 の等級区別をテストが守る")
    recs = world.run(cq.cypher, **cq.params).data()
    # (c) answer_contract の機械化: 応答のキー・非空・順序の契約検査
    assert contract_holds(cq.answer_contract, recs), (
        f"{cq.cq_id}: {cq.text!r} — 応答契約の破綻。"
        f"世界像の変更(commit {cq.approved_commit})に対する回帰疑い"
    )

@pytest.mark.parametrize("tomb", load_retracted_cqs(), ids=lambda t: t.cq_id)
def test_retracted_cq_witness(world, tomb):
    """4.2 の墓標見張り: 削除 CQ の要求構造が『いつの間にか復活・消失』していないか。
    復活=未承認の仕様変更の兆候、消失=意図せず構造が死んだ兆候。両方報告。"""
    exists = world.run(tomb.structure_probe).single()["n"] > 0
    expected = tomb.revival_policy          # 'forbidden' | 'requires-L2'
    if expected == "forbidden":
        assert not exists, f"{tomb.cq_id}: 退位した構造が復活。未承認変更か(→2.6 OverrideEvent 照会)"
```

`pytest.skip` の扱いに注意を奪われたい。E3（審議記録）の CQ をテスト実行から区別して skip するのは、4.1 の等級制度がテスト配管にも埋め込まれている証拠である。skip は「検証しない」ではなく「検証の主体が人間である」の宣言である——skip 件数のレポート（下記 checklists）が「人間に依存している検証の量」を数える。

### 契約回帰 — 名前付き制約の sat 期待値テスト

4.5 の名前付き制約辞書を、期待 verdict 付きの表で持つ。制約の変更（→2.4 の version 管理）は期待値の更新を要求し、更新忘れは回帰テストが止める。

```python
# tests/test_contracts.py — 制約表の sat/unsat 期待値回帰(solver/境界の版数固定)
import pytest
from z3 import Solver

@pytest.mark.parametrize("name,cons,expect", [
    ("inspect_window+world", INSPECT_CASE, "UNSAT"),     # 4.5 の事例を回帰化
    ("night_sampling-alone", NIGHT_ONLY,   "SAT"),
], ids=lambda x: str(x[0]))
def test_constraint_verdict(name, cons, expect):
    v = judge(name, cons)
    assert v["verdict"] == expect
    if expect == "UNSAT":
        assert set(map(str, v["core"])) == EXPECTED_CORES[name]  # core の名前簿記まで回帰化
```

**unsat core まで回帰化する**のが本章の一手である。verdict だけでなく core の名簿まで固定すると、制約の追加・削除が core の構成を変えた瞬間にテストが落ちる。core の変化は「禁止の防壁の誰の寄与で建っているか」の変化——世界像の力学的変化——であり、verdict が同じでも無視してはならない。core 回帰は、世界像の**構造力学的**な健全性の検査である。

### 退行の記録 — テスト失敗の履歴代数化

テスト失敗を CI の赤信号で終わらせず、2.5 の履歴代数へ載せる。失敗レコード（`RegressionEvent`）は、障礙の実例（→3.4 `Incident`）と契約違反（→4.4）の第三の兄弟——**世界像が壊れかけた出来事の第三型**（コード変更由来の壊れ）である。

```cypher
CREATE (r:RegressionEvent {
  test_id: $tid, failed_at: datetime(),
  ci_commit: $sha, ontology_version_ref: $kbver,   // 世界像の版数とコード版数の同時固定
  suspect_change: $blame_sha,                      // git bisect 結果(→2.5 の git 橋の再利用)
  cq_ref: $cq_id,                                  // どの問いの守りの失敗か
  resolved_by: null
});
```

`suspect_change` が入ることで、4.2 の供給源(c)（障害→CQ 変換）と 3.4 の障礙更新（`stale→live`）が自動配管になる——回帰失敗→障礙/制約の `live` 化→次回レビューの議題化。第2部半ばで既に三度書いた循環（事件→形式→運用→事件）が、ここで初めて**機械に回りはじめる**。pytest が認識論の部品である最終的な理由はここにある：テストは世界像の代謝の速度計だからだ。

### 実行可能チェックリスト — 第四章の総点検をクエリで引く

最後に、4.1〜4.5 までが要求してきた「登記」の総点検を、本章の診断定理の統合クエリとして置く。人間が読むチェックリスト（「CQ に上位 goal 参照があるか」）を、機械が引く状態報告に置換する——1.5 の「ドキュメントがコードとずれる」問題の、設計としての解決。

```cypher
// 4章統合健全性レポート(epistemic scorecard) — 週次で自動生成・審議の議題へ
CALL { MATCH (cq:CompetencyQuestion) WHERE NOT (cq)-[:ANSWERS_FOR]->() RETURN count(cq) AS orphan_cq }
CALL { MATCH (t:RetractedCQ) WHERE NOT (t)-[:WATCHED_BY]->(:RegressionTest) RETURN count(t) AS unwatched_tombs }
CALL { MATCH (a:Agent {kind:'machine'})-[:ASSIGNED_TO]<-(r:Requirement {softness:'soft'}) RETURN count(r) AS soft_on_machine }
CALL { MATCH (cf:ConstraintConflict {resolution:'pending'}) RETURN count(cf) AS open_conflicts }
CALL { MATCH (o:Obstacle {status:'stale'}) RETURN count(o) AS stale_obstacles }
CALL { MATCH (t:RetractedClaim) WHERE NOT (t)-[:WATCHED_BY]->(:RegressionTest) RETURN count(t) AS retracted_unwatched }
RETURN orphan_cq, unwatched_tombs, soft_on_machine, open_conflicts,
       stale_obstacles, retracted_unwatched,
       (orphan_cq + unwatched_tombs + soft_on_machine + open_conflicts
        + stale_obstacles + retracted_unwatched) AS epistemic_debt_total;
// epistemic_debt_total の増減は『世界像の誠実さの負債残高』である。
// ゼロ目標は禁止(4.1: 境界を線にしない)。監査条件は『増加率 < 審議消化率』。
```

`soft_on_machine`（機械に割当てられた soft 要求）がゼロを保証できない組織は、第3章の非対称性定理（→3.6）を運用で否定している——数ではなく**検出されている事実**が重要で、検出ゼロは検査自体の死を意味する（指標のゲーミング防止：報告のゼロは検査ログの提示を要求する。4.1 の憲章条二の自己言及登記）。

### 回帰テストの三層 — CQ テスト・構造テスト・運用突合テスト

4.6 の pytest 実践（→前掲の test_cq.py）を、体系として三層に確定する。層の違うテストを混ぜると、失敗の意味が判別できなくなる（意味の失敗と実装の失敗と運用の失敗——三つの失敗は治療者が違う）。

**層一：CQ テスト**（→前掲——能力質問への答えの正しさ）。治療者：オントロジーチーム。失敗=意味の回帰（分類が意味を変えた、→2.2 の差分が暴れた形）。**層二：構造テスト**（グラフの形の不変条件——孤立ノード禁止・必須辺の存在・落日未処理の上限、→3.6 intent-audit・5.3 accountability-check がこの層の会員）。治療者：スキーマ保持者。失敗=簿記の空洞（記録の形が壊れた——内容は無傷の可能性が高い）。**層三：運用突合テスト**（宣言と実在の突合——guard の宣言入力突合（→5.5）、級自動判定（→2.6）、翻訳条約の自己検査（→6.6 の不変条件）、契約の diff 級判定（→4.4））。治療者：統治（審議槽）。失敗=統治の逸脱（形と意味が合って、**運用が宣言から逃げた**）。

```python
# conftest.py — 三層の選別(test layer で tag 分け,失敗の届け出先が自動分岐)
def pytest_collection_modifyitems(items):
    for it in items:
        if "test_cq_" in it.name: it.add_marker("layer1_meaning")
        elif "audit" in it.name or "invariant" in it.name: it.add_marker("layer2_structure")
        else: it.add_marker("layer3_governance")
# CI 側: layer1 失敗→ontology board へ ticket、layer2→schema 保持者、
#        layer3→審議槽(DelibSlot に議題自動起案) ← 検査と席の接続(→7.2)
```

層三の失敗を審議に載せる設計（→「検査と席の接続」原則、→7.2 で三度目の定式化）の意義を一言。層三の失敗はコードの失敗ではなく**組織が宣言を守っていない**失敗で、code review では治療できない（review できる人が統治の当事者である場合がある——→6.6 の腐敗の検査版：自己申告の gate を回す層を CI に置くと、層三は層一に退化する。よって層三の test 実行は CI に置き、失敗の届け出先を人間組織の外（審議槽の自動起案）に固定する）。

pytest 章の締めに、三層の**テスト自体の落日**を置く（→6.6 の落日の再帰）。CQ テストが 12 か月一度も失敗せず、CQ そのものが dormant（→4.2）なら、テストの落日審議が自動起票される——落日しないテストは、意味を守っているのではなく**意味が誰も触っていない保护区**になる（保护区は 2.1 の暴力と対の病——形式化しすぎた所の腐敗）。4 章全体の結論をここで回収する：意味の境界（4.1–4.3）は境界の**維持機構**（4.4–4.6）なしには一日で遊離し、維持機構は三層の失敗の届け出先（席）まで設計されたときだけ生きている。
