## 7.3 Actionable Ontology — 記述から処方へ

オントロジーは世界を記述する——これは本書の第1部以来の基盤である。しかし記述だけのオントロジーは、読み物として死ぬ。会議で参照され、検索でヒットし、しかし**世界を何も変えない**。この節では、オントロジーに処方の層を加える——**状態から、次に何ができるかを導出できるようにする**。Actionable Ontology（実行可能オントロジー）とは、状態記述（descriptive）に加えて、**行動・前提条件・効果・実行権限**の語彙を含むオントロジーである。7.1 のフロネシスの議論を正確に引き継ぎながら進む：行動ノードは「何をすべきか」を**決定しない**（決定は JudgmentEvent の側、→5.1）。行動ノードは「**何が今、できることとして開いているか**」を機械に読ませる。選定の座は人間のまま、その座に届く皿をオントロジーが用意する。この違いを一度失うと、7.5 のパイプラインは即座に危険物になる（決定も処方も機械がやる設計——5.3 の司令塔化の完全版）。

### 処方の語彙 — 行動ノードと三辺

処方の語彙を四要素で定義する。行動（Action）ノードと、それを結ぶ三種類の辺である。

**Action ノード**：`action_id`、`kind`（停止・増感・割当・通知・検査…）、`actor_class`（誰の類が実行しうるか）、`effect_spec`（効果の宣言——世界へのコミットメントの記述形）、`risk_class`（低／中／高——6.4 の方針が参照する危険級）、`intent_link`（この行動が仕える goal への辺、→3.2）。

**前提条件の辺 `REQUIRES`**：Action ノードから状態述語ノードへ。「`stop-line` は `line-running` を要求する」——前提が現状グラフで成立するとき、行動は**開く**（enabled）。

**効果の辺 `EFFECT`**：Action ノードから状態述語へ、`polarity`（+／−）つき。「`stop-line` は `line-running` を消し、`line-stopped` を生む」——効果は**宣言であって実行ではない**（実行は 7.5 の act段で API が担い、宣言は計画と説明の材料になる）。

**実行権限の辺 `CONTROLS`**：エージェント（人間・機械）から Action ノードへ。3.5 の realizability で敷設した `CONTROLS` 辺が、ここで満員の使われ方をする——**権限はオントロジーの内部にある**。この辺なしの Action 実行は、構造的に帰属のない暴力である（→3.6 の `orphan_action` 検出が、この層で初めて本気で機能する）。

```cypher
// 処方層の敷設(3.5 の CONTROLS と 3.6 の実行主体を行動ノードへ接続)
CREATE (a:Action {
  action_id: 'act.stop-line.v3', kind: 'stop',
  actor_class: 'HumanShiftLead',            // 誰の類向けかの宣言(実行資格ではない)
  effect_spec: "NOT line-running; line-stopped",
  risk_class: 'high',
  api_ref: 'site-api://line/M-7/stop',      // 実行の実体(→7.5)。宣言は API の仕様版数を指す。
  intent_link: 'goal://safety/prevent-bearing-failure'
});
CREATE (a)-[:REQUIRES]->(st:StatePred {pred: 'line-running', on: 'M-7'});
CREATE (a)-[:EFFECT {polarity: '-'}]->(st);
CREATE (a)-[:EFFECT {polarity: '+'}]->(st2:StatePred {pred: 'line-stopped', on: 'M-7'});
// 実行権限の辺は 3.5 で既に定義済み(CONTROLS)。agent の種別による許可規則は
// 3.6 の『機械 agent への soft 要求禁止』の行動版として Rego が担保する(→6.4)。
```

`api_ref` が**仕様版数を指す**点を強調する。API の挙動が変われば `effect_spec` の宣言が嘘になる（宣言と実体のずれ——1.5 のドキュメントとコードのずれの処方層版）。CI で「API 仕様変更 → 対応 Action の effect_spec 再検証タスク自動発生」を結ぶ（→4.6 の回帰思想の処方向け版。`effect_spec` が検証対象になるのは 7.6 の統合テストで実装する）。

### enabled_actions — 「いま何がableか」の照会

処方の中心的照会を置く。現状グラフの事実と `REQUIRES` 辺の照合で、開いている行動を列挙する。これは決定ではなく**候補の供給**である（EvidenceBundle の frame_options 供給、→5.3——オントロジーが frame-making の権利を担う場所、→7.1 の第三層の機械的最少版）。

```cypher
// enabled_actions: 現状事実で前提が成立している行動の列挙(候補供給)
MATCH (a:Action)-[:REQUIRES]->(sp:StatePred)
WITH a, count(sp) AS req_total,
     sum(CASE WHEN EXISTS { MATCH (sp)<-[:HOLDS]-(:Observation {fresh: true}) }
         THEN 1 ELSE 0 END) AS req_held
WITH a, req_total, req_held
WHERE req_held = req_total                       // 全前提が成立(『fresh』=観測の鮮度窓内)
OPTIONAL MATCH (ag:Agent)-[:CONTROLS]->(a)
WITH a, collect(ag.agent_id) AS controllers
WHERE size(controllers) > 0                      // 権限 holder のいない Action は候補に出さない
MATCH (a)-[:EFFECT]->(eff)
RETURN a.action_id, a.kind, a.risk_class, controllers,
       collect(eff.polarity + ':' + eff.pred) AS effects_declared
ORDER BY a.risk_class DESC;                      // 高リスクを先頭に(提示順=content、→5.3)
```

設計判断を三つ注釈する。其一、**権限 holder のいない Action は候補から落とす**——3.6 の `orphan_action` が enabled 照会に組み込まれ、執行不能な候補が判断の皿に載らない（皿に載るだけなら無害に見えるが、frame-making の汚染は必ず実務コストになる——現場が「実行できない選択肢」に時間を割く）。其二、`fresh: true` の鮮度窓——前提の成立は**いつの事実か**に依存する（→2.5 の時刻代数）。窓の長さは goal の `decision_budget_sec`（→7.2）から導出する：予算の内で使える観測の鮮度。其三、`ORDER BY risk_class` の提示順の設計——高リスクから先に出す順は安全の順ではなく**注意の配分の順**である（低リスクの行動が埋もれて見えない＝過剰リスク回避の逆転、→5.3 の順序効果の知識を処方 UI に適用する。順の設計自体が DesignDecision 登記対象、→5.5）。

### 記述だけのオントロジーが読まれるだけになる理由

本節の主題の裏面を論じる。Action・REQUIRES・EFFECT・CONTROLS を持たないオントロジー（第1部・第2部までで敷設した語彙だけ）は、なぜ参照はされても運行しないのか。三つの構造的理由。

其一、**閉ループがない**：記述オントロジーの出力（照会結果）は人間の読解に入り、人間の行為へは配線されない。行為→観測→記述の更新の環が、行為の段で断線している（OODA の Act→Observe の切断、→7.2）。其二、**反実仮想が使えない**：4.5 の counterfactual が「制約を緩めると何が壊れるか」を計算できたのは、制約が機械可読だからだが、記述だけの体系では「この語彙で記述したまま行動を変えたら」を計算する場所がない——処方層は反実仮想の**行動版**（「この Action を開いたら／閉いたら世界がどう変わるか」）の計算基盤になる。其三、**責任の辺がない**：CONTROLS なき体系では、実行の帰責が運用の慣習に逃げ、履歴代数と接続しない（2.5 の原則が語彙層に届いていない状態）。

処方層の追加は、この三断線を一度に結ぶ——行為が配線され（act段）、反実仮想が計算され（EFFECT 宣言の伝播）、帰責が辺になる（CONTROLS と actor 簿記）。ただし処方層の危険も同時に置く：**処方が読める体系は、処方が撃てる体系でもある。** enabled_actions が候補ではなく指令として扱われる道（5.3 の司令塔化）は、処方層の直ぐそばに開いている。本章全体の安全設計（5.5 のステートマシン、6.4 の方針門、7.4 のエージェント分離）は、この開いた道に柵をする設計である——**処方を持つオントロジーには、防腐層が前提条件として必要である**（第6章が第4部より前に来た編成順序の理由が、ここで説明される）。

### 処方の循環 — 効果の宣言と効果の実測の突合

処方層を腐敗から守る計器を最後に置く。EFFECT 宣言は未来への約束であり（「stop-line は line-stopped を生む」）、約束は実測と突合されねば腐る（2.3 の保持寿命）。実行後、観測が約束した状態述語を `HOLDS` で受け取ったかを突合する。

```cypher
// effect_verification: 宣言効果と実測効果の突合(ActionExec -> Observation 突合)
MATCH (x:ActionExec {exec_id: $id})-[:FIRED]->(a:Action)-[e:EFFECT]->(sp:StatePred)
OPTIONAL MATCH (sp)<-[:HOLDS]-(obs:Observation)
WHERE obs.at > x.at AND obs.at < x.at + duration($window)
RETURN e.polarity, sp.pred,
       CASE WHEN obs IS NULL THEN 'effect-missing'     // 宣言した効果が発生していない
            ELSE 'effect-held' END AS status;
// 効果の不在が繰り返される Action = 処方層の腐敗(宣言が嘘)。
// 落日条項(→6.6)の処方版: 効果実測の保持率で Action の生存を決める。
```

`effect-missing` の集計は Action の信頼残高であり、保持率の低い Action は enabled 候補から自動的に降格する（Warning→自動退役、→6.6 の落日の循環が処方層にも回る）。逆に「宣言していない効果」の検出（突合の逆方向：実行後の新 `HOLDS` が EFFECT 辺にない）は、**副作用の発見**である——副作用の発見は KB の更新要求（CQAmendment・REQUIRES/EFFECT 辺の追加）として審議槽へ供給される。処方層は宣言で閉じた体系ではなく、**宣言と実測の差分を食って更新される循環**である（6.6 の「運動としてのみ存在する」の処方版）。

### Actionable Ontology の会計 — 処方の資産価値と負債計上

処方化（記述→処方、→前節の Action・RuleAdoption の link）を、維持コストの観点から一回だけ会計する。処方は資産であるが、**未検証の処方と落日した処方（E4 前提の期限切れ、→4.1）は負債である**（→7.1 の減価償却の処方版）。処方資産の会計表を定義する。

| 勘定科目 | 中身 | 計上規則 |
|---|---|---|
| 資産:稼働処方 | review_due 内の RuleAdoption＋実測付き Action | effect_verification 成功計数つきで計上（→7.3） |
| 資産:候補処方 | Quarantine の候補（未 adopt だが供給源あり） | 審議槽への供給計数為価値（→7.1 の皿の材料） |
| 負債:落日処方 | 前提 E4 期限切れ・review_due 超過 | 実行禁止・警告帯（hollow-fluent、→5.2） |
| 負債:孤児処方 | 引用する記述（TBox 語）が削除・改名された処方 | roundtrip 検査が検出（→6.3 の CRITICAL の処方版） |
| 償却費用 | 処方の再検証（revalidate）の実働時間 | 時間予算に計上（→8.2 条件三） |

```cypher
// prescription-ledger — 処方資産の四半期貸借
MATCH (r:RuleAdoption) WHERE r.act='adopt'
WITH r, CASE WHEN r.review_due < datetime() THEN 'liability-expired' ELSE 'asset-live' END AS cls
WITH cls, count(r) AS n
UNION
MATCH (a:Action)-[:REQUIRES]->(t) WHERE NOT (t)-[:LIVES_IN]->(:TBox)
RETURN 'liability-orphan' AS cls, count(a) AS n;
```

会計の目的は、**処方数の増加を資産成長と誤読しない**ことである。処方の残高（処方条項の総数）だけを見るチームは、負債（落日・孤児）を分子に含めた成長報告をする（→6.6 腐敗——統計が燃料でなく外観になる）。資産表は「稼働処方の実測残高」と「負債の滞留年齢」の二本を並べ、負債の滞留が閾値（例：総処方の 15%）を超えたら**新処方の制定を凍結して償却に人手を回す**（→8.2 の再解釈労働の予算の会計実装——新しいものを作る前に、古いものを問い返す時間に人を配る。この凍結規則のない体系は、処方のインフレで通貨価値（=処方の信頼）を失う）。

この会計は 3.1 の四原因の貸借への橋でもある——処方の資産価値の本体は final cause（目的因）の勘定に載る（処方が生きている goal に link されているか、goal の落日で処方は自動的に負債側に落ちる、→3.1 の telos_chain の落日）。記述が form cause の台帳なら、処方は final cause の台帳である—— actionable ontology の維持とは、目的の存続を機械的に追うことなのである。

### Actionカードの六字段 — 処方を読み解くための券

7.3 の Action ノード（処方）を、人間が read できる形=Action カードとして仕様の締めに置く（→8.5 の offer が Action の UI 表示である理由がここで揃う）。六字段：**act_id / intent（何をする語ではなく何のためか、→3.1 final cause の字段）**、**preconditions（E1 実測級の条件+観測 URI、→4.1 宣言の級）**、**effect（書き换える世界状態の宣言、→7.3 の辺）**、**withdrawal（effect が退く条件——→5.3 の確率の withdrawal_conditions の処方の行動版：いつまで有効かを書かない処方は落日しない処方で、落日しない処方は老朽する処方、→5.2 hollow-fluent）**、**seat（この act の异議・落日・改訂の席の URI、→6.6・8.2 の席の字段——席のない処方は執行だけあっても直し手が届かない）**、**history（adopt の日・再検証の日・effect_verification 集計、→4.4 証拠条約·→7.1 残高）**。

```cypher
// action-card — 六字段の CQ(「この処方を読み解けるか」の質問形)
MATCH (a:Action) WHERE a.risk_class IN ['low','medium'] AND a.status='active'
OPTIONAL MATCH (a)-[:ADOPTED_BY]->(ra:RuleAdoption)
OPTIONAL MATCH (a)<-[:EFFECT_VERIFIED]-(ev:EffectEvent)
RETURN a.act_id, a.intent IS NOT NULL AS has_intent, a.withdrawal IS NOT NULL AS has_withdrawal,
       EXISTS { MATCH (a)-[:SEAT_OF]->(:DelibSlot) } AS has_seat, count(ev) AS verifications
ORDER BY has_intent, has_withdrawal, has_seat LIMIT 20;
```

この照会の輸出順が重要で、**字段の欠落が先頭に来る**（read できない処方から先に直す——処方の庫の整頓順序は、庫の側ではなく人間の側で決まる）。withdrawal と seat の欠落は、7 章の自動化（段1〜2、→7.6）で最も高くつく——退き時を書かない自動 act は demote（→7.6 の降格自動）の条件を機械が計算できないからである。**字段が欠けた処方を自動走らせない**は 7.3 の最後の命令文であり、実行則は test_safety_fall（→7.6）の六障害テストに字段検査として織り込まれる。

### 実行練習

1. あなたの KB（2.4 の TBox）に処方層を敷設し、中心業務1本の Action を3つ（低・中・高 risk 各1）、REQUIRES/EFFECT/CONTROLS 辺 記述 に登録せよ。`enabled_actions` を現状データで実行し、候補がゼロで出た場合、そのゼロの意味（前提の成立失敗か、権限 holder 欠落か、鮮度窓切れか）を分解して報告せよ——ゼロ候補は世界の状態の宣言である（→5.4 の「候補ゼロ」）。
2. 処方層がない状態（今の KB）と敷設後で、4.5 の counterfactual の行動版を1本ずつ走らせよ（「`stop-line` の REQUIRES に `two-approvals` を足したら、enabled の平均遅延と夜間カバレッジがどう変わるか」）。差分表を作り、REQUIRES 追加の級（→2.6）と DesignDecision 登記（→5.5）の文案を書け。
3. `effect_verification` の保持率計をあなたの実際の自動化手順（スクリプト・RPA・承認フロー）に当て、宣言と実測のずれを3件見つけよ（典型：「メール送信済み」宣言で実際は迷惑フォルダ、→宣言と実体の層、1.5）。ずれの 各 について、宣言を直すか実測窓を直すかを級つきで決め、EffectSpec の version をどう回すか（→2.4 の版数原則の処方版）を1段落書け。
