## 4.6 pytest実践 — オントロジーの回帰テストを書こう

第4章の部品——検証等級（4.1）、CQ 三つ組（4.2）、retrofit 抽出（4.3）、契約（4.4）、判定器（4.5）——を、開発者の日常語彙であるテストコードに落地させる節である。主題は一つ：**オントロジーの回帰テスト**。コードの回帰テストは「壊したくない動作」の記憶であるが、オントロジーの回帰テストは「壊したくない世界像」の記憶である。2.3 のスティグレールの語を借りれば、pytest スイートは組織の第三次的保持の最も機械に近い形態だ——運用を規定し、再検証を循環させる保持。この節の終わりに、あなたのオントロジーは実行可能な認識論（checklist → テスト）を持つ。テストが失敗するたびに、世界像が実際に守られているかどうかの証拠が一つ増える。

### 回帰テスト＝オントロジーの記憶 — 「壊れた世界像」の再発を見張る

普通のユニットテストとオントロジー回帰テストの差を、本章の語彙で確定する。前者は**関数の挙動**の保存、後者は**構造と宣言の保存**である。2.5 で CQ 墓標（`RetractedCQ`）が「削除された問いの要求していた構造」の見張りになると書いた。pytest はその見張りの実体である。

回帰テストの三層を定義する。

- **L1 構造回帰**：載せねばならない結合・型・語彙が消えていないか（DDL・TBox・`REFERENCES` 辺の生存）。
- **L2 宣言回帰**：契約・制約（→4.4/4.5 の名前付き制約）が CI で sat/unsat の期待どおりに落ちないか（制約の版数と solver 版数の固定つき）。
- **L3 応答回帰**：CQ の答えの形（answer_contract）が保たれているか、期待値そのものではなく**契約として**（数値の固定は 2.4 の version の墓標化と接続する）。

```python
# tests/conftest.py — Neo4j とテスト用最小世界(フィクスチャ)
# 哲学: テスト世界は KB の『ミニチュア世界像』である。ミニチュアの設計者は
# 世界像の設計者と同じでなければならない(現場の語彙で書かれた fixture でないと
# テストは開発者の空想の世界像を回帰させる、→2.6 の権利条文の実装版)。
import pytest
from neo4j import GraphDatabase

@pytest.fixture(scope="session")
def driver():
    d = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "test-pass"))
    yield d
    d.close()

@pytest.fixture
def world(driver):
    """夜間検知デモの固定世界(→3.5)。fixture 名が世界像の名前になる。"""
    with driver.session() as s:
        s.run("""
        CREATE (m:Machine {m_id:'M-7'}), (sh:Shift {shift_id:'S9', type:'night'}),
               (d:Drift {d_id:'D-1', at:datetime('2026-10-01')}),
               (d2:Drift {d_id:'D-2', at:datetime('2026-10-20')}),
               (m)-[:HAS]->(d), (m)-[:HAS]->(d2), (d)-[:OCCURRED_IN]->(sh),
               (d2)-[:OCCURRED_IN]->(sh);
        """)
        yield s
        s.run("MATCH (n) DETACH DELETE n")   # 破棄の自動化 = 世界像の埋葬手順の統一
```

### CQ をテストへ — 三つ組の pytest 実装

4.2 の `CompetencyQuestion` モデル（(a)原文/(b)cypher/(c)応答制約の三つ組）から、テストを**生成**する。手書きテストを禁止するのではない——手書きテストと生成テストが食い違った瞬間（→4.4 の二重管理の窓）を CI が検出するために、生成側を正規の通路にする。

```python
# tests/test_cq.py — CQ レコードからのテスト自動生成(parametrize で全 CQ を回帰化)
# 哲学: 各 CQ テストは「この問いに答えられる世界像」の生存証明。
# 失敗 = 世界像の壊れ方の一種であり、失敗メッセージは CQ の原文で読む。
import pytest
from cq_spec import CompetencyQuestion

CQ_STORE = load_cq_registry()   # 4.2 の履歴代数上の CQ 三つ組を版数付きで読む

@pytest.mark.parametrize("cq", CQ_STORE, ids=lambda c: c.cq_id)
def test_cq_structure(world, cq: CompetencyQuestion):
    if cq.verif_class != "E1":
        pytest.skip(f"{cq.cq_id} は E1 ではない({cq.verif_class}) — 4.1 の等級区別をテストが守る")
    recs = world.run(cq.cypher, **cq.params).data()
    # (c) answer_contract の機械化: 応答のキー・非空・順序の契約検査
    assert contract_holds(cq.answer_contract, recs), (
        f"{cq.cq_id}: {cq.text!r} — 応答契約の破綻。"
        f"世界像の変更(commit {cq.approved_commit})に対する回帰疑い"
    )

@pytest.mark.parametrize("tomb", load_retracted_cqs(), ids=lambda t: t.cq_id)
def test_retracted_cq_witness(world, tomb):
    """4.2 の墓標見張り: 削除 CQ の要求構造が『いつの間にか復活・消失』していないか。
    復活=未承認の仕様変更の兆候、消失=意図せず構造が死んだ兆候。両方報告。"""
    exists = world.run(tomb.structure_probe).single()["n"] > 0
    expected = tomb.revival_policy          # 'forbidden' | 'requires-L2'
    if expected == "forbidden":
        assert not exists, f"{tomb.cq_id}: 退位した構造が復活。未承認変更か(→2.6 OverrideEvent 照会)"
```

`pytest.skip` の扱いに注意を奪われたい。E3（審議記録）の CQ をテスト実行から区別して skip するのは、4.1 の等級制度がテスト配管にも埋め込まれている証拠である。skip は「検証しない」ではなく「検証の主体が人間である」の宣言である——skip 件数のレポート（下記 checklists）が「人間に依存している検証の量」を数える。

### 契約回帰 — 名前付き制約の sat 期待値テスト

4.5 の名前付き制約辞書を、期待 verdict 付きの表で持つ。制約の変更（→2.4 の version 管理）は期待値の更新を要求し、更新忘れは回帰テストが止める。

```python
# tests/test_contracts.py — 制約表の sat/unsat 期待値回帰(solver/境界の版数固定)
import pytest
from z3 import Solver

@pytest.mark.parametrize("name,cons,expect", [
    ("inspect_window+world", INSPECT_CASE, "UNSAT"),     # 4.5 の事例を回帰化
    ("night_sampling-alone", NIGHT_ONLY,   "SAT"),
], ids=lambda x: str(x[0]))
def test_constraint_verdict(name, cons, expect):
    v = judge(name, cons)
    assert v["verdict"] == expect
    if expect == "UNSAT":
        assert set(map(str, v["core"])) == EXPECTED_CORES[name]  # core の名前簿記まで回帰化
```

**unsat core まで回帰化する**のが本章の一手である。verdict だけでなく core の名簿まで固定すると、制約の追加・削除が core の構成を変えた瞬間にテストが落ちる。core の変化は「禁止の防壁の誰の寄与で建っているか」の変化——世界像の力学的変化——であり、verdict が同じでも無視してはならない。core 回帰は、世界像の**構造力学的**な健全性の検査である。

### 退行の記録 — テスト失敗の履歴代数化

テスト失敗を CI の赤信号で終わらせず、2.5 の履歴代数へ載せる。失敗レコード（`RegressionEvent`）は、障礙の実例（→3.4 `Incident`）と契約違反（→4.4）の第三の兄弟——**世界像が壊れかけた出来事の第三型**（コード変更由来の壊れ）である。

```cypher
CREATE (r:RegressionEvent {
  test_id: $tid, failed_at: datetime(),
  ci_commit: $sha, ontology_version_ref: $kbver,   // 世界像の版数とコード版数の同時固定
  suspect_change: $blame_sha,                      // git bisect 結果(→2.5 の git 橋の再利用)
  cq_ref: $cq_id,                                  // どの問いの守りの失敗か
  resolved_by: null
});
```

`suspect_change` が入ることで、4.2 の供給源(c)（障害→CQ 変換）と 3.4 の障礙更新（`stale→live`）が自動配管になる——回帰失敗→障礙/制約の `live` 化→次回レビューの議題化。第2部半ばで既に三度書いた循環（事件→形式→運用→事件）が、ここで初めて**機械に回りはじめる**。pytest が認識論の部品である最終的な理由はここにある：テストは世界像の代謝の速度計だからだ。

### 実行可能チェックリスト — 第四章の総点検をクエリで引く

最後に、4.1〜4.5 までが要求してきた「登記」の総点検を、本章の診断定理の統合クエリとして置く。人間が読むチェックリスト（「CQ に上位 goal 参照があるか」）を、機械が引く状態報告に置換する——1.5 の「ドキュメントがコードとずれる」問題の、設計としての解決。

```cypher
// 4章統合健全性レポート(epistemic scorecard) — 週次で自動生成・審議の議題へ
CALL { MATCH (cq:CompetencyQuestion) WHERE NOT (cq)-[:ANSWERS_FOR]->() RETURN count(cq) AS orphan_cq }
CALL { MATCH (t:RetractedCQ) WHERE NOT (t)-[:WATCHED_BY]->(:RegressionTest) RETURN count(t) AS unwatched_tombs }
CALL { MATCH (a:Agent {kind:'machine'})-[:ASSIGNED_TO]<-(r:Requirement {softness:'soft'}) RETURN count(r) AS soft_on_machine }
CALL { MATCH (cf:ConstraintConflict {resolution:'pending'}) RETURN count(cf) AS open_conflicts }
CALL { MATCH (o:Obstacle {status:'stale'}) RETURN count(o) AS stale_obstacles }
CALL { MATCH (t:RetractedClaim) WHERE NOT (t)-[:WATCHED_BY]->(:RegressionTest) RETURN count(t) AS retracted_unwatched }
RETURN orphan_cq, unwatched_tombs, soft_on_machine, open_conflicts,
       stale_obstacles, retracted_unwatched,
       (orphan_cq + unwatched_tombs + soft_on_machine + open_conflicts
        + stale_obstacles + retracted_unwatched) AS epistemic_debt_total;
// epistemic_debt_total の増減は『世界像の誠実さの負債残高』である。
// ゼロ目標は禁止(4.1: 境界を線にしない)。監査条件は『増加率 < 審議消化率』。
```

`soft_on_machine`（機械に割当てられた soft 要求）がゼロを保証できない組織は、第3章の非対称性定理（→3.6）を運用で否定している——数ではなく**検出されている事実**が重要で、検出ゼロは検査自体の死を意味する（指標のゲーミング防止：報告のゼロは検査ログの提示を要求する。4.1 の憲章条二の自己言及登記）。

### 回帰テストの三層 — CQ テスト・構造テスト・運用突合テスト

4.6 の pytest 実践（→前掲の test_cq.py）を、体系として三層に確定する。層の違うテストを混ぜると、失敗の意味が判別できなくなる（意味の失敗と実装の失敗と運用の失敗——三つの失敗は治療者が違う）。

**層一：CQ テスト**（→前掲——能力質問への答えの正しさ）。治療者：オントロジーチーム。失敗=意味の回帰（分類が意味を変えた、→2.2 の差分が暴れた形）。**層二：構造テスト**（グラフの形の不変条件——孤立ノード禁止・必須辺の存在・落日未処理の上限、→3.6 intent-audit・5.3 accountability-check がこの層の会員）。治療者：スキーマ保持者。失敗=簿記の空洞（記録の形が壊れた——内容は無傷の可能性が高い）。**層三：運用突合テスト**（宣言と実在の突合——guard の宣言入力突合（→5.5）、級自動判定（→2.6）、翻訳条約の自己検査（→6.6 の不変条件）、契約の diff 級判定（→4.4））。治療者：統治（審議槽）。失敗=統治の逸脱（形と意味が合って、**運用が宣言から逃げた**）。

```python
# conftest.py — 三層の選別(test layer で tag 分け,失敗の届け出先が自動分岐)
def pytest_collection_modifyitems(items):
    for it in items:
        if "test_cq_" in it.name: it.add_marker("layer1_meaning")
        elif "audit" in it.name or "invariant" in it.name: it.add_marker("layer2_structure")
        else: it.add_marker("layer3_governance")
# CI 側: layer1 失敗→ontology board へ ticket、layer2→schema 保持者、
#        layer3→審議槽(DelibSlot に議題自動起案) ← 検査と席の接続(→7.2)
```

層三の失敗を審議に載せる設計（→「検査と席の接続」原則、→7.2 で三度目の定式化）の意義を一言。層三の失敗はコードの失敗ではなく**組織が宣言を守っていない**失敗で、code review では治療できない（review できる人が統治の当事者である場合がある——→6.6 の腐敗の検査版：自己申告の gate を回す層を CI に置くと、層三は層一に退化する。よって層三の test 実行は CI に置き、失敗の届け出先を人間組織の外（審議槽の自動起案）に固定する）。

pytest 章の締めに、三層の**テスト自体の落日**を置く（→6.6 の落日の再帰）。CQ テストが 12 か月一度も失敗せず、CQ そのものが dormant（→4.2）なら、テストの落日審議が自動起票される——落日しないテストは、意味を守っているのではなく**意味が誰も触っていない保护区**になる（保护区は 2.1 の暴力と対の病——形式化しすぎた所の腐敗）。4 章全体の結論をここで回収する：意味の境界（4.1–4.3）は境界の**維持機構**（4.4–4.6）なしには一日で遊離し、維持機構は三層の失敗の届け出先（席）まで設計されたときだけ生きている。
