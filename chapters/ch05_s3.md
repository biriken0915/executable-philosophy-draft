## 5.3 なぜ確率的生成に責任を置けないか

5.1 の区画を、本章の中心命題が具体化する。**尤度は正統性ではない。** LLM の出力が「もっともらしい」ことと、その出力を世界へのコミットメントとして**引き受けられる**ことの間には、原理的な断絶がある。この節では、断絶の論理を精密にし、そして断絶を無視した設計の三つの失敗型——司令塔化、隠れ判断、責任の蒸発——を解剖する。5.2 の現象学が判断の材質を語ったのに対し、この節は確率の意味論を扱う。読者に必要な数学は条件付き確率の記号だけである。必要な哲学は「真理」と「正統性」の区別だけである。

### 尤度の意味 — P(next token | context) が意味しないもの

LLM の生成は本質的に条件付き確率の反復である：次のトークンは、これまでの文脈に対する確率分布から選ばれる（あるいは近似される）。この確率は**文脈内でもっともらしい続きの度合い**であり、つぎの三つではない。

**(1) 真理の度合いではない。** 「パリの首都は Paris です」も「パリの首都は Berlin です」も、文脈の設計次第で高い尤度を持ちうる（後者は皮肉・誤答データ・敵対的プロンプトの文脈で高まる）。尤度は**連続性の度合い**であって、対応の正しさではない。3.2 で `arg_type: 'plausible'` と `'logical'` を混ぜるなと書いたが、あの区別はここで根本の意味を持つ——尤度の体系は plausible の体系であり、logical の体系ではない。両体系は同じ文字列を表層に出力しうるが、**出力の意味（何が担保されているか）が違う**。

**(2) 存在の度合いではない。** 「2027年3月の夜勤逸脱 D-912 は深刻だった」を高尤度で生成することは、D-912 の存在を一切主張しない——文脈内の連続性として正しい確率計算の結果だからである。5.2 の現前化の代行が危険なのは、生成文が**主張の形式**（flat な直説法）で現れるのに、生成過程に**主張の機能**（コミットメント）が皆無だからだ。形式と機能のこの断離が、次の節の Quarantine 設計の存在論的理由である。

**(3) 正統性の度合いではない。** 正当な手続を経て承認された出力（2.6 の承認フローを通ったもの）と、高尤度の出力は、統計的に無関係である。正統性は手続の性質であり、尤度は分布の性質である。

三つの「ではない」を束ねる本書の定理（非公式、名前のない定理）を置く。**尤度の体系は、妥当性要求（→6.2 の理解可能性・真理性・正統性・誠実性）のどれも、単独では充足しない。** 尤度が最も近いのは理解可能性（fluency、受け取れる形）である——しかも唯一、LLM が大量に供給できる次元が理解可能性であり、他三者は外部配管（検証・承認・誠実性の登記）で供給するしかない。この非対称配分を設計に埋めない組織は、供給の豊かな次元（もっともらしさ）を、欠乏の次元（真理・正統）の**代理**として使用してしまう。代理使用の失敗が、以下に続く三型である。

### 失敗型一 — 司令塔化（the LLM as bridge operator）

LLM を判断連鎖の**決定地点**に置く設計。「AI が却下し、人間が機械的に承認する」（5.1 の保険解剖）、自動デプロイの go/no-go を LLM 評決に委ねる、クレーム回答を LLM が送り、後追い人間レビューは例外のみ——これらの共通構造は、**reckoning の卓越性（理解可能性＋膨大な候補生成）を根拠に、judgment 配分の主体に座らせる**ことである。5.1 の三条件（コミットメント・accountability 末端・更新経路）のどれを満たさない主体が、命令を出す位置にいる。司令塔化は能力の問題ではなく**位置の誤配**である。

構造的診断を一文で置く。**司令塔化は、尤度を正統性の代理として使う設計である**——「もっともらしい答を返すのだから、それで決めてよい」が暗黙の免状であり、5.3 の定理がその免状を無効にする。

### 失敗型二 — 隠れ判断（latent judgment）

より巧妙で、より多い失敗。「決定は人間が行っている、LLM は補助だけ」という設計で、L LM が**判断の前提を形成**している場合——判断の選択肢の提示順（アンカリング）、根拠の選別（何が証拠として並ぶか）、論点の枠（何について考えるか）を LLM が握っている状態である。人間の署名は形式上末端ノードに座っているが、**判断の材料形成（frame-making）が reckoning に移住している**。

隠れ判断は監査が最も難しい。JudgmentEvent の basis_reckoning（→5.1）に LLM 経路が明示的に登記されていれば検出可能だが、「担当者が参考までに見たメモ」は履歴に載らない（1.6 の NonRecordingRule の逆——**記録すべき相互作用が記録されていない**）。設計対応は判断材料の供給経路を**強制的に形式化**することである：判断画面に並ぶ候補・証拠・論点は、システムが `EvidenceBundle` として生成し、その生成過程（誰が・どの検索・どの LLM 補助で）を登記する。LLM に「自由にメモを作らせない」のではなく、**メモの流通を履歴代数に通す**（2.5 の原則の判断層への拡張）。

```cypher
// EvidenceBundle: 判断の材料形成の履歴化(隠れ判断の検出器)
CREATE (eb:EvidenceBundle {
  eb_id: $eid, judged_event: $jid,
  sources: $source_refs,                    // 検索クエリID・KB参照・文書版数
  llm_assisted: true,
  llm_role: 'frame-maker',                  // 'frame-maker' | 'candidate-generator' — 役割の自己申告必須
  frame_options: $options_json,             // 提示された選択肢と順序(順序は content である)
  generated_at: datetime()
});
MATCH (eb:EvidenceBundle {eb_id: $eid}), (je:JudgmentEvent {j_id: $jid})
CREATE (je)-[:JUDGED_ON {via: $eb_id}]->(eb);
// 検査(→6.4 の Rego に接続): llm_role='frame-maker' の JudgmentEvent の割合が
// 部門平均から外れたら E4 再審議の自動発火(5.1 の update_route の配管)。
```

`frame_options` に**順序まで**保存する設計の重要性。選択肢の提示順は中立的な表示ではなく content である（順序効果は判断研究の確立事実）。順序を保存しない EvidenceBundle は、frame-making の記録ではなく frame-making の否認である。

### 失敗型三 — 責任の蒸発（responsability evaporation）

三型目は、設計が責任を配分した**つもり**で、どこにも配分していない状態である。「AI が生成し、レビューが承認し、ユーザーが信頼した」——三段のそれぞれに主体がいるのに、誤りの帰責地点が存在しない。レビューの承認は実効的承認の条件を満たさない（5.1 の再検証可能性）。生成の主体（開発者）は「レビュー通過を信じた」。ユーザーは「承認済みを信じた」。三段の相互信頼が、帰責の環を**閉じずに素通りさせる**——責任が蒸発するのではなく、**設計が責任の凝結点を作らない**。

蒸発の検査はグラフでできる：`JudgmentEvent` から `RESPONSIBLE_FOR` の末端まで、辺を辿って到達できる経路が存在しない事件は、構造上帰責不能である（→3.6 の orphan_action 同型）。4.6 の scorecard に `unanchored_judgment` を加える。

```cypher
// unanchored judgment 検出(3.6 検査の judgment 層版)
MATCH (je:JudgmentEvent)
WHERE NOT (:Agent {kind: 'human'})-[:RESPONSIBLE_FOR]->(je)
   OR NOT EXISTS { MATCH (je)-[:JUDGED_ON]->(:EvidenceBundle) }   // 材料形成の否認も帰責不能
RETURN je.j_id, 'responsability-evaporation' AS diagnosis;
```

### 三型の統一診断 — 「尤度で正統性を代替した度」を測る

三型は別々ではなく、一つの欠乏の三つの埋め方である。**正統性（承認・手続・帰責）の供給が不足している組織は、尤度（もっともらしさ）で埋める**——司令塔化は決定地点での埋め、隠れ判断は材料での埋め、蒸発は記録での埋め。よって防腐の設計（→6.3〜6.5）は、尤度の遮断ではなく**正統性の供給装置**として設計される（Harbermas の妥当性要求の機械化、→6.2）。本書の第3部後半が「防腐層」と「討議」を同じ章で扱うのは、この供給の一体性のためである。

節末に、5.1〜5.3 の配分表を置いておこう。この表は5.4〜5.6 の実装の設計仕様そのものである。

| 機能 | 誰が（部品） | 誰が（人） | 履歴代数での登記 |
|---|---|---|---|
| 候補生成（reckoning） | LLM・検索・KB | — | `CandidateSet`（モデル版・seed・温度つき、→5.4） |
| 妥当性の機械検証 | Rego・SHACL・sat 判定器 | — | `ValidationVerdict`（core 名簿つき、→4.5・6.4・6.5） |
| 世界へのコミットメント | なし（機械はコミットできない） | 人間エージェント（実効的承認） | `JudgmentEvent`（末端＋材料＋更新経路、→5.1） |
| 経験の更新 | — | 政策・契約の変更者 | `Commit`（2.5 橋）、`policy-diff` PR |

表の第三行の「なし」を直視することが、第3部の通過儀礼である。AI への不信ではなく、**コミットメントという行為の存在論**が「なし」を作る。機械は約束を出せるが、約束に**縛られることがない**——縛られることがない主体の約束は、約束ではなく信号である。

### 責任の簿記 — JudgmentEvent 台帳の運用と矛盾処理

判断を人の側に置いた（→5.1）なら、責任の配線を簿記として完成させねばならない——責任は哲学的名言ではなく、照会可能な関係名簿であるべきだ（→4.4 の「証拠＝データ」の倫理版）。JudgmentEvent 台帳の運用規則を四条、確定する。

**其一、一判断一末端**：世界を変える許可（transition の実行、→5.5）に紐づく各 JudgmentEvent には、単一の decider と単一の accountability terminal（名簿上の ID）を要求する（→5.1 の定義の DB 強制：je_id ごとに `accountable_to` が 0 件または 2 件なら、その判断は CI で reject——2 件の場合は連署であり、連署は単一末端に解消規則（主任筆）を持つ）。**其二、委任の連鎖は簿記される**：A が B に判断を委任するとき（→7.2 の委任深度）、JudgmentEvent に `delegated_from` 辺が載り、A の残余責任が数値で残る（残余責任の数値化：委任後の A が保持する拒否権・監査頻度・落日周期）。**其三、判断の矛盾は台帳の事件**：同一状況スレッドで両立しない判断が登記されたら（例：停止を承認した thread で稼働継続を承認）、矛盾検出クエリが OverrideEvent 相当の事件（→3.4 の N3）を起こし、両判断の decider の共観セッションを自動起案する（→8.3 の矛盾の併置で解決へ）。**其四、判断の履歴は判断者本人に開かれる**：自分の JudgmentEvent 全列と、その後の実測（effect_verification、→7.3）と反論（Objection、→8.4）の突合面——判断者は自分が判断者であることを簿記で知る（→8.2 条件一の自己履歴アクセス権）。

```cypher
// accountability-check — 責任の簿記の invariant(→5.6 の invariant 文化の倫理版)
MATCH (je:JudgmentEvent) WHERE je.at > datetime() - duration('P1Q')
OPTIONAL MATCH (je)-[:ACCOUNTABLE_TO]->(p:Person)
WITH je, count(p) AS terminals
WHERE terminals <> 1
RETURN je.je_id, terminals, CASE WHEN terminals = 0 THEN '責任の蒸発' ELSE '末端二重化' END AS fault;
```

この invariant を test_ownership.py の一テストとして載せること（→4.6）。責任が消えるのは制度の自然現象ではなく、**スキーマが許していること**の帰結だと書く——`ACCOUNTABLE_TO` の不在をクエリが弾かないグラフは、責任の蒸発をデフォルトにしている。本書が「責任の簿記」という語をあえて会計語で置く理由も注いでおく——簿記は、残高が合わなければ帳簿全体が疑われる。二重仕訳（判断の借方＝コミットメント、貸方＝引き受けた不確実性）が合わなくなる瞬間を機械が教えるUntil、責任は語りの側に残り続ける。

尤度→正統性の launderings（→5.3 の洗浄）への最後の防壁も、同じ簿記語彙で定義できる。**正統の残高**——各審議槽・各級・各落日が記録した「承認の実測（→2.6 の保留統計・四率）」の累計であり、これがマイナスに転じた領域（dissent 無視の連続・落日の空振り・forced-consent 発火）では、その領域の全ゲート判定に Warning が自動で添わる（正統の残高は、判定の正しさと独立に、判定の受け入れ可能性の帳簿である——4 妥当性要求の正統性欄の実在残高、→6.2）。

### 確率の約束 — 「70%」はコミットメントか

判断の三要素（→5.1）と 5.3 の中心命題を、一本の文で試す——**「この部品は 70% の确率で 30 日に故障する」はコミットメントか**。答えは三段で違う。(a) 単純な尤度の報告なら No（Reckoning の産出——世界の状態の記述に过ぎない、→5.1）。(b) この文に基づいて発注・停止・保険が動くなら Yes に**近づく**——文が行動の前提になるとき、コミットメントの条件（結果の引き受け）が現実化する。(c) Yes になる条件は、文の側に三要素が書けること——**誰が**この 70% を裏書け（末端）、**何が壊れたら**この文は退くか（根拠の反証条件、→8.5 falsifiable_if の確率版：「訓練分布がこの設备年代の試料を含まないならこの数是退く」）、**誰がいつ**70% を 40% に更新できるか（更新経路）。

校准（calibration——予言确率と実現频度の一致）は a の品質を上げるが、c の三要素を**自動では産生しない**（Brier score の優秀なモデルの持ち主も、誤警報の末端には書かれない——**校准は精度の美德で、責任の機制ではない**）。よって本書の确率要求は一つ——**确率の周囲を契約で包め**：`prob(pump_fail,30d)=0.7` の記録には basis（訓練窗口・适格設备の分布）、withdrawal_conditions（退く条件の列表）、updater（更新の末端と級）の三列を強制する（→llm_call の四版本簿記、→8.5 offer schema と同じ形）。三列が書けない确率文は、判断の語に化けた記述である——→5.3 の laundering（尤度が正統性の語に洗濯される）は、三列の欠落という**具体的な簿記事故**としてのみ発現する。

### 練习解答の型 — 尤度文を契約文に書き换える

本章の練习 2（確率文の契約化）の解答の型を一つ示す（書式を見せないと練习は形式だけ残る、→4.2 CQ 三分間と同じ趣旨）。問題文「ポンプ 3 の 30 日故障确率 0.68」の契約文化：

```yaml
prob_claim:
  claim: "pump3.fail within 30d = 0.68"
  grade: E1                          # 尤度自体は実測級(モデル出力)
  basis: { model: surv-v7, train_window: 2019-2025, fleet_age_mix: "平均4.1年" }
  refute_by: "該 pump の年代区分が訓練分布外なら 0.68 は退く"   # →4.1 E2 カードと同一字段
  commitment:                        # 三要素(→5.1)を尤度の周囲に載せる
    seat: 保全長(段1承認者)           # 末端:この数に基づく停止/継続の承認者
    cost_of_error: "停止コスト 18h/回 vs 故障コスト 72h+安全風険"  # 結果の引き受けの宣言
    updater: { who: 可靠性工程師, grade: L2, period: 月度 }        # 更新経路と級
  calibration: { brier_90d: 0.11, note: "fleet 全体では良好、pump3 年代区分では未測" }
```

注目点は calibration の note で、**全体では校准できているが問題の pump3 の区分では未測**という状態が実务では最频（集合の校准が個別の末端を救わない——5.1 の判断が個別である理由の統計版）。この note が commitment.seat を人間にしている理由であり、契約文の全体が「0.68 に誰がどこまで背負うか」の一頁になっている（尤度→契約の書き换えは、5.3 の中心命題「确率は末端を産生しない、末端は席位である」の機械的な実現である）。

### 実行練習

1. あなたの組織の LLM 利用場所を全部挙げ、それぞれを司令塔化／隠れ判断／蒸発の三型で診断せよ（混合型もある）。診断根拠として、5.3 の定理の三「ではない」（尤度≠真理・存在・正統）のどれが当該場所で違反されているかを1か所ずつ特定せよ。
2. `EvidenceBundle` をあなたの判断画面で実装した場合の最小版（`llm_assisted` と `frame_options` の保存だけ）を設計し、その実装が「メモの流通を履歴代数に通す」をどこまで達成しどこで裏切るかを2段落で評価せよ（裏切りの例：ブラウザ外のコピペ、口頭）。
3. 5.1〜5.3 の配分表をあなたの組織の現状で書き直せ（現状はどの機能を誰が担っているか、登記は存在するか）。差分から最優先の修正1つを決め、2.6 級 L2 の変更説明文（何の供給不足を尤度で埋めていたか）を書け。
