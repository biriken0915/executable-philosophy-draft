## 2.2 ヘーゲル — 止揚（Aufheben）を差分演算として読む

2.1節で、分類は「切る」こと（caedo）であり、必ず残余（surplus）を生むと見た。残余を捨てるか保存するかが設計を分けるとも書いた。では、捨てない設計とは具体的にどんな演算なのか。この節はそこを埋める節である。答えの候補として、ゲオルク・ヴィルヘルム・フリードリヒ・ヘーゲル（G.W.F. Hegel）の止揚（Aufheben）を、形而上学の用語としてではなく、差分演算（differential operation）の仕様として読み替える。止揚は日常語で「取り消し」を意味し、同時に「保管する」「高めて保つ」も意味する — 一つの語が否定と保存を同時に指す。この一語二義こそが、破壊的変更と非破壊的変更を分ける設計規範そのものになる。本節では概念の三段階（即自→対自→即対自）と否定の否定を、分類改版のサイクルとして読み、止揚の三重意味を工場の語彙統合の失敗例に当てはめ、弁証法的進歩は「マージ」ではなく「履歴付き上書き」であるという設計判断を立てる。最後に、その判断を機械的に検証できる差分チェックとして実装する。哲学を飾りにしないための約束事は一つではない。哲学を検算器にすることである。

### 概念は三段階で動く — 即自・対自・即対自

ヘーゲルの『精神現象学』や『小論理学』を読む会に、エンジニアが参加して最もつまずくのは、三段階が「上手な講話の構成」だと思ってしまう点である。正題・反題・合題（these–antithesis–synthesis）という三分法は実際にはヘーゲルの用語ではなく、後世の教科書が扁平化した図である。本節が使うのはそういう図ではない。使うのは概念が内部の矛盾から自己運動する、という構造の方だ。

**即自（an-sich / in-itself）** は、概念がまだ自分自身を区別していない段階である。「未分化だが働いている」という状態を指す。現場の「治具」という語を思い出すといい。作業者はこの語で区別し、区別されていると気づかずに使っている。分類があるのに、分類の境界が可視になっていない。2.1節で述べた正規化以前の語彙の自然状態が即自である。

**対自（für-sich / for-itself）** は、その概念が自分自身と区別される段階である。マスター語彙の設計者が「治具」「冶具」「クランプ」を別概念として定義し、使い分けを求めた瞬間、現場の語は「疑えるもの」になる。区別が意識された瞬間に区別は摩擦を生む — 現場では同じものを指していた語に別定義が与えられ、レポートの数値が動き、担当間で作戦会議が起きる。この摩擦は事故ではない。ヘーゲルの読み方では、矛盾は概念を動かすエンジンであり、停止命令ではない。ある分類が破綻・重複・境界争いを生むのは、その分類が届いていない残余が存在する証拠である。2.1節の残余は、対自の段階で初めて可視になる。

**即対自（an-und-für-sich / in-and-for-itself）** は、区別された概念がより広い規定のうちに自らを再び統一する段階である。注意すべきは、これが最初の即自への往復復元ではないことだ。「現場の言葉に戻ろう」という-retreat（後退）は即対自ではない。即対自は、対自で得た区別 — 失敗からlearned境界・検査実務・残余 — をすべて内部に抱えたうえで、もう一度作動する統一である。『精神現象学』の有名な表現を借りれば、失われた形相を保持しながら進む道（der Weg）である。保存を条件とする前進。ここに本節の全設計が入っている。

工学的に翻訳すると三段階はこうなる。①即自 = 未文書化だが機能している現場語彙。②対自 = 明示化・正規化による分節と、そこに必ず現れる矛盾（境界争い・数値の漂移・現場の不信）。③即対自 = 矛盾を抱えたままの新版、旧版の区別を消さずに抱えた改版。そして設計者が引き受けねばならないのは、②で矛盾が起きた瞬間に③へ進む**演算の設計**である。次節からその演算を分解する。

### 止揚（Aufheben）の三重意味 — 捨てる・保存する・高める

Aufheben はドイツ語で相反する複数の意味を同時に持つ（Aufhebung の三義性はヘーゲル研究の定番である）。日常語では「（law や契約を）取り消す・撤廃する」。同時に「（物を）保管する・とっておく」。さらに哲学語では「高めて保ちながら取り消す」。否定・保存・高度化 — 三つの動作が一つの動詞に溶けている。この構造は三段階構造そのものでもあり、以下のように分解できる。

| 止揚の局面 | 概念運動での意味 | 差分設計での実装要求 |
|---|---|---|
| 捨てる（negation） | 現行規定の作動停止 | `active=false`・`valid_to` の設定。現行クエリから見えなくする |
| 保存する（preservation） | 停止した規定の実在性の保持 | 削除禁止。履歴から参照可能。過去データは新版で再解釈しない |
| 高める（elevation） | より広い規定への接続 | 新旧を結ぶ明示関係（`retires` 等）＋新版が区別を引き継いでいること |

削除（DROP）は三局面のうち「捨てる」だけを実装した演算である。「保存する」も「高める」も起きない。止揚とは異なる演算が密かに実行されている — 本書の用語では**抹消（erase）**である。設計の退化はこの抹消の混入として必ず起きる。

ここで工場語彙の失敗例を一つ置く。2.1節の語彙正規化プロジェクトの話である。ある自動車部品工場がマスター語彙を作り、「治具」「冶具」「クランプ」を `HoldingFixture` 一個にマージした。SQL の `ALTER TABLE ... ADD COLUMN category` で、現場語彙の列を新しい列に上書きし、旧列を `DROP COLUMN` した。三か月後、保守計画システムが「クランプの点検周期超過」を返さなくなった。現場では「クランプ」は工具側の保持具を、「冶具」は刃具側を指しており、点検周期が異なっていたのだ。マージによって区別は失われ、区別にもとづいて書かれていた点検ルールは `WHERE category='HoldingFixture'` に吸収されて消えた。この変更には「捨てる」はあった。「保存する」がなかった — どの行がもともと「クランプ」だったかを指すものがシステムの内外のどこにも残っていなかった。止揚の三重意味が三つの列として残っていれば、この事故は防げた。

### 否定の否定 — 往復復元ではなく第二否定的前進

三段階を並べると「肯定→否定→否定の否定」と見える。だが否定の否定が単なる原状回復なら、ヘーゲルの弁証法は退屈な往復運動になる。『大論理学』の客観的 Essence の巻で論じられた通り、第二の否定は第一の否定の産物を内容として含む。すなわち「否定的なものの保持（Erhaltung des Negativen）」である。否定されたものは無にはならず、保持されたうえで次の規定の材料になる。この前進を**否定的なものの保持**（Preservation of the negative）と呼ぶ。

工場の語彙改版で読むとこうなる。第一次改版（対自）: 「治具」一個の語を否定して「治具/冶具/クランプ」に三分割する。第二次改版（否定の否定）: 現場の混乱を受け、実務の要求（トルク追跡のため全部をまとめて検たい）から、三分割を再び否定する。ここで原状回復なら「全部まとめて『治具』」に戻る — それは改版ではなく後退であり、実際同じ失敗を呼ぶ。第二否定的前進では、三分割で得た区別（境界の知識、現場が示した使い分け、残余として現れた検査実務）を**保持したまま**、より広い規定を作る。すなわち「上位概念 `HoldingDevice` を置き、`HoldingDevice` には下位の三分割を保存したままとる」設計である。語は統合されるが、区別は歴史として内部に残る。絞り込みクエリは上位で動き、点検周期は下位の区別から撃てる。

この読みには正直なアポリア（apory、難点）が付きまとう。三段進の進行を機械に要求することはできない。第三段階の内容は与えられた前提から導出可能ではなく、状況の解釈と実践の熟成が要る。したがって本書の実装には必ず**停止条件**が入る。段階3は自動生成されず、人間が承認するまで履歴付き上書きは保留される。止揚の構造を実装できる。止揚の内容の生成は実装できない。この区別（構造の形式化と内容の非形式化）は第5章の計算と判断の分断（→第5.1節）と同一の線上にある。

### 弁証法的進歩は「マージ」ではなく「履歴付き上書き」

ここで本節の設計判断を宣言する。分類の改版を止揚として実行するなら、その演算は Git のマージではなく、コミット（commit）である。なぜか。マージの語義は「二つの分岐を一つの節点に融合させる」ことで、融合した節点からは各親の姿が不可視になる。Git で merge commit は親を記録するが、ファイルの中身は混ざった現在値だけを残す。統合の意味が現在値に沈殿する。対してコミットは自己と差分を保存する — 上書き（overwrite）するが、抹消（erasure）しない。止揚の三重意味をそのまま写した構造である。

分類変更の四戦略を比較しておこう。

| 戦略 | 捨てる | 保存する | 高める | 現場での現れ |
|---|---|---|---|---|
| 破壊的上書き | ○ | × | × | `DROP COLUMN`、enum 値の書き換え、ラベルの貼替 |
| マージ（融合） | △ | △（節点に埋没） | × | 上位語への一本化。新旧どちらの意味で動いたか回答不能 |
| 履歴付き上書き | ○ | ○ | ○ | 新版を開き旧版を閉じ、`retires` で結ぶ |
| 分岐並存 | × | ○ | × | 語を併存させ続ける。境界争いが永久に未決着のまま残る |

四戦略のうち止揚の条件を満たすのは三行目だけである。分岐並存は「捨てる」を拒否した対自の凍結で、境界を永久に開いたまま運用コストに転嫁する設計（1.2節の境界の面化とは別物だ。面は計測されるが、未決着は計測されない）。破壊的上書きは抹消、マージは保存の欠如である。

マージが組織の対話の省略として現れることも記録しておこう。語彙統合会議で「どちらも正しいのだから一つにまとめよう」と決まった瞬間、矛盾の生産する運動が停止する。2.1節の正規化の暴力は、マージの形をとって最も無自覚に働く。ヘーゲル的に言えば、矛盾を調停で消した組織は、概念の運動を自分の手で止めたことになる。レポートの数値が説明できなくなる時、説明すべき運動がすでに無い。

### 差分設計の規範 — Aufheben-check を通らない変更は止揚を騙っている

では工学的に何をするのか。以上から導かれる仕様は短い。**改版は差分として記録される。差分には三局面が機械的に確認可能であること。** 確認できない改版は止揚を騙っているものとして差し戻す。この規範を本書では Aufheben-check と呼ぶ。チェックは四項である。

1. **否定の証明**: 変更後の状態から、旧規定が `active` でないことが確認できるか（作動停止の記録）。
2. **保存の証明**: 旧規定の定義と、旧規定でラベル付けされたデータが参照可能か（削除の不存在）。
3. **高度化の証明**: 新旧を結ぶ明示の関係（`retires` / `replaces`）が存在し、新版の定義が旧版の区別を引き継いでいるか。
4. **残余の記録**: どの区別・どの数拠が新版の意味に吸収されたかの記述。2.1節の残余を捨てるか保存するかの分岐で「保存」側を選ぶ仕組み。

この四項を検査する実行可能な差分チェックを以下に置く。2.5節のコミットモデルの先行実装であり、Turtle の `retires` 語彙は2.4節で正式定義する（依存環境は付録A）。

```python
"""ch02_s2_aufheben.py — 差分設計の規範 Aufheben-check の実装。
哲学的意図: 止揚（Aufheben）は三局面（捨てる・保存する・高める）が同時に
成立する演算である。うち一つでも欠けば、それは止揚ではなく抹消または
マージである。演算の名前を騙らせないために、規範を check 関数にする。
（コメントは哲学の注釈 — 本書の約束事）"""
from dataclasses import dataclass, field

@dataclass
class Term:
    key: str
    gloss: str
    active: bool = True
    valid_to: str | None = None

@dataclass
class Revision:
    """概念の一回の改版 = 履歴付き上書きのコミット。"""
    intent: str                      # 変更の意図（何の苦情・要求が動いたか）
    negates: list[str]               # 作動を停止する旧 term keys（否定）
    introduces: dict[str, str]       # 新 term key→gloss（新規定の開始）
    carries: list[str]               # 新版が引き継いだ区別の記述（保持の証明）
    absorbed_residuals: list[str]    # 新版に吸収された残余の記録（残余は捨てるな）
    data_ref: dict[str, str] = field(default_factory=dict)
    # 旧 term key → 旧データ集合の参照（保存の証明。DELETE しない宣言）
    retires: dict[str, str] = field(default_factory=dict)
    # 新 term key →  retire する旧 term key（高めるの接続）

@dataclass
class Vocab:
    terms: dict[str, Term] = field(default_factory=dict)

class NotAufhebungError(ValueError):
    pass

def aufheben(v: Vocab, rev: Revision) -> Vocab:
    # --- 局面1 捨てる: 否定は明示的でなければならない。暗黙の消滅を認めない ---
    for k in rev.negates:
        if k not in v.terms or not v.terms[k].active:
            raise NotAufhebungError(f"否定対象 {k} が現行に存在しない（抹消の混入）")
    # --- 局面2 保存する: 停止させるだけで消さない。旧データ参照が必須 ---
    for k in rev.negates:
        if k not in rev.data_ref:
            raise NotAufhebungError(f"{k} の旧データ参照がない = 保存のない改版")
        v.terms[k].active = False
        v.terms[k].valid_to = rev.intent  # 停止の理由は意図とともに記録する
    # --- 局面3 高める: 新旧を結ぶ関係なしは単なる置換、区別の引継ぎ記述なしはマージ ---
    for new, old in rev.retires.items():
        if old not in rev.negates:
            raise NotAufhebungError(f"{new} が否定していない {old} を retire（接続の捏造）")
    if not rev.carries:
        raise NotAufhebungError("carries が空 = 否定的なものの保持がない（対自の遺棄）")
    if not rev.absorbed_residuals:
        raise NotAufhebungError("absorbed_residuals が空 = 残余の記録なし（2.1節の暴力の隠蔽）")
    for k, gloss in rev.introduces.items():
        v.terms[k] = Term(key=k, gloss=gloss)
    return v

def query_history(v: Vocab, key: str, as_of: str) -> str:
    # 哲学的意図: 止揚されたものは「実在しなくなった」のではない。
    # 過去への問いは歴史から答える（保存の工学的意味）。
    t = v.terms.get(key)
    return f"{key}: {t.gloss} (active={t.active})" if t else "unknown term"

if __name__ == "__main__":
    v = Vocab(terms={
        "治具": Term("治具", "型・刃具・ワークを保持するもの（現場語彙、未分化）"),
    })
    # 第一次改版: 対自。一つを否定し三つに区別する。
    v = aufheben(v, Revision(
        intent="正規化プロジェクト: 保守周期の違いを区別したい",
        negates=["治具"], introduces={"クランプ": "工具側の保持具",
                                      "冶具": "刃具側の保持具"},
        carries(["現場の『治具』が実は二系統の周期を持っていた事実"]),
        absorbed_residuals=["現場で『型』と呼ばれていた語"],
        data_ref={"治具": "snapshot://fixture-v0.parquet"},
        retires={"クランプ": "治具", "冶具": "治具"},
    ))
    print("改版1（対自）:", {k: t.active for k, t in v.terms.items()})
    print("歴史への問い:", query_history(v, "治具", "改版1後"))
    # 第二次改版: 否定の否定。三分割を再び否定するが、区別を保持して上位へ上げる。
    v = aufheben(v, Revision(
        intent="トルク追跡の要求。まとめて検したい。ただし点検周期は別々に保つ",
        negates=["クランプ", "冶具"],
        introduces={"HoldingDevice": "保持具の上位（下位の区別を internal に保持）"},
        carries=["周期が異なるという区別を sub_type に引き継ぐ"],
        absorbed_residuals=["現場の『ホルダー』"],
        data_ref={"クランプ": "snapshot://clamp-v1", "冶具": "snapshot://jig-v1"},
        retires={"HoldingDevice": "クランプ", "HoldingDevice2": "冶具"},
    ))
    print("改版2（即対自）:", {k: t.active for k, t in v.terms.items()})
```

上のコードには意図的な破綻がある: `Revision` の第二改版で `HoldingDevice2` が `negates` 之外の項を retire しようとしていないか — 読者は `aufheben()` に一度 `NotAufhebungError` を出させてみればいい。規範は例外として機能するときに初めて規範になる。

規範の運用では、チェック通過だけでは不十分で**沈黙の猶予期間**が必要になる。破壊的な改版（上位概念の導入・語の統合）は、Approved になっても即座には active にならない — 現場が反論する窓を開いたまま作動を遅延させる。猶予期間の設計、すなわち「承認された変更がすぐには存在しなくなる」時刻設計は2.6節の版管理の倫理に譲る。ただし原則はこの節で立つ。変更の発効は対話の終了を待ってよい。

最後に、この規範をどの層で執行するかの方針だけ述べておく。Aufheben-check を文書運用（チェックリスト文化）に置くと、それは必ず形骸化する。本節の実装のように**書き込み経路の関数**に置けば、規範を通らない改版は存在しないのと同じになる。執行の一般形（ポリシーゲート）は6.4節で OPA と Rego として実装する。そこに移管するための正規形として、改版コミットは JSON で書き出せる形に保つ。

```yaml
# revision.json の例 — Aufheben-check の通過証明を改版の付属物として保存する。
# 哲学的意図: 「止揚した」は自己申告ではない。三局面の検査結果が改版の本体の一部。
revision:
  intent: "トルク追跡の要求。まとめて検したい"
  negates: ["クランプ", "冶具"]
  introduces: ["HoldingDevice"]
  carries: ["周期区別を sub_type へ引き継ぐ"]
  absorbed_residuals: ["現場の『ホルダー』"]
  data_ref:
    "クランプ": "snapshot://clamp-v1"
    "冶具": "snapshot://jig-v1"
  retires:
    "HoldingDevice": ["クランプ", "冶具"]
  aufheben_check:
    negation_proved: true
    preservation_proved: true
    elevation_proved: true
    residual_logged: true
  grace_window_days: 14   # 沈黙の猶予（→2.6節）
```

### アポリア — 保存されるのは意味か、記述か

本節の設計規範には解けない難点が Attached している。Aufheben-check は「保存する」を検査できるが、保存されるのは記述（definition・データ参照・引継ぎ文）であって、意味そのものではない。2.1節で見たように、正規化の過程で摩耗した意味 — 語を語っていた身体と状況 — は履歴のどこにも載らない。履歴付き上書きは意味を保存する装置ではなく、意味を復元する**機会**を保存する装置にとどまる。機会が誰にも読み返されなければ、保存は機能したことになるのか。これは終章の知の継承というアポリア（→終章）の最初の断面である。設計はアポリアを消せない。アポリアを運用条件として書き込むことだけができる。上記の `carries` と `absorbed_residuals` は、その書き込みの試みである。次節では、この「改版をコミットとして保存する」考えを、スティグレールの外部記憶論（→第2.3節）に接続して基礎づける。

### 実行練習

1. `python ch02_s2_aufheben.py` を実行し、改版1（対自）と改版2（即対自）の後の `active` 表示を読み比べよ。次に改版2の `retires` を `{"HoldingDevice": ["クランプ", "冶具"]}` と統一して正常通過させ、そのうえで `carries` を空列表に書き換えて `NotAufhebungError` が発火するを観察せよ。「高める」なしに「捨てる」と「保存する」だけでは、どの戦略（四戦略表のどれ）になるかを書き残すこと。
2. `query_history()` を拡張し、旧 term（例「治具」）にラベル付けされたレコードの集合が改版後の絞り込みクエリで**見えてしまう**か見えないかを確かめる関数を追加せよ。実装は任意（list でも dict でもよい）。2.1節の工場失敗例（保守計画が「クランプ」を返さなくなった事故）を再現する側に立ち、`active=false` の扱いの設計がなぜ「見えないが参照できる」でなければならないかを10行以内で説明せよ。
3. 自分が所属する組織で最近起きた分類変更（API の enum 削除、職能名の変更、タグの統合など）を1件選び、それを `Revision` に書き起こして Aufheben-check を通せ。通らないならどの局面が欠けているかを特定し、その変更が「破壊的上書き」「マージ」「分岐並存」のどれだったかを判定して、失われた `carries` に相当する区別が何だったかを復元試着こうとすること。復元できなければ、その欠落こそがこの節のアポリアの現場名簿である。
