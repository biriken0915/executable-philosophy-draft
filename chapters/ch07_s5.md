## 7.5 実線パイプライン — 状況検知 → ACL検証 → Action発火

部品は揃った（検知→1.2・7.2、候補→7.3、編成→7.4、防腐→6.4〜6.5、監査→5.6・6.4）。この節は配線である——テレメトリが POST されてから現場 API が撃たれ、効果が記録されるまでを、一本の実線で通す。中心に置く概念は**時間予算（time budget）**——OODA の内側時計を SLA として実装する設計（→7.2）——と、**完全な監査トレース**（「なぜその Action が撃たれたか」の機械的回答）である。実装は FastAPI（入口）・LangGraph（編成、→7.4 の `app`）・Neo4j（状況と履歴）の三層で、本書のデモ系（保全現場）の完動版を 7.6 に残し、本節は骨格と設計判断を全部出す。

### 入口 — FastAPI エンドポイントと入口簿記

```python
# ingest_api.py — テレメトリ受信(入口の ACL、→6.1 の入り口防腐の API 版)
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

api = FastAPI()

@api.post("/telemetry")
async def ingest(req: Request):
    body = await req.json()
    # 入口 ACL: 外部テレメトリ語彙 → 正規語彙(TermMapping、→6.1)。
    # 解決不能な telemetry 種別は TranslationFailure として 406 で返すが、
    # payload は Quarantine レコードに保存する(残余保存、→2.1・6.1)。
    norm, failure = acl_in.translate_telemetry(body)
    if failure:
        save_quarantine_input(body, failure)          # 捨てない: 条約改訂の供給源
        return JSONResponse(status_code=406, content=failure.model_dump())
    # 入口簿記: actor・受信時刻・source 版数を Commit でなく IngressEvent として載せる(→2.5)
    log_ingress(norm, actor=req.headers.get("x-source"), at=now())
    # 相関 ID でグラフ実行(thread)を開始・再開: 状況の相関=スレッド(→7.4 thread_id)
    thread_id = correlate_thread(norm)                 # 同一 asset/shift の連鎖に相関 ID
    app.invoke(norm_to_flow(norm),
               config={"configurable": {"thread_id": thread_id}})
    return {"thread_id": thread_id}
```

`correlate_thread` を入口設計の要として置く。**状況は独立イベントの列ではなく、相関する連鎖である**（1.2 の「状況」概念の実線版）。同一機械・同一シフト・同一障礙（→3.4）のイベントが同一 thread（OODA の一つのサイクル列）にまとまり、checkpointer がその列の状態を進化させる（→7.4）。相関規則（何が同一スレッドか）は決定論で、E4 宣言・落日つき（→6.6）でなければならない——相関規則は「何が一つの状況か」の定義であり、**状況の分節**（→1.2）の運用時版だからである。相関規則の変更は L2 変更（→2.6）である理由もここで明記される。

### 中段 — 状況照会と候補（→7.3 の照会の実線内での位置）

`norm_to_flow` 内の状況照会を、実線の時間制約の中で確定する。Neo4j への照会 three 本（`enabled_actions`、当該 goal の mission packet の `decision_budget_sec`、障礙 `NEGATES` 一覧）の budget を合計 300ms に固定し、超過時はクエリを kill して候補ゼロ宣言（→5.4）へ落ちる。時間予算配分（Observe 300ms / Propose 8s / Verify 1.5s / Decide human-window / Act 2s）は、goal の `decision_budget_sec` から逆算される（→7.2 の「要求仕様の一部」の実装——予算の階層：全体予算 > 段予算 > クエリ予算。超過の每一段が `clock` 計測（→7.4 の Flow.clock）に載り、scorecard（→4.6）に段別 p99 が上がる）。

予算超過の処理は「遅いなら止める」ではなく、**遅い段の状態を宣言として残す**（UNKNOWN 宣言、→3.5 の教訓）。kill されたクエリの partially-bound results は保存し、再試行の起点にする（残余保存の性能設計版）。

### 出口 — Action発火と effect_verification

```python
# act_client.py — 現場 API 発火(実行段の最小実装・宣言と実体の版数突合つき)
import httpx

def fire_api(decision: dict) -> dict:
    a = load_action(decision["approved_action"])        # Action ノード読取(→7.3)
    spec_ver = a["api_ref"].split("@v")[-1]             // 宣言が指す API 仕様版
    live_ver = httpx.get(a["api_ref"].rsplit("/", 2)[0] + "/spec-version").json()["version"]
    if spec_ver != live_ver:
        return {"status": "stale-spec", "declared": spec_ver, "live": live_ver}
        # ↑ 宣言と実体のずれ(→1.5・7.3)を『撃つ前に』検出して止める。
        #   ずれの検出は L1 事件として effect-missing より深刻(宣言が既に嘘)。
    resp = httpx.post(a["api_ref"], json=decision.get("params", {}), timeout=2.0)
    record_exec(a, decision, resp, at=now())            # ActionExec 登記(→7.3 突合の起点)
    return {"status": resp.status_code, "exec_id": last_exec_id()}
```

`stale-spec` の検査が発火の**直前**に走ることの重要性。CI で宣言と実体の突合を常時回すが（→7.3 の CI 接続）、CI の週次周期に対し API 変更は毎日起こりうる——発火直前の突合は、最後の防波堤である（多重防御、→5.6・6.4 の原則）。`stale-spec` は実行拒否だが、deny の説明（missing フィールド、→6.4 の decision log）として「Action の effect_spec 再検証タスク」を自動生成し、審議槽に載せる（遮断は討議の燃料、→6.2）。

### 監査トレース — 「なぜこのActionが撃たれたか」の完全な回答

完全な説明の構造を定義する。説明の要求形式（→5.5 の「説明＝再生」、→4.5 の counterfactual、→5.3 の basis_reckoning）が、実線で初めて埋まる。

```cypher
// why_action: ActionExec からの完全説明トレース(一発照会)
MATCH (x:ActionExec {exec_id: $id})<-[:FIRED]-(a:Action),
      (x)-[:ANCHORED_IN]->(je:JudgmentEvent)-[:JUDGED_ON]->(eb:EvidenceBundle),
      (x)-[:INSIDE]->(:Transition {exec_ref: $id}),
      (a)-[:INTENT]->(g:Goal)
OPTIONAL MATCH (eb)-[:DERIVED_FROM]->(c:Candidate)   // 候補の provenance(env digest)
OPTIONAL MATCH (je)-[:RESPONDS_TO]->(ra:RuleAdoption) // 規則選定の歴史(→7.1)
RETURN a.action_id, g.text AS served_goal,
       x.guard_snapshot,                              // 発火時点のガード実測値(→5.6)
       c.provenance AS candidate_env,                 // どの reckoning の産物か(→5.4)
       eb.frame_options, eb.llm_role,                 // 材料形成の全容(→5.3)
       je.decider, je.revalidation_path,              // 誰の判断か・再検証の実体(→5.1)
       ra.rule_ref, ra.decider AS rule_by, ra.at AS rule_at   // 規則は誰がいつ選定したか(→7.1)
```

この一発照会が返す七つの要素が、説明の完全性の定義である：仕える目的（g）、発火時点の事実（guard_snapshot）、候補の由来（candidate_env）、材料形成の全容（frame_options）、判断者と再検証経路（decider/revalidation）、規則の選定史（rule_by/rule_at）。要素が一つ欠けると、説明は物語になる（→5.3 の尤度の物語化）。よって**why_action が NULL を返すフィールドの数**を scorecard の指標に置く（説明の完全率、→8.3 の説明設計の機械的床がここで定義される——8章の「理由を問い直す UI」は、この照会の表示装置にすぎない）。

### 時間予算の監査 — 内側時計の黒字・赤字

パイプライン全体の実測周期（ingest→act、interrupt を含む wall-clock）と、mission packet の `decision_budget_sec` の差分を thread ごとに記録する。**予算超過の thread は、その goal の委任が時間的に破綻している事件**である（→7.2 clock_fit の実測）。月次で budget_deficit の上位 goal を listing し、委任深度の引き上げ／SL 引き上げ／段予算の再配分の三択を E3 審議に自動で載せる（→6.6 の落日・再審議の循環が時間予算にも回る）。時間予算は E4 の一形態である——期限が過ぎたら自動で警告に降格する（落日条項の時間設計版）。

### スレッド相関の失敗形 — 状況の分節を誤ると何が壊れるか

`correlate_thread`（→前掲）の設計を、失敗形の目録で締める。相関規則は「何が一つの状況か」の分節（→1.2 の境界問題の実線版）であり、分節の誤りはパイプラインの全段に増幅して伝播する。

**失敗一：分割過剰**（一つの障害が複数スレッドに割れる）。各スレッドは部分状況しか持たず、候補生成が部分状況に対して正しい act を出す（部分対策の重複・重複 act）。検出：重複 act の asset・時刻窓突合（→練習3 の query がこれ）、および「同一事象への複数 thread の co-active 状態数」の scorecard 化。処方：スレッド相関に asset 横断の link（同一 commit・同一班次）を含める——ただし link の定義は E4 宣言で期限つき（相関規則自体が老朽化する、→5.2 の手放しの設計）。
**失敗二：分割不足**（無関係な二事象が同一スレッドに融解する）。状況 digest が混濁し、検証段の前提照会が雑に通り、判断の皿が二つの世界の候補を混ぜる。最頻の危害は「混濁したスレッドの act が、片方の世界では正しく他方では副作用」（→7.3 の effect_verification が検る側面——effect-missing ではなく effect-extra として現れる）。検出：同一スレッド内の `NEGATES` 対立ペア（一方の act の effect が他方の goal を壊す、→3.4 の障礙のグラフ内発火）。
**失敗三：相関の取りこぼし**（同じ障害の実例が別世界として永遠に並列）。障礙の更新（→3.4 の N1/N2）が起きず、stale_obstacles を増やす（→8.1 第四段の実線経路）。

```cypher
// thread-integrity — 相関規則の健全性(週次)
// 過剰分割の代理指標: 同一 asset・短窓で co-active thread 数
MATCH (t1:Thread), (t2:Thread)
WHERE t1.asset = t2.asset AND t1 <> t2 AND t1.status='active' AND t2.status='active'
  AND duration.between(t1.opened, t2.opened).minutes < 60
WITH t1.asset, count(DISTINCT coalesce(t1.tid,t2.tid)) AS co_active
RETURN t1.asset, co_active WHERE co_active > 2 ORDER BY co_active DESC;
```

相関規則の変更運用を一度明記しておく——相関規則の変更は L2 級（→2.6）で、**変更直後の 2 四半期は分割・統合の両指標を監視する**（規則変更そのものが障礙の発生源になる、→3.4 の制度変更障礙）。相関規則を「実装の詳細」として無級で扱う系は、状況の分節を無級で書き換えている——2.6 の中心定理（意味の変更は統治イベント）が、実線パイプラインの一段で再発しないよう、ここで級を確定する。

### SLA の実装 — decision_budget_sec の計算と警告帯

7.5 の時間予算（decision_budget_sec、→7.2 の mission packet 設計）を、稼働する SLA として実装する。予算は「待つな」ではなく**待つ深さの宣言**である（→7.2 の命令：判断の周期が世界の周期に遅れるな）。実装は三段。

**其一、消費の計上**：パイプラインの各段（observe→verify→decide）は、経過秒を Thread に `budget_spent` として更新する（→6.4 監査簿記の列 `budget` に同一の数が載る——SLA の数値は簿記と同一源でなければならない、二重定義禁止、→5.5 宣言簿記の運用版）。**其二、警告帯**：消費が予算の 70% を超えた段で、decision は面板に `budget_pressure` の印を載せる（→8.5 の面板——猶予を短縮するのではなく、猶予の重さを見せる：SLA が猶予を溃さない、→8.5 の衝突解決规則の実線版）。**其三、預算枯渇**：budget_spent >= budget の時、decide は「选択」でなく **Quarantine 起票**を选ぶ（時間の中で判断できない場合、世界の方を調べる——障礙 N5 周期超过、→3.4。預算内で強行に选んだ act の簿記には `hurried: true` が走り、effect_verification 優先度を上げる——急いだものは強く検收する）。

```python
# sla.py — 予算計上と警告帯(pipeline 各ノードの共通脚)
def budget_check(thread, stage_sec):
    spent = thread.budget_spent + stage_sec
    if spent >= thread.decision_budget_sec:
        return Route.QUARANTINE, spent          # 予算枯渇→障礙 N5 起票
    flag = spent >= 0.7 * thread.decision_budget_sec
    return Route.NEXT, spent, ("budget_pressure" if flag else None)
```

`Route.QUARANTINE` の意味を哲学側から一環——判断できない状態を「判断しなかった」と書かず「預算の障礙が起きた」と書く（3.5 の三段構えの SLA 実装。UNKNOWN を UNKNOWN として登記する機構が、ここで動作として現れる）。7.5 の全段（correlate→acl→gate→act→why）が共通脚 budget_check を通すことで、SLA は规定ではなく計器になる——四半期ごとの budget_pressure 発生率と Quarantine 起票率の組み合わせが、「この系統の判断は世界の速さに付いているか」の唯一の誠実な報告である。

### 実行練習

1. `ingest_api.py` を自分のテレメトリ（Webhook・Kafka・バッチ取込）に移植し、入口 ACL の TranslationFailure を 406 で返す配線を実験せよ。unknown 種別1件を Quarantine に載せ、その Quarantine が TermMapping 改訂（条約 v(N+1)）に化けるまでを 6.1 の語彙で1段落報告せよ。
2. `why_action` を自分の既存の自動化1本に対して実行できる形に直し（既存ログから七要素のどれが埋まり、どれが NULL か）、**説明の完全率**を計算せよ。NULL の各要素について、どの登記（JudgmentEvent/EvidenceBundle/RuleAdoption/Transition）を作れば埋まるかを対応表で書き、埋める優先順位を1つ決めよ。
3. thread 相関規則（`correlate_thread`）を自分の業務で1つ設計し（何が同一状況か：同一 asset？同一 incident？同一 shift？）、その規則の E4 宣言文（→4.1 の形式：宣言者・期限・再検証条件）を書け。さらに相関規則の誤りが生む最も危険な事故型（例：同一障害の二重スレッド化による二重 act）を1つ挙げ、検出クエリ（重複 act の asset・時刻窓突合）を1本書け。
