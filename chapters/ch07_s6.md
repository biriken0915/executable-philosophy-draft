## 7.6 統合実装 — FastAPI + LangGraph + Neo4j の完動コード

この章の約束を果たす節である。第1〜6章の成果物——グラフスキーマ（→1.3・2.4）、ゴール木（→3.2）、契約（→4.4）、ACL（→6.1・6.3）、Rego/SHACL（→6.4・6.5）、ステートマシン（→5.5〜5.6）、LLM ラッパー（→5.4）——を**一つの動くデモ**に統合する。デモの名を「Tsurugi（剣）」とする（保全現場の架空の機械ライン。実在しないが、すべての部品が実在する構成で動く）。本節の目的はコードの量ではなく、統合の**検証可能性**である。統合テストで障害シナリオを注入し、システムが**安全側へ倒れる**ことを機械的に示す（→3.5 の安全条件、→6.6 の均衡が、テストという形で初めて実行証明される）。そして運用設計として、**段階的権限委譲**（read-only → propose → act）を置く——本番投入の弁は三段で開け、各段の昇格条件は数値で宣言される。

### リポジトリの形 — 哲学の部品のディレクトリ対応

まず置き場所の地図。統合の最初の失敗は、部品が散装して「再利用できない」ことである。本書の全部品は次のツリーに対応し、このツリー自体が設計文書である。

├── history/             # 2章: 履歴代数の bridge(git→RDF)、commit スキーマ

├── contracts/           # 4章: CQ台帳、DbC(Pydantic)、shapes/(6.5 と同居)

`graph/` に Neo4j の**スキーマ制約**を宣言しておく（uniqueness・type constraint——4.6 の test_cq.py が通る前提条件）。統合テストはこれを testcontainer の Neo4j 5.x に適用して始まり、`book` の全書の Cypher が同じコンテナで走る。

### 統合 — app の起動と wiring

```python
# tsurugi/app_main.py — 全部品起動(本書の体系の『起動可能な目録』)
from fastapi import FastAPI
from tsurugi.flow.ingest_api import api           # 7.5 入口
from tsurugi.flow.orchestration import app        # 7.4 編成(checkpointer = Postgres)
from tsurugi.policy.gate_client import opa_client # 6.4 OPA(サイドカー or 埋め込み)
from tsurugi.graph.driver import neo4j_driver     # 1.3 グラフ

def wire() -> FastAPI:
    # 起動順の設計: グラフ接続 → ポリシー同期(policy/ を OPA bundle として push)
    # → shapes 登録(→6.5 の pyshacl グラフ) → チェックポイント → 入口 API。
    # 逆向きに始めると、検証のないまま入口が受信用に開く時間窓が生まれる
    # (『検証より先に受ける』は 5.3 の司令塔化の運用版。起動順序は防腐である)。
    neo4j_driver.verify_constraints()      # スキーマ制約の存在確認(→4.6)
    opa_client.sync_policy("policy/")      # ポリシー版数を起動時に固定(→6.4 decision log)
    register_shapes("contracts/shapes/")
    app.checkpointer.setup()
    api.include_router()
    return api
```

コメント済みの起動順序の設計を、統合設計の第一条として強調する。**検証部品より先に受信部品を開いてはならない**——デプロイの事故の大多数は、この順序の反転（ゲートless の入口が先行する窓）で起きる。Kubernetes の readinessProbe を opa/shapes 登録の完了に紐づける実装をここに書く価値があるが、本書の語で言えば、**readiness は「防腐が着弾した」の宣言**である。

### 統合テスト — 障害注入と安全側検証

中心のテスト群を書く。テスト哲学は 4.6 の ontology regression と同一だが、対象が系全体に広がる。シナリオは 3.4 の障礙の語彙で書く（障礙 = 目標の否定、テスト = 障礙の実例注入）。

```python
# tests/test_safety_fall.py — 障礙注入テスト(→3.4 の障礙をテスト名に使う)
import pytest

@pytest.mark.parametrize("obstacle,expect", [
    # 障礙(O1): LLM が不正候補(unknown term)を生成
    ("llm-invent-term",      {"final": "quarantined", "world_changed": False}),
    # 障礙(O2): ポリシーが遮断すべき書込を候補が提案(例: llm→master 直書)
    ("llm-writes-master",    {"final": "blocked-rego", "world_changed": False}),
    # 障礙(O3): 人間応答なし(time-boxed interrupt 超過、→7.4)
    ("no-human-decision",    {"final": "safe-default", "world_changed": False}),
    # 障礙(O4): 宣言と実体のずれ(stale-spec、→7.5)
    ("api-spec-drift",       {"final": "stale-spec", "world_changed": False}),
    # 障礙(O5): ゲート後・act 前の状態変更(TOCTOU)
    ("state-changed-after-verify", {"final": "re-verify", "world_changed": False}),
    # 障礙(O6): KB の前提 Expectation が失効(ASSUMED_FOR 辺の失効)
    ("assumption-expired",   {"final": "blocked-mission", "world_changed": False}),
])
def test_safety_side_on_obstacles(session, obstacle, expect):
    inj = inject(obstacle, session)              # 障礙を世界に注入fixture
    final = invoke_flow(session, inj.telemetry)  # 実線全段を通す(7.4 の app)
    assert final["stage"] == expect["final"], f"{obstacle}: {final}"
    # world_changed=False の検証 = act が撃たれていないことのグラフ証明:
    assert count(session, "MATCH (x:ActionExec {thread:$t}) RETURN x",
                 t=inj.thread_id) == 0
    # 残余保存の検証: 障礙は必ず記録に残る(握りつぶし禁止、→4.1 残余条項)
    assert count(session, f"MATCH (e) WHERE e.event_of=$t AND e.kind<>'IngressEvent'") >= 1, \
           f"{obstacle}: 障礙が歴史に載っていない(=蒸発、→5.3)"
```

`world_changed=False` を**グラフで証明する**設計が安全側テストの核心である。戻り値の文字列ではなく、`ActionExec` ノードの不在を照会する——実行者が捏造できない形で検証する（4.4 の「契約違反は例外でなくデータ」の系譜で、**安全条件は戻り値でなくグラフ不変条件**）。O5（TOCTOU）の `re-verify` は 5.6 のステートマシンが act 直前に現状照会を再実行する設計の実装確認である（verify→act の間に世界が変わったら、verify の verdict は古い——verdict に `situation_digest` を添え、act 直前の digest 突合で再検証を強制する）。

`event_of` の残余検証（第三アサーション）で、テストが**記録の義務**まで検査している点を注ぐ。安全側に倒れるだけでなく、倒れたことが歴史に載らなければ、それは学習しない安全である——6.6 の運動としての防腐が、テストの断り書きとして書き込まれている。

### 運用設計 — 段階的権限委譲（read-only → propose → act）

本番の弁を三段で開ける。各段の**昇格条件は数値で宣言**され（E1 級の実測可能条件、→4.1）、降格条件も数値で宣言される（落日条項の運用版、→6.6）。

**段1 read-only（3か月）**：システムは状況照会・候補提示・レポート生成のみ。act なし。昇格条件：`why_action` 完全率 ≥ 0.98（→7.5 の説明の完全率）、段別 p99 が予算内（→7.2）、Quarantine の週次開封率 ≥ 0.8（→5.6 の見逃し防止——開かれない Quarantine は安全の偽称）。

**段2 propose（6か月）**：高リスク以外（`risk_class ≤ medium`）の act を、人間判断必須のまま自動実行（interrupt の time-boxed 既定を「medium 以下は承認あれば実行」に拡張）。昇格条件：段1 の四指標維持 + **effect_verification 保持率 ≥ 0.95**（→7.3 の宣言と実測の突合）+ dissent の審議解決率 ≥ 0.7（→6.2 の槽が実際に回っている証拠）。

**段3 act 拡大**：high risk の act を、判断必須のまま開く。昇格条件は上記維持 + **RuleAdoption の滞留月齢 ≤ 6**（→7.1 の選定残高——現場が選定を更新し続けていることが high risk 委任の前提）。

```python
# rollout_gate.py — 昇格/降格条件の実測(デモでなく毎週計算される『弁の機械』)
def promotion_readiness(session) -> dict:
    m = scorecard_metrics(session)       # 4.6 + 7.2 + 7.5 の統合 scorecard
    return {
      "read_only": dict(why_complete=m.why_action_complete >= 0.98,
                        clock_p99_ok=m.all_segments_in_budget,
                        quarantine_opened=m.q_open_rate >= 0.8),
      "propose":  dict(effect_held=m.effect_verification >= 0.95,
                       dissent_resolved=m.dissent_resolution >= 0.7),
      "act":      dict(phronesis_fresh=m.rule_adoption_age <= 6),
      # 降格条項(落日): どの指標も 2 週連続で閾値未満なら自動降格・事件登記。
      "demote": {k: m.below_two_weeks(k) for k in ("why_complete","effect_held")},
    }
```

`demote` の自動発火を人間判断に任せない設計の理由を明記する。**昇格は人間が承認し、降格は数値が自動発火する**——非対称であるべき権限の弁である（安全側の非対称、→3.5）。人間の承認だけで降格する系は、降格の政治的コスト（失態の告白）に負けて、権限が開いたまま老朽化する（6.6 の落日条項が統治層で要求したものと同一の構造）。

### デモの最終確認 — 一剑の実演

最後に、デモの通し実演の手順（本書の全体系が一本の線で走る瞬間）を記す。(1) テレメトリ POST（`vib=51, sound=metallic-rattle`）。(2) 入口 ACL が `metallic-rattle` を TranslationFailure にする——条約 v8 に無い語（→6.1 の残余）。payload は Quarantine に載る。(3) 正規化された `vib` だけでスレッド進行：`enabled_actions` が stop-line（high）と inspect（low）を開く（→7.3）。(4) LLM 候補生成（env digest 記録、→5.4）、`metallic-rattle` を KB 語彙で書き換えた候補が SHACL Warning（narrative、→6.5）を伴って通過。(5) OPA が stop-line の Rego 判定を allow（前提成立、級あり、→6.4）。(6) interrupt で人間の皿が開く——候補二つ、根拠（frame_options）、却下理由（Quarantine）、反証条件（→5.3・8.5 の形式）。(7) 人間が stop を選む（JudgmentEvent・EvidenceBundle 接続、→5.1）。(8) act 直前の digest 突合通過（→O5）→ 現場 API 発火、`ActionExec` 登記。(9) 観測が `line-stopped` の `HOLDS` を返し effect_verification 保持（→7.3）。(10) `why_action` が七要素全部を返し（→7.5）、Quarantine の `metallic-rattle` が TermMapping v9 提案（→4.2・6.1）の審議槽に自動で載る——**未知の語が条約改訂に化けるまでが、一本の実線で見える**。

この10ステップは本書の全章の通過儀礼である——1章の状況、2章の履歴と権力、3章の目的と障礙、4章の契約と検証、5章のreckoning/judgment とステートマシン、6章の防腐、7章の処方と時間。統合テストの `test_safety_fall` が同じ線を逆から殴る。**動く哲学書とは、この10ステップが CI で毎日走ることを意味する。**

### 昇格と降格の決定表 — 三段を結ぶ六行

段設計（→前掲）の昇格/降格を、六行の決定表で缔ぶ（段は片道でなく双方向——**自動化は常に巻き戻せる構造でなければ、自動化ではなく既成事実**、7.1 の可謬性の段版）。

| 事象 | 決定 | 根拠 |
|---|---|---|
| 六障害テスト通过＋落日周期つき前提清単 | 段1→段2 | 前提の落日=末端の巡回(5.1) |
| effect_verification 30 件対 27 通过 | 段2 維持 | 通过率為不是落日周期の関数(7.3) |
| effect 通过 0 件(hollow、5.2) | 段2→段1 | 手放しの実証消滅=手放しの取消 |
| 障礙 N4(前提崩壊)1 件 | 該 act 段1、其余維持 | 障礙局在(7.2 delegation_audit) |
| 落日審議者=0(無人運行) | 段2→段1＋審議槽起票 | 末端の消滅は段の問題でなく判断の消滅(5.1) |
| dissent 率 5%超(8.4) | 段3 全面停止→段1 | 現場の不服従=委任の撤回(7.2) |

表の読みを一環——**下方向の決定は機械が執行し、上方向の決定は人間が署名する**（段2→段1 の demote は自動、段1→段2 の promote は落日審議の署名を要する。非対称の理由：安全は退避で取れ、退避は速い方が良く、前進は遅い方が良い——→8.5 の「猶予は速い系の前に跪く」の段設計への配線）。この非対称が表の全行を贯いていることを明示的に認める——自動 demote を恐れるチームは、六障害テストの 1 本目（test_safety_fall）が**自動退避そのもの**であることを見れば、退避こそがテストで守られているものだと分かる。
