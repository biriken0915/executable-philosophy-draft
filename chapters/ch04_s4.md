## 4.4 Design by Contract — 主張としてのアサーション

retrofit で過去の質問を掘り起こした（→4.3）。次に、未来への約束の置き方を扱う。Bertrand Meyer の Design by Contract（DbC、1986, *Object-Oriented Software Construction*）は、プログラム内部の検査文（precondition / postcondition / invariant）を、単なるデバッグ装置ではなく**契約**として再定義した発明である。契約——前提と保証と不変条件を、コードの署名として、呼び出し側と呼び出し側双方に法的・構造的に束縛させる。本章の文脈で DbC を第四章に置く理由は明確である。**アサーションは、コードが世界について発する主張（assertion）であり、主張は存在論的宣言である**（→1.5 のラベル＝存在論的宣言の、実行時版）。`assert x > 0` は「この関数が呼ばれる世界の x は正である」という ontological commitment の実行形式であり、契約違反はその主張の世界が崩れた事件——**認識論的事件**である。DbC は崩れを機械が知る機構を、ソフトウェアの構文に埋め込んだ設計哲学である。

### 契約の三部作 — 前提・保証・不変条件

Meyer の原語で正確に敷設し直す。

**事前条件（precondition）**：呼び出し側が満たすべき条件。満たさないなら、実装側は何も保証しない（契約の定義域外）。**事後条件（postcondition）**：事前条件が満たされた上で実装が返す保証。**クラス不変条件（class invariant）**：公開呼び出しの前後で常に真であるクラス側の主張（「残高は非負」「ハッシュ表のバケット数は素数」）。加えて二つの規則——**継承における契約強化則**（ subclass は precondition を弱められない、postcondition を強められない／conformity rule）と、**observer abstraction**（実装でなく査詢で契約を検証する）。

この三つ組が「契約」を名乗る資格の核心は、**責任の所在が構文で固定される**点である。precondition 違反＝呼び出し側の契約違反、postcondition 違反＝実装側の契約違反。同じ例外の飛火が、どちらの過失かをコードが告げる。3.6 の「責任の連鎖の末端は人間」という定理が、ここで実行時の粒度で具体化する——違反報告が過失の所在を名指しできるシステムと、できないシステムでは、学習速度が一桁変わる（過失の名指しなき失敗は、誰の修正タスクにもならない：→8.1）。

### アサーション＝存在論的主張 — なぜ契約違反が「認識論的事件」なのか

DbC の正典は契約を契約法にたとえるが、本章の読者はすでに予感している。**クラス不変条件は、そのクラスが世界に課す分類の宣言である**（→2.1 の分節＝切断）。`invariant: 残高 >= 0` は「このクラスの認識では、負の残高は存在しない」の宣言であり、`ViolationError` はその存在論の外の実在がコードに衝突した瞬間である。

事件の構造を三層で分解する。

1. **実在層**：残高 -500 の口座が現実に存在した（銀行の外部——手作業の帳簿修正、並行振替、currency 丸め）。
2. **主張層**：クラスは -500 を存在させないと宣言していた。
3. **事件層**：違反例外が、宣言と実在の断離を**イベントとして発火させる**——ログに、スタックに、呼び出しスタックの契約項に記録される。

第三層が DbC の発明である。宣言と実在の断離は、通常は事故として現実に現れ（客の残高がマイナス）、コードの中では黙過される（値はそのまま流れる）。契約は断離を**出来事にして履歴に残す**。2.1 の残余保存原則の実行時版——契約違反は、契約という分類の残余である。契約が保存する残余（違反の記録）は、のちに分類の版数変更（→2.4 の deprecation と改訂）の動機になる。断離の履歴が意味史の燃料になる——2.5 の `LostMeaning` と同じ代数が、実行時イベントでも動く。

```python
# dbc_pydantic.py — DbC を Pydantic V2 で敷設する(本書の Python 契約語彙)
# 哲学: assert は「コードの思考の停止」。契約は「コードの主張の宣言」。
# 前者は crash で終わり、後者は violation イベントとして履歴に乗る。
from pydantic import BaseModel, model_validator, field_validator, ValidationError
from datetime import datetime
import uuid

class ContractViolation(BaseModel):
    """違反そのものをファーストクラスの事実として作る。例外ではない(→4.5 の sat と同型)。"""
    violation_id: str
    contract: str          # invariant | precondition | postcondition
    subject: str           # どのクラス/関数の主張か
    claim: str             # 主張の原文(コード式ではなく人間可読の宣言、→3.3 の RefinementTrace と接続)
    world_evidence: dict   # 違反した世界の証拠(値・時刻・入力)
    at: datetime

class Account(BaseModel):
    balance: float
    currency: str = "JPY"

    # class invariant = 存在論的宣言(→1.5)
    @model_validator(mode="after")
    def invariant_non_negative(self):
        if self.balance < 0:
            v = ContractViolation(
                violation_id=str(uuid.uuid4()),
                contract="invariant", subject="Account",
                claim="残高は非負である(このクラスの世界に負の残高は存在しない)",
                world_evidence={"balance": self.balance, "currency": self.currency},
                at=datetime.now())
            raise ValueError(v.model_dump_json())   # 証拠つきの宣言破棄
        return self

def transfer(src: Account, dst: Account, amount: float):
    # precondition = 呼び出し側への要求の宣言(→3.6 の要求割当の実行時版)
    assert amount > 0, "precondition(amount>0) violated by caller"
    # postcondition を先に書く: 実装ではなく「約束」を先に書く作法(Meyer の contract-first)
    try:
        after_src = src.model_copy(update={"balance": src.balance - amount})
        after_dst = dst.model_copy(update={"balance": dst.balance + amount})
        # observer abstraction: 実装でなく、検証可能な査詢で契約を確認する
        assert after_dst.balance == dst.balance + amount, "post: dst balance"
        assert after_src.balance >= 0 or True, "precondition が守られた世界だけが届く場所"
        return after_src, after_dst
    except AssertionError as e:
        raise  # 実装側の違反 = 実装側の契約違反。名指しされる(責任所在の構文化)
```

`ContractViolation` を例外ではなく**データとして作る**設計の意義を強調する。例外は制御の流れだが、データは履歴になる。違反レコードを Neo4j の `Incident` ノード（→3.4 の障礙の実例 INSTANCE_OF）へ書き込めば、契約違反は障礙の**実測サンプル**になる——障礙分析（→3.4）は契約違反ログによって `theoretical → live` の更新を受けていく。formal な障礙木と実行時の違反記録が同一グラフで循環する設計——DbC は第2部の履歴代数に接続する**実行時の入力装置**なのである。

### 契約と CQ — 同一の主張の二つの時制

DbC と CQ（→4.2）は似た形をして別のものではなく、**同じ主張の異なる時制**である。

| 次元 | CQ | DbC |
|---|---|---|
| 主張の時制 | 現在〜過去：この KB は答えられる | 未来：この実行は保証を下す |
| 検証の主体 | データベース全体 | 呼び出し一回 |
| 失敗の意味 | 構造の不足（載っていない） | 宣言と実在の断離（世界が宣言を超えた） |
| 履歴上の役割 | 仕様の仕様（E1/E3） | 障礙の実例（→3.4） |

両者は一本の線で結べる——CQ は構造への契約であり、DbC は実行への CQ である。設計の作法として本書が課す線はこれだ：**CQ の answer_contract（→4.2 の三つ組の (c)）と、境界のコードの契約は、同一文書から生成されねばならない**。両者が手書きで二重管理されると、契約が CQ の追従に遅れ、**テストは通るが世界は壊れる**窓が開く（→4.1 の検証等級 E1 の内部亀裂）。生成は 4.6 の回帰テスト設計で実装する。

### 契約の限界 — すべてを契約化できないこと自体が契約である

DbC の率直な限界を三つ登記する（→4.1 憲章条二の自己適用）。

其一、**不変条件の網羅不能**。クラスの全状態に対する invariant の完全集合は書けない（frame problem の残影）。書かれた invariant は主張の**選択**であり、選択外の属性は無宣言のまま流れる（残余）。対処は契約にも版数と残余宣言を持たせること——`contract_gap: ['currency 丸めは未宣言']` をコードメタデータに書く。

其二、**分散不変条件（distributed invariant）の弱さ**。複数サービス・複数プロセスにまたがる不変条件（「全 Account の合計 = 元帳残高」）は、Meyer の原点（単一オブジェクト）の外にある。解決は二方向——プロトコル側（two-phase commit 等の distributed invariant 機構）と、検証側（→6.3 の OPA の world-state policy、→4.5 の sat 判定で世界全体の整合性）。本書は後者を主軸に置く（→6.3・7.3 の context graph 全体に対する制約）。

其三、**soft 要求は契約化できない**（→3.6 の割当禁止のコード版）。「適切に」「迅速に」は precondition/postcondition の二値に落ちない。契約化を試みると、閾値化（`latency < 200ms`）で soft の内容が失われる。処置——soft 次元は E2/E3 の契約（統計手続・審議記録）へ分離し、コード契約と契約台帳でつなぐ。

```python
# contract_ledger.py — 契約の版数管理: 契約変更も 2.5/2.6 の変更代数に乗せる
# 哲学: invariant の変更は存在論の改訂である(主張しなくなった世界の領域を記録する)。
# diff を取って契約の 'retracted claim' を墓標化するのが本章の DbC と 2.5 の接続点。
def contract_diff(old: str, new: str) -> dict:
    import difflib
    adds, dels = [], []
    for line in difflib.unified_diff(old.splitlines(), new.splitlines()):
        if line.startswith("+") and not line.startswith("+++"): adds.append(line[1:])
        if line.startswith("-") and not line.startswith("---"): dels.append(line[1:])
    return {"retracted_claims": dels,   # → RetractedClaim ノード(→2.5 墓標と同型)
            "new_claims": adds,
            "meaning": "退位した主張は消えない。CI は new のもとで retracted の反例を走り続ける"}
```

`retracted_claims` の反例探索を CI が走り続ける——これは 2.5 の「CQ 墓標が構造回帰を見守る」（→4.2）と同じ見張り設計である。主張を退位させると、退位した主張が**反例として成立し続ける世界**（つまり旧主張が今も真たな世界）を CI は探査し続ける。意味の変更は世界の拡張であり、拡張の側から旧世界が消えたかどうかは、消えたとは自動に保証されない。見張りがその保証の装置である。

### 契約の三語の統治 — 前置・不変・後件を書き換える権利

DbC（precondition・invariant・postcondition、→前掲の「主張としてのアサーション」）の運用統治を一度だけ明示する。契約は code comment より重い（実行される宣言、→4.4）——ゆえに**契約の変更は code review より重い級でなければならない**。級を確定する（→2.6 の級体系の契約への適用）。

| 契約要素 | 変更の級 | 要求される証拠 |
|---|---|---|
| precondition の緩和(呼び出し側の条件を減らす) | L2 | 呼び出し元全数の影響調査＋回帰テスト追加 |
| precondition の強化 | L2 | 現存呼び出し元が全て満す実測(壊れる caller のリスト) |
| invariant の緩和・削除 | **L3** | 条約審議(invariant=世界観の宣言、→2.4 の TBox と同格) |
| postcondition の強化 | L2 | 全実装・全 mock の再検証 |
| postcondition の緩和 | **L3** | 調用側が失われる保証の洗い出し(CQ 化,→4.2) |
| docstring のみ | L0 | — |

非対称の理由を刻む——**緩和と削除が L3** なのは、契約のうち弱まる側が世界観の変更だからである（「何を約束しないか」の決定は「何が重要か」の決定——→3.1 の目的因の変更、→2.4 の分類制定と同格）。強化は L2（約束を増やす決定は実装コストの問題で、世界観の決定ではない）。この級表を CI に inscribe する（diff に `assert`・`require`・`ensure`・invariant 注釈の変更があれば級自動判定——→2.6 の change_grade_check の契約版で、**意味の変更の構造解析**がここで二番目に現れる）。

統治の最終条項を置いておく。契約の削除・緩和の審議には、**その契約が过去に止めた事故の実例**（障礙台帳・OverrideEvent・Quarantine の突合、→3.4・5.6）を自動で添える。契約の削除は「約束が重い」ではなく「約束が何も止めなかった」の実証を伴うときだけ通る——止めなかった約束は形式の過負荷（2.1 の暴力）だが、止めた約束の削除は未来の事故の予約である（**契約の落日設計は、契約が過去に払った保険金を添えて回ってくる**——2.5 の簿記の倫理の DbC 版）。

### 証拠条約の 2 行 — pre/post の証拠 URI 強制

DbC の装饰器（→前掲）に、証拠条約の 2 行を足す——**前条件の成立も後条件の成立も、観測 URI を伴わなければならない**（`assert x > 0` は成立を代码に見せるが、成立が**世界のどの計器のどれの読数**に基づくかは見せない——→4.4 の中心：代码の内部の真理と世界の接缝の証拠を区別する）。

```python
@precondition("vib < THRESH", evidence=lambda ctx: ctx.obs_uri)   # 前条件:観測引用必須
@postcondition("stop_signal_set", evidence=lambda ctx: ctx.act_uri) # 後条件:実 act 引用必須
```

evidence が None の場合、装饰器は assert を pass させるが **Quarantine を起票する**（契約は満たされた、しかし契約の根拠が証拠なし——「正しい決定の証拠なき実行」は 5.6・7.5 の Quarantine と同一の事件類別で、正しさは簿記を救わない）。この設計の要点を一環：証拠 URI の強制は、テストと本番の**同一性**を作る（テストでも本番でも同じ evidence 列が書かれ、テストが本番の形を偽装できない——→4.6 三層テストが「世界変更ノードの不在」を検える前提条件、→7.6 test_safety_fall の 4 章側の実現）。
