## 8.4 Human-in-the-Loop — 自動化ではなく増幅化

共観と避難所——形式化の外側の設計を置いた（→8.3）。この節からは形式化の内側に戻り、**人間をどこに、どういう扱いで置くか**を設計する。Human-in-the-Loop（HITL）は昨今、AI 系の常套句になっている——「人間の承認を入れる」「ラベル付けに人間を使う」「human-on-the-loop」。本書はこれらの使用法を三類型に分解し、そのうち二つがプロレタリア化の続きであることを示し（→8.1）、第三の類型——**共創**——だけを本書の設計に採用する。節の標題の対立語組は重要で、「自動化（automation）」に対して本書が選ぶのは「増幅化（amplification）」である——機械が人間の代わりに行為するのではなく、機械が人間の行為の質と速さと射程を伸ばす配線へ、判断の連鎖を組み替える。

### HITL の三類型 — 承認・介入・共創

**類型一：承認（approval）**。機械が行為し、人間が事前または事後に可否を署名する。本書の語で言えば、人間は JudgmentEvent の decider として登記される——ただし内容形成（frame）が機械にあるなら、5.3 の隠れ判断と見せかけ承認の連鎖である（→5.1 の実効的承認の再検証可能性を満たさない署名）。承認類型の労働者は、8.2 の「わからずに押すボタン」の番人になる。
**類型二：介入（intervention）**。機械が行為し、人間は壊れたとき・危ういときに割り込む（フェイルセーフの人間版、on-the-loop）。人間の労働は**例外処理**に限定される——正常運用は機械、異常時に人間。一見安全だが、8.1 の第四段（自動化が壊れたとき回復できる人間がいない）をそのまま再生産する：例外しか経験していない労働者に、例外の意味を理解している保証はない（例外の経験は、正常の理解の上にのみ立てられる——1.1 の暗黙知は正常運用の身体化であり、正常から人間を退かせば暗黙知は育たない）。
**類型三：共創（co-creation）**。機械と人間が**同じ作業の異なる局面を分担し、互いの出力が互いの次入力になる**循環。機械は候補・根拠・却下・反証条件を供給し（→7.3・8.2 の ActionOffer）、人間は再解釈・新語・障礙記入・不服従で供給に応え（→8.2 の再解釈の席）、その応えが機械の次の皿と規則を更新する（→7.1 の RuleAdoption、→4.2 の CQAmendment）。共創の本質は、**人間の出力が機械の訓練データではなく、機械の憲法の一部になる**ことにある——人間がやるのはラベル付け（機械の改善の手伝い）ではなく、規則と語彙の選定（系の統治への参加）である。

三類型の判別試験を一つ置く。**人間の応答がモデルの学習データにのみ流れ、系の規則（Rego・shape・TermMapping・goal form）に流れないなら、それは共創ではなく類型一または二である**（→5.1 の update_route の所在が主体外へ流出している状態——5.1 練習3 の「経験の国内化」の HITL 版）。

### 介入データを「ラベル」ではなく「反論」として保存する

共創の技術的中心に入る。機械学習の実務で、人間の介入は通常**ラベル**として保存される——正解・不正解、是認・否認、修正差分。ラベルの保存形式は、人間の応答を**機械の未来のための材料**に固定する（人間は未来のモデルの部品にされる——プロレタリア化の最も穏やかで最も完全な形：あなたの判断はあなたの世界の統治には使われず、ベンダーのモデルの勾配になる、→5.1 の経験流出）。

本書は介入を**反論（objection）**として保存する。反論型の最小形：

```python
# intervention.py — 介入の保存形式: ラベルではなく反論
class Objection(BaseModel):
    """人間の介入を『なぜ違ったか』の論証として保存する(→4.4 データとして保存哲学)。"""
    target: str                    # 何を否ったか(candidate id / verdict / 規則 id)
    because: str                   # 理由の自由文(必須・匿名不可、→2.5 intent 原則)
    counter_offer: str | None      # 差し替え候補(無くてもよい: 否定は肯定に優先する)
    evidence_refs: list[str]       # 根拠の参照(現場の観測・過去の実例・CQ)
    rule_critique: str | None      # 『規則そのもの』への批判(これが共創の核)
    route: Literal["model-train", "rule-change", "cq-amendment", "sanctuary"]
    # ^ 人間が応答の『行き先』を選ぶ。全て model-train に既定される UI は
    #   共創を静かに類型一へ退化させる(経験の流出の UI 実装)。
```

`rule_critique` と `route` の二項目が、ラベル形式との決定的な差である。**rule_critique**：「今回の出力は違う」ではなく「この shape のこの制約が、この現場の区別を潰している」——介入が規則改正（→2.6 級つきの変更）に化ける口。Objection はそのまま RuleAdoption/TermMapping/CQAmendment の審議槽へ配線される（→7.1・6.1・4.2 —— 8.2 の再解釈の席が、介入の自然な行き先として機械的に開いている）。**route**：人間が行き先を選ぶ——学習材料として使ってよいと人間が許した場合のみ model-train に流れ、既定は rule-change（系自身を変える）へ寄せる。この既定の寄せ方が「増幅化」の配線そのものである——**経験をまず系の統治へ流し、余ったものをモデルの改善へ流す**。逆（全てモデルへ）が自動化、前が増幅化。

```cypher
// objection 流の監査: 介入の行き先分布(共創の健康計器、→8.1 計器の HITL 版)
MATCH (o:Objection) WHERE o.at > datetime() - duration('P8W')
RETURN o.route, count(o) AS n,
       avg(size(o.evidence_refs)) AS evidence_depth,
       sum(CASE WHEN o.rule_critique IS NOT NULL THEN 1 ELSE 0 END)*1.0/count(o) AS rule_attack_rate
ORDER BY n DESC;
// rule_attack_rate 低位 + route='model-train' 過半 = 共創の退化(類型一/二への逆流)。
```

`evidence_depth`（平均根拠参照数）にも意味がある——反論が根拠なしの直感でなく実例接続で出ている率（→3.4 の障礙実例の循環が、労働者の介入経由で回る）。直感の反論も保存するが、実例接続の反論は RuleAdoption の E1/E2 級の根拠になれる（→4.1 の等級が介入の重みになる）。

### 介入地点の設計 — どこに人を置くかで人間観が決まる

HITL の設計変数の最後の一本を引く。**人間の介入地点**。パイプライン（→7.4）のどの段に人を置くかで、その系が人間を何だと考えているかが決まる。

**提案段に人**（LLM の代わりに人が候補を出す）——人間を生成力の部品とみなす。増幅化の観点で最弱（機械の候補生成の補助に人間を落としめる、→8.2 の技能剥奪）。
**検証段に人**（機械の出力を人が検査）——人間を品質管理のセンサーとみなす。承認類型の本体（→5.3 のlaundering 風険）。
**決定段に人**（judgment を人が下す）——人間を判断の器とみなす（→5.1 の accountability 末端）。**必須だが不十分**——皿が機械由来の frame 内クリックに退化しうる（→8.1 の frame_conformity）。
**規則段に人**（RuleAdoption・shape・mapping・CQ を人が変える）——人間を**憲法の制定参加者**とみなす。本書の設計はここに最も厚く人を置く（→7.1 委任深度の前提条件が phronesis 残高であったこと、→7.6 の段3昇格条件）。
**共観・避難所の段に人**（→8.3）——人間を沈黙を共有する存在とみなす。形式化の外側の人間観。

```python
# human_placement.py — 介入地点の配置表(各段の人間予算・SLA・行き先)
PLACEMENT = {
  "propose":   {"human": "任意(現場の独創候補は dissent で随時注入可)", "route": "candidate"},
  "verify":    {"human": "警告級のみ(機械検証の Warning 判断)",          "route": "rule-change 既定"},
  "decide":    {"human": "必須(time-boxed, 8.5 の皿で)",                "route": "judgment"},
  "rule":      {"human": "常設(知識議席・審議槽・落日再承認)",           "route": "rule-change/cq-amendment"},
  "copresence":{"human": "居るだけ(記録は場の存在のみ)",                 "route": "sanctuary"},
}
# 表の読み: 人間の人時予算が decide に厚く rule に薄い系は、『判断は人間、統治は機械』
# という人間観を予算で告白している(予算が哲学の真の表明、→4.1 の宣言と実測)。
```

最後のコメントを反芻してほしい。**予算が哲学の真の表明である**——会議での人間尊重の宣言と、人時配分表の乖離（→4.1 の宣言と実測の突合が、組織設計にも効く）。決裁段に人時を積み（承認の労働化）、規則段を空席にする組織は、人間を「判断してくれる便利なセンサー」として設計している——5.3 の尤度の物語化が読む説明文と、この表の読みは同じである。

### 共創の計測 — 三類型の実地判別と退化の早期警告

三類型（承認・介入・共創、→5.1 の表）を、実地の判別試験として数値化する。判別の中心は前節の通り「人間の出力の行き先」だが、運用で測る三本の照会を置く。其一、**routinized-consent 率**：判断（JudgmentEvent）のうち、候補集合が単一で（皿が1つ）、根拠面板の滞在が最小値ちょうどの同意の率（→8.5 の READING/REASON_PROBED の履歴で測れる——形式読解の履歴は実質読解の下限証拠である、→8.5 練習2）。其二、**介入の実効半減期**：人間の介入（Objection・override）が、規則変更（RuleAdoption・shape 改訂）に化けるまでの中央値日数——半減期が無限大（化けない）なら、介入は承認に退化している。其三、**共創の配線長**：現場の反論が規則変更になるまでに経由する審議段の数——長い配線は共創の摩擦であり、摩擦が閾値を超えると現場は dissent をやめる（dissent_volume の逓減は配線の詰まりの音、→6.2 槽の健康）。

```cypher
// hitl-degeneracy — 三類型の退化検出(月次 scorecard に登録)
MATCH (je:JudgmentEvent) WHERE je.at > datetime() - duration('P1M')
WITH je, size([(je)-[:JUDGED_ON]->(:EvidenceBundle)-[:HAS]->(:Candidate) | 1]) AS plate_n
RETURN avg(CASE WHEN plate_n = 1 THEN 1.0 ELSE 0.0 END) AS single_plate_rate,
       // ^ 皿が1枚の判断率: 高ければ承認は選択肢の登記ではなく署名の登記
       count(je) AS judgment_count;
MATCH (o:Objection) WHERE o.route = 'model-train'
RETURN count(o) AS model_only_objections;      // 行き先 model-train 過半=共創の退化
```

退化警告（single_plate_rate > 0.6 + model_only_objections 過半）が出た系に、本書が勧める最初の解毒は**皿を増やすことではなく、皿の外を登録可能にすること**である（→7.1 の coin-term・dissent の通路——候補が増えると frame 内クリックが効率化してかえって frame_conformity が上がる逆転がある、→8.1 の frame_conformity の罠）。frame_conformity が測るべきは候補数ではなく**候補外応答の登録率**である（outside-frame registration rate、→8.6 の drill level 4〜5 と同一の設計語彙）。

自動化への政治的回復として、この節の結論を明示しておく。**人間を残すことと、人間を残す意味があることを設計で担保すること**は違う。承認段に人間を置くだけなら、それは責任の洗浄装置に人間を置くことだ（→5.3 laundering の組織実装）。共創の三配線（規則段の席・反論の保存・行き先の選択）が揃っていない HITL は、本書の語で「HITL のふりをした自動化」である——そしてこの偽装は、scorecard の三照会（single_plate_rate・介入半減期・dissent 逓減）で区別できる。哲学は区別のためにある、区別は計器のためにある。

### 异議の作法 — Objection の書き方三例と退化例

8.4 の Objection model（because/counter_offer/evidence_refs/route、→前掲）を、書き方の例で缔ぶ。好的三例と退化二例。

**良い一（規則批判＋反案）**：because:「E4 前提『伝感器連続』が 3 日で 2 回崩壊（evidence:/obs/441,/obs/509）。この前提で夜間自動を続けると、崩壊時の停止が人工判断で遅れる」counter_offer:「前提崩壊時の 10 秒安全停止のみ自動、其余段1へ」route: rule-change。——前提の崩壊実例・反案・行き先が揃う（→3.4 N4 の宣言の書式そのもの）。
**良い二（判断の再検証要求）**：because:「私（保全長）の 11/2 の同意は、推薦 0.7 の basis に旧型設备的分布が混在していることを知らなかった（basis の撤回条件に無かった、→5.3 確率の約束）」counter_offer:「同意の再決着、basis 分離まで該 act を段1に降格」route: rule-change＋自己履歴LED_TO。——自己の判断の歴史を証拠に使える（→8.2 パネルの逆用——自分の同意を自分が退かせる=所有の実地）。
**良い三（皿の外）**：because:「推薦 3 皿はいずれも弁加圧の調整。そもそも夜間弁圧運行の廃止が討議されていない」counter_offer: なし（选項の创設要求）。route: 討議槽——皿の外が规則批判より上位の討議に載る（→7.1 coin-term・→8.6 drill level 5 の書き手版）。
**退化一（苦情）**：because:「この AI は信用できない」——evidence_refs 無·反案無·route 無。受理する（発言級 L0、→2.6）が、審議材料にはならに——解決率の分母に載せず、**質感情報として另枠**（分母に載せると、質の低さが解決率を下げるために异議の受け口が狭くなる、→6.2 歪）。
**退化二（回答案の盗用）**：counter_offer が既存 act 集の焼き直しで、because が無い（反案の量産で討議を満杯にする——→6.6 赤組脚本三の個人版）。検出：counter_offer の重復率と because の引用密度（→B.3 計器）。

書き方 guide を UI に内蔵する（Objection form の placeholder に三例の骨格を載せる、→8.5 の面板と同じ設計哲学——**書式が哲学を配線する**）。

### 异議統計 — 四本を一并に読む

8.4 の計器（dissent_attack_rate・single_plate_rate・介入半減期、→前掲）は四本目まで揃えて并べ読む（単独の計器は必ずゲーム化される、→6.6 統計が燃料でなくなる形態）。**四本目：异議解決の時間（dissent→決着の中央値）**。四列の組み合わせ診断を四つ置く。(低 attack・短 解決)=討議が生きている（异議が出て速く決着する）。(低 attack・長 解決)=討議が空洞（出ない上に決着も遅い=6.6 腐敗四の完走）。(高 attack・短 解決)=現場が鋭い（是正が追いついている）。(高 attack・長 解決)=**委任の危機**（异議が積累して決着しない=現場が系統を「談判対象」に見始めた——dissent が討議でなく交渉になる、交渉は条約贸易に化ける、→6.1 の贸易が討議を迂回する=統治の外部化、6.6 の入口）。

四列を四半期プロットした図に、落日審議（→6.6）の決議を 1 点で書き込む（「次季、どの列を動かすか」の宣言）。計器の図に決定が書かれない限り、計器は観測でなく装饰である（→4.6「あらゆる検査は失敗の届け出先まで設計して初めて検査」——計器の届け出先は最終的に**次季の決定の URI**でなければならない、検査と席の接続の統計版）。

### 実行練習

1. あなたの HITL 実装（承認フロー・レビュー・修正 UI）を三類型で診断し、介入データの保存形式（ラベルか反論か）を特定せよ。`Objection` の `route` 相当（人間が行き先を選べるか）が無い場合、まず route  selector を1項目だけ追加する改造の級（→2.6）と、その改造の Objection 自身（rule_critique として）を書いてから着手せよ。
2. `objection` 流の監査クエリをあなたの修正・差し戻しデータで実行し、rule_attack_rate を計算せよ。低位（例0.1 未満）の場合、介入が規則へ化ける口を1つ開け（例：レビューコメントの「手順そのものへの批判」チェックボックス→審議槽自動登録）し、審議槽のキャパ超過時の優先順位規則（どの口から開くか）を級つきで決めよ。
3. `PLACEMENT` 表をあなたの組織の人時配分実測（1か月のタイムトラックから）で書き直し、宣言（会議・規程での人間観）と予算（実配分）の乖離を1段落で報告せよ。乖離の是正として、decide の人時を rule 段へ移す計画（誰のどの会議を削り、誰を知識議席へ座らせるか）を、2.6 級 L2 の変更説明文の形式で書け。
