## 8.3 共同化への逆流 — 暗黙知へ戻る設計

8.1 が系を裁き、8.2 が所有権と理解の配線を戻した。この節から本章の建設が始まる——**暗黙知への逆流**を設計に組み戻す。供給源は野中郁次郎（Nonaka）の SECI 知識変換モデルである（『組織知識創成論』1995、野中&竹内）。本書は第1部で外化（tacit → explicit、→1.4・4.2 の CQ・1.3 の context graph）を、第2部で結合（explicit → explicit、→2.5 の履歴代数・4.3 の retrofit）を、第5・7章で内面化（explicit → tacit、→5.2 の現前化と更新経路）を、すでに設計してきた。SECI の四つ目の環——**共同化（Socialization、tacit → tacit）**——だけが、これまで一度も設計されていない。暗黙知から暗黙知へ、身体と共同注意を通じて直接流れる知。形式化の果ての章が、あえて**形式化されない知への逆流**を設計する。逆説ではない——共同化は形式化できないが、**共同化の場所・時間・条件は設計できる**。設計すべきは知そのものではなく、知が流れるための空隙なのである。

### SECI の四環と、本書が置いてきた環

SECI の四環を本書の到達点と対応させて確認する。**外化**：暗黙知をことば・図・制度へ引き出す（本書の CQ、context graph、EARS——→4.2・1.4・3.3）。**結合**：形式化された知を結合・伝達する（グラフ横断照会、履歴代数、RDF ブリッジ——→1.3・2.5）。**内面化**：形式知を身体に落とし込み技能へ戻す（反復・練習・更新経路——→5.1 の「経験が主体を変える」、7.2 の現場周期の実測）。そして**共同化**：共に居て、同じものを見て、互いの暗黙知を伝導する——師匠の手元を見る、夕方の雑談で「あの音、変だったろ」が共有される、先輩の沈黙の聞き方を真似る。野中の指摘で重要なのは、共同化が知識創出の**発火点**である多いこと（外化の多くは、共同化の中で温められた共有暗黙知から生まれる——「暗黙知の交配」）。本書の体系は外化以降の環を豊かに持っていて、この発火点の配管を**ゼロから設計していない**。8.1 の計器（site_coinations の逓減）が測っていたのは、まさにこの環の供血不足であった。

### 共観（joint attention）— 状況の共同閲覧の設計

共同化の第一条件は、同じものを**同じ時に**見ていること——共同注意（joint attention）である。設計名を**共観**として置く。共観はダッシュボードの共有ではない（非同期の閲覧は結合であって共同化ではない——同時性与共同性が必須）。設計要素三つ。

其一、**共観セッション**：同じ状況スレッド（→7.5 の thread）を、2〜4人の人間が同一時間で閲覧する場。画面は同一の `situation_digest` を提示し、各人の注釈が時間軸に並ぶ。其二、**見解の併置**：注釈は投票・統合・多数決されない——**並んだまま**保存される（confluence of disagreement）。其三、**沈黙の保持**：セッションにはコメントしない権利があり、無言の参加も参加として記録される（誰がそこに居たか、が記録され、発言しない人の注視時間は残る——→8.5 の「無応答は沈黙の同意ではない」とは別の、**沈黙そのものの価値**）。

```cypher
// copresence — 共観セッションの記録: 暗黙知の発火場所の地誌
CREATE (s:CoproSession {s_id:$id, thread_ref:$thread, started:datetime(),
          duration_min:$min, modality:'same-time'});   // 同時性必須(非同期は別種 Session)
// 参加: 発言しなかった者も参加者として登録(沈黙は記録される、→1.6 の設計の反転使用)
UNWIND $attendees AS a
CREATE (p:Person {person_id:a})-[:PRESENT_IN {spoke:a IN $speakers}]->(s);
// 見解の併置: 統合しない。contradiction は異常ではなく資産。
CREATE (v1:Viewpoint {body:$v1, author:$a1, at:datetime()})-[:ON]->(s),
       (v2:Viewpoint {body:$v2, author:$a2, at:datetime()})-[:ON]->(s),
       (v1)-[:COEXISTS_WITH]->(v2);
// 集計(8.1 の計器の解毒回路): 共観の密度 → 数週後の site_coinations の先行指標
MATCH (s:CoproSession) WHERE s.started > datetime() - duration('P8W')
RETURN date.truncate('week', s.started) AS w, count(s) AS copresence_rate
ORDER BY w;
```

`(v1)-[:COEXISTS_WITH]->(v2)` を統合辺ではなく併存辺として置くのが共同化設計の核心である。見解の統合（多数決・AI 要約・「結論」化）は、その瞬間に**共同化を終了させ結合へ移す**（→4.5 の LLM 要約の現前化代行の危険と同じ構造——統合は消費である）。併存は、矛盾した見解が並んだまま残ることで、後の共観・後の議論・後の夜の実践で再び発火しうる（SECI の螺旋——共同化が外化を孵し、外化が結合を経て内面化され、内面化が新たな共同化の場を育てる。螺旋の第一環が、この併存の庫である）。

### 沈黙の設計 — 「記録しないこと」の避難所

第1.6節で敷設した NonRecordingRule（記録しないことの設計）が、ここで本来的な使われ方をする。暗黙知の避難所——**形式化の網から意図的に外された領域**を設計に設けること。理由は、暗黙知が形式化されるたびに何かを失うこと（1.2 の残余の定理）、そして暗黙知が避難所なしには存在し続ける場を持てないことである。現場の雑談、休憩時間の「あれどうなった？」、師匠の手元を黙って見る時間——これらが記録・可視化・KPI 化された瞬間、それは暗黙知ではなく形式知の模写に変わる（観察可能になった暗黙知は、観察される振る舞いに自己適応してしまう——測定される行為は測定用に変わる、→6.6 指標の武器化の身体版）。

避難所の設計 three 条。**其一、共観の無記録部分**：共観セッションの記録は「誰がいつそこにいたか＋併置された見解」までで、**視線・間の長さ・言わなかった言葉は記録しない**（記録しないことを記録する設計の完了、→1.6）。**其二、雑談領域**：業務チャネルと分離された、検索索引外・監査ログ外の領域（監査不能領域を置くことの統治的条件は 6.6 の条約で既に作ってある——防腐層の計器が届かない場所を条約で宣言する。宣言された避難所は無法地帯ではなく、**条約で守られた空地**である）。**其三、師弟の共働時間**：共観と実作業が重なる時間帯（先輩の作業を新人が黙って見る）。これは共観セッションとは別種の Copresence（`modality:'working-together'`）で記録され、記録されるのは**場の存在と参加と長さだけ**である——内容の記録は不在こそが設計である。

```rego
# policy/sanctuary.rego — 避難所への監視の侵入を止める門(8.3 の防腐条約)
package execphil.sanctuary
default allow = false
# 雑談領域・共観の無記録部分への「索引付け」「KPI抽出」は不許可。
# 抽出バッチの actor が sanctuary スペースを read 対象に含む場合、plan 段で拒否(→6.4 二重防御)。
allow_read { input.actor IN ["person:", "copresence-ui"] 
             startswith(input.scope, "copresence://") }
deny { input.actor IN ["indexing-batch", "kpi-extract", "vendor-analytics"] }
# 避難所の空地は監査ログに『空地として』のみ現れる(何があったかは現れない)。
# 空地の存在自体の監査=空地が縮小されていないかの監視(空地縮小=L2 事件)。
```

`deny` が自社の分析バッチにまで向いている点に注目してほしい。避難所の最大の侵食者は外部の悪意ではなく、**内側の善意の分析**である（「雑談のテキスト解析でリスク検知！」は有用そうに見えて、暗黙知の生態系を殺す——検知に使えるのは暗黙知が形式化された後だけであり、形式化前の暗黙知は避難所でしか育たない。8.1 第四段の逆転：避難所を失った系は、未知が育つ前に未知を見る能力を失う）。

### 共同化の計器 — 逆流の流量

8.1 の三計器（site_coinations / frame_conformity / stale_obstacles）は、逆流の**滞り**を測るものであった。共観設計には**流量**の計器が必要である。共観密度（週あたり CoproSession・参加延べ人数・参加の職層混合度）、見解併置数（COEXISTS_WITH 辺）、共働時間（working-together の合計長）。これらの数値の使い方の条約を 6.6 条約G-1 で先回りしてある（**個人ではなく系の流量として読む**——共観数が個人の KPI になった瞬間、共観は会議に化けて共同化は死ぬ。場の数を測り、中身を測らない）。

流量がゼロに近づく場所を、設計は知っている。形式化の収奪が強い場所——完全な監査ログ、完全な承認フロー、完全な可視化の近くほど、共観は細る（見られている場では人は沈黙を共有しない）。よって共観密度と形式化密度（decision log 件数・承認フロー件数の密度）を併記した地図——**体系の暗部地図**——を四半期ごとに描く。本書の理想は暗部ゼロではない。**暗部と明部の境界が条約で引かれ、暗部が条約で守られていること**である（1.6 の「記録しないことを記録する」の系図は、ここで組織スケールの地図になって閉じる）。

### 師弟の設計 — 暗黙知の伝承を業務時間として実装する

共同化の最も古い形は師弟である（弟子が師匠の手元を見て、真似て、黙って時を積む）。本書の体系はこの形を業務時間に組み戻す設計を置いていないと、8.3 の他のどの設計よりも早く予算会議で削られる。師弟設計を三要素で確定する。**其一、共働の時間割**——師匠の作業に弟子が随伴する時間（`modality:'working-together'` の Copresence、→前掲）を週次で固定し、この時間は生産時間ではなく**移転時間**として会計上区別する（移転時間の計上——知識労働の会計が「成果」しか載せないとき、伝承は常に名目上の仕事になる、→8.2 条件三）。**其二、随伴の非評価性**——随伴時間と弟子の産出を対応付けない（対応付けは即座に「見せるための作業」を生む——2.6 の処罰と名誉の条件の師弟版）。**其三、随伴の反転**——弟子が師匠に随伴するだけでなく、師匠が弟子の作業に随伴する設計（師匠の暗黙知が弟子の新語で更新される回路——site_coinations の供給者は師匠ではなく弟子であることが多い、→8.1 計器の読み）。

```cypher
// apprenticeship-ledger — 師弟の帳簿(伝承の流量計測・評価分離条約つき)
MATCH (s:Person {role:'master'})-[w:COWORK]-((d:Person {role:'apprentice'}))
WHERE w.started > datetime() - duration('P1Q')
WITH d, s, sum(w.hours) AS hours, collect(DISTINCT w.thread) AS threads
OPTIONAL MATCH (d)-[:AUTHORED]->(out) WHERE out:TermMappingProposal OR out:RuleAdoption
WITH d, s, hours, threads, count(out) AS apprentice_outputs
RETURN d.person_id, s.person_id, hours, apprentice_outputs,
       CASE WHEN hours < 4 THEN 'no-transfer-time'      // 帳簿上の随伴が実体ゼロ
            ELSE 'alive' END AS status;
// 読み: hours が低ければ伝承は予算化されていない(=存在しない)。
// apprentice_outputs が 0 なら随伴は形式で、暗黙知の更新は起きていない。
```

随伴の記録が thread（スレッド、→7.5 の状況の相関 ID）に紐づくことに注意せよ。師弟は抽象的な人間関係ではなく、**特定の状況連鎖への共同随伴**である——同一の障害・同一のライン・同一の変更（Commit、→2.5）に一上にに居ることが記録される。これにより、共観（→8.3 の同時閲覧）が事後の振り返りだとすれば、随伴は**状況の最中の共同注意**であり、暗黙知の伝導はここで最も濃く起きる（1.1 の補助覚知の伝承は、言語化の前の共同注意で起きる——ポランニーの「模倣による学習」の実装）。師弟の帳簿が示すもう一つの計器は `no-transfer-time` の分布である——随伴が計上されない部署は、暗黙知の再生産が止まっている部署であり、そこでは形式知の文書だけが増えていく（増える文書・細る伝承——知識のインフレはいつも、この分布から予見される）。

最後に、師弟設計への最頻の反論を潰しておく。「師匠が忙しい」。その通りで、だからこそ師弟は**善意ではなく会計**で守られる（→8.2 条件三）。移転時間という勘定科目を作り、随伴時間を成果評価から隔離し、師匠の随伴時間を成果指標の分子に載せる（分子に載る時、時間は実在する——→4.1 の宣言と実測の設計版）。この三つの会計設計を置かずに「メンター制度」を立ち上げる組織は、スティグレールの予言を自腹で証明する実験を毎期行っていることになる。

### 誰と見るか — 共在の割り当てと「見方が違う人」を選ぶ算法

8.3 の共観（CoproSession・COEXISTS_WITH、→前掲）は、「誰と共在するか」の割り当てが設計されていなければ、席の空いた会議になる。割り当ての原則を三条置く。**其一、見解の距離**——COEXISTS_WITH の辺に付与された viewpoint の標签（現場・保全・品質・安全・外部請負）の組み合回数を台帳化し、**共在経験の最も遠い pair を優先**に共在セッションを組む（遠い人と同じものを見る——Nonaka の externalization が最も摩擦を生む場所であり、摩擦は知識の入口、→1.1 の暗黙知が現れるのは言叶が合わない時）。**其二、歴史の接触**——自己の判断の結果（→8.2 パネル）を他人が見に来る相手を、LED_TO のグラフから自動推薦（「あなたの同意が変えた规則を、その规則で作業する人が見たいと言っている」——見解の接触を抽象の共在でなく因果の共在にする）。**其三、周期の同席**——落日審議・障礙審議（→3.4）に出席歴史のない人を自動で1名招待（参加資格は級でなく抽签——L0 の発言級が出席級と一致する設計、→2.6）。

```cypher
// co-presence-pairing — 見解距離による共在の推薦(月次)
MATCH (a:Person)-[:HOLDS_VIEWPOINT]->(va), (b:Person)-[:HOLDS_VIEWPOINT]->(vb)
WHERE a <> b AND va <> vb AND NOT ((a)-[:COWORK]-(b))
WITH a, b, va, vb,
     size([(a)-[:PARTICIPATED_IN]->(:Thread)<-[:PARTICIPATED_IN]-(b)]) AS shared
WHERE shared = 0   // 接触歴史ゼロ=最も遠い pair
RETURN a.person_id, va.tag, b.person_id, vb.tag
ORDER BY rand() LIMIT 4;   // 推薦(強制しない)——共在は自由でなければならない
```

`rand()` と「推薦」の明記を重要として置く。割り当て算法が共在を**強制**した瞬間、共在は劳動になり、聖域规則（→前掲:copresence に KPI を繋がない）が算法によって内側から破られる。算法は招待まで、受容は人間の自由——**暗黙知の場は、強要された席では開かない**（1.3 の巴——場所は開かれるもので、設置されるものではない。設置できるのは招待と時間と評价の排除まで、→8.2 条件三の時間予算が共在の物質条件）。

### 実行練習

1. あなたの現場で最後に「共に同じものを見て、言葉にならないものを共有した」瞬間を1つ思い出し、その条件（場所・時間・人数・記録の有無）を分解せよ。分解した条件のうち、8.3 の三要素（同時性・併置・沈黙）に対応しているものを特定し、残る欠落から共観セッションの最小設計（1スレッド2人15分）を1つ立てて試行せよ。
2. `sanctuary.rego` をあなたの分析基盤（BI・ログ解析・検索索引）に当て、現在の「善意の分析」が避難所を持つデータ（会話ログ・メモ・チャネル）に既に触っていないかを監査せよ。触っている実例を1件特定し、索引外し（条約G の労働版）の級と移行期間（→2.6 沈黙の猶予の類推）を決め、現場への告知文を100字で書け。
3. 暗部地図をあなたの業務領域で1枚描け（横軸に形式化密度＝承認件数・監査ログ密度、縦軸に共観密度＝雑談・同席・合同巡回の実測推定）。暗部が最も細っている領域について、それは「管理が行き届いた良い領域」か「未知が育っていない危険領域」かを両論書き、8.1 第四段（回復不能）の観点で最終判定と級つき対処案を出せ。
