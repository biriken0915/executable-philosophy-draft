## 7.4 マルチエージェント編成 — LangGraphで判断の流れを作る

処方層まで敷いた（→7.3）。次は実行の編成である。ただし本書の「マルチエージェント」は、AI 人格を並べて会議させる話ではない——**判断の連鎖を、異なる信頼級・異なる時間予算・異なる権限を持つ計算段に分割し、その間を形式化された会話で繋ぐ**ことである。ツールとして LangGraph を選ぶ理由は、それがまさにこの分割のフレームワークだからだ——状態グラフ（StateGraph）で計算（ノード）と制御（辺）を分離し、人間の介入点（interrupt）と永続化（checkpointer）を一級の概念に持つ。LangGraph のドキュメントが強調する通り、エージェント向けのグラフは「ループ・永続化・human-in-the-loop」のためにある（→5.5 のステートマシンとの接続は明記する：LangGraph は状態機械の計算機である。本章の設計命令——ガードは決定論、LLM は候補生成のみ——は LangGraph 上でもそのまま有効である）。

### 状態グラフ — 節点=計算、辺=制御

LangGraph の基本語彙を本書の設計語彙へ翻訳する。**State**（共有される型付きデータ。TypedDict/Pydantic で宣言し、ノードはこれを読み書きする——**状態はグラフの一等市民**であり、5.5 の状態（スナップショット）と意味は同じ）。**ノード**（状態を受けて計算し、状態の部分的更新を返す函数。ノードは辺を知らない）。**辺**（固定遷移と条件分岐。条件辺の述語は**決定論でなければならない**——→5.5 のガード命令の LangGraph 版。`add_conditional_edges(router)` の router 函数に LLM を入れてはならない）。**checkpointer**（各スーパーステップ後の状態の永続化——履歴代数の計算機、→2.5。中断・再開・タイムトラベル（過去状態からの再生）がフレームワークの基本機能である事実は、本書の歴史代数の設計とちょうど噛み合う）。

ここで本章の中心図を置く。四エージェントの分離である。

```
[観測] --deterministic--> [提案] --deterministic--> [検証] --deterministic--> [決定(人間)] --deterministic--> [実行]
  SensorAgent              ProposeAgent            VerifyAgent               interrupt()            ActAgent
  (計算・決定的)            (LLM 許容)              (Rego+SHACL+sat 決定的)   (JudgmentEvent)         (API・決定的)
```

四段の分離の理由を、信頼級で明記する。**観測**：決定的計算（テレメトリの正規化、→1.2、状況照会 `enabled_actions`、→7.3）。**提案**：LLM が唯一関与を許される段（候補生成のみ、→5.4 の PureLlm・Candidate 型・env digest）。**検証**：決定的計算（6.4 Rego・6.5 SHACL・4.5 sat の三層ゲート、→6.5 の gate_pipeline）。**決定**：人間の interrupt——承認ではなく**判断**（→5.1 の実効的承認：根拠の再検証可能な形で提示する）。**実行**：決定的計算（現場 API 発火、effect_verification 接続、→7.3）。

分離の核心は、**LLM が検証・決定・実行のノードに物理的に入れない**ことである（→5.5 の「遷移関数の内側の候補生成のみ」のグラフ実装）。LLM が検証ノードに入れないことは、自分の生成物を自分で通せる構造（司令塔化の最も密な形）を排除する。LLM が router（辺）に入れないことは、制御の決定論（→5.5 ガード命令）を守る。

### 実装 — LangGraph による四段グラフ

```python
# orchestration.py — 四エージェント分離の LangGraph 実装(決定論的辺・LLM は提案段のみ)
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.types import interrupt
from llm_wrapper import PureLlm, LlmEnv          # 5.4 の部品
from gate_pipeline import gate                    # 6.5 の三層ゲート
from ontology_query import enabled_actions        # 7.3 の候補照会

class Flow(TypedDict):
    situation: dict            # 正規化された状況(観測段の産物)
    candidates: list[dict]     # Candidate dict(env digest 込み、→5.4 provenance)
    verdicts: list[dict]       # ゲート判定(通過・violations・warnings)
    decision: dict | None      # JudgmentEvent リンク(人間判断)
    exec_result: dict | None
    clock: dict                # 段別時間予算の実測(→7.2 の内側時計)

def n_observe(s: Flow) -> Flow:
    sit = normalize_telemetry(s["situation"])          # 決定的
    sit["open_actions"] = enabled_actions(sit)         # 7.3 の候補照会(決定的)
    return {**s, "situation": sit}

def n_propose(s: Flow) -> Flow:
    llm = PureLlm(transport); env = LlmEnv(model_ref=ENV_MODEL, temperature=0.2,
                                           seed=42, sys_prompt_version="v9")
    cands = [c.model_dump() for c in candidate_pipeline(   # 5.4 の pipeline
        llm, KB, prompt_for(s["situation"]), env)]
    return {**s, "candidates": cands}                  # ← LLM はここでだけ触れる

def n_verify(s: Flow) -> Flow:
    vs = [gate(c, GRAPH, SHAPES, policy_input(s, c), sat_of(s, c))
          for c in s["candidates"]]                     # 6.5 三層ゲート(決定的)
    return {**s, "verdicts": vs}

def router_after_verify(s: Flow) -> Literal["decide", "quarantine"]:
    # 辺の述語は決定論(→5.5 ガード命令)。LLM 判定を制御に入れてはならない。
    return "decide" if any(v["stage"] == "pass" for v in s["verdicts"]) else "quarantine"

def n_decide(s: Flow) -> Flow:
    # 人間の判断点を interrupt で開く(承認ボタンではなく判断の皿、→5.1・8.5)。
    payload = {   # EvidenceBundle 相当(→5.3): 候補・根拠・却下理由・反証条件
        "candidates": s["candidates"], "verdicts": s["verdicts"],
        "rejected": [v for v in s["verdicts"] if v["stage"] != "pass"],
        "evidence_panel": panel_url(s),                 # 再検証可能性の実体(→8.5)
    }
    d = interrupt(payload)               # 停止→checkpointer が保存→人間応答で再開
    return {**s, "decision": d}

def n_act(s: Flow) -> Flow:
    if not s.get("decision") or not s["decision"].get("approved_action"):
        return s                          # 判断なしで世界は変わらない(設計不変条件)
    r = fire_api(s["decision"]["approved_action"])      # 決定的実行
    return {**s, "exec_result": r}

def n_quarantine(s: Flow) -> Flow:
    rec = quarantine(s["candidates"], s["verdicts"])    # 5.6 の Quarantine(残余保存)
    return {**s, "verdicts": s["verdicts"] + [{"stage": "quarantined", "q": rec.q_id}]}

g = StateGraph(Flow)
for name, fn in [("observe", n_observe), ("propose", n_propose), ("verify", n_verify),
                 ("decide", n_decide), ("act", n_act), ("quarantine", n_quarantine)]:
    g.add_node(name, fn)
g.add_edge(START, "observe"); g.add_edge("observe", "propose")
g.add_edge("propose", "verify")
g.add_conditional_edges("verify", router_after_verify,
                        {"decide": "decide", "quarantine": "quarantine"})
g.add_edge("decide", "act"); g.add_edge("act", END)
g.add_edge("quarantine", END)
app = g.compile(checkpointer=PostgresSaver.from_conn_string(CPN),
                interrupt_before=[])   # interrupt() 内蔵割込で止まる
```

設計不変条件の二重化に注意せよ（→5.6 と同じ構造）。`n_act` 冒頭の「判断なしでは世界は変わらない」に加え、`n_decide` が interrupt で**人間の応答そのものを state に載せる**——checkpointer により、停止中の状態と再開後の判断が履歴として残る（タイムトラベル機能は、→4.5 の counterfactual の実行版である：過去 state に戻り、別分岐を再生して比較できる。監査と教育の両方で使える——→8.6 の練習設計）。

### 「司令塔なき編成」の会話プロトコル — 候補・根拠・反証の形式

四段は会話する。その会話の形式が、司令塔なき編成の条件である——**どの段も他の段に命令できず、形式付きの差し出ししかできない**。提案段は検証段へ命令できない（候補を渡すのみ）、検証段は決定段へ命令できない（判定と missing を渡すのみ）、決定段は実行段へ「どの候補か」しか渡さない（方法の細部は Action ノードの宣言が担う、→7.3）。会話メッセージの最小形式を Pydantic で置く。

```python
# message_format.py — エージェント間会話の形式(候補・根拠・反証の三つ組)
class Exchange(BaseModel):
    """段の間に流れる唯一のメッセージ型。命令(kind='order')が存在しないことに
    注目せよ——形式が権限を表現している(→5.4 Candidate に apply がないのと同型)。"""
    kind: Literal["candidate", "verdict", "evidence", "counter-evidence", "judgment"]
    sender: str                      # ノード名+policy 版数(話者の資格の登記)
    reply_to: str                    # どの差し出しへの応答か(会話の因果連鎖)
    payload: dict                    # candidate は provenance 必須、verdict は missing 必須
    dissent: str | None = None       # 不服従の表明(6.2 の dissent が会話形式に常住)
```

`kind='order'` が型系に**存在しない**こと——これが「司令塔なき編成」の定義である。権限はグラフの辺（制御）とゲート（方針）にのみ住み、メッセージ語彙には命令がない。人間から機械へも `judgment`（コミットメント）であって `order`（方法の命令）ではない——ミッション・コマンドの会話版（→7.2 の意図ベース指揮が、メッセージ型の設計に落ちる）。`dissent` の常置も 6.2 の均衡装置の会話版で、dissent を含む Exchange は履歴代数に載り審議槽へ供給される。

### 失敗の編成 — 各段の失敗の安全な受け

各段の失敗モードと、グラフ上の受けを対応表で閉じる。観測段の失敗（テレメトリ欠損）→ `enabled_actions` の候補ゼロ → Quarantine エンド（→5.4 の候補ゼロ宣言）。提案段の失敗（LLM タイムアウト・schema 外）→ 候補ゼロ宣言＋漂移記録（→5.4 repro_check）。検証段の失敗（判定 UNKNOWN）→ horizon 記録つきの Warning 通過か、goal の `decision_budget_sec` 超過で Quarantine（→3.5 の UNKNOWN 扱い）。決定段の失敗（人間応答なし）→ **time-boxed interrupt**：時間予算内で応答なければ、安全側既定（`risk_class: high` の候補は実行しない＝Quarantine で停止、low risk の通知のみ実行可——既定値は E4 宣言で、期限つき、→4.1・6.6 の落日）。実行段の失敗（API 失敗）→ effect_verification 突合で `effect-missing`（→7.3）→ 再提案ループ（グラフの辺を quarantine→observe に戻すオプション、→7.6 で解禁）。

注意すべきは決定段の「人間応答なし」の設計である。**人間を待たせることを安全策と思い込んではならない**——無限待ちは時間劣位の自己受注（→7.2）で、現場が影子の判断（承認なしの場当たり）へ流出する（→6.6 影子 KB の判断版）。time-boxed interrupt の予算配分（何を待ち、何を既定で安全側へ置くか）は、→8.4 の人間配置設計そのものである。

### LangGraph の故障三型 — checkpoint・loop・interrupt

委任パイプライン（→前掲の LangGraph 実装）の故障を三型で inscribe する（A.4 障害目録六・七の 7 章詳述）。**故障一：checkpoint 消失**。checkpointer の thread_id が段で違い、resume が初めから再走——初めから走ると**人間の承認セグメントが再次走らない**（interrupt は恢復されない、承認は 1 回限りの簿記——承認の再走禁止は 8.5 の単一同意原則と同一）。処方：thread_id の一本化断言（→A.4 五条）＋ resume 時に「承認済みセグメントの再走ゼロ」の assert（checkpoint に `approved_segments` 列表）。**故障二：loop 爆炸**。条件分岐が障礙で戻る辺を持ち、障礙解決→再試→同障礙→再試の環（7.2 の clock と loop の冲突）。処方：段総数上限（graph に `max_supersteps`）＋環の回数を障礙の実例に数え載せ、2 回目で Quarantine（**環は障礙で、障礙は席を持つ**——3.4 の障礙台帳がループ検測の届け出先、検査と席の接続）。**故障三：interrupt 宙吊り**。人間猶予（→8.5 hold_seconds）が切れた場合の黙認動作が未宣言——graph が停止したまま無事を装う（沈黙の破れ三、→5.2 の透明化のパイプライン版）。処方：interrupt に `on_timeout` を強制（デフォルトは安全側 demote＝7.6 の自動降格。猶予切れ=承認拒否と書く——8.5 の「無応答は同意でない」の graph 実装）。

三型の共有項：いずれも**パイプラインが止まる/戻る/消える故障で、世界には何も起きない**こと——つまり故障そのものは安全側（安全不変条件 5、→7.6 の世界変更ノード不動）。危険は故障でなく**故障の処理**にあり、loop の再試が障礙を無視して回し、宙吊りが無事として落日をすり抜ける。よって三型のテスト（test_loop_escape・test_interrupt_timeout）は段昇格条件に載せる（→7.6 段昇格条件に「故障テスト通过」が預めって載る理由）。

### 実行練習

1. `orchestration.py` を自分の領域の業務1本に書き換え、`n_propose` 以外のノードに非決定的要素が入っていないかを lint で検査せよ（禁止 import 検査：`llm_wrapper` の import を propose ノードのファイルに限定する grep/AST テストを1本書け）。
2. `Exchange` の `kind` に `order` を追加する変更がなぜ「設計変更でなく憲法変更」かを1段落で論じ、追加を防ぐ CI 検査（Literal 型の値集合スナップショットテスト）を1本書け。さらに `dissent` を常に None で送る運用が腐敗二（→6.6 槽を空けない権力）とどう同型かを結べ。
3. time-boxed interrupt の時間予算をあなたの業務3場面で決め、各場面の「安全側既定」を1文ずつ書け。その後、4.5 の counterfactual と LangGraph のタイムトラベルを使って「人間が2時間遅く承認した場合」の再生手順（checkpointer の thread_id 操作）を5行で書け——**遅れの反実仮想が定量化できる**ことが、予算設計（7.5 の SLA）の根拠になる。
