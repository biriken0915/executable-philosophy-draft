## 3.5 FOL実践 — ゴール展開木と障害の一階述語論理コード

障礙は ¬G として定義され、障礙分解は ¬G の論理分解に一致する（→3.4）——この節ではその「一致」を、実行可能な Python + z3-solver のコードにする。z3 は SMT ソルバ（satisfiability modulo theories）であり、FOL の断片（本書では線形整数算術＋quantifier-free）の充足可能性を決定する。要求の木を z3 の論理式として再帰構築し、葉（要求・仮定）からの充足を判定し、障礙の網羅を unsat 証明で検査し、最小障礙セットを unsat core と反例列挙で得る。節の後半では、この手法の限界——FOL 全体の決定不能性——を隠さず書く。**限界を隠す形式化は偽りの形式化であり、限界を登記した形式化は誠実な工学である**（→4.1）。

### 論理の選択 — なぜ z3 で、どこまで z3 に頼るか

完全な FOL は決定不能である（Church の定理）。任意の FOL 文の充足可能性を判定するアルゴリズムは存在しない。よって本書の判定器は常に**限定された断片**上で動く。使う theories はつぎの三つに限定する。

1. **線形整数算術（LIA）**：時刻・振動値・閾値・回数。`vib(m,t) ≥ thr(m)`、`t' - t ≤ 300s`。
2. **boolean の組合せ＋有限 quantifier**：機械台数・時点数が有限なので、quantifier は unrolling で消せる（→3.3 の時間窓 unrolling と同じ手）。
3. **datatype（列挙）**：Shift 型、故障コード、EARS 五型。

LTL は時点の有限系列に unrolling して LIA+bool に落とす（bounded model checking の要求版）。unrolling 境界 `T_MAX` と機械数 `M_MAX` は、判定の**有効範囲**であり、要求の木に `verification_horizon` プロパティとして登記する。範囲外の違反は発見されない——この不在の登記が、形式検証を占星術から区別する唯一の部品である。

### 骨格実装 — GoalTree の再帰構築と充足判定

要求の論理は「葉の要求 R と仮定 A が AND で結ばれ、各内部ノード G が子ゴールの conjunction で含意される」という構造である。充足判定の本体は一つ——**`A ∧ R ∧ ¬G_root` が unsat なら充足**（仮定と要求の下で、root ゴールの否定は起こりえない）。

```python
# goal_tree_sat.py — 要求木 z3 充足判定器 (本書の第2部の心臓部)
# 哲学: 充足 = 「要求と仮定を書き換えない限り、goal 違反の世界は存在しない」
# という存在論的不可能性の機械証明である(→4.5 の sat=存在証明 と対).
from __future__ import annotations
from z3 import (Solver, Ints, Int, And, Or, Not, Implies, sat, unsat,
                Optimize, Function, Bool)

class Goal:
    def __init__(self, name: str, formula, children: list[Goal] | None, kind: str):
        self.name, self.f, self.children, self.kind = name, formula, children, kind

class ReqTree:
    def __init__(self, root: Goal):
        self.root = root

    def leaf_formulas(self, g: Goal) -> list:
        if g.children is None:                 # 葉 = requirement or assumption
            return [g.f]
        out = []
        for c in g.children:
            out += self.leaf_formulas(c)
        return out

    def check_satisfaction(self) -> tuple[str, dict]:
        # (1) 分解の内部論理チェック: 各 AND ノードで children ⊨ parent が成立つか
        for g in self._internals(self.root):
            s = Solver()
            kids = And(*[self.expand(c) for c in g.children]) if g.kind == "AND" \
                   else Or(*[self.expand(c) for c in g.children])
            s.add(kids, Not(g.f))
            if s.check() != unsat:
                return f"decomposition-gap@{g.name}", s.model()
        # (2) 要求充足: 葉(要求∧仮定) ∧ ¬root が unsat か
        s = Solver()
        s.add(And(*self.leaf_formulas(self.root)), Not(self.expand(self.root)))
        if s.check() == unsat:
            return "SATISFIED", {}
        return "COUNTEREXAMPLE", s.model()

    def expand(self, g: Goal):
        """goal の定義式を、子の式へ展開した論理式として返す(再帰)。"""
        if g.children is None:
            return g.f
        kids = And(*[self.expand(c) for c in g.children]) if g.kind == "AND" \
               else Or(*[self.expand(c) for c in g.children])
        return And(g.f, kids)

    def _internals(self, g: Goal):
        if g.children is None: return []
        out = [g]
        for c in g.children: out += self._internals(c)
        return out
```

### 保全現場の例 — 4ノードのゴール木で本当に unsat が出るか

3.3 の例（夜間・振動→5分以内点検）を境界付きの有限世界で埋める。時点は 0〜2（Δt=3分）、機械は m1 のみ、振動値は整数 mm/s（0.1mm/s 単位で10倍整数化——LIA の分数回避、境界設定の一例）。

```python
# demo_night_inspection.py
v  = Int("vib_t0");  v1 = Int("vib_t1");  v2 = Int("vib_t2")
ins = [Bool(f"inspect_t{i}") for i in range(3)]
# 環境仮定(assumption): センサーは各3分窓で1回サンプリング(vib は窓の最大値)
A = And(v >= 0, v1 >= 0, v2 >= 0)
# 要求(葉の requirement): 検知ノードは 3分ごとに評価し、検知時 inspect_t_i を立てる
R = And(Implies(v  >= 45, ins[0]),
        Implies(v1 >= 45, ins[1]))
# root goal: 検知から5分(=2窓の unrolling 近似: 3分窓2つ=6分<5分近似は粗い。
#           境界が要求より粗いことを verification_horizon に登記する)
G = Implies(v >= 45, Or(ins[0], ins[1]))

root = Goal("G-inspect-6min", G, [
    Goal("R-detect", R, None, "REQ"),
    Goal("A-sampling", A, None, "ASMP")
], kind="AND")

t = ReqTree(root)
print(t.check_satisfaction())
# ('COUNTEREXAMPLE', model(v>=45, ins[0]=False, ins[1]=False)) — ではなく、
# R が Implies なので model は ins を自由に残す: COUNTEREXAMPLE が出る!
```

**このデモの故意の失敗が本章の核心である。** 上の結果は COUNTEREXAMPLE を返す。なぜか——要求 R は「検知時に inspect を立てる」を意味するが、z3 の model は `v < 45` を選んで implication を空に真（vacuous）にできる。要求は「振動が上がったすべての世界」を強制していない。世界全体（環境条件）を仮定側で与え忘れたためである。

```python
# 修正: 世界制約(振動は実際に上がった)を仮定へ加える。
A2 = And(A, v >= 45)          # 事例世界: 夜間で実際に振動異常が起きた
# → このとき unsat が出るか? R の ins[0] 強制と G の Or(ins0, ins1) から unsat。
```

修正後は unsat——「仮定 A2 と要求 R の下で、goal 違反は存在しない」の証明。要求充足の証明が、要求の木と世界の記述の**両方**に依存することが、このデモの教訓である。充足論証 `sat(A ⊧ R ⇒ G)` の A を薄く書くと充足は空に強くなる（→3.3 の vacuity 検査がここでも発火する）。

### 障礙の網羅検査 — ¬G の覆い込みを unsat で判定する

障礙 O₁..Oₖ が ¬G を覆っているか（網羅性）は、`G ∧ ¬O₁ ∧ ... ∧ ¬Oₖ` が unsat（G と「障礙ゼロ」が共存不能）であること。覆い漏れ（gap）がある場合、solvable モデルが「障礙がないのに goal が壊れた世界」——障礙分析の穴——として返る。このモデルは 3.2 の `gap_witness` に登記される（→3.3 の分解正当性検査と対）。

```python
def obstacle_coverage(g_formula, obstacles: list) -> dict:
    s = Solver(); s.add(g_formula)
    for o in obstacles: s.add(Not(o))
    r = s.check()
    if r == unsat:
        return {"coverage": "COMPLETE"}
    m = s.model()
    return {"coverage": "GAP", "gap_witness": m,
            "reading": "障礙ゼロで goal 違反が起きうる世界が存在する。障礙分解の漏れ。"}

# 障礙ノードの相互重複(二重計上)は sat 両立で測る:
# O1 ∧ O2 が sat なら独立でない(3.4 の CO_CAUSED の論理的根拠)
```

障礙の AND/OR 分解の「正しさ」は二方向からサンドイッチできる——上位障礙の定義（論理式）が子の conjunction と論理同値か（双方向 implication の unsat 検査）を、全エッジで検査する。同値でなく `O_top ⇒ ∨O_children` だけが成立つ場合、逆方向の失敗（子のどれかが起きても ¬G に届かない）は「障礙葉が ¬G より強い」過剰分解で、実害は過剰警戒（False Positive を設計に焼き込む）。過剰分解と過少分解を区別して報告する——報告の粒度が、そのまま対策のコスト配分になる。

### unsat core の実務 — 「どの要求が衝突しているか」の読み方

要求増分同士の矛盾（3.2 の「矛盾が場所を得る」の機械形）は、unsat core で読む。core とは unsat を作る最小仮定集合であり、衝突している要求（または要求＋仮定）の名簿そのもの。

```python
def conflict_roster(requirements: dict[str, any]) -> list[str]:
    s = Solver()
    named = {}
    for name, f in requirements.items():
        b = Bool(f"dep_{name}")
        s.add(Implies(b, f)); s.add(b); named[b] = name
    if s.check() != unsat:
        return []                                  # 矛盾なし
    core = s.unsat_core()
    return [named[b] for b in core if b in named]  # 衝突要求の名簿
```

読み方の実務注：unsat core は衝突**候補**の最小集合であり、唯一の犯人ではない（別の要求を削っても解決しうる）。衝突解決の選択（どれを削るか）は telos の優先（3.2 の softgoal 木）で決まり、論理では決まらない。論理が名前を渡し、人間が級を決める——5章以降の reckoning/judgment 分離が、もうこの小さな関数で発火している。

### 決定不能性の登記 — verification_horizon を要求の木に書く

最後に、本章全体の誠実さを担保する登記コードを置く。z3 は非決定停止しうる（quantifier -heavy な定式、非線性算術）。タイムアウトと未決定は、**結果の缺失**ではなく**結果の種類**として扱う。

```python
from z3 import set_param, Solver, unknown

def bounded_check(tree: ReqTree, horizon: dict, timeout_ms=10_000):
    set_param("timeout", timeout_ms)
    verdict, detail = tree.check_satisfaction()
    if verdict.startswith("unknown") or detail is None:
        # 未決定を要求ノードへ書き戻す(登記された未知 = 限定付き既知)
        return {"verdict": "UNKNOWN@horizon",
                "verification_horizon": horizon,     # T_MAX, M_MAX, Δt
                "obligation": "manual review L2",    # 手動レビューへの自動エスカレーション
                "recheck_by": horizon["review_due"]}
    return {"verdict": verdict, "verification_horizon": horizon}
```

`UNKNOWN` を例外で落とさない設計（verdict として型で持つ）を強調する。未決定の扱いを設計した判定器は、限界の登記を要求木の一級の性質（`verification_horizon`）として産む。限界が要求の属性になったとき、形式検証は無限の約束から**期限付きの契約**へ変わる（→4.4 の Design by Contract は、この契約性を要求分析の全へ拡張する）。

### FOL→z3 の穴二つ — 量化と領域の落とし方

障礙の充足検査（→前掲の z3 利用）で、正しく見えて最常見に壊れる二つを inscribe する。**穴一：量化の爆発**。`ForAll(equipment, ...)` は設备実例の有限集合で grounded に書ける（Python ループで And/Or を展開）が、展開を恐れて z3 の量化に書くと quantifier 消去が走らず unknown になる。**原則：実例集合が既知なら量化は展開する**——世界が有限な限り量化は機械的に扱える（3.2 の実在的完全性の宣言が、量化の展開可能条件を給える:「集合は完全です」と宣言された集合でのみ展開は正当。未知の成員は展開に現れない=世界は開いている、→3.2 の開き宣言の z3 版）。**穴二：整数と実数の取り違え**。振動値の実数演算に Int 型を使うと、境界条件（`vib >= 4.2` の 4.2 が 4 に切捨てられ、境界の test が假に通る——**型は境界を偽装する**）。E1 実測級の境界値を E2 見通し級で書く際の型宣言（Real/Int/FiniteDomain）は、4.1 の級の字段の一部である（実測は実数、計数は整数——数字の型を世界側から決まらせる、→4.4 の不変条件テストで境界値 3 点（下・境界・上）を強制する理由）。

```python
# grounded quantifier — 既知集合の量化は展開(→3.2 完全性宣言のある集合のみ)
def forall_known(items, body):
    return And([body(x) for x in items])   # z3 の ForAll に書かない
```

unknown が返った時の処理は 3.5 の三段構え（UNKNOWN 登記→人間審議）をそのまま使う——**求解器の unknown は障礙ではなく、求解器の側の落日対象**（モデルの量化設計が老朽した、z3_gate の test に量化爆発の回帰を追加、→A.4 障害目録七）。
