## 4.3 RETROFIT-CQs — レガシーから能力質問を逆抽出する

4.2 で CQ は「先に書く仕様」だと述べた。では、先に書かれずに20年生きてきたシステムはどうか。既存の業務データベースのスキーマ、公開済み API、十年分の SQL ログ——これらはすべて、**答えを持っているのに質問を忘れている**知識である。本書の語彙で言えば、レガシーシステムは第三次的保持の巨大な塊である（→2.3）——運用を規定するが、その根拠を内側に持たない保持。この節では、CQ 法を逆向きに走らせる：実データと実クエリから、そのシステムが実際に答えてきた質問（＝実際に載っていた知識）を逆抽出する。この操作を本書では retrofit-CQ 抽出と呼ぶ。抽出物は 4.2 の CQ 三つ組へ昇格させ、**昇格させなかった残余は 1.6 の NonRecordingRule の設計判断として明示的に宣言する**——この二方向（抽出と残余宣言）がセットでなければ、レガシー分析はまた新しい脱知識化になる。

### なぜ「逆抽出」が可能なのか — クエリログは投票用紙である

抽出の論理的根拠を先に固める。SQL/GraphQL/Cypher のクエリログは、運用中の組織が発射した**質問の記録**である。10年間同じ形のパラメータ化クエリ `WHERE dept=$1 AND shift=$2` が走り続けていたなら、それは「部署×シフトで切った集計が要る」という CQ が、仕様書ではなく投票で選出されていたことを意味する。クエリログは投票用紙の山である。 retrofit-CQ 抽出とは、その開票である。

三つのデータ源と、各が開票する情報の性質を整理する。

| 源 | 開票されるもの | 弱点 |
|---|---|---|
| スキーマ（DDL/ER図） | 載る知識の**形式**（構造・結合・型） | 問いは現れない（構造だけ、目的なし） |
| API 契約（OpenAPI/GraphQL SDL） | 公開された**答えの形**（応答スキーマ） | 内部結合の動機が不明 |
| クエリログ（SQL/Neo4j query.log） | 実際に問われた**質問と結合経路** | ノイズ・自動化された反復と手動探索の混在 |

スキーマは形相因、API は公開された答、ログは動力因の行動痕跡——3.1 の四原因がここでは別々の出土品になる。統合（triangulation）が抽出の本体である。

### 抽出パイプライン — ログからの CQ 発掘スクリプト

本書の中核実装を Python で置く。入力はこの10年で最も汎用性が高い形式（SQL テキストログ）、出力は 4.2 の `CompetencyQuestion` 三つ組の下書きである。

```python
# retrofit_cq.py — クエリログからの CQ 逆抽出(テンプレート正規化+投票集計)
# 哲学: 同じ形質のクエリの「出現回数」は、その知識の運用での存在感の代理指標である。
# 頻度で上位 CQ を選ぶことは、仕様を投票で復元すること。投票は知識政治の履歴である(→4.2)。
import re, json, collections
from collections import Counter

NORM = [
    (re.compile(r"\b\d+\b"), "$num"),                    # 数値リテラル→変数化
    (re.compile(r"'[^']*'"), "$str"),                    # 文字列リテラル→変数化
    (re.compile(r"\s+"), " "),
    (re.compile(r"\bin \((?:\$num|\$str)(?:, ?(?:\$num|\$str))+\)"), "in ($set)"),
]

def normalize(sql: str) -> str:
    s = sql.strip().lower().rstrip(";")
    for pat, rep in NORM:
        s = pat.sub(rep, s)
    return s

def extract_tables_joins(sql: str) -> tuple[frozenset, frozenset]:
    tables = frozenset(re.findall(r"\b(?:from|join)\s+([a-z_][\w.]*)", sql.lower()))
    joins = frozenset(re.findall(r"\b([a-z_][\w.]*)\.(\w+)\s*=\s*([a-z_][\w.]*)\.(\w+)", sql.lower()))
    return tables, joins

def mine_queries(log_lines: list[str]) -> list[dict]:
    tpl = Counter()
    meta: dict[str, dict] = {}
    for line in log_lines:
        sql = json.loads(line)["sql"]
        n = normalize(sql)
        tpl[n] += 1
        t, j = extract_tables_joins(sql)
        m = meta.setdefault(n, {"tables": set(), "joins": set(), "sample": sql[:120]})
        m["tables"] |= t; m["joins"] |= j
    out = []
    for n, count in tpl.most_common():
        if count < 5:                 # 単発クエリは探索であり投票ではない(後述)
            continue
        out.append({"cq_draft": n, "votes": count, **meta[n]})
    return out

# 使い方の例:
# rows = [open("query.log").read().splitlines()]
# for c in mine_queries(rows[0]): print(c["votes"], c["cq_draft"][:80])
```

実運用での正規化は本物であるほど雑多になる（コメント除去、CTE 展開、view 実体への解決）。本章の要点は実装の精緻さではなく、**出現回数=freq が CQ の重要度の代理指標として正当化できる条件**の宣言にある——手動探索クエリ（一人一回の試行）は投票ではない。`count < 5` の線引きは E4 宣言（→4.1）であり、`NonRecordingRule` の閾値設定と同じ性格の決定である。閾値を宣言せずに置いた抽出器は、「5回未満の質問は質問ではない」という脱知識化を暗黙に実行する（→2.1 の境界決定の暴力）。宣言する抽出器は、閾値の下に落ちた質問を `SubThresholdQuery` として別テーブルへ逃がし保存する。

### スキーマとの照合 — 答えてきた質問と載っている構造の断層

抽出した CQ ドraftと、DDL を照合すると、三型の断層が現れる。この断層解析こそ retrofit の目的である。

**断層A（載らず問わerず）**：CQ ドraft が参照する結合が DDL に存在しない（アプリ側 JOIN 補完）。アプリの結合ロジックがオントロジーの隠れ層になっている——**知識がコードに沈んでいる**（→1.5 のラベル論の逆像：コードがラベルを引き受けている）。

**断層B（載って問われず）**：DDL の結合・列で、10年のログに一度も現れないもの。載っているが問いのない知識。4.2 の孤立 CQ と双対の、**孤立構造**である。意味を失った構造は、スキーマの墓標である（→2.5 の墓標クエリの DDL 版）。

**断層C（問われ続けて載っていない）**：ログの `joins` がアプリ名（`orders.cust_id = legacy_users.ko户_ban`）のような**意味不明語彙の結合**で埋まる。結合が生きているのに意味が不在——2.4 のマッピング事故の発掘現場。

```python
# fault_report.py — 断層三型の報告器(抽出 CQ × DDL クロス照合)
def fault_report(cqs: list[dict], ddl_tables: set, ddl_fks: set[frozenset]) -> dict:
    rep = {"A_sinked": [], "B_orphan_struct": [], "C_semantic_gap": []}
    used_fks = set()
    for cq in cqs:
        for j in cq["joins"]:
            fk = frozenset({(j[0], j[1]), (j[2], j[3])})
            used_fks.add(fk)
            if fk not in ddl_fks:
                rep["A_sinked"].append((cq["cq_draft"][:60], sorted(fk)))
    for fk in ddl_fks - used_fks:
        rep["B_orphan_struct"].append(sorted(fk))
    # C 型は結合先名簿の語彙検査(人名・顧客番号・現場略語が DDL 正規語彙に不在なら gap)
    for cq in cqs:
        for j in cq["joins"]:
            if j[1] in {"ko_ho_ban", "jiken_no2", "kanyu_cd"} or "_" not in j[1]:
                rep["C_semantic_gap"].append(j)
    return rep
```

`B_orphan_struct` の扱いが設計の分岐点になる。孤立構造を即削除するのは 2.4 の「載らないもの」の再発明である——問いが今はないだけで、問いは再生しうる（3.4 の `theoretical` 障礙と対称に、**theoretical な構造**は将来の問いの容器である）。よって本書の手順は、孤立構造を `RetiredStructure` として墓標登記し（deprecation、→2.4 の `owl:deprecated` 同型）、削除は 2.6 級 L3 の不可逆変更として沈黙の猶予（90日）を課す。墓標登記と即削除の差は、組織が過去の意味を資産と見るかゴミと見るかの分岐そのものである。

### API 契約との照合 — 公開された答えの形が漏らす前提

OpenAPI/GraphQL SDL は「外部に約束した答えの形」である。CQ ドraftの応答制約（4.2 の (c)）と突き合わせると、**契約が引き受けた前提**が抽出される。応答スキーマに `shift_code: string` があれば「シフトは符号で表される」が前提として契約に凍結されている。凍結の版数（API version）と凍結の変更履歴を結ぶと、**前提の履歴**が得られる——前提の変更がいつ、どの CQ の変化に追従した（あるいは追従しなかった）かが、retrofit の歴史層になる。

```json
// retrofit 統合後の CQ レコード例(断層情報つき)。この JSON が本章の出土品の最終形態。
{
  "cq_id": "RCQ-0017",
  "text": "部署×シフト別の逸脱件数を月次で列挙せよ",
  "origin": {"votes": 4211, "window": "2016-2026", "sources": ["query.log", "OpenAPI v2"]},
  "layers": {
    "formal": "MATCH (d:Drift)-[:OCCURRED_IN]->(s:Shift {dept:$dept}) ...",
    "answer_contract": "月 × 部署 × シフト × 件数。0件も返す(NOT NULL)。"
  },
  "faults": ["C_semantic_gap: kanyu_cd→Shift.type マッピング未定義(→2.4)"],
  "survivors": {"sub_threshold_queries": 87, "note": "87件の単発質問を SubThresholdQuery に保存済み。未来の CQ 供給源(→4.2 供給源(b))。"},
  "approval": {"class": "L1", "approved_commit": "urn:commit-0108"}
}
```

`survivors` フィールドを省かないこと。retrofit 抽出の成果物の真の価値は、上位 CQ の発掘以上に、**抽出の網から落ちた残余を保存している事実**にある。1.6 の NonRecordingRule が「記録しないことの設計」だったとすれば、retrofit の対概念は「記録から零れ落ちたものの設計」——残余の再入城である。第2部（意味の保存）と第1部（暗黙知の尊厳）が、この JSON の一行で接続する。

### 暗黙の CQ の発見法 — 運用ログからの逆抽出の完全手順

retrofit（レガシーから能力質問を逆抽出、→前節）の第三の源を、この節で実装する——**運用ログからの逆抽出**。コードもデータも語らないが、運用の詢問行動が語っている能力要求がある。運用者がグラフ・DB・ダッシュボードに実際に投げた質問の集合（Cypher ログ・SQL ログ・BI クエリの検索履歴）は、その系が**現実に応答するために使われている質問**の完全な目録であり、その中に設計文書に書かれていない CQ が眠っている。

手順四段。**(1) 収集**：クエリログを 90 日分、read-only で抽出（BI の利用統計も可——詢問の主体が人間であることの確認だけ必須、→5.1 の判断の簿記の照会版）。**(2) 正規化**：クエリの骨格（参照ノードラベル・関係類型・集計・フィルタ語彙）に正規化して重複統合——「誰が」「いつ」「どこで」の三語彙が反復するクラス、など。**(3) 突合**：既存 CQ 台帳（→4.2）と突合し、**文書にないのに運用で高频の質問**を新 CQ 候補として起票（起票権は L0——→4.2 の CQ 統治に接続）。**(4) 階級**：高频×高影响（質問が act の直前に投げられている——意思決定の直前の詢問は能力要求の重みが違う）で優先順位をつけ、TBox 変更の級つき審議に載せる（→2.6 の級運用）。

```cypher
// log-mining-cq — 運用ログからの CQ 逆抽出(Neo4j query log 例)
MATCH (q:QueryLog) WHERE q.at > datetime() - duration('P90d') AND q.read_only
WITH q.pattern_class AS cls, count(*) AS n,
     sum(CASE WHEN (:DecisionEvent {at: q.at}) IS NOT NULL THEN 1 ELSE 0 END) AS pre_decision
WHERE n > 40 AND NOT EXISTS { MATCH (c:CQ) WHERE c.pattern = cls }
RETURN cls, n, pre_decision, 'undocumented-capability' AS flag
ORDER BY pre_decision DESC, n DESC LIMIT 25;
```

（`pattern_class` は正規化 (2) の産物として前処理で作る列——完全な正規化実装は練習に委ね、**骨格の粗い正規化（ラベル集合＋関係名の集合のハッシュ）でも高频の隠れ CQ は十分掘れる**ことを経験として注記する。）

逆抽出の哲学的位置を確定して閉じる。CQ の正典化（設計者が書く CQ）は系が**答えたい**質問の目録であり、ログの逆抽出は系が**答えている**質問の目録である。両者の差分——答えたいにないのに答えている（系が設計外に使われている=現場が意味を作っている、→1.3 の語彙更新）、答えているにないのに答えたい（設計の夢が運用と接触していない、→4.2 の dormant の鏡像）——の二列が、そのシステムの**意味の実況中継**である（→2.3 の第三次保持の運用監査と同じ読み）。retrofit は過去を保存する作業ではなく、**過去が使われ続けていた意味を、現在の制定に接続する作業**である（→2.2 の止揚——差分計算としての継承の、要求工学における実装）。

### 実行練習

1. 自分のシステムのクエリログ（1日分でよい）を `mine_queries` に流し、`count<5` で弾かれたクエリを実際に5本人間が読んでみよ。その5本のうち何本が「将来の CQ になる芽」だったかを数え、閾値引き下げの判断を CQAmendment（→4.2）の形式で提出せよ。
2. `fault_report` の B 型（孤立構造）を1つ選び、即削除案と `RetiredStructure` 墓標案の比較表を作れ。比較の行に「削除後に問いが再生したときの復旧コスト（→2.5 の lost_meanings 照会の可否）」「スキーマ理解の保持（→2.3 の保持寿命）」を入れ、級 L3 の手続（→2.6）を適用したときどちらが勝つかを条文引用で決めよ。
3. `RCQ-0017` の `C_semantic_gap`（`kanyu_cd`→Shift.type）に対し、2.4 の `skos:closeMatch` ルールを1本設計し、4.6 の回帰テストに載せる形（「この結合を含む CQ は mapping を経由すること」）を Cypher + Pydantic の検査式で書け。
