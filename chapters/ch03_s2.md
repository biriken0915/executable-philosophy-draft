## 3.2 ゴール指向要求工学（GORE）と KAOS

目的の形式化が可能であり、かつ形式化しなければ目的が既定値で発火する——3.1 でこの二本の柱を立てた。この節では、目的を形式化して要求まで**演繹する**学問、goal-oriented requirements engineering（GORE）を本格的に導入する。中心人物は Axel van Lamsweerde である。彼の教科書 *Requirements Engineering: From System Goals to UML Models to Software Justifications*（2009）と、その方法的背骨である KAOS 法（京都大学発祥の要求モデム法。Kernel-Oriented Architectural Specification）が本章の道具立ての全部である。本章の「思想」節が van Lamsweerde をアリストテレスと並置するのは飾りでない。GORE は近代で初めて、目的因を工学の第一級概念として形式語義付きで再入城させた（→3.1 の定理の実装形）からである。

### GORE の転倒 — 「要求を書くな、ゴールから導け」

従来の要求工学が「要求文書」を起点にしたのに対し、GORE は起点を移す。要求（requirements）は起点ではなく**結論**である。起点はゴール（goals）であり、要求は「ゴールを、この環境仮定（assumptions）の下で、このエージェント（agents）に実装させれば成立つか」という構造的な演繹の結果として導かれる。この転倒の意味を三つ並べる。

第一に、要求文書の矛盾が消えるのではないが、矛盾が**場所を得る**。要求同士の矛盾は「両要求が同じゴールの AND 分解の葉にある」ときの障礙分析（→3.4）として現れ、ゴールの矛盾は上位木で検出される。矛盾がログではなく構造になる。

第二に、「なぜその要求か」が質問可能になる。要求ノードは上位ゴールへの充足辺（contribution link）を持つ。要求文書で「根拠」と言えば感覚的な散文だったものが、GORE では**充足関係の論理**——要求 R が環境仮定 A と組でゴール G を形式論理的に満たす（GORE の用語では *satisfaction argument*）——として書く。2.5 の履歴代数で `intent` が必須だったことの要求版がこれである。

第三に、変更の衝撃が計算可能になる。質料（レガシー資産）が変わり環境仮定 A が崩れると、A に依存していた satisfaction argument が切れ、依存ゴール群が「未充足」へ退行する。影響解析（impact analysis）が spreadsheet ではなく論理推論になる。

### KAOS の五階層 — ゴール・障礙・仮定・要求・エージェント

KAOS のオブジェクト体系を本書の語彙で敷設し直す。五つの一級概念は互いに独立で、どの二つにも還元されない。

1. **Goal（ゴール）**：望ましい状態。形式語義を持つ。後述の四型のいずれか。
2. **Obstacle（障礙）**：ゴールの論理的な不満たし可能事態。`O ≡ ¬G` の形であらねばならない——障礙は「起きた悪い出来事」の任意收集ではなく、**G の否定として特定される事態**である（→3.4 で詳しく扱う。ここが GORE の障礙と普通のリスク管理の決定的な差）。
3. **Assumption（仮定）**：環境側が満たすと信頼する性質。設計者の支配外の前提（ネットワークは99.9%稼働、作業者は手順を踏む）。仮定は要求と双対である——要求はシステムエージェントに課し、仮定は環境エージェントに課す。
4. **Requirement（要求）**：システムエージェントに割り当て可能なゴール（下向きの葉に近いノード）。
5. **Agent（エージェント）**：ゴール・仮定・要求の実現を担いうる主体。人間、マシン、組織、物理法則まで「主体」として載る（→3.6）。

五階層の相互関係は、単一の関係述語 **`sat(A₁..Aₙ ⊧ₐ G)`**（エージェント集合 A が環境仮定の下で G を充足）で統一される。この述語の論理的な強さ——充足が実在モデル上の成立ではなく論理的帰結（論証可能な成立）であること——が GORE の全部であり、また GORE の最大の限界でもある（→3.5 で率直に扱う）。

### ゴールの四類型と形式語義 — 線形時態論理（LTL）で意味を与える

KAOS のゴールは形態により四型に分かれ、それぞれ LTL（linear temporal logic）で定義される。LTL の記号は G（globally, 常に）、F（finally, いずれ）、U（until,.untilまで）の三つだけである。

| 型 | 自然言語雛形 | LTL 定義 | 保全現場の例 |
|---|---|---|---|
| achieving（達成） | P を（いずれ）達成 | `◇P`（F P） | 故障検知から30分以内に点検着手 |
| maintaining（維持） | P を常に維持 | `□P`（G P） | 稼働中のポンプの振動値は閾値未満 |
| avoided（回避） | Q を常に回避 | `□¬Q` | 無停止でのベアリング交換の試行 |
| ceasing（ cease・終了） | 現状 P をやめる | `P → ○□¬P` | 停止指示後、回転は恒久停止 |

この四分類が重要なのは、**検験可能性（→4.1）の形式形だからである**。maintaining ゴールは監視で falsify 可能（一度でも ¬P を見れば違反）、achieving ゴールは検認で verify 可能、avoided は maintaining の特殊形、ceasing は遷移の性質。要求の「検証方法」が、要求文書の運用ではなく論理型の帰結として決まる。LTL 型を宣言しないと、検証の設計が始まらない——4章の十分性判定は、この型の宣言を入口に取る。

ゴールの形式化は LTL に限らない。データ条件を含むなら FOL（一階述語論理）に Lift した LTL+FO が要る（3.5 の実装では z3 の FOL で近似する）。重要なのは「型と論理を宣言する」という作法そのもので、特定論理の選択は可換な部品である。

### AND/OR ゴール分解木 — 充足根拠を木として証明する

ゴールは上位→下位へ分解される。AND 分解では、子ゴール群の**同時充足**が親の充足を論理的に含意する（`G ⇔ G₁ ∧ G₂ ∧ ... ∧ □A` の形。A は環境仮定）。OR 分解では、子のどれか一つの充足で親が充足される——OR 分岐は**設計の選択点**であり、要求分析の段階では「選択を保留する」ための構造である。要求工学の初期段階で実装選択を固定しないことの形式的な居場所が OR ノードである（この遅延決定の哲学は 8.4 の人間介入点設計とも共鳴する）。

分解の正当性（decomposition legitimacy）は「漏れのない分解か」に尽きる。形式化すれば——`G ∧ ¬(G₁∧...∧Gₙ∧□A)` が充足可能（unsatisfiable でない）なら、分解は漏れ（gap）を持つ。充足可能性判定は次節以降の z3 の仕事だが、漏れの直感的検出は障礙分析（→3.4）と対になる手続を持つ：**G を保ったまま、全子Goalが同時に壊れうる世界を1つ構成できるなら、分解は漏れている。** 3.5 の実装ではこの両者（機械判定と反例構成）が表裏になる。

### 本書への実装 — goal tree を Neo4j のグラフとして置く

要求分析のツールは様々だが（KAOS ツール suite、Tropos、i*）、本書はグラフで持つ。理由は第1部の設計決定と同一である——意味の横方向のつながり（障礙と制約の共有、同一エージェントの過負荷、softgoal の競合）を、ツールの「木」は辺として持たず、後から人間が見るしかなくするからである。goal tree は木だが、goal **graph** は木でない。障礙の共有、仮定の共有、エージェントの共有——これらが木を網（tangle）に変える。この網の構造こそ影響解析の本体である。

```cypher
// goal tree 本体（3.1 の telos 連鎖 ACHIEVED_FOR と接続）
MATCH (parent:Goal {goal_id: $p}), (c:Goal {goal_id: $c})
CREATE (parent)-[d:DECOMPOSED {kind: $and_or,   // 'AND' | 'OR'
  legitimacy_checked_at: datetime(),
  gap_witness: null}]                          // 漏れの反例（→3.5）がここに入る
->(c);

// satisfaction argument: Requirement(r) + Assumption(a) ⊧ Goal(g)
MATCH (r:Requirement {req_id: $r}), (a:Assumption {asmp_id: $a}), (g:Goal {goal_id: $g})
CREATE (r)-[:SATISFIES {
  arg_type: 'logical',          // 'logical' | 'plausible' — 論証と尤物を混ぜない(→4.1)
  ltlexpr: $ltl,                // 機械検証可能な充足論証の核
  checkable: true               // false の論証は人間証言。4.6 で監査対象になる
}]->(g),
(a)-[:ASSUMED_FOR {criticality: $c}]->(g);

// 障礙の連結: O は G の否定。negates 辺の向きは「G を壊しうる」方向。
MATCH (o:Obstacle {obst_id: $o}), (g:Goal {goal_id: $g})
CREATE (o)-[:NEGATES {not_form: $fol_of_not_g}]->(g);
```

`arg_type` の二値区分（logical / plausible）を強調しておく。充足論証が本当に論理的帰結なのか、「もっともらしい」だけなのかを、ノードに書かせる。GORE の文献自身がこの区別を正直に扱っている（satisfaction argument の妥当性は環境モデルの正しさに相対的だ、と van Lamsweerde は書く）。本書の哲学設計（→4.1 の検証可能性の限界）では、plausible 論証は削除されないが、**plausible であることをデータとして持ち続ける**。尤度と正統性の混線拒否は 5.3 の LLM 論点の先取りでもある。

### softgoal — 十分でない「より良い」を木で扱う

KAOS/GORE（と並行系譜の i*）は softgoal を導入する。「セキュア」「効率的」「保守可能」は充足/不充足の二値で判定できない——充足が程度問題だからである。softgoal の標準的扱いは `AND/OR contribution link + 満足閾値` の木であり、`somepath`（ある分解ルートで十分）や `allpath`（全ルートで必要）の満足様式で評価する。在庫自動発注の失敗（3.1）を softgoal 語彙で書き直せば——`資金最小` と `停止ゼロ` は softgoal であり、自動発注の要求木は `停止ゼロ` への contribution は正、`資金最小` への contribution は負（在庫増）となる。負の contribution を木に載せていれば、発注前に競合が**可視**だった。

```cypher
// softgoal の contribution 集計: 要求ノードの正味効果を木で計算する
MATCH (r:Requirement)-[:CONTRIBUTES {sign: $s, weight: $w}]->(sg:SoftGoal {sg_id: $sgid})
MATCH path = (top:Goal)-[:DECOMPOSED*]->(r)   // 要求が所属する上位木
WITH r, sum(r.CONTRIBUTES.weight * CASE WHEN r.CONTRIBUTES.sign = '+' THEN 1 ELSE -1 END) AS net
MATCH (sg) WHERE NOT (sg)-[:CONTRIBUTES {sign: '-'}]->(:SoftGoal)  // 競合先の正規化
RETURN sg.sg_id, net
ORDER BY net ASC;   // 負の正味効果を持つ要求が先頭に来る。この並びをレビュー会議の議題に。
```

このクエリの「成果」を過大評価しないための注記を添えておく。weight の数値化は softgoal の程度判断を疑似定量化する操作であり、2.1 の分節の暴力が数値の皮を被ったものである。contribution 符号＋重みの決定は 2.6 級 L2 の承認対象とし、数値ではなく**符号の競合を議題に上げる**ことを主目的にする。レビューの議題生成が目的であり、数値は議題の補助線である（→4.2 の CQ も同じ「判定不能なものの審議可能化」という設計思想を共有する）。

### van Lamsweerde の系譜と、彼の問いの現在

最後に思想史の配線をしておこう。GORE の系譜は、3.1 で追放と言った目的因が、実は工学的伝統では生き続けていたことを示す。1970年代の構造化分析（要求を機能分解で書く）→ 1980年代の形式手法（Z、VDM：形相の完全性）→ 1990年代の GORE（目的の第一性）→ 2000年代の softgoal・意図（intention）モデル（目的の程度・主体性）——この流れは、「システムを記述する」という観が「システムが何のために存在するかを記述し、そのために何が十分かを論証する」観へ移行した歴史である。

そして van Lamsweerde の後期研究は、本書の第5部と正面から接続する問いを残している。彼は *Formal Requirements Engineering* の後年、「要求の形式化は人間の価値判断を置換するのではなく、価値判断の**質を上げる**ためにある」と書き続けていた。形式化の限界内での形式化の益——これは 8.4 の Human-in-the-Loop の要求版であり、4.1 の検証可能性の限界の肯定形である。本章は GORE を「目的を機械に渡す方法」としてではなく「目的について人間が議論できる形式語彙」として採用する。この採用の方向の差は、第4部・第5部で決定的な差に育つ。

### goal 木の品質検査 — AND/OR 分解の構造的不変条件

KAOS の goal 分解木（AND/OR 分解、→前掲）に、構造の検査を四条通す。意味の検査（→4.2 の CQ）と形が異なるのは、**分解木の病は意味が正しくても形の病で発生する**からである（正しい目的の集合が、間違った木の形で運用事故になる）。

**検査一：leaf の形式化可能性**——すべての端節点は形式文（LTL/FOL、→3.3）か放棄登記（→3.3 放棄表）のどちらかを持つ。どちらもない端節点は「目的の木」の先が口約束でできていることの証明である（→4.1 の境界——木は境界の地図でもある）。**検査二：OR 分解の相互排他の非要求**——OR 分岐は「どれか一つ」であり、分岐同士が**同時に満たされうる**ことを禁止しない（同時に満たす goal 設計は冗余であり、冗余の OR は偽装である——本物の OR は「同時に成立しうるか」の設計判断を DesignDecision に持つ）。**検査三：AND 分解の完全性**——AND 分解の全 child が満たされたら parent が満たされる（**実在的完全性**）ことの宣言が各 AND 節点にある。宣言のない AND 節点は「全部揃えたのに目的が果たされていない」事故の予約である（欠けた child=形式化し忘れた要求、→3.3 の未読了文の木版）。**検査四：深度と周期の整合**——goal 木の深さ（委任の段数、→7.2 の委任深度の要求工学版）が、現場の周期預算で到達できる深度を超えていない（叶わない深さの木=待たされる事故、→3.4 N5 周期超過の静的検出）。

```cypher
// goal-tree-health — 四検査の Cypher 実装(要求レビュー前に CI で走る)
// 検査一: leaf の形式化/放棄登記の欠落
MATCH (g:Goal) WHERE NOT (g)-[:HAS_SUBGOAL]->()
AND NOT (g)-[:FORMALIZED]->(:Formula) AND NOT (g)-[:WAIVED]->(:WaiverRecord)
RETURN g.goal_id, 'leaf-unformalized';
// 検査三: 実在的完全性の宣言欠落
MATCH (g:Goal)-[:AND_DECOMPOSED]->(:Goal) WHERE g.completeness_claim IS NULL
RETURN g.goal_id, 'and-not-declared-complete';
// 検査四: 周期預算到達不能深度
MATCH path = (root:Goal)-[:HAS_SUBGOAL*1..6]->(g:Goal)
WHERE size(path) >= root.max_depth OR g.decision_budget_sec < 0  // 予算枯渇の節
RETURN root.goal_id, max(size(path)) AS depth, root.max_depth;
```

四検査の失敗を goal 台帳の障礙候補として自動登記する（→3.4——分解木の形の病自体が障礙の源、複合式一の静的版）。哲学の節（3.2 の前段）とこの節の関係を一句で置いておく。GORE が目的原因復権の工学的体（→3.1）だとすれば、**分解木の形の検査はその体への神経の配線**である——AND/OR の木は目的の論理形式であり、論理形式の検験は目的の検験に先行する（論理が正しくなければ、目的の意味の検査すら走る場所がない——4.1 の検証可能性の要求が、ここで goal 木の形に適用されている）。

### 実行練習

1. 3.1 練習3 の goal tree を KAOS 五階層に拡張せよ：各葉に Requirement か Assumption を割り当て、`SATISFIES`/`ASSUMED_FOR` 辺を張り、全叶にエージェント（人間1つ以上を含むこと）を接続せよ。「人間が一つもエージェントとして現れない分解」は本章の語で *dehumanized decomposition* である（→3.6）。
2. maintaining ゴール「稼働中ポンプの振動値は閾値未満」の障礙を `NEGATES` 辺で定義し、その障礙が同時に `avoided`（無停止交換の試行）の negation でもあるケースを作れ。1つの障礙ノードが2つのゴールを negates する構造を、3.4 の障礙木へどう載せるか設計せよ。
3. 上の softgoal 集計クエリに自分のプロジェクトの要求5本を通し、負の net が最も大きい要求を1本選べ。その要求の `CONTRIBUTES` 符号・重みを決定した会議議事録がない場合、2.6 のどの級の変更として事後的に登記すべきか決め、登記レコード（`:intent` 自由文付き）を書け。
