## 3.3 目的から論理へ — 自然言語要求の形式化手順

ゴールの階層と形式語義の型が揃った（→3.2）。この節の実務は、自然言語で書かれた要求を、その型に入る論理式へ**手順的に**変換することである。「手順的に」と強調するのは、形式化が天才の翻訳芸ではなく、翻訳の失敗が記録・再現・監査できる工学工程でなければならないと本書が決めているからだ（2.1 の暴力は形式化に内在し、消せない。消せない暴力は手順にして追跡する——これが第2部全体の統治原則である）。三段変換を敷設する。自然言語 → EARS（制約付き自然言語）→ LTL（線形時態論理）→ FOL+LTL（データ条件込み）。各段は完全に忠実ではない。各段が何を失うかを明示したまま進行するのが、本書の手順の哲学である。

### 第一段階 — EARS：自然言語を構文制限された自然言語へ

EARS（Easy Approach to Requirements Syntax、Rolls らが Rolls-Royce で開発）は、要求文を五つの定型構文に収束させる。自由文をいきなり論理へ翻訳すると、失うものが多すぎる。中間言語を置く。

```
1. Ubiquitous（常時）:        The <system> shall <response>
2. Event-driven（事象駆動）:   When <trigger>, the <system> shall <response>
3. State-driven（状態駆動）:   While <in state>, the <system> shall <response>
4. Unwanted behavior（異常）:  If <condition>, then the <system> shall <response>
5. Optional（任意）:           Where <feature is present>, the <system> shall <response>
```

保全現場の要求を EARS へ正規化する例。左の自由文のどこが危険だったかをコメントで注ぐ。

```
原文: 「夜間の振動異常は点検を優先すること」
EARS: While [Shift.type = 'night'],
      when [vib(m) >= threshold(m) for machine m in Zone z],
      the system shall [raise PriorityFlag on the inspection task for m within 5min].
# 原文の危険: (1)「振動異常」が未定義（threshold とどちらか不明）。
# (2)「優先」が程度語（softgoal 領域。3.2 の貢献記述か、順序の硬性格か不明）。
# (3)「夜間」の範囲未定義（shift 境界 vs 時刻）。
# EARS 化は these を語彙参照（threshold, Shift.type）へ強制し、程度語を露出させる。
```

EARS の本質的機能は、**時態構造の露出**である。While/When/if/where はそのまま LTL の G/(trigger⇒X)/（異常）/（feature 条件）に対応する。自由文段階では動詞の時制と副詞に埋もれていた時間構造が、構文で剥き出しになる。ここが形式化の閾値であり、以降の段はほぼ機械的である。

```python
# ears_to_ltl.py — EARS 五型の機械的 LTL 化（第一近似）
# 哲学: この関数は意味を保証しない。EARS 側の構文が正しければ時間構造だけを保つ。
# 保証の所在(意味の正しさ)はレビューにあり、時間構造の正しさはここに書く。
from dataclasses import dataclass

@dataclass
class Ears:
    kind: str            # 'ubiquitous'|'event'|'state'|'unwanted'|'optional'
    trigger: str | None  # FOL 断片（While/if の中身）
    response: str        # FOL 断片（shall の中身）
    within: str | None   # 時間窓（'PT5M' 等）

def to_ltl(e: Ears) -> str:
    match e.kind:
        case 'ubiquitous':
            return f"G({e.response})"
        case 'event':
            window = f"F[{e.within}](R)" if e.within else "F(R)"
            return f"G(({e.trigger}) -> {window.replace('R', e.response)})"
        case 'state':
            return f"G(({e.trigger}) -> G({e.response}))"
        case 'unwanted':
            return f"G(({e.trigger}) -> {e.response})"  # 異常時の是処動作は event と同型
        case 'optional':
            return f"G(({e.trigger}) -> G({e.response}))"
    raise ValueError(f"unknown EARS kind: {e.kind}")
```

`within` の時間窓が LTL に「5分以内」を載せる方法（有界 until）を明示しない実装になっている。実運用では bounded LTL（TLA+ の temporal operator 等）へ降りるが、骨格としての意味は不変だ——**時間窓は要求の一部であり、時間窓を忘れた変換は要求の書き換えである**（3.1 の在庫システムの発注遅延事故は、within の喪失として再現できる）。

### 第二段階 — LTL + データ条件（FOL への Lift）

`vib(m) >= threshold(m)` のようなデータ条件は純 LTL では書けない。述語を LTL の項として内包する LTL+FO へ移る。本書の実装（→3.5）では z3 の FOL に落として近似する——時間量化を有限時点への instantiation（unrolling）で置き、充足判定を有限境界で下す。有限境界近似は正当性を持つが、無制限の定理証明ではない（→3.5 の決定不能性の節で完全な扱いを書く）。

```
G( (vib(m,t) ≥ threshold(m)) → F[≤30min](Inspect(m,t')) )
   ↑全域量化 m ∈ machines, t ∈ times
# unrolling (時点 0..N, 機械 1..M):
∧_{t=0..N} ∧_{m=1..M} [ vib(m,t) ≥ thr(m) ⇒ ∨_{t'=t..t+⌊30min/Δt⌋} inspect(m,t') ]
# z3 の整数線形制約として drop する(実装は §3.5)。
```

unrolling の粒度 Δt と範囲 N の選びが判定の限界そのものである。「粒度より短い違反窓は発見不能」——境界設定の宣言を要求の木に載せる。境界を載せない形式検証は、検証の網の目を検証しない検証である（→4.1 の検証可能性の限界の技術形）。

### 第三段階 — 形式化が構造的に失うもの：修飾詞の難しさ

三段変換の損失を分類し、損失への設計応答を決めておく。損失は三型に尽くせる。

**型一：境界語の切断（vague predicates）。** 「深刻な故障」「通常の稼働」は輪郭のぼやけた述語である。FOL は二値述語を要求するので、切断は不可避（2.1 の暴力そのもの）。設計応答は多値化ではなく**切断の版数化**である——`threshold(m) = 4.5 mm/s, version: 2026-11` を要求ノードに紐づけ、2.5 の履歴代数に接続する。輪郭を消さず、輪郭の移動を記録する。

**型二：程度語の残留（soft residues）。** 「優先すること」「適切に」は LTL に翻訳不能で、softgoal 木へ逃がす（→3.2）。設計応答は、soft 語をハード要求へ無理やり落とさないことである。落とした瞬間、程度判断の責任が要求の論理に紛れ込み、監査不能になる。`arg_type: 'plausible'` の混線拒否（→3.2）と同じ原則。

**型三：省略された存在前提（implicit presuppositions）。** 「点検タスクに優先旗を立てる」は「当該機械に点検タスクが存在する」を前提とする。タスクが存在しなければ要求は vacuously true になり、空転する。FOL は量化で前提を露出できる（`∃task` の要求化）が、翻訳者は露出の必要性に気づかねばならない。設計応答は vacuity 検出である。

```python
# vacuity_check.py — 「空に真」を検出する: 論証済み要求が前提の不在で自動的に真になっていないか
from z3 import Solver, Bool, BoolRef, Not, And, sat, IsSat

def is_vacuous(assumption: BoolRef, requirement: BoolRef) -> bool:
    # 要求 G が「前提 P の下で真」ではなく「前提 ¬P だけで真」になっていないか:
    # P ∧ ¬G が unsat（G が P 下で常に真）で、かつ ¬P だけでは sat に ¬G が成立する
    # （= 前提が消えると壊れる真しさ）であることを区別する。
    s = Solver(); s.add(assumption, Not(requirement))
    always_holds = s.check() == IsSat.unsat     # P ⊨ G
    if not always_holds:
        return False
    s2 = Solver(); s2.add(Not(assumption), Not(requirement))
    needs_assumption = s2.check() == IsSat.sat  # ¬P ∧ ¬G 可能 → G は P に依存している
    return not needs_assumption                 # 依存なし = 空に真 = vacuous
```

vacuous な要求は「検証にパスするが何も保証しない」要求である。形式検証の現場では珍しくないが、要求文書ベースの運用では検出されない。GORE の充足論証を機械で書く本書の系（→3.5・4.5）では、vacuity 検査は契約テストと同等の市民権を持つ（4.4）。

### 形式化の过程的記録 — 翻訳ログを 2.5 の履歴に接続する

最後に、手順を「手順」足らしめる登記を置く。三段変換の各ステップで、原文のどの句が論理のどの部分になり、何を失ったかを `RefinementTrace` ノードに残す。2.5 の git→RDF 橋と同じ代数である。

```cypher
// 原文句 → 論理部品の対応を登記（翻訳の暴力の追跡可能性）
CREATE (t:RefinementTrace {
  source_text:     '夜間の振動異常は点検を優先すること',
  source_span:     '振動異常',
  ltl_fragment:    'vib(m,t) >= threshold(m)',
  lost:            ['異常の身体知覚的側面(異音)(→1.1)', '異常の程度(softgoalへ逃がした)(→3.2)'],
  gained:          ['境界(4.5mm/s)と版数の確定'],
  translated_by:   'P-201',
  reviewed_by:     'P-114',          // 現場の人間がレビュー者。3.6 のエージェント原則
  at:              datetime()
});
// lost の欄が空欄の翻訳レビューは、翻訳の暴力をなかったことにする手続き。
// 空欄禁止は 2.5 の intent 必須と同じ誠実さの規則。
```

### 翻訳の全体ワークフロー — 誰がどの段をやるか（3.6 の予告）

EARS 化は要求分析者と現場の協働で（現場語彙を skos マッピング経由で正規語彙へ、→2.4）、LTL 化は形式担当者で機械補助（上の ears_to_ltl が叩き台）、FOL+境界化は形式担当者と検証エンジニアの共同、RefinementTrace 登記は全段共通。エージェント割当は 3.6 で形式的に扱うが、既に 1.6・2.6 の原則が支配している——**形式化の権限は書く者にではなく、失われた意味を復元照会できる者に置く**。翻訳ログの閲覧権限が現場にない形式化は、翻訳の暴力を不可視にする。

### 形式化の監査 — 「翻訳表」と「放棄表」を要求文書に添わせる

自然言語要求→形式論理の翻訳（→前節の手順）の運用で最も起きる事故は、翻訳の**失敗**ではなく翻訳の**省略された箇所の非登記**である。要求文書の各節を機械的に形式化した結果、「翻訳された文」「翻訳されなかった文」「翻訳を**放棄すると決めた**文」の三区分が必ず生じる。区分の登記を要求文書の強制様式にする——**翻訳表**（原文→形式文の対応）と**放棄表**（形式化しないことと、その理由と、代替機構）の二表である（→1.6 の記録しない宣言・NonRecordingRule の要求工学版）。

```markdown
## 翻訳表(req-v7)
| 原文 (§3.1) | 形式文 (LTL) | 級 |
|---|---|---|
| 「停止中は給油しない」 | □(¬operating → ¬pumping) | E1 |
## 放棄表(req-v7)
| 原文 (§3.4) | 放棄理由 | 代替機構 | 落日 |
|---|---|---|---|
| 「機械の調子が悪いと感じたら…」 | 検証可能な述語が存在しない | 審議槽+理由面板(→8.5) | 24か月 |
| 「経験豊富な operator が…」 | 定義不能(暗黙知,→1.1) | drill課程(→8.6) | 36か月 |
```

放棄表の三列が運用の核心である。**放棄理由**は怠慢と設計的不同意を区別する（後者は記録された哲学的位置取り——→4.1 の検証可能性の落日と接続）。**代替機構**の列が最重要で、放棄は機構の欠如ではなく機構の**乗り換え**でなければならない（形式化しない決定に代替機構が書かれていない文書は、その要求を静かに消した——2.1 の暴力の要求文書版）。**落日**により放棄も再審議される（「感覚」の語彙が 24 か月後の現場語彙（coin-term）で検証可能になる可能性がある——→1.3 の語彙の更新）。

監査照会を一つ。**原文の文数に対する両表の被覆率**——100% でない要求文書は、翻訳でも放棄でもない第三の状態（**未読了の文**）を含んでいる。未読了の文の集合が、その要求の最大の風険である（誰も翻訳を論争せず、放棄も記録していない要求は、運用で各自の解釈で動く——2.4 の分類制定の非登記が要求文書で起きる）。監査はこの「未読了リスト」を自動生成し、要求レビューの第一議題に置く（→4.2 の CQ 統治——文書そのものの CQ：「この要求の各文は、翻訳されたか、放棄されたか、どちらでもなければ誰が読む予定か」）。

この設計の背景にある論理を一文で置いておく。形式化の誠実さは、翻訳の正しさの総和ではなく、**翻訳と放棄の境界の登記の完全性**で測られる（→4.1 の境界問題の実務形）。よって翻訳表の精度を上げる努力より、放棄表を完备にする努力が、要求の信頼性を大きく上げる——後者は数分で書け、前者は数か月かかるという運用上の非対称もある。

### LTL 五テンプレート — 要求の時制を書く定型

障礙分析（→前掲）で再現する時制パターンの定型五本を、そのまま要求カードに貼れる形で置く（毎回 LTL を書ける必要はない——定型が五本あれば、書けない質問の形が見え、書ける側の負担が下がる。ウィトゲンシュタインの語言遊戯の観点：规則遵循は個別的天才でなく定型の反復で成立する、→4.2 CQ 書式と同じ設計哲学）。

| テンプレ | 式 | 自然言話の型 | 障礙化け(→3.4) |
|---|---|---|---|
| 応答 | `□(req → ◇≤d resp)` | 「要求したら d 以内に返る」 | N5 周期超过 |
| 安全 | `□¬(danger)` | 「never, どの状態でも」 | N1 違反 act の存在 |
| 保証 | `(req ∧ fair) → ◇ done` | 「待ち続ければいつか終わる」 | N3 饥饿 |
| 単調 | `□(s_i → (s_i ∨ s_{i+1}))` | 「一段下に戻らない」 | N4 前提(状態機械の環) |
| 調和 | `□(a → ◇□b)` | 「a を选んだら b が定着する」 | N2 復合(effect 宣言の実証) |

運用の注記を二つ。**其一、五本に落ちない要求は**「我々が今言える時制の限界」の記録として障礙候选に載せる（要求の形式化不能=3.3 の翻訳表の未翻訳欄—→3.2 の叶わない形式化の宣言）。**其二、テンプレの选型は L1 級**（要求の時制の形を変えることは E2 見通し級の変更—→2.6 の級表に「要求テンプレ変更 L1・要求不変条件変更 L3」の二行が預めって載る理由）。

### 実行練習

1. 自分の要求文書から自由文5本を選び EARS 五型に正規化せよ。正規化中に「程度語」が現れた本数を数えよ。程度語の本数が softgoal の個数（→3.2 の競合木の入口数）である——この等式をチームの説明資料にせよ。
2. `ears_to_ltl.py` に「While 状態中に When 事象」の複合 EARS（nested）を追加し、LTL 式 `G(state -> G((trigger) -> F[..](response)))` を生成せよ。state が抜けた瞬間に未完了の response の義務はどうなるか（obligation evacuation）を LTL で書き、ceasing 型（→3.2 の表）で表現せよ。
3. `is_vacuous` に「前提: 点検タスクが存在する」を明示した要求と、前提を忘れた同一要求を流し込み、後者が vacuous と判定されることを確認せよ。判定結果の `needs_assumption` が False になる場合の要求文の書き直しを1案提示せよ（quantifier を露出する形）。
