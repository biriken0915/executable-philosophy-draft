## 3.6 責任の配分 — エージェントモデルと意図

ゴール木が充足された（→3.5）としても、要求文書は完成しない。充足論証 `sat(A ⊧ R ⇒ G)` の中に、まだ名前のない主体がいる。**要求は、誰かに実現させることを言外に含んでいる。** 「5分以内に点検が起きる」は、点検という行為の主体がいなければ空虚である（→3.3 の vacuity 検査が既に示していた）。GORE は主体を agent（エージェント）と呼び、ゴール・要求・仮定の三者すべてが「あるエージェントに実現可能（realizable）」であることを要求する。この節では、エージェントを単なる実行プロセスではなく**意図（intention）の帰属先**として定義する。責任の配分とは、意図の帰属の配分である。そして節の後半で、人間エージェントと機械エージェントの非対称性を確定する——この非対称性が第3部全体の設計原理（AIの脱・司令塔化）の土台になる。

### 実在可能性（realizability）— 実現できる主体にしか要求は割り当てられない

KAOS の agent 概念の中核は、要求 R の **realizability**（実現可能性）の定義である。粗く言えば——要求 R がエージェント A に実現可能とは、R の実現が A の支配領域（environment of A）内の動作だけで決まる、という条件である。支配領域外の事象に依存する要求は、そのエージェントに割り当てられない。

この定義の威力は、否定形で現れる。**「A に実現不可能な要求」を割り当てた瞬間、充足論証は成立しても、実装は空証する。** 3.4 の障礙葉が `REALIZED_BY_FAILURE_OF` で繋いだエージェントが、実はその障礙を支配していなかった——これが組織の要求配分の最頻出事故である（「担当者が対応する」要求の担当者が、担当の変更を支配していない、のような例）。

```cypher
// 支配領域の登記: エージェントが「変更できる」観測・状態・行為の集合
MATCH (a:Agent {agent_id: 'AG-nightshift-lead'})
CREATE (a)-[:CONTROLS {scope: 'inspection_schedule'}]->(:DomainElement {name: 'inspection_schedule'}),
       (a)-[:CONTROLS {scope: 'manual_override'}]->(:DomainElement {name: 'manual_override'});
// 制御できない要素: センサーハードの稼働(保守部門の質料)、天候、本体の来訪。

// realizability 検査: 要求 R の論理式が参照する要素が、
// 割り当て先エージェントの CONTROLS 集合に含まれるか
MATCH (r:Requirement {req_id: $r})-[refs:REFERENCES]->(el:DomainElement),
      (a:Agent {agent_id: $a})
OPTIONAL MATCH (a)-[:CONTROLS]->(el2:DomainElement) WHERE el2 = el
WITH r, el, a, count(el2) AS controlled
WHERE controlled = 0
RETURN r.req_id, el.name AS outside_control,
       'REALIZABILITY-VIOLATION' AS verdict;
```

`REFERENCES` 辺の張方は翻訳ログ（→3.3 の `RefinementTrace`）と共通で、論理式が参照する語彙がそのまま要求の「世界への接触面」である。この検査の産出する `REALIZABILITY-VIOLATION` は、配分ミスの自動検出である——配分ミスの多くは悪意ではなく、組織図の変化と要求文書の陳腐化のすれ違いで生む（3.4 の障礙の `stale` と同じ entropy）。

### 意図的概念 — ゴールはエージェントの内部状態ではない

エージェントモデルの理論的伝統は別に存在する。Intentional Agent 研究（Dennett の意図的立場、Bratman の実践理性の理論、Cohen & Levesque の intention の論理、JSBV 体系）。本書がこれらから拾う中心命題を三つ置く。

**其一、意図は予測の道具である（Dennett）。** 人間を「信念と欲求で行動を予測するシステムとして扱う」ことが有効なのは、予測コストが神経状態を追うより安いからである。同型が設計に使える——エージェントに `intent` を登記することは、その挙動の予測コストを組織全体で下げる操作である（→2.5 の `:intent` 必須、→3.3 の充足論証の同じ代数）。

**其二、意図は再考に抵抗し、持続する（Bratman）。** intention は goal と違い、達成不能の認識後も計画を支え続ける安定化機能を持つ（目標の固執）。これは設計では**two-edged** である。意図の持続は実行の安定を生み、障害を壊さない。しかし「もはや目的に serve しない計画」を回し続ける爆弾にもなる。Bratman の解決は revision（部分的再考）の構造——計画の再考は、上位意図の再採用を要求する。設計翻訳：`intent` の再考は上位 goal の `ACHIEVED_FOR` の再検証を誘発する。**意図の更新は必ず上位の意図の更新を招く、という連鎖の登記**が 8.5 の「理由を問う対話」の形式的原型になる。

**其三、共同意図は「相互belief の閉包」である（Cohen & Levesque, Grosz）。** 共同で G を遂行するとは、各自が G の遂行を意図し、かつ「各自が遂行を意図していることを各自が知っている」無限の相互 belief を持つことである（近似条件で有限化される）。現場チームとシステムの共同遂行は、この相互 belief のインフラである——システムはチームの意図を読み、チームはシステムの意図（`intent`、理由提示、→8.5）を読む。相互 belief の片側の断線が「自動システムの暴走」の定義にほかならない。

```cypher
// 共同遂行の最小登記: shared intent の相互 belief 構造(有限近似)
MATCH (sys:System, team:AgentTeam {team_id: 'nightcrew'})
MERGE (sys)-[:INTENDS {intent: 'G-inspect-5min', role: 'detect+route'}]->(:IntentionNode {i_id: 'I-42'})
MERGE (team)-[:INTENDS {intent: 'G-inspect-5min', role: 'inspect'}]->(:IntentionNode {i_id: 'I-42'})
WITH sys, team
MATCH (n:IntentionNode {i_id: 'I-42'})
MERGE (sys)-[:BELIEVES_OF {about: 'team.role'}]->(n)
MERGE (team)-[:BELIEVES_OF {about: 'sys.role'}]->(n)
MERGE (n)-[:EXPOSED_AS {surface: 'reason-panel'}]->(:Interface)
// EXPOSED_AS が相互 belief の物理実装である(→7.5 の reason panel、→8.5 の対話プロトコル)。
// 意図がインターフェースに露出されないシステムは、共同遂行の条件を機構的に欠く。
```

### エージェントの分類図 — 人間・機械・組織・自然法則

KAOS は agent の類型を機械（machine）、人間（human）、組織（organizational）、野生（wild、制御不能環境）に分ける。本書はこれを「支配領域の性質」と「意図の帰属の可否」という二次元に広げる。

| 類型 | 支配領域 | 意図の帰属 | 要求の割り当て | 例 |
|---|---|---|---|---|
| 人間 | 行為・解釈・再考 | 満（解釈可能） | できる（soft 要求含む） | 夜勤リーダー |
| 機械 | 行為・計算 | 擬似（登記された intent） | 硬性格要求のみ | 検知・通知系 |
| 組織 | 役割・手順・承認 | 半（公式 intent の主体） | 手続要求 | 承認委員会（2.6） |
| 自然法則・野生環境 | 変更不能 | 不可 | 仮定のみ | 重力、通信物理 |

重要なのは softgoal 次元である。「優先する」「適切に」の遂行は、機械への割り当てが原理的に禁止されている（→3.3 の型二の残留が、ここでエージェント割当の問題として再発する）。soft 要求を機械に割当てた瞬間、程度判断が機械の内部に潜り込み、監査不能な判断が誕生する——3.1 の「在庫最適化」事故の agent 割当版である。

### 非対称性 — 人間エージェントと機械エージェントの三つの差

第3部の設計原理の地基を、ここで打っておく。両者は「同じ種類の実行主体」ではない。差は三つある。

**第一に、解釈の開閉。** 人間の意図は開いている——行為の理由を、行為後にでも問い直し、破棄できる（Bratman の再考構造が人間に内在する）。機械の「意図」は登記された文字列であり、行為後に意味を更新する能力を持たない。だから `intent` 更新の連鎖を、人間側が設計・運用で担保し続けるほかない（→8.5）。

**第二に、残余の扱い。** 人間は 2.1 の残余を生きられる——言葉にならなかった状況の手触りを、次の判断に持ち込める。機械は残余を持たない。残余は単に存在しない（→1.6）。機械に残余相当を担わせる試み（例外処理リストの拡張）は、残余を明示知に変換する無限作業であり、1.6 で退けた削減主義の再生産である。

**第三に、懲罰への応答（responsibility）。** 責任の最終的な所在は、懲罰と名誉と解釈義務を受けることのできる存在でなければならない。機械は懲罰されない（サーバ室的な比喩は比喩である）。よって責任の連鎖の末端は常に人間に座る——3.5 の unsat core で「論理は名前を渡し、人間が級を決める」と書いたが、級を**決める**という行為そのものに責任の器がいる。

この三差を、本書では**非対称性定理（非公式）**として扱う。定理という語に甘えて、正確には三つの設計要請として置く。(1) 機械エージェントには soft 要求を割当ない。(2) 機械エージェントの `intent` は人間の再考連鎖に接続されたインターフェースへ露出必須。(3) 責任の連鎖の末端は人間エージェントのノードで終端し、その末端ノードは `RESPONSIBLE_FOR` 辺の到着点として機械に読める形で登記する。

```cypher
// 非対称性の機械検査
// (a) soft 要求が機械エージェントに割当されていないか
MATCH (r:Requirement)-[:ASSIGNED_TO]->(a:Agent {kind: 'machine'})
WHERE r.softness = 'soft'
RETURN r.req_id AS illegal_soft_assignment;
// (b) intent のインターフェース露出を持たない機械エージェント
MATCH (a:Agent {kind: 'machine'})
WHERE NOT EXISTS { MATCH (:IntentionNode)<-[:INTENDS]-(a),
                   (i:IntentionNode)-[:EXPOSED_AS]->(:Interface) WHERE true }
RETURN a.agent_id AS intent_dark_agent;
// (c) 責任末端が未登記の action(実行可能だが責任者がいない行為)
MATCH (act:Action {executes_on: 'field-api'})
WHERE NOT (:Agent)-[:RESPONSIBLE_FOR]->(act)
RETURN act.name AS orphan_action;
```

`orphan_action` は本章の診断定理の第三の兄弟である——**責任者のない行為は、実装されていても実現されていない**（実行された瞬間、責任の連鎖の不在がそのまま事故の帰属不能になる）。2.6 の権限条文が要求側の倫理だとすれば、この (c) は行動側の倫理の検査である。

### 要求の全体ライフサイクルでの agent 変更 — 組織が変わると要求も変わる

配分は一度の割当で終わらない。組織変更（部署統合、委託化）で `CONTROLS` 集合が変わり、realizability が静かに壊れる。要求木のエージェント辺（`ASSIGNED_TO`）は 2.5 の履歴代数で管理し、`CONTROLS` の変更コミットは realizability 再検査を CI で自動的に発火させる（→4.6 の回帰テストと同一の配管）。**要求は紙に書かれた瞬間から腐り始めるのではなく、組織が動き始めた瞬間から腐る。** 腐敗の検出を人間の勤労（定期レビュー）だけに置く設計は、2.3 の「循環なき記憶」と同じ病を持つ。

### 意図の簿記 — belief/desire/intention を照会可能な構造にする

エージェントモデル（BDI: belief–desire–intention、→前節の哲学的地基）を、グラフ上の照会可能構造として実装する——「エージェントに意図があるか」の哲学的問答ではなく、**意図に相当する簿記が存在するか**の検査である（→5.1 の判断の三要素の意図版）。三つの関係名を確定する。

`HOLDS`(agent→Belief: その agent が現在正しいと行動の前提にしている記述。根拠・等級・落日つき——E4 前提の agent 版、→4.1)。`PURSUES`(agent→Goal: その agent が現在実現をコミットしている目的。期限と中止条件つき——コミットメントの簿記)。`COMMITTED_TO`(agent→Plan/Action 群: 目的 Pursuit のための当面の手段への束缚。他 agent への委任を含む——→7.2 の mission packet がこの辺のデータである)。この三辺が揃った agent だけが、3.6 の責任配分の主語になれる——信念・欲望・意図の「哲学的定義」ではなく、**簿記の三辺**として定義する（「意図がある」=「PURSUES と COMMITTED_TO が落日運用つきで登記されている」）。

```cypher
// intent-audit — 意図の簿記の invariant(→3.6 の責任配分の機械検査)
// (a) COMMITTED_TO のある agent に Pursues の親がない(実行だけ追われ目的が不明)
MATCH (a:Agent)-[:COMMITTED_TO]->(p:Plan) WHERE NOT (a)-[:PURSUES]->(:Goal)
RETURN a.id, 'orphan-intention';
// (b) Pursues の goal が落日(Telos chain 切断)でも Commitments が走る
MATCH (a:Agent)-[:PURSUES]->(g:Goal)-[:IN_SERVICE_OF*1..3]->(root:Goal)
WHERE root.sunset < datetime()
MATCH (a)-[:COMMITTED_TO]->(p:Plan) WHERE p.status='active'
RETURN a.id, g.goal_id, 'pursuit-of-dead-telos';
// (c) Belief 集合の落日率(agent の世界観の老朽度)
MATCH (a:Agent)-[h:HOLDS]->(b:Belief)
WITH a, avg(CASE WHEN b.sunset < datetime() THEN 1.0 ELSE 0.0 END) AS stale_rate
RETURN a.id, stale_rate WHERE stale_rate > 0.2 ORDER BY stale_rate DESC;
```

三検査の意味を現場の語で読む。(a) orphan-intention は**影子 act の簿記形**である（目的なしの実行登記——→5.1 のコミットメント欠如が agent スキーマで再発しないための門）。(b) pursuit-of-dead-telos は**目的のゾンビ運用**——上級の目的が落日しても下位のコミットメントが走り続ける（→3.1 の telos_chain の落日と 5.5 のステートマシンのガード落日の合成事故、→3.4 複合式一）。(c) belief の老朽率は agent の世界観が実測から遊離している度で、上位 2 割に再検証（→5.2 の revalidation-patrol の agent 版）を強制する。

BDI の哲学的注釈を最後に一句。この簿記化は「agent に信念があるか」という問いを消去しない——消去するのは、簿記なしの信念語で agent を説明する**特権**である。信念と書かれたものが実は信念のふりをした観測ログでないこと、意図と書かれたものが実行ログの事後叙述でないことを、三検査が保証する（→4.4 の宣言と実体の突合の agent 版）。責任配分（→前節）は、この三辺の主語にのみ配分される——**簿記された主体にのみ責任は載り、載った責任は簿記で追える**。3.6 の結論は 5.3 の結論と同一の定理の要求工学版である（主体は哲学ではなく配列図で立つ）。

### 実行練習

1. 自分のシステムの主要要求10本に `ASSIGNED_TO` と `REFERENCES` を張り、`REALIZABILITY-VIOLATION` 検査を走らせよ。産出された違反のうち、組織図の近年の変更で生じたものの割合を測り、`CONTROLS` の変更履歴（2.5 の Commit 同型）をさかのぼって「いつ要求が腐ったか」の日付を1件確定せよ。
2. `illegal_soft_assignment` 検査の産出ゼロを保証する設計レビューの手順を1ページ書け。手順が「レビュー会議」に依存する場合、会議の欠席がどうシステム品質になるかを 2.3 の保持の循環の語で説明せよ。
3. 夜勤デモの共同遂行（I-42）について、`BELIEVES_OF` の相互構造を片側だけ壊した状態（システムの側だけ team の役割 belief を更新しない）を作り、7.5 の reason panel が何を誤表示するかを予測して書け。壊れた相互 belief が共同遂行をどう崩すか、Cohen & Levesque の条件のどの節が落ちているかを特定せよ。
