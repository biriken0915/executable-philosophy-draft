## 4.1 検証可能性原理 — 意味の境界を引く試み

第2部の第二問——知っていることは十分か——に答えるには、まず「十分」という語の意味を問わねばならない。そして意味を問う哲学伝統のうち、最も大胆で、最も失敗し、最もエンジニアに近い場所に残ったのが、検証可能性原理（verifiability principle）である。この節は分析哲学の一節であるが、同時に本章の設計憲章でもある。**検証できない要求は、実装できない要求である。** この命題は工務店の格言ではなく、ウィーン学団の崩壊した原則の工学的生存形態であり、その出生を知らないまま使うと、4.2 以降で致命傷になる。出生を知らずに使う道具は、道具ではなく呪文である。

### 画像説 — 世界と命題の共役な論理形式

ヴィトゲンシュタイン『論理哲学論考』（1921）から始める。論考の中心装置は画像説（picture theory）である。命題が世界について語るのは、命題の要素と世界の対象が同じ論理的形式（logical form）を共有し、要素の対応が世界への図像（Bild）を構成するときである（「命題は現実の画像である」、4.01）。対応の破れ——命題に現れるが世界に対応しない要素——は無意味（unsinnig）であり、誤りですらない。

要求工学の語に翻訳しよう。**要求文が実装可能なのは、要求語彙の要素とシステム世界の一級の要素（データ・状態・行為）の間に、形式対応が組めるときである。** 3.3 の EARS→LTL→FOL の三段変換は、まさに「論理形式の共有」を手順的に作る作業であった。反転させれば論考の命題は要求分析の命題になる——**形式対応の取れない要求は、実装において誤りですらなく、無意味である。** 「システムは賢く振る舞うべきだ」は偽ではない。偽ですらない。だからテストも実装もできない。

論考のさらに深い所にある境界線（5.6：論証可能なすべてのことは境界線の内側、そして「倫理的なものは表現しえない」）は、3.1 の axiological root（価値の末端は人間が引き受ける、→3.1）と、3.5 の UNKNOWN 登記と同じ姿勢で応答する：形式化の限界の外側を、限界の宣言として形式の内側に書き込む。論考自身は「語れないものには沈黙すべき」（7）で締めるが、本書の伝統——設計の伝統——は、沈黙を**設計された沈黙**（NonRecordingRule、→1.6）に置き換える。沈黙にも所有権と期限を書き込む。

### 検証原理の宣言と、その自爆

ウィーン学団（Schlick、Carnap、そしてPopperの外からの批判）は画像説の境界線を運動纲领へ転化した。**命題の意味は、それを真偽判定する検証手順に尽きる**（Carnap の_weakな形では「確認可能」）。形而上学命題——「絶対者存在す」「歴史の意味」——は認知的に無意味と宣告される。哲学の伝統的問題の多くを、疑似問題として溶解させる試みである。

自爆は早かった。**検証原理自身の命題が、検証原理の要求を満たさない。** 「命題の意味は検証手順に尽きる」は経験命題ではなく、検証手順を持たない。この自己言及敗北は、分析哲学の内側からの最も決定的な反駁である（Quine の経験主義の二つのドグマ、1951 がさらに境界線そのものを相対化した）。

敗北の記録を細かく読んでほしい。学団は敗北しながら、二つの遺産を残した。第一に、境界線を**宣言ではなく手続に置く**という作法（意味の判定は形而上学者にではなく、検証手順の設計者に委ねる）。第二に、境界を**原理の単一線から復数の実務線へ**分解すること（厳密な検証・弱い確認・間接的検認——線は一本ではなく、濃淡の帯になる）。1.2 の「境界は線ではなく面である」が、ここで再び現れる。面として引かれた境界のみが、設計に使える。

### なぜ今もエンジニアリングでは生き残っているのか

哲学の教科書では検証原理は死んだ扱いである。ところがソフトウェアの現場では、検死は行われていない。受入基準が書けない機能は受け取らない（acceptance criteria）、Definition of Done、契約の受入条項、TDD——「検証手順が存在しない要求は、実装しても検証できないから渡さない」という運用規則は、検証原理の生存形態そのものである。なぜ、哲学で崩壊した原則が現場で生き残るのか。理由は三つある。

**其一、現場は自己言及を運用で回避する。** 「検証できない要求は渡さない」自身の正当化は、組織の被りリスクの経験統計であり、哲学的基礎づけを必要としない。実践規範は基礎づけなしに安定する（Poppers の批判的合理主義が合理基準そのものの基礎づけを放棄したように）。現場の検証原理は、純粋原理ではなく**契約の条項**である——契約は自己言及を要らない。

**其二、現場は境界を線として扱わない。** 実際の実務では、完全検証（テスト全網羅）、確率的検証（負荷・MTBF）、相対評価（UXレビュー）、専門家レビュー——四つの検証等級が併存し、等級の低い検証には承認の重み（2.6 の級）を載せる。復数の検証等級の併存という設計が、検証原理を自爆から守っている。

**其三、現場では「無意味」の実害が確定している。** 「賢く振る舞うべきだ」を実装したシステムの動作は、必ず何かになる——何かが起きた後で「賢くはなかった」と非難しても、実装者の過失を認定できない。無意味要求の実装は、**責任配分の不能を製造する**。4.1 の命題（検証不能要求＝実装不能要求）は、意味論の命題としてでなく、責任論の命題として現場に根を持つ。

### 三つの実務規範 — 本書の検証憲章

上記から、本書の検証憲章を三条で置く。この三条は 4.2（CQ）・4.4（契約）・4.5（sat 判定）のすべての実装の前提条文として機能する。

**憲章条一（境界の等級化）**：検証は単一の yes/no ではなく、四等級の手続である。E1=決定論的テストで完全判定、E2=統計・確率的手続、E3=専門家協議の合意記録（→6.2 の妥当性要求）、E4=宣言のみ（telos・価値・公理）。等級は要求ノードに `verif_class` として登記し、E3/E4 には承認の級（2.6）と再検証期限（2.3 の保持寿命）を必ず添う。

**憲章条二（自己言及の登記）**：検証手続自身の正当化は E3/E4 に属する（テスト設計の妥当性はテストでは検証できない）。CI の設定・ゲートの閾値・境界値の決定は、要求ではないが要求を支配する決定であり、**E4 級の宣言として履歴代数に載る**。4.2 の CQ の合意形成が知識政治である、という準備はこれでできる。

**憲章条三（残余の移管）**：E1〜E4 のいずれにも載せられない要求文言（「信頼できる」「誠実な」）は、削除ではなく **phronesis 要求**として区別し、判断主体（人間エージェント、→3.6）への割当として登記する。機械実装からは去るが、設計からは去らない——判断の場（UI・手順・教育）の設計要求に転化する（→8.5）。

```python
# verif_class_register.py — 要求ノードへ検証等級を登記する最小器
# 哲学: 等級の登記は要求の「強さ」ではなく「責任の配分先」を決める。
# E1 が失敗なら CI が止める。E3 が失敗なら誰の審議を止めるか、名簿に書く。
from dataclasses import dataclass

@dataclass(frozen=True)
class VerifRegister:
    req_id: str
    verif_class: str        # 'E1'|'E2'|'E3'|'E4'
    procedure: str          # 手続への参照(テストID・負荷計画・審議記録ID)
    approver_level: str     # 2.6 の級: 'L0'..'L3'
    recheck_due: str        # 2.3 の保持寿命。期限切れ = 検証も deprecation へ進む
    # E4 の procedure は "declared-by:<committee>:<date>" 形式を強制
    def __post_init__(self):
        if self.verif_class == "E4" and not self.procedure.startswith("declared-by:"):
            raise ValueError("E4 must name its declarer — 境界の宣言に匿名を許さない")
        if self.verif_class in ("E3", "E4") and self.recheck_due == "":
            raise ValueError("E3/E4 require recheck_due — 合意は腐る、腐る物は期限を持つ")
```

### 失敗例の解剖 — 「ユーザーフレンドリーなUI」の四等級降格事故

実例で締める。ある要求文書の「ユーザーフレンドリーなUI」は、そのままでは E4 でも検証不能だった（何がフレンドリーかの宣言者もいない）。運用で降格（＝実装可能化）の試みが行われた：(1) UIレビュー会を月次で E3 として制度化（審議記録＝合意の履歴）。(2) タスク完遂時間を E2 の統計的手続に（負荷試験と併走）。(3) 「3クリック以内」を E1 の契約に抽出。**残った残余**——「フレンドリーさ」の身体感覚・心理的安全の部分——は phronesis 要求として新人教育とレビュー会の手順要求へ移管された。残余の実装先がコードから人間の場へ移る瞬間を、読者は見逃さないでほしい。第4部・第5部の UI 設計（→8.5）は、この移管先の設計にほかならない。

検証原理は死んだ。その埋葬地の上に、四等級の境界手続と、境界の宣言簿記と、残余の移管路が建っている。本章は以降、この上物を部品として組んでいく——まず CQ（4.2）は E1/E3 の境界手続そのものである。

### 検証可能性原理の落日 — 原理自身を E4 で宣言する

検証可能性原理（→前掲：意味の境界を検証可能性で引く試み）は、歴史の中で最も速く老朽化した設計原理の一つである（論理実証主義の検証原理——その失敗の解剖は→4.5 に委ねる）。本書がこの原理を「試み」という語で標題に置くのは誠実さではなく、**設計原理としての落日を最初から内蔵させる**ためである。宣言の三類型（E1 実測級 / E2 見通し級 / E4 前提級、→本書の級体系）で言えば、検証可能性原理は E2 見通し級の原理であり、落日周期（例 2 年）と再検証条件（「検証不能だが生存に必要な意味」——沈黙・暗黙知・信頼——を扱う代替機構の設計実績）を持つ。落日が回るとき、原理は自動降格し、その slots（沈黙の設計→1.6、残余の設計→1.2、討議→6.2）が原理の墓標ではなく**後継実装**として評価される。

この自己落日の構造を、本書のあらゆる「原理」に適用する一般形として確定する。

```python
# principle_charter.py — 設計原理の憲章(落日つき宣言の Python 表現)
class Principle(BaseModel):
    p_id: str                     # 'execphil://principle/verifiability'
    statement: str                # 原理の文
    grade: Literal["E1", "E2", "E4"]
    sunset: str                   # ISO 日付
    successors: list[str]         # 後継設計(落日時に評価される代替機構)
    def review_due(self) -> str:  # 落日審議の議題自動生成
        return (f"{self.p_id}: 落日到達。successors={self.successors} の実測を"
                f"評価し、extension(実測証拠つき)/retire/replace を E3 審議で決定")
```

`successors` を宣言時点で書かせる設計の意義を強調する。原理の落日設計で最も危険なのは、落日させて置き去りにすることである——原理を退場させられた組織は、その原理が扱っていた問題を扱う機構なしに残される（検証可能性を捨てた組織は「検証できないが重要なもの」を扱う語彙を失い、意味全体を「信頼だから仕方がない」へ退避させる）。**落日条項は後継の指名を伴うときだけ mature である**——6.6 の落日設計（延命に実測を要する）が、ここで原理のスケールに拡張される。

終章のアポリア（知の継承）に伏線を一本張っておく。検証可能性原理の落日は、本書の不変条件三（目的は閉じない、→4.5）と同名の定理の局所版である——**検証可能性で境界を引く試みは、境界の周縁で必ず意味を切断し、切断された意味が中心を維持している**。この自己言及を認めた上でなお検証可能性を「試み」として使うことが、4.1 の設計の全内容である（原理を信じることと、原理落日の管理人になることは違う——後者が本書の読者に要求する態度である）。

### E1/E2/E4 の分布計測 — 宣言階級の scorecard

検証可能性の境界設計（→前掲の E1 実測級・E2 見通し級・E4 前提級）は、分布として測るまで設計と呼ばれない。宣言の級がどこに集中しているかを四半期ごとに測る三本の照会を確定する。

```cypher
// grade-distribution — 宣言級の分布と偏り(四半期 scorecard)
MATCH (n) WHERE n.grade IN ['E1','E2','E4']
RETURN n.grade, count(n) AS n,
       avg(duration.between(n.at, coalesce(n.next_review, datetime())).days) AS mean_age;
// 偏り一: E4 過密 — 前提級が実測級より多い領域は「信じて回している」領域
// 偏り二: E2 の滞留 — 見通しが実証も放棄もされないまま生き延びている
MATCH (n {grade:'E2'}) WHERE n.sunset < datetime() AND NOT (n)<-[:RESOLVED]-()
RETURN count(n) AS stranded_horizons;
// 偏り三: 級なし宣言 — 級を負わない主张(4.1 の中心の空白)
MATCH (n:Claim) WHERE n.grade IS NULL RETURN count(n) AS ungraded_claims;
```

三つの偏りの診断名を置く。**E4 過密**——前提で回している部門（落日審議の積圧とセットで診断する：前提が多く、再審議が遅い組織は「信任で走る汽船」——→7.1 の phronesis 残高の低い領域と重なる）。**stranded_horizons**——実証も放棄もされなかった E2 の残骸（→3.3 放棄表の落日版。E2 は E1 か E4 か放棄かのどれかに必ず着地する設計を sunset 審議に持たせる）。**ungraded_claims**——級を負わない主张。書物・会議事録・ダッシュボードの表題に級が載らない限り、ungraded は永遠に最多になる（本書が本書の級を卷頭に載せる理由、→preface の訳語の責任·終章の落日条約と同じ自己适用）。

分布計測の目的は「E1 を増やす」ことではない——**分布の形が、その組織がどこで現実に触れ、どこで自我に回っているか**の地図になることである（E1 密度の高い領域=現実と接触している領域。E4 の厚い領域=前提で自己を維持している領域。地図として重要なのは境界の位置で、E4 が悪ではない——自覚された E4 は設計、非自覚の E4 は腐敗、→6.6）。4.1 の検証可能性原理が最後に果たす役割は、世界を形式化可能な区域と不可能な区域に切断することではなく、**切断線の現在地を四半期ごとに報告させること**である（原理の落日設計・→前掲の principle_charter と、この分布計測が一対）。

### E2 宣言カードの二字段 — 見通しを落日つきで持つ形

E2 見通し級（→前掲の実証も放棄もされていない中間の宣言）に、落日可能の形を与える最小の二字段を置く。**其一、`horizon`（いつまで見通すか——時刻でなく事件で書ける：「次回検修まで」「新設备導入まで」）**。**其二、`refute_by`（何が起きたらこの見通しは退くか——1 行で書ける反証条件）**。二字段が揃うと E2 は E1 の未达としてではなく**未来の E1 の預約**として存在する（horizon 到达時刻に refute_by の突合が自動照会され、达則 E1 昇格・退則 E4/放棄に落ちる——2.6 の級の升降が手動儀式でなく時刻表になる、→3.4 障礙の落日が実例突合で回る機制の 4 章版）。

字段の哲学上の位置を一環：refute_by を書けない E2 宣言は**ベルイマン的な主张**（反証不能を自己の不可侵に使う）で、本書の正规系では受理されない——→4.5 の z3 と 5.3 の概率の約束（withdrawal_conditions）が同じ字段を別々の語言で要求している事実は、**反証条件が形式化全体に跨る横断の不変条件**だからである。字段名を E2/CQ/prob offer で統一する（`refute_by` の一個の語で三機構が結ぶ—→4.2 CQ Q3・→5.3 withdrawal・→8.5 falsifiable_if の同値化、→B.3 計器索引）。

### 実行練習

1. 自分の要求文書から5本を四等級に振り分けよ。E1 に落ちる本数がゼロなら、そのシステムは「実装できているが渡せていない」システムである（受け入れ根拠が E3/E4 ばかり）。E4 の `procedure` を declared-by 形式で書き直し、2.6 級 L2 の変更として登記する手順文を1ページ書け。
2. 「ユーザーフレンドリー」型の phronesis 要求を自分のプロダクトから1本選び、三つの降格案（E3 審議化・E2 統計化・E1 抽出）を1本ずつ設計せよ。残余の移管先（教育・レビュー・UI）の実務担当者をエージェント名簿（→3.6）へ登録し、`RESPONSIBLE_FOR` 辺を張れ。
3. 検証原理の自己言及敗北を、あなたの CI の閾値設定に当てはめて書け（「閾値の正しさ」を CI 自身が検証できない構造）。その E4 宣言の再検証期限をいつに設定するか、設定根拠の議論記録を `Commit.intent` 形式（→2.5）で1件作れ。
