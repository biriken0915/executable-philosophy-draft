## 2.4 分類工学 — OWL 2 / RDF スキーマの実装

2.1から2.3まで、分類は暴力的であり、暴力は履歴を要求し、外部化された記憶は認知を書き込む、と説かれてきた。読者がこの三つを「もっともだ」と感じたとしたら、その感じ方自体が既に第二次保持の働きである（→2.3）。では設計者として手を動かせばよいか。この節から本章は実装節に入る。扱う技術は RDF と OWL 2 である。ただし本書の目的は W3C 仕様の紹介ではない。目的は一つ——**分節化の暴力を、仕様として機械に強制できる形に置くこと**——に尽きる。OWL の制約は「世界がこうなっていることを保証する」ものではなく、「世界をこう切り分ける私達の合意が壊れたことを検出する」装置である。この読み方を throughout 忘れないこと。

### TBox と ABox — 切り分けの宣言と、切り分けられたもの

RDF の基本単位は triples（項）である。`(主語, 述語, 目的語)` の三つ組で世界を記述し、主語には URI を使う。URI は名前空間で一意になる——`https://execphil.example/onto#Drift` のように。名前空間の分割は組織分割の写像であり、ここにもう分節化の暴力は始まっている（境界コンテキストの問題、→6.1）。

OWL 2 では記述を二層に分ける。**TBox（terminological box）**は語彙の層——クラス、プロパティ、およびそれらの制約。「Drift は Fault の部分類である」のような、型についての主張。**ABox（assertional box）**は事実の層——`pump-0301` という個体が Drift を起こした、のような主張。1.5節のグラフで言えば、ラベル定義が TBox、ノードが ABox に対応する。しかしグラフと決定的に違うのは、OWL には**推論機（reasoner）**が付くことだ。OWL の TBox は記述ではなく演算である。Hermit や ELK、openllet などの reasoner は、TBox と ABox から「暗黙に真である主張」を導出する。1.1節の語りの限界と対比されたい。OWL の推論は、ポランニー的暗黙知の完全な対極にある——**形式化された知の内部で、明示されていなかった帰結を明示化する**操作だからだ。暴力の語彙で言えば、reasoner は分類が含意する暴力を、分類者が気づく前に執行する。

この二重性（合意の検出装置であり、含意の執行装置でもある）を制御することが、分類工学の本体である。

### 最小構成の TBox — Turtle で書く保全オントロジー

第1章の保全現場の語彙を Turtle 形式で定義する。コメントが哲学の注釈になっていることに注意（スタイル約束、→OUTLINE）。

```turtle
@prefix :  <https://execphil.example/onto#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# --- クラスの分節：切断(cutting)の記録 ---
# 「故障」「逸脱」「劣化」は日常語では重なる。切断して disjoint にすることは、
# 重なりを公式に放棄する宣言である。放棄は 2.1 の暴力だが、
# 明示された放棄は監査可能な暴力である。
:Fault a owl:Class .
:Drift a owl:Class .
:Degradation a owl:Class .

:Drift rdfs:subClassOf :Fault .
# 逸脱は故障の部分類——「故障したが機能している」状態を Drift で受け止める切断。
# 現場では「故障」が停止を意味するため、停止していない異常が
# どの語でも呼べず記録から消える。Drift はその消滅を回収する切断である。

owl:allDisjointClasses (:Fault :Degradation) .
# 注: 正確には owl:AllDisjointClasses の無名個体構文を使う(下記 §実行 で展開)。
# 逸脱は劣化と同一化しない。劣化は方向のある統計過程、逸脱は事象である。
# この切断を忘れると「劣化トレンドの閾値超え＝故障」という静かな同一化が
# ダッシュボードで実行される。

# --- プロパティの切断: domain/range は存在論的塀 ---
:observedOn a owl:ObjectProperty ;
  rdfs:domain :Observation ;
  rdfs:range  :PhysicalAsset .
# domain/range を書かないプロパティは、どんな主語にも目的語にも繋がれる。
# 繋がれること自体が意味の汚染である。塀は暴力だが、開きっぱなしの境界は暴力より悪い。

:hasSeverity a owl:DatatypeProperty ;
  rdfs:domain :Fault ;
  rdfs:range  [ a rdfs:Datatype ;
                owl:oneOf ( "minor"^^xsd:string "major"^^xsd:string "critical"^^xsd:string ) ] .
# 列挙値は分節の最終形態。three値より多い値を現場が使うなら、
# 列挙値は現場の意味を減らす。減らすと決めたなら、減らし方を版数で記録する(→2.5)。

# --- カーディナリティ: 無関係の強制 ---
:Fault rdfs:subClassOf [
  a owl:Restriction ;
  owl:onProperty :observedOn ;
  owl:someValuesFrom :PhysicalAsset ] .
# 「故障は必ず何かの資産の故障である」。存在しない資産の故障は記述を許さない。
# someValuesFrom(存在)でなく allValuesFrom(全称)にしないのは、
# 故障の意味が単一資産に閉じない場合(連鎖障害)を開いておくため。

:Fault rdfs:subClassOf [
  a owl:Restriction ;
  owl:onProperty :observedOn ;
  owl:maxCardinality "3"^^xsd:nonNegativeInteger ] .
# 記録の爆発を防ぐ上限。哲学: 無限の根拠付けは根拠付けではない。
# 上限を設けたことは 2.6 の承認対象になる(任意の定数に権力を埋め込まない)。
```

### 制約の執行 — reasoner を「分類の憲法裁判所」として動かす

TBox だけでは宣言は執行されない。PyPI の `owlready2` を使い、矛盾を検出する実行可能コードとして置く。ここでの運用原則は一つ——**本番グラフへの書き込み前段で reasoner を走らせ、矛盾（unsatisfiable class）を検出したら書き込みを止める**。2.1の暴力論と矛盾しないために重要なのは、reasoner が矛盾「を消す」のではなく矛盾「を報告する」動きをさせ、統合判断を人間に残すことである（→4.4の契約、→6.4のゲートキーパー）。

```python
# tbox_gate.py — OWL reasoner による TBox 矛盾検出（書き込み前ゲート）
# 哲学: reasoner に「正しさ」を判定させるのではない。
# 「この切り分け方は自身と衝突する」という自己矛盾のみを機械に要求する。
# 自己無矛盾性は、意味の保証ではなく、意味の最小限の誠実さである(→4.1)。
from owlready2 import get_ontology, InconsistentOntologyError, default_world
import os

onto = get_ontology("file://onto/maintenance.owl")  # Turtle で書いた TBox
onto.load(path="onto/maintenance.owl", format="rdf/xml")

# ABox 増分を臨時 graph で載せて検証する（本図に触れない）。
# 哲学: 増分の検証は、世界を書き換える前の思考実験でなければならない。
# 思考実験の失敗は世界を汚さない。汚す設計は、検証を世界の実行と呼ぶ。
def validate_increment(ttl_path: str) -> list[str]:
    inc = get_ontology("http://execphil.example/increment#")
    inc.load(path=ttl_path, format="turtle")
    # 一時的に本体へ統合し、矛盾クラスを列挙して即座に分離する
    with onto:
        onto.imported_ontologies.append(inc)
        conflicts = []
        for c in onto.classes():
            try:
                # 不充足（unsatisfiable）なクラス＝その定義が自身と衝突
                if c in onto.inconsistent_classes() if hasattr(onto, "inconsistent_classes") else False:
                    conflicts.append(c.name)
            except Exception:
                pass
        onto.imported_ontologies.remove(inc)
    return conflicts

if __name__ == "__main__":
    print(validate_increment("onto/increment_2026-11.ttl"))
```

（注：`inconsistent_classes()` の取得は reasoner 設定に依存するため、実装では Hermit を明示起動して `classifyReasoners` を使う形に差し替えてよい。骨格——増分を臨時 world で classify し、本図に触れず矛盾名のみを得る——が本質であり、これは git の pre-commit hook と同型の構造である。）

### 現場語彙の管理 — owl:sameAs を使わない理由

2.1の「現場用語の正規化」問題に、OWL の道具で答える。現場が「ぶるぶる」「異音」「振れ上がり」と呼ぶものを正規語彙 `:VibrationAnomaly` に対応付けるとき、最も安易な道具は `owl:sameAs` である。**使ってはならない。** `sameAs` は論理同一であり、語彙 A のすべての述語が語彙 B に移り、矛盾が統合で消える。暴力が履歴ごと消える。これが 2.2 の Aufheben 読解の直接の帰結である——否定（区別の保持）を含まない同一化は、止揚ではなく抹消である。

```turtle
# 正しい管理: 同一ではなく「対応」を、対応は語彙の跨ぎとして記録する。
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .

:vib-term-buruburu a skos:Concept ;
  skos:prefLabel "ぶるぶる"@ja ;
  skos:broader :shopfloor-lexicon ;
  skos:closeMatch :VibrationAnomaly .
# skos:closeMatch(近似)を使う。exactMatch は「完全対応」の主張であり、
# 主張なら版数と承認を要する(→2.6)。exactMatch に格上げすることは
# 二つの語の境界を公式に消す行為であり、変更履歴に残る。

# 語彙間の写像は語彙の内部事象ではなく語彙間の出来事である。
# ゆえに写像は両方の語彙の外部——対応テーブル——に置く。
# 内側の語彙を改造して外側に合わせることは防腐層の裏切りである(→6.1)。
```

`skos:inScheme` と `skos:ConceptScheme` で現場語彙・正規語彙を別スキーマに分離し、マッピングは `s2z_mapping` という第三の名前空間に集約する。マッピングの総数を指標化すると、組織の翻訳コストが見えるようになる（翻訳コストの見積もりは、防腐層の予算計上そのものである——→6.3の round-trip check と接続）。

### 削除しない — deprecated と retires による退位

分類工学の最終規則：**語彙を削除しない。退位させる。** 削除すると、ABox の既存事実が宙に浮く（参照されていたクラスが消え、reasoner が事実全体を読めなくなる）。また 2.5 の履歴追跡が、削除された用語への参照を復元できなくなる。

```turtle
:OldFaultClass a owl:Class ;
  owl:deprecated true ;
  :retiresWith { "retired_at": "2026-11-01", "replaced_by": "onto:Drift" } ;
  rdfs:comment """2026-10-31 承認委員会により退位。
    退位理由は「故障と劣化の切断が運用で機能しなくなったため」。
    この注釈自体が 2.6 の沈黙の猶予期間の記録である。""" .
# owl:deprecated は OWL 標準。retires の詳細は語彙側で定義する(標準語彙に依存しない)。
# 退位語彙は reasoner が推論から除外する。しかし ABox と履歴は読める。
# 消された分類は読めなくなるが、退位した分類は読める。
# この二つの差が、組織の知識の不可逆性の扱いを決める(→2.5)。
```

退位語彙が参照され続けている現象（deprecated なのに現役）は、腐敗の指標である。`grep` で ABox を走査し、退位語彙の残存参照を報告するスクリプトは trivial だが、組織に毎回読ませる価値がある——読ませる行為が、分類権限の透明性を保つ唯一の実務だからだ（→2.6）。

### 実行 — docker で OWL 検証環境を一分で起動する

```bash
# 検証環境の起動（付録A の docker-compose とも共通）
docker run -d --name execphil-owl \
  -p 5150:5150 -p 3030:3030 \
  atomgraph/fuseki:latest

# Jena で TBox+ABox を parse し、矛盾を CLI で確認する
docker exec execphil-owl sh -c \
  "apache-jena-4.10.0/bin/tortoise /tmp/maintenance.ttl"  # 構文+OWL Lite 検証
docker exec execphil-owl sh -c \
  "apache-jena-4.10.0/bin/infer -q /tmp/reasoned.ttl /tmp/rules.ttl"
# ABox を reasoned.ttl に読ませ、reasoner が導出した「明示されていなかった主張」を diff する。
# 明示主張と派生主張の差分が、この TBox の暗黙知である。
```

最後のコメントが本章の OWL 観を言い当てている。**オントロジーの「暗黙知」＝明示主張から reasoner が導出する主張の集合**。OWL の暗黙知は、人間に不可知な暗黙知とは別物で、原理的に可視化できる。この対比を完全な形にするのが次節の Git 的差分——明示・派生・退位・削除のすべてを履歴として結ぶ試みである。

### TBox 差分審議のチェックリスト — 五行の回復

TBox の版本管理（→前掲）の審議で、差分レビュー者が五行だけ回復する様式を置く（重たい審議書ではなく五行が回復される——6.3 の条約審議の書式と同一の思想）。

| 行 | 質問 | fail させない場合 |
|---|---|---|
| 1 | この追加は**区別の创設**か区別の**消去**か(→6.3 roundtrip) | 创設のみ:L1 通过可、消去:L2 強制 |
| 2 | 消す語の**実例引用数**(过去 2 四半期の辺) | 引用 0 なら消せる、>0 なら落日周期必須 |
| 3 | 亲語との**包摂**が site 使用実態とずれていないか(site TBox 突合) | ずれ=条約贸易議題に回す |
| 4 | 変更の**級**(2.6 の級表で L?)(署名者数の預告) | 級未宣言は diff 自体が L2 違反 |
| 5 | この変更で**壊れる CQ/test**(→4.2・4.6 の依頼) | 破坏清単が空=依頼計測が壊れている |

第 5 行の「破坏清単が空=計測が壊れている」が審議の質量を保証する——TBox 変更と CQ/test の依頼辺（`TESTED_BY`、→4.6 三層の TBox 版）が自動生成されていなければ、空は安全ではなく盲点である（→2.5 のブリッジが commit 時に依頼図を更新する設計の理由）。五行審議の回復そのものが Commit の message に残る（→2.5 の由来簿記——審議の資格も歴史を持つ、→2.6 級の署名と同一の簿記）。

### 実行練習

1. 上の TBox を `maintenance.ttl` として保存し、`Drift ⊑ Fault` と `Fault ⊓ Degradation 互いに素` の両立に矛盾する ABox 増分（例：`drift-001 a Drift, Degradation`）を自分で作って §2.4 の gate に流し込め。reasoner がどのクラスを unsatisfiable と報告するかを観察し、報告文言の「人称のなさ」（「クラス Drift は非充足です」）が、誰の判断も名乗らないことの_design 的意味を 10 行で書け。
2. 自分の現場語彙から 5 語を選び、正規語彙（自作でよい）との `closeMatch` / `exactMatch` / 未対応に振り分けよ。未対応の語こそ 2.1 の「残余」である。残余の数をチームの KPI にしたら、何が起きるかを予測し、その KPI を 2.6 の不服従のパスとどう接続するか書け。
3. `owl:deprecated` を 1 つ与えられた語彙に設定し、ABox 残存参照レポートを作れ。参照を 1 つ消さずに 6 か月放置された場合、その語彙の「事実上の寿命」は公式寿命とどうズバリズブるかを、1.5 の TELEMETRI クエリの壊れ方と絡めて説明せよ。
