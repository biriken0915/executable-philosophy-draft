## 2.5 脱知識化の追跡 — Git的コミットツリー

2.4で、語彙は削除せず退位させ、マッピングは抹消せず記録する、と決めた。しかし「退位」や「記録」は状態であり、状態だけでは暴力の歴史は復元できない。必要なのは**変更そのものの履歴**である。分類がどの順で、誰によって、どの意図で書き換えられ、そのとき何が失われたか——この連鎖をデータとして保持する構造が、本章のいう Git 的コミットツリーである。名前の由来は明白で、ソースコード管理システム git が実践している「変更の不可逆的追跡」を、RDF の語彙そのものに移築するからである。ただし git そのものをオントロジー管理に使うのではない（後述の理由で、それは半分正しく半分間違っている）。正しいのは、git の**代数**——コミットが親を持ち、変更が差分で表現され、履歴がマージできる——を RDF データとして再発明し、グラフの上に載せることだ。脱知識化（déqualification、熟練の剥奪。スティグレールのプロレタリア化の現場形、→8.1）の追跡とは、剥奪がどのコミットで起きたかを質問可能にすることである。

### 主張への主張 — RDFS 再指定（reification）

RDF の triples は「世界についての主張」である。オントロジー管理が必要とするのは「主張についての主張」である——いつ、誰が、どの根拠で、この triple を主張したか。RDF はこれを第一級の手段として持っており、RDF 1.1 Semantics の **RDF reification（再指定）** がそれである。 triples の主語・述語・目的語を、それぞれ別の triples の対象として表現する。

```turtle
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prov: <http://www.w3.org/ns/prov#> .   # W3C PROV-O を来歴語彙として採用する(2.3の来歴原則)

# 原 triples（この triple そのものは後から変更される——削除されるかもしれない）
_:fact1 rdf:subject   <urn:pump-0301> .
_:fact1 rdf:predicate <https://execphil.example/onto#hasFault> .
_:fact1 rdf:object    <urn:fault-77> .

# 再指定 triples（原 triples が「主張された」という主張）
<urn:assertion-A17> a rdf:Statement ;
  rdf:subject   _:fact1 ;   # 多くの implementations では原 triples を直接指す
  rdfs:comment  "2026-11-02 03:11、センサー S-0301 の観測に基づく" .
# 実際には rdf:subject/predicate/object は原 triple の成分を直接指す形で書く。
# ここでは概念の骨格のみを示す(完全形は §commit の JSON→RDF 変換で実装する)。

# 主張についての主張（me-born の主張）
<urn:assertion-A17> prov:wasAttributedTo <urn:person-tanaka> ;
  prov:wasGeneratedAtTime "2026-11-02T03:11:00Z"^^xsd:dateTime ;
  prov:wasDerivedFrom <urn:telemetry-E99> ;
  :assertedInCommit <urn:commit-0042> .
# 削除(this assertion の撤回)も同型の triples で書ける。
# 「取り消し」を再指定できることが RDF の中核的な力である。
```

W3C の PROV-O（Provenance Ontology）を来歴語彙として採用するのは 2.3 の原則である。来歴のない保持は幽霊だ、とあちらで決めた。再指定＋PROV-O は、幽霊を名簿に登録する手続きである。

一方で再指定には定評のある弱点がある。 triples が4倍になる冗長性、参照の煩雑さ、そして——最も重要な——**再指定 triples 自体が変更・削除されうる**という無限後退である。すべての履歴を RDF で持つ設計は、履歴の履歴の設計を要求される。この無限後退を断つ pragmatic 解が、次節の「コミットは RDF の中に置くが、コミット自体の不変性は外部の append-only ログが担保する」という二層構造である。

### コミットの代数 — RDF の中に置く git

設計を確定する。コミットは `Commit` クラスの RDF 個体としてグラフ内に置く。各コミットは、差分（`adds`, `retracts` の関連）と、親コミット（`parent`）と、作者（`prov:wasAttributedTo`）と、意図の宣言（`intent`——自由文、省略禁止）を持つ。グラフの「いま」は HEAD コミットから到達可能な主張集合として**派生**する。グラフの全過去は、コミットグラフを横断して**照会**できる。

```turtle
<urn:commit-0042> a :Commit ;
  :parent <urn:commit-0041> ;
  :intent """3号ポンプの Drift 頻度上昇。夜間点検制約の適用条件を絞り込む。
            失うもの: 夜間でも「様子を見る」選択の記録余地(→1.6 NonRecordingRule 参照)。""" ;
  :adds     <urn:assertion-A17> ;       # ABox 増分は主張ノードとして指す
  :retracts <urn:assertion-A09> ;       # 撤回も主張ノードで指す(削除ではない)
  prov:wasAttributedTo <urn:person-suzuki> ;
  :signedBy <urn:person-lead> .
# :intent が自由文でありながら省略禁止なのは、意図の不在が
# 最も危険な脱知識化の印だからである(2.6 の承認フローはこの検証と結合する)。
# 意図文が 1.6 の SchemaDecision.assumed と結ばれ、
# 設計の前提簿記がコミット代数に接続される。
```

HEAD の意味論をクエリで定義する——ここがグラフであることの利益が最大に出る場所だ。

```cypher
// 「現在のグラフ」= HEAD から親を辿って再構成する主張集合。
// 過去状態の読み取りは、HEAD を任意のコミットに差し替えるだけである。
// 過去は保存されない。過去は再構成される(→1.5 「場は保存されない」と同型)。
MATCH path = (head:Commit {sha: $sha})-[:parent*]->(c:Commit)
UNWIND nodes(path) AS com
WITH com ORDER BY com.seq DESC     // 新→旧。同じ主張は新しい方が勝つ
MATCH (com)-[:adds|retracts]->(a:Assertion)
WITH a.uri AS uri, collect(com)-[0] AS first_touch,
     max(CASE WHEN (com)-[:retracts]->(a) THEN com.seq END) AS retracted_at,
     max(CASE WHEN (com)-[:adds]->(a)     THEN com.seq END) AS added_at
WHERE added_at IS NOT NULL AND (retracted_at IS NULL OR retracted_at < added_at)
RETURN count(uri) AS current_assertions;
```

同じ代数を git 実体の pre-commit hook と結ぶ二層構造を先に許こう。RDF コミット履歴は「意味の履歴」であり、git オブジェクトストアは「ファイルの履歴」である。両者は別物として保ち、`signedBy` と git tag を対応させる。**git をオントロジーの単一の真実にしてはならない**理由は二つある。第一に git は差分の単位をファイルと考えるが、意味の単位は triple であり、ファイルの分割次第で意味の境界が動く（意味はファイル境界を跨ぐ——分類権限とリポジトリ権限が一致しない問題、→2.6）。第二に git の履歴は書き手の都合で書き換えられ（rebase）、意味の履歴は書き換え不能でなければならない（force push を許す履歴は、暴力の履歴を消せる履歴である）。

### 差分トラッキング — git diff を RDF 再指定に変換するPython

既存運用が git でオントロジーを管理している場合——多くのチームがそうである——、この bridge script が git 史を意味史へ翻訳する。

```python
# git_history_to_rdf.py — git diff(意味語彙ファイル) を RDF 再指定コミットへ変換する
# 哲学: 翻訳は復元ではない。git 史に残っている「なにが変わったか」と、
# RDF 史に載せる「意味がどう変わったか」は別物である。
# この script は両者の間に対応を張り、差異を :gap として記録する。
import subprocess, hashlib, rdflib
from rdflib import Graph, URIRef, Literal, Namespace, RDF

GIT  = "git"
R    = Namespace("http://execphil.example/reification#")
P    = Namespace("http://www.w3.org/ns/prov#")

def git_log(onto_file: str):
    # 各コミットでの file 差分を unified diff ではなく「追加された語彙行/削除された語彙行」で取る
    commits = subprocess.run([GIT, "log", "--format=%H|%aI|%an|%s", "--", onto_file],
                             capture_output=True, text=True).stdout.strip().split("\n")
    for line in reversed(commits):   # 古い順 = 意味の出生順
        sha, when, author, subject = line.split("|", 3)
        diff = subprocess.run([GIT, "show", "--format=", sha, "--", onto_file],
                              capture_output=True, text=True).stdout
        added   = [l[1:].strip() for l in diff.splitlines() if l.startswith("+") and not l.startswith("+++")]
        removed = [l[1:].strip() for l in diff.splitlines() if l.startswith("-") and not l.startswith("---")]
        yield sha, when, author, subject, added, removed

def to_rdf(onto_file: str) -> Graph:
    g = Graph()
    g.bind("r", R); g.bind("prov", P)
    head = None
    for sha, when, author, subject, added, removed in git_log(onto_file):
        c = URIRef(f"urn:git:{sha}")
        g.add((c, RDF.type, R.Commit))
        if head: g.add((c, R.parent, head))
        g.add((c, P.wasAttributedTo, URIRef(f"urn:git-author:{author}")))
        g.add((c, R.intent, Literal(subject)))
        # git の author はコードを書いた人であり、意味を決めた人とは限らない。
        # 対応は :gap として明示する(翻訳のロスト測定、→6.3 の round-trip 同型)。
        g.add((c, R.gap, Literal("git author ≠ semantic decider; map via signed-off-by")))
        for kind, lines in (("adds", added), ("retracts", removed)):
            for i, ln in enumerate(lines):
                a = URIRef(f"urn:assertion:{sha}:{i}")
                g.add((a, RDF.type, R.Assertion))
                g.add((a, R.rawText, Literal(ln)))   # 解析不能な行も rawText で生きさせる
                g.add((c, getattr(R, kind), a))
        head = c
    return g

if __name__ == "__main__":
    g = to_rdf("onto/maintenance.ttl")
    g.serialize("onto/git_as_reification.ttl", format="turtle")
    print(f"{len(g)} triples — git history has become askable history")
```

`rawText` の設計思想を補強しておく。git 史の行が RDF として解析できるとは限らない（コメント変更、空行、フォーマット）。解析できないものを捨てると、翻訳の残余が履歴から消える——2.1 の残余の原則は履歴にも適用される。rawText として保存された行は、後年、意味解析の道具が伸びたときに救済される。保存は未来への投機である。

### 失われた意味の復元クエリ — 消えたラベルを辿る

いよいよ本章の目的のクエリである。「半年前に存在し、いま存在しない分類」を、その分類が存在した期間の事実ごと復元する。脱知識化の診断——ある語彙が死んだ時期と、技能剥奪が起きた時期が重なるか——はこの照会の上に成立つ。

```sparql
# lost_meanings.sparql — 死んだ語彙の墓標一覧(と、その墓の下に眠る事実)
PREFIX r: <http://execphil.example/reification#>
SELECT ?label ?died ?killedBy ?intent WHERE {
  # 1) 語彙としての主張が、あるコミットで retract されている
  ?c r:retracts ?a . ?a r:rawText ?raw .
  FILTER(REGEX(str(?raw), "skos:prefLabel|owl:deprecated"))
  # 2) 同じ label を持つ語彙が HEAD で存在しない(=完全な消滅)
  ?a r:liftsLabel ?label .
  FILTER NOT EXISTS { ?alive r:liftsLabel ?label . ?alive r:reachableFromHead true }
  # 3) 死をもたらしたコミットの意図文(意図が空なら、それは記録された事故である)
  ?c r:intent ?intent .
  BIND(?c AS ?killedBy)
  # 4) 死亡時期
  ?c <http://www.w3.org/ns/prov#wasGeneratedAtTime> ?died .
}
ORDER BY ?died
# 意図文の空白列が最重要の出力である。
# 「なぜ消したのか」が空の死は、追跡可能な脱知識化のうち最も深刻な型である。
# 事故死の数は、2.6 の承認フローの健全性の一次指標になる。
```

この照会が組織に対して持つ意味を、あえて硬く言い切っておこう。**失われた意味の復元が不能な組織は、同じ失敗の履歴を持たない組織である。** 失敗の履歴を持たない組織は、失敗を学習ではなく記憶喪失として反復する。墓標を持つことは、失われた知識を復活させることではない——1.6 で見たように、暗黙知は復活しない。墓標がやるのは、喪の作業の材料を提供することだけである。喪を経ない組織改造は、2.2 の否定を含まない同一化——抹消——である。

### 実行練習

1. `git_history_to_rdf.py` を自分のリポジトリの用語ファイル（README の用語集セクションでも可）に適用し、生成 turtle の triple 数を git のコミット数と比ベよ。行数差分が大きいコミットと、意味の死（retract）が起きたコミットは一致するか。一致しないコミットの種類を分類せよ。
2. `lost_meanings.sparql` を Neo4j 版（`parent*` 経路）に書き換え、`:intent` が空文字の retract を集計せよ。「意図なき変更」の割合を1か月監視し、承認フロー導入の前後で変化を見る実験計画を1ページで書け（→2.6 と接続）。
3. 同じ RDF コミットツリー上で、HEAD を2つに分岐させて衝突する `exactMatch` を両側に追加し、衝突を検出するクエリを書け。衝突を「マージコミットで統合」せず「両側を立てたまま新コミットで裁定」する設計が 2.2 の Aufheben に対応することを、あなたのクエリの出力例で示せ。
